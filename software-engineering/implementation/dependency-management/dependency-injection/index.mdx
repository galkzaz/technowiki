**Dependency Injection** is a design technique where an object receives the things it depends on from the outside instead of creating them itself.

A **dependency** is simply another object or service a class needs to do its work.


## Problem/Solution
Hardcoded dependencies create tight coupling.

Many classes depend on one or more underlying resources. For example, a spell
checker depends on a dictionary. It is not uncommon to see such classes imple-
mented as static utility classes (link to static utility class):
```java
// Inappropriate use of static utility - inflexible & untestable!
public class SpellChecker {
    private static final Lexicon dictionary = ...;
    private SpellChecker() {} // Noninstantiable
    public static boolean isValid(String word) { ... }
    public static List<String> suggestions(String typo) { ... }
}
```
Problem: `SpellChecker` permanently tied to one dictionary, This creates hardcoded dependency.

Similarly, it’s not uncommon to see them implemented as singletons (link to singletons):
// Inappropriate use of singleton - inflexible & untestable!
```java
public class SpellChecker {
    private final Lexicon dictionary = ...;
    private SpellChecker(...) {}
    public static INSTANCE = new SpellChecker(...);
    public boolean isValid(String word) { ... }
    public List<String> suggestions(String typo) { ... }
}
```
Singleton Version Is Also Bad
```
public static INSTANCE = new SpellChecker(...);
```
Still: One global fixed dependency

Singleton changes lifetime management, but not coupling.

The problem remains:
- resource is internally chosen
- implementation fixed globally

Neither of these approaches is satisfactory, because 
- they assume that there is
only one dictionary worth using. In practice, each language has its own dictionary,
and special dictionaries are used for special vocabularies. 
- Also, it may be
desirable to use a special dictionary for testing. 
- It is wishful thinking to assume
that a single dictionary will suffice for all time

Suppose you need:
| Situation     | Needed Dictionary    |
| ------------- | -------------------- |
| English       | English dictionary   |
| Arabic        | Arabic dictionary    |
| Medical terms | Medical dictionary   |
| Testing       | Fake test dictionary |

The static design cannot adapt easily.

The Main Architectural Problem is that The class controls:
- dependency selection
- dependency creation
- dependency lifetime

instead of focusing only on spell-checking behavior. This violates separation of concerns.

You could try to have `SpellChecker` support multiple dictionaries by 
- making the dictionary field nonfinal and 
- adding a method to change the dictionary in an existing spell checker. 

```java
private static Lexicon dictionary;

public static void setDictionary(Lexicon d) {
    dictionary = d;
}
```
but this would be awkward, error-prone, and unworkable in a concurrent setting. 

This introduces major problems:

**A. Global Mutable State**

Now the entire application shares mutable state.

One component can unexpectedly affect another.

**B. Thread Safety Problems**

Imagine:
```
Thread A changes dictionary
Thread B simultaneously uses spell checker
```
Possible inconsistent behavior.

Concurrent systems become dangerous.

**C. Testing Problems**

Tests interfere with each other.

Example:
```
Test 1 sets English dictionary
Test 2 sets Arabic dictionary
```
Parallel tests break unpredictably.

**D. Hidden Runtime Behavior**

Behavior changes dynamically through global mutation.

Harder to reason about.

**Static utility classes and singletons are inappropriate for classes whose behavior is parameterized by an underlying resource**

**Classes whose behavior depends on external resources should not hardcode those resources internally.**

In the example:

private static final Lexicon dictionary = ...;

the dictionary is the underlying resource.

Examples of underlying resources:

- dictionaries
- databases
- file systems
- APIs
- caches
- configuration
- message brokers
- loggers

These are external collaborators the class depends on.

What is required is the ability to support multiple instances of the class (in our
example, `SpellChecker`), each of which uses the resource desired by the client (in
our example, the dictionary). A simple pattern that satisfies this requirement is to
pass the resource into the constructor when creating a new instance. This is
one form of dependency injection: the dictionary is a dependency of the spell
checker and is injected into the spell checker when it is created
```java
// Dependency injection provides flexibility and testability
public class SpellChecker {
    private final Lexicon dictionary;

    public SpellChecker(Lexicon dictionary) {
        this.dictionary = Objects.requireNonNull(dictionary);
    }

    public boolean isValid(String word) { ... }
    public List<String> suggestions(String typo) { ... }
}
```
Now:
- dependency supplied externally
- immutable after creation
- each instance independent

While our spell checker example had only a single resource (the dictionary), dependency injection works with an
arbitrary number of resources and arbitrary dependency graphs. It preserves
immutability (link to immutability), so multiple clients can share dependent objects (assuming
the clients desire the same underlying resources). 

Dependency injection is equally
applicable to constructors, static factories (link to static factories), and builders (link to static factories)

Without DI, classes often create their own dependencies directly.

Example without DI:

```java
class UserService {

    private EmailService emailService = new EmailService();

    public void registerUser() {
        emailService.sendWelcomeEmail();
    }
}
```

Here:

* `UserService` depends on `EmailService`
* but it also **creates** it

This causes tight coupling.

`UserService` is now strongly tied to:

* a specific implementation
* object creation details
* lifecycle management

This makes testing, replacement, and maintenance harder.


**Solution**

Inject dependencies from outside the class.

Instead of creating dependencies internally, provide them externally.

```java
class UserService {

    private EmailService emailService;

    public UserService(EmailService emailService) {
        this.emailService = emailService;
    }

    public void registerUser() {
        emailService.sendWelcomeEmail();
    }
}
```

Now:

* `UserService` only uses `EmailService`
* someone else creates and provides it

This is dependency injection.

## Key Idea

The class says:

> “I need this dependency”

instead of:

> “I will create this dependency myself”


one of the biggest ideas in modern architecture: Business Objects Should Not Assemble Themselves

Instead: system composition handled externally, This leads directly to:
* IoC containers
* modular systems
* clean architecture
* plugin systems
* enterprise frameworks

## Types of Dependency Injection
### Constructor Injection (Most Recommended)

Dependencies provided through constructor.

```java
class Service {

    private final Repository repository;

    public Service(Repository repository) {
        this.repository = repository;
    }
}
```

Advantages:

* immutable dependencies
* guarantees required dependencies exist
* easier testing
* clearer design

This is generally the preferred approach.


---

**Why Constructor Injection Fits Frameworks Naturally**

Frameworks love constructor injection because dependencies are explicit.

Example:

```java id="gjlwmq"
public Service(Repository repo)
```

Framework can easily inspect constructor and resolve dependencies.

This is why constructor injection became dominant.

### Setter Injection

Dependencies provided through setters.

```java
class Service {

    private Repository repository;

    public void setRepository(Repository repository) {
        this.repository = repository;
    }
}
```

Useful for:

* optional dependencies
* reconfiguration

Drawback:

* object may exist in invalid state temporarily

### Field Injection

Framework injects directly into fields.

```java
class Service {

    @Inject
    private Repository repository;
}
```

Common in frameworks like:

* Spring Framework
* Jakarta CDI

Drawbacks:

* hidden dependencies
* harder testing
* breaks immutability
* harder to reason about

Generally discouraged in modern design.

## Dependency Inversion Principle Connection

DI is strongly related to the SOLID principle:

### Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules.

Both should depend on abstractions.

Example:

```java
interface NotificationService {
    void send();
}
```

```java
class EmailService implements NotificationService {
}
```

```java
class UserService {

    private NotificationService service;

    public UserService(NotificationService service) {
        this.service = service;
    }
}
```

`UserService` depends on abstraction, not implementation.

DI helps implement DIP.

---
Dependency Injection ≠ Dependency Inversion Principle

| Dependency Injection          | Dependency Inversion Principle        |
| ----------------------------- | ------------------------------------- |
| Technique/mechanism           | Design principle                      |
| How dependencies are provided | How dependencies should be structured |
| Operational                   | Architectural                         |
| Can exist without DIP         | DIP often uses DI                     |

## Inversion of Control (IoC)

DI is a form of **Inversion of Control**.

Normally:

* object controls its dependencies

With IoC:

* external system controls dependency wiring

DI is the mechanism that achieves this.

### Manual DI

```java

```

Good for:

* small apps
* learning
* simple systems

---

Frameworks Build on Manual DI, APIs designed for manual dependency injection are trivially adapted, Meaning: **Good DI design is framework-independent.**

Example:

```java id="bjlwmq"
class Service {

    private final Repository repo;

    public Service(Repository repo) {
        this.repo = repo;
    }
}
```

works both:

* manually
* with Spring
* with Guice
* with Dagger

**Why This Matters**

If your code only works because of framework magic: design quality is weaker

Good architecture should remain clean without framework. Framework should assist architecture, not define it.

---

**Manual DI Is the Foundation**

DI frameworks are essentially: automation layers over manual DI

If you understand manual DI deeply:

* frameworks become easy
* annotations make sense
* IoC containers become understandable

Without manual DI knowledge: framework behavior feels magical/confusing.

---

**Important Architectural Principle**

This implies: **Design First, Framework Second**

Bad approach: Design architecture around framework

Better approach: 
- Design clean DI architecture
- Then framework automates wiring

This is a major engineering distinction.

## Charactaistics
1. DI is not limited to one dependency

dependency injection works with an arbitrary number of resource.

```java
class OrderService {

    private final PaymentGateway gateway;
    private final InventoryService inventory;
    private final NotificationService notifications;
    private final Logger logger;

    public OrderService(
        PaymentGateway gateway,
        InventoryService inventory,
        NotificationService notifications,
        Logger logger
    ) {
        this.gateway = gateway;
        this.inventory = inventory;
        this.notifications = notifications;
        this.logger = logger;
    }
}
```
2. Dependencies form a graph

Dependencies can depend on other dependencies, creating a graph.
Example:
```
OrderController
      |
      v
OrderService
   /      \
  v        v
Payment   Inventory
   |
   v
Database
```
Each object depends on others.

DI scales to entire object networks.

**Without DI**

Each class manually creates its own dependencies:

nested object creation chaos

Example:
```java
new OrderService(
    new PaymentService(
        new Database()
    )
)
```
Hard to manage in large systems.

**With DI Containers**

Frameworks like: Spring Framework, Google Guice, automatically build the dependency graph.

DI scales from: one object + one dependency

to entire enterprise dependency graphs, while preserving:

* immutability
* configurability
* testability
* modularity
* resource sharing

That scalability is why DI became foundational in modern software engineering.

3. It preserves immutability 

Example:

```java
private final Lexicon dictionary;
```
Dependency never changes after construction. This creates immutable object state.

**Why Immutability Matters**

Immutable objects are:
| Benefit                | Explanation                         |
| ---------------------- | ----------------------------------- |
| Thread-safe            | No changing shared state            |
| Predictable            | Behavior stable after construction  |
| Easier to reason about | No hidden mutation                  |
| Easier to test         | Stable state                        |
| Safer                  | Prevents accidental reconfiguration |

DI Encourages Constructor Injection, Constructor injection naturally supports immutability.
```java
public SpellChecker(Lexicon dictionary)
```
Combined with:
```java
private final Lexicon dictionary;
```
This creates stable object composition.

4. Multiple clients can share dependent objects

It preserves immutability (link to immutability), so multiple clients can share dependent objects (assuming
the clients desire the same underlying resources).

This refers to shared dependencies.

Example:

```java id="4dmg6f"
Lexicon english = new EnglishLexicon();

SpellChecker sc1 = new SpellChecker(english);
SpellChecker sc2 = new SpellChecker(english);
SpellChecker sc3 = new SpellChecker(english);
```

All share same immutable resource safely.

**Why Sharing Matters**

Shared immutable dependencies improve:

| Area        | Benefit                       |
| ----------- | ----------------------------- |
| Memory      | Avoid duplicate objects       |
| Performance | Expensive resources reused    |
| Consistency | Shared configuration          |
| Scalability | Efficient resource management |

sometimes clients need different resources.

Example:

```java id="r26r0v"
new SpellChecker(englishDictionary);
new SpellChecker(arabicDictionary);
```

DI supports both:

* shared resources
* customized resources

5. Applicable to constructors, static factories, and builders

DI is not limited to constructors.

**A. Constructor Injection**

Most common.


### SOLID Principles
DI is most strongly connected to SOLID.

#### A. Dependency Inversion Principle (DIP)

This is the primary relationship.

DIP says:

High-level modules should depend on abstractions, not implementations

DI helps achieve this by injecting implementations externally.

Without DI:

```java id="t4mzv4"
class UserService {
    private EmailService service = new EmailService();
}
```

High-level logic depends directly on low-level details.

With DI:

```java id="n8y84z"
class UserService {

    private NotificationService service;

    public UserService(NotificationService service) {
        this.service = service;
    }
}
```

Now the service depends on abstraction.

---

#### B. Single Responsibility Principle (SRP)
DI separates: **business logic** from **object construction/wiring**

Without DI: Class responsibilities:
- business logic
- creating dependencies
- configuring dependencies

With DI: Class responsibility:
- only business logic

Construction is delegated elsewhere.

---

#### C. Open/Closed Principle (OCP)
DI makes systems extensible without modifying existing code.

Example:

```java id="32edvv"
interface PaymentProcessor {}
```

New implementations:

```java id="rmd4mu"
class StripeProcessor implements PaymentProcessor {}
class PaypalProcessor implements PaymentProcessor {}
```

`CheckoutService` remains unchanged.

### Design Patterns
DI interacts with many classic design patterns.

#### A. Strategy Pattern

DI commonly injects strategies.



#### B. Factory Pattern
Factories create dependencies.

DI containers are effectively advanced factories.

A useful variant of the pattern is to pass a resource factory to the constructor.
A factory is an object that can be called repeatedly to create instances of a type.
Such factories embody the Factory Method pattern.

Instead of injecting: a ready-made object, you inject: omething that can CREATE objects on demand

This is called: Factory Injection, or Injecting a factory/provider/supplier.

**Regular Dependency Injection**

Normal DI:

```java id="1pmr9y"
class SpellChecker {

    private final Lexicon dictionary;

    public SpellChecker(Lexicon dictionary) {
        this.dictionary = dictionary;
    }
}
```

The dependency already exists.

**Factory Injection**

Now instead inject:

```java id="2mqqha"
Supplier<Lexicon>
```

Example:

```java id="8g2jlwm"
class SpellChecker {

    private final Supplier<Lexicon> dictionaryFactory;

    public SpellChecker(Supplier<Lexicon> dictionaryFactory) {
        this.dictionaryFactory = dictionaryFactory;
    }

    public void check(String word) {
        Lexicon dictionary = dictionaryFactory.get();
    }
}
```

Now the object can create dictionaries dynamically when needed.

Why Inject a Factory Instead of an Instance? Because sometimes you need:

* multiple instances
* lazy creation
* runtime-specific objects
* short-lived objects
* dynamic selection

**Example Problem**

Suppose a game creates many tiles:

```text id="i8vqt9"
Tile1
Tile2
Tile3
...
```

Injecting one Tile object is insufficient. You need a mechanism to produce many tiles.


Java 8 introduced: `The Supplier<T> Interface`, It represents: a function/object that supplies objects of type T on demand.

Definition conceptually:

```java id="xg0t44"
interface Supplier<T> {
    T get();
}
```
Example

```java id="gt5s0v"
Supplier<Tile> factory = () -> new Tile();
```

Usage:

```java id="lpjohd"
Tile tile = factory.get();
```

Each call can create a new object.

For example, here is a method that makes a mosaic using a client-provided factory to produce each tile:
```java
    public Mosaic create(
            Supplier<? extends Tile> tileFactory,
            int numberOfTiles) {
```
The method says: I accept any factory capable of producing Tile objects or subclasses of Tile, This follows the substitution principle.
```java
import java.util.ArrayList;
import java.util.List;
import java.util.function.Supplier;

/*
 * =========================================
 * Tile Abstraction
 * =========================================
 */
interface Tile {
    String render();
}

/*
 * =========================================
 * Concrete Tile Implementations
 * =========================================
 */
class GrassTile implements Tile {

    @Override
    public String render() {
        return "Grass";
    }
}

class WaterTile implements Tile {

    @Override
    public String render() {
        return "Water";
    }
}

class StoneTile implements Tile {

    @Override
    public String render() {
        return "Stone";
    }
}

/*
 * =========================================
 * Mosaic Object
 * =========================================
 */
class Mosaic {

    private final List<Tile> tiles;

    public Mosaic(List<Tile> tiles) {
        this.tiles = tiles;
    }

    public void display() {

        System.out.println("Mosaic:");

        for (Tile tile : tiles) {
            System.out.println("- " + tile.render());
        }

        System.out.println();
    }
}

/*
 * =========================================
 * Mosaic Builder
 *
 * Dependency Injection:
 *     Supplier<? extends Tile> is injected
 *
 * Factory Method:
 *     tileFactory.get() creates Tile objects
 * =========================================
 */
class MosaicBuilder {

    public Mosaic create(
            Supplier<? extends Tile> tileFactory,
            int numberOfTiles) {

        List<Tile> tiles = new ArrayList<>();

        for (int i = 0; i < numberOfTiles; i++) {

            /*
             * Factory Method Call
             */
            Tile tile = tileFactory.get();

            tiles.add(tile);
        }

        return new Mosaic(tiles);
    }
}

/*
 * =========================================
 * Main Application
 * =========================================
 */
public class Main {

    public static void main(String[] args) {

        MosaicBuilder builder = new MosaicBuilder();

        /*
         * =========================================
         * Inject GrassTile Factory
         * =========================================
         */
        Mosaic grassMosaic =
                builder.create(GrassTile::new, 5);

        grassMosaic.display();

        /*
         * =========================================
         * Inject WaterTile Factory
         * =========================================
         */
        Mosaic waterMosaic =
                builder.create(WaterTile::new, 3);

        waterMosaic.display();

        /*
         * =========================================
         * Inject StoneTile Factory
         * =========================================
         */
        Mosaic stoneMosaic =
                builder.create(StoneTile::new, 4);

        stoneMosaic.display();

        /*
         * =========================================
         * Custom Lambda Factory
         * =========================================
         */
        Mosaic customMosaic =
                builder.create(() -> {

                    System.out.println("Creating special tile...");

                    return new GrassTile();

                }, 2);

        customMosaic.display();
    }
}
```

## Relationship Between DIP, IoC, and DI

### Dependency Inversion Principle (DIP)

DIP is an **architectural design principle** from SOLID.

It answers:

> “How should dependencies between modules be structured?”

Core idea: Depend on abstractions, not concrete implementations

Focus:

* dependency direction
* architecture
* coupling
* abstractions/interfaces

---

### Inversion of Control (IoC)

IoC is a **broader design concept/pattern family**.

It answers:

> “Who controls object creation and workflow?”

Traditional control: Application code controls everything

IoC: External framework/container controls parts of the system

Examples of IoC:

* Dependency Injection
* Event systems
* Template Method pattern
* Callbacks
* Plugin architectures

So IoC is a large umbrella concept.

---

### Dependency Injection (DI)

DI is a **specific technique** used to implement IoC.

It answers:

> “How are dependencies provided?”

Instead of:

```java id="z8kmj3"
new EmailService()
```

dependencies are injected externally.

---

### Their Actual Relationship

```text id="3nh89l"
IoC (broad concept)
    └── DI (specific technique)

DIP (architectural principle)
    └── often implemented using DI
```

---

### Important Distinction

#### DIP and IoC are orthogonal concepts

They interact, but one is not contained inside the other.

| Concept | Type                     | Main Focus                      |
| ------- | ------------------------ | ------------------------------- |
| DIP     | Design principle         | Dependency structure            |
| IoC     | Control principle        | Who controls execution/creation |
| DI      | Implementation technique | How dependencies are supplied   |

---

### Example Showing the Difference

**You can use DI without fully applying DIP**

```java id="sz4ggo"
class UserService {

    private EmailService emailService;

    public UserService(EmailService emailService) {
        this.emailService = emailService;
    }
}
```

This uses DI.

But it still depends on concrete `EmailService`.

So DIP is not fully achieved.

---

**DIP with DI**

```java id="ehgo6z"
interface NotificationService {
}
```

```java id="w2o1t6"
class EmailService implements NotificationService {
}
```

```java id="0x9vwq"
class UserService {

    private NotificationService service;

    public UserService(NotificationService service) {
        this.service = service;
    }
}
```

Now:

* DI is used
* DIP is satisfied
* IoC may be involved if container manages wiring

---

**Better Structural View**

```text id="vghr2q"
                 IoC
                  |
         -----------------
         |               |
        DI         Other IoC Forms


                 DIP
                  |
      Often implemented using
                  |
                  DI
```

---

**Why People Confuse Them**

Frameworks like:

* Spring Framework
* ASP.NET Core

often combine:

* IoC containers
* DI mechanisms
* DIP-friendly architecture

So the concepts appear together constantly.

But conceptually they are separate.

```text
Class creates everything it needs
```

```text

```

## Summary
In summary, do not use a singleton or static utility class to implement a class
that depends on one or more underlying resources whose behavior affects that of
the class, and do not have the class create these resources directly. Instead, pass
the resources, or factories to create them, into the constructor (or static factory or
builder). This practice, known as dependency injection, will greatly enhance the
flexibility, reusability, and testability of a class.
