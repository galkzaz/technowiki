**Immutability** is a **class design practice** where an object’s state cannot change after the object is created.

In software engineering, immutability is primarily about:

* **predictability**
* **safety**
* **maintainability**
* **thread-safety**
* **simpler reasoning**
* **reliable state management**


Immutability defines:

* how objects manage state
* whether state can change
* how objects interact safely
* how APIs expose data
* how systems avoid unintended side effects

**Mental Model**

Mutable programming: Same object evolves over time

Immutable programming: Every change creates a new version

## Core Idea

A mutable object changes state:

```java
user.setName("Ali");
```

An immutable object never changes:

```java
User updated = user.withName("Ali");
```

The original object remains unchanged.

## Fundamental Principle

After construction:

```text
Object State = Fixed
```

No field changes.
No internal mutation.
No hidden updates.


## Real-World Analogy

### Mutable Object

A whiteboard:

```text
Erase -> Rewrite -> Modify
```

Same object changes continuously.

---

### Immutable Object

A printed document:

```text
Need changes?
Create new version.
```

Original stays intact forever.


## Characteristics of Immutable Classes

An immutable class usually has:

| Rule                          | Description                      |
| ----------------------------- | -------------------------------- |
| Final state                   | Fields cannot change             |
| No setters                    | No mutation methods              |
| Fully initialized constructor | Complete valid state at creation |
| Defensive copying             | Prevent external mutation        |
| Controlled access             | Avoid exposing mutable internals |
| Stable behavior               | Same input → same output         |


## Basic Immutable Class

### Mutable Version

```java
class User {
    private String name;

    public void setName(String name) {
        this.name = name;
    }
}
```

State changes anytime.

---

### Immutable Version

```java
final class User {

    private final String name;

    public User(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}
```

Properties:

* `final class`
* `final field`
* no setters

---

## Why Immutability Matters

### 1. Predictability

Mutable state creates uncertainty:

```java
process(user);
```

Did `process()` change the user? Unknown.

Immutable objects remove ambiguity:

```java
process(user);
```

User cannot change.

Behavior becomes easier to reason about.

---

### 2. Thread Safety

Mutable shared state causes concurrency problems:

* race conditions
* synchronization issues
* deadlocks
* inconsistent reads

Immutable objects are naturally thread-safe because state never changes.


**Mutable Shared State Problem**

```java
counter++;
```

Multiple threads may corrupt state.

---

**Immutable Alternative**

```java
Counter next = counter.incremented();
```

No shared mutation.

---

### 3. Reduced Side Effects

Mutability creates hidden interactions.

Example:

```java
void applyDiscount(Order order)
```

Did it mutate the order? Maybe.

Immutable design makes effects explicit:

```java
Order discounted = applyDiscount(order);
```

---

### 4. Easier Testing

Immutable objects:

* keep stable state
* avoid hidden mutations
* simplify assertions

Tests become deterministic.

---

### 5. Better Caching

Immutable objects are safe to reuse.

Example:

```java
Map<Key, Value>
```

If keys mutate:

```java
hashCode()
equals()
```

may break. Immutable keys are reliable.

---

### 6. Functional Programming Compatibility

Immutability is foundational for:

* pure functions
* reactive systems
* functional programming
* event sourcing
* stream processing

## Immutability vs Final

Many developers confuse them.

`final` Reference ≠ Immutable Object

```java
final List<String> names = new ArrayList<>();
names.add("A");
```

Reference is fixed. Object still mutable.

**Truly Immutable**

```java
List<String> names = List.of("A", "B");
```

No mutation allowed.


## Deep vs Shallow Immutability

### Shallow Immutability

Fields cannot change, but internal objects can.

```java
class User {
    private final Address address;
}
```

If `Address` is mutable:

```java
user.getAddress().setCity("Cairo");
```

Object effectively changed.

---

### Deep Immutability

Everything inside is immutable too.

```text
Immutable Object
 └── Immutable Fields
      └── Immutable Nested Objects
```

## Defensive Copying

Used to protect immutable objects from external mutation.

**Problem**

```java
class User {
    private final List<String> roles;

    public User(List<String> roles) {
        this.roles = roles;
    }
}
```

External code can modify list after construction.

**Safe Version**

```java
class User {

    private final List<String> roles;

    public User(List<String> roles) {
        this.roles = List.copyOf(roles);
    }

    public List<String> getRoles() {
        return roles;
    }
}
```

Now internal state is protected.

## Immutable Object Lifecycle

```text
Create Object
      ↓
Use Object
      ↓
Need Modification?
      ↓
Create New Object
```

Instead of:

```text
Create
Modify
Modify
Modify
```

## Copy-on-Write Pattern

Very common with immutable design.

Example:

```java
User updated = user.withEmail("a@x.com");
```

Internally:

```text
Copy old state
Change one field
Return new object
```

## Builder Pattern + Immutability

Builders help construct complex immutable objects.

**Example**

```java
User user = User.builder()
    .name("Ali")
    .email("a@test.com")
    .build();
```

Final object remains immutable.

## Usage
### Immutability in Domain Modeling

Very useful for:

* value objects
* money
* dates
* identifiers
* configurations
* events

**Example: Money**

Mutable money is dangerous:

```java
price.setAmount(0);
```

Immutable:

```java
Money discounted = price.multiply(0.9);
```

Safer and clearer.

---

### Immutability in Distributed Systems

Critical for:

* event-driven systems
* messaging
* CQRS
* event sourcing
* Kafka-style logs
* snapshots

Events should never change after publication.

---

### Immutability in Reactive Systems

Reactive systems rely heavily on immutable state because:

* async systems share data across threads
* mutable state creates race conditions
* streams become unpredictable

Immutable messages make reactive pipelines safer.

---

### Immutability in Caching

Cached mutable objects are dangerous:

```text
Cache contains object
↓
Some code mutates object
↓
All consumers now see unexpected changes
```

Immutable cached data is safer.

---

### Immutability and Referential Transparency

A core functional programming idea.

Same input always produces same output.

```text
f(x) = same result forever
```

Requires immutable state.

---

## Immutability and Side Effects

Mutation is a side effect.

Immutable design minimizes side effects.

This improves:

* debugging
* reasoning
* concurrency
* reliability

## Performance Trade-Offs

Immutability is not free.

Potential costs:

| Cost               | Explanation                    |
| ------------------ | ------------------------------ |
| More allocations   | New objects created frequently |
| Higher GC pressure | More temporary objects         |
| Copying overhead   | Especially large structures    |

## Structural Sharing

Advanced immutable systems optimize copying.

Used in:

* persistent data structures
* functional languages
* Redux-like state systems

Instead of full copy:

```text
Reuse unchanged parts
Copy only modified parts
```

## When Immutability Is Ideal

Immutability is excellent for:

| Domain                 | Why              |
| ---------------------- | ---------------- |
| Value objects          | Stable identity  |
| Configuration          | Read-only        |
| Events                 | Historical truth |
| DTOs                   | Safe transfer    |
| Multi-threading        | Thread safety    |
| Functional programming | Pure functions   |
| Reactive systems       | Safe async flow  |

## When Mutability May Be Better

Mutability may be preferable for:

| Scenario                      | Reason                 |
| ----------------------------- | ---------------------- |
| Large high-performance loops  | Avoid allocations      |
| Low-level systems             | Memory optimization    |
| Game engines                  | Frequent state updates |
| Real-time systems             | Minimize GC            |
| Temporary internal algorithms | Performance-sensitive  |


## Common Immutable Design Rules

### Java-Oriented Rules

1. Make class `final`

```java
final class User
```
2. Make fields `private final`

```java
private final String name;
```
3. No setters
4. Validate during construction
5. Protect mutable inputs

```java
List.copyOf()
```
6. Never expose mutable internals

## Common Mistakes

### Returning Mutable Internal State

Bad:

```java
return roles;
```

If mutable.

---

### Assuming `final` Means Immutable

Wrong assumption.

---

### Mutable Nested Objects

Outer object appears immutable but isn't.

---

### Hidden Mutation

Caching internal mutable state unsafely.

## Summary

Immutability is a class design approach where object state cannot change after creation.

It improves:

* predictability
* thread safety
* reliability
* maintainability
* testing
* concurrency safety

Core idea: Do not modify existing state. Create new state instead.

It is foundational in:

* modern concurrency
* reactive systems
* functional programming
* distributed systems
* event-driven architectures
* reliable software design
