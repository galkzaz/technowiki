Reactive programming is a **programming model for handling asynchronous data streams and events** in a way that is:

* non-blocking
* event-driven
* composable
* responsive under concurrency

In concurrency terms, reactive programming is mainly about:

> **How multiple asynchronous activities coordinate and propagate data without blocking threads.**

## Core Idea

Traditional concurrent programming often asks:

* “Which thread executes this code?”
* “How do I synchronize shared state?”
* “How do I avoid race conditions?”

Reactive programming shifts the focus toward:

* “How does data flow through the system?”
* “What happens when new events arrive?”
* “How can operations react asynchronously without waiting?”

## Mental Model

Instead of:

```text
call function → wait → get result
```

Reactive programming works like:

```text
subscribe → data arrives over time → react to it
```

## Reactive Programming vs Traditional Blocking Concurrency

### Traditional Blocking Model

```text
Request Thread
    |
    |---- wait for DB
    |
    |---- wait for API
    |
    |---- wait for file
```

The thread is occupied while waiting.

---

### Reactive Model

```text
Request arrives
    |
    |---- register callbacks/pipeline
    |
    |---- thread released
    |
Data becomes available later
    |
    |---- continuation executes
```

Threads are not held during waiting periods.

---

## Relationship to Concurrency

Reactive programming is strongly connected to concurrency because it helps systems:

* handle many tasks simultaneously
* maximize CPU utilization
* minimize blocked threads
* coordinate asynchronous operations

It is especially useful for:

* I/O-bound systems
* distributed systems
* real-time event processing
* high-throughput servers

---

## Core Concurrency Concepts in Reactive Programming

---

### 1. Asynchronous Execution

Reactive systems assume operations complete later.

Example:

```text
Database query
HTTP request
Message queue event
File read
```

Instead of blocking:

```java
String data = api.call(); // waits
```

Reactive:

```java
api.call()
   .subscribe(data -> process(data));
```

Execution continues immediately.

---

### 2. Non-Blocking Execution

Non-blocking means:

> A thread never waits idly for slow operations.

Traditional:

```text
Thread waits for network
```

Reactive:

```text
Thread registers interest
Thread becomes free
OS/framework notifies later
```

This enables very high concurrency with fewer threads.

---

### 3. Event-Driven Coordination

Reactive programming treats everything as events:

* mouse clicks
* HTTP requests
* Kafka messages
* sensor updates
* database changes

The system reacts when events occur.

```text
Event occurs
    ↓
Pipeline executes
    ↓
Result propagated
```

---

### 4. Data Streams

Reactive programming models data as streams.

A stream may produce:

* 1 value
* many values
* infinite values

Example stream:

```text
1 → 2 → 3 → 4 → ...
```

or:

```text
HTTP requests arriving continuously
```

---

### 5. Push-Based Concurrency

Traditional iteration is usually pull-based:

```text
consumer asks for data
```

Reactive is push-based:

```text
producer pushes data to consumers
```

Example:

```text
Kafka topic pushes events
```

instead of:

```text
consumer repeatedly polling manually
```

---

### 6. Backpressure

One of the biggest concurrency problems:

```text
Producer faster than consumer
```

Reactive systems solve this using backpressure.

Backpressure means:

> Consumers control how much data they can handle.

Without backpressure:

```text
Fast producer
    ↓
Memory explosion
    ↓
System crash
```

With backpressure:

```text
Consumer says:
"Send only 100 items now"
```

This is critical in high-concurrency systems.

---

## Reactive Pipeline

A reactive workflow is usually represented as a pipeline.

Example:

```text
Incoming Requests
        ↓
Validation
        ↓
Async Database Call
        ↓
Transform Data
        ↓
Async API Call
        ↓
Send Response
```

Each stage reacts when data becomes available.

---

## Execution Flow Example

### Blocking Version

```java
User user = database.find(id); // thread blocked
Order order = api.fetch(user); // thread blocked
return order;
```

Thread usage:

```text
Thread occupied entire time
```

---

### Reactive Version

```java
database.find(id)
    .flatMap(user -> api.fetch(user))
    .subscribe(order -> send(order));
```

Thread usage:

```text
Thread starts operation
↓
Thread released
↓
Continuation runs later
```

## Reactive Streams Lifecycle

Reactive streams usually follow this flow:

```text
Publisher
    ↓
Subscriber subscribes
    ↓
Subscription created
    ↓
Data emitted asynchronously
    ↓
Completion or error signal
```

## Important Reactive Concepts

### Publisher / Producer

Produces asynchronous data.

Examples:

* Kafka topic
* database query
* HTTP stream

---

### Subscriber / Consumer

Receives data asynchronously.

---

### Operators

Transform streams.

Examples:

* map
* filter
* flatMap
* reduce

Example:

```java
stream
   .filter(x -> x > 10)
   .map(x -> x * 2)
```

---

### Scheduler

Controls execution threads.

Reactive programming abstracts thread management.

Instead of manually doing:

```java
new Thread(...)
```

you declare scheduling behavior.

## Reactive Concurrency Model

Reactive systems often use:

* event loops
* worker pools
* task scheduling
* continuations
* callbacks
* async state machines

instead of: one-thread-per-request

## Thread Usage Comparison

### Traditional Server

```text
10,000 requests
→ possibly 10,000 blocked threads
```

Expensive:

* memory
* context switching
* scheduler overhead

---

### Reactive Server

```text
10,000 requests
→ maybe 8–100 threads
```

because threads are not blocked.

---

## Reactive vs Multithreading

Reactive programming is NOT merely multithreading.

Multithreading focuses on: running code simultaneously

Reactive programming focuses on: coordinating asynchronous flows


Reactive systems may use:

* few threads
* many threads
* thread pools
* event loops

depending on implementation.

## Reactive vs Async/Await

Async/await simplifies asynchronous syntax.

Reactive programming additionally provides:

* streams
* composition
* backpressure
* event pipelines
* continuous data flow

## When It May Not Help

Reactive programming is often unnecessary for:

* simple CRUD apps
* CPU-heavy computation
* small systems
* straightforward synchronous workflows

Reactive code can become:

* harder to debug
* harder to trace
* harder to reason about

---

## Relationship to Reactive Systems

Reactive programming is a programming technique.

Reactive systems are a broader architectural concept emphasizing:

* responsiveness
* resilience
* elasticity
* message-driven communication

Reactive programming is often used to implement reactive systems.

### Traditional Blocking Restaurant

```text
Waiter stands beside customer waiting for kitchen
```

---

### Reactive Restaurant

```text
Waiter takes order
↓
Kitchen works independently
↓
Waiter serves another customer
↓
Kitchen signals when ready
```

Threads behave similarly in reactive systems.

## Key Takeaways

Reactive programming in concurrency is about:

* asynchronous data flow
* non-blocking execution
* event-driven coordination
* stream processing
* efficient thread utilization
* handling massive concurrency with fewer threads

The major shift is:

```text
FROM:
"Execute step-by-step while waiting"

TO:
"React when data/events become available"
```
