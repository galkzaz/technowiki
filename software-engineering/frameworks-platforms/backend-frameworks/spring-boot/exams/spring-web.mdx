## Differences between Spring Web MVC and Spring WebFlux

<QandA>
<Question>

What are the main differences between the older Spring component for developing REST
services, Spring Web MVC, and the new Spring WebFlux?

</Question>
<Answer>

The difference between Spring Web MVC and Spring WebFlux isn’t just “old vs new”—it’s a fundamentally different programming model and runtime philosophy.

1. Programming Model

Spring Web MVC
- Imperative (blocking) 
- One request → one thread → waits for I/O 
```java
@GetMapping("/users")
public List<User> getUsers() {
    return userService.getAllUsers(); // blocking
}
```
Spring WebFlux
- Reactive (non-blocking) 
- Uses async streams (Mono, Flux) 
```java
@GetMapping("/users")
public Flux<User> getUsers() {
    return userService.getAllUsers(); // non-blocking
}
```
2. Threading & Scalability

Spring Web MVC
- Uses thread-per-request model 
- Based on Servlet API (e.g., Apache Tomcat) 
- Threads get blocked during I/O (DB calls, HTTP calls) 

👉 Problem:
- High concurrency = many threads = memory overhead 

Spring WebFlux
- Uses event-loop model (like Node.js) 
- Runs on servers like: 
    - Netty 
    - or Servlet 3.1+ containers 

👉 Benefit:
- Handles many requests with fewer threads 
- Ideal for high-concurrency, I/O-heavy systems 

3. Blocking vs Non-Blocking

| Feature      | Spring Web MVC | Spring WebFlux       |
| ------------ | -------------- | -------------------- |
| Execution    | Blocking       | Non-blocking         |
| I/O Calls    | Thread waits   | Thread released      |
| Backpressure | ❌              | ✅ (Reactive Streams) |


4. API Style

Web MVC
- Uses standard Java types: 
    - `List`, `Object`, etc. 
WebFlux
- Uses reactive types: 
    - `Mono<T>` → 0 or 1 result 
    - `Flux<T>` → stream of many results 

**5. Performance Characteristics**

Web MVC
- Better for: 
    - CPU-bound tasks 
    - Simple CRUD apps 
    - Traditional architectures 

WebFlux
- Better for: 
    - I/O-heavy systems (API gateways, streaming) 
    - Real-time apps 
    - Microservices with many external calls 

6. Learning Curve & Complexity

Web MVC
- Easier to understand 
- Straightforward debugging 

WebFlux
- Requires understanding: 
    - Reactive programming 
    - Streams 
    - Backpressure 
- Harder debugging (async flow) 

7. Ecosystem Compatibility

Web MVC
- Works with most libraries (blocking) 
- Mature ecosystem 

WebFlux
- Needs reactive-compatible libraries 
    - e.g., reactive DB drivers 
- Mixing blocking code = kills benefits 

The Real Difference
- Spring Web MVC = “Do this, wait for result” 
- Spring WebFlux = “Start this, continue when result arrives” 

**When to Use What**

Choose Web MVC if:
- Your app is simple CRUD 
- You use blocking DB drivers (JPA/Hibernate) 
- You don’t need extreme scalability 

Choose WebFlux if:
- High concurrency (thousands of users) 
- Many external API calls 
- Streaming / real-time data 
- You can stay fully reactive 

**Key Takeaway**

WebFlux is not a replacement for Web MVC—it’s an alternative for different problems.

</Answer>
</QandA>

<QandA>
<Question>

How does springdoc-openapi help a developer document REST APIs?

</Question>
<Answer>

springdoc-openapi helps developers document REST APIs by automatically generating OpenAPI (Swagger) documentation directly from your Spring Boot code—so you don’t have to manually write and maintain API docs.
Here’s how it actually helps in practice:

**1. Auto-generates API documentation from code**

When you use Spring Boot with `springdoc-openapi`:
- It scans your controllers (`@RestController`)
- Detects endpoints (`@GetMapping`, `@PostMapping`, etc.)
- Extracts:
    - Paths
    - HTTP methods
    - Parameters
    - Request/response models

👉 **Result:** A full OpenAPI Specification JSON is generated automatically.

**2. Provides interactive API UI (Swagger UI)**

`springdoc` integrates with Swagger UI out of the box.
- You get a web interface (usually at `/swagger-ui.html`)
- You can:
    - Explore endpoints
    - See request/response schemas
    - Execute API calls directly from the browser

👉 **Extremely useful for:**
- Frontend developers
- QA testers
- API consumers

**3. Reduces manual documentation effort**

**Without springdoc:**
- You’d manually write YAML/JSON OpenAPI specs
- Keep them in sync with code (error-prone)

**With springdoc:**
- Docs stay in sync automatically
- Changes in code = updated documentation

**4. Supports annotations for richer documentation**

You can enhance docs using OpenAPI annotations:
From Swagger Core:

```java
@Operation(summary = "Get user by ID")
@ApiResponse(responseCode = "200", description = "User found")
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) { ... }
```

👉 This allows:
- Better descriptions
- Custom response codes
- Examples
- Security documentation

**5. Documents request/response models automatically**

springdoc:
- Reads your DTOs (POJOs)
- Generates schema definitions

Example:
```java
class User {
    private Long id;
    private String name;
}
```
👉 Automatically becomes a schema in OpenAPI.

**6. Supports advanced features**

- Grouping APIs (e.g., public vs admin)
- Security schemes (JWT, OAuth2)
- Versioning
- Kotlin, WebFlux support

**7. Works with minimal configuration**

Typical setup:
```xml
<dependency>
  <groupId>org.springdoc</groupId>
  <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
</dependency>
```
👉 No complex config required—just add dependency and run.

**Bottom line**

springdoc-openapi acts as a bridge between your Spring Boot code and OpenAPI documentation, giving you:
- ✅ Automatic API documentation
- ✅ Interactive testing UI
- ✅ Always up-to-date specs
- ✅ Minimal setup


</Answer>
</QandA>

<Question>

What are the @PathVariable and @RequestParam annotations used for?

</Question>
<Answer>

In Spring Web (Spring MVC / Spring Boot), both @PathVariable and @RequestParam are used to extract data from an HTTP request—but they come from different parts of the URL and serve different design purposes.

**@PathVariable**

✔ Purpose
Used to extract values from the URI path itself.
✔ Example URL
GET /users/42
✔ Controller
```java
@GetMapping("/users/{id}")
public User getUser(@PathVariable("id") Long id) {
    return userService.findById(id);
}
```
✔ Key Idea
- The value (42) is part of the resource path 
- Represents a specific resource identifier 
✔ When to use
- Identifying a resource 
- RESTful APIs (resource-based URLs) 

**@RequestParam**

✔ Purpose
Used to extract values from the query string parameters
✔ Example URL
GET /users?age=25&active=true
```java
@GetMapping("/users
✔ Controller
@GetMapping("/users")
public List<User> getUsers(
    @RequestParam int age,
    @RequestParam boolean active
) {
    return userService.findByAgeAndActive(age, active);
}
```
✔ Key Idea
- Values come after ? in the URL 
- Used for filtering, sorting, pagination, optional inputs 

Core Differences
| Aspect     | `@PathVariable`   | `@RequestParam`                        |
| ---------- | ----------------- | -------------------------------------- |
| Source     | URL path          | Query string                           |
| Example    | `/users/42`       | `/users?id=42`                         |
| Purpose    | Identify resource | Filter / modify request                |
| Required   | Usually required  | Optional by default (`required=false`) |
| REST style | More RESTful      | Less RESTful                           |

</Answer>

## Error handling
<QandA>
<Question>

How can you separate protocol-specific error handling from the business logic in an API implementation class?

</Question>
<Answer>

You don’t get clean APIs by mixing HTTP concerns (status codes, headers, request formats) directly into your service logic. That leads to tight coupling and makes your business layer unusable outside HTTP (e.g., messaging, batch jobs). The goal is simple: keep business logic protocol-agnostic and push HTTP-specific behavior to the edges.
Here are the main ways to do that in Spring:

**1. Throw Domain Exceptions from the Business Layer**

Your service layer should not know anything about HTTP.
✔ Business layer
```java
@GetMapping("/users
public class UserService {
    public User findById(Long id) {
        return userRepository.findById(id)
            .orElseThrow(() -> new UserNotFoundException(id));
    }
}
```
- No ResponseEntity 
- No HTTP status codes 
- Only domain-specific exceptions 

**2. Map Exceptions to HTTP in a Global Handler**

Use @ControllerAdvice to translate exceptions → HTTP responses.
✔ Exception handler
```java
@GetMapping("/users
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<String> handleNotFound(UserNotFoundException ex) {
        return ResponseEntity.status(404).body(ex.getMessage());
    }
    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handleGeneric(Exception ex) {
        return ResponseEntity.status(500).body("Internal error");
    }
}
```
Now:
- Business layer throws UserNotFoundException 
- Web layer converts it into 404 Not Found

**3. Keep Controllers Thin**

Controllers should just:
- Accept HTTP input 
- Call service 
- Return result 
✔ Controller
```java
@GetMapping("/users
@RestController
@RequestMapping("/users")
public class UserController {
    private final UserService userService;
    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userService.findById(id);
    }
}
```
Notice:
- No try/catch 
- No HTTP error logic 
- Clean and readable 

**4. (Optional) Use Problem Details (Better API Design)**

Spring supports RFC 7807 (ProblemDetail) for structured errors.
```java
@GetMapping("/users
@ExceptionHandler(UserNotFoundException.class)
public ProblemDetail handleNotFound(UserNotFoundException ex) {
    ProblemDetail problem = ProblemDetail.forStatus(404);
    problem.setDetail(ex.getMessage());
    return problem;
}
```
This gives consistent API error responses.


</Answer>
