Spring Cloud Stream is a framework from the Spring ecosystem that helps you build event-driven microservices by abstracting away the complexity of messaging systems like Apache Kafka or RabbitMQ.

Spring Cloud Stream provides a streaming abstraction over messaging, based on the publish and subscribe
integration pattern. 

Spring Cloud Stream is based on the publish and subscribe pattern, where a publisher publishes
messages to topics and subscribers subscribe to topics they are interested in receiving messages from.

**Spring Cloud Stream**, built on top of **Spring Cloud Function**, provides you with
all the necessary plumbing to integrate your functions with external messaging
systems like RabbitMQ or Kafka.

Spring Cloud Stream is a framework for building scalable, event-driven, and
streaming applications. It’s built on top of Spring Integration, which offers the communication layer with message brokers; Spring Boot, which provides auto-configuration for the middleware integration; and Spring Cloud Function, which produces,
processes, and consumes events. 

Spring Cloud Stream relies on the native features of
each message broker, but it also provides an abstraction to ensure a seamless experience independently of the underlying middleware. For example, features like consumer groups and partitions (native in Apache Kafka) are not present in RabbitMQ,
but you can still use them thanks to the framework providing them for you.

The framework supports integrations with RabbitMQ, Apache Kafka, Kafka Streams,
and Amazon Kinesis. There are also integrations maintained by partners for Google
PubSub, Solace PubSub+, Azure Event Hubs, and Apache RocketMQ.

## The Idea

Instead of writing low-level code to connect to Kafka or RabbitMQ, Spring Cloud Stream lets you:
- Focus on business logic (produce / process / consume data)
- While it handles communication, serialization, routing, and integration

Spring Cloud Stream lets you build event-driven microservices by writing simple functions, while it handles all messaging infrastructure behind the scenes.

## How It Works

At a high level, it sits between your application and the messaging system:
```
Your Code  ⇄  Spring Cloud Stream  ⇄  Kafka / RabbitMQ
```
You don’t deal directly with topics, queues, or brokers — the framework abstracts them.

## Core Concepts
Spring Cloud Stream is built around a set of core abstractions that simplify interaction with messaging systems:
- **Message**: → The data being sent (payload + headers), A standardized data structure used to represent the data exchanged between producers and consumers through the messaging system. 
- **Publisher (Supplier)**: → Produces messages, A component responsible for sending messages to the messaging system via an output destination. 
- **Subscriber (Consumer)**: → Consumes messages, A component that receives messages from the messaging system via an input destination. 
- **Destination**: → Logical name for a topic/queue, A logical abstraction representing the communication channel with the messaging system. Publishers send messages to output destinations, while subscribers receive messages from input destinations. These destinations are mapped by binders to physical entities such as queues or topics. 
- **Binder (Destination Binder)**: → Connects your app to Kafka/RabbitMQ, A component that provides integration with external messaging systems (e.g., Kafka or RabbitMQ). It abstracts the underlying implementation, similar to how a JDBC driver works for databases. 
- **Destination Binding**: → Links your code to the destination, The bridge that connects application-defined producers and consumers to external messaging system entities (such as queues and topics) through the binder.

!(Spring Cloud Stream core concepts)[/docs/assets/software-engineering/frameworks-platforms/backend-frameworks/spring-boot/spring-cloud/spring-cloud-stream/core-concepts.png]
All of these are handled by the framework itself. The core of your application,
the business logic, is not aware of the external messaging system. Destination binders
are responsible for letting the application communicate with the external message
brokers, including any vendor-specific concerns. The bindings are auto-configured by
the framework, but you can still provide your own configuration to adapt them to your needs.

The actual messaging system to be used is determined at runtime, depending on what is found
on the classpath. Spring Cloud Stream comes with opinionated conventions on how to handle
messaging. These conventions can be overridden by specifying a configuration for messaging
features such as consumer groups, partitioning, persistence, durability, and error handling; for
example, retries and dead letter queue handling.

Once you implement your functions, you don’t have to make any changes to
your code. You only need to add a dependency on Spring Cloud Stream and
configure it to adapt to your needs.

In Spring Cloud Stream, destination binders provide integration with external
messaging systems.

In Spring Cloud Stream, destination bindings (input and output) bridge the
producers and consumers in your applications with exchanges and queues in a
message broker like RabbitMQ.

Functions and consumers are activated automatically when new messages arrive. Suppliers need to be explicitly activated, such as by explicitly sending a message
to a destination binding.

## Example Flow

3. Binder maps it to the actual system 
4. Consumer receives and processes it

## Programming Model (Modern Style)
The programming model is based on a functional paradigm,
where functions implementing one of the functional interfaces (Supplier, Function, or Consumer)
in the java.util.function package can be chained together to perform decoupled event-based
processing. To trigger such functional-based processing externally, from non-functional code,
the StreamBridge helper class can be used.
```java
@Bean
public Supplier<String> supplier() {
    return () -> "Hello";
}
@Bean
public Consumer<String> consumer() {
    return message -> System.out.println(message);
}
@Bean
public Function<String, String> processor() {
    return value -> value.toUpperCase();
}
```
- Supplier → sends data 
- Consumer → receives data 
- Function → transforms data

To tie the various functions together, we use configuration. 

This programming model can be used independently of the messaging system used, for example, RabbitMQ or Apache Kafka!
## Sending and Receiving messages
Spring Cloud Stream comes with two programming models: one older and nowadays deprecated model based on the use of annotations (for example, `@EnableBinding`, `@Output`, and `@StreamListener`) and one newer model based on writing functions. 
## Implementing event producers
Suppliers act as message sources in Spring Cloud Stream. They are responsible for producing messages, typically in response to specific events or triggers.

Unlike functions and consumers, suppliers are not invoked automatically by incoming messages. Instead, they must be explicitly activated, meaning they only produce messages when triggered (e.g., via polling, scheduled execution, or manual invocation).

Spring Cloud Stream provides multiple ways to define and configure suppliers, allowing them to support different use cases such as event-driven publishing, periodic message generation, or integration with external systems.

!(Spring Cloud Stream suppliers diagram)[/docs/assets/software-engineering/frameworks-platforms/backend-frameworks/spring-boot/spring-cloud/spring-cloud-stream/core-concepts.png]

To implement a publisher, we only need to implement the `java.util.function`.Supplier functional interface as a Spring bean. For example, the following is a publisher that publishes messages as a string:
```java
@Bean
public Supplier<String> myPublisher() {
    return () -> new Date().toString();
}
```
It is also possible to define a Spring bean that processes messages, meaning that it both consumes
and publishes messages. This can be done by implementing the java.util.function.Function
functional interface – for example, a Spring bean that consumes incoming messages and publishes
a new message after some processing (both messages are strings in this example):
```java
@Bean
public Function<String, String> myProcessor() {
    return s -> "ML PROCESSED: " + s;
}
```
### Supplier Activation
A supplier is triggered by Spring Cloud Stream by default every second, so we could expect output
like the following if we start a Spring Boot application including the functions and configuration
described previously:
```
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:30 CET 2021
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:31 CET 2021
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:32 CET 2021
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:33 CET 2021
```
In cases where the supplier should be triggered by an external event instead of using a timer, the
StreamBridge helper class can be used. For example, if a message should be published to the
processor when a REST API, `sampleCreateAPI`, is called, the code could look like the following:
```java
@Autowired
private StreamBridge streamBridge; 

@PostMapping
void sampleCreateAPI(@RequestBody String body) {
    streamBridge.send("myProcessor-in-0", body);
}
```
The `StreamBridge` helper class is used to trigger the processing. It will publish a message on a topic. 

## Implementing event consumers
A subscriber is implemented as a Spring bean implementing the `java.util.function.Consumer`
functional interface. For example, the following is a subscriber that consumes messages as strings:
```java
@Bean
public Consumer<String> mySubscriber() {
    return s -> System.out.println("ML RECEIVED: " + s);
}
```

To make Spring Cloud Stream aware of these functions, we need to declare them using the `spring.cloud.function.definition` configuration property. For example, for the three functions defined
previously, this would look as follows:
```yml
spring.cloud.function:
  definition: myPublisher;myProcessor;mySubscriber
```
Finally, we need to tell Spring Cloud Stream what destination to use for each function. To connect our three functions so that our processor consumes messages from our publisher and our subscriber consumes messages from the processor, we can supply the following configuration:
```yml
spring.cloud.stream.bindings:
  myPublisher-out-0:
    destination: myProcessor-in
  myProcessor-in-0:
    destination: myProcessor-in
  myProcessor-out-0:
    destination: myProcessor-out
  mySubscriber-in-0:
    destination: myProcessor-out
```
This will result in the following message flow:
```
myPublisher → myProcessor → mySubscriber
```

## Consumer groups
if we scale up the number of instances of a message consumer, for example,
if we start two instances of the product microservice, both instances of the product microservice
will consume the same messages, This could result in one message being processed two times, potentially leading to duplicates
or other undesired inconsistencies in the database. Therefore, we only want one instance per
consumer to process each message. This can be solved by introducing a consumer group, In Spring Cloud Stream, a consumer group can be configured on the consumer side. For example,
for the product microservice, it will look like this:
```yml
spring.cloud.stream:
  defaultBinder: rabbit
  default.contentType: application/json
  bindings.messageProcessor-in-0:
    destination: products
    group: productsGroup
```
From this configuration:
- Spring Cloud Stream applies, by default, a naming convention for binding a configuration to a function. For messages sent to a function, the binding name is `<functionName>-in-<index>`:
    - functionName is the name of the function, which is `messageProcessor`.
    - `index` is set to `0`, unless the function requires multiple input or output arguments. We will not use multi-argument functions, so index will always be set to 0 in our examples.
    - For outgoing messages, the binding name convention is `<functionName>-out-<index>`.
- The `destination` property specifies the name of the topic that messages will be consumed
from, which is products in this case.
- The `group` property specifies what consumer group to add instances of the product microservice to, which is `productsGroup` in this example. This means that messages sent to the products topic will only be delivered by Spring Cloud Stream to one of the instances of the product microservice.

## Guaranteed Order and Partitions

**Guaranteed ordering** and **partitioning** are closely related concepts in event-driven systems and messaging platforms such as Spring Cloud Stream and Apache Kafka.

If the business logic requires that messages are consumed and processed in the same order as they
were sent, we cannot use multiple instances per consumer to increase processing performance;
for example, we cannot use consumer groups. This might, in some cases, lead to an unacceptable
latency in the processing of incoming messages.

We can use **partitions** to ensure that messages are delivered in the same order as they were sent
but without losing performance and scalability.

### 1. Why Ordering is a Problem

Imagine an Order Service publishes these events:

```text
OrderCreated(orderId=100)
OrderPaid(orderId=100)
OrderShipped(orderId=100)
```

Consumers expect:

```text
Created → Paid → Shipped
```

But in distributed systems:

* Multiple producer instances may exist
* Multiple consumer instances may exist
* Messages may be processed concurrently
* Different brokers may route messages differently

Without special handling, consumers might receive:

```text
Paid
Created
Shipped
```

or

```text
Created
Shipped
Paid
```

which can corrupt business state.

---

### 2. What Does Guaranteed Order Mean?

Guaranteed ordering means:

> Messages that belong to the same business entity are always processed in the exact order they were produced.

Example:

For Order #100:

```text
Created
Paid
Shipped
```

must always arrive in that order.

For Order #200:

```text
Created
Paid
```

must also arrive in order.

However:

```text
Order100 Created
Order200 Created
Order100 Paid
Order200 Paid
```

may be interleaved.

Ordering is usually guaranteed **per key**, not globally.

---

### 3. How Kafka Provides Ordering

Kafka guarantees order only **inside a partition**.

Suppose a topic:

```text
orders
```

has:

```text
Partition 0
Partition 1
Partition 2
```

Messages inside a partition are ordered:

```text
Partition 0

Offset 0 -> Created(100)
Offset 1 -> Paid(100)
Offset 2 -> Shipped(100)
```

Kafka guarantees consumers read:

```text
Created
Paid
Shipped
```

in that order.

---

### 4. What is Partitioning?

Partitioning means dividing a topic into multiple ordered streams.

Example:

```text
Orders Topic

Partition 0
Partition 1
Partition 2
```

Visualized:

```text
Orders Topic
│
├── Partition 0
├── Partition 1
└── Partition 2
```

Benefits:

* Scalability
* Parallel processing
* High throughput
* Ordering within each partition

---

### 5. How Messages Are Assigned to Partitions

A partition key is chosen.

Example:

```java
orderId
```

Kafka calculates:

```text
hash(orderId) % numberOfPartitions
```

Suppose:

```text
hash(100) % 3 = 0
hash(200) % 3 = 1
```

Result:

```text
Order100 -> Partition 0
Order200 -> Partition 1
```

All events for Order100 go to the same partition.

---

### 6. Why Partitioning Enables Ordering

Suppose:

```text
Order100 Created
Order100 Paid
Order100 Shipped
```

All use key:

```text
100
```

Kafka sends all of them to:

```text
Partition 0
```

Partition 0:

```text
Offset 0 Created
Offset 1 Paid
Offset 2 Shipped
```

Order is preserved.

If events were spread across partitions:

```text
Created -> P0
Paid -> P1
Shipped -> P2
```

ordering would be impossible.

---

### 7. Spring Cloud Stream Partitioning

Spring Cloud Stream hides broker-specific APIs.

You tell it:

```text
Use orderId as partition key
```

and it routes messages consistently.

### Important Rule

Ordering in Kafka (and therefore in Spring Cloud Stream) is: **Guaranteed per partition**, not **Guaranteed across the entire topic**

Therefore, To guarantee ordering for a business entity:
1. Choose a partition key
2. Use the same key for all related events
3. Ensure those events always go to the same partition
4. Let a single consumer instance process that partition
```

This pattern is fundamental for event-driven microservices handling orders, payments, accounts, inventory, and other stateful business entities.

## Making messaging resilient to failures
If a consumer fails to process a message, it may be re-queued for the failing consumer until it is
successfully processed. If the content of the message is invalid, also known as a **poisoned message**, the message will block the consumer from processing other messages until it is manually
removed. If the failure is due to a temporary problem, for example, the database can’t be reached
due to a temporary network error, the processing will probably succeed after a number of retries.

It must be possible to specify the number of retries until a message is moved to another storage
for fault analysis and correction. A failing message is typically moved to a dedicated queue called
a **dead-letter queue**. To avoid overloading the infrastructure during temporary failure (for example, a network error), it must be possible to configure how often retries are performed, preferably
with an increasing length of time between each retry.

Spring Cloud Stream uses the retry pattern with an exponential backoff strategy by default, relying on the Spring Retry library for imperative consumers and the `retryWhen()` Reactor operator for reactive consumers, you can customize it via configuration properties.

Spring Cloud Stream defines several defaults to make the interaction more resilient, including error channels and graceful shutdown. You can configure different aspects of message processing, including dead-letter queues, acknowledgment flows, and republishing messages on error.

In Spring Cloud Stream, this can be configured on the consumer side, for example, for the product
microservice, as shown here:
```yml
spring.cloud.stream.bindings.messageProcessor-in-0.consumer:
  maxAttempts: 3
  backOffInitialInterval: 500
  backOffMaxInterval: 1000
  backOffMultiplier: 2.0

spring.cloud.stream.rabbit.bindings.messageProcessor-in-0.consumer:
  autoBindDlq: true
  republishToDlq: true

spring.cloud.stream.kafka.bindings.messageProcessor-in-0.consumer:
  enableDlq: true
```
In the preceding example, we specify that Spring Cloud Stream should perform 3 retries before
placing a message on the dead-letter queue. The first retry will be attempted after 500 ms and
the two other attempts after 1000 ms.
Enabling the use of dead-letter queues is binding-specific; therefore, we have one configuration
for RabbitMQ and one for Kafka.

### Relation between Producers, Consumers and Partitions
The number of **partitions** directly affects how much parallelism Kafka can provide to producers and consumers, but the relationships are different for producers and consumers.

#### 1. Producers vs Partitions

There is **no strict relationship** between the number of producers and the number of partitions.

You can have:

```text
1 Producer  -> 10 Partitions
```

or

```text
100 Producers -> 3 Partitions
```

Both are valid.

Example:

```text
Producer A
Producer B
Producer C

          Orders Topic
    ┌──────┬──────┬──────┐
    │ P0   │ P1   │ P2   │
    └──────┴──────┴──────┘
```

All producers can write to any partition.

Kafka brokers coordinate writes and maintain ordering within each partition.

---

#### 2. Consumers vs Partitions

Here there is a very important relationship.

Within a consumer group:

```text
One partition can be consumed by only one consumer instance at a time.
```

Therefore:

```text
Maximum consumer parallelism
=
Number of partitions
```

---

##### Example 1

Topic:

```text
Orders
P0
P1
P2
```

Consumer Group:

```text
C1
C2
C3
```

Assignment:

```text
P0 -> C1
P1 -> C2
P2 -> C3
```

All consumers are active.

---

##### Example 2

Topic:

```text
Orders
P0
P1
P2
```

Consumer Group:

```text
C1
C2
C3
C4
C5
```

Assignment:

```text
P0 -> C1
P1 -> C2
P2 -> C3

C4 -> idle
C5 -> idle
```

Two consumers do nothing.

Why?

Because only three partitions exist.

---

##### Example 3

Topic:

```text
Orders
P0
P1
P2
P3
P4
P5
```

Consumers:

```text
C1
C2
```

Assignment:

```text
C1 -> P0 P1 P2
C2 -> P3 P4 P5
```

Consumers handle multiple partitions.

---

#### 3. Spring Cloud Stream Example

Suppose:

```yaml
spring:
  cloud:
    stream:
      bindings:
        processOrder-in-0:
          destination: orders
          group: shipping-service
```

Kafka topic:

```text
orders

```

Deployment:

```text
shipping-service-1
shipping-service-2
shipping-service-3
```

Kafka might assign:

```text
P0,P1 -> Instance 1
P2,P3 -> Instance 2
P4,P5 -> Instance 3
```

All three instances process messages concurrently.

---

#### 4. Rule of Thumb

Think of partitions as **units of parallelism**.

```text
Partitions determine:
✓ Consumer scalability
✓ Consumer parallelism
✓ Ordering boundaries
```

Not:

```text
✗ Producer scalability
```

Producers can scale independently.

---

#### 5. Common Sizing Strategy

Suppose you expect:

```text
8 consumer instances
```

in the future.

Create:

```text
12 partitions
```

instead of:

```text
2 partitions
```

Why?

Because later you can run:

```text
Consumer 1
Consumer 2
...
Consumer 8
```

and Kafka can distribute partitions among them.

If you only have:

```text
2 partitions
```

then no matter how many consumer instances you add:

```text
Maximum active consumers = 2
```

---

#### 6. Spring Cloud Stream Partitioning + Scaling

Imagine an e-commerce system:

```text
Orders Topic
12 Partitions
```

Partition key:

```java
orderId
```

Spring Cloud Stream:

```yaml
spring:
  cloud:
    stream:
      bindings:
        orderEvents-out-0:
          producer:
            partition-key-expression: payload.orderId
            partition-count: 12
```

Result:

```text
Order 100 -> P3
Order 200 -> P8
Order 300 -> P1
```

All events for the same order stay together, preserving order, while many consumers can process different orders in parallel.

#### Summary

| Component              | Relationship with Partitions                                  |
| ---------------------- | ------------------------------------------------------------- |
| Producers              | No hard limit; many producers can write to the same partition |
| Consumers (same group) | Maximum active consumers = number of partitions               |
| Ordering               | Guaranteed only within a partition                            |
| Scalability            | Partitions determine consumer parallelism                     |
| Best Practice          | Create enough partitions to support future consumer scaling   |

A useful mental model is:

```text
Partitions = lanes on a highway

Producers = cars entering the highway
Consumers = cars leaving the highway

More cars can enter regardless of lanes.

But the number of lanes determines how much traffic can flow in parallel and how many independent streams of ordered messages exist.
```

```

**Scaling Consumers (Real Behavior)**

Consumer Group
```yml
spring:
  cloud:
    stream:
      bindings:
        paymentConsumer-in-0:
          destination: orders.created
          group: payment-service
```
- Kafka creates a consumer group: payment-service 
- Partitions are distributed across instances: 

```
6 partitions → 3 instances
Instance A → partitions 0,1
Instance B → partitions 2,3
Instance C → partitions 4,5
```
Max parallelism = number of partitions

**Partitioning Strategy**

To ensure ordering (e.g., per customer):
```yml
spring:
  cloud:
    stream:
      bindings:
        orderSupplier-out-0:
          producer:
            partitionKeyExpression: headers['customerId']
            partitionCount: 6
```
Result:
- Same customerId → always same partition 
- Guarantees ordering per customer

**Production Best Practices**

✅ Partitions
- Start with: #partitions = max expected parallel consumers 
- Example: 6–12 (not 1, not 100 blindly) 

✅ Replication
- Minimum: 3 
- Ensures fault tolerance 

✅ Consumer Groups
- One group per service 
- Multiple instances per group for scaling 

✅ Naming Convention
```
<domain>.<event>
orders.created
orders.updated
payments.failed
```
✅ Idempotency
- Consumers must handle duplicates (Kafka = at-least-once) 

**Common Mistakes**
- ❌ Using 1 partition → no scalability 
- ❌ No consumer group → duplicate processing everywhere 
- ❌ Ignoring keys → broken ordering 
- ❌ Too many partitions → operational overhead 

🧠 Final Mental Model

Spring Cloud Stream is just a clean abstraction, But in production, you MUST think in:
- Topics 
- Partitions 
- Consumer Groups 
- Keys (for ordering) 

🧭 One-Line Reality Check
If you don’t design partitions and keys properly, Spring Cloud Stream won’t save you — Kafka behavior still rules everything.
