Spring Cloud Stream is a framework from the Spring ecosystem that helps you build event-driven microservices by abstracting away the complexity of messaging systems like Apache Kafka or RabbitMQ.

Spring Cloud Stream provides a streaming abstraction over messaging, based on the publish and subscribe
integration pattern. 

**Spring Cloud Stream**, built on top of **Spring Cloud Function**, provides you with
all the necessary plumbing to integrate your functions with external messaging
systems like RabbitMQ or Kafka.

Spring Cloud Stream is a framework for building scalable, event-driven, and
streaming applications. It’s built on top of Spring Integration, which offers the communication layer with message brokers; Spring Boot, which provides auto-configuration for the middleware integration; and Spring Cloud Function, which produces,
processes, and consumes events. 

Spring Cloud Stream relies on the native features of
each message broker, but it also provides an abstraction to ensure a seamless experience independently of the underlying middleware. For example, features like consumer groups and partitions (native in Apache Kafka) are not present in RabbitMQ,
but you can still use them thanks to the framework providing them for you.

The framework supports integrations with RabbitMQ, Apache Kafka, Kafka Streams,
and Amazon Kinesis. There are also integrations maintained by partners for Google
PubSub, Solace PubSub+, Azure Event Hubs, and Apache RocketMQ.

## The Idea

Instead of writing low-level code to connect to Kafka or RabbitMQ, Spring Cloud Stream lets you:
- Focus on business logic (produce / process / consume data)
- While it handles communication, serialization, routing, and integration

Spring Cloud Stream lets you build event-driven microservices by writing simple functions, while it handles all messaging infrastructure behind the scenes.

## How It Works

At a high level, it sits between your application and the messaging system:
```
Your Code  ⇄  Spring Cloud Stream  ⇄  Kafka / RabbitMQ
```
You don’t deal directly with topics, queues, or brokers — the framework abstracts them.

## Core Concepts
Spring Cloud Stream is built around a set of core abstractions that simplify interaction with messaging systems:
- **Message**: → The data being sent (payload + headers), A standardized data structure used to represent the data exchanged between producers and consumers through the messaging system. 
- **Publisher (Supplier)**: → Produces messages, A component responsible for sending messages to the messaging system via an output destination. 
- **Subscriber (Consumer)**: → Consumes messages, A component that receives messages from the messaging system via an input destination. 
- **Destination**: → Logical name for a topic/queue, A logical abstraction representing the communication channel with the messaging system. Publishers send messages to output destinations, while subscribers receive messages from input destinations. These destinations are mapped by binders to physical entities such as queues or topics. 
- **Binder (Destination Binder)**: → Connects your app to Kafka/RabbitMQ, A component that provides integration with external messaging systems (e.g., Kafka or RabbitMQ). It abstracts the underlying implementation, similar to how a JDBC driver works for databases. 
- **Destination Binding**: → Links your code to the destination, The bridge that connects application-defined producers and consumers to external messaging system entities (such as queues and topics) through the binder.

!(Spring Cloud Stream core concepts)[/docs/assets/software-engineering/frameworks-platforms/backend-frameworks/spring-boot/spring-cloud/spring-cloud-stream/core-concepts.png]
All of these are handled by the framework itself. The core of your application,
the business logic, is not aware of the external messaging system. Destination binders
are responsible for letting the application communicate with the external message
brokers, including any vendor-specific concerns. The bindings are auto-configured by
the framework, but you can still provide your own configuration to adapt them to your needs.

The actual messaging system to be used is determined at runtime, depending on what is found
on the classpath. Spring Cloud Stream comes with opinionated conventions on how to handle
messaging. These conventions can be overridden by specifying a configuration for messaging
features such as consumer groups, partitioning, persistence, durability, and error handling; for
example, retries and dead letter queue handling.

Once you implement your functions, you don’t have to make any changes to
your code. You only need to add a dependency on Spring Cloud Stream and
configure it to adapt to your needs.

In Spring Cloud Stream, destination binders provide integration with external
messaging systems.

In Spring Cloud Stream, destination bindings (input and output) bridge the
producers and consumers in your applications with exchanges and queues in a
message broker like RabbitMQ.

Functions and consumers are activated automatically when new messages arrive. Suppliers need to be explicitly activated, such as by explicitly sending a message
to a destination binding.

## Example Flow
1. Supplier generates a message 
2. Message goes to a destination (e.g., Kafka topic) 
3. Binder maps it to the actual system 
4. Consumer receives and processes it

## Programming Model (Modern Style)
Spring Cloud Stream uses functional programming:
```java
@Bean
public Supplier<String> supplier() {
    return () -> "Hello";
}
@Bean
public Consumer<String> consumer() {
    return message -> System.out.println(message);
}
@Bean
public Function<String, String> processor() {
    return value -> value.toUpperCase();
}
```
- Supplier → sends data 
- Consumer → receives data 
- Function → transforms data

## Sending and Receiving messages
Spring Cloud Stream comes with two programming models: one older and nowadays deprecated model based on the use of annotations (for example, `@EnableBinding`, `@Output`, and `@StreamListener`) and one newer model based on writing functions. 
## Implementing event producers
Suppliers act as message sources in Spring Cloud Stream. They are responsible for producing messages, typically in response to specific events or triggers.

Unlike functions and consumers, suppliers are not invoked automatically by incoming messages. Instead, they must be explicitly activated, meaning they only produce messages when triggered (e.g., via polling, scheduled execution, or manual invocation).

Spring Cloud Stream provides multiple ways to define and configure suppliers, allowing them to support different use cases such as event-driven publishing, periodic message generation, or integration with external systems.

!(Spring Cloud Stream suppliers diagram)[/docs/assets/software-engineering/frameworks-platforms/backend-frameworks/spring-boot/spring-cloud/spring-cloud-stream/core-concepts.png]

To implement a publisher, we only need to implement the `java.util.function`.Supplier functional interface as a Spring bean. For example, the following is a publisher that publishes messages as a string:
```java
@Bean
public Supplier<String> myPublisher() {
    return () -> new Date().toString();
}
```
It is also possible to define a Spring bean that processes messages, meaning that it both consumes
and publishes messages. This can be done by implementing the java.util.function.Function
functional interface – for example, a Spring bean that consumes incoming messages and publishes
a new message after some processing (both messages are strings in this example):
```java
@Bean
public Function<String, String> myProcessor() {
    return s -> "ML PROCESSED: " + s;
}
```
### Supplier Activation
A supplier is triggered by Spring Cloud Stream by default every second, so we could expect output
like the following if we start a Spring Boot application including the functions and configuration
described previously:
```
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:30 CET 2021
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:31 CET 2021
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:32 CET 2021
ML RECEIVED: ML PROCESSED: Wed Mar 09 16:28:33 CET 2021
```
In cases where the supplier should be triggered by an external event instead of using a timer, the
StreamBridge helper class can be used. For example, if a message should be published to the
processor when a REST API, sampleCreateAPI, is called, the code could look like the following:
```java
@Autowired
private StreamBridge streamBridge; 

@PostMapping
void sampleCreateAPI(@RequestBody String body) {
    streamBridge.send("myProcessor-in-0", body);
}
```
## Implementing event consumers
A subscriber is implemented as a Spring bean implementing the java.util.function.Consumer
functional interface. For example, the following is a subscriber that consumes messages as strings:
```java
@Bean
public Consumer<String> mySubscriber() {
    return s -> System.out.println("ML RECEIVED: " + s);
}
```

To make Spring Cloud Stream aware of these functions, we need to declare them using the `spring.
cloud.function.definition` configuration property. For example, for the three functions defined
previously, this would look as follows:
```yml
spring.cloud.function:
  definition: myPublisher;myProcessor;mySubscriber
```
Finally, we need to tell Spring Cloud Stream what destination to use for each function. To connect our three functions so that our processor consumes messages from our publisher and our subscriber consumes messages from the processor, we can supply the following configuration:
```yml
spring.cloud.stream.bindings:
  myPublisher-out-0:
    destination: myProcessor-in
  myProcessor-in-0:
    destination: myProcessor-in
  myProcessor-out-0:
    destination: myProcessor-out
  mySubscriber-in-0:
    destination: myProcessor-out
```
This will result in the following message flow:
```
myPublisher → myProcessor → mySubscriber
```

## Making messaging resilient to failures
Spring Cloud Stream uses the retry pattern with an exponential backoff strategy by default, relying on the Spring Retry library for imperative consumers and the
retryWhen() Reactor operator for reactive consumers, you can customize it via configuration properties.

Spring Cloud Stream defines several defaults to make the interaction more resilient, including error channels and graceful shutdown. You can configure different
aspects of message processing, including dead-letter queues, acknowledgment flows,
and republishing messages on error.

### Kafka topics + partitions
| Spring Cloud Stream | Kafka (Real World)                    |
| ------------------- | ------------------------------------- |
| Destination         | Topic                                 |
| Binder              | Kafka Client (Producer/Consumer APIs) |
| Binding             | Topic + Consumer Group configuration  |
| Supplier            | Kafka Producer                        |
| Consumer            | Kafka Consumer                        |
| Message             | Kafka Record (key, value, headers)    |

**Production Example Architecture**

Imagine a real system:
```
👉 Order Service → Payment Service → Notification Service
```
Topics
- orders.created
- payments.processed
- notifications.sent

**Spring Cloud Stream Configuration → Kafka Mapping**

Example: Order Service (Producer)
```yml
spring:
  cloud:
    stream:
      bindings:
        orderSupplier-out-0:
          destination: orders.created
      kafka:
        binder:
          brokers: kafka-1:9092,kafka-2:9092,kafka-3:9092
```
What actually happens in Kafka:
- Topic created: orders.created 
- Partitions: (default or configured, e.g., 6) 
- Replication factor: (e.g., 3) 

**Partitions**

Why partitions matter:
- Parallel processing 
- Scalability 
- Ordering guarantees (per partition) 

Example:
```
Topic: orders.created
Partitions: 6
Replication Factor: 3
```
```
Partition 0 → Broker 1
Partition 1 → Broker 2
Partition 2 → Broker 3
...
```

**Scaling Consumers (Real Behavior)**

Consumer Group
```yml
spring:
  cloud:
    stream:
      bindings:
        paymentConsumer-in-0:
          destination: orders.created
          group: payment-service
```
- Kafka creates a consumer group: payment-service 
- Partitions are distributed across instances: 

```
6 partitions → 3 instances
Instance A → partitions 0,1
Instance B → partitions 2,3
Instance C → partitions 4,5
```
Max parallelism = number of partitions

**Partitioning Strategy**

To ensure ordering (e.g., per customer):
```yml
spring:
  cloud:
    stream:
      bindings:
        orderSupplier-out-0:
          producer:
            partitionKeyExpression: headers['customerId']
            partitionCount: 6
```
Result:
- Same customerId → always same partition 
- Guarantees ordering per customer 

**Message Structure in Kafka**
Spring Cloud Stream message:
```json
{
  "payload": {...},
  "headers": {
    "customerId": "123"
  }
}
```
Kafka record:
```
Key   → customerId
Value → payload
Headers → metadata
```

```
[Order Service]

      ↓

      ↓
[Payment Service]
   Consumer + Function
      ↓
payments.processed (6 partitions)
```

**Production Best Practices**

✅ Partitions
- Start with: #partitions = max expected parallel consumers 
- Example: 6–12 (not 1, not 100 blindly) 

✅ Replication
- Minimum: 3 
- Ensures fault tolerance 

✅ Consumer Groups
- One group per service 
- Multiple instances per group for scaling 

✅ Naming Convention
```
<domain>.<event>
orders.created
orders.updated
payments.failed
```
✅ Idempotency
- Consumers must handle duplicates (Kafka = at-least-once) 

**Common Mistakes**
- ❌ Using 1 partition → no scalability 
- ❌ No consumer group → duplicate processing everywhere 
- ❌ Ignoring keys → broken ordering 
- ❌ Too many partitions → operational overhead 

🧠 Final Mental Model

Spring Cloud Stream is just a clean abstraction, But in production, you MUST think in:
- Topics 
- Partitions 
- Consumer Groups 
- Keys (for ordering) 

🧭 One-Line Reality Check
If you don’t design partitions and keys properly, Spring Cloud Stream won’t save you — Kafka behavior still rules everything.
