## overview
Kafka is a distributed streaming platform. It has three main capabilities:
- Reading and writing records like a message queue
- Storing records with fault tolerance
- Processing streams as they occur

As a generalization, a core piece of Kafka can be thought of as providing the IT equivalent
of a receiver that sits in a home entertainment system. Figure shows the data flow
between receivers and end users.

![Producers, receivers, and data flow overview](/docs/assets/software-engineering/design-architecture/distributed-systems/messaging-systems/kafka/Producers-receivers-and-data-flow-overview.png)

As figure above shows, digital satellite, cable, and Blu-ray™ players can connect to a
central receiver. You can think of those individual pieces as regularly sending data in a
format that they know about. That flow of data can be thought of as nearly constant
while a movie or CD is playing. The receiver deals with this constant stream of data
and converts it into a usable format for the external devices attached to the other end
(the receiver sends the video to your television and the audio to a decoder as well as to
the speakers).

Kafka includes clients to interface with other systems. One such client type is called
a producer, which sends multiple data streams to the Kafka brokers. The brokers serve a
similar function as the receiver in figure above. Kafka also includes consumers, clients that
can read data from the brokers and process it. Data does not have to be limited to only
a single destination. The producers and consumers are completely decoupled, allow-
ing each client to work independently.

Kafka acts like a middle man for data coming into the system (from producers) and out of the system (for consumers or end users). The loose coupling can be achieved by allowing this separation between the producer and the end user of the message. The producer can send whatever message it wants and still have no clue about if anyone is subscribed.

## Kafka usage
### Kafka for the developer
{/* This section explains why Kafka matters to software developers, not just infrastructure engineers or data teams. The core idea is that Kafka changes how applications communicate and process data. */}
This section explains *why Kafka matters to software developers*, not just infrastructure engineers or data teams. The core idea is that Kafka changes how applications communicate and process data.

#### Why Developers Care About Kafka

Traditionally, applications are tightly connected:

* Application A directly calls Application B
* Services depend on each other synchronously
* Databases are shared across systems
* Failures propagate easily
* Scaling becomes difficult
* Testing requires many mocks and integrations

Kafka introduces a different model:

> Applications communicate through streams of events instead of direct coupling.

Take, for example, an HR system that employees would use to submit paid vacation
leaves. If you are used to a create, read, update, and delete (CRUD) system, the submis-
sion of time off would likely be processed by not only payroll but also project burndown
charts for forecasting work. Do you tie the two applications together? What if the pay-
roll system goes down? Should that impact the availability of the forecasting tooling?

Instead of:

```text
HR App --> Payroll API
HR App --> Forecasting API
HR App --> Reporting DB
```

You get:

```text
HR App --> Kafka Topic --> Payroll Service
                        --> Forecasting Service
                        --> Reporting Service
                        --> Analytics Service
```

The producer does not need to know who consumes the data.

## Kafka vs traditional message brokers
Kafka is NOT just a traditional message broker with a different name.

Kafka overlaps with message brokers, BUTKafka's model and architecture are fundamentally different

Traditional brokers like RabbitMQ, IBM MQ, ActiveMQ are often designed around:

```text id="n6h8te"
Producer -> Queue -> Consumer
```

Usually:

1. Producer sends message
2. Broker stores temporarily
3. Consumer receives message
4. Message gets removed/acknowledged

This is classic queue behavior.

{/* Kafka's Core Difference */}

Kafka behaves more like:

```text id="d6wru0"
Persistent distributed event log
```

rather than:

```text id="yz8fvx"
Temporary delivery queue
```

That single difference changes many things.

---

**Most Important Kafka Feature**
- The ability to replay messages by default
- Parallel processing of data

### Message Replay

one of Kafka’s defining features,The ability to replay messages by default.

{/* **Traditional Queue Behavior** */}

In many traditional brokers:

```text id="grngtx"
Consumer reads message
Message disappears
```

or becomes unavailable to other consumers.

The queue’s purpose is usually:

```text id="2zdcwi"
Deliver once
Then remove
```

 {/* Kafka Behavior */}

In Kafka:
- Consumer reads message
- Message remains in topic

Kafka stores messages for a retention period.

Example:
- Keep messages for 7 days
- Keep messages forever

Consumers only track their own position (offset).

**Offsets Are the Key Idea**

Kafka does NOT track: Was the message consumed globally?

Instead each consumer tracks: What position have I reached?

Example:

```text id="u2mujq"
Topic:
Offset 0 -> A
Offset 1 -> B
Offset 2 -> C
```
- Consumer X: Currently at offset 2
- Consumer Y: Currently at offset 0

Both can independently read the same data.

This is radically different from many traditional queues.

**Why Replay Matters**

Imagine consuming millions of messages, and you forget to use a specific field from the original message(discovered a bug)

Example: Forgot to use `customer_region` field

Traditional systems may require:

* backups
* dead-letter queues
* duplicate storage
* complex replay mechanisms

Kafka allows:
```text id="n8ks3f"
Reset offset -> Reprocess history
```
This is incredibly powerful.

**Kafka Assumes Failure and Bugs**

This is a deep distributed-systems philosophy.

programmer mistakes are expected just as much as hardware failures, Meaning: Systems should be designed assuming:
* developers make mistakes
* deployments fail
* consumers crash
* schemas evolve
* logic changes

Kafka’s replayability supports recovery from all of these.

**Kafka as an Immutable Log**

Kafka topics are append-only logs:

```text id="xslqva"
0 -> Event A
1 -> Event B
2 -> Event C
3 -> Event D
```
Messages are not removed after reading. Consumers merely move through the log. This is much closer to:
* database transaction logs
* commit logs
* event sourcing logs

than traditional message queues.

**Why Kafka Handles Massive Throughput**

How can Kafka handle huge numbers of messages efficiently? How do all of these log file entries allow Kafka to maintain performance without
causing a server to run out of resources? The throughput of small messages can sometimes overwhelm a system because the processing of each method takes time and overhead, The answer involves several architectural optimizations.
1. **Batching**

Instead of sending:

```text id="zz7h7n"
1 message
1 network call
```

Kafka batches messages:

```text id="k47bwm"
1000 messages
1 network call
```

Kafka uses batching of messages for sending data as well as for writing data.

This dramatically reduces overhead. Because:
* network calls are expensive
* system calls are expensive
* disk operations are expensive

Batching amortizes the cost.

2. **Sequential Disk Writes**

This is a HUGE Kafka design principle.

Kafka uses Writing to the end of a log, Kafka appends data sequentially:

```text id="31mjlwm"
Existing Log
[A][B][C][D]
             ^
          append here
```

This is much faster than random writes.

**Why Sequential Writes Matter**

Hard disks and even SSDs perform much better with sequential access.

Random access:

```text id="7sjlwm"
Jump here
Jump there
Jump elsewhere
```

causes overhead. Sequential append:

```text id="9wjlwm"
Write continuously forward
```

is extremely efficient. Kafka exploits this heavily.

**Kafka Treats Disk as Efficient, Not Slow**

Traditional systems often assume:

```text id="djlwmv"
Disk is slow
Avoid disk
```

Kafka instead optimizes access patterns so disk becomes extremely fast.

This was one of Kafka’s revolutionary ideas.

**Kafka’s Core Performance Philosophy**

Kafka achieves scale through:

| Technique         | Purpose              |
| ----------------- | -------------------- |
| Batching          | Reduce overhead      |
| Sequential writes | Fast disk throughput |
| Partitioning      | Parallelism          |
| Replication       | Reliability          |
| Pull consumers    | Backpressure control |
| Append-only logs  | Simplicity + speed   |

### Kafka and Microservices

Microservices used to talk using REST APIs,  Traditional microservice communication often looks like this:

```text id="r18m52"
Service A --> REST call --> Service B
```

This is synchronous communication.

**Problem with REST Between Microservices**

REST creates coupling. Service A depends on:

* Service B being available
* network connectivity
* API compatibility
* immediate response

If Service B fails: Request may fail, This creates cascading failures.

Kafka Changes the Communication Style, With Kafka:

```text id="xby67s"
Service A --> Event --> Kafka
Service B consumes later
```

This is asynchronous communication. The producer does not wait for a response.

**Why This Helps Microservices**

Kafka allows services to become more independent. Benefits:

* reduced coupling
* failure isolation
* scalability
* replayability
* independent deployment
* asynchronous workflows

Instead of: Call another service directly, you think: Publish an event describing what happened.

**Event-Driven Microservices**

This is one of the major modern architectural patterns.

Example:

```text id="2j9kw5"
OrderPlaced event
```

Consumers:

* Inventory service
* Payment service
* Shipping service
* Analytics service
* Notification service

The producer knows nothing about consumers.

This is event-driven architecture.


### Stream processing

Streams sits on top of producers and consumers. This is very important. Kafka Streams is NOT Kafka itself.

It is:

```text id="w6l9ea"
A higher-level client library
```

built on top of:

* Kafka producers
* Kafka consumers

---

**Core Kafka vs Kafka Streams**

**Core Kafka**

You manually handle:

* consuming records
* processing logic
* offset handling
* state management

**Kafka Streams**

You work with higher-level abstractions like:

```text id="2dwn36"
map
filter
join
aggregate
window
stream transformations
```

It treats Kafka topics as continuous streams of data.

---

**“Unbounded Stream”**

Kafka is fundamentally designed for unbounded streams(The data never truly ends)

Unlike:

```text id="6jlwmk"
Read fixed file
```

streaming systems process:

```text id="njlwmv"
Continuous endless flow of events
```

Examples:

* user clicks
* sensor data
* transactions
* logs
* GPS updates
---

### Exactly-Once processing

This is one of Kafka’s major advanced features.

{/* Why This Is Hard in Distributed Systems */}

Distributed systems naturally produce problems like:

* duplicate messages
* retries
* crashes
* partial failures
* network errors

Without special handling: Message may process twice, or: Message may be lost

---

**Delivery Guarantees**

Distributed messaging systems usually discuss:

| Guarantee     | Meaning                  |
| ------------- | ------------------------ |
| At-most-once  | Might lose messages      |
| At-least-once | Might duplicate messages |
| Exactly-once  | Processed once only      |

Exactly-once is the hardest.

**Why Exactly-Once Matters**

Example: Bank transfer

Duplicate processing is dangerous.

Without EOS:

```text id="ynjlwm"
$100 transferred twice
```

Exactly-once semantics tries to ensure: One logical processing result, despite retries or failures.

---

**Kafka Streams + Exactly-Once**

users running end-to-end workloads on top of Kafka with the Streams API may benefit from hardened delivery guarantees, Kafka Streams makes EOS easier.

Without framework support, developers historically had to build:

* deduplication logic
* idempotency handling
* transactional coordination
* state recovery

manually. Kafka Streams automates much of this without the overhead of any custom application logic,
ensuring that a message was only processed once from the beginning to the end of
the transaction.

## When Not to use KAfka
Kafka is powerful, but it is NOT a universal solution.

Good engineers do not ask: Can Kafka do this?

They ask: Should Kafka do this?

**Main Idea**

Kafka is optimized for a specific access pattern: High-throughput sequential event streaming, Kafka is NOT optimized for every possible workload.

---

### Case 1: Infrequent Batch Processing

What if you only need a once-monthly or even once-yearly summary of aggregate
data? Suppose you don’t need an on-demand view, quick answer, or even the ability to
reprocess data. 

Example:

```text id="jlwm6"
Generate annual sales report
```

If the workload is:

* infrequent
* small enough
* offline
* non-real-time

then Kafka may be unnecessary. In these cases, you might not need Kafka running throughout the
entire year for those tasks alone.

---

**Why Kafka Might Be Overkill**

Kafka is designed for:

* continuous streaming
* real-time ingestion
* always-on infrastructure
* event pipelines

If your system only runs: Once per month, then simpler batch systems may work better.

Example alternatives:

* cron jobs
* SQL batch queries
* ETL pipelines
* Spark batch jobs
* scheduled scripts

---

**Streaming vs Batch Processing**

**Batch Processing**: Process finite dataset occasionally.

Example: Nightly payroll calculation.

**Stream Processing**: Continuously process incoming events

Example: Real-time fraud detection

Kafka shines in streaming workloads.

### Case 2: Random Data Lookup

If your main access pattern for data is a mostly random lookup of data, Kafka
might not be your best option.  Kafka is not ideal for random lookups.

Why? Kafka is fundamentally an append-only log.

Access pattern:

```text id="jlwm2c"
Read sequentially
Write sequentially
```

Kafka is optimized for:

* sequential writes
* sequential reads
* streaming access

NOT: Find row instantly by arbitrary key

Linear read and writes are where Kafka shines and will keep your data moving as quickly as possible.

---

**Databases vs Kafka**

Relational databases optimize for: Random indexed access

Example:

```sql
SELECT * FROM users WHERE id = 42;
```

Databases use:

* indexes
* B-trees
* hashing
* query optimizers

Kafka does not behave like this.

---

**Kafka Indexes Are Different**

Kafka having index files, they are not really what you would compare to a relational database having fields and primary keys from which indexes are built.

But Kafka indexes are mainly for: Locating offsets in log segments

NOT for: Arbitrary relational querying

Kafka is not a replacement for:

* PostgreSQL
* MySQL
* MongoDB
* Elasticsearch

---

**Important Distinction**

Kafka is optimized for: Event streaming

Databases are optimized for: State querying

This is a fundamental architectural difference.

### Case 3: Strict Global Ordering

This is one of the most misunderstood Kafka topics.

Strict ordering across the entire topic is difficult. Why? Kafka ordering guarantees are: Per partition

NOT: Across all partitions globally

**Example**

Topic:

```text id="jlwm1d"
Partition 0
Partition 1
Partition 2
```

Each partition preserves order internally:

```text id="jlwm2d"
Partition 0:
A -> B -> C
```

But across partitions: No guaranteed global order

---

**Why Partitions Exist**

Partitions enable:

* scalability
* parallelism
* high throughput

Without partitions: Only one processing lane

With partitions: Many processing lanes

---

*The Trade-Off*

Kafka forces a classic distributed-systems tradeoff:

| Goal                   | Result                  |
| ---------------------- | ----------------------- |
| Strict global ordering | Lower scalability       |
| High parallelism       | Relaxed global ordering |

You usually cannot maximize both simultaneously.

---

**Why One Partition Limits Throughput**

To avoid any
unordered messages, care should be taken to ensure that only one producer request
thread is the maximum and, simultaneously, that there is only one partition in the
topic. 

So To preserve exact ordering:

```text id="jlwm6d"
One producer thread
One partition
One consumer
```

But then:

* no parallel consumption
* limited throughput
* reduced scalability

This becomes a bottleneck for very large workloads.

There are various workarounds, but if you have vast amounts of data that
depend on strict ordering, there are potential gotchas that might come into play once
you notice that your consumption is limited to one consumer per group at a time

---

**Important Distributed Systems Principle**: Scalability often conflicts with strict ordering

Many distributed systems make this compromise.


### Case 4: Large Messages

Kafka is optimized for: Many relatively small messages

NOT huge files. Default Kafka message size: ~1 MB

---

**Why Large Messages Are Problematic**

Large messages increase:

* memory pressure
* network overhead
* replication cost
* page cache pressure
* GC pressure (JVM)
* latency spikes

---

**What Is Page Cache?**

Operating systems cache disk data in RAM. Kafka relies heavily on this.

Smaller messages allow: More messages cached in memory.

Huge messages reduce efficiency.

---

**Typical Kafka Design Pattern**

Instead of sending huge files THROUGH Kafka.Send:

```text id="jlwm1e"
Metadata + file reference
```

Example:

```json
{
  "fileLocation": "s3://bucket/archive.zip",
  "event": "archive_uploaded"
}
```

Kafka transports the event. Large storage systems store the actual file.

---

**Summary**

Kafka is optimized for:

| Kafka Strengths      |
| -------------------- |
| Sequential streaming |
| High throughput      |
| Event pipelines      |
| Real-time processing |
| Parallel consumers   |
| Distributed logs     |
| Replayable events    |

Kafka is NOT primarily optimized for:

| Weak Fits                       |
| ------------------------------- |
| Random querying                 |
| Huge binary files               |
| Rare batch jobs                 |
| Strict global ordering at scale |

---

**Bigger Engineering Lesson**

Every distributed system is built around specific trade-offs.

Kafka intentionally optimizes for: Scalable event streaming, and sacrifices some convenience in other workloads.

That is normal in systems engineering.

## Summary
- Apache Kafka is a streaming platform that you can leverage to process large
numbers of events quickly.
- Although Kafka can be used as a message bus, using it only as that ignores the
capabilities that provide real-time data processing.
- Kafka may have been associated with other big data solutions in the past, but
Kafka stands on its own to provide a scalable and durable system. Because it
uses the same fault tolerant and distributed system techniques, Kafka fills the
needs of a modern data infrastructure’s core with its own clustering capabilities.
- In instances of streaming a large number of events like IoT data, Kafka handles
data fast. As more information is available for your applications, Kafka provides
results quickly for your data that was once processed offline in batch mode.
