REST over HTTP is a **synchronous direct communication style** where one service communicates with another service using the HTTP protocol and REST architectural principles.

It is the most common communication mechanism in microservices, web APIs, and distributed systems.

## Position in Distributed Systems Architecture

```text
distributed-systems
└── service-communication
    ├── direct-communication
    │   ├── REST over HTTP
    │   ├── gRPC
    │   ├── GraphQL
    │   └── WebSocket
    │
    └── asynchronous-communication
        ├── Kafka
        ├── RabbitMQ
        └── Event Streaming
```

REST belongs to:

* **Direct communication**
* Usually **request/response**
* Usually **synchronous**
* Typically **stateless**

## What is REST?

REST stands for:

> **Representational State Transfer**

It is an architectural style introduced by Roy Fielding in his doctoral dissertation.

REST defines principles for designing distributed networked systems.

REST itself is **not a protocol**.

HTTP is the protocol commonly used to implement REST APIs.

## REST + HTTP

REST APIs commonly use:

| Concept        | HTTP Mapping      |
| -------------- | ----------------- |
| Resource       | URL               |
| Operation      | HTTP Method       |
| Representation | JSON/XML          |
| Status         | HTTP Status Codes |
| Metadata       | Headers           |

Example:

```http
GET /users/10
```

Meaning:

* Resource: `users`
* Resource ID: `10`
* Operation: retrieve user

Response:

```json
{
  "id": 10,
  "name": "Alice"
}
```

## Core REST Concepts

### Resources

REST revolves around **resources**.

Examples:

```text
/users
/orders
/products/100
/payments/55
```

A resource is identified by a URI.

### Representations

The server sends a representation of the resource.

Usually:

* JSON
* XML
* HTML

Example:

```json
{
  "id": 100,
  "name": "Laptop",
  "price": 1200
}
```

### HTTP Methods

REST uses standard HTTP verbs.

| Method | Meaning           |
| ------ | ----------------- |
| GET    | Retrieve resource |
| POST   | Create resource   |
| PUT    | Replace resource  |
| PATCH  | Partial update    |
| DELETE | Remove resource   |

Example:

```http
POST /orders
```

Create a new order.

### Statelessness

Each request contains all information needed.

Server does not store client session state between requests.

Example:

```http
Authorization: Bearer token
```

included in every request.

Benefits:

* Scalability
* Simpler load balancing
* Easier horizontal scaling

### Uniform Interface

REST APIs expose a consistent interface:

* predictable URLs
* standard methods
* standard status codes

This reduces coupling.

## HTTP as Transport Layer

REST commonly uses HTTP because HTTP already provides:

| Feature             | Purpose           |
| ------------------- | ----------------- |
| Methods             | CRUD operations   |
| Status codes        | Operation results |
| Headers             | Metadata          |
| Content negotiation | JSON/XML          |
| Caching             | Performance       |
| TLS/HTTPS           | Security          |

## HTTP Request Structure

Example:

```http
POST /products HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer token
```

Body:

```json
{
  "name": "Keyboard",
  "price": 50
}
```

## HTTP Response Structure

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /products/101
```

Body:

```json
{
  "id": 101,
  "name": "Keyboard",
  "price": 50
}
```

## HTTP Status Codes

REST APIs heavily depend on status codes.

| Code                      | Meaning                 |
| ------------------------- | ----------------------- |
| 200 OK                    | Success                 |
| 201 Created               | Resource created        |
| 204 No Content            | Success without body    |
| 400 Bad Request           | Invalid input           |
| 401 Unauthorized          | Authentication required |
| 403 Forbidden             | Access denied           |
| 404 Not Found             | Resource missing        |
| 409 Conflict              | State conflict          |
| 500 Internal Server Error | Server failure          |

## REST in Microservices

Example:

```text
Order Service ──HTTP──> Payment Service
```

Flow:

1. Order service sends HTTP request
2. Payment service processes payment
3. Payment service returns response

Example:

```http
POST /payments
```

## REST Communication Characteristics

| Characteristic       | Description               |
| -------------------- | ------------------------- |
| Synchronous          | Caller waits for response |
| Direct               | Service-to-service        |
| Stateless            | Requests independent      |
| Human-readable       | JSON/text                 |
| Platform-independent | Works everywhere          |
| Loosely coupled      | Interface-based           |

## Advantages of REST over HTTP

### Simplicity

Easy to understand and debug.

### Wide Adoption

Supported everywhere:

* Browsers
* Mobile apps
* Backend services
* Cloud providers

### Language Agnostic

Any language supporting HTTP can communicate.

### Scalability

Statelessness improves horizontal scaling.

### Cache Support

HTTP caching improves performance.

Example:

```http
Cache-Control: max-age=3600
```

### Tooling Ecosystem

Large ecosystem:

* OpenAPI
* Swagger
* Postman
* API gateways
* Load balancers

## Disadvantages

### Higher Latency

HTTP + JSON serialization adds overhead.

Compared to binary protocols like gRPC:

* larger payloads
* slower parsing

### Tight Runtime Dependency

In synchronous communication:

```text
Service A -> Service B
```

If B is down:

* A may fail
* cascading failures may occur

### Chatty Communication

REST APIs may require many network calls.

Example:

```text
GET /orders/1
GET /customers/10
GET /products/5
```

Multiple round trips.

### Versioning Complexity

API evolution requires careful versioning.

Examples:

```text
/v1/users
/v2/users
```

## REST Constraints

REST architecture defines constraints.

### Client-Server

Separation between client and server.

### Stateless

No client session state on server.

### Cacheable

Responses may be cached.

### Uniform Interface

Consistent communication model.

### Layered System

Intermediaries allowed:

```text
Client -> Gateway -> Service
```

### Code on Demand (Optional)

Server may send executable code.

Rare in APIs.

## REST vs RPC

| REST                | RPC               |
| ------------------- | ----------------- |
| Resource-oriented   | Action-oriented   |
| Uses HTTP semantics | Procedure calls   |
| Flexible            | Often stricter    |
| Human-readable      | Often binary      |
| Common on web       | Common internally |

REST:

```http
POST /orders
```

RPC:

```text
createOrder()
```

## REST vs gRPC

| REST             | gRPC                      |
| ---------------- | ------------------------- |
| Text/JSON        | Binary/Protobuf           |
| Human-readable   | Compact                   |
| HTTP/1.1 common  | HTTP/2                    |
| Easier debugging | Higher performance        |
| Web-friendly     | Internal-service-friendly |

## REST API Design Best Practices

### Use Nouns for Resources

Good:

```text
/orders
/users
```

Avoid:

```text
/getOrders
/createUser
```

### Use Proper HTTP Methods

```http
GET /users
POST /users
DELETE /users/10
```

### Use Meaningful Status Codes

Avoid always returning:

```http
200 OK
```

even on failures.

### Keep APIs Stateless

Avoid server-side session state.

### Use Versioning

```text
/api/v1/orders
```

### Support Pagination

Example:

```http
GET /products?page=2&size=20
```

## Reliability Concerns in Distributed Systems

REST communication faces distributed-system challenges:

### Timeouts

Service may not respond.

### Retries

Transient failures may require retries.

### Circuit Breakers

Prevent cascading failures.

Common pattern:

```text
Service A -> Circuit Breaker -> Service B
```

### Idempotency

Repeated requests should be safe when retried.

Example:

```http
PUT /users/10
```

should produce same result multiple times.

## Where REST Fits Best

REST works especially well for:

### External APIs

Public APIs:

* web
* mobile
* partner integrations

### CRUD-Oriented Systems

Applications centered around resources.

### Cross-Platform Communication

When interoperability matters more than raw speed.

## When REST May Not Be Ideal

REST may be less suitable for:

| Scenario                          | Better Alternative |
| --------------------------------- | ------------------ |
| High-performance internal RPC     | gRPC               |
| Event-driven systems              | Kafka              |
| Real-time bidirectional streaming | WebSockets         |
| Massive async workflows           | Messaging systems  |

## Conceptual Summary

REST over HTTP is:

```text
A stateless, synchronous, resource-oriented
service communication style built on HTTP.
```

In distributed systems it provides:

* interoperability
* simplicity
* scalability
* standardization

But introduces challenges involving:

* latency
* partial failures
* retries
* service dependency chains
* network reliability
