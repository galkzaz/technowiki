## Distributed Systems Fundamentals

A **Distributed System** is a collection of independent computers that work together and appear to users as a single coherent system.

Examples:

* Google Search
* Netflix streaming platform
* Amazon marketplace
* Uber ride-sharing system
* Banking systems
* Multiplayer games
* Cloud platforms

Instead of one machine doing all the work, many machines cooperate over a network.

**Mental Model**

Think of distributed systems as:

```text
Many independent computers
+
Communication over unreliable network
+
Coordination under failures
+
Shared goals
```

The entire field revolves around managing:

* communication
* latency
* failures
* consistency
* scalability
* coordination

at scale.
## Why Distributed Systems Exist

Single-machine systems eventually hit limits:

* CPU limits
* Memory limits
* Storage limits
* Geographic limits
* Reliability limits

Distributed systems solve these by enabling:

| Goal                    | Meaning                              |
| ----------------------- | ------------------------------------ |
| Scalability             | Handle more users/data               |
| Reliability             | Survive failures                     |
| Availability            | Stay operational                     |
| Performance             | Reduce latency / increase throughput |
| Geographic distribution | Serve users globally                 |
| Resource sharing        | Share compute/storage                |

## Core Idea

A distributed system consists of:

```text
+-----------+       Network       +-----------+
| Machine A | <-----------------> | Machine B |
+-----------+                     +-----------+
        \                           /
         \                         /
          \                       /
                +-----------+
                | Machine C |
                +-----------+
```

Each machine:

* Has its own memory
* Has its own CPU
* Fails independently
* Communicates via messages

This is fundamentally different from:

* Multithreading
* Multiprocessing on one machine
* Shared-memory systems

## Fundamental Characteristics

### A. Concurrency

Many machines operate simultaneously.

Example:

* Thousands of users sending requests at once
* Multiple services processing events in parallel

Challenges:

* Race conditions
* Coordination
* Ordering

---

### B. No Shared Memory

Machines communicate through:

* TCP
* HTTP
* gRPC
* Message queues
* Event streams

Data is exchanged via messages.

This leads to:

* Serialization
* Network latency
* Partial failure

---

### C. Partial Failure

The hardest distributed systems concept.

In a single machine:

* if CPU dies → system dies

In distributed systems:

* one node may fail
* network may fail
* some nodes may work
* others may be unreachable

Example:

```text
A can talk to B
B can talk to C
A cannot talk to C
```

System state becomes uncertain.

---

### D. Independent Clocks

Each machine has its own clock.

Clocks drift.

This causes:

* ordering problems
* synchronization issues
* consistency challenges

Important concepts:

* Logical clocks
* Lamport timestamps
* Vector clocks

## Communication Models

### A. Request–Response

Traditional model.

```text
Client -> Request
Server -> Response
```

Examples:

* REST APIs
* gRPC calls

Characteristics:

* synchronous
* tightly coupled
* immediate reply

---

### B. Message Passing

Systems communicate asynchronously.

```text
Producer -> Queue -> Consumer
```

Examples:

* Apache Kafka
* RabbitMQ

Advantages:

* decoupling
* buffering
* retry
* scalability

---

### C. Event-Driven Systems

Services react to events.

```text
OrderCreated Event
    -> payment service
    -> inventory service
    -> shipping service
```

Foundation of:

* reactive systems
* streaming systems
* microservices

---

## Distributed System Architectures

### A. Client–Server

```text
Client ---> Server
```

Simple centralized model.

Examples:

* Web applications
* Database servers

---

### B. Multi-Tier Architecture

```text
Client
  |
API Layer
  |
Business Layer
  |
Database
```

Separates responsibilities.

---

### C. Peer-to-Peer (P2P)

All nodes are equal.

Examples:

* BitTorrent
* blockchain networks

---

### D. Microservices

Application split into small independent services.

```text
User Service
Order Service
Payment Service
Inventory Service
```

Each service:

* deploys independently
* scales independently
* owns data

---

## Transparency in Distributed Systems

Good distributed systems try to hide complexity.

| Transparency Type        | Meaning                            |
| ------------------------ | ---------------------------------- |
| Location transparency    | User doesn't know machine location |
| Replication transparency | Multiple copies hidden             |
| Failure transparency     | Failures hidden/recovered          |
| Concurrency transparency | Multiple users hidden              |
| Migration transparency   | Resources move invisibly           |

Example:
Users do not know which exact Google server handled their search.

### B. Horizontal Scaling

## Challenges

## A. Network Problems

Networks are:

* slow
* unreliable
* lossy

Compared to memory access:

* network is extremely expensive

---

## B. Latency

Communication takes time.

Types:

* propagation delay
* serialization delay
* queue delay

Distributed systems often optimize:

* fewer network hops
* locality
* caching

---

## C. Consistency

How synchronized is shared data?

Example:

* User updates profile
* Another user reads old profile

Questions:

* When do replicas update?
* What data is visible?

---

## D. Coordination

Machines must agree.

Examples:

* leader election
* distributed locks
* consensus

---

## E. Failure Handling

Failures are normal.

Need:

* retries
* replication
* failover
* monitoring

---

## CAP Theorem

One of the most important distributed systems concepts.

A distributed system cannot simultaneously guarantee all three:

| Property            | Meaning                        |
| ------------------- | ------------------------------ |
| Consistency         | All nodes see same data        |
| Availability        | Every request gets response    |
| Partition Tolerance | System survives network splits |

During a network partition:

* choose consistency
  OR
* choose availability

Not both.

## Consistency Models

### Strong Consistency

All users immediately see latest data.

Like:

* single database illusion

Cost:

* slower
* harder to scale

---

### Eventual Consistency

Replicas eventually converge.

Common in:

* distributed caches
* DNS
* NoSQL systems

Benefits:

* highly scalable
* highly available

Tradeoff:

* temporary stale data

---

## Replication

Keeping copies of data across machines.

Goals:

* fault tolerance
* availability
* performance

### Types

#### Primary–Replica

```text
Primary -> Replicas
```

Writes:

* primary

Reads:

* replicas

---

#### Multi-Leader

Multiple writable nodes.

Challenges:

* conflict resolution

---

#### Leaderless

No central leader.

Examples:

* Dynamo-style systems

## Partitioning (Sharding)

Split data across nodes.

Example:

```text
Users A-M -> Server 1
Users N-Z -> Server 2
```

Benefits:

* scalability
* parallelism

Challenges:

* rebalancing
* distributed joins
* hot shards

## Consensus

How distributed nodes agree on a value/state.

Critical for:

* leader election
* metadata
* coordination

Popular algorithms:

* Raft
* Paxos

Used in:

* distributed databases
* cluster managers


## Fault Tolerance

System continues despite failures.

Techniques:

* replication
* retries
* redundancy
* checkpointing
* quorum systems

## Distributed Transactions

Operations spanning multiple machines.

Challenges:

* atomicity across network
* failures mid-transaction

Techniques:

* Two-Phase Commit (2PC)
* Saga pattern

## Distributed System Patterns

### Common Patterns

| Pattern         | Purpose                       |
| --------------- | ----------------------------- |
| Load Balancer   | Distribute traffic            |
| Circuit Breaker | Prevent cascading failures    |
| Retry Pattern   | Recover transient failures    |
| Bulkhead        | Isolate failures              |
| CQRS            | Separate reads/writes         |
| Event Sourcing  | Store events instead of state |
| Pub/Sub         | Event broadcasting            |

## Observability

Critical because systems are distributed.

Main pillars:

| Area    | Purpose                        |
| ------- | ------------------------------ |
| Logging | Record events                  |
| Metrics | Numeric measurements           |
| Tracing | Follow request across services |

Example:
A request may travel through:

```text
API Gateway
 -> Auth Service
 -> Order Service
 -> Payment Service
 -> Inventory Service
```

Tracing tracks the entire path.

## Reactive Systems Relation

Distributed systems often evolve into:

* asynchronous
* event-driven
* non-blocking systems

Reactive systems focus on:

* responsiveness
* resilience
* elasticity
* message-driven communication

This is why topics like:

* reactive programming
* Kafka
* asynchronous messaging
* non-blocking I/O

fit naturally inside distributed systems architecture.

## Key Distributed Systems Principles

### Principle 1: Network is not reliable

Never assume messages arrive.

---

### Principle 2: Failure is normal

Design for failure first.

---

### Principle 3: Latency matters

Remote calls are expensive.

---

### Principle 4: Data replication creates consistency problems

Copies diverge.

---

### Principle 5: Coordination is expensive

Avoid global synchronization when possible.

---

### Principle 6: Scalability requires partitioning

Eventually data/work must split.
