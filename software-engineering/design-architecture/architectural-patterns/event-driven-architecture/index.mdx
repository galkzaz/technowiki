**Event-Driven Architecture (EDA)** is an **architectural pattern** where system components communicate by producing and reacting to **events** instead of calling each other directly.

It is one of the core patterns used in:

* Distributed Systems
* Microservices
* Reactive Systems
* Real-time systems
* Streaming platforms
* Asynchronous architectures

**Mental Model**

Think of EDA like:

```text
YouTube subscriptions
```

When a creator uploads a video:

* creator does not contact viewers directly
* platform distributes event
* subscribers react independently

Producer does not know consumers.

# Core Idea

Instead of:

```text
Service A → directly calls → Service B
```

EDA works like this:

```text
Service A → emits event → Event Broker → interested consumers react
```

The sender does not need to know:

* who receives the event
* how many receivers exist
* when receivers process it
* where receivers are located

This creates **loose coupling**.

# What Is an Event?

An **event** is a record that: “Something happened in the system.”

Examples:

* `OrderPlaced`
* `PaymentCompleted`
* `UserRegistered`
* `InventoryUpdated`
* `TemperatureChanged`
* `FileUploaded`

An event usually contains:

* event name/type
* timestamp
* payload/data
* metadata

Example:

```json
{
  "eventType": "OrderPlaced",
  "orderId": 123,
  "customerId": 77,
  "timestamp": "2026-05-12T10:30:00Z"
}
```

# Main Components of EDA

## 1. Event Producer (Publisher)

Component that creates/emits events.

Example:

* Order Service publishes `OrderPlaced`

---

## 2. Event Broker / Event Bus

Middleware that transports events.

Examples:

* Apache Kafka
* RabbitMQ
* Apache Pulsar
* Redis
* NATS

Responsibilities:

* receive events
* store/queue events
* deliver events to consumers
* retry delivery
* scaling

---

## 3. Event Consumer (Subscriber)

Component that reacts to events.

Example:

* Email Service listens to `OrderPlaced`
* Inventory Service listens to `OrderPlaced`
* Analytics Service listens to `OrderPlaced`

## Simple Flow

### Traditional Request/Response

```text
Client
  |
  v
Order Service
  |
  +--> Payment Service
  |
  +--> Inventory Service
  |
  +--> Email Service
```

Tightly coupled.

---

### Event-Driven Flow

```text
Client
  |
  v
Order Service
  |
  | emits OrderPlaced
  v
Event Broker
  |
  +--> Payment Consumer
  |
  +--> Inventory Consumer
  |
  +--> Email Consumer
  |
  +--> Analytics Consumer
```

Much more decoupled.

# Key Characteristics

## 1. Asynchronous Communication

Producer does not wait for consumers.

```text
Publish event → continue execution
```

This is why EDA is highly scalable.

---

## 2. Loose Coupling

Services know only event contracts.

They do NOT know:

* implementation details
* internal logic
* deployment location

---

## 3. Reactive Behavior

Components react to events.

This is why EDA is strongly connected to:

* Reactive Systems
* Reactive Programming
* Streaming architectures

---

## 4. Scalability

Consumers scale independently.

Example:

```text
10 consumers processing OrderPlaced events in parallel
```

---

## 5. Real-Time Processing

Events can be processed immediately after occurring.

Used in:

* fraud detection
* stock trading
* monitoring
* IoT
* analytics

## Types of Event-Driven Architecture

### 1. Publish-Subscribe (Pub/Sub)

Producer publishes event to topic.

Multiple consumers receive it.

```text
Publisher → Topic → many subscribers
```

Used for:

* notifications
* broadcasting
* live feeds

---

### 2. Event Streaming

Events form a continuous stream.

Consumers process streams in real time.

Usually implemented using:

* Apache Kafka
* Apache Flink
* Apache Spark

Used for:

* analytics
* telemetry
* monitoring
* fraud detection

---

### 3. Event Sourcing

State changes stored as immutable events.

Instead of:

```text
CurrentBalance = 500
```

store:

```text
MoneyDeposited +100
MoneyWithdrawn -50
MoneyDeposited +450
```

Current state reconstructed from events.

Very important in:

* CQRS
* Domain-Driven Design (DDD)

---

### 4. CQRS + Events

Separate:

* write operations (commands)
* read operations (queries)

Events synchronize read models.

Very common in microservices.

# Important Concepts in EDA

## Eventual Consistency

Systems synchronize asynchronously.

---

## Idempotency

Repeated processing produces same result.

---

## Dead Letter Queue (DLQ)

Failed events moved for inspection.

---

## Replayability

Past events replayed.

Common in Kafka systems.

---

## Backpressure

Consumers signal overload.

Very important in reactive systems.

## Relationship to Other Architectural Concepts

### EDA vs Request-Response

#### Request-Response

```text
Caller waits for response
```

Usually synchronous.

Example:

```http
GET /users/1
```

---

#### EDA

```text
Producer emits event and continues
```

Usually asynchronous.

---

### EDA vs Message Queue

Message queue is a technology/mechanism.

EDA is a full architectural style.

Queue may exist inside EDA.

---

### EDA vs Reactive Systems

Reactive systems are broader.

EDA is one implementation style that helps build reactive systems.

Reactive systems emphasize:

* responsiveness
* resilience
* elasticity
* message-driven communication

EDA provides the message-driven foundation.

---

### EDA vs Reactive Programming

Reactive Programming:

* programming model
* streams + async data flow

EDA:

* system architecture pattern

Reactive programming often implements consumers/producers.

Example:

* Project Reactor
* RxJava


## Advantages

### Decoupling

Independent services.

---

### Scalability

Consumers scale horizontally.

---

### Fault Isolation

Failure in one consumer may not stop others.

---

### Extensibility

New consumers can subscribe without changing producers.

---

### Real-Time Responsiveness

Immediate reactions to events.

---

### Better Distributed Systems Design

Natural fit for microservices.

---

## Challenges

### 1. Complexity

Harder than synchronous systems.

---

### 2. Debugging Difficulty

Flow becomes distributed.

Tracing events is harder.

---

### 3. Eventual Consistency

Data may not update instantly everywhere.

Important distributed systems concept.

---

### 4. Ordering Problems

Events may arrive:

* late
* duplicated
* out of order

---

### 5. Idempotency

Consumers must safely handle duplicate events.

Example:

```text
Process PaymentCompleted twice
```

must not charge customer twice.

---

### 6. Schema Evolution

Events evolve over time.

Need backward compatibility.
