## One important structural change

I would **not** put OAuth implementation pages directly under the architecture section. Keep the layers separate:

```text
software-engineering/
  design-architecture/
    security/
      api-security/
        oauth2/                 ← OAuth concepts, protocol, architecture

  frameworks-platforms/
    backend-frameworks/
      spring-security/
        oauth2/                 ← Spring Security OAuth implementation
```

And if you later document an actual OAuth provider:

```text
software-engineering/
  design-architecture/
    security/
      api-security/
        identity-providers/
          keycloak/
          auth0/
          microsoft-entra-id/
```

That gives you:

```text
OAuth 2.0
   │
   ├── Protocol / Architecture
   │
   ├── Identity Provider technologies
   │      ├── Keycloak
   │      ├── Auth0
   │      └── Microsoft Entra ID
   │
   └── Framework implementations
          └── Spring Security OAuth2
```

### Important distinction for your TOC

I would also keep **OpenID Connect separate from OAuth 2.0**, while linking them:

```text
security/
  api-security/
    oauth2/
    openid-connect/
```

OAuth 2.0 → **delegated authorization**

OpenID Connect → **authentication/identity layer built on OAuth 2.0**

This prevents the OAuth section from gradually becoming a giant mixture of authorization, authentication, JWT, identity providers, and Spring Security.
