
{/* PKCE (Proof Key for Code Exchange) in OAuth 2.0 */}


PKCE (pronounced “pixy”) is an OAuth 2.0 security mechanism that protects the Authorization Code Flow against authorization-code interception and misuse.

PKCE was originally designed to protect the authorization code flow in mobile apps, and was later recommended to be used by single-page apps as well. In later years, it was recognized that its ability to prevent authorization code injection makes it useful for every type of OAuth client, even apps running on a web server that use a client secret. Because of its history in the use of mobile apps and single-page apps, it is sometimes incorrectly thought that PKCE is an alternative to a client secret. However PKCE is not a replacement for a client secret, and PKCE is recommended even if a client is using a client secret, since apps with a client secret are still susceptible to authorization code injection attacks.

It was originally designed to protect public clients, such as mobile apps and single-page applications (SPAs), which cannot safely keep a client secret. It is also recommended for confidential clients, such as backend web applications.

PKCE is an extension to the authorization code flow to prevent CSRF and authorization code injection attacks.

The technique involves the client first creating a secret on each authorization request, and then using that secret again when exchanging the authorization code for an access token. This way if the code is intercepted, it will not be useful since the token request relies on the initial secret.

The full spec is available as RFC7636. 
## The problem PKCE solves

Consider a mobile online-shopping application that lets a customer sign in through Keycloak. Without PKCE, the flow looks like this:
```
1\. Mobile app

Starts authorization and requests a code
        ↓
Authorization request

2\. Authorization server (Keycloak)

Authenticates the customer and returns an authorization code
        ↓
Redirect URI delivers the code

3\. Mobile app

Exchanges the authorization code for tokens
```
The problem is that another application on the device might intercept the redirect and steal the authorization code.

If the attacker obtains the code and can successfully exchange it for tokens, the attack succeeds.

PKCE adds a secret value that the legitimate app creates before authorization. The app must prove possession of that value when exchanging the authorization code.

The central idea: stealing the authorization code alone is no longer sufficient. The attacker also needs the original code verifier.

## The three essential PKCE terms

| Term                    | Meaning                                                   |
| ----------------------- | --------------------------------------------------------- |
| `code_verifier`         | A high-entropy secret generated by the client             |
| `code_challenge`        | A derived value sent in the initial authorization request |
| `code_challenge_method` | Specifies how the challenge was derived from the verifier |

The authorization server remembers the challenge associated with the authorization request and later checks that the verifier presented at the token endpoint matches it.

## Code verifier

The `code_verifier` is a cryptographically random string generated by the client application.

For example:

```
code_verifier =
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

This is an illustrative verifier, not a value to hardcode in an application.

### Requirements

A PKCE verifier must satisfy the following requirements:

- It must contain between 43 and 128 characters.
- It uses characters from the unreserved URI character set: letters, digits, `-`, `.`, `_`, and `~`.
- It should be generated using a cryptographically secure random number generator.
- It must remain available to the client until the authorization-code exchange is completed.

For example, in a Java application:

```Java
import java.security.SecureRandom;
import java.util.Base64;

public class PkceExample {
    private static final SecureRandom RANDOM = new SecureRandom();

    public static String generateCodeVerifier() {
        byte[] bytes = new byte[32];
        RANDOM.nextBytes(bytes);

        return Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(bytes);
    }

    public static void main(String[] args) {
        String verifier = generateCodeVerifier();

        System.out.println("Code verifier: " + verifier);
    }
}
```

Thirty-two random bytes produce 43 `Base64URL` characters without padding, satisfying the verifier length requirement.

:::note

Base64-URL-encoding is a minor variation on the typical Base64 encoding method. It starts with the same Base64-encoding method available in most programming languages, but uses URL-safe characters instead. You can implement a Base64-URL-encoding method by taking a Base64-encoded string and making the following modifications to the string: Take the Base64-encoded string, and change + to -, and / to _, then trim the trailing = from the end.

PHP
```PHP
function base64_urlencode($str) {
  return rtrim(strtr(base64_encode($hash), '+/', '-_'), '=');
}
```
JavaScript
```JavaScript
function base64_urlencode(str) {
  return btoa(String.fromCharCode.apply(null, 
    new Uint8Array(str)))
      .replace(/\+/g, '-')
      .replace(/\//g, '_')
      .replace(/=+$/, '');
}
```
:::

### Why is the verifier secret?

The verifier acts as proof that the token requester possesses the value generated by the client that initiated authorization.

The client sends it to the token endpoint only when exchanging the authorization code. It does not send the verifier in the initial authorization request.

The verifier is not a replacement for user authentication, client authentication, or access-token validation. It protects a particular step of the OAuth flow.

## Code challenge

The `code_challenge` is a derived value calculated from the code verifier. The client sends it to the authorization server during the authorization request.

With the recommended `S256` method:
$$ 
\text\{code\_challenge} = \text{BASE64URL}(\text{SHA256}(\text\{code\_verifier}))
$$

The client applies SHA-256 to the verifier and encodes the resulting bytes using Base64URL without padding.

### Example

Suppose the client generates this verifier:

```
dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
```

It calculates a challenge:

```
SHA256(verifier)
        |
        v
Base64URL encoding without padding
        |
        v
code_challenge
```

The resulting challenge is sent in the authorization request:

```
GET /authorize?
    response_type=code&
    client_id=shopping-mobile&
    redirect_uri=com.example.shop:/callback&
    code_challenge=calculated_challenge&
    code_challenge_method=S256
```

The challenge shown here is a placeholder; a real request contains the computed value.

### Why not send the verifier immediately?

Because the authorization request and its parameters may be observed by parties other than the intended client. PKCE avoids exposing the original verifier at this stage.

The authorization server stores the challenge alongside the authorization transaction. When the client later presents the verifier, the server independently derives the challenge and compares the result with the stored value.

Think of it as a commitment:

- Before authorization: the client commits to a verifier by sending its derived challenge.
- During token exchange: the client proves possession of the verifier.
- At validation: the authorization server verifies that the proof matches the original commitment.

Importantly, SHA-256 is not being used to encrypt the verifier. It is a one-way cryptographic hash.

## 4. Challenge methods

The `code_challenge_method` parameter tells the authorization server how the client derived the challenge.

There are two methods defined by the PKCE specification.

| Method  | Calculation                      | Recommendation                                             |
| ------- | -------------------------------- | ---------------------------------------------------------- |
| `S256`  | `BASE64URL(SHA256(verifier))`    | Use this method                                            |
| `plain` | `code_challenge = code_verifier` | Avoid unless there is a specific compatibility requirement |

### Method A: `S256`

The client computes:

```
verifier = random secret

challenge = BASE64URL(SHA256(verifier))
```

The authorization server receives only the challenge during authorization.

At the token endpoint, the client sends the verifier. The server calculates its SHA-256 challenge and compares it with the stored challenge.

An observer who sees the challenge cannot feasibly recover a properly generated, high-entropy verifier from its SHA-256 hash.

You cannot feasibly recover the `code_verifier` from the code_challenge when using `S256`, assuming the verifier was generated securely and randomly.

### Method B: `plain`

With the `plain` method:

```
code_challenge = code_verifier
```

The initial authorization request exposes the verifier itself as the challenge. This eliminates the protection against an observer who can obtain both the authorization code and the challenge.

Therefore, use `S256` whenever possible. Modern implementations should not choose `plain` merely because it is simpler.

## PKCE flow

Let's follow a complete authorization-code flow for an online-shopping mobile application using Keycloak.

Assume these components:

- Client: the shopping mobile app.
- Authorization server: Keycloak.
- Resource server: the Spring Boot shopping API.
- User: the customer who wants to view their orders.

PKCE sequence
```
|-------------------------------------------------------------------------------------------|
|Step 1 — Mobile app
|
|Generate a random `code_verifier` and derive the `S256` `code_challenge`.
|-------------------------------------------------------------------------------------------|
        ↓
|-------------------------------------------------------------------------------------------|
|Step 2 — Keycloak authorization endpoint                                                   |
|Receive `client_id`, `redirect_uri`, `code_challenge`, and `code_challenge_method=S256`.   |
|Authenticate the customer and obtain any required consent.                                 |
|-------------------------------------------------------------------------------------------|
        ↓|
|-------------------------------------------------------------------------------------------|
|Step 3 — Redirect to the mobile app                                                        |
|                                                                                           |
|Return an authorization code through the registered redirect URI.                          |
|-------------------------------------------------------------------------------------------|
        ↓|
|-------------------------------------------------------------------------------------------|
|Step 4 — Mobile app to Keycloak token endpoint                                             |
|                                                                                           |
|Submit the authorization code and the original `code_verifier`.                            |
|-------------------------------------------------------------------------------------------|
        ↓|
|-------------------------------------------------------------------------------------------|
|Step 5 — Keycloak validates PKCE                                                           |
|                                                                                           |
|Recalculate the challenge and compare it with the challenge                                |
|stored for the authorization code.                                                         |
|-------------------------------------------------------------------------------------------
        ↓
|-------------------------------------------------------------------------------------------
|Step 6 — Tokens returned
|
|If all required checks succeed, issue tokens. 
|The mobile app can use its access token to call the Spring Boot API.
|-------------------------------------------------------------------------------------------
```
### Step 1: Generate the verifier and challenge

When the native app begins the authorization request, instead of immediately launching a browser, the client first creates what is known as a “code verifier“. This is a cryptographically random string using the characters A-Z, a-z, 0-9, and the punctuation characters -._~ (hyphen, period, underscore, and tilde), between 43 and 128 characters long.

Once the app has generated the code verifier, it uses that to derive the code challenge.

The client generates both values before starting authorization.

```Java
String verifier = generateCodeVerifier();
String challenge = generateS256Challenge(verifier);
```

The client retains the verifier securely for the duration of the authorization transaction.

### Step 2: Send the authorization request

The client redirects the customer to Keycloak:

```
GET /realms/shop/protocol/openid-connect/auth?
    response_type=code&
    client_id=shopping-mobile&
    redirect_uri=com.example.shop:/callback&
    scope=openid%20orders&
    state=random_state&
    code_challenge=calculated_challenge&
    code_challenge_method=S256
```
a complete authorization request will include the following parameters.

- response_type=code – indicates that your server expects to receive an authorization code
- client_id= – The client ID you received when you first created the application
- redirect_uri= – Indicates the URL to return the user to after authorization is complete, such as org.example.app://redirect
- state=1234zyx – A random string generated by your application, which you’ll verify later
- code_challenge=XXXXXXXXX – The code challenge generated as previously described
- code_challenge_method=S256 – either plain or S256, depending on whether the challenge is the plain verifier string or the - SHA256 hash of the string.

The `state` parameter is included to help correlate the response with the original request and protect against request-forgery and response-injection attacks. The client must validate it when processing the response.

The authorization server records the challenge and associates it with the authorization transaction.

The authorization server should recognize the `code_challenge` parameter in the request, and associate that with the authorization code it generates. Either store this in the database along with the authorization code, or if you’re using self-encoded authorization codes then it can be included in the code itself. (See The Authorization Response for details.) The server returns the authorization code as normal, and does not include the challenge in the data returned.

### Step 3: Receive the authorization code

After successful authentication and authorization, Keycloak redirects to the registered URI:

```
com.example.shop:/callback
    ?code=AUTHORIZATION_CODE
    &state=random_state
```

The client validates `state` and extracts the authorization code.

An attacker might intercept this redirect and obtain `AUTHORIZATION_CODE`. PKCE is designed to prevent that code alone from being sufficient to obtain tokens.

### Step 4: Exchange the code for tokens

The client sends a request to Keycloak's token endpoint:

The application will then exchange the authorization code for an access token. 

```
POST /realms/shop/protocol/openid-connect/token
Content-Type: application/x-www-form-urlencoded
```

Form body:

```
grant_type=authorization_code
&client_id=shopping-mobile
&code=AUTHORIZATION_CODE
&redirect_uri=com.example.shop:/callback
&code_verifier=ORIGINAL_RANDOM_VERIFIER
```

In addition to the parameters defined in Authorization Code Request , the client will also send the `code_verifier` parameter. A complete access token request will include the following parameters:

- grant_type=authorization_code – Indicates the grant type of this token request
- code – The client will send the authorization code it obtained in the redirect
- redirect_uri – The redirect URL that was used in the initial authorization request
- client_id – The application’s registered client ID
- client_secret (optional) – The application’s registered client secret if it was issued a secret
- code_verifier – The code verifier for the PKCE request, that the app originally generated before the authorization request.

The `code_verifier` is the original random string, not the challenge.

Since the `code_challenge` and `code_challenge_method` were associated with the authorization code initially, the server should already know which method to use to verify the code_verifier.

### Step 5: Validate the verifier

If the method is plain, then the authorization server needs only to check that the provided `code_verifier` matches the expected `code_challenge` string. If the method is S256, then the authorization server should take the provided `code_verifier` and transform it using the same hash method, then comparing it to the stored `code_challenge` string.

Keycloak performs the PKCE check conceptually as follows:

```
stored_challenge = challenge saved at authorization time

received_verifier = verifier from token request

calculated_challenge =
    BASE64URL(SHA256(received_verifier))

if calculated_challenge == stored_challenge:
    PKCE validation succeeds
else:
    reject token request
```

The authorization server must also perform the other required authorization-code and client checks. A successful PKCE check by itself does not guarantee token issuance.

### Step 6: Return tokens and call the API

If the verifier matches the expected value, then the server can continue on as normal, issuing an access token and responding appropriately. If there is a problem, then the server responds with an `invalid_grant` error.

The PKCE extension does not add any new responses, so clients can always use the PKCE extension even if an authorization server does not support it.

If validation succeeds, Keycloak can return a response such as:

```json
{
  "access_token": "ACCESS_TOKEN",
  "token_type": "Bearer",
  "expires_in": 300,
  "refresh_token": "REFRESH_TOKEN"
}
```

The mobile application then calls the protected API:

```
GET /api/orders
Authorization: Bearer ACCESS_TOKEN
```

The Spring Boot resource server validates the access token and applies its authorization rules. It does not normally repeat the PKCE verification; PKCE protects the earlier authorization-code exchange.

## PKCE for public clients

A public client is an OAuth client that cannot reliably keep credentials confidential. Typical examples include:

- Native mobile applications (Android and iOS).
- Single-page applications (SPAs) running in a browser.
- Desktop applications distributed to end users.

### Why public clients need PKCE

Suppose you build an Android shopping application and configure it with:

```
client_id = shopping-mobile
client_secret = ?
```

You cannot safely embed a shared client secret in the APK. An attacker could inspect the application package, extract the secret, and reuse it.

A client ID is not secret, and PKCE does not turn it into one.

Without PKCE, an intercepted authorization code could potentially be exchanged by another party. With PKCE, the token requester must also possess the original verifier.

| Without PKCE                                                             | With PKCE                                              |
| ------------------------------------------------------------------------ | ------------------------------------------------------ |
| Authorization code is the key piece of evidence needed for the exchange. | Authorization code and matching verifier are required. |
| An intercepted code may be usable by an attacker.                        | An intercepted code alone is insufficient.             |
| No proof ties the exchange to the original challenge.                    | The exchange is bound to the original challenge.       |

For public clients, use Authorization Code Flow with PKCE and `S256`.

A few important details:

- Use the system browser or another appropriate external user agent for user authentication in native applications.
- Use registered redirect URIs and validate the OAuth `state` parameter.
- Generate a new verifier for each authorization transaction.
- Protect tokens and the verifier from unnecessary exposure.
- Do not rely on a hardcoded client secret as proof of a native app's identity.

PKCE does not prevent every attack against a compromised device, malicious application, or stolen access token. **It specifically protects the authorization-code exchange**.

## PKCE for confidential clients

A confidential client can keep its credentials secret in a protected environment, such as a server-side application.

Examples include:

- A Spring Boot backend that performs OAuth authorization-code exchanges.
- A server-rendered web application.
- A backend-for-frontend (BFF) that manages browser sessions.

Such clients can authenticate themselves at the token endpoint using methods such as HTTP Basic client authentication or `private_key_jwt`, depending on the authorization server's configuration.

### Why use PKCE if the client already has a secret?

Client authentication and PKCE solve different problems.

| Mechanism               | What it proves or protects                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| Client authentication   | The token requester can authenticate as the registered client.                                  |
| PKCE                    | The token requester possesses the verifier associated with the original authorization request.  |
| Redirect URI validation | Helps prevent an authorization code from being delivered to an unapproved destination.          |
| `state` validation      | Helps correlate the response with the initiating request and defend against CSRF-style attacks. |

Imagine a confidential web application whose authorization code is leaked through an insecure redirect, browser history, logging, or another unintended channel.

Even though the application has a client secret, an attacker who obtains the code might attempt to redeem it. PKCE adds a further requirement: the matching verifier.

However, PKCE is not a substitute for client authentication. A confidential client should normally use both client authentication and PKCE.

A conceptual token request might contain:

```
POST /token
Authorization: Basic BASE64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded
```

Form body:

```
grant_type=authorization_code
&code=AUTHORIZATION_CODE
&redirect_uri=https://shop.example.com/callback
&code_verifier=ORIGINAL_RANDOM_VERIFIER
```

The exact client-authentication mechanism and request format depend on the authorization server. The important point is that both checks apply: client authentication establishes the client's identity, while PKCE validates possession of the verifier.

For modern OAuth deployments, PKCE is recommended for confidential clients as well as public clients.

## Error Response

The authorization server can require that public clients must use the PKCE extension. This is really the only way to allow native apps to have a secure authorization flow without using the client secret, especially without the redirect URI security that’s available with web-based clients. Since the authorization server should know that a specific client ID corresponds to a public client, it can deny authorization requests for public clients that do not contain a code challenge.

If the authorization server requires public clients to use PKCE, and the authorization request is missing the code challenge, then the server should return the error response with error=invalid_request and the error_description or error_uri should explain the nature of the error.
## PKCE security properties

PKCE provides a useful security boundary, but understanding what it does and does not protect is essential.

### What PKCE protects against

- Authorization-code interception

An attacker obtains the authorization code but lacks the verifier required to redeem it successfully.

- Unauthorized code redemption

A party that steals a code cannot simply exchange it for tokens without satisfying the PKCE check.

- Binding the exchange to the original transaction

The authorization server checks the verifier against the challenge associated with the authorization code.

### What PKCE does not protect against

| Threat                         | Why PKCE alone is insufficient                                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Phishing                       | A user can still be tricked into authenticating on a malicious site.                                                          |
| Compromised client             | Malware that can read the verifier or control the app may bypass the intended protection.                                     |
| Access-token theft             | PKCE protects the code exchange, not subsequent use of a stolen access token.                                                 |
| CSRF and response injection    | `state`, appropriate transaction binding, and correct OAuth/OIDC response validation remain important.                        |
| Open redirectors               | Incorrect redirect handling can expose authorization responses; PKCE is not a replacement for strict redirect URI validation. |
| Weak verifier generation       | Predictable verifiers undermine the protection PKCE is meant to provide.                                                      |
| Malicious authorization server | PKCE does not make an untrusted authorization server trustworthy.                                                             |

### Important implementation rules

1. Prefer `S256`; do not use `plain` when `S256` is supported.
2. Generate a cryptographically random verifier with the required length and character set.
3. Use a fresh verifier for each authorization transaction.
4. Ensure the authorization server requires PKCE where appropriate and validates it correctly.
5. Never log verifiers, authorization codes, access tokens, or refresh tokens unnecessarily.
6. Validate redirect URIs, `state`, and—when using OpenID Connect—relevant ID token claims such as `iss`, `aud`, and `nonce` when applicable.
7. Use TLS for authorization and token endpoint communication.
8. Continue to validate access tokens and enforce authorization at the resource server.

### A subtle but important point: PKCE is not encryption

The code challenge is visible to parties who can observe the authorization request. Its security comes from using a one-way hash with a sufficiently random verifier, not from hiding the challenge.

Also, the token endpoint should reject a missing or incorrect verifier when PKCE is required. A server that silently skips the check can defeat the protection.

## Final comparison: the complete picture

| Concept                                  | Generated or handled by | Sent at which stage?             | Purpose                                         |
| ---------------------------------------- | ----------------------- | -------------------------------- | ----------------------------------------------- |
| `code_verifier`                          | OAuth client            | Token request                    | Proves possession of the original random value  |
| `code_challenge`                         | OAuth client            | Authorization request            | Commits the client to the verifier              |
| `code_challenge_method`                  | OAuth client            | Authorization request            | Specifies the transformation, preferably `S256` |
| Authorization code                       | Authorization server    | Authorization response           | Short-lived credential exchanged for tokens     |
| Client secret or other client credential | Confidential client     | Token request, when configured   | Authenticates the client                        |
| Access token                             | Authorization server    | Token response, then API request | Grants access to protected resources            |

The essential distinction is this:

- Authorization code: grants the opportunity to request tokens.
- PKCE verifier: proves possession of the value tied to the original authorization transaction.
- Client authentication: authenticates a confidential client.
- Access token: authorizes access to protected APIs, subject to the resource server's validation and authorization policies.

For your Spring Boot and Keycloak studies, a good next step is to implement the Authorization Code Flow with PKCE for a native or SPA client, then observe what happens when the token request uses the wrong verifier, omits the verifier, or attempts to reuse an authorization code.
