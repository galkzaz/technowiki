{/* ## Lab: OAuth Native App with Android Custom URL Scheme */}

In the previous lab, the redirect was:

```text
https://shop.example.com/oauth/callback
```

and Android used **HTTPS URL matching + App Links**.

In this lab we replace that with a **custom URL scheme**:

```text
shoppingapp://oauth/callback
```

The important difference is:

```text
Previous lab:
HTTPS URL
    ↓
Android URL matching
    ↓
Verified App Link
    ↓
Ionic App

This lab:
Custom URL scheme
    ↓
Android intent filter
    ↓
Ionic App
```

There is **no `assetlinks.json`**, no HTTPS domain verification, and no App Links.

We'll still use:

* Ionic Angular
* Capacitor
* Android
* Keycloak
* OAuth 2.0 Authorization Code Flow
* PKCE
* `state`
* System Browser
* Custom URL Scheme

## 2. What Changes from the App Links Lab?

The previous lab had:

```text
https://shop.example.com/oauth/callback
```

and required:

```text
AndroidManifest.xml
        +
assetlinks.json
        +
HTTPS domain
        +
certificate fingerprint
```

This lab uses:

```text
shoppingapp://oauth/callback
```

and requires only:

```text
AndroidManifest.xml
        +
custom scheme registration
```

So:

|                                       | HTTPS App Link                            | Custom URL Scheme              |
| ------------------------------------- | ----------------------------------------- | ------------------------------ |
| Redirect                              | `https://shop.example.com/oauth/callback` | `shoppingapp://oauth/callback` |
| HTTPS                                 | Yes                                       | No                             |
| Domain                                | Required                                  | No                             |
| `assetlinks.json`                     | Required                                  | No                             |
| Certificate verification              | Yes                                       | No                             |
| Android intent filter                 | Yes                                       | Yes                            |
| PKCE                                  | Yes                                       | Yes                            |
| Risk of another app claiming redirect | Lower                                     | Higher                         |

That last row is why **PKCE is especially important** with custom schemes.

## 5. What Is a Custom URL Scheme?

A normal HTTPS URL looks like:

```text
https://shop.example.com/oauth/callback
```

A custom-scheme URL looks like:

```text
shoppingapp://oauth/callback
```

Break it down:

```text
shoppingapp://oauth/callback
│           │    │
│           │    └── path
│           └─────── host
└─────────────────── scheme
```

The scheme is:

```text
shoppingapp
```

Android will be configured to say:

> "I can handle URLs whose scheme is `shoppingapp`."

## 6. Configure the Android Intent Filter

Open:

```text
android/app/src/main/AndroidManifest.xml
```

Find the `MainActivity`.

Configure it like this:

```xml
<activity
    android:name=".MainActivity"
    android:exported="true"
    android:launchMode="singleTask">

    <intent-filter>
        <action android:name="android.intent.action.MAIN" />

        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>

    <intent-filter>
        <action android:name="android.intent.action.VIEW" />

        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />

        <data
            android:scheme="shoppingapp"
            android:host="oauth"
            android:path="/callback" />

    </intent-filter>

</activity>
```

The important part is:

```xml
<data
    android:scheme="shoppingapp"
    android:host="oauth"
    android:path="/callback" />
```

This tells Android:

```text
shoppingapp://oauth/callback
        │       │
        │       └── path = /callback
        └────────── host = oauth
```

## 7. Compare It with HTTPS Matching

In the previous lab we had:

```xml
<data
    android:scheme="https"
    android:host="shop.example.com"
    android:pathPrefix="/oauth" />
```

Now we have:

```xml
<data
    android:scheme="shoppingapp"
    android:host="oauth"
    android:path="/callback" />
```

So Android is still doing **URL matching**.

The only difference is the scheme.

#### HTTPS

```text
https://shop.example.com/oauth/callback
│       │                 │
scheme  host              path
```

#### Custom scheme

```text
shoppingapp://oauth/callback
│             │    │
scheme        host path
```

Therefore:

> **Custom URL schemes still use Android URL matching.**

What they don't have is the **verified HTTPS domain association** that App Links provide.

## 19. Generate PKCE in Ionic

Create:

```text
src/app/oauth.service.ts
```

```typescript
import { Injectable } from '@angular/core';

@Injectable({
  providedIn: 'root'
})
export class OAuthService {

  private readonly clientId =
    'shopping-mobile';

  private readonly authorizationEndpoint =
    'http://localhost:8080/realms/shop/protocol/openid-connect/auth';

  private readonly tokenEndpoint =
    'http://localhost:8080/realms/shop/protocol/openid-connect/token';

  private readonly redirectUri =
    'shoppingapp://oauth/callback';


  async createLoginUrl(): Promise<string> {

    const codeVerifier =
      this.generateCodeVerifier();

    const codeChallenge =
      await this.generateCodeChallenge(
        codeVerifier
      );

    const state =
      this.generateRandomString(32);

    localStorage.setItem(
      'oauth_code_verifier',
      codeVerifier
    );

    localStorage.setItem(
      'oauth_state',
      state
    );

    const params =
      new URLSearchParams({
        client_id: this.clientId,

        response_type: 'code',

        redirect_uri:
          this.redirectUri,

        scope:
          'openid profile',

        state,

        code_challenge:
          codeChallenge,

        code_challenge_method:
          'S256'
      });

    return (
      `${this.authorizationEndpoint}?${params}`
    );
  }


  private generateCodeVerifier():
    string {

    const bytes =
      new Uint8Array(32);

    crypto.getRandomValues(
      bytes
    );

    return this.base64UrlEncode(
      bytes
    );
  }


  private async generateCodeChallenge(
    verifier: string
  ): Promise<string> {

    const data =
      new TextEncoder()
        .encode(verifier);

    const digest =
      await crypto.subtle.digest(
        'SHA-256',
        data
      );

    return this.base64UrlEncode(
      new Uint8Array(digest)
    );
  }


  private generateRandomString(
    length: number
  ): string {

    const bytes =
      new Uint8Array(length);

    crypto.getRandomValues(
      bytes
    );

    return this.base64UrlEncode(
      bytes
    );
  }


  private base64UrlEncode(
    bytes: Uint8Array
  ): string {

    let binary = '';

    bytes.forEach(
      byte => {
        binary +=
          String.fromCharCode(byte);
      }
    );

    return btoa(binary)
      .replace(/\+/g, '-')
      .replace(/\//g, '_')
      .replace(/=/g, '');
  }


  async exchangeCode(
    code: string
  ): Promise<any> {

    const codeVerifier =
      localStorage.getItem(
        'oauth_code_verifier'
      );

    if (!codeVerifier) {
      throw new Error(
        'Missing code_verifier'
      );
    }

    const body =
      new URLSearchParams({
        grant_type:
          'authorization_code',

        client_id:
          this.clientId,

        code,

        redirect_uri:
          this.redirectUri,

        code_verifier:
          codeVerifier
      });

    const response =
      await fetch(
        this.tokenEndpoint,
        {
          method: 'POST',

          headers: {
            'Content-Type':
              'application/x-www-form-urlencoded'
          },

          body
        }
      );

    if (!response.ok) {

      throw new Error(
        await response.text()
      );
    }

    return response.json();
  }
}
```

## 20. Why We Store `code_verifier`

When login begins:

```text
Native App
    │
    ├── code_verifier = SECRET
    │
    └── code_challenge = SHA256(verifier)
```

Only this is sent to Keycloak initially:

```text
code_challenge
```

The verifier stays with the application.

Later:

```text
Keycloak
    │
    │ authorization code
    ▼
shoppingapp://oauth/callback
    │
    ▼
Native App
    │
    │ code + code_verifier
    ▼
Keycloak
```

This protects against authorization-code interception.

## 21. Open the System Browser

Use Capacitor's Browser API.

Update:

```text
src/app/app.component.ts
```

```typescript
import { Component, OnInit } from '@angular/core';
import { App } from '@capacitor/app';
import { Browser } from '@capacitor/browser';
import { OAuthService } from './oauth.service';

@Component({
  selector: 'app-root',
  templateUrl: 'app.component.html',
})
export class AppComponent
  implements OnInit {

  receivedUrl = '';

  constructor(
    private oauth: OAuthService
  ) {}


  async ngOnInit() {

    App.addListener(
      'appUrlOpen',
      async event => {

        console.log(
          'OAuth redirect:',
          event.url
        );

        this.receivedUrl =
          event.url;

        await this.handleOAuthRedirect(
          event.url
        );
      }
    );


    const launch =
      await App.getLaunchUrl();

    if (launch?.url) {

      await this.handleOAuthRedirect(
        launch.url
      );
    }
  }


  async login() {

    const url =
      await this.oauth
        .createLoginUrl();

    await Browser.open({
      url
    });
  }


  private async handleOAuthRedirect(
    url: string
  ) {

    const parsed =
      new URL(url);

    if (
      parsed.protocol !==
      'shoppingapp:'
    ) {
      return;
    }

    if (
      parsed.hostname !==
      'oauth'
    ) {
      return;
    }

    if (
      parsed.pathname !==
      '/callback'
    ) {
      return;
    }

    const error =
      parsed.searchParams
        .get('error');

    if (error) {

      console.error(
        'OAuth error:',
        error
      );

      return;
    }

    const code =
      parsed.searchParams
        .get('code');

    const returnedState =
      parsed.searchParams
        .get('state');

    const expectedState =
      localStorage.getItem(
        'oauth_state'
      );

    if (
      !returnedState ||
      returnedState !== expectedState
    ) {

      throw new Error(
        'Invalid OAuth state'
      );
    }

    if (!code) {

      throw new Error(
        'Missing authorization code'
      );
    }

    await Browser.close();

    const tokens =
      await this.oauth
        .exchangeCode(code);

    console.log(
      'Access token:',
      tokens.access_token
    );
  }
}
```

## 29. Exchange the Code

If `state` is valid:

```text
code
+
code_verifier
```

are sent to:

```text
POST /realms/shop/protocol/openid-connect/token
```

Conceptually:

```http
POST /realms/shop/protocol/openid-connect/token

Content-Type:
application/x-www-form-urlencoded

grant_type=authorization_code
&client_id=shopping-mobile
&code=ABC123
&redirect_uri=shoppingapp://oauth/callback
&code_verifier=XYZ...
```

Keycloak checks:

```text
SHA256(code_verifier)
        ==
original code_challenge
```

If correct:

```text
HTTP 200
```

and returns tokens.

For example:

```json
{
  "access_token": "...",

  "token_type": "Bearer",
  "id_token": "..."
}
```

## 31. The Security Problem with This Approach

Now we reach the most important difference from App Links.

Suppose another application installs:

```text
MaliciousApp
```

and declares:

```xml
<data
    android:scheme="shoppingapp"
    android:host="oauth"
    android:path="/callback" />
```

Now both applications claim:

```text
shoppingapp://oauth/callback
```

Conceptually:

```text
             shoppingapp://oauth/callback
                         │
                 ┌───────┴───────┐
                 │               │
                 ▼               ▼
           ShoppingApp      MaliciousApp
```

There is no HTTPS domain that Android can verify against.

That's the fundamental weakness of custom URL schemes.

---

## 32. Why PKCE Matters Even More Here

Suppose the malicious app intercepts:

```text
shoppingapp://oauth/callback?code=ABC
```

It gets:

```text
authorization_code = ABC
```

But the legitimate application generated:

```text
code_verifier = SECRET
```

and the malicious application doesn't know it.

The attacker tries:

```text
POST /token

code=ABC
code_verifier=???
```

Keycloak checks:

```text
SHA256(???)
       ≠
original code_challenge
```

and rejects the request.

Therefore:

```text
Custom Scheme
     +
PKCE
     ↓
Interception doesn't automatically
give attacker the access token
```

This is one of the major reasons **PKCE is mandatory/strongly expected for native applications**.

## 35. The Android Manifest Is the Key

The entire custom URL registration boils down to:

```xml
        android:name=
```

```text
        │       └────────── oauth
```

## 38. The Most Important Conceptual Diagram

This lab demonstrates exactly where **Custom URL Schemes** fit into your OAuth Native Apps TOC:

```text
OAuth for Native Apps
│
├── Architecture
│
├── External User-Agent
│   └── System Browser
│
├── Redirect URIs
│   │
│   ├── HTTPS URL Matching
│   │   │
│   │   └── App-Claimed URLs
│   │       ├── Android App Links
│   │       └── iOS Universal Links
│   │
│   └── Custom URL Schemes
│       │
│       └── shoppingapp://oauth/callback
│
└── PKCE
```

And the security comparison is:

```text
                   Redirect URI
                       │
             ┌─────────┴──────────┐
             │                    │
       HTTPS URL             Custom Scheme
             │                    │
             ▼                    ▼
      https://...          shoppingapp://...
             │                    │
             ▼                    ▼
       URL matching          URL matching
             │                    │
             ▼                    │
      Domain verification         │
             │                    │
             ▼                    │
       App Links             No domain
       Universal Links       verification
             │                    │
             └─────────┬──────────┘
                       │
                       ▼
                      PKCE
                       │
                       ▼
               Authorization Code
                  Protection
```

### The key lesson

**Custom URL Scheme** and **App Link** both ultimately use Android's URL/intent matching to get the OAuth response back into the application.

The difference is **how strongly the operating system can establish that the receiving app is the legitimate application**:

```text
Custom URL Scheme
─────────────────
shoppingapp://...
       │
       ▼
"I registered this scheme."

No domain ownership verification.


App Link
────────
https://shop.example.com/...
       │
       ▼
"I registered this URL pattern."
       +
       │
       ▼
"Android verified that I am authorized
to associate with shop.example.com."
```

And because a custom scheme can potentially be claimed by another app, **PKCE is critical**:

```text
Custom Scheme
      +
PKCE
      ↓
Intercepted authorization code
      ≠
Access token
```

That is the central security model you should retain for **OAuth Native Apps → Custom URL Schemes**.
