The traditional way for a class to allow a client to obtain an instance is to provide
a public constructor. There is another technique that should be a part of every
programmer’s toolkit. A class can provide a public **Static factory method**, which is
simply a static method that returns an instance of the class. 

Here’s a simple example from Boolean (the boxed primitive class for boolean). This method translates a boolean primitive value into a Boolean object reference:
```java
public static Boolean valueOf(boolean b) {
    return b ? Boolean.TRUE : Boolean.FALSE;
}
```

A **Static factory method** is a static method in a class that returns an instance of that class (or a subtype), instead of creating objects directly using a constructor.

Instead of writing:
```java
User user = new User("user", 25);
```
You write:
```java
User user = User.create("user", 25);
```
Where:
```java
class User {
    private String name;
    private int age;

    private User(String name, int age) {  // constructor can be private
        this.name = name;
        this.age = age;
    }

    public static User create(String name, int age) {
        return new User(name, age);
    }
}
```
**Static Factory Methods** are fundamentally a creational pattern alternative to constructors:
- Encapsulate object creation
- Allow naming (e.g., of(), valueOf())
- Enable caching, reuse, polymorphism

A class can provide its clients with static factory methods instead of, or in addition to, public constructors.

a static factory method is not the same as the Factory Method pattern from Design Patterns.

## Advantages
Providing a static factory method instead of a public constructor has both advantages and disadvantages.

This is usually listed as:
1. Named constructors (readability)
2. Instance control (caching, reuse)
3. Return subtype
4. Return different implementations based on input
5. Return implementations that may not exist yet (SPI / pluggability) 

Static factory methods give you:
- runtime flexibility 
- performance tuning 
- API stability across versions 
- implementation hiding 

This is why they are heavily used in core Java libraries.


### Named constructors

One advantage of static factory methods is that, unlike constructors, they
have names. If the parameters to a constructor do not, in and of themselves,
describe the object being returned, a static factory with a well-chosen name is
easier to use and the resulting client code easier to read(They can have meaningful names).

Constructors are limited to the class name, but factory methods can express intent:
```java
User.of("test", 25);
User.fromJson(json);
User.guestUser();
```
Much clearer than overloaded constructors.

For example, the constructor `BigInteger(int, int, Random)`, which returns a `BigInteger` that is
probably prime, would have been better expressed as a static factory method
named `BigInteger.probablePrime`. (This method was added in Java 4.)

:::info

In Java, `BigInteger.probablePrime(int bitLength, Random rnd)` is a static method in the `java.math.BigInteger` class that returns a randomly generated positive `BigInteger` of a specified bit length that is "probably" prime. 

:::

A class can have only a single constructor with a given signature. Program-
mers have been known to get around this restriction by providing two constructors
whose parameter lists differ only in the order of their parameter types. This is a
really bad idea. The user of such an API will never be able to remember which
constructor is which and will end up calling the wrong one by mistake. People
reading code that uses these constructors will not know what the code does
without referring to the class documentation

Because they have names, static factory methods don’t share the restriction
discussed in the previous paragraph. In cases where a class seems to require
multiple constructors with the same signature, replace the constructors with static
factory methods and carefully chosen names to highlight their differences.

### Can cache and reuse instances

A second advantage of static factory methods is that, unlike constructors,
they are not required to create a new object each time they’re invoked(They can control object creation (caching / reuse)). 

A constructor must create a new object every time:
```java
Boolean b1 = new Boolean(true);
Boolean b2 = new Boolean(true);

System.out.println(b1 == b2); // false
```
Always different objects.

This allows immutable classes to use preconstructed instances, or to cache
instances as they’re constructed, and dispense them repeatedly to avoid creating
unnecessary duplicate objects. 

The `Boolean.valueOf(boolean)` method illustrates this technique: it never creates an object. 
```java
Boolean b1 = Boolean.valueOf(true);
Boolean b2 = Boolean.valueOf(true);

System.out.println(b1 == b2); // true
```
Same object reused.

Internally, something like this happens((Caching / Reuse)):
```java
public static final Boolean TRUE = new Boolean(true);
public static final Boolean FALSE = new Boolean(false);

public static Boolean valueOf(boolean b) {
    return b ? TRUE : FALSE;
}
```
Only two instances ever exist.

This technique is similar to the  Flyweight pattern. 

**Advantages**
- performance
    - It can greatly improve performance if equivalent objects are requested often, especially if they are expensive to create.
    - Avoid object creation (which is expensive under heavy load)
    - Reduce GC pressure
    - Improve memory locality
    - Very important in high-throughput systems (microservices)
- Identity Guarantees
    - The ability of static factory methods to return the same object from repeated invocations allows classes to maintain strict control over what instances exist at any time. 
    - Classes that do this are said to be **instance-controlled**. 
    - Normally:
        ```java
        a.equals(b)  // compares value
        a == b       // compares reference
        ```
        With caching:
        ```java
        a.equals(b) && a == b
        ```
    Both are true, This is called instance control
    - There are several reasons to write instance-controlled classes. A class that controls its instances can guarantee:
      - Singleton
          - Instance control allows a class to guarantee that it is a singleton or noninstantiable. 
          - Only one instance exists
      - Limited instances
          - (e.g., Boolean → only TRUE/FALSE)
      - Canonical instances
          - Also, it allows an immutable value class to make the guarantee that no two equal instances exist: a.equals(b) if and only if a == b. This means:
              - No duplicate objects exist
              - Equality becomes identity
              -  Extremely powerful optimization
          - No duplicates for equal values
          - This is the basis of the Flyweight pattern(Reuse shared objects instead of creating new ones.). 
          - Instead of:
              ```java
              new Color(255, 0, 0); // created many times
              ```
              Use:
              ```java
              Color.of(255, 0, 0); // returns cached instance
              ```
              Only one "red" object exists.
          - Enum types provide this guarantee

**Real Java Examples**
1. **Boolean.valueOf**
Only 2 objects
2. **Integer.valueOf**
```java
Integer a = Integer.valueOf(100);
Integer b = Integer.valueOf(100);

System.out.println(a == b); // true (cached)
```
But:
```java

Integer y = Integer.valueOf(1000);

System.out.println(x == y); // false (not cached)
```
JVM caches small integers (usually -128 to 127)

3. **Enum (STRONGEST guarantee)**
```java
enum Status {
    SUCCESS, FAILED
}
Status s1 = Status.SUCCESS;
Status s2 = Status.SUCCESS;

System.out.println(s1 == s2); // always true
```
Enums are instance-controlled by design

**Why Immutable Classes Benefit Most**

For mutable objects:
```java
user.setName("X"); // changes state
```
Sharing is dangerous.

For immutable objects:
```java
String s = "hello";
```
Safe to reuse because state never changes.

**Real Microservices Impact**

In high-scale systems:
- Millions of requests 
- Thousands of identical values (IDs, statuses, configs) 

Using caching:
- reduces heap usage 
- reduces GC pauses 
- improves latency 

**When NOT to Use This**

Don’t force caching when:
- Objects are large and rarely reused 
- Cache management becomes complex 
- Memory overhead > benefit

### Can return subtype
A third advantage of static factory methods is that, unlike constructors,
they can return an object of any subtype of their return type. This gives you
great flexibility in choosing the class of the returned object.
```java
public static List<String> createList() {
    return new ArrayList<>();
}
```
The caller only sees List, not the actual implementation.

a very powerful design advantage of static factory methods they can return any subtype of their declared return type, including **non-public implementation classes**, which enables strong abstraction and clean APIs.

**Hiding implementation classes**

One application of this flexibility is that an API can return objects without
making their classes public. Hiding implementation classes in this fashion leads to
a very compact API. This technique lends itself to interface-based frameworks, where interfaces provide natural return types for static factory methods.

With constructors:
```java
List<String> list = new ArrayList<>();
```
You know the exact implementation (ArrayList).

With static factory methods:
```java
List<String> list = Collections.emptyList();
```
You only see List, but you don’t know (or care) what class is returned.

A static factory method can return:
- A subclass 
- A hidden class 
- A cached instance 
- Even different implementations based on input 

Example:
```java
interface PaymentService {
    void pay();
    static PaymentService create(String type) {
        return switch (type) {
            case "stripe" -> new StripePaymentService();
            case "paypal" -> new PaypalPaymentService();
            default -> throw new IllegalArgumentException();
        };
    }
}
```
Return type is interface, but implementation varies.

You can make implementation classes non-public:
```java
interface PaymentService {
    void pay();
    static PaymentService stripe() {
        return new StripeServiceImpl(); // hidden class
    }
}
// package-private class (NOT public)
class StripeServiceImpl implements PaymentService {
    public void pay() {
        System.out.println("Stripe payment");
    }
}
```
Result:

Client code:
```java
PaymentService service = PaymentService.stripe();
```
Client does NOT know:
- class name 
- package structure 
- implementation details 

**Makes APIs Smaller**
The Collections Framework API is much smaller than it would have been had
it exported forty-five separate public classes, one for each convenience implementation. It is not just the bulk of the API that is reduced but the conceptual weight:
the number and difficulty of the concepts that programmers must master in order
to use the API. The programmer knows that the returned object has precisely the
API specified by its interface, so there is no need to read additional class docu-
mentation for the implementation class. Furthermore, using such a static factory
method requires the client to refer to the returned object by interface rather than
implementation class, which is generally good practice

Without factories:

Client must know:
- ArrayList
- LinkedList
- HashSet
- TreeSet
- CopyOnWriteArrayList
- ...

With factories:
- List.of()
- Collections.emptyList()
- Collections.synchronizedList(...)

Client only learns:
- List 
- Set 
- Map

**Reduces “Conceptual Weight”**

Instead of learning:
- 45 different classes
- inheritance hierarchies
- implementation details

You only learn: List / Set / Map + factory methods

This is a huge API design win.

**Real Example: Java Collections Framework**

```java
List<String> list = Collections.unmodifiableList(originalList);
```
Internally:
- returns a hidden class 
- not exposed to the user 

```java title="https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/Collections.java#L1477"
public static <T> List<T> unmodifiableList(List<? extends T> list) {
    if (list.getClass() == UnmodifiableList.class || list.getClass() == UnmodifiableRandomAccessList.class) {
       return (List<T>) list;

```

Other examples:

- `Collections.emptyList()`;
- `Collections.singletonList("x")`;

Each returns different internal implementations.

**lends itself to interface-based frameworks**

Example:
```java

```
You depend on: abstraction (`List`), not implementation (`ArrayList`)

### Vary behavior based on input
A fourth advantage of static factories is that the class of the returned object can vary from call to call as a function of the input parameters. Any sub-type of the declared return type is permissible. The class of the returned object can
also vary from release to release.

This “fourth advantage” is where static factory methods become architecturally powerful, not just convenient. They can return different implementations based on input—and even change those implementations across versions—without breaking clients.

```java
public static Shape create(int type) {
    if (type == 1) return new Circle();
    else return new Rectangle();
}
```
A constructor cannot do this flexibly.

**Core Idea**

A static factory method can decide: What is the BEST implementation to return for this input?

instead of always doing:
```
new SomeClass(...)
```

**Real Example: EnumSet (from the JDK)**

In `EnumSet`:
```java
EnumSet<Color> set = EnumSet.of(Color.RED, Color.BLUE);
```
You never know what concrete class you got.

The `EnumSet` class has no public constructors, only static factories.
In the OpenJDK implementation, they return an instance of one of two subclasses, **depending on the size of the underlying enum type**: 
1. Small enums (≤ 64 elements): if it has sixty-four or fewer elements, as most enum types do, the static factories return a `RegularEnumSet` instance, which is backed by a single long(RegularEnumSet → uses a single long (64 bits)); 
2. Large enums (> 64 elements): if the enum type has sixty-five or more elements, the factories return a `JumboEnumSet` instance, backed by a long array(JumboEnumSet → uses long[]).

this is brilliant, Because:
- small enum → ultra-fast bit operations
- large enum → scalable structure

Same API, different optimized implementations.
```java title="https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/EnumSet.java#L112"
    public static <E extends Enum<E>> EnumSet<E> noneOf(Class<E> elementType) {
        Enum<?>[] universe = getUniverse(elementType);
        if (universe == null)
            throw new ClassCastException(elementType + " not an enum");
    
        if (universe.length <= 64)
            return new RegularEnumSet<>(elementType, universe);
        else
            return new JumboEnumSet<>(elementType, universe);
    }
    public static <E extends Enum<E>> EnumSet<E> allOf(Class<E> elementType) {
        EnumSet<E> result = noneOf(elementType);
        result.addAll();
        return result;
    }
```
Imagine:
```java 
enum Status { A, B, C }
```
This has 3 values → small enum

So:
```java 
EnumSet<Status> set = EnumSet.allOf(Status.class);
```
Internally:
```java 
RegularEnumSet (uses one long)
```
Now:
```java 
enum BigEnum { E1, E2, ..., E100 }
```
Internally:
```java 
JumboEnumSet (uses long[])
```
The existence of these two implementation classes is invisible to clients. If `RegularEnumSet` ceased to offer performance advantages for small enum types, it could be eliminated from a future release with no ill effects. Similarly, a future release could add a third or fourth implementation of EnumSet if it proved beneficial for performance. Clients neither know nor care about the class of the object they get back from the factory; they care only that it is some subclass of EnumSet.

So Advantages of this design
1. Performance Optimization

Choose best structure dynamically:
- bitset for small 
- array for large 

2. Future Flexibility

class can vary from release to release, Tomorrow, Java could do:
- SmallEnumSetV2
- CompressedEnumSet
- GPUOptimizedEnumSet 

And your code:
```
EnumSet.of(...)
```
still works unchanged

3. Zero API Change

No need to expose:
- RegularEnumSet
- JumboEnumSet

Cleaner API

4. Client Doesn’t Care

Client logic:
```
if (set.contains(X)) ...
```
Doesn’t depend on implementation

**Compare with Constructor (Why This Is Impossible)**

If constructors were used:
```
new RegularEnumSet(...)
new JumboEnumSet(...)
```
Problems:
- client must know classes 
- tightly coupled 
- cannot switch implementations later

### Enables pluggable / extensible architectures(Support for Service Provider Frameworks (SPI))
A fifth advantage of static factories is that the class of the returned object
need not exist when the class containing the method is written. 

A static factory enables service provider frameworks by allowing implementations to be registered and discovered at runtime, even if those implementations didn’t exist when the factory was written.

That sounds abstract, but it means: Your code depends on an interface, but the actual implementation can be added later by someone else.
#### Example: Notification System (Pluggable)

We want:
- Core system defines API 
- External developers can add new providers later (Email, SMS, WhatsApp…) 

1. Service Interface (known at design time)
```java
public interface NotificationService {
    void send(String message);
}
```
2. Static Factory (written once)
```java
import java.util.*;

public class NotificationFactory {
    private static final Map<String, NotificationService> providers = new HashMap<>();
    // Provider registration API
    public static void register(String name, NotificationService service) {
        providers.put(name.toLowerCase(), service);
    }
    // Service access API (STATIC FACTORY)
    public static NotificationService get(String name) {
        NotificationService service = providers.get(name.toLowerCase());
        if (service == null) {
            throw new IllegalArgumentException("No provider found: " + name);
        }
        return service;
    }
}
```
This is the key:
- `get()` is the static factory 
- It returns something unknown at compile time 

3. Provider Implementations (can be added later)

Email provider
```java
public class EmailService implements NotificationService {
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}
```
SMS provider (could be added later by another team)
```java
public class SmsService implements NotificationService {
    public void send(String message) {
        System.out.println("SMS: " + message);
    }
}
```
4. Registration (can happen at runtime)
```java
public class App {
    public static void main(String[] args) {
        NotificationFactory.register("email", new EmailService());
        NotificationFactory.register("sms", new SmsService());
        NotificationService service = NotificationFactory.get("email");
        service.send("Hello!");
    }
}
```
Such flexible

What Makes This Special

The factory was written BEFORE `SmsService` existed
```
NotificationFactory → knows nothing about SMS
```
Yet:
```java
NotificationFactory.get("sms");
```
works perfectly.

Even More Realistic (Plugin Style)

Imagine:

#### Example: Editor Plugin System
**Goal**

We want:
- Core app knows only Plugin interface 
- Plugins are added as JARs/classes later 
- No ServiceLoader 
- Dynamic discovery at runtime 

1. Plugin API (Core Contract)
```java
public interface EditorPlugin {
    String name();
    void execute(String content);
}
```
2. Plugin Registry (Manual Factory)

Instead of ServiceLoader, we build our own registry:
```java
import java.util.*;
public class PluginRegistry {
    private static final List<EditorPlugin> plugins = new ArrayList<>();
    public static void register(EditorPlugin plugin) {
        plugins.add(plugin);
    }
    public static List<EditorPlugin> getPlugins() {
        return plugins;
    }
}
```
This is your custom service provider framework

3. Plugins (External Modules)

Markdown plugin
```java
public class MarkdownPlugin implements EditorPlugin {
    static {
        PluginRegistry.register(new MarkdownPlugin());
    }
    public String name() {
        return "Markdown Plugin";
    }
    public void execute(String content) {
        System.out.println("[Markdown] " + content.toUpperCase());
    }
}
```
Word Count plugin
```java
public class WordCountPlugin implements EditorPlugin {
    static {
        PluginRegistry.register(new WordCountPlugin());
    }
    public String name() {
        return "Word Counter";
    }
    public void execute(String content) {
        System.out.println("[Words] " + content.split("\\s+").length);
    }
}
```
Important Trick Used Here
```
static block → auto-register at class loading time
```
This replaces ServiceLoader discovery mechanism

4. Plugin Loader (Manual Class Discovery)

We simulate loading plugins dynamically.

Option A: Hardcoded (simple)
```java
public class PluginLoader {
    public static void loadPlugins() {
        // Force class loading (triggers static blocks)
        try {
            Class.forName("MarkdownPlugin");
            Class.forName("WordCountPlugin");
        } catch (ClassNotFoundException e) {
            e.printStackTrace();
        }
    }
}
```
Option B: Package scanning (realistic approach)

In production, you'd scan a package:
```java
public class PluginScanner {
    public static void scanAndLoad() throws Exception {
        String[] classes = {
            "MarkdownPlugin",
            "WordCountPlugin"
        };
        for (String className : classes) {
            Class.forName(className); // triggers static registration
        }
    }
}
```
5. Core Application (Plugin Host)
```java
public class App {
    public static void main(String[] args) throws Exception {
        // Load plugins dynamically
        PluginScanner.scanAndLoad();
        String content = "Hello plugin system";
        for (EditorPlugin plugin : PluginRegistry.getPlugins()) {
            System.out.println("Running: " + plugin.name());
            plugin.execute(content);
        }
    }
}
```
Output
```
Running: Markdown Plugin
[Markdown] HELLO PLUGIN SYSTEM
Running: Word Counter
[Words] 3
```

#### Service Provider Frameworks
Such flexible static factory methods form the basis of service provider frameworks, like the Java
Database Connectivity API (JDBC). 

A service provider framework is a system in
which providers implement a service, and the system makes the implementations
available to clients, decoupling the clients from the implementations.

What is a Service Provider Framework? A service provider framework lets:
- Providers → implement a service 
- Clients → use the service 
- Framework → connects them dynamically 

Clients and implementations are completely decoupled

This is the standard Java SPI mechanism in Java SE. It solves exactly this problem: “Load implementations that didn’t exist when the core system was written.”

There are three essential components in a service provider framework: 
1. **Service interface**:
    - which represents an implementation; 
    - Defines the contract:
      ```java
      public interface PaymentService {
          void pay();
      }
      ```
2. **Provider registration API**
    - which providers use to register implementations; 
    - Providers register themselves:
        ```java
        DriverManager.registerDriver(new MySQLDriver());
        ```
3. **Service access API**
    - which clients use to obtain instances of the service. 
    - The service access API is the flexible static factory that forms the basis of the service provider framework.
        ```java
        Connection conn = DriverManager.getConnection(url);
        ```
        This is the key line:
            - You don’t know which class is returned 
            - It may not have existed when DriverManager was written
    - The service access API may allow clients to specify criteria for choosing an implementation. 
    - In the absence of such criteria, the API returns an instance of a default implementation, or allows the client to cycle through all available implementations. 

4. **Service provider interface**
    - An optional fourth component of a service provider framework is a service provider interface, which describes a factory object that produce instances of the service interface. 
    - Instead of reflection:
        ```java
        Class.forName("com.mysql.Driver");
        ```
        You define:
        ```java
        public interface Driver {
            Connection connect(...);
        }
        ```
        Providers implement this
    - In the absence of a service provider interface, implementations must be instantiated reflectively.

In the case of JDBC, `Connection` plays the part of the service interface,` DriverManager.registerDriver` is the
provider registration API, `DriverManager.getConnection` is the service access
API, and `Driver` is the service provider interface.
| Component                  | Example                        |
| -------------------------- | ------------------------------ |
| Service Interface          | `Connection`                   |
| Provider Registration      | `DriverManager.registerDriver` |
| Service Access (factory)   | `DriverManager.getConnection`  |
| Service Provider Interface | `Driver`                       |

What happens internally:
```java
Connection conn = DriverManager.getConnection("jdbc:mysql://...");
```
Internally:
- finds a registered driver 
- delegates creation to it 
- returns a Connection

The MySQL driver: mysql-connector.jar, could be added years after JDBC was designed.

Why Static Factory Enables This? Because:
```java
public static Connection getConnection(...)
```
can return:
- `MySQLConnection` 
- `PostgresConnection` 
- `OracleConnection` 

WITHOUT changing the API.

The “Class May Not Exist Yet” Meaning, When JDBC was created: PostgreSQL driver didn’t exist, But today:
```java
Connection conn = DriverManager.getConnection(...)
```
still works

Java provides built-in support:
```java
ServiceLoader<PaymentService> loader =
    ServiceLoader.load(PaymentService.class);

for (PaymentService service : loader) {
    service.pay();
}
```
This is the modern replacement for manual frameworks

4. ServiceLoader (Factory)
```java
import java.util.ServiceLoader;

public class NotificationFactory {
    private static final ServiceLoader<NotificationService> loader =
            ServiceLoader.load(NotificationService.class);

    public static NotificationService get(String type) {
        for (NotificationService service : loader) {
            if (service.getClass().getSimpleName().toLowerCase()
                    .contains(type.toLowerCase())) {
                return service;
            }
        }
        throw new IllegalArgumentException("No provider found: " + type);
    }
}
```
What’s happening here

At runtime:
- ClassPath scanning → finds new JARs → loads implementations dynamically
- No code change needed

5. Usage

```java[title="https://github.com/joansmith/spring-boot/blob/master/spring-boot-autoconfigure/src/main/java/org/springframework/boot/autoconfigure/jdbc/DataSourceBuilder.java#L67"]
	private static final String[] DATA_SOURCE_TYPE_NAMES = new String[] {
			"org.apache.tomcat.jdbc.pool.DataSource",
			"com.zaxxer.hikari.HikariDataSource",
			"org.apache.commons.dbcp.BasicDataSource",
			"org.apache.commons.dbcp2.BasicDataSource" };

	private Class<? extends DataSource> type;

	private ClassLoader classLoader;

	private Map<String, String> properties = new HashMap<String, String>();

	public static DataSourceBuilder create() {
		return new DataSourceBuilder(null);
	}

	public static DataSourceBuilder create(ClassLoader classLoader) {
		return new DataSourceBuilder(classLoader);
	}

	public DataSourceBuilder(ClassLoader classLoader) {
		this.classLoader = classLoader;
	}

	public DataSource build() {
		Class<? extends DataSource> type = getType();
		DataSource result = BeanUtils.instantiate(type);
		maybeGetDriverClassName();
		bind(result);
		return result;
	}

	private void maybeGetDriverClassName() {
		if (!this.properties.containsKey("driverClassName")
				&& this.properties.containsKey("url")) {
			String url = this.properties.get("url");
			String driverClass = DatabaseDriver.fromJdbcUrl(url).getDriverClassName();
			this.properties.put("driverClassName", driverClass);
		}
	}

	private void bind(DataSource result) {
		MutablePropertyValues properties = new MutablePropertyValues(this.properties);
		new RelaxedDataBinder(result).withAlias("url", "jdbcUrl").bind(properties);
	}

	public DataSourceBuilder type(Class<? extends DataSource> type) {
		this.type = type;
		return this;
	}

	public DataSourceBuilder url(String url) {
		this.properties.put("url", url);
		return this;
	}

	public DataSourceBuilder driverClassName(String driverClassName) {
		this.properties.put("driverClassName", driverClassName);
		return this;
	}

	public DataSourceBuilder username(String username) {
		this.properties.put("username", username);
		return this;
	}

	public DataSourceBuilder password(String password) {
		this.properties.put("password", password);
		return this;
	}

	@SuppressWarnings("unchecked")
	public Class<? extends DataSource> findType() {
		if (this.type != null) {
			return this.type;
		}
		for (String name : DATA_SOURCE_TYPE_NAMES) {
			try {
				return (Class<? extends DataSource>) ClassUtils.forName(name,
						this.classLoader);
			}
			catch (Exception ex) {
				// Swallow and continue
			}
		}
		return null;
	}

	private Class<? extends DataSource> getType() {
		Class<? extends DataSource> type = findType();
		if (type != null) {
			return type;
		}
		throw new IllegalStateException("No supported DataSource type found");
	}
```

##### Logging
```java
Logger logger = LoggerFactory.getLogger(MyClass.class);
````

```java[title["https://github.com/qos-ch/slf4j/blob/master/slf4j-api/src/main/java/org/slf4j/LoggerFactory.java#L445"]
public static Logger getLogger(String name) {
    ILoggerFactory iLoggerFactory = getILoggerFactory();
    return iLoggerFactory.getLogger(name);
}
```
The primary role of this method is to ensure SLF4J is initialized and then delegate the actual logger creation to an underlying provider (like Logback).

During the first call to `getLogger`, `LoggerFactory` performs a "bind" operation. In SLF4J 2.x, it uses the Java ServiceLoader to find an implementation of `SLF4JServiceProvider` on the classpath.

Key Implementation Steps
1. Initialization Check: Before returning a logger, getILoggerFactory() checks the INITIALIZATION_STATE. If it is UNINITIALIZED, it triggers a discovery process to find a concrete logging implementation (e.g., searching the classpathfor a provider).
2. Provider Discovery: It uses the Java ServiceLoader to find classes implementing SLF4JServiceProvider.
3. Substitution: If a request for a logger occurs while initialization is still in progress, SLF4J provides a SubstituteLogger to buffer events until the real logging system is ready.
4. Delegation: Once initialized, the call is handed off to the specific factory of the underlying framework (like ch.qos.logback.classic.LoggerContext) to return the actual Logger instance.


In Logback, the `getLogger` logic is primarily handled by the `ch.qos.logback.classic.LoggerContext` class, which implements SLF4J's `ILoggerFactory`. 

When you call `LoggerFactory.getLogger`, it delegates to the LoggerContext to either find an existing logger or create a new one in the hierarchy. 
The `getLogger(String name)` method first checks a `loggerCache` for an existing instance to ensure efficiency. If not found, it recursively builds the logger hierarchy, creating nodes from the root logger downwards (e.g., a -> a.b -> a.b.c). The process is synchronized on the parent logger to ensure thread safety during creation. 
- Caching: `A Map<String, Logger> (loggerCache)` ensures identical logger instances are returned for the same name.
- Hierarchy: Loggers are structured in a tree. Requesting a child logger triggers the creation of missing intermediate parents.

The logic is defined in https://github.com/qos-ch/logback/blob/master/logback-classic/src/main/java/ch/qos/logback/classic/LoggerContext.java#L121

## Disadvantages
Static factory methods are powerful, but if you rely on them exclusively (and hide all constructors), you introduce some real trade-offs. Here are the key disadvantages and limitations, with practical context.


### 1. Cannot be subclassed (if no accessible constructors)
The main limitation of providing only static factory methods is that classes without public or protected constructors cannot be subclassed. 

If you make constructors private:
```java
class User {
    private User(...) {}
    public static User create(...) { ... }
}
```
Then:
```java
class AdminUser extends User {} // ❌ impossible
```

**Static Factory Causes This**

When you design a class like:
```java
class MyClass {

    private MyClass() {}

    public static MyClass of() {
        return new MyClass();
    }
}
```
You’ve effectively made it: non-subclassable
**Why this matters:**
*   Breaks inheritance-based extension 
*   Limits framework usage that relies on subclassing 

For example, it is impossible to subclass any of the convenience implementation classes in the **Collections** Framework. 

In the Java Collections Framework:
```java
List<String> list = Collections.unmodifiableList(new ArrayList<>());
```
The returned object:
- is a hidden class 
- has no accessible constructor 
- cannot be subclassed

This Is a “Limitation”, Because you lose: Inheritance-based extension
```
class MyList extends ??? // ❌ you can’t extend it
```
Arguably this can be a blessing in disguise(Because it pushes you toward better design) 

1. Prefer Composition over Inheritance
it encourages programmers to use composition instead of inheritance

Instead of:
```java
class MyList extends ArrayList<String> { ... }  // fragile
```
You do:
```java
class MyList {
    private final List<String> list;
    public MyList(List<String> list) {
        this.list = list;
    }
}
```
This is composition, composition is better
- avoids tight coupling 
- avoids fragile base class problem 
- easier to change implementation 

2. Required for Immutability

For immutable classes:
```java
final class Money {
    private final int amount;
    private Money(int amount) {
        this.amount = amount;
    }
    public static Money of(int amount) {
        return new Money(amount);
    }
}
```
If subclassing were allowed:
```java
class EvilMoney extends Money {
    void mutate() { ... }  // breaks immutability
}
```
So restriction ensures: No subclass → no state corruption → safe immutability

3. Prevents “fragile base class problem”

Inheritance can break when base class changes.

Example:
```java
class Base {
    void doWork() { ... }
}
```
If you extend it:
```java
class Child extends Base {
    @Override void doWork() { ... }
}
```
If Base changes → Child may break

Static factory + no subclassing avoids this entirely.

4. Encourages Controlled Design

Instead of: anyone can extend your class, You get: you control all implementations.
| Aspect                      | Static Factory Only |
| --------------------------- | ------------------- |
| Subclassing                 | ❌ Not allowed       |
| Immutability                | ✅ Strong            |
| Encapsulation               | ✅ Strong            |
| Flexibility via inheritance | ❌ Reduced           |
| Composition usage           | ✅ Encouraged        |

The main limitation of static factory–only classes is that they cannot be subclassed because they lack accessible constructors. However, this restriction can be beneficial because it enforces immutability and encourages composition over inheritance, which leads to more robust and maintainable designs.

#### Real cases where static factories break things
##### 1. JPA (Hibernate) entity instantiation
In Hibernate / JPA, the framework creates entities via reflection.

**❌ Broken version (static factory only)**
```java
@Entity
public class User {
    private String name;
    private User(String name) {   // ❌ no default constructor
        this.name = name;
    }
    public static User of(String name) {
        return new User(name);
    }
}
```

**💥 What happens**
At runtime: `org.hibernate.InstantiationException: No default constructor for entity`

**✅ Fix (required by JPA)**
```java
@Entity
public class User {
    private String name;
    protected User() {}  // ✔ required by JPA
    private User(String name) {
        this.name = name;
    }
    public static User of(String name) {
        return new User(name);
    }
}
```
👉 **JPA requires a no-arg constructor**, even if you use factories.

##### 2. Jackson (JSON deserialization)
In Jackson:

**❌ Broken version**
```java
public class User {
    private final String name;
    private User(String name) {
        this.name = name;
    }
    public static User of(String name) {
        return new User(name);
    }
}
```

**💥 Error**
`Cannot construct instance of User: no Creators, like default constructor, exist`

**✅ Fix options**

**Option A: Add constructor**
```java
@JsonCreator
public User(@JsonProperty("name") String name) {
    this.name = name;
}
```

**Option B: Annotate factory**
```java
@JsonCreator
public static User of(@JsonProperty("name") String name) {
    return new User(name);
}
```
👉 Without annotations, static factories break deserialization.

##### 3. Spring Dependency Injection
In Spring Boot:

**❌ Anti-pattern**
```java
@Service
public class PaymentService {
    private final Repository repo;
    private PaymentService(Repository repo) {
        this.repo = repo;
    }
    public static PaymentService create(Repository repo) {
        return new PaymentService(repo);
    }
}
```

**💥 Problem**
Spring cannot instantiate it: `No default constructor found`

**✅ Correct Spring style**
```java
@Service
public class PaymentService {
    private final Repository repo;
    public PaymentService(Repository repo) {  // ✔ constructor injection
        this.repo = repo;
    }
}
```
👉 **Spring prefers constructor injection**, not static factories.

##### 4. Spring Proxying (AOP / Transactions)
Spring may create subclasses (proxies) dynamically.

**❌ Problem case**
```java
public final class PaymentService {  // ❌ final class
    private PaymentService() {}
    public static PaymentService create() {
        return new PaymentService();
    }
}
```
👉 Spring cannot proxy:
- **Final classes**
- **Private constructors only**

**💥 Result**
- `@Transactional` won’t work
- AOP won’t apply

Frameworks often need:
1. **Reflection**
2. **Subclassing (proxies)**
3. **Constructor access**

Static factories alone block these.

### 2. Harder to discover (no "new" keyword)
A second shortcoming of static factory methods is that they are hard for programmers to find.

With constructors:
```java
User u = new User("user");
```
Very obvious how to create the object.

With static factories:
```java
User u = User.of("user");
User u = User.create("user");
User u = User.from("user");
```
**Problem:**
*   No standard naming convention 
*   Developers must read documentation or IDE hints 
    * They do not stand out in API documentation in the way that constructors do, so it can be difficult to figure out how to instantiate a class that provides static factory methods instead of constructors. 
    * The Javadoc tool may someday draw attention to static factory methods. 
    * In the meantime, you can reduce this problem by drawing attention to static factories in class or interface documentation and by adhering to common naming conventions. Here are some common names for static factory methods. This list is far from exhaustive:
        * **from**—A type-conversion method that takes a single parameter and returns a corresponding instance of this type, for example:
            ```
            Date d = Date.from(instant);
            ```
        * **of**—An aggregation method that takes multiple parameters and returns an instance of this type that incorporates them, for example:
            ```
            Set<Rank> faceCards = EnumSet.of(JACK, QUEEN, KING);
            ```
        * **valueOf**—A more verbose alternative to from and of, for example:
            ```
            BigInteger prime = BigInteger.valueOf(Integer.MAX_VALUE);
            ```
        * **instance** or **getInstance**—Returns an instance that is described by its parameters (if any) but cannot be said to have the same value, for example:
            ```
            StackWalker luke = StackWalker.getInstance(options);
            ```
        * **create** or **newInstance**—Like instance or getInstance, except that the method guarantees that each call returns a new instance, for example:
            ```
            Object newArray = Array.newInstance(classObject, arrayLen);
            ```
        * getType—Like getInstance, but used if the factory method is in a different class. Type is the type of object returned by the factory method, for example:
            ```
            FileStore fs = Files.getFileStore(path);
            ```
        * **newType**—Like **newInstance**, but used if the factory method is in a different class. Type is the type of object returned by the factory method, for example:
            ```
            BufferedReader br = Files.newBufferedReader(path);
            ```
        * **type**—A concise alternative to getType and newType, for example:
            ```
            List<Complaint> litany = Collections.list(legacyLitany);
            ```

## Constructor vs Static Factory Method
static factory methods and public constructors both have their uses, and it pays to understand their relative merits. Often static factories are preferable, so avoid the reflex to provide public constructors without first considering static factories.

Constructor: Tightly bound to a class that exists now

Static factory: Can return any implementation—even ones added in the future

| Feature                 | Constructor               | Static Factory Method                |
| ----------------------- | ------------------------- | ------------------------------------ |
| Name                    | Same as class             | Any meaningful name                  |
| Object creation         | Always creates new object | Can reuse/cached objects             |
| Return type             | Must be the class itself  | Can return subtype                   |
| Flexibility             | Limited                   | Very flexible                        |
| Visibility control      | Can be private            | Works well with private constructors |
| Overloading readability | Poor when many params     | Better via method names              |

**Example Comparison**

**Constructor approach:**
```java
User u1 = new User("user", 25);
User u2 = new User("user", 25, true);
```
Hard to understand what true means.

**Static factory approach:**
```java
User u1 = User.normalUser("user", 25);
User u2 = User.adminUser("user", 25);
```
Self-explanatory.

**When to Use Which?**

**Use constructors when:**
- Object creation is simple 
- No need for naming variations 
- No caching or logic required 

**Use static factory methods when:**
- You want readable, expressive creation 
- You need caching/singletons 
- You may return different implementations 
- You want better API design 



Limitations of constructors

### decision tree for when to choose constructor vs factory
Use this mental model:

*   **Step 1: Do you need framework support?**
    *   **JPA / Hibernate:** Constructor is **REQUIRED**.
    *   **Spring DI:** Constructor is **preferred** for injection.
    *   **Jackson:** Requires a constructor or an annotated factory.
    *   *Guideline:* If **YES**, do not rely only on static factories.

*   **Step 2: Do you need inheritance?**
    *   **Yes:** Use constructors to allow subclassing.
    *   **No:** Static factory methods are appropriate.

*   **Step 3: Do you need flexibility in the returned type?**
    *   **Return a subtype?** Use a **static factory**.
    *   **Always the same class?** A **constructor** is sufficient.

*   **Step 4: Do you need caching or instance control?**
    *   **Yes:** Use a **static factory** (e.g., Singletons, Flyweights).
    *   **No:** A **constructor** is sufficient.

*   **Step 5: Is object creation simple?**
    *   **Simple:** Use a **constructor**.
    *   **Complex or conditional:** Use a **static factory** to encapsulate the logic.

*   **Final Decision Tree (Simplified):**
    *   Need framework support?
        *   Yes → Use **Constructor**
        *   No → Need flexibility (subtypes) or instance control (caching)?
            *   Yes → Use **Static Factory**
            *   No → Use **Constructor**

*   **Best Practice (Real Systems):** Use **both** together to satisfy framework requirements while providing a clean API:

```java
@Entity
public class User {
    // Required by JPA/Hibernate
    protected User() {}

    // Private constructor to enforce factory usage
    private User(String name) {
        this.name = name;
    }

    // Clean API for clients
    public static User of(String name) {
        return new User(name);
    }
}
```
