## Name

**Utility Class Pattern**
(also called Static Utility Class or Helper Class)

## Intent

Provide a centralized place for:

* stateless helper methods
* reusable algorithms
* static factory methods
* operations on values/objects

while preventing object instantiation.

## Problem (Motivation)
Occasionally you’ll want to write a class that is just a grouping of static methods
and static fields. Such classes have acquired a bad reputation because some people
abuse them to avoid thinking in terms of objects, but they do have valid uses
1. Grouping operations on primitives / arrays

Example:

* `java.lang.Math`
* `java.util.Arrays`

👉 These are **pure function groups**

---

2. Grouping static factory methods (or helpers for interfaces)

Example:

* `java.util.Collections`

👉 These are **behavior providers for interfaces**

---

3. Java 8+ interfaces can now hold static methods

So instead of utility classes, you can sometimes:

* put helper methods inside the interface itself

---

4. Grouping methods for a final class

Because:

* you cannot extend a final class
* so you cannot attach behavior via subclassing


Sometimes we need methods that:

* do not depend on object state
* are shared globally
* logically belong together

Examples:

* math operations
* string helpers
* array algorithms
* collection utilities

Creating objects for such behavior is unnecessary.

Without a dedicated structure:

* helper methods become scattered
* duplicate code appears
* APIs become inconsistent

## Solution

Create a class that:

* contains only `static` members
* has a `private constructor`
* acts as a namespace for related behavior

## Structure

### Core Characteristics

| Feature                  | Purpose               |
| ------------------------ | --------------------- |
| `static methods`         | Shared behavior       |
| `private constructor`    | Prevent instantiation |
| `final class` (optional) | Prevent inheritance   |
| Stateless design         | No object state       |

## Basic Implementation in Java

```java id="7v5i4s"
public final class MathUtils {

    // Prevent instantiation
    private MathUtils() {
        throw new AssertionError("Utility class");
    }

    public static int add(int a, int b) {
        return a + b;
    }

    public static int max(int a, int b) {
        return Math.max(a, b);
    }
}
```

Usage:

```java id="b6oq3r"
int result = MathUtils.add(5, 3);
```

## How It Works

The class:

* is never instantiated
* exposes reusable operations statically
* groups related functionality

Instead of:

```java id="y5m0u7"
MathUtils utils = new MathUtils();
utils.add(1, 2);
```

You directly use:

```java id="x0y2y0"
MathUtils.add(1, 2);
```

## Advantages

| Advantage          | Explanation               |
| ------------------ | ------------------------- |
| Reusability        | Shared logic in one place |
| No object creation | Lower overhead            |
| Clear organization | Related functions grouped |
| Easy access        | Direct static calls       |
| Stateless          | Simple behavior           |

## Disadvantages

| Disadvantage                         | Explanation                         |
| ------------------------------------ | ----------------------------------- |
| Can encourage procedural programming | Overuse weakens OOP                 |
| Harder to mock in tests              | Static methods harder to replace    |
| Global-style access                  | Can increase coupling               |
| No polymorphism                      | Static methods cannot be overridden |

## Utility Class vs Object-Oriented Design

### Bad Usage

Using utility classes for everything:

```java id="xw3o9c"
UserUtils.save(user);
UserUtils.validate(user);
UserUtils.print(user);
```

This often becomes:

* procedural programming
* anemic domain model

### Good Usage

Use utility classes for:

* stateless generic operations
* cross-cutting helpers
* algorithms
* conversions

## Utility Class vs Singleton

| Feature        | Utility Class      | Singleton                |
| -------------- | ------------------ | ------------------------ |
| Has instances? | No               | One                    |
| Constructor    | Private            | Private                  |
| State allowed? | Usually no         | Yes                      |
| Access style   | Static methods     | `getInstance()`          |
| Purpose        | Group helper logic | Single controlled object |

## Utility Class vs Static Factory Class

| Utility Class          | Static Factory              |
| ---------------------- | --------------------------- |
| General helper methods | Creates objects             |
| Often algorithmic      | Often construction-oriented |
| Example: `Math`        | Example: `Collections`      |

## Internal Mechanics

Without constructor:

```java id="a3v93h"
public class Utils {
}
```

Java automatically generates:

```java id="f34m9w"
public Utils() {
}
```

So users can instantiate it accidentally.

Private constructor prevents this.

### Keep methods stateless

Avoid mutable static state.

### Keep utilities cohesive


## Anti-Patterns

### God Utility Class

```java id="ezl0dy"

```

Contains unrelated logic.

### Business Logic Dumping

Replacing proper domain objects with utilities.

### Mutable Static Globals

```java id="grdjmb"

```

## When to Use

Use Utility Class when:

Behavior is stateless
No object identity needed
Methods are generic helpers
Logic is reusable globally
Operations belong together conceptually

## When NOT to Use

Do NOT use when:

Behavior depends on object state
Polymorphism is required
Domain modeling is important
Dependency injection is needed
Stateful behavior exists

## Utility Class vs Singleton vs Factory

These three concepts are often confused because:

* all may use private constructors
* all may expose static methods
* all may control object creation

But they solve **completely different problems**.

---

### 1. High-Level Purpose Comparison

| Concept       | Main Goal                               |
| ------------- | --------------------------------------- |
| Utility Class | Group stateless helper functions        |
| Singleton     | Ensure exactly one shared instance      |
| Factory       | Centralize and abstract object creation |

---

### 2. Core Mental Model

| Pattern       | Think Of It As            |
| ------------- | ------------------------- |
| Utility Class | 📦 Toolbox                 |
| Singleton     | 🏢 Single shared service   |
| Factory       | 🏭 Object creation machine |

---

### 3. Object Existence

| Feature                 | Utility Class | Singleton | Factory                 |
| ----------------------- | ------------- | --------- | ----------------------- |
| Instances exist?        | No          | One     | Creates many          |
| Constructor accessible? | Private     | Private | Often private/protected |
| Uses `new` internally?  | Usually no    | Once      | Frequently              |

---

### 4. State Management

| Feature               | Utility Class       | Singleton          | Factory           |
| --------------------- | ------------------- | ------------------ | ----------------- |
| Holds state?          | Ideally stateless | Usually stateful | Usually stateless |
| Shared mutable state? | Dangerous           | Common             | Rare              |
| Lifecycle matters?    | No                | Yes              | Sometimes         |

### 8. When to Use Each

| Situation                      | Best Choice   |
| ------------------------------ | ------------- |
| Pure helper methods            | Utility Class |
| One shared application service | Singleton     |
| Complex object creation        | Factory       |

Use Utility Class when:

- Stateless
- Generic helper behavior
- No lifecycle needed
- Pure functions

---

Use Singleton when:

- Exactly one shared resource exists
- Shared state/lifecycle matters

---

Use Factory when:

- Construction is complex
- Creation logic must be abstracted
- Different implementations may be created

---

Utility classes are:

> “functions grouped into a namespace”

Singletons are:

> “globally shared objects”

Factories are:

> “object creation abstractions”

Modern enterprise systems (especially Spring) strongly prefer:

* dependency injection
* managed objects
* composition

over:

* static utility overuse
* manual global state
* procedural-style helpers

### 9. Dependency Injection Compatibility

## Spring Framework Perspective (Very Practical)

Spring intentionally avoids excessive:

* static utilities
* manual singletons
* global access patterns

because they hurt:

* testability
* flexibility
* dependency injection

---

### How Spring Replaces Utility-Class Overuse


#### Traditional Utility Approach

```java id="39wlnz"
public class EmailUtils {

    public static void send(String msg) {
        // send email
    }
}
```

Usage:

```java id="7n9wsl"
EmailUtils.send("Hello");
```

Problems:

* hard to mock
* hard to replace
* tightly coupled
* static dependency

---

### Spring Preferred Approach

#### Service Bean

```java id="hjlwm7"
@Service
public class EmailService {

    public void send(String msg) {
        // send email
    }
}
```

Usage:

```java id="5o5u9p"
@Service
public class UserService {

    private final EmailService emailService;

    public UserService(EmailService emailService) {
        this.emailService = emailService;
    }

    public void register() {
        emailService.send("Welcome");
    }
}
```

---

### Why Spring Avoids Utility Overuse

#### Better Testability

Mock easily:

```java id="phjlwm"
@Mock
EmailService emailService;
```

Impossible with many static utilities.

---

#### Loose Coupling

Can swap implementation:

```java id="g0jlwm"
EmailService
SmsEmailService
MockEmailService
```

---

#### Dependency Injection

Spring manages lifecycle automatically.

---

#### Polymorphism

Interfaces work naturally.

---

### When Spring STILL Uses Utility Classes

Spring absolutely still uses them — but carefully.

Examples:

| Spring Utility Class | Purpose                  |
| -------------------- | ------------------------ |
| `StringUtils`        | String helpers           |
| `CollectionUtils`    | Collection helpers       |
| `ReflectionUtils`    | Reflection helpers       |
| `ClassUtils`         | Class metadata utilities |

These are:

* stateless
* generic
* infrastructure-oriented

NOT business logic.

---

### Spring Design Philosophy

Spring encourages:

```text id="jlwm43"
Behavior → Objects/Beans
Algorithms/helpers → Utilities
```

That is a very important architectural distinction.

## Evolution Example

### Step 1 — Duplicate code

```java id="e5wz1i"
int max = a > b ? a : b;
```

Repeated everywhere.

### Step 2 — Centralize helper

```java id="kqwxru"
MathUtils.max(a, b);
```

### Step 3 — Full utility class

```java id="t3jlwm"
public final class MathUtils {

    private MathUtils() {}

    public static int max(int a, int b) {
        return a > b ? a : b;
    }
}
```

## Key Insight

> A Utility Class is essentially a “namespace for related stateless behavior” inside object-oriented programming.

It is useful when:

* objects are unnecessary
* behavior is generic
* state does not matter

But overusing it can slowly turn an OOP system into procedural code.
