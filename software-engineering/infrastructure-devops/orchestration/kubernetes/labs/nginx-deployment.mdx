## Create Kubernetes manifests
We can now create a Deployment of NGINX in the namespace using the kubernetes/labs-nginx-deployment/nginx-deployment.yaml file. This file looks as follows:
```yml
# Specifies the Kubernetes API group and version used to create the Deployment resource.
apiVersion: apps/v1

# Declares the type of Kubernetes resource we want to create.
kind: Deployment

# Contains identifying information about the Deployment.
metadata:
  # Assigns the name "nginx-deploy" to this Deployment.
  name: nginx-deploy

# Defines the desired state of the Deployment.
spec:
  # Specifies that Kubernetes should maintain one replica (Pod) of the application.
  replicas: 1

  # Defines which Pods this Deployment manages.
  selector:
    # Selects Pods whose labels match app: nginx-app.
    matchLabels:
      # The Deployment manages Pods with this label.
      app: nginx-app

  # Defines the template Kubernetes uses to create new Pods.
  template:
    # Contains metadata for the Pods created by this Deployment.
    metadata:
      # Defines the labels that will be assigned to every created Pod.
      labels:
        # This label must match the Deployment's selector above.
        app: nginx-app

    # Defines the specification of the Pod.
    spec:
      # Lists the containers that will run inside the Pod.
      containers:
        # Begins the definition of the first container.
        - name: nginx-container
          # Specifies the container image to download and run.
          # "latest" refers to the latest published Nginx image tag.
          image: nginx:latest

          # Declares the network ports exposed by the container.
          ports:
            # Begins the definition of a container port.
            - containerPort: 80
              # Nginx listens for HTTP traffic on port 80 inside the container.
```
Let’s explain this source code in more detail:
- The kind and apiVersion attributes are used to specify that we are declaring a Deployment object.
- The metadata section is used to describe the Deployment object. For example, we give it
the name nginx-deploy.

Next comes a spec section that defines our desired state for the Deployment object:
- replicas: 1 specifies we want to have one Pod up and running.
- The selector section specifies how the Deployment will find the Pods it manages. In this case, the Deployment will look for Pods that have the app label set to nginx-app.
- The template section is used to specify how Pods will be created.
- The metadata section specifies the label, app: nginx-app, which is used to identify the Pods, thereby matching the selector.
- The spec section specifies details for the creation of the single container in the Pod, that is, name, image, and what ports it uses.

## Access the application
To enable external communication with the web servers, create a Service using the `nginx-service.yaml` file. It looks like the following:
```yml
# Specifies the Kubernetes API group and version used to create the Service resource.
apiVersion: v1

# Declares the type of Kubernetes resource we want to create.
kind: Service

# Contains identifying information about the Service.
metadata:
  # Assigns the name "nginx-service" to this Service.
  name: nginx-service

# Defines the desired configuration of the Service.
spec:
  # Specifies the Service type.
  # NodePort exposes the Service on a static port on each Kubernetes node.
  type: NodePort

  # Defines which Pods receive traffic from this Service.
  selector:
    # Selects Pods with the label app: nginx-app.
    # This matches the label defined in the nginx Deployment.
    app: nginx-app

  # Defines the network ports used by the Service.
  ports:
    # Begins the definition of a Service port.
    - # The port on which the target Pod/container receives traffic.
      # Kubernetes forwards traffic to port 80 inside the selected Pod.
      targetPort: 80

      # The port exposed internally by the Service within the cluster.
      # Other Pods can access the Service using nginx-service:80.
      port: 80

      # The port exposed on each Kubernetes node.
      # You can access the Nginx Service using:
      # http://<NodeIP>:30080
      nodePort: 30080
```
The `kind` and `apiVersion` attributes are used to specify that we are declaring a Service object.

The metadata section is used to describe the Service object – for example, to give it a name:
`nginx-service`.

Next comes a spec section, which defines the desired state of the Service object:
- With the `type` field, we specify that we want `NodePort` – that is, a Service that is accessible
externally on a dedicated port on each node in the cluster. This means that an external
caller can reach the Pods behind this Service using this port on any of the nodes in the
cluster, independent of which nodes the Pods actually run on.
- The `selector` is used by the Service to find available Pods, which, in our case, are Pods
labeled with `app: nginx-app`.
- Finally, ports are declared as follows:
    - `port: 80` specifies which port the Service will be accessible on – that is, internally
    in the cluster.
    - `targetPort: 80` specifies the port in the Pod where the requests will be forwarded
    to.
    - `nodePort: 30080` specifies which port the Service will be externally accessible
    on using any of the nodes in the cluster. By default, a node port must be in the
    range of `30000` to `32767`.

    :::note
    This port range is used to minimize the risk of colliding with other ports in use. In
    a production system, a load balancer is typically placed in front of the Kubernetes
    cluster, shielding the external users both from the knowledge of these ports and the
    IP numbers of the nodes in the Kubernetes cluster.
    :::

Create the Service with the following command:
```sh
kubectl apply -f nginx-service.yaml
```
To see what we get, run the `kubectl get svc` command. Expect a response like the following:
```
NAME            TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
nginx-service   NodePort   10.107.173.72   <none>        80:30080/TCP   25s
```

:::info

kubectl supports short names for many of the API objects as an alternative to their
full name. For example, svc was used in the preceding command instead of the full
name, service. Run the kubectl api-resources command to see all available
short names.

:::

```sh
# Display Services.
kubectl get services

# Display the Service details.
kubectl describe service nginx-service

# Display the Pods selected by the Service.
kubectl get pods -l app=nginx-app
```

Note for Minikube: You can access the Service using:
```sh
minikube service nginx-service
```

This opens the Service using the appropriate Minikube access URL.

To access the web server through the Service’s node port, we need to know the IP address or
hostname of the single node in our cluster. When using the Docker driver, the hostname is always `localhost`.
The node port, `30080`, is forwarded from the Docker engine by the –ports option in the minikube
start command. This means that
the Service can be reached at the address `localhost:30080`.

With this information, we can direct a web browser on macOS and Windows to the deployed
web server using the address http://localhost:30080. Expect a response such as the following:
```
Welcome to nginx!
If you see this page, nginx is successfully installed and working. Further configuration is required for the web server, reverse proxy, API gateway, load balancer, content cache, or other features.

For online documentation and support please refer to nginx.org.
To engage with the community please visit community.nginx.org.
For enterprise grade support, professional services, additional security features and capabilities please refer to f5.com/nginx.

Thank you for using nginx.
```

Great! But what about the internal cluster IP address and port?

One way to verify that the web server is also reachable internally in the cluster is to launch a
small Pod that we can use to run curl from the inside. The curl command will use the internal
cluster IP address and port. We don’t need to use the internal IP address; instead, we can use a
DNS name that is created for the Service in the internal DNS server. The short name of the DNS
name is the same as the name of the Service – that is, `nginx-service`.

Run the following command:
```sh
kubectl run -i --rm --restart=Never curl-client --image=curlimages/curl --command -- curl -s 'http://nginx-service:80'
```
The command looks a bit complex, but it will do the following:
1. Create a Pod with a small container based on the Docker image, curlimages/curl, which
contains the curl command.
2. Run the `curl -s 'http://nginx-service:80'` command inside the container and redirect
the output to the terminal using the -i option.
3. Delete the Pod using the --rm option.

Expect the output from the preceding command to contain the following information (we are
only showing parts of the response here):
```
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
<style>

....

</body>
</html>
pod "curl-client" deleted from development namespace
```
This means that the web server is also accessible internally in the cluster!

#### 12. Clean up

Delete the lab's Kubernetes resources:

```sh
kubectl delete namespace development
```

Stop Minikube but preserve its cluster:

```sh
minikube stop -p labs-nginx-deployment
```

Or delete the entire profile and cluster:

```sh
minikube delete -p labs-nginx-deployment
```

Deleting the profile removes its cluster resources and configuration. It is not the same as merely stopping the cluster.


## Summary

We tried out Kubernetes by creating a local single-node cluster using minikube. The minikube
cluster runs as a Docker container using the Docker driver. To make ports accessible outside of
the Docker engine, we can use the `--ports` option on the minikube start command. 

Using the
Kubernetes CLI tool known as **kubectl**, we deployed a simple web server based on **NGINX**. We
tried out resilience capabilities by deleting the web server, and we observed it being recreated
automatically. We learned how to manually scale it by requesting that 2 Pods run on the web
server. We created a Service with a node port and verified that we could access it both externally
and from the inside of the cluster.
