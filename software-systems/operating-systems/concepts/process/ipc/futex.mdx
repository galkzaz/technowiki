With increasing parallelism, efficient synchronization and locking is very important for performance. 
- **Spin locks** (and **mutexes** implemented by busy waiting in general) are fast if the wait is short, but waste CPU cycles if not. If there is much contention, it is therefore more efficient to block the process and let the kernel unblock it only when the lock is free. 
- Unfortunately, this has the inverse problem: it works well under heavy contention, but continuously switching to the kernel is expensive if there is very little contention to begin with. 
- To make matters worse, it may not be easy to predict the amount of lock contention. 

One nice solution that tries to combine the best of both worlds is the **futex**, or **fast user space mutex**.

**A futex (Fast Userspace Mutex)** is a Linux synchronization mechanism designed to combine the advantages of **spinlocks** and blocking **mutexes**.

A **futex** is a feature of Linux that implements basic locking (much like a mutex) but avoids dropping into the kernel unless it really has to. Since switching to the kernel and back is quite expensive, doing so improves performance considerably.

It solves this dilemma:
| Technique                   | Advantage                                 | Problem                                       |
| --------------------------- | ----------------------------------------- | --------------------------------------------- |
| **Spin lock / busy wait**   | Extremely fast if wait time is very short | Wastes CPU cycles if lock held long           |
| **Blocking mutex (kernel)** | Efficient under heavy contention          | System calls + context switches are expensive |

A futex combines both.

**futexes** are very versatile and used to implement a range of synchronization primitives, from mutexes
to condition variables. They are also a very low-level feature of the kernel that most users will never use directly—instead they are wrapped by standard libraries that offer higher-level primitives. It is only when you lift the hood that you see the futex mechanism powering many different kinds of synchronization.

A **futex ("fast userspace mutex")** is a kernel system call that programs use to build synchronization primitives such as:
- Semaphores
- Mutexes
- Condition variables
- Read-write locks

## Core Idea of Futex
A futex is a construct supported by the kernel to let user space processes synchronize on shared events. It consists of two parts: 
1. a kernel service
2. a user library. 

The kernel service provides a ‘‘wait queue’’ that allows multiple processes to wait on a lock. They will not run, unless the kernel explicitly unblocks them. 

- For a process to be put on the wait queue requires an (expensive) system call. If possible, it should be avoided. 
- In the absence of any contention, therefore, the futex works entirely in user space. Specifically, the processes or threads share a common lock variable—a fancy name for an integer in shared memory that serves as the lock.
- Suppose we have multithreaded program and the lock is initially—1 which we assume to mean that the lock is free. 
    - A thread may grab the lock by 
        - performing an atomic ‘‘decrement and test’’ (atomic functions in Linux consist of inline assembly wrapped in C functions and are defined in header files). 
        - Next, the thread inspects the result to see whether or not the lock was free. If it was not in the locked state, all is well and our thread has successfully grabbed the lock.
    - A futex keeps most operations in user space and only enters the kernel when necessary.
    - However, if the lock is held by another thread, our thread has to wait. 
      - In that case, the futex library does not spin, but uses a system call to put the thread on the
        wait queue in the kernel. Hopefully, the cost of the switch to the kernel is now justified, because the thread was blocked anyway. 
    - When a thread is done with the lock, 
        - it releases the lock with an atomic ‘‘increment and test’’ 
        - and checks the result to see if any processes are still blocked on the kernel wait queue. If so, it will let
        the kernel know that it may wake up (unblock) one or more of these processes. In other words, if there is no contention, the kernel is not involved at all.

A **futex** is simply: A four-byte integer in shared memory that both user space and the kernel understand.

Key principle: User space handles uncontended cases, kernel handles contended cases.

So:
1. Try to acquire lock in user space (atomic operation).
2. If lock is free → success immediately (very fast).
3. If lock is busy → call kernel to sleep on futex queue.
4. When lock released → kernel wakes waiting threads.

**Futex Lock Workflow**
1. **Attempt Lock (Fast Path)**

Thread tries atomic operation in user space.

Example pseudo:
```
if (atomic_compare_exchange(lock, 0, 1))
    SUCCESS
else
    go to slow path
```
No kernel call occurs.

2. **Contention Occurs (Slow Path)**

If lock already taken:
```
futex_wait(lock, expected_value)
```
Kernel:
1. Checks if value still matches
2. Puts thread to sleep
3. Adds thread to wait queue

3. **Unlock**

Thread releases lock:
```
lock = 0
futex_wake(lock, 1)
```
Kernel wakes one waiting thread.

**Why Futex is Efficient**
1. **Case 1 — Low Contention**
```
Thread A locks
Thread B tries after A unlocks
```
Result:
```
Atomic instruction only
NO kernel call
```
Performance ≈ spinlock speed.

2. **Case 2 — High Contention**
```
Thread A holds lock long
Thread B, C, D try
```
Result:
```
Threads sleep
CPU not wasted
Kernel wakes them later
```
Performance ≈ blocking mutex.

## Futex Memory Layout
A futex is just a **32-bit integer in shared memory**.
Example:
```
int lock = 0
```
Values often mean:
1. 0 = unlocked
2. 1 = locked
3. >1 = locked + waiters

```c
void lock(int *futex)
{
    int c = 0;

    if (atomic_compare_exchange_strong(futex, &c, 1))
        return;

    while (1) {
        if (c == 2 || atomic_exchange(futex, 2) != 0)
            futex_wait(futex, 2);

        c = 0;
        if (atomic_compare_exchange_strong(futex, &c, 2))
            return;
    }
}
```
We will break this into three conceptual phases.

1. **Phase 1 — Fast Path (No Contention)**

Initial state: `futex = 0`
```c
int c = 0;
if (atomic_compare_exchange_strong(futex, &c, 1))
    return;
```
What happens here: The thread tries to atomically change the lock value: `0  →  1`

Meaning: `unlocked → locked`

`atomic_compare_exchange_strong`

Operation:
```c
if (*futex == c)
    *futex = 1
    return true
else
    c = *futex
    return false
```
Example:
```
futex = 0
Thread A runs CAS
CAS(0 → 1)  SUCCESS
```
Result:
- Thread A acquired the lock immediately
- No kernel call.
- This is the fast path.

Thread A locks

State: `futex = 1`

2. **Phase 2 — Contention Detected**

Thread B tries

If the CAS fails:
```c
futex != 0
```
Meaning: some other thread holds the lock

Execution continues here:
```c
while (1) {
```
This loop manages waiting and retrying.

3. **Phase 3 — Prepare to Sleep**
```c
if (c == 2 || atomic_exchange(futex, 2) != 0)
    futex_wait(futex, 2);
```
This line is the core futex trick.

3.1 **Step 1 — Mark "waiters exist"**
```c
atomic_exchange(futex, 2)
```
This operation:
```c
old = *futex
*futex = 2
return old
```
Meaning: lock state → "locked with waiters"

Example timeline:
```
Thread A holds lock
futex = 1
```
Thread B runs:
```
atomic_exchange(futex,2)
old = 1
futex = 2
```
Now the system knows: lock held + waiting threads exist

State:
- futex = 2
- Thread B sleeping

3.2 **Step 2 — Decide if we must sleep**

Condition:
```c
if (c == 2 || atomic_exchange(...) != 0)
```
Two cases trigger sleep:
1. **Case 1: `c == 2`, Meaning**: we already know waiters exist
2. **Case 2: `atomic_exchange(...) != 0`, Meaning**: lock already held

4. **Phase 4 — Sleep in Kernel**
```c
futex_wait(futex, 2);
```
This system call does:
```c
if (*futex == 2)
    sleep
else
    return immediately
```
Kernel behavior:
- Thread added to futex wait queue
- Thread blocked
- Scheduler runs other threads
- This is the slow path.
- CPU is not wasted spinning.

5. **Phase 5 — Wakeup and Retry**

After being woken:
```c
c = 0;
if (atomic_compare_exchange_strong(futex, &c, 2))
    return;
```
Thread tries to acquire lock again. But this time: `CAS(0 → 2)`

Why 2? Because the system knows there are waiters.

Example:
```
Thread A unlocks
futex becomes 0
Thread B wakes
CAS(0 → 2)
```
Thread B acquires lock.

```c

Example cases:

1. **Case A — No Waiters**
```
futex = 1
atomic_fetch_sub → returns 1
new futex = 0
```
Condition:` 1 != 1 → false`, So nothing happens.

- lock released
- no syscall
- Fast.

2. **Case B — Waiters Exist**
```

Condition: `2 != 1 → true`, So we execute:
```c

```
Thread B wakes

2. **Step 2 — Wake a Waiting Thread**
```c
futex_wake(futex,1)
```
State: Thread B owns lock

Kernel:
- remove 1 thread from wait queue
- mark runnable
- Scheduler eventually runs that thread.

**Why This Design Works**

This implementation achieves:
- Fast uncontended locking
    * 1 atomic instruction
    * no syscall
- Efficient contention handling
    * threads sleep
    * no CPU waste
- Correct wakeups
    * Because futex_wait only sleeps if:
        * ```*futex == expected```
    * This avoids the lost wakeup problem.

The futex() System Call Implementation Path
User-space perspective
The first thing semaphores do is manipulate a counter:
```
if (atomic_decrement_if_positive(&sem->value)) {
    // success without kernel
} else {
    futex(uaddr, FUTEX_WAIT, expected_value, NULL);
}
```
Key Idea Summary
- Fast path:
    * atomic CAS only
- Slow path:
    * mark waiters
    * sleep in kernel
- Unlock:
    * wake one waiter if needed

## Futex operations
### FUTEX_WAIT
Sleep if value matches expected.
```
futex(addr, FUTEX_WAIT, expected)
```
Kernel only sleeps if:
```
*addr == expected
```
Prevents race conditions.

The futex syscall generally takes three key parameters:
```
futex(uaddr, FUTEX_WAIT, val, timeout);
futex(uaddr, FUTEX_WAKE, nr_wake);
```
Where:
 - uaddr = address of the futex word in user memory
 - FUTEX_WAIT = "block if value equals expected"
 - FUTEX_WAKE = "wake up N waiters" 

 Key design point
 - Uncontended fast path: all work happens in user space with atomics (no syscall).
 - Contended path: the thread issues FUTEX_WAIT → enters kernel wait queue.
 - Waker threads issue FUTEX_WAKE → kernel wakes N threads. 

 This hybrid design avoids expensive syscalls in the common uncontended case.

### FUTEX_WAKE
Wake N waiting threads.

```
futex(addr, FUTEX_WAKE, n)
```
