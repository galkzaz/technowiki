When the semaphore’s ability to count is not needed, a simplified version of the semaphore, called a **mutex**, is sometimes used. **Mutexes** are good only for managing mutual exclusion to some shared resource or piece of code. They are easy and efficient to implement, which makes them especially useful in thread packages that are implemented entirely in user space.

A mutex (Mutual Exclusion Lock) is a synchronization primitive that ensures at most one thread executes a critical section at any time.

A mutex is a shared variable that can be in one of two states: unlocked or locked. Consequently, only 1 bit is required to represent it, but in practice an integer often is used, with 0 meaning unlocked and all other values meaning locked

Core properties:
- Binary state: locked / unlocked
- Ownership: only the locking thread may unlock
- Blocking: threads sleep if lock is unavailable
A mutex enforces mutual exclusion, not resource counting.

## Theoretical Perspective
Critical Section Problem
A correct mutex must satisfy:
    1. Mutual exclusion
    2. Progress
    3. Bounded waiting (fairness)
Classic software solutions:
- Peterson’s algorithm
- Bakery algorithm
Modern systems rely on:
- Atomic hardware instructions (CAS, test-and-set)
## Hardware Perspective
### basic mutex(Blocking (lock))
Two procedures are used with mutexes. 
1. When a thread (or process) needs access to a critical region, it calls `mutex_lock`. 
    * If the mutex is currently unlocked (meaning that the critical region is available), the call succeeds and the calling thread is free to enter the critical region.
2. On the other hand, if the mutex is already locked, the calling thread is blocked until the thread in the critical region is finished and calls `mutex_unlock`. 
    * If multiple threads are blocked on the mutex, one of them is chosen at random and allowed to acquire the lock.

mutexes can easily be implemented in user space provided that a `TSL` or `XCHG` instruction is available. The code for mutex lock and mutex unlock for use with a user-level threads package:
```nasm
mutex_lock:
    TSL REGISTER,MUTEX | copy mutex to register and set mutex to 1
    CMP REGISTER,#0 | was mutex zero?
    JZE ok | if it was zero, mutex was unlocked, so return
    CALL thread_yield | mutex is busy; schedule another thread
    JMP mutex_lock | try again
ok: RET | return to caller; critical region entered

mutex_unlock:
    MOVE MUTEX,#0 | store a 0 in mutex
    RET | return to caller
```
### distinction between busy waiting and blocking mutexes
The code of mutex lock is similar to the code of [enter region of Test-and-Set](software-systems/operating-systems/process/ipc/busy-waiting.mdx#Test-and-Set) with a crucial difference. 
- When enter region fails to enter the critical region in, it keeps testing the lock repeatedly (busy waiting). 
- in Kernel Threads, Eventually, the clock runs out and some other process is scheduled to run. Sooner or later the process holding the lock gets to run and releases it(progress is guaranteed by preemption).
- With (user) threads, the situation is different because there is no clock that stops threads that have run too long. Consequently, a thread that tries to acquire a lock by busy waiting will loop forever and never acquire the lock because it never allows any other thread to run and release the lock(no hardware interrupt forcing a thread switch inside the process).

That is where the difference between `enter_region` and `mutex_lock` comes in.
When the later fails to acquire a lock, it calls `thread_yield` to give up the CPU to
another thread. Consequently there is no busy waiting. When the thread runs the
next time, it tests the lock again.

1️⃣ Busy Waiting in Classic Mutual Exclusion
In early mutual exclusion algorithms (e.g., the classic enter region solution from Tanenbaum’s text), a thread that fails to acquire a lock:
- Repeatedly checks the lock variable
- Spins in a loop
- Waits until the lock becomes free
This is called busy waiting (or spinning).
While spinning:
- The thread consumes CPU cycles
- It does not voluntarily give up the processor
However, in a preemptive operating system, this eventually works because:
- The hardware clock interrupt forces a context switch
- The scheduler runs another process
- Eventually, the lock holder runs and releases the lock
- The spinning process later observes the lock is free
Thus, progress is guaranteed by preemption.

2️⃣ Why Busy Waiting Works with Kernel Threads
In systems like Linux:
- The timer interrupt fires periodically
- The scheduler preempts running threads
- Even a spinning thread cannot monopolize the CPU forever
This preemption ensures fairness and eventual progress.
For example, in Linux the scheduler inside the kernel ensures that threads are periodically interrupted and rescheduled.

3️⃣ Why Busy Waiting Fails with Pure User-Level Threads
Now consider user-level threads, managed entirely in user space without kernel awareness.
Examples include:
- Green threads
- Early runtime thread libraries
- Language-level schedulers
In this case:
- The kernel schedules the process
- The thread library schedules threads
- There is no hardware interrupt forcing a thread switch inside the process
If one thread spins:
- It never yields control
- The user-level scheduler never runs
- The thread holding the lock never executes
- The system deadlocks
Thus:
A busy-waiting thread can prevent the lock holder from ever running.
There is no clock interrupt inside user-level scheduling to save the system.

4️⃣ The Crucial Difference: Blocking vs Spinning
Modern mutex implementations (e.g., pthread_mutex_lock) solve this by:
    1. Trying an atomic fast-path acquisition
    2. If it fails → blocking via the kernel
On Linux this is implemented using the futex mechanism.
Instead of spinning forever:
- The thread calls into the kernel
- The kernel puts it to sleep
- The scheduler runs the lock holder
- When unlocked, the kernel wakes one waiter
This ensures:
- No CPU waste
- Guaranteed progress
- Correct behavior even with user-level scheduling

The essential difference between the classic `enter_region` solution and a mutex lock lies in what happens when lock acquisition fails.
In the `enter_region` solution:
- A thread that fails to acquire the lock
- Continuously tests the lock in a loop
- Consumes CPU while waiting (busy waiting)

In contrast, a mutex lock:
- Attempts to acquire the lock
- If it fails, calls thread_yield()
- Voluntarily gives up the CPU
- Allows another thread to run

When the `yielding_thread` is scheduled again:
- It rechecks the lock
- Attempts acquisition again

Thus, no CPU time is wasted spinning.

thread_yield() means: "I am willing to let another runnable thread execute now." This creates cooperative scheduling instead of preemptive forcing.
So the execution pattern becomes:
```
Try lock
    ↓
Fail?
    ↓
Yes → yield CPU
    ↓
Later → try again
```
Instead of:
```
Try lock
    ↓
Fail?
    ↓
Yes → spin forever
```
{/*Why This Prevents the User-Level Thread Deadlock*/}
With user-level threads, busy waiting can block the lock holder from running.
But with thread_yield():
- The failing thread voluntarily stops running
- The scheduler can run the lock holder
- The lock holder releases the lock
- Eventually the yielding thread retries successfully

Thus, progress is restored.


Since `thread_yield` is just a call to the thread scheduler in user space, it is very
fast(it does not involve a system call. It is simply a function call within the same process). As a consequence, neither `mutex_lock` nor `mutex_unlock` requires any kernel
calls(can both be implemented entirely in user space. No kernel entry is required.). Using them, user-level threads can synchronize entirely in user space using
procedures that require only a handful of instructions.

This allows user-level threads to perform synchronization using only:
- A few atomic instructions
- A scheduler function call
- Some memory accesses
Thus, synchronization overhead is minimal.

{/*Why This Is Fast*/}
In this model:
- Threads are managed by a runtime library.
- The kernel sees only one process (or one kernel thread).
- Context switching between user threads is done by saving/restoring registers in user space.
- No system call, no privilege switch, no scheduler trap.

This makes operations extremely cheap compared to kernel-based synchronization.

{/*What "No Kernel Calls" Really Means*/}
In a pure user-level threading system:
```
mutex_lock:
    try atomic acquire
    if fail → thread_yield()
```  
```
mutex_unlock:
    release lock
```
There is:
- No futex
- No syscall
- No scheduler interrupt
- No kernel wake-up queue

Everything happens inside the process.

Kernel calls are expensive because they involve:
- Privilege level switch (user → kernel mode)
- TLB effects
- Context switching overhead
- Scheduler involvement

Avoiding them reduces latency significantly.

{/*But There Is a Trade-Off*/}
This design works efficiently only under certain conditions:
It works well when:
- All threads are user-level
- Scheduling is cooperative
- There is low contention
- Only one CPU core is used
It breaks down when:
- A thread blocks in a system call
- Multiple CPU cores are involved
- True parallelism is required

### Non-blocking (trylock)
Ihe this basic mutex interface it provides only two operations:
- `mutex_lock()` — acquire the lock, blocking if necessary
- `mutex_unlock()` — release the lock

However, practical systems often require greater flexibility. One such extension is: `mutex_trylock()`, Unlike `mutex_lock()`, which blocks until the lock becomes available, `mutex_trylock()`:
- Attempts to acquire the lock
- Returns immediately
- Succeeds if the lock is free
- Returns a failure code if the lock is already held
- It never blocks.

            ```
            lock()
                if locked:
                    sleep until available
            ```
        </td>
        <td>
            ```
            trylock()

                else:
                    acquire and return SUCCESS
            ```

The key difference is no waiting.

{/*Why Trylock Is Useful*/}
trylock() provides flexibility.
Instead of being forced to wait, a thread can:
- Perform other useful work
- Try another resource
- Avoid potential deadlock
- Implement timeouts
- Maintain responsiveness

This is especially useful in:
- Event-driven systems
- Real-time systems
- High-performance servers
- Lock ordering avoidance strategies

Internally, trylock() typically performs:
    1. Atomic compare-and-swap
    2. If success → return success
    3. If fail → return error

No: Yield, Sleep, Kernel call, Scheduler involvement, It is extremely fast.

In POSIX threads: `pthread_mutex_trylock()`, If the mutex is already locked:
- It returns EBUSY
- The calling thread continues immediately

On Linux, this is implemented using the same fast-path atomic logic as pthread_mutex_lock, but without entering the blocking slow path via the futex mechanism.

**Deadlock Avoidance Strategy**

Trylock can help prevent deadlocks in multi-lock systems.
Example:
Thread A:
```
- Lock L1
- Trylock L2
- If fails → unlock L1 and retry
```
Without trylock Blocking on L2 could cause circular wait. Thus, trylock() enables dynamic lock ordering strategies.

The "bare-bones" mutex guarantees safety.
trylock() adds:
- Control
- Adaptability
- Deadlock management capability
- Performance tuning flexibility

This is a shift from pure synchronization toward concurrency design control.

So The introduction of trylock() reflects a general principle: Synchronization primitives evolve from minimal correctness tools into flexible control-flow mechanisms. A mutex is no longer just: "Enter critical section or wait.", It becomes: "Attempt access and let the programmer decide the strategy on failure.

| ---------------------- | ---------- | ------------------------- |
| Blocking               | Yes        | No                        |
| Guarantees acquisition | Eventually | Not guaranteed            |
| Simplicity             | High       | Requires handling failure |
| Deadlock flexibility   | Low        | High                      |
| CPU waste              | None       | None                      |

However:
- Poorly designed retry loops using trylock() can reintroduce busy waiting.
- It shifts complexity from the synchronization primitive to the application.

## Internal State Machine
A mutex transitions between:
```
UNLOCKED → LOCKED (no waiters)
LOCKED → LOCKED (with waiters)
LOCKED → UNLOCKED
```
When contention(race) occurs:
- Thread is added to wait queue
- Scheduler removes it from run queue
- Upon unlock, one waiter is awakened

## Ownership Semantics
Mutexes enforce strict ownership:
- Only owner may unlock
- Unlocking from another thread = undefined behavior
- Enables debugging and deadlock detection

This is the primary difference from semaphores.

## Types of Mutexes (POSIX)
| Type           | Behavior                |
| -------------- | ----------------------- |
| Normal         | Deadlock if relocked    |
| Recursive      | Same thread can re-lock |
| Error-checking | Detects misuse          |
| Robust         | Detects owner death     |

Robust mutexes handle thread crashes safely.


## Memory Ordering Guarantees
Mutexes provide:
- Acquire semantics on lock
- Release semantics on unlock

This ensures:
- No memory reordering across lock boundary
- Proper visibility of shared data

This is enforced using CPU memory barriers.

## Correctness View
A mutex must ensure:
- Safety: Never two threads in critical section simultaneously.
- Liveness: If lock is free, some waiting thread eventually acquires it.

## Sharing Data Across Processes
Synchronization requires shared state. But processes normally do not share memory.

Algorithms such as Peterson’s algorithm, Bakery algorithm, Classical semaphore implementations, and other synchronization primitives all assume: The participating execution units can read and write the same memory location.
For example:
- Peterson’s algorithm requires shared variables like turn and flag[].
- A semaphore requires a shared counter.
- Producer–consumer requires a shared buffer.

Without shared memory, these algorithms cannot function.

for Threads This Is Not a Problem, as Threads within a single process:
- Share the same virtual address space
- Share global variables
- Share heap memory
- Share static data

Therefore: Any mutex variable stored in memory is automatically shared. No special mechanism is required. This is why user-level threads can synchronize entirely in user space.

for Processes This Is a Problem, as Processes, by definition:
- Have separate virtual address spaces
- Cannot directly access each other’s memory

So how can two processes share:
- A semaphore counter?
- A turn variable?
- A shared buffer?

At first glance, they cannot.

There are tow solutions Solution 1: 
1. Kernel-Resident Synchronization Objects
2. Shared Memory Regions


### Kernel-Resident Synchronization Objects
One solution is to move the shared synchronization state into the kernel.
For example:
- System V semaphores
- POSIX named semaphores
- Kernel-managed mutexes
In this design:
- The semaphore counter lives in kernel memory.
- Processes manipulate it via system calls.
- The kernel ensures atomicity and blocking.
This eliminates the need for shared user memory.
However:
- Every operation requires a system call.
- Performance is lower.
- Kernel involvement is constant.

### Shared Files
If true shared memory is unavailable:
- A file can be used as a shared backing store.
- Processes map or read/write the same file.
- File locks may provide coordination.

This is slower and less elegant, but functional.

### Shared Memory Regions
Modern operating systems allow processes to explicitly share memory regions.
Examples:
- mmap with shared flags (UNIX)
- POSIX shared memory
- Memory-mapped files
- Windows shared sections

Systems such as UNIX and Microsoft Windows support this.

When processes map the same physical memory into their virtual spaces:
- They can share buffers
- They can share semaphores
- They can share mutex variables

Now classical algorithms become possible again.

When processes share most or all of their address spaces:
They begin to resemble threads.
However, a fundamental distinction remains.
Threads Share:
- Address space
- Open file descriptors
- Signal handlers
- Timers
- Process identity

Processes (even if sharing memory) Have:
- Separate file descriptor tables
- Separate signal handling state
- Separate kernel process structures
- Separate scheduling identities

Thus:
Threads are lighter-weight execution contexts within one process.
Processes remain independently managed kernel entities.

it is always true that multiple processes
sharing a common address space never have the efficiency of user-level threads
since the kernel is deeply involved in their management.

Even when processes share memory:
- The kernel manages each separately.
- Context switches involve kernel-level scheduling.
- System calls are required for many operations.
- Page tables and TLB effects are separate.
User-level threads:
- Switch via simple register save/restore.
- Avoid kernel transitions.
- Are significantly cheaper to manage.
Thus:
Shared-memory processes never reach the efficiency of user-level threads.

Synchronization requires:
    1. Shared state
    2. Atomic modification of that state

Threads satisfy (1) automatically.
Processes require explicit OS support.
This is why:
- Classical textbook algorithms assume shared memory.
- Real-world multiprocess synchronization depends heavily on OS mechanisms.

## Mutex vs Spinlock
Mutexes and spinlocks are both synchronization primitives used to protect critical sections. However, they differ in their behavior and usage.

Mutexes:
- Block the thread until the lock is available.
- Release the lock when the thread is done.
- Can be used for mutual exclusion and synchronization.

Spinlocks:
- Busy-wait until the lock is available.
- Release the lock when the thread is done.
- Can be used for mutual exclusion and synchronization.

| Mutex               | Spinlock                 |
| ------------------- | ------------------------ |
| Sleeps if busy      | Spins actively           |
| Good for long waits | Good for short waits     |
| Used in user space  | Kernel & low-level       |
| Involves scheduler  | No scheduler involvement |

Spinlocks waste CPU under contention.
Mutexes trade CPU for latency.
## Differences between Mutexes and Semaphores
Concurrency in operating systems requires mechanisms to control access to shared resources. Two fundamental synchronization primitives used for this purpose are:
- Semaphores
- Mutexes
Although they appear similar and are sometimes confused, they differ conceptually and operationally.

Semaphores and Mutexes are not the same. But they are related.
### Definition
A **semaphore**, introduced by Edsger W. Dijkstra, is an abstract data type consisting of:
- An integer value
- A set of waiting processes or threads
- Two atomic operations: wait (P) and signal (V)

The semaphore value represents the number of available resources.

A **mutex** (mutual exclusion lock) is a synchronization primitive designed specifically to protect critical sections(A locking mechanism that enforces ownership).

Unlike semaphores, mutexes enforce ownership.

### Operations
A semaphore has two atomic operations: wait (P) and signal (V), 
1. wait(S) (also called P or down)
    1. Decrement the semaphore value.
    2. If the result is negative, block the calling thread.
    3. Otherwise, allow the thread to proceed.
2. signal(S) (also called V or up)
    1. Increment the semaphore value.
    2. If there are blocked threads, wake one of them.
These operations must be executed atomically.

A mutex has two atomic operations: lock() and unlock().
1. lock()
- If unlocked, the calling thread acquires the mutex.
- If locked, the calling thread blocks.
2. unlock()
- Releases the mutex.
- Only the thread that acquired the mutex may release it.

### Types
There are two types of semaphores:
Binary Semaphore
- Value restricted to 0 or 1.
- Used to enforce mutual exclusion.
Counting Semaphore
- Value ranges from 0 to N.
- Used to control access to multiple identical resources.
### Characteristics
semaphore
- No ownership concept(does NOT track ownership).
- Any thread may call signal(), even if it did not previously call wait().
- Can be used for both mutual exclusion and synchronization.

A mutex has 
- Binary state (locked or unlocked).
- Ownership enforced(Only the thread that locked it can unlock it.).
- Designed exclusively for mutual exclusion(Designed strictly for protecting critical sections).
- Often supports priority inheritance.

### Relation between Mutex and Binary Semaphore
Is a Mutex a Type of Semaphore? This depends on perspective.

From a theoretical standpoint: A mutex can be modeled as a binary semaphore initialized to 1.

However, from a practical and implementation perspective:
A mutex is a specialized synchronization primitive with additional semantics such as ownership and priority inheritance. Therefore, while related, they are not identical.

Modern mutex ≠ semaphore. Why?
Because mutex adds:
- Ownership tracking
- Error detection
- Priority inheritance
- Recursive locking support (optional)

Semaphores do not provide these by default.

Is Mutex a Binary Semaphore?

Mathematically:
Yes — a mutex behaves like a binary semaphore with value 0/1.

Practically:
No — because of ownership and scheduling semantics.

| Feature                  | Semaphore                           | Mutex              |
| ------------------------ | ----------------------------------- | ------------------ |
| Value range(Counter value)              | 0..N                                | 0 or 1             |
| Ownership                | No                                  | Yes                |
| Unlock by another thread | Allowed                             | Not allowed        |

| Priority inheritance     | Not inherent                        | Commonly supported(Usually supported) |

### User-Space (POSIX) Implementation in Linux
Both POSIX mutexes and semaphores rely on:
- Atomic CPU instructions
- The Linux futex mechanism
- Kernel scheduler only when blocking is required

Both `pthread_mutex_t` and `sem_t`are implemented using futex(Futex = Fast Userspace Mutex).

| Feature                      | `pthread_mutex_t`            | `sem_t` (POSIX semaphore)     |
| ---------------------------- | ---------------------------- | ----------------------------- |
| Primary Purpose              | Mutual exclusion             | Resource counting & signaling |
| Value Range                  | 0 / 1                        | 0 .. N                        |
| Ownership Tracking           | Yes                          | No                            |
| Fast Path                    | Atomic compare-and-swap      | Atomic decrement              |
| Kernel Entry Needed?         | Only if contended            | Only if blocking required     |
| Blocking Mechanism           | `futex(FUTEX_WAIT)`          | `futex(FUTEX_WAIT)`           |
| Wake Mechanism               | `futex(FUTEX_WAKE)`          | `futex(FUTEX_WAKE)`           |
| Priority Inheritance         | Supported (PI mutex)         | Not inherently supported      |
| Recursive Lock Support       | Optional                     | Not supported                 |
| Unlock by Different Thread   | Undefined behavior           | Allowed                       |
| Typical Internal State       | Owner thread ID + lock state | Integer counter               |
| Performance When Uncontended | Very fast (user-space only)  | Very fast (user-space only)   |

**How pthread_mutex works**

Fast path:
- Atomic compare-and-swap (CAS)
- No kernel call
If contention:
- Calls futex(FUTEX_WAIT)
- Kernel blocks thread
Unlock:
- Atomic store
- futex(FUTEX_WAKE) if needed

**How POSIX semaphore works**

Very similar:
- Atomic decrement
- If negative → futex wait
- Post → futex wake

Difference:
- Semaphore keeps counter >1 possible.
- Mutex only 0/1 and tracks owner.

**Implementation Flow (User-Space)**
1. Mutex Lock (Uncontended)
    1. Atomic CAS
    2. If success → return
    3. No kernel involvement
2. Mutex Lock (Contended)
    1. Atomic CAS fails
    2. Call futex wait
    3. Kernel blocks thread

1. Semaphore Wait (Uncontended)
    1. Atomic decrement
    2. If result ≥ 0 → return
2. Semaphore Wait (Contended)
    1. Atomic decrement makes value < 0
    2. Call futex wait
    3. Kernel blocks thread

### Key Architectural Differences
**Ownership**
- Mutex tracks which thread owns it.
- Semaphore does not.

**Priority Inheritance**
Mutex:
- Prevents priority inversion.
Semaphore:
- No built-in priority inheritance.

**Intended Use**
Mutex:
- Protect shared data structures.
Semaphore:
- Control access to N identical resources.
- Synchronization between independent threads.

### Modern Linux Design Preference
Inside kernel development:
- Prefer mutex for mutual exclusion
- Prefer rw_semaphore for reader-writer cases
- Prefer completion for signaling
- Use counting semaphore only when resource counting is required

Semaphores are less commonly used in new kernel code.
### Practical Example Difference
**Semaphore Example**

Thread A:
```c
sem_wait(&s);
```
Thread B:
```c
sem_post(&s);   // perfectly legal
```
**Mutex Example**

Thread A:
```c
pthread_mutex_lock(&m);
```
Thread B:
```c
pthread_mutex_unlock(&m);  // ❌ undefined behavior
Mutex enforces ownership.
```
### When Should You Use Which?
Use mutex when:
- Protecting critical section
- One thread modifies shared data
- Lock/unlock same thread

Use semaphore when:
- Controlling access to N identical resources
- Signaling between threads
- Producer–consumer style coordination

### Final Summary
In Linux:
- Both mutexes and semaphores use atomic instructions.
- In user space, both rely on the futex system call.
- In kernel space, both use spinlocks and wait queues.
- Mutex adds ownership and priority handling.
- Semaphore provides generalized counting without ownership enforcement.
They are related but semantically and structurally distinct primitives.
```
Semaphore = resource counter
Mutex = ownership lock

Mutex is specialized, safer, and more structured.
```

## Summary
A mutex is:
- A guarded doorway
- With an ownership register
- Backed by atomic hardware support
- Integrated with the scheduler
- Enforcing memory ordering

It is both:
- A hardware-level atomic construct
- A scheduler-level blocking primitive
- A correctness guarantee mechanism

## Implementation
### Linux
#### User-Space (POSIX) Mutex in Linux
Linux implements `pthread_mutex_t` using:
- Atomic operations
- The futex mechanism

Fast Path (Uncontended)
    1. Atomic CAS attempts to acquire lock
    2. If successful → return
    3. No system call

Slow Path (Contended)
    1. CAS fails
    2. Call futex(FUTEX_WAIT)
    3. Kernel blocks thread
    4. Unlock performs futex(FUTEX_WAKE)

This design minimizes kernel involvement.

#### Kernel-Space Mutex in Linux
Defined in:
- `kernel/locking/mutex.c`

Kernel mutex structure (simplified):
```c
struct mutex {
    atomic_long_t owner;
    spinlock_t wait_lock;
    struct list_head wait_list;
};
```
Key characteristics:
- Tracks owner
- Maintains wait queue
- Uses spinlock internally to protect wait list
- Puts threads into TASK_UNINTERRUPTIBLE sleep
