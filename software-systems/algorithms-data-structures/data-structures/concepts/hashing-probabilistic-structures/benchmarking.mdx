## word-list benchmark
Given a fixed word list, how can we search for a word efficiently?

lets starts with a fixed dictionary:

```text
Number of words = 213,557
```

For our first try at this problem, we choose a primary hash table H that will hold $b = 2^{18}-1$ = 262,143 elements. Our word list contains 213,557 words.

The goal is to support fast searches such as:

```text
Is "computer" in the word list?
```

Instead of using binary search on a sorted array, they want to try **hash-based search**.

The basic structure is:

```text
                 word
                  │
                  ▼
          Java String.hashCode()
                  │
                  ▼
          abs(hashCode(word))
                  │
                  ▼
             % 262143
                  │
                  ▼
             bin index
                  │
                  ▼
                H[i]
```

If our hash function perfectly distributes the 213,557 words  strings, meaning no two words landed in the same bin. there will be no collisions and only about
40,000 open bins.
```text
213,557 occupied bins
262,143 total bins
```

Therefore:

$$
262,143 - 213,557 = 48,586
$$

bins would be empty.

The ideal situation would look approximately like:

```text
H[0] → word
H[1] → word
H[2] → empty
H[3] → word
H[4] → word
...
```

Most occupied bins would contain exactly one word.

This, however, is not the case. Next Table shows the distribution of
the hash values for the Java String class on our word list with a table of 262,143
bins. Recall 

```text
hash(s) = abs(hashCode(s)) % b
```

For every word.

For example, suppose:

```text
hashCode("computer") = 123456789
```

Then:

$$
123456789 \bmod 262143
$$
gives some bin index.

The same process is performed for all 213,557 words.

### How this table generated
Table 5-4 is generated by **taking every word in the word list, hashing it, mapping the hash to a table bin, and then counting how many words land in each bin**.

The process is essentially:

```text
213,557 words
      │
      ▼
Java String.hashCode()
      │
      ▼
integer hash code
      │
      ▼
abs(hashCode) % 262143
      │
      ▼
bin index: 0 ... 262142
      │
      ▼
count how many words land in each bin
      │
      ▼
Table 
```

** Start with the word list**

The benchmark contains:

```text
n = 213,557 words
```

For example, imagine a tiny word list:

```text
cat
dog
house
tree
apple
```

The actual benchmark does this for all 213,557 words.

** Calculate the Java hash code**

For each word, Java's `String.hashCode()` is calculated:

```java
int hash = word.hashCode();
```

For example:

```text
"cat"   → 98262
"dog"   → 99644
"house" → ...
"tree"  → ...
```

Java's algorithm is:

```text
h = 0

for each character c:
    h = 31 * h + c
```

So for `"cat"`:

```text
c = 99
a = 97
t = 116

h = 0
h = 31(0) + 99       = 99
h = 31(99) + 97      = 3166
h = 31(3166) + 116   = 98262
```

** Convert the hash code into a table index**

using:

```text
index = abs(hashCode) % b
```

where:

```text
b = 2^18 - 1
  = 262143
```

So:

```text
index = abs(hashCode) % 262143
```

For example, if:

```text
hashCode("cat") = 98262
```

then:

```text
98262 % 262143 = 98262
```

So `"cat"` goes into:

```text
H[98262]
```

If another word produces:

```text
hashCode = 524405
```

then:

```text
524405 % 262143 =  162119
```

so it goes into:

```text
H[162119]
```

** Repeat for all 213,557 words**

Conceptually, the program does:

```text
for each word:

    hashCode = word.hashCode()

    index = abs(hashCode) % 262143

    H[index].add(word)
```

The result is a hash table:

```text
H[0]
H[1]
H[2]
H[3]
...
H[262142]
```

Some bins remain empty:

```text
H[0]       → empty
H[1]       → "something"
H[2]       → "another", "word"
H[3]       → empty
H[4]       → "example"
...
```

** Count the number of words in each bin**.

After all 213,557 words have been inserted, the program counts the chain length of every bin.

For example, suppose we had:

```text
Bin     Words
--------------------------
0       empty
1       cat
2       dog, house
3       empty
4       tree
5       apple, orange, pear
```

Then the distribution is:

```text
0 words → 2 bins
1 word  → 2 bins
2 words → 1 bin
3 words → 1 bin
```

The real benchmark performs exactly this counting operation over **262,143 bins**. That's what this Table represents

The resulting table was:

| Words in a bin | Number of bins |

|              1 |         94,319 |
|              2 |         38,637 |
|              3 |         10,517 |

|              5 |            362 |
|              6 |             53 |

The first column means: **How many words ended up in one bin?**

The second column means: **How many bins have that many words?**

For example:

```text
2 → 38,637
```

means: There are **38,637 bins**, and each of those bins contains exactly **2 words**.

And:

```text

```

means: Only **3 bins** contain exactly **7 words**.

The number of bins must add up to 262,143:


```text

+ 4 ×  2,066
+ 5 ×    362
+ 6 ×     53
+ 7 ×      3
```

So the table is essentially a **histogram of hash-table bin occupancy**.

** How the actual program could generate it**

A simplified Java version would look like this:

```java
int b = 262143;

// Number of words in each bin
int[] binCount = new int[b];

for (String word : words) {

    int hashCode = word.hashCode();

    int index = Math.abs(hashCode) % b;

    binCount[index]++;
}
```

Now `binCount[i]` tells us:

```text
bin i contains how many words
```

Then generate the Table:

```java
int max = 0;

for (int count : binCount) {
    if (count > max) {
        max = count;
    }
}

for (int k = 0; k <= max; k++) {

    int numberOfBins = 0;

    for (int count : binCount) {
        if (count == k) {
            numberOfBins++;
        }
    }

    System.out.println(k + ": " + numberOfBins);
}
```

The output would conceptually be:

```text
0: 116186
1: 94319
2: 38637
3: 10517
4: 2066
5: 362
6: 53
7: 3
```

** Why does the table stop at 7?**

Because, for this particular:

* word list,
* Java `String.hashCode()`,
* table size `262143`,
* and `%` mapping,

the **largest bin contains 7 words**.

So:

```text
maximum chain length = 7
```

This is one of the things the table is trying to show.

The distribution is:

```text
              Number of bins
                    │
0 words  █████████████████████████
1 word   ███████████████████
2 words  ████████
3 words  ██
4 words  ▌
5 words  ▏
6 words  ▏
7 words  ▏
                    └──────────────
```

Most bins contain either **0 or 1 word**, relatively few contain 2 or 3, and only three contain 7.

**The key idea**

**This Table is not another data structure. It is a statistical summary of the hash table after all words have been hashed.**

```text
   │ 213,557 words
```

### Results
You can see, no bin contains more than seven strings.

for nonempty bins, the average number of strings per bin
is approximately 1.46. 

There are:

$$
262143 - 116186 = 145957
$$

nonempty bins.

There are 213,557 words.

Therefore:

$$
\frac{213557}{145957}
\approx 1.463
$$

So:

$$
\boxed{1.46}
$$

words per **nonempty** bin.

Notice that this is **not** the same as the load factor.

The load factor is:

$$
\alpha = \frac{213557}{262143}
\approx 0.815
$$

**Why is the maximum chain only 7?**

This is actually evidence that the hash function is distributing the words reasonably well.

The longest chain is:

```text
7 words
```

and only three bins have that many.

So the worst chain looks like:

```text
H[i]
 │
 ├── word 1
 ├── word 2
 ├── word 3
 ├── word 4
 ├── word 5
 ├── word 6
 └── word 7
```

Searching that chain requires at most around seven string comparisons in the worst case for that table.

That's quite small compared with:

```text
213,557
```

total words.

**So why isn't the distribution "perfect"?**

Because collisions still occur.

The distribution is:

```text
94,319 bins → 1 word
38,637 bins → 2 words
10,517 bins → 3 words
...
```

A perfect distribution would ideally have:

```text
213,557 bins → 1 word
48,586 bins → 0 words
```

Instead, many words share bins.

For example:

```text
Perfect:

H[0] → word
H[1] → word
H[2] → word
H[3] → word


Actual:

H[0] → word
H[1] → word → word
H[2] → empty
H[3] → word → word → word
```

You may be surprised that this is really a good hashing function"

Why?

Because at first you might look at the 116,186 empty bins and think:

> "The hash function is wasting a huge amount of space. Maybe we need a better hash function."

But that's not necessarily true.

Remember:

```text
213,557 words
262,143 bins
```

Even with a **perfect collision-free** mapping, you must have:

$$
262143 - 213557 = 48586
$$

empty bins.

So empty bins are unavoidable with this table size.

The actual distribution has:

```text
116,186 empty bins
```

instead of the theoretical minimum:

```text
48,586 empty bins
```

There are certainly more empty bins than ideal, but the nonempty bins still have relatively short chains.

The longest chain is only 7.

For the record, there were only five pairs of strings with identical hashCode values, or example:

```text
"hypoplankton"
"unheavenly"
```

both produce:

```text
427,589,249
```

This is a different type of collision.

There are actually **two levels where collisions can happen**.

1. Level 1 — identical hash codes

```text
"hypoplankton"
       │
       ▼
427589249

"unheavenly"
       │
       ▼
427589249
```

These two strings have the exact same Java hash code.

2. Level 2 — different hash codes mapping to the same bin

Suppose:

```text
word A → 100000
word B → 362143
```

but:

$$
100000 \bmod 262143 = 100000
$$

and maybe another hash code also maps to bin `100000`.

So:

```text
different hash codes
       ↓
same table index
       ↓
collision
```

This second type is much more common.

**Hash code vs table index**

This benchmark is a great example of why we must distinguish these concepts.

```text
String
   │
   ▼
hashCode()
   │
   ▼
integer hash code
   │
   ▼
abs(hashCode) % 262143
   │
   ▼
table index
```

For example:

```text
"computer"
      ↓
123456789
      ↓
123456789 % 262143
      ↓
some bin
```

Two different strings can:

1. Case A: same hash code

```text
A → 427589249
B → 427589249
```

2. Case B: different hash codes but same bin

```text
A → 123456
B → 385599

123456 % 262143 = 123456
385599 % 262143 = 123456
```

3. Case C: different hash codes and different bins

```text
A → 123456 → H[123456]
B → 200000 → H[200000]
```

The hash table must deal with collisions at the **bin level**.

### Memory Benchmark
Almost half of the table bins (116,186) have no strings
that hash to them. So this hashing function wastes about 500KB of memory (assuming the size of a pointer is four bytes).  Why?

The primary table contains:

```text
262,143 bins
```

and each bin is represented by a pointer.

Assuming:

```text
pointer = 4 bytes
```

then:

$$
262143 \times 4
$$

gives:

$$
1,048,572\text{ bytes}
$$

approximately:

$$
1.0\text{ MB}
$$

for the primary array.

But only:

```text
145,957 bins
```

are nonempty.

Therefore:

```text
116,186 pointers
```

point to nothing.

If you use the LinkedList class, each nonempty element of H will require 12 bytes
of memory, assuming the size of a pointer is four bytes(assuming the Java `LinkedList` object has that amount of overhead under their simplified memory model).

**Why does each nonempty bin need a linked list?**

Because they are using **separate chaining**.

Conceptually:

```text
H
│
├── H[0] → null
├── H[1] → Node
├── H[2] → Node → Node
├── H[3] → null
├── H[4] → Node → Node → Node
│
└── ...
```

Every nonempty bin points to a linked list.

For the previ‐
ous example of 213,557 words, we require 5,005,488 bytes of memory beyond the
actual string storage. The breakdown of this memory usage is:
• Size of the primary table: 1,048,572 bytes
• Size of 116,186 linked lists: 1,394,232 bytes
• Size of 213,557 list elements: 2,562,684 bytes

**in addition to the actual strings themselves.**

Each string has 12 bytes of overhead. We can therefore add 213,557*12 = 2,562,684 addi‐
tional bytes to our overhead. So the algorithm chosen in the example requires
7,568,172 bytes of memory. 

```text
                 HASH TABLE MEMORY
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
 Primary array    Linked-list       List elements
 1,048,572 B       overhead          2,562,684 B
                   1,394,232 B
       │               │                │
       ▼               ▼                ▼
 262,143 refs      LinkedList       213,557 nodes
```
The actual number of characters in the strings in the
word list we used in the example is only 2,099,075, so it requires approximately 3.6
times the space required for the characters in the strings.

**Why is this important for Hash-Based Search?**

This benchmark demonstrates an important point:

> **Hash-based search is not simply "O(1), therefore everything is free."**

You have to pay for the hash table.

There is a preprocessing cost:

```text
Word list
   ↓
hash every word
   ↓
build table
   ↓
allocate memory
   ↓
insert words
```

Then searches become very fast:

```text
query
  ↓
hash(query)
  ↓
H[index]
  ↓
short chain
  ↓
compare
```

So there is a classic trade-off:

```text
            PREPROCESSING
                  +
              MEMORY
                  ↓
          FAST SEARCH
```

**Why not simply use a much smaller table?**

Suppose we reduce:

```text
b = 262,143
```

to:

```text
b = 50,000
```

Then:

$$
\alpha =
\frac{213557}{50000}
\approx 4.27
$$

Now the average chain length becomes much larger.

You would get something like:

```text
H[0] → word → word → word → word
H[1] → word → word → ...
H[2] → word → word → word → ...
```

Search becomes more expensive.

So:

```text
smaller b
   ↓
less array memory
   ↓
higher load factor
   ↓
more collisions
   ↓
longer chains
   ↓
slower search
```

---

**Why not make the table enormous?**

Suppose:

```text
b = 10,000,000
```

Then:

$$
\alpha =
\frac{213557}{10000000}
\approx 0.021
$$

Collisions would become much less likely.

But now you're allocating millions of table entries for only 213,557 words.

```text
More bins
    ↓
fewer collisions
    ↓
faster searches

BUT

More bins
    ↓
more memory
```

This is exactly the **Memory vs Performance** trade-off from your Section 6.

perfect hashing?

Now the opening paragraph makes much more sense.

The authors say:

> "When the word list is fixed and not likely to change, we can do better by creating a perfect hash function."

Why?

Their ordinary solution has:

```text
262,143 bins
+
213,557 list elements
+
linked-list overhead
+
collisions
```

But because the dictionary is fixed, they could potentially construct a **perfect hash function**.

Ideally:

```text
213,557 words
       ↓
perfect hash
       ↓
213,557 unique positions
```

Then:

```text
no collision chains
no linked-list nodes
potentially less memory
direct lookup
```

And if they use a **minimal perfect hash**, the table could conceptually have exactly:

```text
213,557 positions
```

for the 213,557 words.

That's why the perfect-hashing alternative is attractive for this particular benchmark.

**The big lesson**

The benchmark is **not primarily trying to prove that Java's `String.hashCode()` is perfect**. It is demonstrating that:

> A conventional hash table can make searching a 213,557-word collection extremely efficient, while also showing the real memory cost of achieving that performance.

And because the word list is **static**, the authors then point out that **perfect/minimal perfect hashing could potentially remove the collision-handling overhead altogether**.

### implementation simplicity vs memory efficiency
{/* This paragraph is discussing the **engineering trade-off between implementation simplicity and memory efficiency** when using Java's JDK collection classes for a hash table.
 */}
Most of this overhead is the price of using the classes in the JDK. The engineering
trade-off must weigh the simplicity and reuse of the classes compared to a more
complex implementation that reduces the memory usage.


** What does "Most of this overhead" mean?**

The book is referring to the extra memory discussed in the previous benchmark.

A hash table doesn't only store the actual words. A Java implementation may also need:

```text
Hash table
├── array of references
│
├── LinkedList objects
│
├── list-node objects
│
├── references such as next
│
└── Java object metadata/alignment
```

For example:

```text
H[0] ──→ null

H[1] ──→ Node ──→ Node ──→ null
             │
             └── word
```

The actual word is only part of the memory consumption.

The Java objects and references needed to organize those words are **overhead**.

---

** "The price of using the classes in the JDK"**

The JDK gives you ready-made data structures such as:

```java
HashMap
LinkedList
ArrayList
```

This is extremely convenient.

Instead of implementing a linked list yourself:

```java
class Node {
    String value;
    Node next;
}
```

you can simply use:

```java
LinkedList<String> list = new LinkedList<>();
```

But the general-purpose JDK implementation has its own object and metadata overhead.

So you're effectively making this trade:

```text
                 JDK collections
                       │
          ┌────────────┴────────────┐
          │                         │
       Advantages                Cost
          │                         │
     easy to use               more memory
     well tested               object overhead
     reusable                  general-purpose
     maintainable
```

---

** "The engineering trade-off"**

This is the central idea.

You have two possible approaches.

1. **Approach A — Use the JDK**

For example:

```java
Map<String, Word> words = new HashMap<>();
```

Advantages:

* very little code
* well-tested
* easy to understand
* easy to maintain
* reusable
* good performance for most applications

Potential disadvantage:

* additional memory overhead
* less control over the internal representation

2. **Approach B — Build a specialized implementation**

You could instead design a custom structure specifically for your application.

For example:

```text
Custom Hash Table

array
  │
  ├── index 0 → word
  ├── index 1 → word
  ├── index 2 → word
  └── ...
```

You might avoid:

```text
LinkedList object
Node objects
next references
some object metadata
```

and therefore reduce memory usage.

But now **you have to implement and maintain everything yourself**.

---

** Why would you choose the more complex implementation?**

when memory is a significant constraintUse one of several variations(alternative hash-table designs). For example, imagine an application storing:

```text
10 million keys
```

If each entry has even a small amount of additional overhead, the total can become substantial.

For example, conceptually:

```text
10,000,000 entries
×
20 bytes extra overhead
=
200 MB
```

The exact numbers depend on the implementation, JVM, object layout, references, and architecture, but the principle is important:

> **Small per-entry overhead can become large at scale.**

---

alternative hash-table designs.

```text
Hash Tables
│
├── Separate Chaining
│
├── Open Addressing
│   ├── Linear Probing
│   ├── Quadratic Probing
│   └── Double Hashing
│
├── Perfect Hashing
├── Minimal Perfect Hashing
└── other specialized representations
```

These alternatives can reduce memory overhead in particular situations.

For example, **open addressing** stores entries directly in the table rather than allocating a separate linked-list node for every entry:

```text
Separate chaining:

H[5] → Node → Node → Node
         ↓
       object
         ↓
       object


Open addressing:

H[0] → empty
H[1] → key
H[2] → key
H[3] → empty
H[4] → key
```

The second approach can have better memory locality and less per-entry object overhead, although it has its own constraints and trade-offs.

```text
enough memory

good hash function
      +

      +
```

then:

```text
             Use the JDK
                 ↓

```

You don't need to build a highly optimized custom hash table just because one might theoretically use less memory.

** This is an important software-engineering principle**

The paragraph isn't really about hashing alone.

It's demonstrating:

> **Don't optimize implementation complexity unless the resource savings justify it.**

You can think of it as:

```text
                    Engineering Trade-off
                           │
             ┌─────────────┴─────────────┐
             │                           │
        Simplicity                  Optimization
             │                           │
        JDK classes                Custom structure
             │                           │
        less code                  more code
        easier maintenance         more complexity
        more overhead              less overhead
```

The correct choice depends on the application's constraints.
