A self-balancing tree is a tree-based data structure that automatically maintains its height as elements are inserted or deleted. Its goal is to keep searching, inserting, and deleting efficient, even when the input data arrives in an unfavorable order.

Self-balancing trees are an extension of the Binary Search Tree (BST), so let's start with the problem they solve.

## 1. Why do we need self-balancing trees?

A Binary Search Tree organizes values according to this rule:

* Values smaller than a node go into its left subtree.

* Values greater than a node go into its right subtree.

* The same rule applies recursively to every node.

For example, inserting `40, 20, 60, 10, 30, 50, 70` produces a reasonably balanced BST.

### Case 1: A balanced BST

```
        40
       /  \
     20    60
    / \    / \
   10  30 50  70
```

The tree has three levels of nodes, so a search can reach a target quickly.

Now consider inserting the sorted values `10, 20, 30, 40, 50, 60, 70` into a regular, unbalanced BST.


**A perfectly balanced tree has the minimum possible height**.

### Case 2: A degenerate BST

If we insert too many nodes in a Binary Search
Tree, we end up with a tree of very high height, where many
nodes have only one child. 

For example, if we insert nodes with
keys/values always greater than the previous one(sorted order), we end up with
something that looks more like a **Linked List**. 

![The same binary search tree in a very badly balanced form, in a somewhat balanced form, and in a perfectly balanced form.](/docs/assets/software-systems/data-structures-and-algorithms/data-structures/trees//tree-balancing.png)

```
10 → 20 → 30 → 40
```
BST becomes:
```
10
  \
  20
    \
    30
      \
      40
```

The tree becomes a chain, behaving much like a linked list.

But we can rearrange nodes in a tree such that its height is reduced. This is called **tree balancing**. 

The problem is that a regular BST does not guarantee its shape.

| Operation | Balanced BST   | Worst-case unbalanced BST |
| --------- | -------------- | ------------------------- |
| Search    | $O(log⁡n)$      | $O(⁡n)$              |
| Insert    | $O(log⁡n)$      | $O(⁡n)$              |
| Delete    | $O(log⁡n)$      | $O(⁡n)$              |

Here, `n` is the number of nodes. These bounds assume the balanced tree maintains logarithmic height; a regular BST can become unbalanced depending on insertion order.

The key idea: instead of hoping that the BST stays balanced, a self-balancing tree actively repairs its structure when necessary.

Most operations with trees involve following links between nodes
until we get to a specific one. The higher the height of the tree,
the longer the average path between nodes, and the more times
we need to access the memory. Therefore, it’s important to reduce
tree height.

Consider a Binary Search Tree with n nodes. Its maximum height
is n, in which case it looks like a Linked List. The minimum height,
with the tree perfectly balanced, is log2 n. The complexity of searching an item in a binary search tree is proportional to its height. In
the worst case, the search must descend to the lowest level, reaching all the way to the tree’s leaves in order to find the item. Searching in a balanced Binary Search Tree with n items is thus O(log n).
That’s why this data structure is often chosen for implementing
Sets (which requires finding if items are already present) and Maps
(which requires finding key-values).

However, tree balancing is an expensive operation, as it requires sorting all nodes. Rebalancing a tree after each insertion or deletion can greatly slow down these operations. Usually, trees are undergo balancing after several insertions and deletions take
place. But balancing the tree from time to time is only a reasonable
strategy for trees that are rarely changed.

To efficiently handle binary trees that change a lot, **self-balancing binary trees** were invented. Their procedures for inserting or removing items directly ensure the tree stays 
balanced.

## What does “balanced” actually mean?

A tree is balanced when its height remains small relative to the number of nodes.

The height of a tree is the number of edges on its longest path from the root to a leaf. Some definitions count nodes instead, but this does not change the asymptotic complexity.

For a tree with `n` nodes:

* A well-balanced tree has height $O(log⁡n)$.

* A completely skewed tree can have height $O(⁡n)$.

For example, if a balanced tree contains approximately one million nodes, its height can be around 20 edges, whereas a skewed tree can have nearly one million edges.

This difference explains why balancing is important.

## How does a self-balancing tree work?

A self-balancing tree typically follows the same three steps:

1. Perform the operation

Insert a new value or delete an existing value using the tree's ordering rules.

2. Detect imbalance

Check whether the operation has violated the tree's balancing rules.

3. Restore balance

Rearrange nodes, often using rotations, and update any balancing metadata.

The exact rules depend on the tree type. AVL trees enforce stricter height balance, while Red-Black trees use coloring rules to keep the height bounded.

### Tree rotations

A rotation is a local restructuring operation that changes the parent-child relationships between nodes without breaking the BST ordering property.

Consider inserting `10, 20, 30` into an ordinary BST.

Before balancing:

```
10
  \
   20
     \
      30
```

This is a right-leaning chain. A left rotation at node `10` produces:

```
     20
    /  \
   10   30
```

The tree is now balanced.

Notice what changed:

* `20` became the root of this subtree.

* `10` became the left child of `20`.

* `30` remained the right child of `20`.

* The sorted order `10 < 20 < 30` was preserved.

A left rotation moves the right child up and the former parent down to the left.

A right rotation performs the mirror-image operation. Together, left and right rotations are the basic building blocks of many self-balancing binary search trees.

Some imbalances require two rotations. For example, an insertion may create a left-right or right-left pattern, which needs a double rotation to restore the tree's balance.

Importantly, rotations are local: they rearrange a subtree while preserving the relative sorted order of its values.

## Main types of self-balancing trees

Not all self-balancing trees use the same definition of balance. These are the main types worth learning.

### AVL Tree

An AVL tree is a BST that maintains a strict height-balance condition at every node.

The balance factor is commonly defined as:
$$
BF(v)=h(v_L)-h(v_R)
$$
Every node must have a balance factor of −1-1−1, 000, or +1+1+1.

They
require a bit more time to insert and delete items than Red-Black
Trees, but tend to have better balancing. This means they’re faster
than Red-Black Trees for retrieving items. 

AVL Trees are often used
to optimize performance in read-intensive scenarios

Best to study when you want to understand height balance and rotations in detail.

![Red Black Trees](https://images.openai.com/static-rsc-4/

### Red-Black Tree

The **Red-Black Tree** is a famous example of a self-balancing tree, which colors nodes either “red” or “black” for its balancing strategy. 

**Red-Black Trees** are frequently used to implement Maps: the map can be heavily edited in an efficient way, and finding any given key in the map remains fast because of self-balancing.

A Red-Black tree assigns each node a red or black color and enforces rules involving node colors and black-height.

These rules prevent the longest paths from becoming excessively longer than the shortest paths.

Common in general-purpose ordered maps and sets, including Java's TreeMap and TreeSet implementations.


### B-Tree

A B-tree is a balanced multiway search tree: a node can contain multiple keys and have more than two children.

Rather than relying primarily on binary rotations, it maintains balance through operations such as splitting, merging, and redistributing keys between nodes.

Particularly useful for databases and storage systems, where reducing disk or page accesses matters.

### B+ Tree

A B+ tree is a B-tree variant in which records or record pointers are typically stored in the leaves, and internal nodes guide searches. Leaf nodes are commonly linked for efficient range scans.

Widely used in database indexes and storage engines.

### Splay Tree

A Splay tree moves an accessed node toward the root using rotations. It does not maintain a strict balance condition after every operation, but its operations have amortized logarithmic time complexity.

Useful when some elements are accessed much more frequently than others.

### Comparison

| Tree       | Balancing strategy                    | Search                              | Insert / Delete                     |
| ---------- | ------------------------------------- | ----------------------------------- | ----------------------------------- |
| AVL        | Strict height balance                 | $O(log⁡n)$ worst case | $O(log⁡n)$ worst case |
| Red-Black  | Color invariants                      | $O(log⁡n)$ worst case | $O(log⁡n)$ worst case |
| B-tree     | Multiway node occupancy               | $O(log⁡n)$ worst case | $O(log⁡n)$ worst case |
| B+ tree    | Multiway structure with linked leaves | $O(log⁡n)$ worst case | $O(log⁡n)$ worst case |
| Splay tree | Move accessed nodes toward root       | $O(log⁡n)$ amortized  | $O(log⁡n)$ amortized  |

For B-trees and B+ trees, these conventional bounds assume a fixed branching factor or fixed storage-page size. Their actual performance also depends on the number of keys per node and the cost of accessing storage.

For Splay trees, an individual operation can take $O(⁡n)$(n); the logarithmic guarantee is amortized across a sequence of operations.

## Self-balancing tree versus regular BST

A self-balancing tree is not a completely different idea from a BST. It is a tree structure that adds extra rules and operations to maintain a useful shape.

| Feature                        | Regular BST | Self-balancing BST               |
| ------------------------------ | ----------- | -------------------------------- |
| Stores ordered values          | Yes         | Yes                              |
| Follows BST ordering rules     | Yes         | Yes                              |
| Automatically restores balance | No          | Yes                              |
| Guarantees logarithmic height  | No          | Yes, for AVL and Red-Black trees |
| Needs extra balancing logic    | No          | Yes                              |
| May require rotations          | No          | Yes, for AVL and Red-Black trees |

Think of it this way:

* BST: knows where values belong.

* Self-balancing BST: knows where values belong and how to keep the tree efficient.

The B-tree and B+ tree follow the same broad balancing idea but are multiway trees rather than binary trees.

## What happens during insertion and deletion?

### Insertion

Consider inserting `10, 20, 30` into an AVL tree.

1. Insert `10` as the root.

2. Insert `20` as the right child of `10`.
BST becomes:
```
10
  \
  20
```
3. Insert `30` as the right child of `20`.
BST becomes:
```
10
  \
  20
    \
    30
```
1. Detect that node `10` has a balance factor of −2.

2. Perform a left rotation at `10`.

The resulting tree is:

```
     20
    /  \
   10   30
```

The tree's ordering remains correct, and its height is reduced.

### Deletion

Deletion is more involved because removing a node can change the heights of several ancestors.

A typical AVL deletion works as follows:

1. Find the node to delete.

2. Delete it using standard BST deletion rules.

3. Update the heights of affected ancestors.

4. Check their balance factors.

5. Apply rotations wherever necessary.

Unlike some insertion cases, a deletion can require rebalancing at multiple ancestors on the path toward the root.

## Time complexity and space complexity

Let n be the number of stored elements.

| Operation               | AVL / Red-Black tree     | Unbalanced BST, worst case |
| ----------------------- | ------------------------ | -------------------------- |
| Search                  | $O(log⁡n)$                | $O(⁡n)$               |
| Insert                  | $O(log⁡n)$                | $O(⁡n)$               |
| Delete                  | $O(log⁡n)$                | $O(⁡n)$               |
| Find minimum / maximum  | $O(log⁡n)$                | $O(⁡n)$               |
| In-order traversal      | $O(⁡n)$                   | $O(⁡n)$              |
| Space to store the tree | $O(⁡n)$                   | $O(⁡n)$               |

A balanced tree does not make every operation constant-time. It prevents the tree from becoming so tall that basic operations degrade into linear-time traversal.

The space needed for the tree remains $O(⁡n)$(n), although each implementation may also store extra metadata such as a height or color for each node.

## Example in Java: using a self-balancing tree

Java provides `TreeMap` and `TreeSet`, which use a Red-Black tree implementation to maintain ordered keys or elements.

You usually do not need to implement balancing yourself to benefit from it.

```Java
import java.util.TreeMap;

public class SelfBalancingTreeDemo {
    public static void main(String[] args) {
        TreeMap<Integer, String> students = new TreeMap<>();

        // Insert keys in an unfavorable order for a regular BST.
        students.put(10, "Ali");
        students.put(20, "Mona");
        students.put(30, "Omar");
        students.put(40, "Sara");
        students.put(50, "Noor");

        // Search by key.
        System.out.println(students.get(30));

        // Keys are maintained in sorted order.
        System.out.println(students.keySet());

        // Retrieve the smallest and largest keys.
        System.out.println(students.firstKey());
        System.out.println(students.lastKey());

        // Delete a key.
        students.remove(30);

        System.out.println(students.keySet());
    }
}
```

Expected output:

```
Omar
[10, 20, 30, 40, 50]
10
50
[10, 20, 40, 50]
```

Even though keys are inserted in sorted order, the underlying Red-Black tree maintains its balancing invariants.

## When should you use a self-balancing tree?

Choose a self-balancing tree when you need ordered data with predictable search, insertion, and deletion performance.

* AVL tree: useful when fast lookups are important and you want strict height balance.

* Red-Black tree: a good general-purpose choice for dynamically changing ordered collections.

* B-tree / B+ tree: appropriate for database indexes and storage systems that operate on disk pages.

* Splay tree: worth considering when access patterns are nonuniform and recently accessed items are likely to be accessed again.

If you only need fast membership checks and do not need sorted traversal, a hash table may be a better fit. If you need to retrieve keys in order, find the next larger key, or perform range queries, an ordered tree is often more appropriate.

## 10. Recommended learning roadmap

For your Data Structures and Algorithms study, I recommend organizing this topic in the following order:

1. Binary Search Tree recap — ordering invariant, search, insertion, deletion, height, and worst-case behavior.

2. Tree rotations — left rotation, right rotation, double rotations, and why rotations preserve BST ordering.

3. AVL Trees — node heights, balance factors, LL, RR, LR, and RL cases; insertion and deletion.

4. Red-Black Trees — color invariants, recoloring, rotations, insertion fix-up, and deletion fix-up.

5. B-Trees and B+ Trees — node capacity, splitting, merging, redistribution, and database indexes.

6. Splay Trees — zig, zig-zig, zig-zag, and amortized analysis.

7. Comparison and implementation — complexity analysis, use cases, testing, and benchmarking.

The main takeaway: a self-balancing tree preserves the useful ordering behavior of a BST while controlling its height. That is what lets it guarantee efficient ordered operations instead of depending on how values happen to be inserted.
