If your items are structured in a sorted array, we can also search them in O(log n) time through Binary Search. This search process discards half the search space in each step.

**Binary Search** is a searching algorithm for finding a target element in a **sorted collection**.

The key idea is simple:

> Instead of checking elements one by one, repeatedly divide the search range in half.

This makes binary search dramatically faster than sequential search for large sorted collections.

Binary Search divides the sorted collection in half until the sought-for item is found, or until it is determined that the item does not exist in the collection.

Binary Search delivers better performance than Sequential Search because it starts with a collection whose elements are already sorted. 

## The Basic Idea

Suppose we have this sorted array:

```text
Index:   0   1   2   3   4   5   6   7   8
         ↓   ↓   ↓   ↓   ↓   ↓   ↓   ↓   ↓
Array:  10  20  30  40  50  60  70  80  90
```

We want to find:

```text
70
```

A sequential search would do:

```text
10 → 20 → 30 → 40 → 50 → 60 → 70
```

Potentially 7 comparisons. Binary search instead looks at the **middle**. The middle is:

```text
50
```

Compare:

```text
70 > 50
```

Therefore:

> `70` cannot be anywhere in the left half.

We can immediately discard:

```text
10 20 30 40 50
```

and continue with:

```text
60 70 80 90
```

Now inspect the middle:

```text
70
```

Found!

Only **2 comparisons** were necessary.

**Why Can We Throw Half Away?**

This is the most important concept behind binary search.

Binary search depends on the collection being **sorted**.

Suppose:

```text
10 20 30 40 50 60 70 80 90
```

and the target is:

```text
70
```

We inspect:

```text
50
```

Since:

```text
70 > 50
```

and the array is sorted, every element before `50` is also:

```text
≤ 50
```

Therefore none of them can be `70`.

So we know:

```text
target > middle
```

and can discard the left half.

Similarly, if:

```text
target < middle
```

we discard the right half.

If:

```text
target == middle
```

we are finished.

## Input/Output
The input to Binary Search is an indexed collection A whose elements are totally ordered, which means that given two index positions, `i` and `j`, `A[i] < A[j]` if and only if `i < j`. We construct a data structure that holds the elements (or pointers to the elements) and preserves the ordering of the keys. The output to Binary Search is either `true` or `false`.

## Context and Motivation
binary search is an algorithmic strategy, but the data structure you choose determines how practical it is.

When searching through the ordered collection, a logarithmic number of probes is necessary in the worst case.

Suppose we have a sorted collection:

```text
10  20  30  40  50  60  70  80  90
```

Binary search repeatedly divides the remaining search space in half.

For `n` elements, the number of probes is approximately:

```text
log₂(n)
```

So:

```text
n = 8       → about 3 probes
n = 16      → about 4 probes
n = 1,024   → about 10 probes
n = 1,048,576 → about 20 probes
```

Therefore:

```text
Worst-case search time = O(log n)
```

Here, a **probe** means examining a particular element/candidate.

For an array, a probe is essentially:

```c
A[mid]
```

But Binary Search Needs a Way to Navigate, The important question is:

> **How do we efficiently reach the middle element?**

With an array, this is easy.

For example:

```text
Index:  0   1   2   3   4   5   6   7
        ↓               ↓
       10  20  30  40  50  60  70  80
                        mid
```

We can directly access:

```c
A[4]
```

Arrays provide **random access**.

Accessing an element by index takes:

```text
O(1)
```

So binary search can efficiently perform:

```text
calculate middle
       ↓
access A[mid]
       ↓
discard half
       ↓
calculate new middle
       ↓
access A[mid]
       ↓
...
```

This gives us: $O(log n)$

**static collections**

> The elements don't change, or changes are extremely rare.

For example:

3. Binary search is straightforward

## The Three Possible Outcomes

At every iteration, binary search compares the target with the middle element.

There are only three possibilities:

1. Case 1 — Target found

```text
target == A[mid]
```

Return the position.

2. Case 2 — Target is larger

```text
target > A[mid]
```

Search the right half:

```text
mid + 1 ... high
```

3. Case 3 — Target is smaller

```text
target < A[mid]
```

Search the left half:

```text
low ... mid - 1
```

So the fundamental decision is:

```text
                 Compare target
                       │
             ┌─────────┼─────────┐
             ↓         ↓         ↓
          target     target     target
            <          =          >
           mid        mid        mid
            │          │          │
            ↓          ↓          ↓
        left half    found     right half
```

## The Search Range

Binary search maintains a range containing all positions where the target could still exist.

We normally use two variables:

```c
low
high
```

For an array:

```text
A[0 ... n-1]
```

initially:

```text
low = 0
high = n - 1
```

The possible search range is:

```text
low ---------------- high
 ↓                       ↓
[   ][   ][   ][   ][   ][   ][   ]
```

Calculate the middle:

```text
mid = low + (high - low) / 2
```

Then compare:

```text
A[mid]
```

with the target.

**Why Use `low + (high - low) / 2`?**

You will often see:

```c
mid = (low + high) / 2;
```

This is mathematically correct.

However, in languages with fixed-width integers such as C, C++, and Java, `low + high` can overflow.

For example, conceptually:

```text
low  = 2,000,000,000
high = 2,100,000,000
```

Adding them could exceed the maximum value of a 32-bit signed integer.

Instead use:

```c
mid = low + (high - low) / 2;
```

This avoids the addition of two potentially large indices.

It is therefore the preferred implementation.

```text
                                    70
```
```text
                                      │

```

This is the fundamental Binary Search strategy.
## Pseudocode

### Iterative Pseudocode
The standard **iterative binary search** assumes that the collection is sorted in ascending order.

```text
BINARY-SEARCH(A, n, target)

    low ← 0
    high ← n - 1

    while low ≤ high do <1>

        mid ← low + (high - low) / 2 <2>

        if A[mid] = target then
            return mid

        else if target < A[mid] then
            high ← mid - 1

        else
            low ← mid + 1

    return NOT_FOUND
```
1. Repeat while there is a range to be searched
2. Midpoint computed using integer arithmetic.

**How it works**

```text
                 Search range
             low             high
              ↓                ↓
             [──────────────────]
                      ↓
                     mid
                      │
              Compare A[mid]
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      target <     target =    target >
       A[mid]       A[mid]      A[mid]
          │           │           │
          ↓           ↓           ↓
      high=mid-1    found      low=mid+1
```

**Example**

For:

```text
A = [10, 20, 30, 40, 50, 60, 70, 80, 90]
target = 70
```

the search proceeds:

```text
low=0, high=8
mid=4 → A[4]=50
70 > 50
        ↓
low=5, high=8

mid=6 → A[6]=70
70 = 70
        ↓
return 6
```

The critical requirement is that **`A` must be ordered**. Without the ordering property, we cannot safely discard half of the search space.

### Recursive Pseudocode
The key idea is:

Instead of keeping track of the search boundaries, it creates a smaller array (sliced) containing only the half where the target could still exist, then recursively searches that smaller array.

#### Recursive with `slice()
```
function binary_search(items, key)

    if items is empty
        return NULL

    i ← items.length / 2

    if key = items[i]
        return items[i]

    if key > items[i]
        sliced ← items.slice(i + 1, items.length)
    else
        sliced ← items.slice(0, i)

    return binary_search(sliced, key)
```
```text
if not items
    return NULL
```

This is the **base case** for the recursion.

It means:

> If the collection is empty, the target cannot be present.

For example:

```text
items = []
```

There is nothing to search, so:

```text
return NULL
```

This prevents the recursion from continuing forever.

#### Recursive with `low/high`
Better recursive implementation, Instead of creating slices, we can keep the original array and pass:

```text
low
high
```

For example:

```text
function binary_search(items, key, low, high)

    if low > high
        return NULL

    mid ← low + (high - low) / 2

    if key = items[mid]
        return items[mid]

    if key < items[mid]
        return binary_search(items, key, low, mid - 1)

    return binary_search(items, key, mid + 1, high)
```
Now we're doing:

```text
same array
    │
    ├── low
    ├── mid
    └── high
```

rather than creating:

```text
new array
new array
new array
...
```

This is generally the preferred implementation.

The `slice()` version expresses "search the remaining half" by physically creating that half, while the `low/high` version expresses the same idea by simply changing the **search boundaries**.

## Complexity

### Time Complexity
Each step of binary_search does a constant number of opera-
tions and discards half the input. This means for n items, log2 n
steps fully reduce the input. As each step involves a fixed number
of operations, the algorithm is O(log n). You can search a million,
or a trillion items, yet the search is still going to perform well.

**Why Binary Search Is `O(log n)`**

This is worth understanding mathematically.

Suppose there are `n` elements.

After one comparison: `n / 2` remain.

After two: `n / 2²` remain.

After three: `n / 2³` remain.

After `k` comparisons: `n / 2ᵏ` remain.

We stop when approximately one element remains: `n / 2ᵏ = 1`

Therefore: `n = 2ᵏ`

Taking logarithms:

```text
k = log₂(n)
```

Therefore:

```text
Binary Search = O(log₂ n)
```

Since changing the base of a logarithm only changes the constant factor:

```text
O(log₂ n) = O(log n)
```

| Case         |       Time |
| ------------ | ---------: |
| Best case    |     `O(1)` |
| Average case | `O(log n)` |
| Worst case   | `O(log n)` |

Best case occurs when:

```text
A[mid] == target
```

on the first iteration.

For example:

```text
[10 20 30 40 50 60 70]
          ↑
        target
```

If the target is `40`, it is immediately found.

---

### Space Complexity

The iterative implementation uses only:

```text
low
high
mid
```

Therefore:

```text
Space = O(1)
```

This is an important advantage over a naive recursive implementation, which uses the call stack.

recursive creates a new array every time it recursively calls itself:

```text
sliced ← items.slice(...)
```

That means although the algorithm performs approximately:

```text
O(log n)
```

search levels, creating the slices requires copying elements.

For example:

```text
[1,2,3,4,5,6,7,8]
        ↓ slice
[5,6,7,8]
        ↓ slice
[5,6]
        ↓ slice
[5]
```

Those arrays aren't free to create.

Therefore, this implementation is generally less efficient than the standard recursive Binary Search that passes **index boundaries**.

**Complexity comparison**

| Implementation            |                                          Search |                                 Extra space | Main issue         |
| ------------------------- | ----------------------------------------------: | ------------------------------------------: | ------------------ |
| Iterative with `low/high` |                                        O(log n) |                                        O(1) | None significant   |
| Recursive with `low/high` |                                        O(log n) |                         O(log n) call stack | Recursion          |
| Recursive with `slice()`  | Search logic O(log n), but slicing adds copying | O(n) cumulative allocation/copying possible | Creates new arrays |

## Implementation
### Iterative Binary Search

#### C
A standard implementation in C is:

```c
#include <stdio.h>

int binarySearch(const int A[], int n, int target)
{
    int low = 0;
    int high = n - 1;

    while (low <= high)
    {
        int mid = low + (high - low) / 2;

        if (A[mid] == target)
        {
            return mid;
        }
        else if (target < A[mid])
        {
            high = mid - 1;
        }
        else
        {
            low = mid + 1;
        }
    }

    return -1;
}

int main(void)
```

**Understanding the Loop Condition**

One of the most important details is:

```c

```

Why `<=` rather than `<`?

Because the range can shrink until exactly **one element** remains.

For example:

```text

high = 5
```

There is still one possible element:

```text
        ↓
[10 20 30 40 50 60 70]
           ↑
          index 5
```

So we must examine it.

If we used:

```c
while (low < high)
```

we would stop too early.

The condition:

```c
low <= high
```

means:

> Continue while there is at least one candidate position.

**How the Search Range Shrinks**

Suppose we have: $n = 16$

Initially: 16 elements

After one iteration: ≈ 8 elements 

After two: ≈ 4

After three: ≈ 2

After four: ≈ 1

After five: 0

So the number of elements isn't decreasing by a constant amount.

It is being **divided by 2**.

That is the reason for: O(log n)

#### Java
Given an ordered collection of elements as an array, the following Java code in shows a parameterized implementation of Binary Search for any base type `T`. Java
provides the `java.util.Comparable<T>` interface that contains the `compareTo`
method. Any class that correctly implements this interface guarantees a total ordering of its instances.
```Java
/**
 * Generic Binary Search implementation.
 *
 * The collection must be sorted in ascending order.
 *
 * @param <T> the type of elements being searched.
 *            T must implement Comparable<T>.
 */
public class BinarySearch<T extends Comparable<T>> {

    /**
     * Searches the collection for a non-null target.
     *
     * @param collection sorted array to search
     * @param target value to search for
     * @return true if target is found, false otherwise
     */
    public boolean search(T[] collection, T target) {

        // Binary search cannot compare a null target.
        if (target == null) {
            return false;
        }

        // Define the initial search range.
        int low = 0;
        int high = collection.length - 1;

        // Continue while there is a valid search range.
        while (low <= high) {

            // Calculate the middle index.
            int mid = low + (high - low) / 2;

            // Compare target with the middle element.
            int rc = target.compareTo(collection[mid]);

            if (rc < 0) {
                // Target is smaller than the middle element.
                // Search the left half.
                high = mid - 1;

            } else if (rc > 0) {
                // Target is larger than the middle element.
                // Search the right half.
                low = mid + 1;

            } else {
                // target == collection[mid]
                // The target has been found.
                return true;
            }
        }

        // Search range became empty.
        // Target does not exist in the collection.
        return false;
    }

    /**
     * Test the BinarySearch implementation.
     */
    public static void main(String[] args) {

        // The array MUST be sorted for binary search.
        Integer[] numbers = {
            10, 20, 30, 40, 50,
            60, 70, 80, 90
        };

        // Create a BinarySearch object for Integer.
        BinarySearch<Integer> binarySearch = new BinarySearch<>();

        // Test 1: Target exists.
        Integer target1 = 70;

        boolean result1 = binarySearch.search(numbers, target1);

        System.out.println("Searching for " + target1);
        System.out.println("Found: " + result1);
        System.out.println();

        // Test 2: Target does not exist.
        Integer target2 = 35;

        boolean result2 = binarySearch.search(numbers, target2);

        System.out.println("Searching for " + target2);
        System.out.println("Found: " + result2);
        System.out.println();

        // Test 3: First element.
        Integer target3 = 10;

        boolean result3 = binarySearch.search(numbers, target3);

        System.out.println("Searching for " + target3);
        System.out.println("Found: " + result3);
        System.out.println();

        // Test 4: Last element.
        Integer target4 = 90;

        boolean result4 = binarySearch.search(numbers, target4);

        System.out.println("Searching for " + target4);
        System.out.println("Found: " + result4);
        System.out.println();

        // Test 5: Null target.
        Integer target5 = null;

        boolean result5 = binarySearch.search(numbers, target5);

        System.out.println("Searching for null");
        System.out.println("Found: " + result5);
    }
}
```

```text
          │                   │
          ↓                   ↓
      search left         search right
```

** What Does "Total Ordering" Mean?**

The passage says:

This means the objects have a consistent ordering relationship.

For two objects `a` and `b`, comparison tells us whether:

For example, if:

This is what allows binary search to safely eliminate half of the collection.

### Recursive Binary Search

#### Recursive with `slice()
#### Recursive with `low/high`
Binary search can also be expressed recursively.

```c
int binarySearchRecursive(
    const int A[],
    int low,
    int high,
    int target)
{
    if (low > high)
    {
        return -1;
    }

    int mid = low + (high - low) / 2;

    if (A[mid] == target)
    {
        return mid;
    }

    if (target < A[mid])
    {
        return binarySearchRecursive(
            A, low, mid - 1, target);
    }

    return binarySearchRecursive(
        A, mid + 1, high, target);
}
```

Call it with:

```c
int result = binarySearchRecursive(
    A,
    0,
    n - 1,
    target
);
```

The recursive structure mirrors the mathematical definition:

```text
Search(A, low, high, target)

    if range is empty
        not found

    mid = middle

    if A[mid] == target
        found

    if target < A[mid]
        search left half

    else
        search right half
```

---

### Iterative vs Recursive

| Property       | Iterative                      | Recursive                  |
| -------------- | ------------------------------ | -------------------------- |
| Time           | `O(log n)`                     | `O(log n)`                 |
| Extra space    | `O(1)`                         | `O(log n)`                 |
| Implementation | Usually simpler for production | Often conceptually elegant |
| Function calls | One function                   | Multiple recursive calls   |
| Stack usage    | Constant                       | Logarithmic                |

For an array implementation, the **iterative version is usually preferable when you simply need binary search**, because it achieves `O(1)` auxiliary space.

## Analysis
### Search/Access Costs

Binary Search adds a small amount of complexity for large performance gains. **Binary Search reduces the number of elements you inspect, but that does not always mean it is fast in practice.** The cost of *accessing* each element can dominate the algorithm.

**1. In-memory array: Binary Search works extremely well**

Suppose we have:

```text
[10, 20, 30, 40, 50, 60, 70, 80, 90]
```

Because this is an array, accessing `A[mid]` is very cheap:

```text
A[4]
```

The computer can calculate the memory address directly:

```text
address = base_address + index × element_size
```

So Binary Search can jump directly to the middle.

For `n` elements:

```text
Number of probes ≈ log₂(n)
```

For example:

```text
n = 1,000,000

log₂(1,000,000) ≈ 20
```

So instead of potentially examining one million elements with Sequential Search, Binary Search needs only around 20 probes.

---

** What changes when the collection is on disk?**

Now imagine the million elements are stored in a file:

```text
data.bin
```

A large collection might need to be kept in secondary storage, such as a file on a disk. In such a case, the ith element is accessed by its  offset location within the file. Using secondary storage, the time required to search for an element is dominated by the costs to access the storage



Conceptually:

```text
File
│
├── element 0
├── element 1
├── element 2
├── ...
├── element 500000
├── ...
└── element 999999
```

Binary Search still needs to calculate:

```text
mid = 500000
```

and access:

```text
element[500000]
```

But this is no longer simply a memory access.

The program may need to access a location on **secondary storage**.

For example:

```text
CPU
 │
 ▼
Operating System
 │
 ▼
File System
 │
 ▼
Disk / SSD
 │
 ▼
Required data
```

That access can be much more expensive than accessing an element already in RAM.

---

** The important distinction: computational complexity vs access cost**

Binary Search still performs:

```text
O(log n)
```

comparisons/probes.

But the cost of each probe is no longer necessarily:

```text
O(1)
```

in practical terms.

We can think about the total cost as:

```text
Total Search Cost
    =
Number of Probes
    ×
Cost of Accessing a Probe
```

For an in-memory array:

```text
O(log n) × cheap memory access
```

For secondary storage:

```text
O(log n) × expensive storage access
```

Therefore, the **20 disk accesses** required to search one million records could be much more important than the 20 comparisons themselves.

---

** Why "the ith element is accessed by its offset"**

the ith element is accessed by its offset location within the file. This means that if the records have a fixed size, we can calculate where a particular element is located.

Suppose every record is exactly 100 bytes.

Then:

```text
record 0 → offset 0
record 1 → offset 100
record 2 → offset 200
record 3 → offset 300
...
```

So record `i` is approximately:

```text
offset = i × 100
```

For example:

```text
record 500000

offset = 500000 × 100
       = 50,000,000 bytes
```

Binary Search can therefore determine where the middle record is located without reading all preceding records.

That's good.

But it still has to **access the storage containing that location**.

---

** Why multiple random accesses can become expensive**

Consider Binary Search over a disk file.

It might access:

```text
500000
   ↓
250000
   ↓
375000
   ↓
437500
   ↓
...
```

These locations can be far apart in the file.

So the access pattern is roughly:

```text
        File
──────────────────────────────────────────
0                                      1M
             ↑
           access

      ↑
    access

                   ↑
                 access

             ↑
           access
```

This is called **random access**.

For storage systems, especially traditional hard disks, random access can be expensive compared with sequentially reading nearby data.

Even with SSDs, storage access has significantly different costs from CPU/register/cache/RAM operations.

---

** So is Binary Search bad for files?**

**Not necessarily.**

The point is not:

> "Never use Binary Search on files."

Instead, it says:

> When storage access dominates the running time, we should consider data structures and algorithms designed specifically for external storage.

This is an important transition from **ordinary in-memory algorithms** to **external-memory algorithms**.

---

** One important solution: B-Trees**

A classic solution is a **B-Tree** or **B+ Tree**.

These structures are specifically useful when data is stored on secondary storage.

Instead of having a binary tree like:

```text
              50
             /  \
           25    75
          / \    / \
        10  40  60  90
```

a B-Tree can have many keys in each node:

```text
             [30 | 60 | 90]
           /      |      |      \
          /       |      |       \
     [10 20]  [40 50] [70 80] [100 110]
```

Why is that useful? Because one storage access can bring an entire node/page into memory.

Instead of:

```text
disk access
    ↓
one comparison
    ↓
disk access
    ↓
one comparison
    ↓
disk access
```

we can have:

```text
             disk access
                  ↓
        ┌───────────────────┐
        │ 30 | 60 | 90      │
        │ multiple keys      │
        └───────────────────┘
                  ↓
        many comparisons
        in memory
```

This greatly reduces the number of storage accesses.

---

** This is why databases use B+ Trees**

This concept is fundamental to database indexing.

Suppose a database has:

```text
10,000,000 customer records
```

and we want:

```sql
SELECT *
FROM customer
WHERE customer_id = 735291;
```

A naive approach might scan records sequentially:

```text
record 1
record 2
record 3
...
```

That's potentially:

```text
O(n)
```

A Binary Search-like approach could reduce the number of probes to:

```text
O(log n)
```

but if each probe requires a storage access, that can still be costly.

A database index such as a **B+ Tree** is designed to minimize the number of storage pages that must be accessed.

Conceptually:

```text
                Root
          [100 | 500 | 900]
          /      |       \
         /       |        \
      Page      Page      Page
       ↓         ↓         ↓
    records   records   records
```

Each page contains many keys, so the tree has a **high branching factor**.

That makes the tree much shorter than a binary tree.

---

So
> **Algorithmic complexity alone does not determine real-world performance.**

For an in-memory array:

```text
Binary Search
      ↓
O(log n) comparisons
      ↓
very cheap random access
      ↓
excellent performance
```

For secondary storage:

```text
Binary Search
      ↓
O(log n) probes
      ↓
potentially expensive storage accesses
      ↓
storage access becomes dominant
```

Therefore, we may choose a data structure specifically designed around the characteristics of the storage system:

```text
                    Searching
                       │
          ┌────────────┴────────────┐
          │                         │
    In-memory data            Secondary storage
          │                         │
    Sorted Array              B-Tree / B+ Tree
          │                         │
    Binary Search          Minimize page accesses
```

**The key takeaway**

**Binary Search minimizes the number of elements examined. It does not necessarily minimize the cost of accessing those elements.**

For RAM-based arrays, this distinction is often small because random access is cheap.

For disk/database storage, **I/O operations can dominate**, so specialized structures such as **B-Trees and B+ Trees** become more appropriate.

This is an important bridge from the basic **Binary Search algorithm** to the broader topic of **external-memory searching and database indexing**.

### Invariant
**Binary Search Is Really About Maintaining an Invariant**

A useful way to understand binary search at an algorithmic level is through its **search invariant**.

At the beginning of every iteration:

> If the target exists in the array, it must be somewhere between `low` and `high`.

Initially:

```text
low = 0
high = n - 1
```

So the entire array is a candidate range.

After examining `mid`, we preserve this invariant by eliminating the half that cannot contain the target.

For example:

```text
target > A[mid]
```

means:

```text
target cannot be in [low, mid]
```

so we change:

```text
low = mid + 1
```

The invariant remains true:

```text
If target exists,
it must be in [low, high].
```

Eventually the range becomes empty:

```text
low > high
```

At that point, the invariant tells us:

> There is no possible position left for the target.

Therefore the target does not exist.

This is the foundation of a formal correctness proof.

---

**Correctness Argument**

We can prove binary search correct using the invariant.

#### Initialization

Initially:

```text
low = 0
high = n - 1
```

Therefore every element of the array is inside the search range.

So if the target exists, it is inside the range.

---

#### Maintenance

Suppose:

```text
mid = ...
```

There are three cases.

1. Case A

```text
A[mid] == target
```

The target has been found.

2. Case B

```text
target < A[mid]
```

Because the array is sorted, everything after `mid` is at least `A[mid]`.

Therefore the target cannot be after `mid`.

We set:

```text
high = mid - 1
```

3. Case C

```text
target > A[mid]
```

Because the array is sorted, everything before `mid` is at most `A[mid]`.

Therefore the target cannot be before `mid`.

We set:

```text
low = mid + 1
```

Thus the invariant remains true.

---

#### Termination

Eventually:

```text
low > high
```

The search range is empty.

Since every iteration preserved the property that any possible target must lie inside the range, an empty range means:

```text
target does not exist
```

Therefore the algorithm is correct.

---

### Binary Search Requires More Than "Sorted Data"

The most common statement is:

> Binary search requires a sorted array.

That's generally correct, but there is another important requirement:

> We must be able to efficiently access the middle element.

Consider an array:

```text
A[0], A[1], A[2], ...
```

We can access:

```c
A[mid]
```

in:

```text
O(1)
```

So the binary search itself is `O(log n)`.

But imagine a linked list:

```text
10 → 20 → 30 → 40 → 50 → 60 → 70
```

There is no direct:

```text
list[mid]
```

operation.

To reach the middle, we have to traverse the list.

This changes the practical efficiency considerably.

Therefore binary search is particularly natural for:

* arrays
* vectors
* random-access sequences
* sorted tables

---

### Duplicate Elements

Now consider:

```text
A = [10, 20, 20, 20, 30, 40]
```

Search for:

```text
20
```

A normal binary search may return **any one** of the three `20`s.

For example:

```text
10 20 20 20 30 40
    ↑
```

It does not necessarily return the first occurrence.

This leads to important binary-search variations.

1. **First Occurrence**

Sometimes the problem isn't:

> Does `20` exist?

Instead it is:

> Where is the **first** `20`?

We modify binary search.

When we find:

```text
A[mid] == target
```

we don't immediately return.

Instead, we remember the position and continue searching left.

Conceptually:

```text
if A[mid] == target:
    answer = mid
    high = mid - 1
```

This allows us to find the leftmost occurrence.

2. **Last Occurrence**

Similarly, to find the last occurrence:

```text
if A[mid] == target:
    answer = mid
    low = mid + 1
```

So:

```text
First occurrence
    ↓
search further left

Last occurrence
    ↓
search further right
```

Both remain:

```text
O(log n)
```

---

### Lower Bound

A very important binary-search variation is **lower bound**.

Given:

```text
[10, 20, 20, 30, 40, 50]
```

find the first position where:

```text
A[i] >= target
```

For:

```text
target = 25
```

the answer is:

```text
30
```

at index:

```text
3
```

because:

```text
A[3] = 30 >= 25
```

and no earlier element satisfies the condition.

---

### Upper Bound

Similarly, **upper bound** finds the first position where:

```text
A[i] > target
```

For:

```text
A = [10, 20, 20, 30, 40]
```

and:

```text
target = 20
```

upper bound is:

```text
30
```

at index:

```text
3
```

because index `3` is the first position where:

```text
A[i] > 20
```

These concepts are extremely useful in competitive programming, standard libraries, and range queries.

---

### Binary Search Does Not Always Search for an Element

This is a very important advanced idea.

Binary search can search for a **boundary**, not just a value.

For example:

```text
False False False False True True True True
```

Suppose we want the first `True`.

Binary search can find it.

This general pattern is:

```text
P(x) = false false false ... true true true
```

We search for the transition:

```text
false → true
```

This is sometimes called **binary search on a monotonic predicate**.

---

**Example: First Value ≥ Target**

Suppose:

```text
A = [10, 20, 30, 40, 50, 60]
```

and:

```text
target = 35
```

We want the first element satisfying:

```text
A[i] >= 35
```

Evaluate:

```text
10 >= 35 → false
20 >= 35 → false
30 >= 35 → false
40 >= 35 → true
50 >= 35 → true
60 >= 35 → true
```

So we have:

```text
false false false true true true
                    ↑
                  answer
```

Binary search can locate this boundary in `O(log n)`.

---

**The Most Important Mental Model**

Don't think of binary search merely as:

> "Look at the middle element."

A better mental model is:

> **Maintain a range of possible answers and eliminate half of the impossible answers at every step.**

That idea generalizes far beyond ordinary array searching.

```text
Possible answers
────────────────────────────────
        ↓
     eliminate half
        ↓
Possible answers
────────────
        ↓
     eliminate half
        ↓
Possible answers
──────
        ↓
      answer
```

---

### Common Mistakes

#### Mistake 1: Using binary search on unsorted data

This is invalid:

```text
[50, 10, 80, 20, 40, 70]
```

There is no guarantee that eliminating a half is safe.

---

#### Mistake 2: Wrong middle calculation

Prefer:

```c
mid = low + (high - low) / 2;
```

instead of:

```c
mid = (low + high) / 2;
```

for overflow safety.

---

#### Mistake 3: Forgetting `+1`

If:

```text
target > A[mid]
```

we must use:

```c
low = mid + 1;
```

not:

```c
low = mid;
```

Otherwise the same `mid` may be examined repeatedly.

---

#### Mistake 4: Forgetting `-1`

If:

```text
target < A[mid]
```

we use:

```c
high = mid - 1;
```

not:

```c
high = mid;
```

---

#### Mistake 5: Incorrect loop condition

Usually:

```c
while (low <= high)
```

is appropriate when `high` is an inclusive boundary.

---

#### Mistake 6: Assuming duplicates have a particular result

Normal binary search does not necessarily return:

```text
first occurrence
```

or:

```text
last occurrence
```

unless specifically implemented to do so.

## Variations

### search-or-insert operation

This section extends **Binary Search** from a simple **"does this element exist?"** operation into a **"search-or-insert"** operation.

The important idea is that Binary Search can tell us **not only whether an element exists, but also exactly where it belongs if it doesn't exist**.

---

** The problem: search or insert**

Suppose we have a sorted array:

```text
ordered = [10, 20, 30, 40, 50]
```

We want to search for a target.

There are two possibilities:

1. Target exists

```text
target = 30
```

Binary Search returns:

```text
index = 2
```

2. Target doesn't exist

Suppose:

```text
target = 35
```

The target should be placed between `30` and `40`:

```text
[10, 20, 30, 35, 40, 50]
             ↑
           index 3
```

So a useful search function should be able to return:

```text
"Found at index 2"
```

or:

```text
"Not found, but insert at index 3"
```

That's what this technique provides.

---

** Why return a negative number?**

The function has to distinguish between:

```text
target found
```

and:

```text
target not found
```

Remember that all valid array indexes are non-negative:

```text
0
1
2
3
4
...
```

Therefore, we can use a **negative number to represent "not found."**

The function uses:

```text
-(p + 1)
```

where `p` is the correct insertion position.

For example, if the target should be inserted at:

```text
p = 3
```

the function returns:

```text
-(3 + 1)
= -4
```

So:

```text
return -4
```

means:

```text
target not found
insert at index 3
```

---

** Why not simply return `-p`?**

You might wonder why we don't simply return:

```text
-p
```

The problem is when:

```text
p = 0
```

we would return:

```text
-0
```

But:

```text
-0 == 0
```

So we couldn't distinguish:

```text
found at index 0
```

from:

```text
not found, insert at index 0
```

That's why the encoding uses:

```text
-(p + 1)
```

This guarantees that the "not found" result is always strictly negative.

Inserting into or deleting from an ordered array becomes inefficient as the size of the array grows, because every array entry must contain a valid element. Therefore, inserting involves extending the array (physically or logically) and pushing, on average, half of the elements ahead one index position. Deletion requires shrinking the array and moving half of the elements one index position lower.

```c
#include <stdio.h>
#include <stdbool.h>

/*
 * Binary Search-Or-Insert
 *
 * The array must be sorted in ascending order.
 *
 * bs_contains():
 *     Returns the index if target is found.
 *     Returns -(insertion_position + 1) if target is not found.
 *
 * bs_insert():
 *     Inserts target into the correct position if it is not
 *     already present.
 */


/*
 * Search for target using Binary Search.
 *
 * Return value:
 *
 *     >= 0
 *         Target was found.
 *         The return value is its index.
 *
 *     < 0
 *         Target was not found.
 *         The encoded value -(p + 1) is returned,
 *         where p is the insertion position.
 */
int bs_contains(const int ordered[], int size, int target)
{
    int low = 0;
    int high = size - 1;

    while (low <= high)
    {
        /*
         * Calculate the middle index.
         *
         * This form avoids possible integer overflow
         * compared with (low + high) / 2.
         */
        int mid = low + (high - low) / 2;

        /*
         * Target is smaller than the middle element.
         * Search the left half.
         */
        if (target < ordered[mid])
        {
            high = mid - 1;
        }

        /*
         * Target is larger than the middle element.
         * Search the right half.
         */
        else if (target > ordered[mid])
        {
            low = mid + 1;
        }

        /*
         * Target is equal to the middle element.
         * Target has been found.
         */
        else
        {
            return mid;
        }
    }

    /*
     * Target was not found.
     *
     * When the loop finishes, low is the position
     * where target should be inserted.
     *
     * Encode the insertion position as:
     *
     *     -(low + 1)
     *
     * The +1 is necessary because -0 is still 0.
     */
    return -(low + 1);
}


/*
 * Insert target into the sorted array if it is not
 * already present.
 *
 * Parameters:
 *
 *     ordered    - sorted array
 *     size       - current number of elements
 *     capacity   - maximum number of elements
 *     target     - value to insert
 *     inserted   - output flag indicating whether insertion occurred
 *
 * Returns:
 *
 *     New size of the array.
 */
int bs_insert(
    int ordered[],
    int size,
    int capacity,
    int target,
    bool *inserted
)
{
    /*
     * Search for the target.
     */
    int idx = bs_contains(ordered, size, target);

    /*
     * Target already exists.
     */
    if (idx >= 0)
    {
        *inserted = false;
        return size;
    }

    /*
     * Target was not found.
     *
     * Decode the insertion position.
     *
     * If:
     *
     *     idx = -(p + 1)
     *
     * then:
     *
     *     p = -(idx + 1)
     */
    int insertion_position = -(idx + 1);

    /*
     * Make sure there is enough space.
     */
    if (size >= capacity)
    {
        *inserted = false;

        printf("Error: array is full. Cannot insert %d.\n",
               target);

        return size;
    }

    /*
     * Shift elements one position to the right.
     *
     * Example:
     *
     *     [10, 20, 30, 40, 50]
     *                 ^
     *                 insertion position = 3
     *
     * becomes:
     *
     *     [10, 20, 30, 40, 40, 50]
     *
     * before placing target at index 3.
     */
    for (int i = size; i > insertion_position; i--)
    {
        ordered[i] = ordered[i - 1];
    }

    /*
     * Place the new element in its correct position.
     */
    ordered[insertion_position] = target;

    *inserted = true;

    return size + 1;
}


/*
 * Print all elements in the array.
 */
void print_array(const int ordered[], int size)
{
    printf("[");

    for (int i = 0; i < size; i++)
    {
        printf("%d", ordered[i]);

        if (i < size - 1)
        {
            printf(", ");
        }
    }

    printf("]\n");
}

 */
int main(void)
{
```

Python can simply do:

```python
ordered.insert(position, target)
```

because Python's list manages its own storage.

In C, we have to perform the shifting ourselves:

```c
for (int i = size; i > insertion_position; i--)
{
    ordered[i] = ordered[i - 1];
}

ordered[insertion_position] = target;
```

For example, inserting `35`:

```text
Before:

index:   0   1   2   3   4
        [10, 20, 30, 40, 50]
                 ↑
              position 3


Shift right:

        [10, 20, 30, 40, 40, 50]
                 ↑


Insert:

        [10, 20, 30, 35, 40, 50]
```

So the complexity remains:

| Operation                |   Complexity |
| ------------------------ | -----------: |
| Binary Search            | **O(log n)** |
| Find insertion position  | **O(log n)** |
| Shift elements           |     **O(n)** |
| Insert into sorted array |     **O(n)** |
| Search + Insert          |     **O(n)** |

The key point is that **Binary Search makes finding the insertion position fast, but it cannot eliminate the cost of physically shifting array elements.**

```Python
"""
Binary Search-Or-Insert

The collection must be sorted in ascending order.

bs_contains():
    - Returns the index if target is found.
    - Returns -(insertion_position + 1) if target is not found.

bs_insert():
    - Inserts target at the correct position if it is not already present.
"""


def bs_contains(ordered, target):
    """
    Search for target using Binary Search.

    Returns:
        >= 0 : index where target was found
        < 0  : -(insertion_position + 1) if target was not found
    """

    low = 0
    high = len(ordered) - 1

    while low <= high:

        # Calculate the middle index.
        mid = (low + high) // 2

        # Target is smaller than the middle element.
        if target < ordered[mid]:
            high = mid - 1

        # Target is larger than the middle element.
        elif target > ordered[mid]:
            low = mid + 1

        # Target is equal to the middle element.
        else:
            return mid

    # Target was not found.
    #
    # At this point, low is the correct position
    # where target should be inserted.
    #
    # We encode the insertion position as:
    #
    #    -(low + 1)
    #
    # The +1 is necessary because index 0 cannot
    # be represented by a negative zero.
    return -(low + 1)


def bs_insert(ordered, target):
    """
    Insert target into the sorted list if it is not already present.

    Returns:
        True  : target was inserted
        False : target was already present
    """

    # Search for the target.
    idx = bs_contains(ordered, target)

    # Negative result means target was not found.
    if idx < 0:

        # Decode the insertion position.
        insertion_position = -(idx + 1)

        # Insert target at the correct position.
        ordered.insert(insertion_position, target)

        return True

    # Target already exists.
    return False

    print(f"{operation}")
    print(f"Array: {ordered}")
    print()
```

** Understanding `bs_contains`**

Here is the function:

```python
def bs_contains(ordered, target):
    """Return index of target in ordered or -(p+1) where to insert it."""

    low = 0
    high = len(ordered) - 1

    while low <= high:

        mid = (low + high) // 2

        if target < ordered[mid]:
            high = mid - 1

        elif target > ordered[mid]:
            low = mid + 1

        else:
            return mid

    return -(low + 1)
```

The first part is ordinary Binary Search.

---

** The important difference is the final `return`**

Normally, Binary Search does:

```python
return -1
```

when the target isn't found.

But this implementation does:

```python
return -(low + 1)
```

Why?

Because when the loop finishes, `low` tells us where the target **belongs**.

This is the key observation.

** What does Python `insert()` actually do?**

This is where the second paragraph becomes important.

Consider:

```python
ordered = [10, 20, 30, 40, 50]
```

We want to insert:

```text
35
```

at index `3`.

Before:

```text
index:    0   1   2   3   4

        [10, 20, 30, 40, 50]
```

We need:

```text
index:    0   1   2   3   4   5
          ↓   ↓   ↓   ↓   ↓   ↓
        [10, 20, 30, 35, 40, 50]
```

The elements after position `3` have to move:

```text
40 → index 4
50 → index 5
```

Conceptually:

```text
Before:

[10, 20, 30, 40, 50]
             ↑   ↑
             │   │
             └───┘
               move

After:

[10, 20, 30, 35, 40, 50]
```

So Binary Search finds the position quickly, but **inserting into an array is still expensive**.

---

** Binary Search is O(log n), but insertion is O(n)**

This is one of the most important points.

Searching:

```text
bs_contains()
       ↓
O(log n)
```

But inserting into an array:

```text
ordered.insert(...)
       ↓
O(n)
```

in the worst case.

Why?

Because potentially many elements have to move.

---

** Example: insertion at the beginning**

Suppose:

```text
[20, 30, 40, 50, 60]
```

We want to insert:

```text
10
```

Binary Search immediately determines:

```text
insertion position = 0
```

But now every element has to move:

```text
60 → 5
50 → 4
40 → 3
30 → 2
20 → 1
```

Conceptually:

```text
Before:

[20, 30, 40, 50, 60]

After:

[10, 20, 30, 40, 50, 60]
```

That's `O(n)` movement.

Notice the interesting situation:

```text
Finding position     → O(log n)
Performing insertion → O(n)
```

Therefore:

```text
Total = O(log n) + O(n)
      = O(n)
```

The insertion dominates.

---

** Why "on average, half the elements" move**

Suppose the array contains `n` elements.

The insertion position could be anywhere:

```text
Beginning
    ↓
[ ... n elements ... ]
                  ↑
               End
```

If we insert near the beginning, many elements move.

If we insert near the end, few elements move.

On average, approximately half the elements need to move:

```text
n / 2
```

So the average amount of shifting is:

```text
O(n)
```

The constant `1/2` doesn't change Big-O notation:

```text
O(n/2) = O(n)
```

---

** Deletion has the same problem**

Suppose:

```text
[10, 20, 30, 40, 50, 60]
```

Delete:

```text
30
```

We need to close the gap:

```text
Before:

[10, 20, 30, 40, 50, 60]
          ↑
       remove
```

Then:

```text
40 → move to index 2
50 → move to index 3
60 → move to index 4
```

Result:

```text
[10, 20, 40, 50, 60]
```

Again, potentially many elements must move.

Therefore:

```text
Search       → O(log n)
Insertion    → O(n)
Deletion     → O(n)
```

for a sorted array.

---

** This gives us an important trade-off**

A sorted array is excellent when the collection is mostly static:

```text
              Sorted Array
                    │
          ┌─────────┴─────────┐
          │                   │
       Search              Updates
          │                   │
       O(log n)             O(n)
          │                   │
       Excellent            Expensive
```

So if you have:

```text
1000000 elements
```

and you search millions of times but almost never insert/delete, a sorted array can be a very good choice.

But if the collection changes constantly:

```text
insert
delete
insert
insert
delete
...
```

then repeatedly shifting array elements becomes expensive.

---

** Compare with a Binary Search Tree**

This leads naturally to the next data structure: the **Binary Search Tree (BST)**.

A balanced BST can provide approximately:

```text
Search     → O(log n)
Insert     → O(log n)
Delete     → O(log n)
```

while a sorted array provides:

```text
Search     → O(log n)
Insert     → O(n)
Delete     → O(n)
```

Conceptually:

| Operation          | Sorted Array |  Balanced BST |
| ------------------ | -----------: | ------------: |
| Search             |     O(log n) |      O(log n) |
| Insert             |         O(n) |      O(log n) |
| Delete             |         O(n) |      O(log n) |
| Maintains ordering |          Yes |           Yes |
| Random access      |    Excellent |            No |
| Memory locality    |    Excellent | Usually worse |

There is a trade-off: arrays have excellent cache locality and simple storage, while trees make dynamic updates much easier.

The section is really connecting **three separate operations**:

```text
                         │
```

The clever part is:

> **Binary Search doesn't just tell us that the target is absent; when the search ends, `low` tells us where the target should be inserted.**

That's why the return value:

is useful.

So the **Binary Search part remains logarithmic**, but maintaining a sorted array under frequent insertions/deletions is **linear-time** because of the element shifting.

## Comparsion
### Binary Search vs Sequential Search

The fundamental difference is how much information each comparison gives us.

**Sequential Search**

```text
Check one element
        ↓
Check next element
        ↓
Check next element
        ↓
...
```

It eliminates approximately **one candidate** per comparison.

Therefore:

```text
O(n)
```

---

**Binary Search**

```text
Check middle
      ↓
Eliminate half
      ↓
Check middle
      ↓
Eliminate half
      ↓
...
```

It eliminates approximately **half the candidates** per comparison.

Therefore:

```text
O(log n)
```

This is the key algorithmic improvement.


Consider one million sorted elements.

**Sequential Search**

In the worst case: `1,000,000` elements may need to be examined.

**Binary Search**

The number of halvings is approximately:

```text
log₂(1,000,000)
≈ 20
```

So the difference is enormous:

```text
Sequential Search:
1,000,000 comparisons

Binary Search:
≈ 20 comparisons
```

This is why binary search is one of the fundamental examples of **divide-and-conquer thinking**.

| Property                          | Sequential Search | Binary Search                              |
| --------------------------------- | ----------------- | ------------------------------------------ |
| Data must be sorted               | No                | **Yes**                                    |
| Search strategy                   | One-by-one        | Divide in half                             |
| Worst-case                        | `O(n)`            | `O(log n)`                                 |
| Best case                         | `O(1)`            | `O(1)`                                     |
| Extra space, iterative            | `O(1)`            | `O(1)`                                     |
| Works naturally with arrays       | Yes               | Yes                                        |
| Works naturally with linked lists | Yes               | Not efficiently                            |
| Supports duplicate-aware variants | Yes               | Yes                                        |
| Requires random access            | No                | Generally yes for efficient implementation |

### Binary Search and Divide and Conquer

Binary search is one of the simplest examples of **divide and conquer**.

The pattern is:

```text
             Problem
                │
        ┌───────┴───────┐
        │               │
    eliminate        eliminate
     half              half
        │
     remaining
     problem
        │
       ...
```

But binary search is slightly unusual compared with algorithms such as merge sort.

**Merge Sort**

Recursively processes **both halves**:

```text
       n
      / \
    n/2 n/2
```

**Binary Search**

Only processes **one half**:

```text
       n
       |
      n/2
       |
      n/4
       |
      n/8
```

That's why binary search is: O(log n)

rather than: O(n log n)


### Binary Search as a Decision Process

Another useful way to view binary search is as a sequence of decisions.

For example:

```text
Target = 70

              50
             /  \
            <    >
                70
               /  \
              ...
```

Every comparison answers a question:

```text
Is target < middle?
Is target = middle?
Is target > middle?
```

Each answer determines which part of the search space remains.

This is why binary search is closely related to **decision trees** and logarithmic search complexity.

---

## When Should You Use Binary Search?

Binary search is appropriate when:

1. The data is sorted or has a monotonic structure.
2. You can efficiently access the middle candidate.
3. You perform enough searches that the sorting cost is worthwhile.
4. You need `O(log n)` search time.

For example:

```text
Sorted array of product IDs
Sorted timestamps
Sorted student IDs
Sorted dictionary words
Sorted database/index structures
```

---

**One Important Practical Consideration**

Suppose you have an unsorted array:

```text
[50, 10, 80, 20, 40, 70]
```

and only need to search it **once**.

Sorting it just to perform binary search may not be worthwhile.

You would have:

```text
Sort:      O(n log n)
Search:    O(log n)
--------------------
Total:     O(n log n)
```

while sequential search takes:

```text
O(n)
```

for a single search.

However, if you need to perform many searches on the same collection, sorting once can make sense:

```text
Sort once:
O(n log n)

Then m searches:
O(m log n)
```

This is a classic algorithm-design trade-off: **Pay a preprocessing cost to make future queries cheaper.**

## Binary Search Summary

The entire algorithm can be reduced to this:

```text
1. Start with the entire sorted collection.

2. Find the middle element.

3. Compare the target with the middle.

4. If equal:
       return the middle position.

5. If target is smaller:
       discard the right half.

6. If target is larger:
       discard the left half.

7. Repeat until the search range is empty.
```

The core implementation is:

```c
int binarySearch(const int A[], int n, int target)
{
    int low = 0;
    int high = n - 1;

    while (low <= high)
    {
        int mid = low + (high - low) / 2;

        if (A[mid] == target)
            return mid;

        if (target < A[mid])
            high = mid - 1;
        else
            low = mid + 1;
    }

    return -1;
}
```

The key properties to remember are:

```text
Requirement:
    sorted data

Strategy:
    repeatedly eliminate half

Best case:
    O(1)

Average case:
    O(log n)

Worst case:
    O(log n)

Iterative space:
    O(1)
```

And the most important conceptual insight is:

> **Binary search is not fundamentally about arrays or middle elements. It is about maintaining a valid search space and using an ordering/monotonic property to eliminate half of that space at every step.**

That insight leads directly to more advanced topics such as **first/last occurrence, lower/upper bounds, range searching, and binary search on a monotonic predicate**.
