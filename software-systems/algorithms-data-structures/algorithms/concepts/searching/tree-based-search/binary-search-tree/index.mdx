BST Search is a searching algorithm that uses a Binary Search Tree as its search structure. It is similar in spirit to binary search, but instead of repeatedly cutting an array in half, it follows links through a tree.

## Introduction

### What is Tree-Based Search?

A **Binary Search Tree** is a binary tree with an ordering rule.

For every node:

```text
values in left subtree < node < values in right subtree
```

For example:

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

At `50`:

```text
left  → values smaller than 50
right → values greater than 50
```

At `30`:

```text
left  → values smaller than 30
right → values greater than 30
```

And so on. This ordering is what makes searching efficient.

**Tree-based search** is a family of searching techniques where the data is organized as a **tree**, and the tree's structure is used to quickly eliminate parts of the search space.

Instead of examining elements one by one:

```text
A → B → C → D → E → ...
```

we organize values hierarchically:

```text
          50
        /    \
      30      70
     /  \    /  \
   20   40  60   80
```

The structure itself tells us where to look.

For example, searching for `60`:

```text
50
 ↓
60
```

We don't need to examine `30`, `20`, `40`, `70`, or `80`.

The key idea is:

> **Use the ordering of the tree to eliminate an entire subtree at every comparison.**

A **Binary Search Tree** is particularly useful because each comparison tells us which subtree can contain the key.

For example:

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

Searching for `60`:

```text
60 > 50
    ↓
go right

60 < 70
    ↓
go left

60 = 60
    ↓
found
```

The critical observation is that we don't inspect every node.

### BST as a Search Structure

The most common type of search tree is the binary search tree (BST), which is
composed of nodes. Each node contains a single value in the
collection and stores references to potentially two child nodes, left and right.

A **Binary Search Tree (BST)** is a binary tree with an ordering rule.

For every node:

```text
all keys in left subtree < node.key
all keys in right subtree > node.key
```

This ordering is what makes searching efficient.

1. Linear Search

    ```text
    array/list
        ↓
    check one item
        ↓
    check next item
        ↓
    check next item
    ```

    Potentially: `O(n)`

2. Binary Search

    ```text
    sorted array
        ↓
    compare middle
        ↓
    discard half
        ↓
    repeat
    ```

    Typically: `O(log n)`

3. Hash-Based Search

    ```text
    key
    ↓
    hash function
    ↓
    bucket
    ↓
    compare
    ```

    Expected: `O(1)`

4. BST Search

    ```text
    key
    ↓
    compare with node
    ↓
    left or right
    ↓
    compare again
    ↓
    repeat
    ```

    Balanced tree:

    ```text
    O(log n)
    ```

This gives us four different ways of reducing the search space.

### BST vs Binary Search

These two are closely related but **not the same thing**.

1. Binary Search

    Binary search operates on a **sorted array/list**.

    ```text
    [10, 20, 30, 40, 50, 60, 70, 80]
                    ↑
                    middle
    ```

    It repeatedly chooses the middle element.

    ```text
    search space
    ────────────────────────
            ↓
        middle
        /      \
    discard    discard
    ```

    The data must generally be stored in a structure that supports efficient indexing.

2. BST Search

    BST search operates on a **tree**.

    ```text
                 50
               /    \
             30      70
            /  \    /  \
           0   40  60   80
    ```

    There is no array index such as `middle`.

    Instead, we follow pointers:

    ```text
    50
    ↓
    70
    ↓
    60
    ```

So:

| Binary Search                    | BST Search                                 |
| -------------------------------- | ------------------------------------------ |
| Sorted array                     | Binary search tree                         |
| Uses indexes                     | Uses pointers/references                   |
| Chooses middle position          | Chooses child                              |
| Divides array search space       | Eliminates a subtree                       |
| Excellent for static sorted data | Good for dynamic ordered data              |
| `O(log n)` on sorted array       | `O(log n)` when tree height is logarithmic |

The algorithms are conceptually related:

> **Both use comparisons to eliminate a large portion of the remaining search space.**

### BST (Binary Search Tree) vs BST search
The key difference is that **BST (Binary Search Tree) is primarily a data structure**, while **BST search is an algorithm performed on that data structure**.

* **BST as a data structure** → how the tree is organized, inserted, deleted, balanced, etc.
* **BST Search** → how we exploit that organization to locate a key.

1. **BST as a data structure**

    A **Binary Search Tree** is a way of **organizing and storing data**.

    For every node:

    ```text
            50
            /  \
        30    70
        / \    / \
        20  40  60  80
    ```

    It maintains the ordering rule:

    ```text
    left subtree  <  node  <  right subtree
    ```

    The BST data structure includes operations such as:

    * `insert`
    * `search`
    * `delete`
    * `findMin`
    * `findMax`
    * traversal

    So when we say:

    > "Use a BST to store these values."

    we are talking about the **data structure**.

2. **BST search as an algorithm**

    Once you have a BST, you need an algorithm to find a value in it.

    For example, search for `60`:

    ```text
            50
            /  \
        30    70
                /
            60
    ```

    The search algorithm does:

    ```text
    60 > 50 → go right
    60 < 70 → go left
    60 = 60 → found
    ```

Think of it like this:

| **BST search**    | Algorithm      | Follows left/right links to find a value     |
| **BST deletion**  | Algorithm      | Removes a node while preserving BST ordering |

So:

```text
             BST
              │
      ┌───────┼────────┐
      ↓       ↓        ↓
```


Here, **BST is not itself the searching algorithm**. The algorithm is the procedure that traverses the BST.

However, BST is also commonly taught under **Data Structures**:

```text
Data Structures
```

So the same concept appears in both areas, but with a different focus:

> **Data Structures:** How do we organize the data?

> **Algorithms:** How do we operate on that organization efficiently?

**One more important distinction: BST vs Binary Search**

Don't confuse these two:

**Binary Search**

```text
Sorted array:
[10, 20, 30, 40, 50, 60, 70]

              ↓
         compare middle
              ↓

```

is a **searching algorithm**.

**Binary Search Tree**

```text
          40

       20    60
```

is a **data structure** that supports a search algorithm.

Both exploit the idea:

```text
smaller → left

```

but they operate on completely different structures.

### The BST Ordering Property

Everything depends on this property.

For every node `N`:

```text
             N
           /   \
          /     \
       smaller  larger
```

More formally:

```text
all keys in left subtree  < N.key

all keys in right subtree > N.key
```

For example:

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

At `50`:

```text
20, 30, 40 < 50

60, 70, 80 > 50
```

At `30`:

```text
20 < 30

40 > 30
```

This ordering is what makes search possible.

### Motivation(Why Use a BST for Searching?)

**Binary Search on an Array Is Efficient**

Binary searching on an array in memory is efficient, as we have already seen. 

Suppose we have a sorted array:

```text
[10, 20, 30, 40, 50, 60, 70, 80]
```

Binary search can find an element in: $O(log n)$

For example, searching for `70`:

```text
[10 20 30 40 50 60 70 80]
             ↑
            40

70 > 40
→ search right half

[50 60 70 80]
       ↑
      60

70 > 60
→ search right

[70 80]
 ↑
70 found
```

Very efficient. So why not always use a sorted array? The problem is **changing the collection**.

---

**The Problem with Ordered Arrays**

However, using ordered arrays becomes drastically less effective when the underlying
collection changes frequently. 

Suppose the array is:

```text
[10, 20, 30, 40, 50]
```

Now we want to insert:

```text
25
```

Because the array must remain sorted:

```text
[10, 20, 25, 30, 40, 50]
```

we have to move elements:

```text
30 → right
40 → right
50 → right
```

Conceptually:

```text
Before:

10  20  30  40  50
        ↓   ↓   ↓

After:

10  20  25  30  40  50
```

So insertion can require: $O(n)$

operations.

Deletion has the same problem.

If we delete `20`:

```text
[10, 20, 30, 40, 50]
     ↓
[10, 30, 40, 50]
```

elements have to be shifted.

Therefore:

> **Sorted arrays provide excellent searching, but insertion and deletion can be expensive.**

---

**Why This Becomes a Problem with Dynamic Collections**

A **static collection** doesn't change very often.

For example:

```text
10 20 30 40 50 60 70
```

We build it once and perform many searches.

A sorted array is excellent here.

But imagine a collection where we constantly perform:

```text
insert
search
delete
insert
insert
search
delete
...
```

This is a **dynamic collection**.

The problem becomes:

```text
Sorted Array

Search       → O(log n)       GOOD
Insert       → O(n)           BAD
Delete       → O(n)           BAD
```

We want a structure that supports **both searching and changing the collection efficiently**.

---

**Hash-Based Search**

With a dynamic collection, we must adopt a different
data structure to maintain acceptable search performance.
 
Hash-Based Search can handle dynamic collections.
 
A hash table solves an important part of the problem.

For example:

```text
Hash Table

insert  → O(1) average
search  → O(1) average
delete  → O(1) average
```

So hash tables are very good for dynamic collections.

Hash-Based Search has two limitations.
1. Problem #1: Choosing Hash Table Size
  we might select a hash table size that is much too small for effective resource usage.
  A hash table normally has a fixed number of bins/buckets at a particular point in time.

  For example:

  ```text
  Hash table:

  [0]
  [1]
  [2]
  [3]
  [4]
  [5]
  [6]
  [7]
  ```

  Suppose you expect:

  ```text
  n = 1000 elements
  ```

  You might choose a sufficiently large table.

  But what if you don't know `n` beforehand?

  You might initially have:

  ```text
  10 elements
  ```

  and later have:

  ```text
  10,000,000 elements
  ```

  Then your original table size may no longer be appropriate.

  You can resize/rehash the table, but that introduces additional work and memory-management considerations.
  
  So,we often have no a priori knowledge(known beforehand) of the number of elements to store, so it is hard to select the proper size of the hash table. If you don't know how large the collection will become, choosing the initial hash table size is harder.
2. Problem #2: Hash Tables Are Not Ordered
  
  Hash tables do not allow you to iterate over their elements in sorted order.

  This is the more important distinction for BSTs.

  Suppose we have these values:

  ```text
  10
  20
  30
  40
  50
  60
  70
  ```

  A hash table might organize them according to their hashes:

  ```text
  bucket 0 → 40
  bucket 1 → 10
  bucket 2 → 70
  bucket 3 → 20
  bucket 4 → 50
  bucket 5 → 30
  bucket 6 → 60
  ```

  The physical organization is based on the hash function, **not the ordering of the keys**.

  Therefore, if you ask:

  > Give me all values from 30 through 60 in sorted order.

  A hash table doesn't naturally provide:

  ```text
  30, 40, 50, 60
  ```

  You would need additional processing.

---

**This Is Where Search Trees Come In**

An alternate strategy is to use a search tree to store dynamic sets. 

A search tree is designed around **ordering**.

For example:

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

Notice what the tree gives us:

```text
             50
           /    \
      smaller   larger
```

This ordering is maintained while the collection changes.

---

**Why a Search Tree Is Useful**

A search tree combines several desirable properties:

```text
Dynamic
   +
Ordered
   +
Efficient Search
```

Conceptually:

```text
                 Search Tree
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
    Search         Insert        Delete
       │             │             │
    efficient      efficient     efficient
```

And because the elements remain ordered, we can perform operations such as:

```text
minimum
maximum
predecessor
successor
range queries
sorted traversal
```
1. Return Ordered Ranges of Elements: make it possible to return
ordered ranges of elements together, something hash tables are unable to accomplish, Suppose the tree contains:

  ```text
                50
              /    \
            30      70
          /  \    /  \
        20   40  60   80
  ```

  Suppose we ask:

  ```text
  Give me all elements between 30 and 70.
  ```

  The answer is:

  ```text
  30, 40, 50, 60, 70
  ```

  Because the BST maintains ordering, we can traverse the relevant part of the tree in sorted order.

  A hash table doesn't naturally maintain this ordering.

  This is a major reason to choose a BST over a hash table when **ordered queries** matter.

2. Search trees perform well both in memory and in secondary storage
  - A BST can be used when the data fits in RAM
  - When the dataset is much larger and stored on disk/SSD, specialized search trees such as B-trees, B+ trees


The most common type of search tree is the binary search tree (BST).

"Binary" means each node can have **at most two children**.


Use a binary search tree when:
- You must traverse the data in ascending (or descending) order
- The data set size is unknown, and the implementation must be able to handle
any possible size that will fit in memory
- The data set is highly dynamic, and there will be many insertions and deletions
during the collection’s lifetime

BSTs are useful when you need:

* searching
* insertion
* deletion
* sorted traversal
* minimum/maximum
* predecessor/successor
* range queries

So the motivation for BST Search can be summarized as:

> **A sorted array gives us efficient search but expensive updates; a hash table gives us efficient dynamic lookup but loses ordering; a search tree attempts to provide efficient dynamic operations while preserving ordering.**

And the BST achieves this by organizing the collection like:

```text
                  50
                /    \
              30      70
             /  \    /  \
           20   40  60   80
```

where every comparison tells us **which subtree to search next**.

That is exactly what turns the BST from merely a tree-shaped data structure into a **search structure**.

## Binary Search Tree Structure

Consider:

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

### Nodes and Edges

A **node** stores a value and links to its children.

Conceptually:

```text
Node
├── key
├── left
└── right
```

For example:

```text
      ┌─────────────┐
      │ key = 50    │
      │ left  ──────┼──→ 30
      │ right ──────┼──→ 70
      └─────────────┘
```

An **edge** is the connection between two nodes.

### Root

The top node is the **root**.

```text
              50  ← root
            /    \
          30      70
```

The root is where BST search normally begins.

### Parent and Child

For:

```text
        50
       /  \
     30    70
```

`50` is the parent of:

```text
30
70
```

`30` and `70` are children of `50`.

### Left and Right Subtrees

Every node can have:

* left subtree
* right subtree

For `50`:

```text
              50
             /  \
      left subtree  right subtree
```

The BST property says:

```text
left subtree  < 50
right subtree > 50
```

### Leaf Nodes

A **leaf** has no children.

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
       ↑    ↑   ↑    ↑
     leaves
```

### Depth

The **depth** of a node is the number of edges from the root to that node.

```text
              50       depth 0
            /    \
          30      70   depth 1
         /  \    /  \
       20   40  60   80 depth 2
```

For example:

```text
depth(50) = 0
depth(30) = 1
depth(60) = 2
```

### Height

The **height of a tree** is the length of the longest path from the root to a leaf.

For:

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

the height is:

```text
2
```

because the longest path contains two edges:

```text
50 → 30 → 20
```

Height is extremely important for BST search because:

> **BST search takes time proportional to the height of the tree.**

### BST Ordering Property

This is the most important property.

For every node `x`:

```text
                    x
                  /   \
                 /     \
        smaller values  larger values
```

For example:

```text
             50
           /    \
         30      70
        /  \    /  \
      20   40  60   80
```

We have:

```text
20 < 30 < 40 < 50 < 60 < 70 < 80
```

This ordering is what makes BST search possible.

## The BST Search Problem
Given:

```text
BST T
search key k
```

we want to determine whether `k` exists in the tree.

There are two possible outcomes.
1. Successful search
2. Unsuccessful search

### Input
The input to BST Search describes what data we are searching in, what value we are looking for, and how the stored values can be compared.

The input and output to algorithms using search trees is the same as for Binary Search because both algorithms solve the same fundamental problem: finding an element by its key. Their underlying data structures are different.

Each element `e` from a collection `C` to be stored in the binary search tree
needs to have one or more properties that can be used as a key `k`. these keys determine the universe `U` and must be fully ordered. More commonly, this is called a total order. For any two keys $k_i$ and $k_j$, we must be able to determine whether:

* $k_i < k_j$
* $k_i = k_j$
* $k_i > k_j$

When the values in the collections are primitive types (such as strings or integers),
the values themselves can be the key values. Otherwise, they are references to the
structures that contain the values.

BST search receives:

1. a BST
2. a search key

For example:

```text
BST:

             50
           /    \
         30      70
        /  \    /  \
      20   40  60   80

key = 60
```
the key used for searching does not always have to be the entire element stored in the tree.

.
#### Collection of Elements
A collection of elements is the set of data stored in the Binary Search Tree (BST).

Suppose we want to store employee records:

| Employee ID | Name  | Salary |
| ----------- | ----- | ------ |
| 105         | Alice | 50,000 |
| 102         | Bob   | 45,000 |
| 108         | Carol | 60,000 |
| 101         | David | 40,000 |
| 104         | Emma  | 48,000 |

Our collection is:
$$
C=\{e1,e2,e3,e4,e5}
$$
Each $ei$ represents one employee record.

We choose the employee ID as the key and build a BST using those IDs:
```
                     105
                    Alice
                  /       \
               102           108
               Bob            Carol
              /   \
         101        104
         David      Emma

```

BST ordered by employee ID. Each node stores an employee record, and its ID determines its position.

The collection contains five employee objects, but the BST organizes them according to their IDs.

Why does this matter? BST Search needs a structured collection in which comparisons can guide the search toward the correct subtree.

#### Search Key
A key is the value used to identify, compare, and locate an element.

Example:

```text
key = 60
```

At every node we compare:

```text
key
  vs
currentNode.key
```

There are only three possibilities:

```text
key == current.key
key <  current.key
key >  current.key
```

Suppose we want to find the employee whose ID is `104`.

Our input is:

```
Collection: employee records stored in a BST
Search key: 104
```

The search begins at the root, whose key is `105`.

```
Search key = 104
Current key = 105

104 < 105 → go left
```

At the next node, the key is `102`.

```
104 > 102 → go right
```

We reach `104` and find the employee.

```
105 → 102 → 104 → FOUND
```

Notice the difference:

* Element: the entire employee record.

* Key: the employee ID used to locate that record.

For primitive values, the element itself can be the key.

For example:

```
Elements: 20, 40, 60, 80
Keys:     20, 40, 60, 80
```

```Java
int value = 60;
```

Here, `60` is both the stored element and the search key.


But consider employee records:

```
Employee
├── id: 102
├── name: "Alice"
└── salary: 50000
```

```Java
class Employee {
    int id;
    String name;
    double salary;
}
```

An employee object contains multiple properties. We can choose `id` as the key and compare employees by their IDs.

```
Element: Employee(102, "Alice", 50000)
Key:     102
```

The BST is ordered by employee ID, not necessarily by name or salary.

For example, to search for employee ID `102`, the BST compares the requested ID with the ID stored in each visited employee node.

```
                Employee(105)
                /           \
       Employee(102)     Employee(110)
```

The search finds `Employee(102)` by comparing IDs, even though the complete objects contain other information.

In Java, the node could store a reference to the employee object:

Java

```
class Node {
    Employee value;
    Node left;
    Node right;

    Node(Employee value) {
        this.value = value;
    }
}
```

The comparison logic would use `value.id`, rather than comparing the employee objects by their memory references.

For an integer BST, the distinction may disappear because the stored integer can also be the search key.

For an object-based BST, the key is often just one property of the object.

the key determines the search order, while the element is the actual data being stored and returned. They can be the same thing, as with integers, or different things, as with employee records.
#### Fully Ordered Keys
A BST can make correct search decisions only when its keys have a consistent ordering.

For any two keys `a` and `b`, we must be able to determine their relationship:
$$
a\<b , a=b , a>b
$$
For example, integer IDs have a natural order:

```
101 < 102 < 104 < 105 < 108
```

That order gives the BST its essential rule:

```
                  105
                 /   \
        IDs < 105     IDs > 105
```

If the search key is `104`, we go left. If it is `108`, we go right.


Strings can also be ordered lexicographically:

```
"Alice" < "Bob" < "Charlie"
```

fully ordered  means that every pair of keys can be compared consistently. In mathematics, this is called a total order.

For example:

| Key type         | Possible ordering                                     |
| ---------------- | ----------------------------------------------------- |
| Integers         | `10 < 20 < 30`                                        |
| Strings          | `"Alice" < "Bob" < "Carol"` using lexicographic order |
| Dates            | Earlier date `<` later date                           |
| Employee objects | Compare their employee IDs                            |

Important: the ordering must be consistent. If comparisons cannot reliably determine the relationship between keys, ordinary BST search cannot safely choose the correct subtree.

Not every property is suitable as a key. For example, if we organize employees by a complex preference relation that cannot compare every pair consistently, ordinary BST search may not work correctly.

Duplicates also require a defined policy. If two employees share an ID, the BST must specify whether duplicate keys are allowed, stored together, or handled another way.

In summary:
```
Collection C
    ↓
Elements e
    ↓
Choose a key k for each element
    ↓
Keys have a consistent total order
    ↓
Compare search key with current node's key
    ↓
Smaller → left | Equal → found | Larger → right
```
### Output

The algorithm can return:

* the node containing the key
* the associated value
* `true/false`
* `null` if the key doesn't exist

For example:

```text
search(60)
```

might return: `Node(60)`

while:

```text
search(55)
```

might return: `null`

### Successful Search

A successful search eventually finds:

```text
key == current.key
```

Example:

```text
search(60)

              50
                \
                 70
                /
               60  ← found
```

### Unsuccessful Search

An unsuccessful search eventually reaches an empty subtree:

```text
null
```

For example, search for `55`:

```text
             50
               \
                70
               /
             60
            /
          null
```

The path is:

```text
50 → 70 → 60 → null
```

Therefore:

```text
55 does not exist
```

## BST Search Algorithm
At every node, perform one comparison.

Suppose:

```text
current.key = 50
search key = 60
```

There are exactly three possibilities:

1. **Case 1 — Equal**

    ```text
    60 == 60
    ```

    Stop.

    ```text
    FOUND
    ```

2. **Case 2 — Smaller**

    ```text
    60 < 70
    ```

    Go left.

3. **Case 3 — Larger**

    ```text 
    60 > 50
    ```

    Go right.

    So the algorithm is:

    ```text
                    current
                        │
            ┌─────────┼─────────┐
            ↓         ↓         ↓
        key <      key ==     key >
            │         │         │
            ↓         ↓         ↓
            left      FOUND      right
    ```
### Basic Idea

Start at the root.

At each node:

```text
Is key equal to current node?
```

If yes:

```text
FOUND
```

If the key is smaller:

```text
go LEFT
```

If the key is larger:

```text
go RIGHT
```

Continue until:

```text
found
```

or:

```text
null
```

1. Compare with Current Node

Suppose:

```text
current = 50
key = 30
```

Compare:

```text
30 < 50
```

Therefore:

```text
go left
```

2. Search Left Subtree

If:

```text
key < current.key
```

then the key **cannot be in the right subtree**.

So:

```text
current = current.left
```

3. Search Right Subtree

If:

```text
key > current.key
```

then the key **cannot be in the left subtree**.

So:

```text
current = current.right
```

4. Found Case

If:

```text
key == current.key
```

stop.

```text
return current
```

5. Not-Found Case

If:

```text
current == null
```

stop.

```text
return null
```

This means the search has reached the position where the key would have had to exist.

### Step-by-Step Example

Consider:

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

Search for:

```text
60
```

#### Step 1

Compare:

```text
60 vs 50
```

Since:

```text
60 > 50
```

go right.

```text
              50
                \
                 70
```

#### Step 2

Compare:

```text
60 vs 70
```

Since:

```text
60 < 70
```

go left.

```text
              70
             /
            60
```

#### Step 3

Compare:

```text
60 vs 60
```

Equal.

```text
FOUND
```

Search path:

```text
50 → 70 → 60
```

Only **3 nodes** were examined.

---

**Why Can We Ignore the Other Nodes?**

This is the most important conceptual part.

After:

```text
60 > 50
```

we know that everything in the left subtree is smaller than `50`.

```text
              50
             /  \
            /    \
          30      70
         / \
       20  40
```

Because:

```text
20 < 50
30 < 50
40 < 50
```

none of these can be `60`.

So we eliminate:

```text
       30
      /  \
    20    40
```

with **one comparison**.

This is exactly the same fundamental idea behind Binary Search:

> **Use ordering information to eliminate a portion of the search space.**

## BST Search Pseudocode

### Recursive Search
The recursive version naturally follows the tree structure:

```text
function BST_Search(node, key):

    if node == NULL:
        return NULL

    if key == node.key:
        return node

    if key < node.key:
        return BST_Search(node.left, key)

    return BST_Search(node.right, key)
```

The recursive calls represent:

```text
search left subtree
```

or:

```text
search right subtree
```

For:

```text
search(60)
```

the calls conceptually become:

```text
BST_Search(50, 60)
        ↓
BST_Search(70, 60)
        ↓
BST_Search(60, 60)
        ↓
FOUND
```

### Iterative Search

The iterative version is often easier to understand operationally:

```text
function BST_Search(root, key):

    current ← root

    while current != NULL:

        if key == current.key:
            return current

        if key < current.key:
            current ← current.left
        else:
            current ← current.right

    return NULL
```

The important variable is: `current`

It moves down exactly one level at each iteration.

The iterative version is often preferable for a simple search because it doesn't require recursive call-stack space.

## Why BST Search Works

### Ordering Property

Suppose we're at:

```text
        50
       /  \
     ...  ...
```

and searching for:

```text
30
```

Because:

```text
30 < 50
```

we know:

```text
30 cannot be anywhere in the right subtree.
```

Therefore we can completely ignore it.

### Eliminating Subtrees

This is the core idea.

Suppose:

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

Search:

```text
20
```

At `50`:

```text
20 < 50
```

Therefore we eliminate:

```text
       70
      /  \
    60    80
```

We don't inspect those nodes.

Then:

```text
50
 ↓
30
 ↓
20
```

The search space gets smaller as we descend.

### Search Path

A BST search examines only **one root-to-node path**.

For `60`:

```text
              50
                \
                 70
                /
              60
```

Only these nodes are examined:

```text
50
70
60
```

The nodes:

```text
20
30
40
80
```

are never examined.

### Comparison with Binary Search

Binary search:

```text
array
─────────────────────────────
        middle
       /      \
    discard  discard
```

BST search:

```text
              node
             /    \
          discard  discard
```

Conceptually they do the same thing:

> **Make a comparison and discard a portion of the search space.**

The difference is how the search space is represented.

## Search Complexity

### Search Path

This is where **tree height** becomes important.

BST search follows one path:

```text
root → child → child → ... → target
```

Therefore its running time is proportional to the number of levels visited.

That is related to tree height `h`.

If:

```text
h = height of the BST
```
then BST search takes:
```text
T(n) = O(h)
```
because we follow at most one path from the root to a leaf/null position.

### Tree Height

If the tree is balanced:

```text
              50
           /      \
         30        70
        /  \      /  \
      20   40   60   80
```

Height is approximately:

```text
log₂(n)
```

Therefore:

```text
BST Search = O(log n)
```

### Best Case

The best case occurs when the root contains the key.

```text
             50
            /  \
          ...
```

Search:

```text
50
```

One comparison:

```text
O(1)
```

### Average Case

For a reasonably balanced BST: $O(log n)$

The exact average depends on:

* tree shape
* insertion order
* distribution of searches

An ordinary unbalanced BST does **not automatically guarantee** `O(log n)`.

### Worst Case

If the tree becomes skewed:

Consider:

```text
10
  \
   20
     \
      30
        \
         40
           \
            50
```

This is essentially a linked list.

Searching for `50` requires:

```text
10 → 20 → 30 → 40 → 50
```

Therefore: $O(n)$

The BST has effectively become a linked list.

### Balanced BST

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

A balanced tree has height approximately:

```text
log₂(n)
```

Therefore:

```text
Search = O(log n)
```

Examples include:

* AVL trees
* Red-Black trees

These are BST-based structures that maintain balance.

### Degenerate BST

A degenerate BST looks like:

```text
10
  \
   20
     \
      30
        \
         40
           \
            50
```

Its height is:

```text
n - 1
```

Therefore:

```text
Search = O(n)
```

### Complexity Summary

| Case              |                                     Complexity |
| ----------------- | ---------------------------------------------: |
| Best              |                                           O(1) |
| Balanced          |                                       O(log n) |
| Average           | O(h) / commonly O(log n) for well-shaped trees |
| Worst             |                                           O(n) |
| Space — iterative |                                           O(1) |
| Space — recursive |                                           O(h) |

The crucial formula is:

```text
BST Search = O(h)
```

Everything else follows from the height.

## Balanced vs Unbalanced BST

### Balanced Tree

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

Height: $O(log n)$

Search: $O(log n)$

### Skewed Tree

```text
50
  \
   70
     \
      80
        \
         90
```

The tree is heavily skewed.

Search can become: $O(n)$

### Degenerate Tree

The extreme case is effectively a linked list:

```text
10
  \
   20
     \
      30
        \
         40
```

There is almost no benefit from the tree structure.

### Effect on Search Performance

This is the critical relationship:

```text
tree height
     ↓
search path length
     ↓
number of comparisons
     ↓
search performance
```

Therefore:

```text
small height → fast search
large height → slow search
```

## Successful vs Unsuccessful Search

There is another useful distinction.

Suppose:

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

Search for `60`:

```text
50 → 70 → 60 → FOUND
```

Search for `65`:

```text
50 → 70 → 60 → right → NULL
```

Notice that an unsuccessful search still follows a valid BST path. It doesn't randomly stop. The ordering property tells us exactly where `65` **would have been** if it existed. That idea becomes important for insertion as well.

### Successful Search Path

For:

```text
search(60)
```

we have:

```text
50 → 70 → 60
```

The search stops at an actual node.

### Failed Search Path

For:

```text
search(65)
```

we have:

```text
50 → 70 → 60 → NULL
```

The search stops at an empty child link.

### External/Null Position

Think of `NULL` as representing a missing child:

```text
              60
             /  \
           ...  NULL
```

If we're searching for `65`:

```text
65 > 60
```

so we move right:

```text
60 → NULL
```

That tells us: There is no node where `65` could exist.

### Number of Comparisons

For successful search:

```text
number of comparisons ≈ depth of target + 1
```

For unsuccessful search:

```text
number of comparisons ≈ depth of the null position
```

The exact counting convention can differ depending on whether you count key comparisons only or loop iterations as well, but the important relationship is:

> **The number of comparisons is proportional to the search path length.**

## BST Search and Ordering

BST ordering gives us more than ordinary membership search.

### Minimum

The minimum value is the **leftmost node**.

```text
              50
             /
           30
          /
        20
       /
     10
```

Keep going left:
```text
minimum = leftmost node
```

```text
50 → 30 → 20 → 10
```

Therefore:

```text
minimum = 10
```

**Algorithm**:

```text
while node.left != null:
    node = node.left

return node
```

**Complexity**:

```text
O(h)
```

or: $O(log n)$

in a balanced tree.

### Maximum

The maximum is the **rightmost node**.
```text
              50
             /  \
           30    70
                   \
                    80
                      \
                       90
```

```text
maximum = rightmost node
```
Therefore:

```text
50 → 70 → 80 → 90
```

Therefore:

```text
maximum = 90
```

Again: $O(h)$

### Predecessor

The **predecessor** of a key is the largest key smaller than it.

For:

```text
             50
           /    \
         30      70
        /  \    /  \
      20   40  60   80
```

The predecessor of `50` is:`40`

because:

```text
40 < 50
```

and there is no larger value below `50`.

### Successor

The **successor** is the smallest key greater than the given key.

For `50`:

```text
successor(50) = 60
```

because:

```text
60 > 50
```

and it is the smallest such value.

### Range Search

This is one of the major advantages of an ordered tree.

Suppose we want:

```text
all values between 30 and 70
```

The BST structure allows us to avoid visiting irrelevant branches.

For example:

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

The values in the range are:

```text
30, 40, 50, 60, 70
```
This is called a **range query**.

A BST can perform such ordered/range operations efficiently, especially when the tree is balanced. A hash table isn't naturally suited to this kind of ordered query.


## Search and the Shape of the Tree

The same set of values can produce dramatically different search performance.

#### Good shape

```text
             50
           /    \
         30      70
        / \      / \
      20  40   60  80
```

Height: $O(log n)$

#### Bad shape

Insert:

```text
10, 20, 30, 40, 50
```

and you can get:

```text
10
  \
   20
     \
      30
        \
         40
           \
            50
```

Height: $O(n)$

This leads to one of the major lessons of BSTs:

> **A BST's search performance depends on its height, and its height depends on how the tree is shaped.**

## Search with Duplicate Keys

A standard BST definition often assumes:

```text
left < node < right
```

But real data can contain duplicates.

For example:

```text
50
30
50
70
```

Where should the second `50` go?

There is no single universal answer.

### Duplicate-Key Problem

Suppose:

```text
        50
       /
     30
       \
        50
```

or:

```text
        50
       /  \
     30    50
```

Both are possible depending on the implementation policy.

### Duplicate Policies

There are several policies:

```text
duplicates
    │
    ├── always put duplicates left
    │
    ├── always put duplicates right
    │
    ├── store a count in the node
    │
    └── store multiple values in the node
```
For pure searching, the important point is that the duplicate policy must be consistent.

Otherwise the ordering rule becomes ambiguous.

#### Policy 1 — Duplicates go left

```text
left ≤ node
right > node
```

#### Policy 2 — Duplicates go right

```text
left < node
right ≥ node
```

#### Policy 3 — Store a count

Instead of creating multiple nodes:

```text
Node
├── key = 50
└── count = 3
```

#### Policy 4 — Store a collection

```text
Node
├── key = 50
└── values = [...]
```

### Effect on Search

With duplicates, `search(50)` might return:

* any node containing `50`
* the first encountered `50`
* the leftmost `50`
* the rightmost `50`
* all matching values

The exact behavior depends on the BST implementation.


## The Relationship with BST Insertion

Although we're focusing on **search**, insertion helps explain why the structure works.

Suppose we insert:

```text
65
```

into:

```text
              50
                \
                 70
                /
               60
```

We perform exactly the same navigation:

```text
65 > 50 → right
65 < 70 → left
65 > 60 → right
```

We reach an empty position:

```text
              50
                \
                 70
                /
               60
                 \
                  65
```

Notice:

> **BST insertion uses the same search path as BST search.**

Search asks:

```text
"Does the key exist?"
```

Insertion asks:

```text
"Where should this key go?"
```

This is why the search algorithm is fundamental to understanding the other BST operations.

## BST Search vs Other Search Algorithms
Use a binary search tree when:
- You must traverse the data in ascending (or descending) order
- The data set size is unknown, and the implementation must be able to handle
any possible size that will fit in memory
- The data set is highly dynamic, and there will be many insertions and deletions
during the collection’s lifetime

| Algorithm     | Structure    |      Typical Search | Ordered? | Dynamic?       |
| ------------- | ------------ | ------------------: | -------- | -------------- |
| Linear Search | Array/list   |              `O(n)` | No       | Yes            |
| Binary Search | Sorted array |          `O(log n)` | Yes      | Poor insertion |
| Hash Search   | Hash table   |      `O(1)` average | No       | Yes            |
| BST Search    | BST          | `O(log n)` balanced | Yes      | Yes            |
| Balanced BST  | AVL/RB tree  |          `O(log n)` | Yes      | Yes            |

### Linear Search

```text
10 → 20 → 30 → 40 → 50
```

May need to inspect everything: $O(n)$

### Binary Search

Requires sorted data:

```text
[10 20 30 40 50 60 70]
          ↑
        middle
```

Search: $O(log n)$

but inserting into the middle of an array can be expensive.

### Hash-Based Search

```text
key
 ↓
hash(key)
 ↓
bucket
 ↓
collision handling
 ↓
found/not found
```

A hash table typically provides: $O(1)$ average search. But it doesn't naturally maintain sorted order. For example, a hash table doesn't naturally answer:

```text
give me all keys between 30 and 70
```

as efficiently as an ordered tree can.

### Tree-Based Search
```text
key
 ↓
compare
 ↓
left/right
 ↓
compare
 ↓
left/right
```

BST provides a combination:

```text
fast search
+
ordered data
+
dynamic insertion/deletion
```

This is its main appeal.

Balanced: $O(log n)$

But it maintains an ordering that gives us additional capabilities.

For example:

```text
find smallest
find largest
find predecessor
find successor
range queries
ordered traversal
```

## BST Search Space and Trade-offs

### Time

Balanced BST:

```text
Search = O(log n)
```

Unbalanced BST:

```text
Search = O(n)
```

### Memory

A BST needs nodes and links.

Conceptually:

```text
Node
├── key
├── left pointer
└── right pointer
```

So compared with an array, there is additional memory overhead for pointers/references.

### Ordering

This is one of the BST's biggest strengths.

The tree maintains:

```text
smaller ← node → larger
```

Therefore operations such as:

```text
min
max
predecessor
successor
range queries
sorted traversal
```

are naturally supported.

### Dynamic Data

BSTs are particularly useful when the dataset changes:

```text
insert
delete
search
```

all work within the same structure.

With a balanced BST, these can generally be maintained at: $O(log n)$

### Static Data

For static data, a sorted array plus binary search can often be simpler and more memory-efficient.

For example:

```text
[10, 20, 30, 40, 50, 60, 70]
```

Binary search provides: $O(log n)$

without pointer overhead.

Therefore, BSTs are especially attractive when **the data is dynamic and ordered operations matter**.

## Practical Applications

### Ordered Sets

A BST can implement a set where:

```text
insert(x)
contains(x)
remove(x)
```

are supported while maintaining ordering.

For example:

```text
Set = {20, 30, 40, 50, 60, 70}
```

### Ordered Maps

Instead of storing only keys: `key`

a node can store:

```text
key → value
```

For example:

```text
101 → "Alice"
205 → "Bob"
310 → "Charlie"
```

The BST can be ordered by the key.

### Range Queries

Suppose we have:

```text
employee ID
salary
```

and need:

```text
all employees with salary between
50000 and 70000
```

An ordered tree can exploit the ordering to avoid examining irrelevant values.

### Dynamic Ordered Data

BSTs are particularly useful when:

```text
data arrives
   ↓
insert
   ↓
search
   ↓
delete
   ↓
insert
   ↓
search
```

and we need to preserve ordering throughout the process.

## Summary
The entire algorithm can be reduced to:

```text
                    Start
                      │
                      ↓
                  current
                      │
                 ┌────┴────┐
                 │         │
               null       not null
                 │         │
              NOT FOUND    ↓
                       compare key
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
           key < node    key == node   key > node
              │             │             │
              ↓             ↓             ↓
        current=left      FOUND      current=right
              │                           │
              └────────────┬──────────────┘
                           ↓
                       repeat
```

That's **BST Search**.

### Core Algorithm

BST search is essentially:

```text
current = root

while current != null:

    if key == current.key:
        return current

    if key < current.key:
        current = current.left
    else:
        current = current.right

return null
```

The entire algorithm revolves around one rule:

```text
key < node.key → LEFT
key > node.key → RIGHT
key = node.key → FOUND
```

### Complexity

The most important formula is:

```text
BST Search = O(h)
```

where `h` is the tree height.

Therefore:

```text
balanced BST:
h = O(log n)
       ↓
search = O(log n)
```

but:

```text
degenerate BST:
h = O(n)
       ↓
search = O(n)
```

Best case: $O(1)$

when the root contains the key.

### Strengths

BST search provides:

* efficient searching when the tree is balanced
* ordered data
* dynamic insertion
* dynamic deletion
* minimum/maximum
* predecessor/successor
* range queries
* sorted traversal

### Weaknesses

A basic BST does **not guarantee** `O(log n)`.

Bad insertion order can produce:

```text
10
  \
   20
     \
      30
        \
         40
```

which turns the tree into essentially a linked list.

Therefore, if guaranteed logarithmic performance is required, we use a **self-balancing BST**, such as an AVL tree or Red-Black tree.

### Mental Model

The best way to remember BST Search is:

```text
                  BST
                   │
                  root
                   │
             compare key
              /          \
        key smaller     key larger
             │              │
           LEFT            RIGHT
             │              │
             └──────┬───────┘
                    ↓
               compare again
                    │
             ┌──────┴──────┐
             ↓             ↓
           FOUND          NULL
                           ↓
                       NOT FOUND
```

Or, even more simply:

> **BST Search is binary search performed through tree links instead of array indexes.**

The critical relationship to remember is:

```text
BST ordering
     ↓
eliminate one subtree
     ↓
follow one path
     ↓
path length = tree height
     ↓
Search = O(h)
     ↓
balanced → O(log n)
skewed   → O(n)
```

That is the core of **Binary Search Tree Search as a searching algorithm**, separate from BST as a general data structure.
