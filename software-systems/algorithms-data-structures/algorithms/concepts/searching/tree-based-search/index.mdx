
**Tree-Based Search** is a family of searching techniques where data is organized in a **tree structure**, and the search algorithm uses the tree's structure to avoid examining every element.

The main idea is:

> **Instead of searching through items one by one, organize them into a tree so that each comparison lets us eliminate part of the search space.**

Tree-Based Search is not one algorithm, **Tree-Based Search is a category of searching techniques**, not one specific algorithm.

For example:

```text
Tree-Based Search
│
├── Binary Search Tree (BST)
│   └── BST Search
│
├── Balanced BST
│   ├── AVL Tree
│   └── Red-Black Tree
│
├── B-Tree
│
├── B+ Tree
│
└── Trie
```
Different trees use different search strategies.

## Why do we need Tree-Based Search?

Suppose we have:

```text
10  20  30  40  50  60  70  80  90
```

With **linear search**, looking for `80` might require:

```text
10 → 20 → 30 → 40 → 50 → 60 → 70 → 80
```

That's potentially **O(n)** work.

With a suitable tree:

```text
             50
            /  \
          30    70
         / \    / \
       20  40  60  80
```

Searching for `80`:

```text
80 > 50 → go right
80 > 70 → go right
80 = 80 → found
```

Only three comparisons.

This is the fundamental advantage of tree-based searching.

---

**Binary Search on an Array Is Efficient**

Binary searching on an array in memory is efficient, as we have already seen. 

Suppose we have a sorted array:

```text
[10, 20, 30, 40, 50, 60, 70, 80]
```

Binary search can find an element in: $O(log n)$

For example, searching for `70`:

```text
[10 20 30 40 50 60 70 80]
             ↑
            40

70 > 40
→ search right half

[50 60 70 80]
       ↑
      60

70 > 60
→ search right

[70 80]
 ↑
70 found
```

Very efficient. So why not always use a sorted array? The problem is **changing the collection**.

---

**The Problem with Ordered Arrays**

However, using ordered arrays becomes drastically less effective when the underlying
collection changes frequently. 

Suppose the array is:

```text
[10, 20, 30, 40, 50]
```

Now we want to insert:

```text
25
```

Because the array must remain sorted:

```text
[10, 20, 25, 30, 40, 50]
```

we have to move elements:

```text
30 → right
40 → right
50 → right
```

Conceptually:

```text
Before:

10  20  30  40  50
        ↓   ↓   ↓

After:

10  20  25  30  40  50
```

So insertion can require: $O(n)$

operations.

Deletion has the same problem.

If we delete `20`:

```text
[10, 20, 30, 40, 50]
     ↓
[10, 30, 40, 50]
```

elements have to be shifted.

Therefore:

> **Sorted arrays provide excellent searching, but insertion and deletion can be expensive.**

---

**Why This Becomes a Problem with Dynamic Collections**

A **static collection** doesn't change very often.

For example:

```text
10 20 30 40 50 60 70
```

We build it once and perform many searches.

A sorted array is excellent here.

But imagine a collection where we constantly perform:

```text
insert
search
delete
insert
insert
search
delete
...
```

This is a **dynamic collection**.

The problem becomes:

```text
Sorted Array

Search       → O(log n)       GOOD
Insert       → O(n)           BAD
Delete       → O(n)           BAD
```

We want a structure that supports **both searching and changing the collection efficiently**.

---

**Hash-Based Search**

With a dynamic collection, we must adopt a different
data structure to maintain acceptable search performance.
 
Hash-Based Search can handle dynamic collections.
 
A hash table solves an important part of the problem.

For example:

```text
Hash Table

insert  → O(1) average
search  → O(1) average
delete  → O(1) average
```

So hash tables are very good for dynamic collections.

Hash-Based Search has two limitations.
1. Problem #1: Choosing Hash Table Size
  we might select a hash table size that is much too small for effective resource usage.
  A hash table normally has a fixed number of bins/buckets at a particular point in time.

  For example:

  ```text
  Hash table:

  [0]
  [1]
  [2]
  [3]
  [4]
  [5]
  [6]
  [7]
  ```

  Suppose you expect:

  ```text
  n = 1000 elements
  ```

  You might choose a sufficiently large table.

  But what if you don't know `n` beforehand?

  You might initially have:

  ```text
  10 elements
  ```

  and later have:

  ```text
  10,000,000 elements
  ```

  Then your original table size may no longer be appropriate.

  You can resize/rehash the table, but that introduces additional work and memory-management considerations.
  
  So,we often have no a priori knowledge(known beforehand) of the number of elements to store, so it is hard to select the proper size of the hash table. If you don't know how large the collection will become, choosing the initial hash table size is harder.
2. Problem #2: Hash Tables Are Not Ordered
  
  Hash tables do not allow you to iterate over their elements in sorted order.

  This is the more important distinction for BSTs.

  Suppose we have these values:

  ```text
  10
  20
  30
  40
  50
  60
  70
  ```

  A hash table might organize them according to their hashes:

  ```text
  bucket 0 → 40
  bucket 1 → 10
  bucket 2 → 70
  bucket 3 → 20
  bucket 4 → 50
  bucket 5 → 30
  bucket 6 → 60
  ```

  The physical organization is based on the hash function, **not the ordering of the keys**.

  Therefore, if you ask:

  > Give me all values from 30 through 60 in sorted order.

  A hash table doesn't naturally provide:

  ```text
  30, 40, 50, 60
  ```

  You would need additional processing.

---

**This Is Where Search Trees Come In**

An alternate strategy is to use a search tree to store dynamic sets. 

A search tree is designed around **ordering**.

For example:

```text
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

Notice what the tree gives us:

```text
             50
           /    \
      smaller   larger
```

This ordering is maintained while the collection changes.

---

**Why a Search Tree Is Useful**

A search tree combines several desirable properties:

```text
Dynamic
   +
Ordered
   +
Efficient Search
```

Conceptually:

```text
                 Search Tree
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
    Search         Insert        Delete
       │             │             │
    efficient      efficient     efficient
```

And because the elements remain ordered, we can perform operations such as:

```text
minimum
maximum
predecessor
successor
range queries
sorted traversal
```
1. Return Ordered Ranges of Elements: make it possible to return
ordered ranges of elements together, something hash tables are unable to accomplish, Suppose the tree contains:

  ```text
                50
              /    \
            30      70
          /  \    /  \
        20   40  60   80
  ```

  Suppose we ask:

  ```text
  Give me all elements between 30 and 70.
  ```

  The answer is:

  ```text
  30, 40, 50, 60, 70
  ```

  Because the BST maintains ordering, we can traverse the relevant part of the tree in sorted order.

  A hash table doesn't naturally maintain this ordering.

  This is a major reason to choose a BST over a hash table when **ordered queries** matter.

2. Search trees perform well both in memory and in secondary storage
  - A BST can be used when the data fits in RAM
  - When the dataset is much larger and stored on disk/SSD, specialized search trees such as B-trees, B+ trees

## What is a tree?

A tree is a hierarchical data structure consisting of **nodes** connected by **edges**.

For example:

```text
             A
           /   \
          B     C
         / \     \
        D   E     F
```

Important terminology:

```text
A → root
B, C → children of A
D, E → children of B
F → child of C
```

A node can have zero or more children, depending on the type of tree.

For searching, we are particularly interested in trees where the structure provides some **ordering or indexing information**.

## BST Search
**How BST Search works**

The key idea: eliminate an entire subtree

This is what makes tree-based searching interesting.

Suppose we want to find:

```text
60
```

in:

```text
              50
             /  \
           30    70
          / \    / \
        20  40  60  80
```

Start at the root:

```text
60 vs 50
```

Since:

```text
60 > 50
```

we know that `60` cannot be in the left subtree.

So we go right:

```text
              50
                \
                 70
                /
               60
```

Now:

```text
60 vs 70
```

Since:

```text
60 < 70
```

go left:

```text
             70
            /
           60
```

Now:

```text
60 == 60
```

Found.

So the search path was:

```text
50 → 70 → 60
```

When we compare:

```text
search key = 60
current node = 50
```

we discover:

```text
60 > 50
```

Therefore, we don't need to examine:

```text
        30
       /  \
     20    40
```

The entire subtree is eliminated.

That's similar to what happens in **Binary Search**.

Binary Search:

```text
[10 20 30 40 50 60 70 80]

             ↓
        examine middle
             ↓
       discard half
```

BST Search:

```text
             50
            /  \
           /    \
     discard    continue
      subtree
```

Both use comparisons to eliminate unnecessary work.

**Time complexity**

Let:

```text
h = height of the tree
```
Therefore:

```text
Time = O(h)
```

## Balanced tree

```text
             50
           /    \
         30      70
        / \      / \
      20  40   60  80
```

The height is approximately:

```text
log₂(n)
```

Therefore:

```text
Search = O(log n)
```
## Completely unbalanced tree

Suppose values are inserted in sorted order:

```text
10
  \
   20
     \
      30
        \
         40
           \
            50
```

This looks almost like a linked list.

Searching for `50` requires:

```text
10 → 20 → 30 → 40 → 50
```

Therefore:

```text
Search = O(n)
```

## Balanced BSTs

A normal BST does **not guarantee** `O(log n)` search.

Balanced trees solve this problem.

Examples include:

```text
Balanced Search Trees
│
├── AVL Tree
│
└── Red-Black Tree
```

They maintain the tree's height close to: $O(log n)$

so operations such as:

```text
search
insert
delete
```

can remain: $O(log n)$

in the worst case.

## Tree-Based Search vs Binary Search

These concepts are related but different.

### Binary Search

Data structure:

```text
sorted array
```

Example:

```text
[10, 20, 30, 40, 50, 60, 70]
```

Algorithm:

```text
Binary Search
```

Typical complexity: $O(log n)$

---

### BST Search

Data structure:

```text
Binary Search Tree
```

Example:

```text
       40
      /  \
    20    60
   / \    / \
 10  30  50  70
```

Algorithm:

```text
BST Search
```

Complexity:

```text
O(h)
```

or, for a balanced BST: $O(log n)$

## Tree-Based Search vs Hash-Based Search

This distinction is also useful for your current algorithms study.

|                           | Tree-Based Search     | Hash-Based Search       |
| ------------------------- | --------------------- | ----------------------- |
| Main structure            | Tree                  | Hash table              |
| Ordering                  | Usually ordered       | Usually not ordered     |
| Typical search            | O(log n) balanced BST | O(1) average            |
| Worst case                | O(n) for ordinary BST | O(n)                    |
| Supports sorted traversal | Yes                   | Generally no            |
| Range queries             | Good                  | Generally poor          |
| Find min/max              | Efficient in BST      | Not naturally efficient |
| Exact lookup              | Good                  | Excellent               |

For example:

### Hash table

```text
"alice" → hash → bucket 17
```

You directly calculate where to look.

### BST

```text
             50
            /  \
          30    70
                /
               60
```

You **navigate** through comparisons.

## Summary

BST is not always better than binary search or hash tables, Instead, each structure is good for a different situation.

### Sorted array

Best when:

```text
data changes rarely
+
fast search is needed
```

```text
Search → O(log n)
```

### Hash table

Best when:

```text
data changes frequently
+
fast exact-key lookup is needed
+
ordering isn't important
```

```text
Search → O(1) average
```

### BST / Search tree

Best when:

```text
data changes frequently
+
fast search is needed
+
ordering matters
```

```text
Search → O(log n) if balanced
```
