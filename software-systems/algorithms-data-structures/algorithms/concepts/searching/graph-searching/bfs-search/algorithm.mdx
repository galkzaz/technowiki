{/* # Breadth-First Search — Algorithm */}


In the overview, we learned that BFS explores a graph level by level. Now let's examine how the algorithm achieves that behavior, trace its execution, and understand the decisions made at each step.

The focus here is the algorithm itself—not how to implement a queue or build a graph data structure.

## 1. Algorithm inputs and outputs
Before writing an algorithm, define what it receives and what it produces.

BFS takes a graph $G=(V,E)$ and a starting vertex $s$, called the source.

- Input: a graph and a valid source vertex.
- Output: the vertices reachable from the source, in BFS traversal order.
- Optional additional outputs: a parent array and a distance array, which can be used to reconstruct shortest paths.

For example, if the source is `A`, BFS explores only the vertices reachable from `A`. It does not automatically visit disconnected components elsewhere in the graph.


### Inputs

BFS normally receives:

- Graph $G=(V,E)$: a set of vertices $V$ and edges $E$.
- Source vertex $s$: the vertex from which the search begins.

For example:

```
        A
       / \
      B   C
     /     \
    D       E
```

If `A` is the source, BFS explores the vertices reachable from `A`.

### Outputs

The basic BFS algorithm produces a traversal order: the sequence in which vertices are processed.

```
A, B, C, D, E
```

Breadth-First Search produces two computed arrays. `dist[v]`(or `distance[v]`) records the number
of edges in a shortest path from `s` to `v`. `pred[v]`(or `parent[v]`) records the predecessor vertex of `v`
based on the breadth-first search ordering. The `pred[]` values record the breadth-first tree search result; if the original graph is unconnected, then all vertices `w`
unreachable from `s` have a `pred[w]` value of `–1`.

:::note

Some  implementations use different variable naming conventions:
| BFS code | Common alternative name      | Meaning                                                                                     |
| ------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------- |
| `dist[v]`                | `distance[v]`                | Shortest distance (number of edges) from the source to vertex `v`.                          |
| `pred[v]`                | `parent[v]`                  | The predecessor or parent of vertex `v` in the BFS tree.                                    |
| `color[v]`               | `visited[v]` (approximately) | Tracks the traversal state, although a Boolean `visited` cannot represent all three colors. |

Suppose BFS starts at `A`:

```
        A
       / \
      B   C
     /
    D
```

The resulting arrays could be:

| Vertex | `distance[]` | `parent[]` |
| ------ | ------------ | ---------- |
| A      | 0            | -1         |
| B      | 1            | A          |
| C      | 1            | A          |
| D      | 2            | B          |

For example:

```
distance[D] = distance[B] + 1;  // 2
parent[D] = B;
```

- `distance[]` tells us how far a vertex is from the source.
- `parent[]` allows us to reconstruct the path from the source to a destination.

`distance[]` and `parent[]` are widely used and make the purpose of each array more immediately understandable.

:::

BFS can also maintain additional information:

| Output          | Meaning                                        | Example             |
| --------------- | ---------------------------------------------- | ------------------- |
| Traversal order | Order in which vertices are processed          | `A, B, C, D, E`     |
| `visited[v]`    | Whether vertex `v` has been discovered         | `visited[D] = true` |
| `distance[v]`   | Minimum number of edges from the source to `v` | `distance[D] = 2`   |
| `parent[v]`     | Previous vertex on the BFS discovery path      | `parent[D] = B`     |

The traversal order is the basic output. The distance and parent arrays are optional extensions that allow BFS to solve shortest-path problems.

For vertices unreachable from the source, their distance can be represented by infinity (or a sentinel such as `-1` in code), and their parent remains unset.

## 2. The BFS algorithm

The BFS algorithm maintains four important pieces of information:

| Data         | Purpose                                              |
| ------------ | ---------------------------------------------------- |
| `queue`      | Holds discovered vertices waiting to be processed.   |
| `visited[]`  | Prevents a vertex from being discovered repeatedly.  |
| `parent[]`   | Records which vertex first discovered each vertex.   |
| `distance[]` | Records the minimum number of edges from the source. |

The `parent[]` and `distance[]` arrays are optional if we only want to traverse the graph. They are useful when we want shortest paths or distances.

## BFS pseudocode
### pseudocode 1
Here is the standard BFS pseudocode:

```
BFS(G, source):

    create an empty queue Q
    create visited[v] = false for every vertex v

    visited[source] = true
    ENQUEUE(Q, source)

    while Q is not empty:

        u = DEQUEUE(Q)
        PROCESS(u)

        for each vertex v adjacent to u:

            if visited[v] == false:

                visited[v] = true
                ENQUEUE(Q, v)
```

The pseudocode is short, but every step serves a purpose.

#### Step 1: Initialize the search

```
create an empty queue Q
create visited[v] = false for every vertex v

visited[source] = true
ENQUEUE(Q, source)
```

Initially, no vertices have been discovered. We then mark the source as discovered and add it to the queue.

Why mark the source immediately? Because it is already scheduled for exploration. Marking it prevents a neighbor from adding it again.

#### Step 2: Select the next vertex

```
while Q is not empty:

    u = DEQUEUE(Q)
```

The queue uses FIFO (First In, First Out): the vertex added earliest is removed first.

This is what allows BFS to process vertices in distance order. Vertices discovered at a smaller distance enter the queue before vertices discovered at a larger distance.

#### Step 3: Process the current vertex

```
PROCESS(u)
```

Processing depends on the problem. It might mean:

- Printing the vertex.
- Checking whether it is the target.
- Recording its information.
- Performing some application-specific operation.

The traversal algorithm itself does not dictate what processing means.

#### Step 4: Examine adjacent vertices

```
for each vertex v adjacent to u:

    if visited[v] == false:

        visited[v] = true
        ENQUEUE(Q, v)
```

For each neighbor, BFS checks whether it has already been discovered.

If not, BFS marks it visited and enqueues it.

The order matters: mark a vertex when it is discovered and enqueued, not when it is dequeued. Otherwise, multiple neighbors might enqueue the same vertex before it is processed.

### pseudocode 2

```
BFS(graph, source):

    create an empty queue
    mark all vertices as not visited
    initialize all parents to NONE
    initialize all distances to INFINITY

    visited[source] = true
    distance[source] = 0
    enqueue(source)

    while queue is not empty:

        u = dequeue()

        process(u)

        for each neighbor v of u:

            if not visited[v]:

                visited[v] = true
                parent[v] = u
                distance[v] = distance[u] + 1

                enqueue(v)
```

Let's examine the algorithm carefully.

#### Step 1: Initialize the search

Initially, no vertex has been discovered.

```
visited = { }
parent  = { }
queue   = [ ]
```

We then discover the source vertex `A`:

```
visited[A]  = true
parent[A]   = NONE
distance[A] = 0

queue = [A]
```

The source has distance zero because no edges are needed to reach it from itself.

#### Step 2: Remove the next vertex

```
u = dequeue()
```

The algorithm removes the front vertex from the queue.

For the first iteration:

```
Queue before: [A]
Current:       A
Queue after:   []
```

It then examines every neighbor of `A`.

#### Step 3: Examine neighbors

Suppose `A` is connected to `B` and `C`.

```
        A
       / \
      B   C
```

Neither neighbor has been discovered, so BFS processes each one:

```
visited[B]  = true
parent[B]   = A
distance[B] = distance[A] + 1

visited[C]  = true
parent[C]   = A
distance[C] = distance[A] + 1
```

The queue becomes:

```
[B, C]
```

#### Step 4: Repeat until the queue is empty

BFS continues removing vertices and discovering their unvisited neighbors.

```
while queue is not empty:
    ...
```

When the queue is empty, there are no more discovered vertices waiting for processing. Every vertex reachable from the source has been discovered and processed.

If the graph is disconnected, vertices in other components remain undiscovered.

### pseudocode 3
Here is the standard algorithm:

```
BFS(G, source):

    create an empty queue Q

    for each vertex v in G:
        visited[v] = false
        parent[v] = NIL
        distance[v] = INFINITY

    visited[source] = true
    distance[source] = 0
    ENQUEUE(Q, source)

    while Q is not empty:

        u = DEQUEUE(Q)
        PROCESS(u)

        for each vertex v adjacent to u:

            if visited[v] == false:

                visited[v] = true
                parent[v] = u
                distance[v] = distance[u] + 1

                ENQUEUE(Q, v)

    return visited, parent, distance
```

This version returns the search information in addition to performing the traversal.

There are four key operations:

1. Initialize the search state.
2. Add the source to the queue.
3. Remove and process the next vertex.
4. Discover and enqueue its unvisited neighbors.

The algorithm stops when the queue becomes empty. At that point, every vertex reachable from the source has been discovered and processed.


## 3. Initialization

Initialization establishes a clean starting state.

```c
for each vertex v in G:
    visited[v] = false
    parent[v] = NIL
    distance[v] = INFINITY
```

Let's examine why each value is needed.

- `visited[v] = false`: no vertex has been discovered yet.
- `parent[v] = NIL`: no predecessor has been assigned.
- `distance[v] = INFINITY`: no path from the source has been established.

Then BFS initializes the source:

```
visited[source] = true
distance[source] = 0
ENQUEUE(Q, source)
```

Why is the source's distance zero? Because it takes zero edges to reach the source from itself.

Why mark the source visited before enqueueing it? Because the source is already discovered. If we wait until it is dequeued, a neighboring vertex could enqueue the source again.

After initialization, the state is:

```
Queue:    [A]
Visited:  {A}
Distance: A = 0
Parent:   parent[A] = NIL
```

Here, `A` is the source.

## 4. Main loop and neighbor exploration

The central part of BFS is:

```
while Q is not empty:

    u = DEQUEUE(Q)
    PROCESS(u)

    for each vertex v adjacent to u:

        if visited[v] == false:

            visited[v] = true
            parent[v] = u
            distance[v] = distance[u] + 1

            ENQUEUE(Q, v)
```

There are two stages in each iteration.

### Stage A: Process the next vertex

```
u = DEQUEUE(Q)
PROCESS(u)
```

BFS removes the oldest waiting vertex from the queue.

Because the queue is FIFO (First In, First Out), vertices discovered earlier are processed earlier.

### Stage B: Explore its neighbors

```
for each vertex v adjacent to u:
```

BFS examines every vertex connected to `u` by an outgoing edge—or simply every incident neighbor in an undirected graph.

For each neighbor, it checks:

```
if visited[v] == false:
```

If the neighbor has not been discovered, BFS records how it reached that neighbor, assigns its distance, marks it visited, and enqueues it.

Consider this small example:

```
A -- B
|
C
```

Starting at `A`, BFS discovers `B` and `C` before processing either one.

```
Initially:       [A]
After A:         [B, C]
After B:         [C]
After C:         []
```

BFS finishes when the queue is empty.

## 5. The role of discovery and visited marking

This is one of the most important parts of BFS.

Discovery means that the algorithm has encountered a vertex for the first time. Processing means removing that vertex from the queue and examining its neighbors.

These are different events.

Consider a triangle:

```
    A
   / \
  B---C
```

Start at `A`.

1. BFS discovers `A` and enqueues it.
2. BFS processes `A`, discovers `B` and `C`, and enqueues both.
3. BFS processes `B`. It sees that `C` is already discovered, so it does not enqueue `C` again.
4. BFS processes `C`. It sees that `B` and `A` are already discovered, so it does not enqueue them again.

The visited set prevents repeated discovery and ensures termination even when the graph contains cycles.

### Why mark visited when enqueueing?

Correct:

```
if not visited[v]:
    visited[v] = true
    ENQUEUE(Q, v)
```

Potentially problematic:

```
if not visited[v]:
    ENQUEUE(Q, v)

# Marking visited only when dequeued is too late.
```

In the second version, two different vertices might enqueue the same neighbor before either copy is processed. That causes duplicate queue entries and unnecessary work.

### Why does this matter for shortest paths?

When BFS first discovers a vertex `v` from `u`, it records:

```
parent[v] = u
distance[v] = distance[u] + 1
```

BFS processes vertices in nondecreasing distance order. Therefore, the first discovery of `v` establishes its minimum edge distance from the source. A later route cannot improve that distance.

This is a key property of BFS, and we will prove it formally in the correctness section.

## 4. Why does BFS mark vertices as visited?

Consider this graph:

```
    A
   / \
  B---C
```

Suppose BFS starts at `A`.

1. It discovers `B` and `C`.
2. When processing `B`, it encounters `C` again.
3. Because `C` is already marked visited, BFS does not enqueue it again.
4. When processing `C`, it similarly skips `B`.

Without the visited check, cycles could cause repeated work or even an endless traversal.

A subtle but important distinction:

- Discovered: the vertex has been marked visited and scheduled or processed.
- Processed: the vertex has been removed from the queue and its neighbors examined.

A discovered vertex does not have to be processed immediately.


## 6. The BFS traversal order

BFS processes vertices in nondecreasing distance from the source.

Consider this graph:

```
          A
        /   \
       B     C
      / \     \
     D   E     F
```

The distance levels are:

```
Level 0:          A
                 / \
Level 1:        B   C
               / \   \
Level 2:      D   E   F
```

The corresponding distances are:

| Vertex | Distance from `A` |
| ------ | ----------------- |
| A      | 0                 |
| B      | 1                 |
| C      | 1                 |
| D      | 2                 |
| E      | 2                 |
| F      | 2                 |

One valid traversal is:

```
A → B → C → D → E → F
```

The order within a level depends on the order in which neighbors are examined. For example, if `C` is examined before `B`, the level-one order may be `C, B`.

However, BFS will not process a distance-two vertex before processing all distance-one vertices.

Important distinction: traversal order is not necessarily a unique ordering of the graph. The distance of each reachable vertex is independent of neighbor ordering, but the traversal sequence can vary.

## Early termination when searching for a target

Sometimes we want to find a specific target `T`, rather than traverse the entire reachable graph.

We can stop as soon as `T` is first discovered, because BFS discovers vertices in nondecreasing order of distance.

```
if not visited[v]:
    visited[v] = true
    parent[v] = u
    distance[v] = distance[u] + 1

    if v == target:
        reconstruct path
        return

    enqueue(v)
```

This is valid for finding one shortest path in an unweighted graph. If the goal is to process every vertex at the target's distance or enumerate all shortest paths, the stopping condition must be adjusted.

## Three-Color Breadth-First Search (BFS)

**Breadth-First Search **makes its progress without requiring any backtracking. It
records its progress by coloring vertices white, gray, or black, as Depth-First Search
did. Indeed, the same colors and definitions apply.

BFS can use the same three colors as DFS:

- **WHITE**: The vertex has not been discovered.
- **GRAY**: The vertex has been discovered and is waiting in the queue, or is currently being processed.
- **BLACK**: The vertex has been completely processed; all its neighbors have been examined.

The difference is how the algorithms explore the graph:

- DFS: Goes as deep as possible along one path, using recursion or a stack.
- BFS: Explores the graph level by level, using a queue.

In BFS, the colors help us distinguish between vertices that have not been discovered, vertices waiting to be processed, and vertices whose adjacency lists have already been examined.

### 1. Three colors in BFS

The state transitions are:

```
WHITE  ──────>  GRAY  ──────>  BLACK
Undiscovered    Discovered     Fully processed
                In queue       Removed from queue
                or processing
```

A key difference from DFS is that BFS colors a vertex gray when it is discovered and enqueued, not when it is removed from the queue.

Consider the following example:

```
          A
        /   \
       B     C
      / \     \
     D   E-----F
```

Assume:

- The graph is undirected.
- We start from `A`.
- Neighbors are processed alphabetically.

The BFS traversal order will be:

```
A -> B -> C -> D -> E -> F
```

### 2. Three-Color BFS pseudocode

The algorithm has two main operations:

1. Initialize all vertices and the queue.
2. Process vertices in FIFO (First In, First Out) order.

```
breadthFirstSearch(G, s):

    for each vertex v in G:
        color[v] = WHITE
        pred[v] = -1
        distance[v] = INFINITY

    create an empty queue Q

    color[s] = GRAY
    distance[s] = 0
    enqueue(Q, s)

    while Q is not empty:

        u = dequeue(Q)

        for each neighbor v of u:

            if color[v] == WHITE:

                color[v] = GRAY
                pred[v] = u
                distance[v] = distance[u] + 1

                enqueue(Q, v)

        color[u] = BLACK
```

Let's understand the important operations.

| Operation                       | Meaning                                       |
| ------------------------------- | --------------------------------------------- |
| `color[s] = GRAY`               | Discover the source vertex.                   |
| `enqueue(Q, s)`                 | Add the source to the queue.                  |
| `dequeue(Q)`                    | Take the next vertex to process.              |
| `color[v] == WHITE`             | Check whether a neighbor is undiscovered.     |
| `color[v] = GRAY`               | Mark the neighbor as discovered.              |
| `pred[v] = u`                   | Record how the neighbor was discovered.       |
| `distance[v] = distance[u] + 1` | Record its shortest distance from the source. |
| `color[u] = BLACK`              | Finish processing the current vertex.         |

Important: A vertex becomes gray when it is enqueued. This prevents another vertex from discovering and enqueuing it again.

**Another pseudocode**

```
breadthFirstSearch(G, s)

    // Initialization
    foreach v in V do
        pred[v] = -1
        dist[v] = ∞
        color[v] = WHITE (1)

    // Initialize the source vertex
    color[s] = GRAY
    dist[s] = 0

    // Initialize the queue
    Q = empty Queue (2)
    enqueue(Q, s)

    // BFS traversal
    while Q is not empty do
        u = head(Q)

        foreach neighbor v of u do
            if color[v] = WHITE then
                dist[v] = dist[u] + 1
                pred[v] = u
                color[v] = GRAY
                enqueue(Q, v)

        dequeue(Q)
        color[u] = BLACK (3)
```

- (1) Initially all vertices are marked as not visited.
- (2) Queue maintains collection of gray nodes that are visited.
- (3) Once all neighbors are visited, this vertex is done.


Variable meanings:

| Variable   | Meaning                                            |
| ---------- | -------------------------------------------------- |
| `G`        | Input graph                                        |
| `s`        | Source vertex                                      |
| `V`        | Set of vertices                                    |
| `Q`        | FIFO queue                                         |
| `color[v]` | State of vertex (`WHITE`, `GRAY`, or `BLACK`)      |
| `dist[v]`  | Shortest distance from source `s` to vertex `v`    |
| `pred[v]`  | Predecessor (parent) of vertex `v` in the BFS tree |

Important: A vertex becomes `GRAY` when discovered and enqueued. It becomes `BLACK` after all its neighbors have been examined. This ensures that each vertex is enqueued at most once.

| Discover A | G   | W   | W   | W   | W   | W   | `[A]`             |
| Process A  | B   | G   | G   | W   | W   | W   | `[B,C]`           |
| Process B  | B   | B   | G   | G   | G   | W   | `[C,D,E]`         |
| Process C  | B   | B   | B   | G   | G   | G   | `[D,E,F]`         |
| Process D  | B   | B   | B   | B   | G   | G   | `[E,F]`           |
| Process E  | B   | B   | B   | B   | B   | G   | `[F]`             |
| Process F  | B   | B   | B   | B   | B   | B   | `[]`              |

Legend: `W = WHITE`, `G = GRAY`, `B = BLACK`.

Notice that the queue determines the order in which gray vertices become black.


## Visited Set

The visited set is one of the most important parts of BFS.

It records which vertices have already been discovered. Without it, BFS could repeatedly add the same vertices to the queue, especially when the graph contains cycles.

### The problem without a visited set

Consider this graph:

```
    A ----- B
     \     /
       \ /
        C
```

The graph contains the edges:

```
A -- B
A -- C
B -- C
```

If BFS starts at `A`, it discovers both `B` and `C`.

When processing `B`, the algorithm encounters `C` again. When processing `C`, it encounters `B` again.

Without discovery tracking, the algorithm could continue adding `B` and `C` repeatedly.

### Mark vertices when enqueuing

The correct approach for ordinary BFS is to mark a vertex as visited when it is first discovered, before adding it to the queue.

```
if not visited[v]:
    visited[v] = true
    parent[v] = u
    enqueue(v)
```

The order matters.

Incorrect:

```
if not visited[v]:
    enqueue(v)
    visited[v] = true
```

This ordering can still work in a strictly sequential implementation if no duplicate entry is possible between these operations, but the essential rule is that the vertex must be marked before another exploration can enqueue it. In ordinary sequential BFS, simply marking before enqueueing makes this guarantee clear.

### Visited set and shortest paths

Marking vertices on discovery also ensures that the first parent assigned to a vertex comes from a vertex at the minimum possible distance.

For example:

```
        A
       / \
      B   C
       \ /
        D
```

BFS discovers `D` through either `B` or `C`, depending on neighbor order.

Both paths have two edges:

```
A -> B -> D
A -> C -> D
```

Once `D` is discovered, BFS does not overwrite its parent with another path of equal length.

The result is one shortest path, not necessarily every shortest path.

### Boolean array versus set

The choice depends on how vertices are identified.

- Boolean array: convenient when vertices have integer IDs from `0` to `V - 1`.
- Hash set: useful when vertices are arbitrary objects or strings.
- Three-color array: useful when distinguishing undiscovered, active, and fully processed vertices is important.

For a basic BFS, a Boolean array is usually sufficient.

## Parent Relationships and the BFS Tree

Although parent relationships are not strictly required to traverse a graph, they are essential when we want to reconstruct paths or understand how BFS reached a vertex.

When a vertex `v` is discovered from `u`, BFS sets:

```
parent[v] = u
```

Because BFS assigns the parent only when discovering a previously undiscovered vertex, each reachable vertex other than the source receives one parent.

### Example

For the graph:

```
        A
       / \
      B   C
     / \   \
    D   E   F
```

The parent relationships are:

```
parent[A] = NONE
parent[B] = A
parent[C] = A
parent[D] = B
parent[E] = B
parent[F] = C
```

These relationships form the BFS tree:

```
        A
       / \
      B   C
     / \   \
    D   E   F
```

The BFS tree contains only the edges that first discovered each vertex. The original graph may contain additional edges that do not appear in the tree.

### Why is the BFS tree useful?

It gives us:

1. A path from the source to every reachable vertex.
2. The shortest-path distance to every reachable vertex when edges are unweighted.
3. A record of how the traversal discovered the graph.
4. A basis for reconstructing paths and analyzing levels.

The BFS tree is a discovery structure; it does not necessarily include all edges of the original graph.

## Handling disconnected graphs

A graph is disconnected if some of its vertices cannot be reached from one another.

Consider:

```
Component 1          Component 2       Isolated vertex

    A                     D                  F
   / \
  B   C                   |
                          E
```

If we run:

```
BFS(G, A)
```

BFS visits only `A`, `B`, and `C`. It cannot reach `D`, `E`, or `F` from `A`.

To visit every vertex, we need an outer loop that starts a new BFS whenever it encounters an undiscovered vertex.

```
BFS-ALL(G):

    for each vertex v in G:
        visited[v] = false

    for each vertex s in G:

        if visited[s] == false:

            BFS-FROM-SOURCE(G, s, visited)
```

Here, `BFS-FROM-SOURCE` is the standard BFS algorithm, modified to use the shared `visited` array rather than initializing a new one each time.

The traversal proceeds as follows:

1. Start at `A` and visit `A`, `B`, and `C`.
2. Continue scanning vertices. Skip `B` and `C` because they are already visited.
3. Reach `D`, which is unvisited, and start another BFS. This visits `D` and `E`.
4. Reach `F`, which is also unvisited, and start another BFS. Since `F` is isolated, that traversal visits only `F`.

The result is a BFS forest containing one BFS tree per connected component.

For an undirected graph, this finds its connected components. For a directed graph, it finds the vertices reachable from each selected starting vertex, but those traversals do not necessarily correspond to the graph's strongly connected components.

The complexity remains $O(V+E)$ with an adjacency-list representation, because all vertices and edges are examined only a bounded number of times across the entire run.


## 9. Directed versus undirected graphs

The basic BFS algorithm works with both directed and undirected graphs. The difference is how the algorithm interprets adjacency.

### Undirected graph

An undirected edge connects two vertices in both directions.

```
A --- B --- C
```

If the graph contains the edge `A — B`, then:

- `B` is a neighbor of `A`.
- `A` is a neighbor of `B`.

Starting at `A`, BFS can discover `B`, then `C`.

### Directed graph

A directed edge has a specific direction.

```
A ---> B ---> C

A <--- D
```

Suppose the edges are:

```
A → B
B → C
D → A
```

Starting BFS at `A` follows outgoing edges:

```
A → B → C
```

It does not visit `D`, because the edge goes from `D` to `A`, not from `A` to `D`.

This illustrates an important rule:

BFS follows the edges available in the direction of traversal.

| Property                                     | Undirected graph                        | Directed graph                                    |
| -------------------------------------------- | --------------------------------------- | ------------------------------------------------- |
| Which edges are followed?                    | All incident edges                      | Outgoing edges                                    |
| Reachability means                           | A path exists between vertices          | A directed path exists from source to destination |
| Can a vertex be unreachable from the source? | Yes, if it belongs to another component | Yes, if no directed path leads to it              |
| Does ordinary BFS find shortest paths?       | Yes, by number of edges                 | Yes, by number of directed edges                  |

The BFS pseudocode itself does not need to change. Only the graph's neighbor relation changes.

## 6. Important algorithmic observations

- Neighbor order affects traversal order. It does not affect the minimum distance found for a vertex.
- The source has distance zero. Each newly discovered neighbor has distance one greater than the vertex that discovered it.
- Every vertex is enqueued at most once when visited is marked at discovery.
- BFS finds shortest paths by number of edges in an unweighted graph, because vertices are discovered in nondecreasing distance order.
- A queue is the mechanism, not the whole explanation. The key property comes from combining FIFO ordering with marking vertices when discovered.

The most important idea to carry forward is this: BFS discovers vertices in nondecreasing distance from the source. The FIFO queue and discovery-time marking work together to achieve this property. The next topic, BFS correctness, explains why that property guarantees shortest paths in unweighted graphs.
