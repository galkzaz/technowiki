
Looking for specific information in memory is a key operation in computing. A sound knowledge of search algorithms is essential. The simplest search algorithm is Sequential Search: look at all items one after the other, until you find the one you want—or check all items to realize it’s not there

## Introduction to Searching
**Searching** is the process of locating an item, or determining information about an item, within a collection of data.

For example, given:

```text
[15, 8, 23, 4, 42, 16, 9]
```

we might ask:

> Does `23` exist in the collection?

or:

> Where is `23` located?

or:

> Find all values between `10` and `20`.

These are all **searching problems**, but they have different requirements and therefore may use different algorithms.

### What Is Searching?

Searching is the process of finding one or more elements in a **search space** according to some condition.

The simplest form is:

> Given a collection of elements and a target value, determine whether the target exists and, if so, locate it.

For example:

```text
Data:
[10, 25, 7, 42, 18, 31]

Target:
42
```

A search algorithm should determine that:

```text
42 exists
position = 3
```

assuming zero-based indexing.

#### Searching is more than finding an exact value

Depending on the problem, we may want to:

* find an exact value
* find the first occurrence
* find the last occurrence
* find all occurrences
* find the smallest value ≥ target
* find the largest value ≤ target
* find values within a range
* find the closest value
* determine whether an element satisfies a condition

So, **searching is a general problem-solving operation**, not just "find a number."

---

### Search Queries and Problem Model
#### Fundamental Search Queries

Before studying **searching algorithms**, it is useful to understand **what we are actually asking a search algorithm to do**.

Searching is not always just: “Find this element.”

Different applications ask different questions. Given a collection C of elements, Two of the most fundamental search queries are:

1. **Existence Query** — Does the element exist? Does C contain a target element? Given a collection C, we often simply want to
know whether the collection already contains a given element t. The response
to such a query is true if an element exists in the collection that matches the
desired target t, or false if this is not the case
2. **Associative Lookup** — What information is associated with this key? Return information associated in collection C with a target key value k. A key is
usually associated with a complex structure called a value. The lookup retrieves
or replaces this value.

These two queries form the foundation of structures such as **sets, maps, dictionaries, hash tables, and search trees**.

---

##### Existence Queries

An **existence query** asks whether a collection contains a particular element.

In its simplest form:

```text
Does C contain t?
```

where:

* `C` = collection
* `t` = target element

The result is simply: "true" or "flase"
```

**Example**

Suppose we have:

```text
C = [10, 25, 30, 42, 57]
```

We ask:

```text
Does C contain 30?
```

The answer is: "true"

For: "Does C contain 35?""

the answer is: "false"

**Conceptually**

We can represent the operation as:

```text
contains(C, t) → boolean
```

For example:

```text
contains([10, 25, 30, 42, 57], 30)
        ↓
      true
```

and:

```text
contains([10, 25, 30, 42, 57], 35)
        ↓
      false
```

---

**Example with Strings**

```text
C = ["Alice", "Bob", "Charlie"]
```

Query:

```text
contains(C, "Bob")
```

Result:

```text
true
```

Query:

```text
contains(C, "David")
```

Result:

```text
false
```

---

**What Does Existence Search Return?**

The important point is that we **do not necessarily need the element itself**.

The result is simply:

```text
true / false
```

For example:

```text
if (contains(C, 42)) {
    // 42 exists
}
```

We don't necessarily care:

* where `42` is stored,
* how many times it occurs,
* what other information is associated with it.

We only care whether it exists.

--- 

**Why is this a search problem?**

To determine whether `30` exists, an algorithm has to **search the collection**.

For example, with linear search:

```text
[10, 25, 30, 42, 57]
  ↑
check 10 → no

[10, 25, 30, 42, 57]
      ↑
check 25 → no

[10, 25, 30, 42, 57]
          ↑
check 30 → yes
```

The algorithm can stop as soon as it finds the target.

This is why an existence query is closely related to **membership testing**.

---

###### Existence Queries and Sets

An existence query is particularly important for a **set**.

A set contains unique elements:

```text
S = {10, 20, 30, 40}
```

The fundamental operation is:

```text
contains(S, x)
```

For example:

```text
contains(S, 20) → true
contains(S, 25) → false
```

A set generally cares about: **Is this element present?**, It does not necessarily associate another value with the element.

---

**Example: Usernames**

Imagine a system maintaining registered usernames:

```text
{"alice", "bob", "charlie", "david"}
```

When someone tries to register `"bob"`, the system might ask:

```text
Does "bob" already exist?
```

This is an **existence query**.

```text
contains(users, "bob") → true
```

The system can then reject the duplicate username.

---

##### Associative Lookup

An **associative lookup** is different. Instead of asking: “Does this element exist?”

we ask: **Given a key, what information is associated with that key?**

Here, the collection contains **key-value associations**.

For example:

```text
Key       Value
-------------------------
101       "Ahmed"
102       "Sara"
103       "Omar"
```

Here The key identifies the record, while the value contains the associated information

* `101`, `102`, `103` are **keys**
* `"Ahmed"`, `"Sara"`, `"Omar"` are **values**

We can perform:

```text
lookup(C, 102)
```

and get:

```text
"Sara"
```

---

**Key-Value Model**

We can think of associative lookup as:

```text
key → value
```

For Example: Student Records

Suppose we have:

```text
ID     Student
--------------------
101    Ahmed
102    Sara
103    Omar
```

The collection can conceptually be represented as:

```text
C = {
    101 → Ahmed,
    102 → Sara,
    103 → Omar
}
```

The lookup operation is:

```text
get(C, key) → value
```

For example:

```text
get(C, 102)
    ↓
"Sara"
```

---

**Example**

Suppose we have:

```text
C = {
    1001 → "Alice",
    1002 → "Bob",
    1003 → "Charlie"
}
```

Now:

```text
lookup(C, 1002)
```

returns:

```text
"Bob"
```

While:

```text
lookup(C, 1005)
```

might return:

```text
not found
```

depending on the API.

---

**Why Is It Called "Associative"?**

It is called **associative** because the collection maintains an association:

```text
key → value
```

For example:

```text
"alice" → User object
"bob"   → User object
"carol" → User object
```

The key allows us to retrieve the associated value.

This is the basic idea behind **maps/dictionaries**.

---

**Associative Lookup with Complex Values**

The value does not have to be a simple string.

It can be a complete object or record.

For example:

```text
ID = 102
```

might be associated with:

```text
Student {
    id: 102
    name: "Sara"
    age: 22
    grade: 92
}
```

Conceptually:

```text
102 ───────────────→ Student object
                       │
                       ├── name = Sara
                       ├── age = 22
                       └── grade = 92
```

Then:

```text
lookup(C, 102)
```

returns the entire `Student` object.

This is what the statement means by:

> "A key is usually associated with a complex structure called a value."

---

**Associative Lookup Is More Than Searching for an Element**

This distinction is important.

Consider:

```text
[1001, 1002, 1003]
```

Searching for `1002` answers:

```text
Does 1002 exist?
```

But consider:

```text
1001 → Alice
1002 → Bob
1003 → Charlie
```

Searching for `1002` now means:

```text
What information is associated with 1002?
```

The answer is:

```text
Bob
```

So the search key is used to **locate a record/value**.

- **Python**

```python
students = {
    101: "Ahmed",

```

Output:

```text
Sara

##### Associative Lookup Can Also Update Values

Associative collections usually support more than just retrieving values.

For example:

```text
102 → "Sara"
```

We can replace the associated value:

```text
put(C, 102, "Mona")
```

Now:

```text
102 → "Mona"
```

So the same key can be used to access and update the associated value.

For example:

```text
Before:

102 → "Sara"

        ↓ update

After:

102 → "Mona"
```

So associative collections commonly provide operations such as:

```text
get(key)
put(key, value)
remove(key)
containsKey(key)
```

This is why associative lookup is fundamental to **maps/dictionaries**.

##### Existence vs Associative Lookup

The two queries are closely related, but their purposes are different.

| Feature                | Existence Query    | Associative Lookup                |
| ---------------------- | ------------------ | --------------------------------- |
| Main question          | Does it exist?     | What is associated with this key? |
| Input                  | Target/element     | Key                               |
| Output                 | `true` / `false`   | Associated value                  |
| Typical structure      | Set                | Map / Dictionary                  |
| Example                | `contains(30)`     | `get(30)`                         |
| Main purpose           | Membership testing | Retrieve information              |
| Key-value relationship | Not required       | Required                          |

---

**Simple Comparison**

Suppose we have:

```text
C = {
    101 → "Ahmed",
    102 → "Sara",
    103 → "Omar"
}
```

1. Existence query

We ask:

```text
Does key 102 exist?
```

Result:

```text
true
```

Conceptually:

```text
containsKey(C, 102) → true
```

2. Associative lookup

We ask:

```text
What is associated with key 102?
```

Result:

```text
"Sara"
```

Conceptually:

```text
get(C, 102) → "Sara"
```

---

**The Important Relationship**

An associative lookup can often be thought of as combining two ideas:

```text
             Search
               │
               ▼
        Find the key
               │
               ▼
      Retrieve its value
```

For:

```text
102 → Sara
```

the algorithm first determines where key `102` is, then returns:

```text
Sara
```

An existence query stops after determining whether the key/element is present:

```text
             Search
               │
               ▼
       Is key present?
          /        \
        yes        no
        ↓           ↓
      true        false
```

---

**Example with a Student Database**

Suppose:

```text
Students

ID      Name
----------------
101     Ahmed
102     Sara
103     Omar
104     Mona
```

1. **Query 1 — Existence**

```text
Does student 103 exist?
```

Answer:

```text
true
```

2. **Query 2 — Associative Lookup**

```text
What is the name of student 103?
```

Answer:

```text
Omar
```

3. **Query 3 — Nonexistent key**

```text
Does student 110 exist?
```

Answer:

```text
false
```

And:

```text
What is associated with student 110?
```

Answer:

```text
not found
```

##### Relationship to Searching Algorithms
{/* **Why This Matters for Searching Algorithms** */}
These two queries lead to two important categories of search operations.

```text
                    Searching
                        │
              ┌─────────┴─────────┐
              │                   │
         Existence          Associative Lookup
              │                   │
       "Does it exist?"      "What belongs to k?"
              │                   │
        true / false             value
```

Different data structures are optimized for these operations.

For example:

| Data Structure     | Existence            | Associative Lookup   |
| ------------------ | -------------------- | -------------------- |
| Array              | Linear/Binary Search | Search record by key |
| Linked List        | Linear Search        | Linear Search        |
| Hash Table         | Very fast average    | Very fast average    |
| Binary Search Tree | Tree Search          | Tree Search          |
| B-tree             | Indexed search       | Indexed lookup       |
| Hash Map           | Key existence        | Key → value          |

This distinction becomes important when we study different searching data structures.

For example:

```text
Searching Algorithms
│
├── Linear Search
│
├── Binary Search
│
├── Hash-Based Searching
│
├── Tree-Based Searching
│
└── ...
```

Each algorithm can be used to answer different queries.

- **Linear Search**

```text
contains(array, target)
```

or:

```text
find(array, target)
```

- **Binary Search**

Can answer:

```text
Does target exist?
```

and can also locate:

```text
first occurrence
last occurrence
insertion position
predecessor
successor
```

- **Hash Table**

Particularly useful for:

```text
contains(key)
get(key)
put(key, value)
remove(key)
```

So the **query type** helps determine what searching technique or data structure is appropriate.

##### Connection to Sets and Maps
This distinction also explains the difference between two fundamental abstract data types:

```text
Set
```

and:

```text
Map

A very useful mental model is:

```text
             Searching Queries
                    │
          ┌─────────┴─────────┐
          │                   │
          ▼                   ▼
     Existence            Associative
       Query                Lookup
          │                   │
          ▼                   ▼
        Set                 Map
          │                   │
          ▼                   ▼
    contains(x)           get(key)
```

- **Set**

A **set** primarily answers: > Does this element exist?

```text
S = {10, 20, 30, 40}
```

Query:

```text
contains(S, 30)
→ true
```

There is no separate value associated with `30`.

Main question:

```text
Is 30 present?
```

- **Map**

A **map** associates keys with values:

```text
M = {
    10 → "Ahmed",
    20 → "Sara",
    30 → "Omar"
}
```
Query:

```text
containsKey(M, 30)
→ true
```

or:

```text
get(M, 30)
→ "Omar"
```

Main question:

```text
What is associated with 30?
```

So conceptually:

```text
Set
 │
 └── element → existence

Map
 │
 └── key → value
```

---

**A Subtle but Important Point**

An **existence query** does not necessarily mean that the algorithm returns only a Boolean internally.

For example, a linear search might return:

```text
index = 2
```

and then the caller converts that into:

```text
true
```

So:

```text
find(C, t) → index
```

can be used to implement:

```text
contains(C, t) → boolean
```

For example:

```text
C = [10, 20, 30, 40]

find(C, 30) → 2

contains(C, 30) → true
```

This shows that **searching for an element** and **asking whether it exists** are related but conceptually different operations.

---

**Summary**

The two fundamental queries are:

1. Existence Query

> **Is the target present in the collection?**

```text
contains(C, t) → true / false
```

Primarily associated with **sets** and membership testing.

2. Associative Lookup

> **What value/record is associated with this key?**

```text
get(C, k) → value
```

Primarily associated with **maps/dictionaries** and key-value data.

The key distinction is:

```text
Existence:
    key → "Is it there?"
             ↓
          boolean

Associative Lookup:
    key → "What's associated with it?"
             ↓
           value
```

*Existence search** is the foundation of **sets**, while **associative lookup** is the foundation of **maps/dictionaries**.

For example, **Hash Tables** can be viewed as a data structure that efficiently supports both:

```text
contains(key)     → Does this key exist?
get(key)          → What value is associated with this key?
put(key, value)   → Create or replace the association
```

This is why, when we later study **hash tables, binary search trees, B-trees, and other search structures**, we should always ask: **Are we searching merely for existence, or are we searching to retrieve a value associated with a key?**

This is a good foundation for the next sections because later algorithms such as **Linear Search, Binary Search, Hashing, and Tree Searching** can be understood in terms of **which search queries they support and how efficiently they answer them**.

A **search problem** defines what we are looking for and where we are looking for it.

A search problem usually contains:

```text
Search Space
     ↓
Search Key / Target
     ↓
Search Condition
     ↓
Search Algorithm
     ↓
Result
```

For example:

```text
Array:
[12, 5, 27, 8, 19, 34]

Target:
19

Condition:
Find an element equal to 19

Result:
Found at index 4
```

We can describe the problem formally as:

> Given a collection `A` and a search criterion, determine whether an element satisfying the criterion exists and return the required information about it.

The required information might be:

```text
boolean
index
element
range
set of elements
closest element
```

**Example**

Suppose we have:

```text
A = [4, 9, 15, 21, 30]
```

and the problem is:

> Find the first element greater than `17`.

The answer is:

```text
21
```

Notice that `17` itself does not need to exist in the array.

This is why it is useful to distinguish different types of searching.

### Search Key

A **search key** is the value or attribute used to identify the element we are searching for.

For example:

```text
Student records:

ID      Name       Grade
101     Ahmed      85
102     Sara       92
103     Omar       78
```

If we search using:

```text
ID = 102
```

then `102` is the **search key**.

The algorithm compares the search key against the corresponding key of each record.

```text
Search key
    ↓
   102
    ↓
Student ID
    ↓
101 → no
102 → yes
```

#### Key vs entire element

An element can contain many fields:

```text
Student {
    id
    name
    age
    grade
}
```

We usually don't compare the entire object.

Instead, we search using a particular field:

```text
student.id
```

That field is the **search key**.

#### Examples of search keys

| Data             | Possible search key |
| ---------------- | ------------------- |
| Student records  | Student ID          |
| Employees        | Employee ID         |
| Books            | ISBN                |
| Products         | Product ID          |
| Users            | Username            |
| Dictionary       | Word                |
| Database records | Primary key         |

This concept becomes particularly important when searching complex data structures.

---

### Search Target

The **search target** is the specific value or condition that we want to find.

For example:

```text
Array:
[10, 20, 30, 40, 50]

Target:
30
```

Here:

```text
Search target = 30
```

The distinction between **search key** and **search target** is useful.

Suppose we have:

```text
Employee:
ID = 105
Name = "Ahmed"
Department = "Engineering"
```

If we search by employee ID:

```text
Search key    = ID
Search target = 105
```

The key tells us **what attribute to compare**.

The target tells us **what value we are looking for**.

**Another example**

```text
Products:

ID     Name       Price
1      Laptop     1000
2      Phone       500
3      Tablet      700
```

Search:

> Find the product whose ID is `2`.

Then:

```text
Search key    = ID
Search target = 2
```

Result:

```text
Phone
```

### Search Space

The **search space** is the collection of possible elements that the algorithm may need to examine.

For example:

```text
A = [8, 3, 12, 5, 19, 7]
```

The array is the search space.

If we search for `19`:

```text
Search space = A
Target       = 19
```

#### Search space does not have to be an array

It can be:

* array
* linked list
* tree
* hash table
* graph
* database
* file
* filesystem
* memory
* sorted range
* state space of a problem

For example, in a graph:

```text
       A
      / \
     B   C
    /     \
   D       E
```

If we are looking for vertex `E`, the graph represents the search space.

In a path-finding problem, the search space can instead consist of possible **states or paths**.

**Why search space matters**

The structure of the search space strongly influences the algorithm.

For an unsorted array:

```text
[8, 3, 12, 5, 19, 7]
```

we may need to inspect elements sequentially.

For a sorted array:

```text
[3, 5, 7, 8, 12, 19]
```

we can eliminate large portions of the search space using **Binary Search**.

So a major question in searching is:**What information does the structure of the search space give us?**

### Successful Search

A **successful search** occurs when the desired element or condition is found.

Example:

```text
A = [10, 20, 30, 40, 50]

Target = 30
```

Since `30` exists:

```text
Search → SUCCESS
```

The algorithm may return:

```text
index = 2
```

For example, using linear search:

```text
10 → no
20 → no
30 → yes
```

#### Possible successful-search results

Depending on the problem, success may return:

```text
true
```

or:

```text
index = 2
```

or:

```text
element = 30
```

or:

```text
record = Student(102, "Sara", 92)
```

or even:

```text
range = [10, 20]
```

#### Successful search cost

The amount of work required for a successful search depends on where the answer is located.

For linear search:

```text
[10, 20, 30, 40, 50]
 ↑
target
```

Only one comparison may be required.

But:

```text
[10, 20, 30, 40, 50]
             ↑
           target
```

requires more comparisons.

This leads to concepts such as:

* best case
* average case
* worst case

which are important when analyzing searching algorithms.

---

#### Unsuccessful Search

An **unsuccessful search** occurs when no element satisfies the search condition.

Example:

```text
A = [10, 20, 30, 40, 50]

Target = 35
```

Since `35` does not exist:

```text
Search → FAILURE
```

A search algorithm might return:

```text
-1
```

or:

```text
false
```

or:

```text
null
```

depending on the programming language and API.

#### Linear search

For:

```text
[10, 20, 30, 40, 50]
```

searching for `35` requires checking:

```text
10 → no
20 → no
30 → no
40 → no
50 → no
```

All elements are examined.

Therefore, linear search has:

```text
Worst case = O(n)
```

for both:

* searching for an element near the end
* searching for an element that does not exist

**Important distinction**

An unsuccessful search is not necessarily an error.

It is often a **valid result**:

> "The requested item does not exist."

For example:

```text
findUser("john123")
```

may legitimately return:

```text
User not found
```

### Exact-Match Searching

**Exact-match searching** means that we want an element whose search key is exactly equal to the target.

The condition is essentially:

```text
key(element) == target
```

Example:

```text
A = [10, 20, 30, 40, 50]

target = 30
```

We want:

```text
element == 30
```

**Example with strings**

```text
Names:
["Ahmed", "Sara", "Omar", "Mona"]

Target:
"Omar"
```

The search succeeds because:

```text
"Omar" == "Omar"
```

#### Common exact-match algorithms

Depending on the data structure, we can use:

* Linear Search
* Binary Search
* Hash Table lookup
* Tree Search
* B-tree/B+ tree lookup

For example:

| Structure          | Typical exact search |
| ------------------ | -------------------- |
| Unsorted array     | Linear Search        |
| Sorted array       | Binary Search        |
| Hash table         | Hash lookup          |
| Binary Search Tree | Tree search          |
| B-tree             | B-tree search        |

**Important idea**

The same search problem can have very different performance depending on the organization of the data.

For example:

```text
Unsorted array
→ Linear Search
→ O(n)
```

while:

```text
Sorted array
→ Binary Search
→ O(log n)
```

and a well-designed hash table can provide approximately:

```text
Hash lookup
→ O(1) average
```

---

### Range Searching

**Range searching** asks for elements whose values fall within a specified range.

Instead of:

> Find `25`.

we might ask:

> Find all values between `20` and `40`.

For:

```text
A = [10, 15, 22, 27, 35, 42, 50]
```

query:

```text
20 ≤ x ≤ 40
```

result:

```text
22, 27, 35
```

**Range searching is different from exact searching**

Exact:

```text
target = 27
```

Range:

```text
20 ≤ x ≤ 40
```

The result of exact searching is often one element.

The result of range searching can contain many elements.

#### Range searching on sorted data

Suppose:

```text
A = [5, 10, 15, 20, 25, 30, 35, 40, 45]
```

We want:

```text
20 ≤ x ≤ 35
```

Instead of examining every element, we can find the boundaries:

```text
first element ≥ 20
```

and:

```text
first element > 35
```

This is commonly implemented using **binary-search variants** such as:

* lower bound
* upper bound

Conceptually:

```text
                range
                  ↓
5  10  15 | 20  25  30  35 | 40  45
           ↑                 ↑
       lower bound       upper bound
```

This becomes very important in advanced searching algorithms and database indexing.

---

### Approximate Searching

**Approximate searching** looks for an element that is not necessarily an exact match but is **close to the target according to some definition of closeness**.

For example:

```text
A = [10, 20, 30, 40, 50]

Target = 33
```

There is no exact `33`.

But we might ask:

> What is the closest value to 33?

The answer could be:

```text
30
```

or:

```text
30 and 40
```

depending on the definition.

**Approximate searching requires a distance or similarity rule**

For numerical data:

```text
distance(a, b) = |a - b|
```

For strings, we might use a similarity or edit-distance measure.

Example:

```text
Target = "kitten"

Candidate = "sitten"
```

The strings differ by one character.

#### Examples

Approximate searching appears in:

* spell checking
* autocomplete
* fuzzy string matching
* recommendation systems
* nearest-neighbor search
* geographic searches
* similarity search

For example:

> Find restaurants within 2 km of a location.

This is a spatial approximate/range query rather than an exact equality query.

---

### Static vs Dynamic Search

This distinction concerns whether the data changes while we are performing searches.

#### Static Searching

A **static search space** does not change, or changes very rarely, after it has been prepared.

Example:

```text
Dictionary:
[apple, banana, cherry, ...]
```

We may build an efficient structure once and perform many searches.

For example:

```text
Build sorted array
       ↓
Binary Search
       ↓
many searches
```

The important characteristic is:

```text
Data → mostly unchanged
Queries → many
```

This allows us to spend time preprocessing the data.

**Example**

Suppose we have:

```text
1,000,000 employee IDs
```

and need to perform millions of searches.

We could sort the IDs once:

```text
O(n log n)
```

and then use binary search:

```text
O(log n)
```

for each query.

---

#### Dynamic Searching

A **dynamic search space** changes frequently.

For example:

```text
Insert employee
Delete employee
Search employee
Insert employee
Search employee
Delete employee
```

Now the data structure must support both:

```text
Search
Insert
Delete
```

efficiently.

Examples include:

* Binary Search Trees
* AVL Trees
* Red-Black Trees
* B-trees
* Hash Tables

#### Static vs dynamic

| Property            | Static                       | Dynamic                     |
| ------------------- | ---------------------------- | --------------------------- |
| Data changes        | Rarely                       | Frequently                  |
| Preprocessing       | Often useful                 | More limited                |
| Typical structure   | Sorted array                 | Tree/hash table             |
| Search optimization | Heavy preprocessing possible | Must balance search/update  |
| Example             | Dictionary index             | Database index with updates |

**Important trade-off**

A structure that is excellent for searching may be expensive to modify.

For example, inserting into a sorted array can require shifting many elements:

```text
Before:
[10, 20, 30, 40]

Insert 25:

[10, 20, 25, 30, 40]
          ↑
       elements shifted
```

So searching algorithms must often be considered together with **update operations**.

---

### Internal vs External Searching

This distinction concerns **where the data resides during the search**.

#### Internal Searching

**Internal searching** means the data being searched is stored in **main memory (RAM)** during the operation.

For example:

```text
CPU
 ↓
RAM
 ↓
[10, 20, 30, 40, 50]
```

Examples:

* Linear Search on an array
* Binary Search on an array
* Searching a tree in memory
* Hash table lookup in RAM

The main concern is usually:

> How many computational operations or memory accesses are required?

---

#### External Searching

**External searching** occurs when the data is too large to fit conveniently in main memory and is stored on external storage.

Historically this meant:

* magnetic disks
* tapes

Today it can include:

* SSDs
* databases
* large files
* distributed storage

Conceptually:

```text
CPU
 ↓
RAM
 ↓
Storage
 ↓
Huge dataset
```

The important issue is that accessing external storage is much more expensive than accessing RAM.

Therefore, external searching focuses heavily on **reducing I/O operations**.

**Example**

Imagine a database containing:

```text
10 billion records
```

We cannot simply load everything into RAM and perform a linear search.

Instead, databases use structures such as:

* B-trees
* B+ trees
* indexes
* hash indexes
* LSM trees

to reduce the amount of data that must be read from storage.

---

#### Internal vs External Search: Key Difference

The fundamental distinction is:

```text
Internal Search
     ↓
Data primarily in RAM
     ↓
CPU / memory operations dominate
```

versus:

```text
External Search
     ↓
Data primarily on storage
     ↓
I/O operations dominate
```

For example, suppose we need to search 1 million sorted integers.

1. Internal approach

If they are already in memory:

```text
Binary Search
O(log n)
```

Only around 20 comparisons are needed for 1 million elements.

2. External approach

If the data is stored on disk, the number of **disk/block accesses** becomes much more important than the number of individual comparisons.

This is why a B+ tree might be preferable for database searching.


**How These Concepts Fit Together**

These concepts describe different dimensions of a search problem.

```text
                    SEARCHING
                        │
        ┌───────────────┼────────────────┐
        │               │                │
     What?           Where?           How?
        │               │                │
   ┌────┴────┐     ┌────┴─────┐    ┌────┴────────┐
   │         │     │          │    │             │
Exact     Range  Internal   External Static     Dynamic
   │         │
Approximate │
            │
```

A real search problem can combine several of these characteristics.

For example:

> Find all products priced between `$100` and `$200` in a database containing millions of products that are continuously updated.

This is:

```text
Range searching
        +
External searching
        +
Dynamic searching
```

Another example:

> Find an employee with ID `1250` in an in-memory sorted array.

This is:

```text
Exact-match searching
        +
Internal searching
        +
Static searching
        +
Binary Search
```

---

#### Summary

| Concept                 | Meaning                                | Example                |
| ----------------------- | -------------------------------------- | ---------------------- |
| **Searching**           | Finding data satisfying a condition    | Find `42`              |
| **Search Problem**      | Formal task of locating desired data   | Find employee ID `105` |
| **Search Key**          | Attribute used to identify data        | `employee.id`          |
| **Search Target**       | Value being searched for               | `105`                  |
| **Search Space**        | Collection of possible candidates      | Array of employees     |

| **Unsuccessful Search** | Desired item is not found              | `42` doesn't exist     |
| **Exact-Match**         | Key must equal target                  | Find ID `105`          |
| **Range Search**        | Find values within boundaries          | `100 ≤ price ≤ 200`    |

| **Internal Search**     | Data is in main memory                 | Array in RAM           |
| **External Search**     | Data is primarily in external storage  | Database on SSD        |

The most important idea is that **the choice of searching algorithm depends heavily on the properties of the search space**:

```text
Unsorted data
    → Linear Search

Sorted data
    → Binary Search

Key → value mapping
    → Hashing

Hierarchical data
    → Tree Search

Large external data
    → B-tree / B+ tree / external indexing

Similarity requirement
    → Approximate / nearest-neighbor search

Range requirement
    → Lower/upper-bound or indexed range search
```

These concepts provide the foundation for the next major topics in **Searching Algorithms**, such as **Linear Search, Binary Search, Interpolation Search, Jump Search, Exponential Search, Fibonacci Search, Hash-based Search, Tree Search, and Range Searching**.

## Search Problem Model

Before studying individual searching algorithms such as **Linear Search** and **Binary Search**, it helps to define exactly what a search algorithm is expected to do.

A **search problem model** describes:

1. what data we search,
2. what identifies an element,
3. how elements are compared,
4. what constitutes a match, and
5. what information the algorithm must return.

A useful abstraction is:

```text
Input Data
    │
    ▼
Search Key / Target
    │
    ▼
Comparison
    │
    ▼
Matching Condition
    │
    ▼
Search Result
```

For example:

```text
Records:
[10, 20, 20, 30, 40]

Target:
20

Possible results:
    first occurrence  → index 1
    last occurrence   → index 2
    all occurrences   → [1, 2]
    insertion position → index 1 or 3 depending on convention
```

The important point is that **"search for 20" is not a complete specification**. We must also say what result we want.

---

### Input Representation

The **input representation** describes how the data being searched is organized and stored.

A search algorithm cannot operate without some representation of the search space.

Common representations include:

* arrays
* linked lists
* records/objects
* trees
* hash tables
* files
* database indexes

---

#### Array Representation

The simplest representation is an array:

```text
A = [15, 8, 23, 4, 42, 16]
```

Each element has an index:

```text
Index:  0   1   2   3   4   5
        ↓   ↓   ↓   ↓   ↓   ↓
A:     15   8  23   4  42  16
```

A search algorithm can access:

```text
A[i]
```

directly.

This makes arrays particularly suitable for algorithms such as:

* Linear Search
* Binary Search
* Jump Search
* Interpolation Search

---

#### Sorted Array Representation

The same data could be organized as:

```text
A = [4, 8, 15, 16, 23, 42]
```

Now the data has an important property:

```text
A[i] ≤ A[i+1]
```

This additional information enables more efficient searching algorithms.

For example, **Binary Search** uses the ordering to eliminate half of the remaining search space after each comparison.

---

#### Record Representation

Often an element is not simply an integer.

For example:

```text
Student {
    id
    name
    grade
}
```

The data could be:

```text
[
    {101, "Ahmed", 85},
    {102, "Sara", 92},
    {103, "Omar", 78}
]
```

We may search using the `id` field.

So the representation contains:

```text
Record
 ├── id
 ├── name
 └── grade
```

but the search algorithm might use only:

```text
record.id
```

---

#### Why Representation Matters

Different representations provide different capabilities.

For example:

```text
Unsorted Array
    ↓
No ordering information
    ↓
Linear Search is natural
```

while:

```text
Sorted Array
    ↓
Ordering information available
    ↓
Binary Search becomes possible
```

And:

```text
Hash Table
    ↓
Hash function maps keys to locations
    ↓
Fast exact lookup
```

So **input representation is one of the factors that determines which search algorithm is appropriate**.

---

### Search Key and Records

A **record** is a complete data item.

A **key** is the part of the record used to identify or compare it during searching.

Consider:

```text
Employee
----------------
ID       = 105
Name     = Ahmed
Salary   = 30000
Dept     = IT
```

The complete employee is the **record**:

```text
R = {
    ID: 105,
    Name: Ahmed,
    Salary: 30000,
    Dept: IT
}
```

If we search by employee ID:

```text
key(R) = R.ID
```

The search key is: `105`

So:

```text
Record
   │
   ├── ID      ← Search Key
   ├── Name
   ├── Salary
   └── Dept
```

---

#### Why Separate Keys from Records?

Searching usually does not require comparing the entire record.

Suppose:

```text
R1 = {101, Ahmed, 85}
R2 = {102, Sara, 92}
R3 = {103, Omar, 78}
```

Search:

```text
target = 102
```

We compare:

```text
101 == 102 → false
102 == 102 → true
```

We do not need to compare:

```text
Ahmed
Sara
Omar
85
92
78
```

The key gives us the property that identifies the record.

---

**Example: Database**

A database table might contain:

```text
ID     Name       Age
-----------------------
101    Ahmed      25
102    Sara       30
103    Omar       28
```

Here:

```text
Record = entire row
Key    = ID
```

A query such as:

```text
WHERE ID = 102
```

is essentially an **exact-match search on the key**.

---

### Key Comparisons

A **key comparison** is the operation used to determine the relationship between the search target and a record's key.

Suppose:

```text
target = 30
```

and:

```text
record.key = 25
```

The search algorithm needs to determine how `25` relates to `30`.

Depending on the problem, we may ask:

```text
25 == 30 ?
25 < 30 ?
25 > 30 ?
```

These comparisons form the fundamental operations of many searching algorithms.

---

#### Linear Search

Linear Search generally uses equality:

```text
if (A[i] == target)
    found;
```

Example:

```text
[10, 20, 30, 40]

target = 30

10 == 30 → false
20 == 30 → false
30 == 30 → true
```

---

#### Binary Search

Binary Search needs ordering comparisons.

For example:

```text
A[mid] < target
```

or:

```text
A[mid] > target
```

This tells Binary Search which half of the search space can be discarded.

Therefore:

> **Equality tells us whether we found the target; ordering tells us where to continue searching.**

This distinction is fundamental.

---

### Equality Tests

An **equality test** asks:

> Are these two keys equal?

Formally:

```text
key == target
```

For numerical values:

```text
25 == 25 → true
25 == 30 → false
```

For strings:

```text
"cat" == "cat" → true
"cat" == "dog" → false
```

---

#### Equality in Linear Search

Consider:

```text
A = [8, 15, 23, 42]
target = 23
```

Linear Search performs:

```text
8  == 23 → false
15 == 23 → false
23 == 23 → true
```

The equality test determines whether the search succeeds.

---

#### Equality and Duplicate Values

Suppose:

```text
A = [10, 20, 20, 20, 30]
```

and:

```text
target = 20
```

An equality test tells us that several elements match:

```text
index 1 → 20 == 20
index 2 → 20 == 20
index 3 → 20 == 20
```

But equality alone does **not** tell us whether we should return:

```text
1
```

or:

```text
3
```

or:

```text
[1, 2, 3]
```

That is determined by the **search result specification**.

---

### Ordering Comparisons

An **ordering comparison** determines whether one key is smaller or larger than another.

The basic relationships are:

```text
a < b
a == b
a > b
```

For example:

```text
20 < 50  → true
20 == 50 → false
20 > 50  → false
```

Ordering is particularly important when the search space is sorted.

---

**Binary Search Example**

Consider:

```text
A = [10, 20, 30, 40, 50, 60, 70]
```

Search for:

```text
target = 60
```

Initially:

```text
        mid
         ↓
[10, 20, 30, 40, 50, 60, 70]
                  ↑
```

We compare:

```text
A[mid] = 40
target = 60
```

Since:

```text
40 < 60
```

we know the target cannot be in:

```text
[10, 20, 30]
```

So we continue searching the right half:

```text
[50, 60, 70]
```

This is the power of ordering information.

---

#### Equality vs Ordering

| Comparison    | Question  | Main use            |
| ------------- | --------- | ------------------- |
| Equality      | `a == b`? | Exact match         |
| Less than     | `a < b`?  | Determine direction |
| Greater than  | `a > b`?  | Determine direction |
| Less/equal    | `a <= b`? | Bounds/ranges       |
| Greater/equal | `a >= b`? | Bounds/ranges       |

A useful way to remember this:

```text
Equality
    ↓
"Did I find it?"

Ordering
    ↓
"Where should I search?"
```

---

### Search Result

The **search result** specifies what the algorithm returns after searching.

A search algorithm does not necessarily return just `true` or `false`.

Possible results include:

```text
Found / Not Found
Index
Record
First occurrence
Last occurrence
All occurrences
Insertion position
Predecessor
Successor
Range
```

---

#### Boolean Result

The simplest search result is:
1. true or:
2. false

Example:

```text
contains(A, 25)
```

returns:

```text
true
```

if `25` exists.

---

#### Index Result

We might instead return the position:

```text
A = [10, 20, 30, 40]

target = 30
```

Result:

```text
index = 2
```

---

#### Record Result

For a collection of objects:

```text
findEmployee(105)
```

might return:

```text
Employee {
    id: 105,
    name: "Ahmed",
    salary: 30000
}
```

---

#### Why the Result Specification Matters

Consider:

```text
A = [10, 20, 20, 20, 30]
```

Search for:

```text
20
```

There are several valid interpretations.

We could return:

```text
2nd element
```

or:

```text
index 1
```

or:

```text
index 3
```

or:

```text
[1, 2, 3]
```

Therefore, **the desired result must be specified before choosing or implementing the algorithm**.

---

### First Occurrence

The **first occurrence** is the smallest index containing the target.

Consider:

```text
A = [10, 20, 20, 20, 30]
```

Search:

```text
target = 20
```

Matches occur at:

```text
1
2
3
```

Therefore:

```text
first occurrence = 1
```

---

#### Why First Occurrence Matters

Finding any occurrence is different from finding the first.

A normal Binary Search might find:

```text
index 2
```

but if the requirement is:

> Find the first `20`.

then returning `2` is not sufficient.

We must continue searching toward the left.

Conceptually:

```text
[10, 20, 20, 20, 30]
     ↑   ↑   ↑
     1   2   3

     ← continue left
```

This leads to the **lower-bound** style of binary searching.

---

#### First Occurrence Algorithm Idea

When Binary Search finds the target:

```text
if A[mid] == target:
    save mid
    continue searching left
```

Eventually:

```text
saved = first occurrence
```

This is typically:

```text
O(log n)
```

for a sorted array.

---

### Last Occurrence

The **last occurrence** is the largest index containing the target.

For:

```text
A = [10, 20, 20, 20, 30]
```

we have:

```text
20 occurs at:

1
2
3
```

Therefore:

```text
last occurrence = 3
```

---

#### Binary Search Idea

When we find:

```text
A[mid] == target
```

we save the position and continue searching toward the right:

```text
if A[mid] == target:
    save mid
    continue searching right
```

Eventually we obtain:

```text
last occurrence = 3
```

Again, for sorted data this can be done in:

```text
O(log n)
```

---

### All Occurrences

Sometimes we need **every position where the target occurs**.

Example:

```text
A = [10, 20, 20, 20, 30, 40]
```

Search:

```text
target = 20
```

Result:

```text
[1, 2, 3]
```

---

#### Simple Linear Search

The straightforward solution is to scan the entire array:

```text
for every element:
    if element == target:
        add index to result
```

Complexity:

```text
O(n)
```

because every element may need to be examined.

---

#### Sorted Data

If the array is sorted, we can use Binary Search to find:

```text
first occurrence
```

and:

```text
last occurrence
```

Then the matching range is:

```text
[first, last]
```

For:

```text
[10, 20, 20, 20, 30]
```

we get:

```text
first = 1
last  = 3
```

Therefore all matching indices are:

```text
1, 2, 3
```

This leads directly to the next concept.

---

### Insertion Position

The **insertion position** is the position where a new element should be inserted while maintaining sorted order.

Consider:

```text
A = [10, 20, 30, 40]
```

Insert:

```text
25
```

The correct position is:

```text
index = 2
```

because:

```text
[10, 20, 25, 30, 40]
          ↑
```

---

**What If the Target Already Exists?**

Consider:

```text
A = [10, 20, 20, 30]
```

Where should we insert another `20`?

There are two common conventions.

##### Lower bound

Insert before the first existing `20`:

```text
[10, 20, 20, 20, 30]
     ↑
   index 1
```

So:

```text
lower_bound(20) = 1
```

##### Upper bound

Insert after all existing `20`s:

```text
[10, 20, 20, 20, 30]
             ↑
           index 3
```

So:

```text
upper_bound(20) = 3
```

This distinction is extremely useful for implementing:

* first occurrence
* last occurrence
* range searches
* counting duplicates
* maintaining sorted collections

---

### Predecessor and Successor

These concepts are particularly useful when searching **ordered data**.

#### Predecessor

The **predecessor** of a value is the largest element that is **smaller than the target**.

Consider:

```text
A = [10, 20, 30, 40, 50]
```

Target:

```text
35
```

The predecessor is:

```text
30
```

because:

```text
30 < 35
```

and no larger element smaller than `35` exists.

---

#### Successor

The **successor** is the smallest element that is **greater than the target**.

For:

```text
A = [10, 20, 30, 40, 50]
```

and:

```text
target = 35
```

the successor is:

```text
40
```

because:

```text
40 > 35
```

and no smaller element greater than `35` exists.

---

#### Visual Representation

```text
10    20    30    40    50
                ↑
              target
               35
         │            │
         ↓            ↓
    predecessor    successor
         30            40
```

---

**What If the Target Exists?**

Suppose:

```text
A = [10, 20, 30, 40, 50]
target = 30
```

There are different definitions.

If predecessor means **strictly smaller**:

```text
predecessor = 20
```

If successor means **strictly greater**:

```text
successor = 40
```

Sometimes APIs define predecessor/successor differently, so the exact specification should be stated.

---

#### Why Are They Useful?

Predecessor and successor operations are common in:

* Binary Search Trees
* balanced search trees
* ordered sets
* ordered maps
* range queries
* scheduling
* nearest-value searches

For example:

> Find the largest price not exceeding `$100`.

This is essentially a predecessor-style search.

---

### Range of Matching Elements

The **range of matching elements** identifies the contiguous region containing all occurrences of a target in sorted data.

Consider:

```text
A = [10, 20, 20, 20, 30, 40]
```

Target:

```text
20
```

The matching elements occupy:

```text
        matching range
             ↓
[10, 20, 20, 20, 30, 40]
      └───────┘
       1      3
```

Therefore:

```text
first = 1
last  = 3
```

and the matching range is: [1, 3]

#### Using Lower and Upper Bounds

A particularly clean way to define the range is:

```text
first = lower_bound(target)
end   = upper_bound(target)
```

For:

```text
A = [10, 20, 20, 20, 30, 40]
```

we get:

```text
lower_bound(20) = 1
upper_bound(20) = 4
```

Notice that `upper_bound` returns the position **after** the final matching element.

Therefore:

```text
matching range = [1, 4)
```

This is a **half-open range**:

```text
1 ≤ index < 4
```

which corresponds to:

```text
indices: 1, 2, 3
values:  20, 20, 20
```

The number of occurrences can therefore be calculated very conveniently:

```text
count = upper_bound(target) - lower_bound(target)
```

Here:

```text
count = 4 - 1
      = 3
```

---

#### Summary

Let's use one example to connect all the concepts.

Consider the sorted array:

```text
A = [10, 20, 20, 20, 30, 40, 50]
```

and:

```text
target = 20
```

##### Input representation

```text
Sorted array
```

##### Search key

For a simple integer array:

```text
key = element itself
```

##### Search target

```text
20
```

##### Key comparison

We can perform:

```text
A[mid] == 20
A[mid] < 20
A[mid] > 20
```

##### Search result

Could be:

```text
Any occurrence → 2
```

or:

```text
First occurrence → 1
```

or:

```text
Last occurrence → 3
```

or:

```text
All occurrences → [1, 2, 3]
```

or:

```text
Insertion position
```

or:

```text
Matching range → [1, 4)
```

---

**The Important Relationship**

These concepts are not isolated. They build on each other:

```text
                 Search Problem Model
                         │
          ┌──────────────┴──────────────┐
          │                             │
   Input Representation          Search Specification
          │                             │
    ┌─────┴─────┐                 ┌─────┴──────────┐
    │           │                 │                │
 Records      Structure       Key + Target      Result
                                  │                │
                            ┌─────┴──────┐    ┌────┴─────────┐
                            │            │    │              │
                         Equality    Ordering  One match   Multiple
                                              │              │
                                      ┌───────┴───────┐      │
                                      │               │      │
                                    First           Last   All
                                      │               │      │
                                      └───────┬───────┘      │
                                              │              │
                                        Matching Range ──────┘
```

The key idea is:

> **A searching algorithm is defined not only by how it searches, but also by what information the search is required to return.**

For example, **Binary Search** is often introduced simply as "find an element in a sorted array," but the same basic idea can be adapted to find:

```text
Exact match
First occurrence
Last occurrence
Lower bound
Upper bound
Insertion position
Predecessor
Successor
Range of matches
```

That is why understanding the **search problem model first** makes the later searching algorithms much easier to understand.

## Search Strategies and Data Organization

Search performance depends not only on the search algorithm, but also on how the data is organized.

> **The way data is organized can have a major effect on how efficiently we can search it.**

A search algorithm doesn't operate in isolation. Its performance depends on the structure and organization of the collection being searched.

For example:

```text
Unorganized data
      ↓
C = [42, 17, 8, 93, 25, 61, 14]
      ↓
Linear Search
      ↓
O(n)
```
If we want to search for `25`, a simple **Linear Search** can examine elements one by one:

```text
42 → 17 → 8 → 93 → 25
                    ↑
                  found
```

This can require **O(n)** time.

But we could organize the data differently:

If we organize the same data:

```text
Sorted data
      ↓
C = [8, 14, 17, 25, 42, 61, 93]
      ↓
Binary Search
      ↓
O(log n)
```

Now the collection is **sorted**.

The ordering gives us additional information that a search algorithm can exploit.

For example, with **Binary Search**:

```text
[8, 14, 17, 25, 42, 61, 93]
             ↑
            25
```

We can eliminate approximately half of the remaining elements at each step.

The search becomes:

```text
O(log n)
```

instead of:

```text
O(n)
```

But organizing the data introduces additional costs, particularly when the collection changes.

---

### data organization techniques

For example:

```text
Unorganized collection
        ↓
[42, 17, 8, 93, 25, 61, 14]
        ↓
Linear Search
        ↓
O(n)
```

We could organize the same data as:

```text
Sorted collection
        ↓
[8, 14, 17, 25, 42, 61, 93]
        ↓
Binary Search
        ↓
O(log n)
```

Or we could use other data structures:

```text
Collection
   │
   ├── Sorted Array
   │      └── Binary Search
   │
   ├── Hash Table
   │      └── Hash-based lookup
   │
   ├── Binary Search Tree
   │      └── Tree-based search
   │
   └── Balanced Search Tree
          └── O(log n) search
```

So the **Searching Algorithms** chapter is not only about algorithms that scan data. It also considers how we can **organize the data to make queries faster**.

### Searching Without Data Organization

The simplest approach is to search the collection **without imposing any special organization on the data**.

For example:

```text
C = [42, 7, 91, 13, 25, 60]
```

There is no useful ordering.

If we search for `25`, we may have to examine:

```text
42 → 7 → 91 → 13 → 25
```

This is the situation where **Linear Search** is appropriate.

```text
Unorganized Collection
        ↓
   Linear Search
        ↓
      O(n)
```

**Why is this useful?**

Because there is no preprocessing requirement.

We can receive the data and immediately search it.

For example:

```text
insert elements
      ↓
search immediately
```

We don't need to sort or build another data structure first.

**Example**

Suppose a program receives:

```text
[17, 4, 92, 31, 8, 55]
```

and needs to determine whether `31` exists.

Linear Search can immediately process it.

#### Main characteristic

**Low organization cost, but potentially higher search cost.**

---

### Searching with Organized Data

Instead of leaving the collection arbitrary, we can organize it in a way that helps future searches.

For example:

```text
Unorganized:

[42, 7, 91, 13, 25, 60]
```

Organize it:

```text
[7, 13, 25, 42, 60, 91]
```

Now the search algorithm has additional information.

For example, with Binary Search, we can look at the middle:

```text
[7, 13, 25, 42, 60, 91]
          ↑
         42
```

If we're searching for `13`:

```text
13 < 42
```

Therefore, we know that everything to the right of `42` can be ignored.

```text
[7, 13, 25] | 42 | [60, 91]
     ↑
search here
```

This is the fundamental idea behind **Binary Search**.

Sorting is not free.

Suppose we start with:

```text
[42, 7, 91, 13, 25]
```

Before we can use Binary Search, we need to sort:

```text
[7, 13, 25, 42, 91]
```

That sorting operation itself requires time.

For example, a comparison-based sorting algorithm may require:

```text
O(n log n)
```

So if we only perform **one search**, sorting the entire collection may not be worthwhile.

We can think of the cost as:

```text
          Sorting
             ↓
       O(n log n)
             +
          Searching
             ↓
          O(log n)
```

versus simply:

```text
Linear Search
     ↓
    O(n)
```

For a single query, Linear Search can therefore be perfectly reasonable.


**The important principle**

```text
More organization
       ↓
More information about the data
       ↓
Search can eliminate possibilities
       ↓
Potentially faster queries
```

But:

```text
More organization
       ↓
More work to create/maintain that organization
```

That trade-off is central to data structures.

---

### Unsorted vs. Sorted Data

This compares the two basic situations.

#### Unsorted Data

Example:

```text
[42, 7, 91, 13, 25, 60]
```

There is no ordering that helps us determine where `25` might be.

We may need to examine every element.

```text
Linear Search → O(n)
```

---

#### Sorted Data

Example:

```text
[7, 13, 25, 42, 60, 91]
```

The ordering provides information.

If searching for `25`:

```text
           42
          /  \
       smaller larger
          ↓
     [7,13,25]
```

We can eliminate the larger portion.

```text
Binary Search → O(log n)
```

#### Comparison

| Property                  | Unsorted        | Sorted                      |
| ------------------------- | --------------- | --------------------------- |
| Organization              | None            | Ordered                     |
| Linear Search             | Yes             | Yes                         |
| Binary Search             | No              | Yes                         |
| Search cost               | O(n)            | O(log n) with Binary Search |
| Initial organization cost | Low             | Sorting required            |
| Update complexity         | Usually simpler | Can be more expensive       |

The key point is:

> **Sorted data makes more efficient searching possible, but maintaining the sorted order has a cost.**

### Preprocessing for Efficient Searching

**Preprocessing** means performing some work **before the actual search queries** in order to make future searches faster.

Suppose we receive:

```text
[42, 7, 91, 13, 25, 60]
```

Instead of immediately searching, we can preprocess it:

```text
Input data
    ↓
Preprocessing
    ↓
Organized data
    ↓
Many searches
```

For example:

```text
[42, 7, 91, 13, 25, 60]
            ↓
          sort
            ↓
[7, 13, 25, 42, 60, 91]
```

Then we can perform many Binary Searches.

**Why preprocessing can be worthwhile**
{/* Why Sorting Becomes Useful for Many Searches */}
Imagine:

```text
n = 1,000,000 elements
```

and we need:

```text
1,000,000 searches
```

Sorting once may be worthwhile because the resulting organization can be reused.

Conceptually:
```text
Unsorted data
     │
     │ sort once
     ↓
Sorted data
     │
     ├── search 1
     ├── search 2
     ├── search 3
     ├── ...
     └── search 1,000,000
```

The preprocessing cost is paid once and then reused.

This leads to an important distinction:

1. One-time cost

```text
Sorting → O(n log n)
```

2. Repeated benefit

```text
Each Binary Search → O(log n)
```

So the total cost can be attractive when the collection is searched frequently.

---

### Sorting as Search Preprocessing

Sorting is one of the simplest forms of preprocessing for searching.

Suppose:

```text
C = [50, 12, 87, 23, 4, 31, 65]
```

Before sorting:

```text
Search → Linear Search
       → O(n)
```

After sorting:

```text
[4, 12, 23, 31, 50, 65, 87]
```

Now:

```text
Search → Binary Search
       → O(log n)
```

But we must pay the sorting cost first.

For a comparison-based sorting algorithm such as Merge Sort:

```text
Sorting → O(n log n)
```

Then each Binary Search is:

```text
O(log n)
```

If we perform `q` searches, a simplified total cost is:

```text
O(n log n + q log n)
```

where:

* `n` = number of elements
* `q` = number of search queries

Without sorting and using Linear Search:

```text
O(qn)
```

So the choice depends heavily on how many queries we need to perform.

1. **One search**

```text
Sort + Binary Search
≈ O(n log n)

Linear Search
≈ O(n)
```

Sorting just to perform one search may not make sense.

2. **Many searches**

For many queries:

```text
Sort once
    +
many O(log n) searches
```

can be much more attractive from an algorithmic perspective.

### Search vs. Update Trade-offs

This is one of the most important concepts in this section.

A data structure is often optimized for **some operations at the expense of others**.

There are two broad categories:

```text
             Operations
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
     Queries             Updates
       │                   │
       ↓                   ↓
    Search              Insert
    Lookup              Delete
                        Modify
```

A sorted collection is optimized for certain queries, but maintaining the sorted order can make updates more expensive.

It helps to think of operations as two categories.
1. **Queries**

Operations that ask questions about the data:

```text
Does x exist?
Find x.
Find the value associated with x.
Find the minimum.
Find the maximum.
```
2.  **Updates**

Operations that modify the data:

```text
Insert x.
Delete x.
Modify x.
```

A sorted collection may give us:

```text
             Sorted Collection
                    │
        ┌───────────┴───────────┐
        ↓                       ↓
     Queries                  Updates
        │                       │
        ↓                       ↓
     Faster                  Potentially
     search                  more expensive
```

For example:

```text
Sorted array:

[10, 20, 30, 40, 50]
```

Searching can be fast with Binary Search.

But inserting `25` requires:

```text
[10, 20, 30, 40, 50]
        ↓
shift elements
        ↓
[10, 20, 25, 30, 40, 50]
```

Deletion Has the Same Problem

Suppose:

```text
[10, 20, 25, 30, 40, 50]
```

We delete `25`.

We need:

```text
[10, 20, 30, 40, 50]
```

In an array, elements after `25` may need to move:

```text
25 30 40 50
   ↓  ↓  ↓
30 40 50
```

So although searching is efficient, modifying the collection can be expensive.

Therefore:

```text
Fast Search
     ↕
More Expensive Updates
```

This is the **search/update trade-off**.

This paragraph is introducing one of the most important concepts in data structures:

```text
             Data Organization
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
      Fast Search        Easy Updates
          │                   │
          ↓                   ↓
   More organization     Less organization
          │                   │
          ↓                   ↓
     More maintenance    Simpler updates
```

A data structure optimized for searching may not be optimized for insertion and deletion.

---

### Query/Update Trade-offs
#### Search Cost

**Search cost** measures the computational work required to answer a search query.

Typical examples:

- Linear Search

```text
O(n)
```

2. Binary Search

```text
O(log n)
```

3. Hash Table

Average-case lookup can be approximately:

```text
O(1)
```

depending on the hash table's implementation and load conditions.

4. Search Tree

A balanced search tree typically provides:

```text
O(log n)
```

search.

So:

```text
Data Organization
       ↓
Search Strategy
       ↓
Search Complexity
```

---

#### Insertion Cost

**Insertion cost** measures how much work is required to add an element.

Consider:

```text
[10, 20, 30, 40, 50]
```

Insert:

```text
25
```

To preserve order:

```text
[10, 20, 25, 30, 40, 50]
```

In an array, some elements may have to move.

Therefore, maintaining sorted order can make insertion more expensive.

Compare that with an unsorted array:

```text
[10, 20, 30, 40, 50]
```

We could simply append:

```text
[10, 20, 30, 40, 50, 25]
```

Insertion may be simpler, but now searching loses the benefit of sorted order.

---

#### Deletion Cost

Deletion can have a similar problem.

Suppose:

```text
[10, 20, 25, 30, 40, 50]
```

Delete `25`.

The resulting array should be:

```text
[10, 20, 30, 40, 50]
```

Elements after `25` may need to shift.

Thus:

```text
Sorted Array
     ↓
Efficient Search
     +
Potentially expensive insertion/deletion
```

Again, this illustrates the trade-off.

---

#### Maintenance Cost

**Maintenance cost** is the ongoing work required to keep a data structure in the form that makes searching efficient.

For a sorted collection:

```text
Insert
   ↓
restore sorted order

Delete
   ↓
preserve sorted order

Update
   ↓
possibly reposition element
```

So the collection cannot simply be changed arbitrarily.

**Example**

Suppose:

```text
[10, 20, 30, 40, 50]
```

Change:

```text
30 → 60
```

If we simply modify it:

```text
[10, 20, 60, 40, 50]
```

the collection is no longer sorted.

We need to restore the ordering:

```text
[10, 20, 40, 50, 60]
```

The maintenance cost is therefore part of the overall cost of choosing an organized data structure.

---

### Static vs. Dynamic Collections

This distinction is very important when deciding whether preprocessing is worthwhile.

#### Static Collection

A **static collection** does not change, or changes very rarely, after it has been prepared.

For example:

```text
Database of country codes
```

could be loaded once:

```text
Load data
   ↓
Sort / organize
   ↓
Many searches
```

Since the data rarely changes, preprocessing can be very useful.

```text
          Prepare once
               ↓
       ┌───────┴───────┐
       ↓               ↓
   Search 1         Search 2
       ↓               ↓
      ...             ...
```

---

#### Dynamic Collection

A **dynamic collection** frequently changes.

For example:

```text
Online shopping inventory
```

might continuously receive:

```text
Insert product
Delete product
Update product
Search product
```

If we use a sorted structure, every modification may require maintaining the organization.

```text
Insert
   ↓
maintain organization

Delete
   ↓
maintain organization

Update
   ↓
maintain organization
```

Therefore, the best structure for a dynamic collection may differ from the best structure for a static collection.

---

#### Static vs. Dynamic

| Property      | Static Collection | Dynamic Collection              |
| ------------- | ----------------- | ------------------------------- |
| Insertions    | Rare              | Frequent                        |
| Deletions     | Rare              | Frequent                        |
| Searches      | Often many        | Mixed with updates              |
| Preprocessing | Often worthwhile  | May need continuous maintenance |
| Sorting once  | Very useful       | May become expensive            |
| Main concern  | Query performance | Query/update balance            |

This is an important reason why **Binary Search on a sorted array** isn't always the universal solution to searching.

2. **Method 2 — Books alphabetically ordered**

#### Factor 5: How Many Elements Are Inspected?

The real cost of a search is strongly related to how many elements the algorithm must inspect, but the total cost also includes the work required to organize and maintain the collection.

Suppose we have:

```text

```

Searching for `42` with Sequential/Linear Search might inspect:

```text

```

So it inspects 4 elements.

For a different target:

```text

```

it may inspect all 7:

```

Therefore, the basic cost of Sequential Search is related to:

```text

```

This gives:

```text

      ↓

      ↓
O(n)
```

Other algorithms reduce the number of elements that need to be inspected.

For example:

```text
Binary Search
      ↓
Eliminates approximately half
of the remaining elements
      ↓
O(log n)
```

A hash table can often go directly to a small number of candidate locations:

```text
Hash Search
      ↓
Average-case lookup ≈ O(1)
```

Use the following guide to select the best algorithm for you:

##### Small Collections

Sequential Search offers the simplest implementation and is implemented as a
basic construct in many programming languages. Use this algorithm when the
collection is available only sequentially, as with an iterator.

This corresponds directly to **Linear Search**.

Suppose:

```text
C = [18, 42, 7, 31, 15]
```

For a small collection, the simplicity of:

```c
for (int i = 0; i < n; i++) {
    if (A[i] == key)
        return i;
}
```

can be more important than introducing a more complicated data structure. Why?
Because with a small `n`, even `O(n)` may involve very little work.

For example: n = 10, Scanning at most 10 elements is trivial, You don't necessarily need:

```text
sorting
hash table
binary search tree
index
```

just to search ten elements.

---
 
**Sequential Access**

An **iterator** typically gives you elements one at a time:

```text
iterator
   ↓
element 1
   ↓
element 2
   ↓
element 3
   ↓
...
```

You cannot necessarily jump directly to element 500.

Therefore, Linear Search is a natural fit:

```text
Iterator
   ↓
next()
   ↓
compare
   ↓
next()
   ↓
compare
```

This is one reason Linear Search is useful beyond arrays.

---

##### Restricted Memory

When the collection is an array that doesn't change and you want to conserve memory, use Binary Search.

An array gives efficient indexed access:

```text
A[0]
A[1]
A[2]
...
```

Binary Search can use that to repeatedly access the middle element.

For:

```text
[5, 12, 18, 27, 35, 42, 50]
```

searching for `42`:

```text
             27
            /  \
       smaller larger
                   ↓
             [35,42,50]
                  ↓
                  42
```

The search requires only:

```text
O(log n)
```

comparisons.

**Why "restricted memory"?** Binary Search on an array can be implemented **in place**. It only needs a few variables:

```text
low
high
mid
```

So auxiliary memory is: O(1)

For example:

```c
int binarySearch(int A[], int n, int key) {
    int low = 0;
    int high = n - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;

        if (A[mid] == key)
            return mid;

        if (A[mid] < key)
            low = mid + 1;
        else
            high = mid - 1;
    }

    return -1;
}
```

No additional tree or hash-table structure is required.

---

**Why "doesn't change"?**

This is particularly important. Binary Search requires: "sorted array", If the array is static:

```text
Sort once
   ↓
Keep sorted
   ↓
Perform many searches
```

There is little maintenance cost.

So a static sorted array is an excellent environment for Binary Search.

---

##### Dynamic Membership

If the elements in the collection **change frequently**, consider Hash-Based
Search and Binary Search Tree for their ability to spread out the costs associated with maintaining their data structures

This is where the earlier **search vs. update trade-off** becomes important.

Suppose our collection changes continuously:

```text
insert
delete
insert
update
search
delete
insert
search
...
```

A sorted array can become inconvenient because maintaining its order can require moving elements.

For example:

```text
[10, 20, 30, 40, 50]
```

Insert `25`:

```text
[10, 20, 25, 30, 40, 50]
```

Elements need to move.

Instead, we can use structures specifically designed for dynamic collections
1. (Hash-Based Search), A **Hash Table** organizes elements using a hash function.

Conceptually:

```text
key
 ↓
hash function
 ↓
index
 ↓
bucket
```

For example:

```text
"apple"
   ↓
hash("apple")
   ↓
index 7
   ↓
bucket[7]
```

This allows direct-looking lookup rather than scanning the entire collection.

Typical average-case performance:

```text
Search      ≈ O(1)
Insert      ≈ O(1)
Delete      ≈ O(1)
```

These are average-case expectations and depend on the implementation, hashing quality, load factor, and collision handling.

**Why useful for dynamic membership?**

Because a hash table is designed to support:

```text
insert
delete
search
```

without requiring the entire collection to remain sorted.

2. Binary Search Tree

A **Binary Search Tree (BST)** organizes elements according to their ordering relationship.

For example:

```text
          40
         /  \
       20    60
      / \    / \
    10  30  50  70
```

The BST property is:

```text
left subtree < node < right subtree
```

This organization supports searching while also maintaining ordering information.

For a balanced tree:

```text
Search ≈ O(log n)
Insert ≈ O(log n)
Delete ≈ O(log n)
```

But an important qualification is necessary: Ordinary BST, A normal BST can become unbalanced:

```text
10
  \
   20
     \
      30
        \
         40
```

Then its height can become `O(n)`.

Therefore:

```text
Ordinary BST
Worst-case search = O(n)
```

Balanced search trees such as AVL trees and Red-Black trees are designed to maintain logarithmic height.

---

**Why Hash Tables and BSTs Are Different**

Both can support dynamic membership, but they provide different capabilities.

| Feature                | Hash Table           | Binary Search Tree   |
| ---------------------- | -------------------- | -------------------- |
| Exact lookup           | Excellent            | Good                 |
| Average search         | O(1)                 | O(log n) if balanced |
| Maintains sorted order | No                   | Yes                  |
| Ordered traversal      | No natural ordering  | Yes                  |
| Range queries          | Not naturally suited | Well suited          |
| Dynamic insertion      | Yes                  | Yes                  |
| Dynamic deletion       | Yes                  | Yes                  |

This distinction leads directly to the next recommendation.

---

##### Sorted Access

Use Binary Search Tree when you need **dynamic membership** and the **ability to process elements in the collection in sorted order**.

This is an important distinction. Suppose you need both:

```text
1. Search for a particular element
2. Process all elements in sorted order
```

A Hash Table is not naturally designed for the second requirement.

Consider:

```text
Hash Table:

bucket 0 → 42
bucket 1 → 7
bucket 2 → 91
bucket 3 → 18
...
```

The elements are organized according to hash values, **not according to their natural ordering**.

If you want:

```text
7
18
42
91
...
```

you would need additional work. A BST, however, inherently maintains ordering.

In-Order Traversal Gives Sorted Order

Consider:

```text
          40
         /  \
       20    60
      / \    / \
    10  30  50  70
```

Perform **in-order traversal**:

```text
Left → Root → Right
```

Result:

```text
10 → 20 → 30 → 40 → 50 → 60 → 70
```

So a BST provides two useful properties:

```text
BST
 │
 ├── Search by key
 │
 ├── Insert/Delete dynamically
 │
 └── Process elements in sorted order
```

That is exactly why the passage recommends a BST when **dynamic membership + sorted access** are both required.

---

#### Factor 6: Upfront Preprocessing

Don't forget to account for any upfront preprocessing required by the algorithm This means we shouldn't look only at **search complexity**, We should consider the **entire lifecycle** of the collection.

For example, suppose we have an unsorted array:

```text
[42, 7, 91, 13, 25]
```

and decide to use Binary Search. We cannot immediately do that.

First:

```text
Unsorted
   ↓
Sorting
   ↓
[7, 13, 25, 42, 91]
   ↓
Binary Search
```

So the real cost includes:

```text
Preprocessing + Searches
```

not just:

```text
Search
```

---

**Total Cost of Searching**

Suppose:

* `n` = number of elements
* `q` = number of queries

With Linear Search:

```text
q searches × O(n)

= O(qn)
```

With sorting + Binary Search:

```text
Sorting
   +
q Binary Searches

= O(n log n) + O(q log n)
```

So we should not simply say: "Binary Search is faster than Linear Search."

The more accurate question is: **What is the total cost of preparing, maintaining, and querying the collection?**

#### Summary
Compare the three searching techniques we've covered:

```text
Linear Search
    ↓
No organization required
    ↓
O(n)
```

```text
Binary Search
    ↓
Requires sorted sequential data
    ↓
Eliminate half
    ↓
O(log n)
```

```text
BST Search
    ↓
Requires BST ordering
    ↓
Follow one tree path
    ↓
O(h)
    ↓
O(log n) if balanced
```

And:

```text
Hash-Based Search
    ↓
Requires hash-based organization
    ↓
Jump to bucket
    ↓
O(1) expected
```

So the broader idea behind your **Searching** chapter becomes:

```text
                         Searching
                             │
       ┌─────────────────────┼─────────────────────┐
       ↓                     ↓                     ↓
 Linear Search         Comparison Search       Hash-Based
       │                     │                     │
      O(n)                   │                  O(1) expected
                             │
                    ┌────────┴────────┐
                    ↓                 ↓
              Binary Search       Tree Search
                    │                 │
                  O(log n)            │
                                      ↓
                                    BST
                                      │
                                    O(h)
                                      │
                              ┌───────┴───────┐
                              ↓               ↓
                          balanced        skewed
                          O(log n)          O(n)
```

Use this decision table:

| Situation                                 | Suitable approach          | Main reason                    |
| ----------------------------------------- | -------------------------- | ------------------------------ |
| Small collection                          | Linear Search              | Simplicity                     |
| Sequential access                         | Linear Search              | Can only move sequentially     |
| Static sorted array                       | Binary Search              | Fast search + low extra memory |
| Memory constrained                        | Binary Search on array     | O(1) auxiliary space           |
| Frequently changing membership            | Hash Table                 | Efficient dynamic lookup       |
| Frequently changing membership + ordering | Search Tree                | Dynamic updates + ordering     |
| Need sorted traversal                     | Binary Search Tree         | Maintains ordered structure    |
| Many searches, few updates                | Preprocess + Binary Search | Amortize preprocessing         |
| Many searches + many updates              | Dynamic search structure   | Balance query/update costs     |

---

The Most Important Lesson: **asymptotic search complexity alone is not enough to choose an algorithm**. You should evaluate:

```text
                    Search Strategy
                          │
          ┌───────────────┼────────────────┐
          ↓               ↓                ↓
      Query Cost      Preparation Cost   Update Cost
          │               │                │
          ↓               ↓                ↓
       Search         Sorting/Indexing   Insert/Delete
```

And for a real application:

```text
                    Total Cost
                        =
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
   Preprocessing    Query Cost      Maintenance
        │               │               │
        ↓               ↓               ↓
      Sort          Search          Insert/Delete
      Build index   Lookup          Rebalance
      Build tree    Queries         Rehash
```

Therefore, the correct question is not simply: **"Which searching algorithm is fastest? it is: **"Which search strategy gives the lowest overall cost for the way this collection is accessed and modified?"**

That is the key concept connecting **Linear Search → Binary Search → Hash Tables → Binary Search Trees** in your Searching Algorithms chapter.


### The Key Concept


```text
                    SEARCHING
                        │
                        ↓
             How is the data organized?
                        │
             ┌──────────┴──────────┐
             ↓                     ↓
         Unorganized            Organized
             │                     │
             ↓                     ↓
       Linear Search       Sorted / Indexed /
             │             Hash-based / Tree
             ↓                     │
           O(n)                    ↓
                             Faster queries
                                   │
                                   ↓

                                   │

                 Insert          Delete        Maintain
```
We can improve search performance by organizing the data, but that organization itself costs time and may make insertions and deletions more expensive.
This gives us a fundamental data-structure design question:

```text
                    What do we optimize?
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
           Search        Insert        Delete
             │             │             │
             ↓             ↓             ↓
         Fast queries   Fast updates   Fast updates
```
There is usually **no single organization that is optimal for every operation**.

That is why the Searching Algorithms chapter goes beyond **Linear Search** and **Binary Search** and eventually studies structures such as **search trees and hash tables**.

Searching is not just about "how do I find an element?It is also: **How should I organize my data so that the kinds of searches I perform become efficient, while keeping the cost of insertion, deletion, and maintenance acceptable?**
