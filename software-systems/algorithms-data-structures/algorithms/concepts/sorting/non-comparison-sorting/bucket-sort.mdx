**Bucket Sort** is a **non-comparison sorting algorithm** that sorts elements by first **distributing them into a number of buckets**, then sorting the elements inside each bucket, and finally concatenating the buckets.

Bucket Sort works by distributing elements into different **buckets**.

The central idea is:

> Instead of comparing every element with every other element, use the **value of an element to determine where it belongs**.

Given a set of n elements, Bucket Sort constructs a set of n ordered buckets into which the elements of the input set are partitioned; Bucket Sort reduces its processing costs at the expense of this extra space. If a hash function, hash(A[i]), can uniformly partition the input set of n elements into these n buckets, Bucket Sort can sort, in the worst case, in O(n) time.

Suppose we have values between: 0.0 and 1.0

Input:

```text
0.12
0.67
0.23
0.89
0.45
0.31
0.76
```

We could create:

```text
Bucket 0 → [0.12]
Bucket 1 → [0.23]
Bucket 2 → [0.31]
Bucket 3 → [0.45]
Bucket 4 → [0.67]
Bucket 5 → [0.76]
Bucket 6 → [0.89]
```

Then sort each bucket individually.

Finally concatenate them:

```text
[0.12, 0.23, 0.31, 0.45, 0.67, 0.76, 0.89]
```
## How Bucket Sort Works

General process:

```text
Input
  │
  ▼
Distribute elements into buckets
  │
  ├── Bucket 0
  ├── Bucket 1
  ├── Bucket 2
  ├── ...
  └── Bucket k
          │
          ▼
     Sort each bucket
          │
          ▼
       Concatenate
          │
          ▼
        Output
```

Once all elements to be sorted are inserted into the buckets, Bucket Sort extracts the values from left to right using Insertion Sort on the contents of each bucket. This orders the elements in each respective bucket as the values from the buckets are extracted from left to right to repopulate the original array. An example execution is shown in Figure

Unlike Counting Sort, buckets generally represent **ranges** rather than individual values.

For example:

```text
0.0 ─ 0.1 → Bucket 0
0.1 ─ 0.2 → Bucket 1
0.2 ─ 0.3 → Bucket 2
...
```

## Why Is Bucket Sort a Non-Comparison Sort?

Consider:

```text
[0.42, 0.12, 0.89, 0.33, 0.71]
```

A comparison-based algorithm might ask:

```text
Is 0.42 < 0.12?
Is 0.42 < 0.89?
...
```

Bucket Sort instead uses the **value itself** to determine a bucket.

For example, divide the range `[0, 1)` into five buckets:

```text
Bucket 0 → [0.0, 0.2)
Bucket 1 → [0.2, 0.4)
Bucket 2 → [0.4, 0.6)
Bucket 3 → [0.6, 0.8)
Bucket 4 → [0.8, 1.0)
```

Then:

```text
0.12 → Bucket 0
0.33 → Bucket 1
0.42 → Bucket 2
0.71 → Bucket 3
0.89 → Bucket 4
```

The algorithm has already established the **relative order between buckets** without comparing the elements.

## The Three Main Steps

Bucket Sort has three fundamental phases:

```text
1. Create buckets
        ↓
2. Distribute elements
        ↓
3. Sort and concatenate
```

Let's examine each carefully.

---

### Step 1 — Create the Buckets

Suppose we have: `n = 10` elements.

A common implementation creates approximately `n` buckets:

```text
B[0]
B[1]
B[2]
...
B[n-1]
```

Each bucket is usually represented by a dynamic list/vector.

For example:

```text
vector<vector<double>> buckets(n);
```

Conceptually:

```text
buckets
│
├── bucket[0]
├── bucket[1]
├── bucket[2]
├── ...
└── bucket[n-1]
```

The number of buckets is not necessarily required to equal `n`; it is a design choice.

---

### Step 2 — Determine the Bucket

This is the most important part. We need a **bucket-index function**: $B(x)$, that maps an element `x` to a bucket.

For values in: $[0,1)$, with `n` buckets, a common mapping is:
{/* index=⌊nx⌋ */}
$$
index = \lfloor n x \rfloor
$$

For example, with:

$$
n=10
$$

we get:

```text
x       floor(10x)       bucket
--------------------------------
0.12       1              B1
0.26       2              B2
0.39       3              B3
0.68       6              B6
0.72       7              B7
0.94       9              B9
```

Notice something important:

```text
0.12 < 0.26 < 0.39
```

and therefore:

```text
B1 < B2 < B3
```

The bucket positions encode part of the ordering.

---

### Step 3 — Sort Each Bucket

After distribution:

```text
B1 → [0.17, 0.12]

B2 → [0.26, 0.21, 0.23]

B7 → [0.78, 0.72]
```

Each bucket still needs to be sorted.

We can use:

* Insertion Sort
* Quick Sort
* Merge Sort
* another appropriate sorting algorithm

Insertion Sort is particularly common in textbook implementations because buckets are expected to be small.

For example:

```text
B2 = [0.26, 0.21, 0.23]
```

becomes:

```text
[0.21, 0.23, 0.26]
```

---

### Step 4 — Concatenate the Buckets

Finally:

```text
B0
B1
B2
B3
...
Bn-1
```

are concatenated.

For example:

```text
B1 → [0.12, 0.17]
B2 → [0.21, 0.23, 0.26]
B3 → [0.39]
B6 → [0.68]
B7 → [0.72, 0.78]
B9 → [0.94]
```

gives:

```text
[0.12, 0.17, 0.21, 0.23, 0.26, 0.39, 0.68, 0.72, 0.78, 0.94]
```

## Pesudocode

```text
sort (A)
    create n buckets B
    for i = 0 to n-1 do (1)
        k = hash(A[i])
        add A[i] to the k-th bucket B[k]
    extract (B, A) (2)
end
extract (B, A)
    idx = 0
    for i = 0 to n-1 do
        insertionSort (B[i]) (3)
        foreach element e in B[i] (4)
            A[idx++] = e
end
```
1. Create bucket list and hash all elements to proper bucket.
2. Process all buckets to extract values back into A in sorted order.
3. If more than one element in bucket, sort first.
4. Copy elements back into proper position in A.

## Why Does Bucket Sort Work?

This is the key idea behind the algorithm.

Suppose:

```text
B2 = [0.21, 0.26, 0.23]
B3 = [0.31, 0.39]
```

Every element in `B2` is less than every element in `B3`. Why? Because:

```text
B2 → [0.2, 0.3)
B3 → [0.3, 0.4)
```

Therefore:
{/* x∈B2​,y∈B3 */}
$$
x \in B_2,\quad y \in B_3
$$

implies:

$$
x < y
$$

So we **do not need to compare elements between buckets**.

We only need to sort elements **inside the same bucket**.

This is the fundamental reason Bucket Sort can be efficient.

---

## Bucket Sort Is Not Completely "Comparison-Free"

This is an important subtlety.

The **distribution phase** can be performed without comparing elements against each other.

But the algorithm usually performs comparisons when sorting each bucket.

For example:

```text
Bucket:
[0.26, 0.21, 0.23]
```

If we use Insertion Sort:

```text
0.21 < 0.26
0.23 < 0.26
```

Those are comparisons.

So why is Bucket Sort called a **non-comparison sorting algorithm**?

Because its efficiency comes from using the key's value to perform the major global ordering/distribution rather than relying entirely on pairwise comparisons.

The internal bucket sorting can itself be comparison-based.

This distinction is particularly important when studying sorting theory.

## Distribution Assumption
Bucket Sort becomes efficient when the input is **reasonably uniformly distributed** across the buckets.

Consider:

```text
[0.05, 0.12, 0.18, 0.22, 0.31, 0.42, 0.53, 0.67, 0.74, 0.91]
```

Distribution might look like:

```text
B0 → [0.05]
B1 → [0.12, 0.18]
B2 → [0.22]
B3 → [0.31]
B4 → [0.42]
B5 → [0.53]
B6 → [0.67]
B7 → [0.74]
B8 → []
B9 → [0.91]
```

Most buckets contain only a few elements.

That's excellent for Bucket Sort.

---

### Worst-Case Distribution

Now consider:

```text
[0.51, 0.52, 0.53, 0.54, 0.55, 0.56, 0.57, 0.58, 0.59, 0.60]
```

Depending on the bucket configuration, many elements may end up together.

For example:

```text
B5 → [0.51, 0.52, 0.53, 0.54, 0.55,
      0.56, 0.57, 0.58, 0.59]
```

Now the bucket contains almost all the input.

So instead of:

```text
many small sorting problems
```

we effectively have:

```text
one large sorting problem
```

If that bucket is sorted with Insertion Sort, its cost can become:

$$
O(n^2)
$$

Therefore:

$$
\text{"Bucket Sort worst case can be "} O(n^2)
$$



### Average-Case Complexity

Let's derive the usual average-case intuition.

Suppose:

* \(n\) elements
* \(k\) buckets

and the elements are approximately uniformly distributed.

Then the expected number of elements per bucket is:

$$
\frac{n}{k}
$$

If we use Insertion Sort inside each bucket, sorting one bucket costs approximately:

$$
O\left(\left(\frac{n}{k}\right)^2\right)
$$

Across \(k\) buckets:

$$
k \cdot O\left(\frac{n^2}{k^2}\right)
$$

which simplifies to:

$$
O\left(\frac{n^2}{k}\right)
$$

If:

$$
k \approx n
$$

then:

$$
O\left(\frac{n^2}{n}\right)
=
O(n)
$$

Add the cost of distribution:

$$
O(n)
$$

and concatenation:

$$
O(n)
$$

giving:

$$
\boxed{O(n)}
$$

expected time under suitable distribution assumptions.

## Complexity


**why Bucket Sort is expected to run in \(O(n)\) time**, even though it uses **Insertion Sort**, which can take \(O(n^2)\).

The key idea is:

> We don't need every bucket to contain one element. We only need the **total expected cost of sorting all buckets** to be \(O(n)\).

Let's go through the argument step by step.

Suppose we have:

* \(n\) input elements
* \(n\) buckets
* values uniformly distributed in \([0,1)\)

For example:

```text
Input:
0.78  0.17  0.39  0.26  0.72
```

With 5 buckets:

```text
B0   [0.0, 0.2)
B1   [0.2, 0.4)
B2   [0.4, 0.6)
B3   [0.6, 0.8)
B4   [0.8, 1.0)
```

The important property is:

```text
B0 < B1 < B2 < B3 < B4
```

Meaning every value in `B0` is smaller than every value in `B1`, etc.

Therefore, after sorting each individual bucket, we can simply concatenate:

```text
sorted B0
    ↓
sorted B1
    ↓
sorted B2
    ↓
...
```

No comparisons between buckets are necessary.

---

**Distributing elements costs O(n)**

The `sortPointers()` function goes through every element once:

```text
for each element:
    determine bucket
    insert element into bucket
```

There are \(n\) elements.

Therefore:

$$
T_{distribution} = O(n)
$$

So far, everything is straightforward.

The interesting question is:

> **How expensive is it to sort all the individual buckets?**

**Define \(n_i\)**

Let $n_i$ be the number of elements that ended up in bucket \(i\).

For example, suppose we have 10 elements:

```text
B0:  2 elements
B1:  0 elements
B2:  1 element
B3:  3 elements
B4:  1 element
B5:  0 elements
B6:  2 elements
B7:  1 element
B8:  0 elements
B9:  0 elements
```

Then:

```text
n0 = 2
n1 = 0
n2 = 1
n3 = 3
...
```

Since there are \(n\) buckets:

$$
n_0+n_1+\cdots+n_{n-1}=n
$$

This equation is always true.

**Why is the expected value of \(n_i\) equal to 1?**

This is the most important part.

There are \(n\) elements and \(n\) buckets.

Because the values are uniformly distributed, each element has probability

$$
p=\frac{1}{n}
$$

of landing in a particular bucket.

For a particular bucket \(B_i\):

```text
Element 1 → probability 1/n
Element 2 → probability 1/n
Element 3 → probability 1/n
...
Element n → probability 1/n
```

Therefore, the expected number of elements in that bucket is:

$$
E[n_i] = n \times \frac{1}{n}
$$

so:

$$
\boxed{E[n_i]=1}
$$

In plain English:

> **On average, each bucket contains one element.**

But **average = 1 does NOT mean every bucket contains exactly one element**.

For example:

```text
Bucket:  B0 B1 B2 B3 B4 B5
Size:     0  2  1  3  0  0
```

The average can still be 1.

That's why we need variance.

---

**Why do we care about variance?**

Insertion Sort has a cost related to the **square of the number of elements** in the bucket.

For a bucket containing \(k\) elements:

$$
T_{InsertionSort}(k)=O(k^2)
$$

So:

```text
bucket size       sorting cost
--------------------------------
0                 0
1                 1
2                 4
3                 9
4                16
10               100
100            10,000
```

Therefore, we cannot simply say:

> "Each bucket has an expected size of 1, so sorting is O(1)."

That's not enough.

We need to determine the expected value of:

$$
n_i^2
$$

because that's what controls the sorting cost.

---

**Variance tells us how spread out the bucket sizes are**

For a binomial random variable:

$$
Var[n_i] = np(1-p)
$$

We have:

$$
p=\frac1n
$$

Therefore:

$$
Var[n_i]
=
n\left(\frac1n\right)
\left(1-\frac1n\right)
$$

Simplifying:

$$
Var[n_i]=1-\frac1n
$$

So the variance is approximately:

$$
1
$$

when \(n\) is large.

This tells us that the bucket sizes don't become wildly large under the uniform-distribution assumption.

---

{/* <!-- The important identity --> */}

Now we use:

$$
Var(X)=E[X^2]-(E[X])^2
$$

Rearrange it:

$$
E[X^2]=Var(X)+(E[X])^2
$$

For our bucket:

$$
X=n_i
$$

Therefore:

$$
E[n_i^2]
=
Var[n_i]+(E[n_i])^2
$$

We already know:

$$
Var[n_i]=1-\frac1n
$$

and:

$$
E[n_i]=1
$$

Therefore:

$$
E[n_i^2]
=
\left(1-\frac1n\right)+1^2
$$

so:

$$
E[n_i^2]=2-\frac1n
$$

For large \(n\):

$$
E[n_i^2]\approx2
$$

The crucial observation is:

$$
\boxed{E[n_i^2]=O(1)}
$$

In other words:

> The expected squared size of an individual bucket is **constant**.

Var(X) = E(X^2) - [E(X)]^2

---

**Now consider ALL buckets**

This is the part that gives us \(O(n)\).

There are \(n\) buckets.

For each bucket:

$$
E[n_i^2]=O(1)
$$

Insertion Sort on bucket \(i\) costs:

$$
O(n_i^2)
$$

Therefore the expected total cost is:

$$
E\left[\sum_{i=0}^{n-1}n_i^2\right]
$$

By linearity of expectation:

$$
=
\sum_{i=0}^{n-1}E[n_i^2]
$$

Each term is \(O(1)\):

$$
=
O(1)+O(1)+\cdots+O(1)
$$

There are \(n\) terms:

$$
\boxed{O(n)}
$$

That's the central argument.

---

**A concrete example**

Imagine 10 elements distributed like this:

```text
Bucket       Number of elements
--------------------------------
B0                    1
B1                    0
B2                    2
B3                    1
B4                    3
B5                    0
B6                    1
B7                    1
B8                    1
B9                    0
```

The bucket sizes are:

```text
1, 0, 2, 1, 3, 0, 1, 1, 1, 0
```

Insertion Sort costs approximately:

```text
1² + 0² + 2² + 1² + 3² + 0² + 1² + 1² + 1² + 0²
```

which is:

```text
1 + 0 + 4 + 1 + 9 + 0 + 1 + 1 + 1 + 0
= 18
```

The total is still proportional to \(n\), rather than \(n^2\).

The expensive bucket `B4` containing 3 elements doesn't destroy the overall performance.

---

**Why don't we just say every bucket has one element?**

Because that would be wrong.

Consider:

```text
n = 10
```

We might get:

```text
0 0 0 0 0 0 0 0 0 10
```

Then:

$$
E[n_i]
$$

for this particular distribution is still 1 **as an average across buckets**, but sorting the last bucket costs:

$$
10^2=100
$$

For a sufficiently bad distribution, one bucket could contain almost everything:

```text
0 0 0 0 0 ... 0 n
```

and then:

$$
T=O(n^2)
$$

Therefore, Bucket Sort's \(O(n)\) claim depends on the **distribution assumption**.

---

**The hidden assumption: uniform distribution**

This is extremely important.

The analysis assumes the input values are approximately **uniformly distributed over \([0,1)\)**.

For example:

```text
0.03
0.14
0.27
0.32
0.41
0.58
0.63
0.72
0.81
0.95
```

is reasonably distributed.

But this:

```text
0.51
0.51
0.50
0.52
0.51
0.50
0.51
0.52
0.50
0.51
```

is not.

Most values would land in the same bucket:

```text
B0   B1   B2   B3   B4   B5   B6   B7   B8   B9
 0    0    0    0    0   10    0    0    0    0
```

Then we effectively have:

```text
Insertion Sort(10 elements)
```

which costs:

$$
O(10^2)
$$

and generally:

$$
\boxed{O(n^2)}
$$

---

**Putting the complete analysis together**

Bucket Sort has three major stages.

1. Stage 1 — Create buckets

```text
create n buckets
```

Cost: $O(n)$

2. Stage 2 — Distribute elements

```text
for each element:
    calculate bucket
    insert into bucket
```

Cost: $O(n)$

3. Stage 3 — Sort individual buckets

Bucket \(i\) contains \(n_i\) elements.

Insertion Sort costs:

$$
O(n_i^2)
$$

Across all buckets:

$$
O\left(\sum_{i=0}^{n-1}n_i^2\right)
$$

Under the uniform-distribution assumption:

$$
E[n_i^2]=O(1)
$$

Therefore:

$$
E\left[\sum_{i=0}^{n-1}n_i^2\right]
=
O(n)
$$

So:

$$
T(n)
=
O(n)+O(n)+O(n)
$$

and therefore:

$$
\boxed{E[T(n)]=O(n)}
$$

---

So

```text
                 n elements
                     │
                     ▼
            Distribute into n buckets
                     │
                     │ O(n)
                     ▼
       ┌────┬────┬────┬────┬────┐
       │ B0 │ B1 │ B2 │... │Bn-1│
       └────┴────┴────┴────┴────┘
          │    │    │       │
          ▼    ▼    ▼       ▼
        IS    IS   IS      IS
          │    │    │       │
          └────┴────┴───────┘
                     │
                     ▼
              concatenate
                     │
                     ▼
                  sorted
```

The mathematical reasoning is:

```text
Bucket i has ni elements
        │
        ▼
Insertion Sort cost = O(ni²)
        │
        ▼
E[ni²] = Var(ni) + E[ni]²
        │
        ▼
E[ni²] = (1 - 1/n) + 1
        │
        ▼
E[ni²] = 2 - 1/n = O(1)
        │
        ▼
n buckets × O(1)
        │
        ▼
O(n)
```

when we sum up the costs of executing Insertion Sort on all \(n\) buckets, the expected performance cost remains \(O(n)\)."

does **not** mean:

> "Insertion Sort is an \(O(n)\) algorithm."

Insertion Sort is still:

$$
O(k^2)
$$

for a bucket containing \(k\) elements.

Rather, Bucket Sort arranges things so that, **on average under the assumed distribution**, the buckets are small enough that:

$$
\sum_i n_i^2
$$

is expected to be only:

$$
O(n)
$$

That distinction is the heart of the Bucket Sort analysis.

**Bucket Sort is fast not because Insertion Sort becomes fast, but because the buckets are expected to be small.**

And mathematically:

$$
E[n_i]=1
\quad\Rightarrow\quad
E[n_i^2]=O(1)
\quad\Rightarrow\quad
n\text{ buckets}\times O(1)=O(n)
$$

This is why we uses **variance and expected squared bucket size**, rather than just the average bucket size.


In summary

The complexity depends heavily on the distribution of the data.

With reasonably uniform distribution:

$$
O(n+k)
$$

or commonly described as average:

$$
O(n)
$$

But in the worst case, all elements could fall into one bucket.

For example:

```text
[0.51, 0.52, 0.53, 0.54, ...]
```

If everything goes into one bucket, that bucket still needs to be sorted.

Depending on the sorting algorithm used inside the buckets, the worst case can become:

$$
O(n^2)
$$

if a quadratic sorting algorithm is used.

---

Bucket Sort is often described as:

#### Best case

$$
O(n+k)
$$

when the buckets are very small and distribution is favorable.

#### Average case

$$
O(n+k)
$$

under appropriate distribution assumptions.

#### Worst case

$$
O(n^2)
$$

when most/all elements fall into one bucket and the internal sort is quadratic.

Space:

$$
O(n+k)
$$

because we need the buckets and their stored elements.

## Bucket Size Matters

Suppose:

```text
n = 1,000,000
```

but we create only:

```text
k = 2
```

buckets.

Then each bucket may contain around:

```text
500,000
```

elements.

That's not very useful.

On the other hand:

```text
k = 1,000,000
```

buckets could create significant memory overhead.

Therefore, selecting the number of buckets is an important implementation/design decision.

A common practical choice is:

$$
k \approx n
$$

for uniformly distributed values, but there is no universal rule.

## Bucket Index Formula

For values in:

$$
[0,1)
$$

using \(k\) buckets:
{/* index=⌊kx⌋ */}
$$
index=\lfloor kx\rfloor
$$

Example:

$$
k=10
$$

and:

$$
x=0.73
$$

Then:

$$
index=\lfloor10(0.73)\rfloor
$$

$$
=\lfloor7.3\rfloor
$$

$$
=7
$$

So:

```text
0.73 → Bucket 7
```

---

## Bucket Sort for Arbitrary Ranges

The simple formula:

$$
\lfloor kx\rfloor
$$

assumes:

$$
0 \leq x < 1
$$

What if the values are:

```text
[20, 35, 42, 57, 61, 73, 88]
```

with:

$$
min=20
$$

and:

$$
max=88
$$

We can normalize the value.

One possible mapping is:

$$
index =
\left\lfloor
k\frac{x-min}{max-min}
\right\rfloor
$$

For example, with:

$$
k=7
$$

and:

$$
x=57
$$

we calculate:

$$
index=
\left\lfloor
7\frac{57-20}{88-20}
\right\rfloor
$$

$$
=
\left\lfloor
7\frac{37}{68}
\right\rfloor
$$

$$
=
\left\lfloor3.808...\right\rfloor
$$

$$
=3
$$

So `57` goes into bucket `3`.

However, implementations need to handle the maximum value carefully because the formula can produce an index equal to `k`.

---

## Bucket Sort with Negative Numbers

Bucket Sort isn't inherently limited to positive numbers.

The main challenge is designing an appropriate mapping function.

For example:

```text
[-50, -20, -10, 0, 15, 30, 45]
```

We can determine:

```text
min = -50
max = 45
```

and normalize values into a range such as:

$$
[0,1]
$$

using:

$$
normalized(x)=
\frac{x-min}{max-min}
$$

For:

```text
x = -20
```

we get:

$$
\frac{-20-(-50)}{45-(-50)}
=
\frac{30}{95}
$$

Then the normalized value can be mapped to a bucket.

## Implementation
### A Complete Python Implementation

Here is a simple Bucket Sort implementation for values in `[0, 1)`:

```python
def bucket_sort(arr):
    n = len(arr)

    if n <= 1:
        return arr

    ## Create n empty buckets
    buckets = [[] for _ in range(n)]

    ## Distribute elements into buckets
    for value in arr:
        index = int(n * value)
        buckets[index].append(value)

    ## Sort each bucket
    for bucket in buckets:
        bucket.sort()

    ## Concatenate buckets
    result = []

    for bucket in buckets:
        result.extend(bucket)

    return result


## Test

       0.72, 0.94, 0.21, 0.12,
       0.23, 0.68]

print(bucket_sort(arr))
```

Output:

```c
#include <stdio.h>
#include <stdlib.h>

void insertion_sort(double bucket[], int size)
{
    for (int i = 1; i < size; i++)
    {
        double key = bucket[i];
        int j = i - 1;

        while (j >= 0 && bucket[j] > key)
        {
            bucket[j + 1] = bucket[j];
            j--;
        }

        bucket[j + 1] = key;
    }
}

void bucket_sort(double arr[], int n)
{
    /*
     * Each bucket can contain at most n elements.
     * This is a simple educational implementation.
     */
    double **buckets = malloc(n * sizeof(double *));
    int *sizes = calloc(n, sizeof(int));

    for (int i = 0; i < n; i++)
    {
        buckets[i] = malloc(n * sizeof(double));
    }

    /* Distribution */
    for (int i = 0; i < n; i++)
    {
        int index = (int)(n * arr[i]);
        buckets[index][sizes[index]++] = arr[i];
    }

    /* Sort each bucket */
    for (int i = 0; i < n; i++)
    {
        insertion_sort(buckets[i], sizes[i]);
    }

    /* Concatenate */
    int position = 0;

    for (int i = 0; i < n; i++)
    {
        for (int j = 0; j < sizes[i]; j++)
        {
            arr[position++] = buckets[i][j];
        }
    }

    /* Free memory */
    for (int i = 0; i < n; i++)
    {
        free(buckets[i]);
    }

    free(buckets);
    free(sizes);
}

void print_array(double arr[], int n)
{
    for (int i = 0; i < n; i++)
    {
        printf("%.2f ", arr[i]);
    }

    printf("\n");
}

{
    double arr[] = {

        0.23, 0.68
    };

    int n = sizeof(arr) / sizeof(arr[0]);

    printf("Before sorting:\n");
    print_array(arr, n);

    bucket_sort(arr, n);

    printf("After sorting:\n");
```

#### Implementation 2
```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/*
 * Number of buckets.
 */
static int num;

/*
 * Return the number of buckets.
 *
 * We use one bucket per element.
 */
int numBuckets(int numElements)
{
    num = numElements;
    return numElements;
}

/*
 * Hash function.
 *
 * Input values must be in the range [0, 1).
 *
 * Example with 10 buckets:
 *
 * 0.12 -> 1
 * 0.26 -> 2
 * 0.68 -> 6
 * 0.94 -> 9
 */
int hash(double *d)
{
    int bucket = (int)(num * (*d));

    return bucket;
}

/*
 * Linked-list node representing an element
 * inside a bucket.
 */
typedef struct entry
{
    void *element;
    struct entry *next;
} ENTRY;

/*
 * Bucket structure.
 */
typedef struct
{
    int size;
    ENTRY *head;
} BUCKET;

/*
 * Extract elements from buckets and place them
 * into the output array.
 *
 * IMPORTANT:
 *
 * We use a separate temporary array called result.
 * This prevents us from overwriting pointers in
 * ar that belong to buckets that have not yet been
 * processed.
 */
void extract(BUCKET *buckets,
             int (*cmp)(const void *, const void *),
             void **ar,
             int n)
{
    int bucketIndex;
    int outputIndex = 0;

    /*
     * Temporary array containing the sorted pointers.
     */
    void **result = malloc(n * sizeof(void *));

    if (result == NULL)
    {
        fprintf(stderr, "Failed to allocate result array\n");
        exit(EXIT_FAILURE);
    }

    /*
     * Process buckets from smallest to largest.
     */
    for (bucketIndex = 0;
         bucketIndex < num;
         bucketIndex++)
    {
        ENTRY *ptr;
        ENTRY *tmp;

        /*
         * Skip empty buckets.
         */
        if (buckets[bucketIndex].size == 0)
        {
            continue;
        }

        /*
         * Remember where this bucket starts
         * in the result array.
         */
        int bucketStart = outputIndex;

        ptr = buckets[bucketIndex].head;

        /*
         * Extract all elements from the linked list.
         *
         * We insert each element into the sorted
         * portion of result[] using insertion sort.
         */
        while (ptr != NULL)
        {
            int position = outputIndex - 1;

            /*
             * Move larger elements to the right.
             */
            while (position >= bucketStart &&
                   cmp(result[position], ptr->element) > 0)
            {
                result[position + 1] = result[position];
                position--;
            }

            /*
             * Insert the current element.
             */
            result[position + 1] = ptr->element;

            outputIndex++;

            /*
             * Move to the next linked-list node.
             */
            tmp = ptr;
            ptr = ptr->next;

            free(tmp);
        }

        /*
         * Bucket is now empty.
         */
        buckets[bucketIndex].head = NULL;
        buckets[bucketIndex].size = 0;
    }

    /*
     * Copy the sorted pointers back into ar.
     */
    memcpy(ar, result, n * sizeof(void *));

    free(result);
}

/*
 * Sort an array of pointers using Bucket Sort.
 */
void sortPointers(void **ar,
                  int n,
                  int (*cmp)(const void *, const void *))
{
    if (n <= 1)
    {
        return;
    }

    /*
     * Number of buckets = number of elements.
     */
    num = numBuckets(n);

    /*
     * Allocate buckets.
     *
     * calloc initializes size = 0 and
     * head = NULL for every bucket.
     */
    BUCKET *buckets =
        (BUCKET *)calloc(num, sizeof(BUCKET));

    if (buckets == NULL)
    {
        fprintf(stderr, "Failed to allocate buckets\n");
        exit(EXIT_FAILURE);
    }

    /*
     * Distribute elements into buckets.
     */
    for (int i = 0; i < n; i++)
    {
        /*
         * ar[i] points to a double.
         */
        int k = hash((double *)ar[i]);

        /*
         * Make sure the bucket index is valid.
         */
        if (k < 0 || k >= num)
        {
            fprintf(stderr,
                    "Invalid bucket index %d for value %.2f\n",
                    k,
                    *(double *)ar[i]);

            free(buckets);
            exit(EXIT_FAILURE);
        }

        /*
         * Allocate linked-list node.
         */
        ENTRY *e =
            (ENTRY *)calloc(1, sizeof(ENTRY));

        if (e == NULL)
        {
            fprintf(stderr,
                    "Failed to allocate bucket entry\n");

            free(buckets);
            exit(EXIT_FAILURE);
        }

        /*
         * Store pointer to the original element.
         */
        e->element = ar[i];

        /*
         * Insert at the beginning of the bucket.
         */
        e->next = buckets[k].head;
        buckets[k].head = e;

        buckets[k].size++;
    }

    /*
     * Sort buckets and write sorted pointers
     * back into ar.
     */
    extract(buckets, cmp, ar, n);

    /*
     * Release bucket array.
     */
    free(buckets);
}

/*
 * Compare two double values.
 */
int compare_double(const void *a, const void *b)
{
    double x = *(const double *)a;
    double y = *(const double *)b;

    if (x < y)
    {
        return -1;
    }

    if (x > y)
    {
        return 1;
    }

    return 0;
}

/*
 * Print an array of doubles.
 */
void print_array(double arr[], int n)
{
    for (int i = 0; i < n; i++)
    {
        printf("%.2f ", arr[i]);
    }

    printf("\n");
}

/*
 * Main test program.
 */
int main(void)
{
    /*
     * Bucket Sort implementation expects
     * values in the range [0, 1).
     */
    double arr[] =
        {
            0.78,
            0.17,
            0.39,
            0.26,
            0.72,
            0.94,
            0.21,
            0.12,
            0.23,
            0.68};

    int n = sizeof(arr) / sizeof(arr[0]);

    printf("Before sorting:\n");
    print_array(arr, n);

    /*
     * sortPointers() expects void* pointers
     * to the elements.
     */
    void **pointers =
        malloc(n * sizeof(void *));

    if (pointers == NULL)
    {
        fprintf(stderr,
                "Failed to allocate pointer array\n");

        return EXIT_FAILURE;
    }

    /*
     * Store the address of every array element.
     */
    for (int i = 0; i < n; i++)
    {
        pointers[i] = &arr[i];
    }

    /*
     * Perform Bucket Sort.
     */
    sortPointers(
        pointers,
        n,
        compare_double);

    /*
     * The pointer array is now sorted.
     *
     * Copy values from the pointed-to elements
     * into arr[].
     */
    double *sorted =
        malloc(n * sizeof(double));

    if (sorted == NULL)
    {
        fprintf(stderr,
                "Failed to allocate sorted array\n");

        free(pointers);

        return EXIT_FAILURE;
    }

    for (int i = 0; i < n; i++)
    {
        sorted[i] = *(double *)pointers[i];
    }

    /*
     * Copy sorted values back to arr.
     */
    memcpy(
        arr,
        sorted,
        n * sizeof(double));

    free(sorted);
    free(pointers);

    printf("\nAfter sorting:\n");
    print_array(arr, n);

    return EXIT_SUCCESS;
}
```

## When Should You Use Bucket Sort?

Bucket Sort is particularly useful when you know something about the **distribution of the input values**.

Good scenario:

```text
n = 1,000,000

values: approximately uniformly distributed between 0 and 1
```

Bucket Sort can produce:

```text
many buckets
+
few elements per bucket
=
small internal sorting problems
```

This is the ideal situation.

Use Bucket Sort when the following two properties hold:
1. **Uniform distribution**: The input data must be uniformly distributed for a given range. Based on this
distribution, n buckets are created to evenly partition the input range.
2. **Ordered hash function**: The buckets are ordered. If i < j, elements inserted into bucket bi are lexico‐
graphically smaller than elements in bucket bj.

---

## When Should You Avoid It?

Bucket Sort is not appropriate for sorting arbitrary strings, for example, because typically it is impossible to develop a hash function with the required characteristics. However, it could be used to sort a set of uniformly distributed floating-point numbers in the range [0, 1).

Bucket Sort is less attractive when:

1. Values are heavily clustered

```text
[0.500001,
 0.500002,
 0.500003,
 ...
```

Many values may enter the same bucket.

2. Distribution is unknown

If you don't know how the input is distributed, it becomes harder to predict bucket performance.

3. The value range is awkward

If values span a very large or irregular range, constructing an effective bucket mapping can be difficult.

4. You need predictable worst-case performance

For applications requiring guaranteed:

$$
O(n\log n)
$$

performance, algorithms such as Merge Sort or Heap Sort may be more appropriate.


## Variations
This section is introducing **Hash Sort**, which is essentially a more general version of the Bucket Sort idea we just discussed.

The important difference is that instead of using exactly \(n\) buckets, **Hash Sort chooses a fixed number \(k\) of buckets and uses a special hash function that preserves lexicographic order**.

---

**The basic idea**

Suppose we want to sort strings:

```text
"cat"
"apple"
"banana"
"zebra"
"abc"
"abd"
```

A normal hash function is usually designed to spread values out:

```text
hash("cat") → 391
hash("apple") → 17
hash("banana") → 843
```

But that is **not suitable for sorting**, because the hash values don't necessarily preserve the original ordering.

For sorting, we need a special property:

$$
a_i < a_j
\quad\Longrightarrow\quad
hash(a_i) \le hash(a_j)
$$

where `<` means **lexicographic ordering**.

For example:

```text
"abc" < "abd" < "abe" < "abf"
```

must result in:

```text
hash("abc") < hash("abd") < hash("abe") < hash("abf")
```

This is sometimes called an **order-preserving hash** in this context.

**Why does preserving order matter?**

Suppose we have:

```text
"abc"
"abd"
"acd"
"bba"
"zzz"
```

The hash function might produce:

```text
"abc" → 28
"abd" → 29
"acd" → 55
"bba" → 676
"zzz" → 17575
```

Therefore:

```text
"abc" → bucket 28
"abd" → bucket 29
"acd" → bucket 55
"bba" → bucket 676
"zzz" → bucket 17575
```

Because the hash values preserve ordering:

```text
bucket 28 < bucket 29 < bucket 55 < bucket 676 < bucket 17575
```

we know:

```text
everything in bucket 28
        <
everything in bucket 29
        <
everything in bucket 55
        <
everything in bucket 676
        <
everything in bucket 17575
```

So after sorting **inside each bucket**, we can simply concatenate the buckets.

That's exactly the same fundamental idea as Bucket Sort.

The hash function hash(e) defined bellow operates over elements containing just lowercase letters. It converts the first three characters of the string (using
base 26 representation) into an integer value; for the string “abcdefgh,” its first three
characters (“abc”) are extracted and converted into the value 0*676 + 1*26 + 2 = 28.
This string is thus inserted into the bucket labeled 28
```c
/** Number of buckets to use. */
int numBuckets (int numElements) {
return 26*26*26;
}
/**
* Hash function to identify bucket number from element. Customized
* to properly encode elements in order within the buckets.
*/
int hash (void *elt) {
return (((char*)elt)[0] - 'a')*676 +
(((char*)elt)[1] - 'a')*26 +
(((char*)elt)[2] - 'a');
}
```
**Why 26 × 26 × 26 buckets?**

The example assumes strings contain lowercase English letters:

```text
a b c d ... z
```

There are:

$$
26
$$

possible values for each character.

The hash function looks only at the **first three characters**.

Therefore the number of possible combinations is:

$$
26^3
$$

which is:

$$
26\times26\times26
=
17,576
$$

So:

```c
int numBuckets(int numElements) {
    return 26 * 26 * 26;
}
```

creates:

```text
17,576 buckets
```

Notice something important: The number of buckets is **not dependent on `numElements`**.

Whether we have:

```text
100 strings
```

or:

```text
1,000,000 strings
```

we still have:

```text
17,576 buckets
```

The hash function is:

```c
int hash(void *elt) {
    return (((char*)elt)[0] - 'a') * 676 +
           (((char*)elt)[1] - 'a') * 26 +
           (((char*)elt)[2] - 'a');
}
```

The important concept is **base-26 representation**. The code uses:

```c
(char*)elt
```

to interpret the element as a string.

Then:

```c
((char*)elt)[0]
```

is the first character.

For:

```text
"abcdefgh"
```

we have:

```text
position 0 → 'a'
position 1 → 'b'
position 2 → 'c'
```

We convert each character into a number:

```text
a → 0
b → 1
c → 2
d → 3
...
z → 25
```

So:

```text
"abc"
```

becomes:

```text
0 1 2
```

**Why 676?**

Since each character has 26 possibilities, the first character needs to represent all combinations of the next two characters.

There are:

$$
26^2=676
$$

possible combinations for two characters.

Therefore the first character is multiplied by:

$$
676
$$

The second character is multiplied by:

$$
26
$$

and the third character is multiplied by:

$$
1
$$

So:

$$
hash(s)
=
c_0\times26^2+c_1\times26+c_2
$$

**Example: `"abc"`**

Convert:

```text
a → 0
b → 1
c → 2
```

Then:

$$
hash("abc")
=
0\times676
+
1\times26
+
2
$$

Therefore:

$$
=0+26+2
$$

$$
\boxed{28}
$$

So:

```text
"abc"
    ↓
bucket 28
```

**Another example: `"abd"`**

```text
a → 0
b → 1
d → 3
```

Therefore:

$$
hash("abd")
=
0(676)+1(26)+3
$$

$$
=29
$$

So:

```text
"abc" → 28
"abd" → 29
```

and therefore:

```text
"abc" < "abd"
```

is preserved.

**Another example: `"baa"**

```text
b → 1
a → 0
a → 0
```

Therefore:

$$
hash("baa")
=
1(676)+0(26)+0
$$

$$
=676
$$

So:

```text
"abc" → 28
"abd" → 29
"baa" → 676
```

Again:

```text
"abc" < "abd" < "baa"
```

and:

```text
28 < 29 < 676
```

**Why this is effectively a lexicographic encoding**

Think about ordinary decimal numbers.

For example:

```text
123
124
125
```

Their numerical representation preserves their ordering.

The hash function is doing something similar, except it uses **base 26** instead of base 10.

```text
decimal:

123 = 1×100 + 2×10 + 3


base 26:

abc = 0×26² + 1×26 + 2
```

So we can think of the hash as:

```text
three-character string
        │
        ▼
base-26 number
        │
        ▼
bucket index
```

**The complete Hash Sort process**

Suppose we have:

```text
"dog"
"cat"
"apple"
"car"
"zoo"
"abc"
```

Hash Sort does:

```text
                 Input
                   │
                   ▼
              hash(element)
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
     bucket      bucket     bucket
       ...          ...        ...
        │
        ▼
 sort each bucket
        │
        ▼
 concatenate buckets
        │
        ▼
      sorted
```

For example:

```text
"abc" → 28
"car" → ...
"cat" → ...
"dog" → ...
"zoo" → ...
```

Because bucket numbers preserve lexicographic ordering, processing buckets from smallest to largest produces the correct global ordering.

**Where does Insertion Sort come in?**

This is exactly the same idea we discussed for Bucket Sort.

Suppose several strings have the same first three characters:

```text
"abcdef"
"abcxyz"
"abcaaa"
"abcmmm"
```

All of them produce the same hash:

```text
"abc" → 28
```

Therefore:

```text
bucket 28:

abcdef
abcxyz
abcaaa
abcmmm
```

The hash function cannot distinguish them because it only examines the first three characters.

So we have to sort them **inside the bucket**.

For example, using Insertion Sort:

```text
abcaaa
abcdef
abcmmm
abcxyz
```

Then Hash Sort moves to the next bucket.

**why does too few buckets lead to O(n²)?**

Suppose we have:

```text
n = 100,000
```

and only:

```text
k = 26
```

buckets.

The average bucket size is:

$$
\frac{100000}{26}
\approx3846
$$

Insertion Sort on a bucket containing approximately 3846 elements can require:

$$
O(3846^2)
$$

operations.

More generally, if the elements are evenly distributed among \(k\) buckets:

$$
n_i\approx\frac nk
$$

Each bucket costs approximately:

$$
O\left(\left(\frac nk\right)^2\right)
$$

There are \(k\) buckets:

$$
k\left(\frac nk\right)^2
$$

Simplify:

$$
\frac{n^2}{k}
$$

Therefore:

$$
T(n)=O\left(n+\frac{n^2}{k}\right)
$$

for the simplified evenly distributed case.

So
$$
T(n)\approx O\left(n+\frac{n^2}{k}\right)
$$

where:

* \(n\) = number of input elements
* \(k\) = number of buckets

The first \(n\) comes from:

```text
hash + distribution
```

The second term comes from:

```text
Insertion Sort inside buckets
```

**What happens when k is large?**

Suppose:

$$
k=n
$$

Then:

$$
\frac{n^2}{k}
=
\frac{n^2}{n}
=
n
$$

So:

$$
T(n)=O(n+n)
$$

Therefore:

$$
\boxed{O(n)}
$$

This is basically the situation from the previous Bucket Sort example.

**What happens when k is constant?**

Suppose:

$$
k=26
$$

Then:

$$
\frac{n^2}{26}
$$

Since 26 is a constant:

$$
O\left(\frac{n^2}{26}\right)=O(n^2)
$$

Therefore:

$$
T(n)=O(n^2)
$$

So if the number of buckets doesn't grow as the input gets larger, eventually the buckets become large enough that Insertion Sort dominates.

**A very important distinction from ordinary hashing**

Don't confuse this Hash Sort hash function with a typical hash table hash function.

A normal hash table wants:

```text
similar keys
     ↓
different buckets
```

and usually does **not** care about ordering.

For example:

```text
hash("abc") → 17
hash("abd") → 903
hash("abe") → 42
```

That's perfectly fine for a hash table.

But Hash Sort needs:

```text
"abc" < "abd" < "abe"

therefore:

hash("abc") ≤ hash("abd") ≤ hash("abe")
```

So this is an **order-preserving hash function**, specifically designed for sorting.

**Why only the first three characters?**

This is a trade-off.

Using:

```text
first 3 characters
```

gives:

$$
26^3=17,576
$$

possible buckets.

If we used four characters:

$$
26^4=456,976
$$

buckets.

Five characters:

$$
26^5=11,881,376
$$

buckets.

So:

```text
characters used       buckets
--------------------------------
3                      17,576
4                     456,976
5                  11,881,376
```

More characters allow finer partitioning:

```text
more characters
       ↓
more buckets
       ↓
smaller buckets
       ↓
less Insertion Sort work
```

But there is a trade-off:

```text
more buckets
     ↓
more memory
     ↓
more bucket initialization / management
```

So we don't simply create an infinite number of buckets.

**Hash Sort vs the Bucket Sort**

The two ideas are extremely closely related.

|                      | Bucket Sort                    | Hash Sort                             |
| -------------------- | ------------------------------ | ------------------------------------- |
| Main idea            | Partition into ordered buckets | Partition using order-preserving hash |
| Bucket count         | Often \(n\)                    | Usually fixed \(k\)                   |
| Input example        | Numbers                        | Strings                               |
| Partition function   | Numeric range                  | Hash/encoding                         |
| Ordering requirement | Buckets correspond to ranges   | Hash preserves lexicographic order    |
| Local sorting        | Often Insertion Sort           | Insertion Sort                        |
| Good case            | Uniform distribution           | Good distribution + enough buckets    |
| Potential worst case | \(O(n^2)\)                     | \(O(n^2)\)                            |
| Key parameter        | Bucket count/distribution      | \(k\) + hash function                 |

Conceptually:

```text
                Hash Sort
                    │
                    ▼
             order-preserving
                hash(e)
                    │
                    ▼
              bucket number
                    │
                    ▼
          ┌───────────────────┐
          │                   │
       bucket 0            bucket k-1
          │                   │
          ▼                   ▼
    Insertion Sort      Insertion Sort
          │                   │
          └─────────┬─────────┘
                    ▼
               concatenate
                    │
                    ▼
                 sorted
```

---

**The most important takeaway**

There are really **three ideas** you should remember from this section.

1. The hash function must preserve order

```text
a < b
  ↓
hash(a) ≤ hash(b)
```

Otherwise, the buckets cannot simply be concatenated in bucket-number order.

2. More buckets usually mean smaller local sorting problems

```text
k ↑
↓
average bucket size ↓
↓
Insertion Sort work ↓
```

3. Too few buckets eventually produces quadratic behavior

Approximately:

$$
T(n)=O\left(n+\frac{n^2}{k}\right)
$$

Therefore:

```text
k ≈ n       → O(n)
k = constant → O(n²)
```

So the fundamental strategy is:

> **Use the hash function to establish the global order, then use Insertion Sort only to resolve ordering within each bucket.**

And that connects directly to the Bucket Sort analysis: **the entire performance question comes down to how large the individual buckets become.**

### Bucket Sort vs Quick Sort

Consider the fundamental difference.

**Quick Sort**

```text

      ↓
Compare elements with pivot
      ↓
Partition
      ↓
Recursively sort
```

It relies heavily on **comparisons**.

**Bucket Sort**

```text

      ↓
Map value → bucket
      ↓

      ↓
Concatenate
```

It relies heavily on the **distribution of values**.

### Bucket Sort and the Pigeonhole Idea

There is a useful conceptual relationship with the **pigeonhole principle**.

Suppose we have:

```text
1000 elements
```

and:

```text
1000 buckets
```

If the values are distributed well, many buckets may contain:

```text
0 or 1 element
```

Then very little sorting is necessary inside the buckets.

The algorithm has effectively transformed:

```text
one large sorting problem
```

into:

```text
many tiny sorting problems
```

This is the fundamental strategy.

---

### Bucket Sort as "Divide by Value"

This is a useful mental model:

```text
Comparison sorting:

Divide according to comparisons
        ↓
    left / right
        ↓
recursive sorting
```

Bucket Sort:

```text
Divide according to value ranges
        ↓
 bucket 0 / bucket 1 / ... / bucket k
        ↓
sort locally
        ↓
combine
```

So Bucket Sort is essentially:

> **Partition the value space first, then sort locally.**

## Important Properties

| Property                | Bucket Sort                            |
| ----------------------- | -------------------------------------- |
| Category                | Non-comparison sorting                 |
| Main technique          | Distribution                           |
| Requires bucket mapping | Yes                                    |
| Internal sorting        | Yes                                    |
| Stable                  | Not inherently                         |
| In-place                | Usually no                             |
| Extra space             | \(O(n+k)\)                             |
| Best case               | \(O(n+k)\)                             |
| Average case            | \(O(n+k)\) under suitable distribution |

---
 
The Most Important Insight

Don't memorize Bucket Sort simply as:

> "Create buckets, sort them, combine them."

The deeper idea is: Use the values to establish coarse ordering before sorting locally

Suppose:

```text
B0 < B1 < B2 < B3
```

means every value in `B0` is smaller than every value in `B1`, every value in `B1` is smaller than every value in `B2`, etc.

Then the global sorting problem becomes:

```text
Global problem
      │
      ▼
Distribute by value
      │
      ├── small problem
      ├── small problem
      ├── small problem
      └── small problem
      │
      ▼
Sort locally
      │
      ▼
Concatenate
```

That is why Bucket Sort can achieve **linear expected time** under appropriate distribution assumptions, while comparison-based sorting has the \(\Omega(n\log n)\) lower bound.
