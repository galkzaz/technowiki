**Divide-and-Conquer (D&C)** is a problem-solving paradigm used heavily in sorting.

**Divide-and-Conquer sorting** is a general paradigm that divides a problem, solves subproblems, and combines results.

**Core structure:**
```
Divide → Conquer → Combine
```
Meaning:
1. **Divide**: Break the array into smaller subarrays
2. **Conquer**: Recursively sort those subarrays
3. **Combine**: Merge results into a final sorted array

Two ways to "divide" in D&C sorting:

1. **Structural Division (Merge Sort)**
    - Divide by index (middle)
    - Data is not rearranged initially
    - Fix happens in combine phase

2. **Value-Based Division (Partitioning)**
    - Divide by value (pivot)
    - Data is rearranged immediately
    - No combine phase needed

We can classify sorting algorithms:
```
Divide-and-Conquer Sorts
│
├── Merge-Based (need combine step)
│   └── Merge Sort
│
└── Partition-Based (no combine step)
    └── Quick Sort
```
For large datasets which aren’t nearly sorted, O(n^2) algorithms are too slow. In these cases, we need more
efficient algorithms. The most famous efficient sorting algorithms are Merge Sort and Quicksort, both O(n log n).

## Partition-Based Sorting(Value-Based Division)

**(Partition-Based Sorting** is a core algorithmic paradigm where an array is rearranged (partitioned) around a **pivot** element, and then sorting is achieved by recursively applying the same idea to subarrays.

This idea is most famously used in **Quicksort**, but the partitioning technique itself appears in many algorithms (selection, median finding, etc.).

### Core Idea
A Divide and Conquer strategy solves a problem by dividing it into two independent subproblems, each about half the size of the original problem. You can apply this strategy to sorting as follows: 
1. find the median element in the collection `A` and swap it with the middle element of A. 
2. Now swap elements in the left half that are greater than `A[mid]` with elements in the right half that are less than or equal to `A[mid]`.
3. This subdivides the original array into two distinct subarrays that can be recursively sorted in place to sort the original collection `A`

The fundamental operation is: Partition the array so that:
- `Elements < pivot` go to the left
- `Elements > pivot` go to the right
- Pivot ends up in its final sorted position

After one partition step:
```
[ smaller elements | pivot | larger elements ]
```
Then recursively:
- Sort left part
- Sort right part

{/*A **partition-based sort** is a **Divide-and-Conquer** algorithm where the divide step rearranges the array such that no combine step is needed.*/}
A **partition-based sort** is a specialized form of **Divide-and-Conquer** where the division step rearranges the array around a pivot, eliminating the need for a combine step.

The Combine Step is the Key Differentiator

In Merge Sort:
- Heavy combine step
- Must merge arrays → O(n)

But in Quick Sort:
- No combine step
- Work is done during partition

This leads to the key classification: Partition-Based Sorting (Special Case of D&C)

How Quick Sort Fits: Step-by-step:
1. Partition
    ```
    [ elements < pivot | pivot | elements > pivot ]
    ```
2. Pivot is already in final position
3. **Recursively sort**:
    - Left subarray
    - Right subarray
4. No merge required

Partition-based sorting introduces a powerful reusable pattern: Partition Pattern:
- Choose pivot
- Rearrange elements
- Return pivot index

**Why Partition-Based Sorting is Powerful**
1. **In-place**: No extra memory (O(1) space)
2. **Cache-friendly**: Works on contiguous arrays
3. **Divide-and-Conquer**: Breaks problem recursively

Partition-based sorting works because: Each partition step places at least one element in its final position, This guarantees progress toward a fully sorted array.

**Why Partition-Based Sorting Works**

Key invariant after partition:
```
Left side ≤ pivot ≤ Right side
```
This guarantees:
- Pivot is in final sorted position
- Subproblems are independent

Used in:
- Quick Sort
- Quickselect
- Median of medians
- Dutch National Flag

### Computing the median(Pivot)
{/*Why not always pick the median as pivot?*/}
Implementing this approach is challenging because it might not be obvious how to compute the median element of a collection without sorting the collection first(The true median requires sorting (or near-sorting))!,That would cost $O(n log n)$ — defeating the purpose.

So we face a paradox:
- We want the median to get perfect balance
- But finding it is expensive

It turns out that you can use any element in `A` to partition `A` into two subarrays; if you
choose “wisely” each time, then both subarrays will be more or less the same size
and you will achieve an efficient implementation.

So, You don’t need the exact median — just a good enough pivot, Instead of perfect balance:
```
50% | pivot | 50%
```
We accept approximate balance:
```
30% | pivot | 70%
```
This is still efficient.

**Why “Any Element” Works**

You can pick any element as pivot:
- First element
- Last element
- Random element

Partition still works:
```
[ < pivot | pivot | > pivot ]
```
- Correctness is always preserved
- Performance depends on pivot quality

“Choose Wisely” means: Try to avoid extremely unbalanced partitions, for example

- Bad Pivot (Worst Case)
    ```
    [1 2 3 4 5]
    ```
    pivot = 1
    ```
    → [] 1 [2 3 4 5]
    ```
    This gives:
    ```
    T(n) = T(n-1) + O(n) → O(n²)
    ```
2. Good Pivot (Balanced)

    pivot ≈ middle value
    ```
    → [smaller half] pivot [larger half]
    ```
    This gives:
    ```
    T(n) = 2T(n/2) + O(n) → O(n log n)
    ```

**Balanced Recursion Tree**
```
Level 0: n
Level 1: n/2 + n/2
Level 2: n/4 + n/4 + n/4 + n/4
...
```
Height ≈ log n

**Unbalanced Recursion Tree**
```
n → n-1 → n-2 → ...
```
Height ≈ n

The efficiency of partition-based sorting depends not on choosing the exact median, but on consistently choosing pivots that produce reasonably balanced partitions, ensuring logarithmic recursion depth.

#### Pivot Strategies
**A. Random Pivot**
```
pivot = arr[rand() % n];
```
- Avoids worst case (with high probability)
- Used in practice

**B. Median-of-Three**

Pick median of: first, middle, last
- Very common optimization
- Good balance in real data

**C. True Median (Theoretical)**

Using Median of Medians algorithm:
- Guarantees perfect balance
- Runs in O(n)

BUT:
- High constant cost
- Rarely used in practice

### Partition Schemes(Partition Operation)
Partitioning is in-place and linear time O(n).

There are two classic schemes:

#### Lomuto Partition Scheme
The Lomuto partition scheme is a simple, efficient algorithm for Quicksort that reorders an array around a pivot—typically the last element—by scanning it once. It uses a "wall" pointer to track elements smaller than the pivot, swapping them to the front to ensure all smaller elements are left of the pivot.

Core Idea
- Pick last element as pivot
- Maintain boundary of smaller elements

We maintain a boundary:
```
i = end of "≤ pivot" region
```
Then scan with another pointer j.

**Key Aspects of the Lomuto Partition Scheme**
- **Pivot Selection**: Usually the last element in the given subarray is chosen as the pivot.
- Mechanism: Maintains a pointer `i` as a "wall" (initially before the first element) and iterates through the array with another pointer `j`.
- **Operation**: If an element `arr[j]` is less than or equal to the pivot, the wall `i` is moved forward, and arr[j] is swapped with `arr[i]`.
- **Final Step**: After the loop, the pivot (at the end) is swapped with the element at `i+1`, placing the pivot in its final sorted position.
- **Performance**: It is easy to implement but generally less efficient than Hoare’s partition scheme, performing more swaps. The time complexity is $O(n^2)$ in the worst case (e.g., sorted array) and $O(nlogn)$ in the average case.

Example Algorithm Steps
1. Initialize pivot as `arr[high]`.
2. Set a variable `i = low - 1` (the boundary for smaller elements).
3. **Iterate `j` from `low` to `high - 1`**:
    ◦ If `arr[j] <= pivot`, increment `i` and swap `arr[i]` with `arr[j]`.
4. Swap `arr[i + 1]` with `arr[high]` (place pivot in its place).
5. Return `i + 1`

Why i = left - 1? Because:
- It represents empty "≤ pivot" region 
- First valid element goes to left

**Visual Summary**

Before:
```
[ ? ? ? ? pivot ]
```
After:
```
[ ≤ pivot | pivot | > pivot ]
```

**Loop Invariant**

At any point during the loop:
```
A[left ... i]      ≤ pivot
A[i+1 ... j-1]     > pivot
A[j ... right-1]   unknown
```
This invariant is the heart of correctness

**Iteration Logic**

For each element A[j]:

1. **Case 1**: `A[j] ≤ pivot`
- Expand smaller region
- Swap into correct place
```
i++
swap(A[i], A[j])
```
2. **Case 2**: `A[j] > pivot`
- Do nothing
- Let it stay in "greater" region

Final Step

After loop:
```
swap(A[i+1], A[right])
```
This places pivot in its final sorted position.

Input:
```
A = [8, 3, 5, 2, 7]
```

pivot = 7

Iterations:
| j | A[j] | Action | Array State     |
| - | ---- | ------ | --------------- |
| 0 | 8    | skip   | [8, 3, 5, 2, 7] |

| 2 | 5    | swap   | [3, 5, 8, 2, 7] |

```

```

Result:
```
[3, 5, 2] 7 [8]
        ↑
        p = 3
```

Given an array segment:
```
A[left ... right]
```
We want to:
- Choose a pivot (usually `A[right]`) 
- Rearrange the array so that: 
```
A[left ... p-1] ≤ pivot
A[p]            = pivot
A[p+1 ... right] > pivot
```

```
// Divides array into three partitions
algorithm partition(A, lo, hi) is
  // Pivot value
  pivot := A[(lo + hi) / 2] // Choose the middle element as the pivot (integer division)
  
  // Lesser, equal and greater index
  lt := lo
  eq := lo
  gt := hi
  
  // Iterate and compare all elements with the pivot
  while eq <= gt do
    if A[eq] < pivot then
      // Swap the elements at the equal and lesser indices
      swap A[eq] with A[lt]
      // Increase lesser index
      lt := lt + 1
      // Increase equal index
      eq := eq + 1
    else if A[eq] > pivot then
      // Swap the elements at the equal and greater indices
      swap A[eq] with A[gt]
      // Decrease greater index
      gt := gt - 1
    else // if A[eq] = pivot then
      // Increase equal index
      eq := eq + 1
  
  // Return lesser and greater indices
  return lt, gt
```

  ```c
  // Function to swap two elements
  void swap(int* a, int* b) {
      int temp = *a;
      *a = *b;
      *b = temp;
  }

  /*
   * Lomuto Partition Scheme:
   * 1. Uses the last element as the pivot.
   * 2. Maintains an index 'i' as the wall for elements <= pivot.
   * 3. Scans through the array with 'j' and swaps elements into the left partition.
   */
  int lomuto_partition(int arr[], int low, int high) {
      int pivot = arr[high];
      int i = (low - 1);

      for (int j = low; j < high; j++) {
          if (arr[j] <= pivot) {
              i++;
              swap(&arr[i], &arr[j]);
          }
      }
      swap(&arr[i + 1], &arr[high]);
      return (i + 1);
  }

      int n = sizeof(arr) / sizeof(arr[0]);
      int pivot_index = lomuto_partition(arr, 0, n - 1);

      printf("Pivot placed at index: %d\n", pivot_index);
      printf("Partitioned array: ");
      for (int k = 0; k < n; k++) printf("%d ", arr[k]);
      return 0;
  }
  ```

  ```javascript
  /**
   * Lomuto Partitioning:
   * Rearranges elements in the array based on a pivot (last element).
   * Elements smaller than the pivot are moved to the left.
   */
  function lomutoPartition(arr, low, high) {
    const pivot = arr[high];
    let i = low - 1;

    for (let j = low; j < high; j++) {
      if (arr[j] <= pivot) {
        i++;
        // Swap using array destructuring
        [arr[i], arr[j]] = [arr[j], arr[i]];
      }
    }

    // Final swap to place pivot correctly
    [arr[i + 1], arr[high]] = [arr[high], arr[i + 1]];
    return i + 1;
  }
  ```

  ```rust
   * Lomuto Partition Scheme:
   * Partitions a mutable slice of integers around its last element.

  fn lomuto_partition(arr: &mut [i32], low: usize, high: usize) -> usize {
      let pivot = arr[high];
      let mut i = low as isize - 1;

      for j in low..high {
          if arr[j] <= pivot {
              i += 1;
              arr.swap(i as usize, j);

  }
  ```

#### Hoare Partition Scheme
**Hoare's Partition Scheme** is a linear-time (O(n)) algorithm used in Quicksort to divide an array into two subarrays based on a "pivot" value. Invented by Sir Tony Hoare, it is generally more efficient than the Lomuto Partition Scheme because it performs roughly three times fewer swaps on average and handles duplicate elements more effectively

**Core Idea**

Instead of growing a “≤ pivot” region like Lomuto, Hoare uses: Two pointers moving toward each other
1. i → from left
2. j ← from right

They scan and swap misplaced elements.

Given an array `arr[]`, the task is to partition the array by **assuming first element as pivot element**. 

The partition of an array must satisfy the following two conditions:
- Elements smaller than pivot element must appear at index less than or equal to **partition index**.
- Elements larger than or equal to pivot element must appear at index greater than **partition index**.

Partition index is equal to count of elements, strictly smaller than pivot, minus one.

There might be more than one possible partition arrays.

**Examples:**

- Input:` arr[] = [5, 3, 8, 4, 2, 7, 1, 10]`
- Output: `[1, 3, 2, 4, 8, 7, 5, 10]`
- Explanation: The partition index is `3` and pivot element is `5`, all elements smaller than pivot element `[1, 3, 2, 4]`- were arranged before partition index and elements larger than or equal to pivot `[8, 7, 5, 10]` were arranged after- partition index.

- Input: `arr[] = [12, 10, 9, 16, 19, 9]`
- Output: `[9, 10, 9, 16, 19, 12]` 
- Explanation: The partition index is `2` and pivot element is `12`, all elements smaller than pivot element `[9, 10, 9]` were- arranged before or at partition index and elements larger than or equal to pivot `[16, 19, 12]` were arranged after partition index.

**How It Works**

We are fixing two types of mistakes:
1. Left side should have ≤ pivot
2. Right side should have ≥ pivot


Loop Behavior

1. **Step 1**: Move i right

- Find first element ≥ pivot
- This element is on the wrong side

2. **Step 2**: Move j left
- Find first element ≤ pivot
- Also on the wrong side

3. **Step 3**: Swap them
- Fix both mistakes in one swap

Key Observations
- Left side:
[7, 3, 5, 2] ≤ pivot (8)
- Right side:
[8] ≥ pivot
- Pivot (8) ended up at the end by coincidence, not by guarantee.

Hoare only guarantees:
```
Left ≤ pivot   |   Right ≥ pivot
```
NOT: pivot is at final sorted position
##### Pseudocode
```
function hoare_partition(A, left, right):
    pivot ← A[left]
    i ← left - 1
    j ← right + 1

    while true:

        repeat:
            i ← i + 1
        until A[i] ≥ pivot

        repeat:
            j ← j - 1
        until A[j] ≤ pivot

        if i ≥ j:
            return j

        swap A[i] ↔ A[j]
```
Return Value Meaning
```
return j
```
This means:
```
A[left ... j]     ≤ pivot
A[j+1 ... right]  ≥ pivot
```
It returns a partition boundary, not pivot index

**Loop Invariant**

At any point:
```
A[left ... i-1]   ≤ pivot
A[j+1 ... right] ≥ pivot
```
Unknown region:
```
A[i ... j]
```
Visual Summary
```
Before:
[ ? ? ? ? ? ]

During:
[ ≤ pivot | unknown | ≥ pivot ]

After:
[ ≤ pivot | ≥ pivot ]
```
Hoare partition works by simultaneously correcting misplaced elements from both ends, leading to fewer swaps and better performance, but it does not place the pivot in its final sorted position.

**Common Pitfalls** 
- Assuming pivot ends in final position
- Using wrong recursion boundaries
- Infinite loop (wrong conditions)

  ```c
  #include <stdio.h>

  // Function to swap two elements
  void swap(int* a, int* b) {
      int temp = *a;
      *a = *b;
      *b = temp;
  }

  /*
   * Hoare Partition Scheme:
   * 1. Uses the first element as the pivot.
   * 2. Uses two pointers (i and j) that move toward each other.
   * 3. Swaps elements that are on the wrong side of the pivot.
   * 4. More efficient than Lomuto as it performs fewer swaps on average.
   */
  int hoare_partition(int arr[], int low, int high) {
      int pivot = arr[low];
      int i = low - 1;
      int j = high + 1;

      while (1) {
          // Increment i while elements are less than the pivot
          do {
              i++;
          } while (arr[i] < pivot);

          // Decrement j while elements are greater than the pivot
          do {
              j--;
          } while (arr[j] > pivot);

          // If pointers meet or cross, partitioning is complete
          if (i >= j) return j;

          // Swap elements to correct their positions relative to pivot
          swap(&arr[i], &arr[j]);
      }
  }

  int main() {
      int arr[] = {10, 80, 30, 90, 40, 50, 70};
      int n = sizeof(arr) / sizeof(arr[0]);
      int split_index = hoare_partition(arr, 0, n - 1);

      printf("Split index: %d\n", split_index);
      printf("Array after partitioning: ");
      for (int k = 0; k < n; k++) printf("%d ", arr[k]);
      return 0;
  }
  ```

  **Notes:**
  - The function returns the split index `j`, not necessarily the final position of the pivot.
  - The two subarrays for recursion would be `[low...j]` and `[j+1...high]`.
  - Average time complexity is $O(n)$, and it is generally faster than the Lomuto scheme.

  ```java
  import java.util.Arrays;

  public class HoarePartition {

      /**
       * Hoare Partition Scheme:
       * Scans from both ends and swaps misplaced elements.
       * Uses the first element as the pivot by default.
       */
      public static int hoarePartition(int[] arr, int low, int high) {
          int pivot = arr[low];
          int i = low - 1;
          int j = high + 1;

          while (true) {
              // Move i right as long as arr[i] < pivot
              do {
                  i++;
              } while (arr[i] < pivot);

              // Move j left as long as arr[j] > pivot
              do {
                  j--;
              } while (arr[j] > pivot);

              // If indices cross, the split point is found
              if (i >= j) {
                  return j;
              }

              // Swap arr[i] and arr[j]
              int temp = arr[i];
              arr[i] = arr[j];
              arr[j] = temp;
          }
      }

      public static void main(String[] args) {
          int[] data = {10, 80, 30, 90, 40, 50, 70};
          int splitIdx = hoarePartition(data, 0, data.length - 1);

          System.out.println("Split index: " + splitIdx);
          System.out.println("Array after partitioning: " + Arrays.toString(data));
      }
  }
  ```

  **Notes:**
  - The `do-while` loops ensure that the pointers move at least once, avoiding infinite loops with duplicate elements.
  - Naming follows standard Java `camelCase`.
  - The split index `j` defines the two sub-problems for the Quicksort algorithm.

  ```javascript
  /**
   * Hoare Partitioning:
   * Rearranges the array elements using two pointers and a pivot.
   * Returns the split point index for recursive sorting.
   */
  function hoarePartition(arr, low, high) {
    const pivot = arr[low];
    let i = low - 1;
    let j = high + 1;

    while (true) {
      do {
        i++;
      } while (arr[i] < pivot);

      do {
        j--;
      } while (arr[j] > pivot);

      if (i >= j) return j;

      // Swap using destructuring assignment
      [arr[i], arr[j]] = [arr[j], arr[i]];
    }
  }

  // Testing the method
  const data = [10, 80, 30, 90, 40, 50, 70];
  const splitIndex = hoarePartition(data, 0, data.length - 1);
  console.log(`Split index: ${splitIndex}`);
  console.log(`Partitioned array: ${data}`);
  ```

  **Notes:**
  - Uses modern JavaScript destructuring for concise swapping logic.
  - The algorithm is in-place and highly efficient in terms of constant factors.
  - In Hoare's scheme, the pivot element can end up in either the left or right partition.

  ```rust
  /**
   * Hoare Partition Scheme:
   * Partitions a mutable slice of i32 around its first element.
   * Returns the split point index 'j'.
   */
  fn hoare_partition(arr: &mut [i32], low: usize, high: usize) -> usize {
      let pivot = arr[low];
      let mut i = low as isize - 1;
      let mut j = high as isize + 1;

      loop {
          // Rust doesn't have do-while, so we use loop + break
          loop {
              i += 1;
              if arr[i as usize] >= pivot { break; }
          }
          loop {
              j -= 1;
              if arr[j as usize] <= pivot { break; }
          }

          if i >= j {
              return j as usize;
          }

          arr.swap(i as usize, j as usize);
      }
  }

  fn main() {
      let mut data = vec![10, 80, 30, 90, 40, 50, 70];
      let n = data.len();
      let split_idx = hoare_partition(&mut data, 0, n - 1);

      println!("Split index: {}", split_idx);
      println!("Array after partition: {:?}", data);
  }
  ```

  **Notes:**
  - Rust's `swap` method provides a safe way to exchange elements in a slice.
  - Pointers `i` and `j` are cast to `isize` to handle the initial boundary state safely.
  - The split point `j` is used to create sub-slices for recursive partitioning.

#### Key Difference between Lomuto and Hoare
| Feature        | Lomuto                 | Hoare                                        |
| -------------- | ---------------------- | -------------------------------------------- |
| Pivot position | Usually last element   | Usually first element                        |
| Pointers       | One (j) + boundary (i) | Two pointers (i, j)                          |
| Swaps          | More                   | Fewer                                        |
| Return value   | Final pivot index      | Split index (not necessarily pivot position) |

Lomuto:
- Easier 
- More “teaching-friendly” 
- Pivot ends in correct position 

Hoare:
- More efficient 
- More subtle 
- Used in high-performance implementations

Why Hoare is Faster
- Fewer swaps
    - Swaps only when necessary
    - Fixes two elements per swap
- Better cache behavior
    - Fewer writes
- Works well with duplicates (better than Lomuto)

#### Differnce between Pivot strategy and Partition scheme
**Pivot strategy** decides what to partition around, **Partition scheme** decides how to do it efficiently.

Choosing A[p] (pivot) → belongs to Pivot Strategies,  Rearranging the array around pivot → belongs to Partition Schemes. Think of It Like This
1. **Step 1**: Choose pivot  ← (Pivot Strategy)
2. **Step 2**: Partition     ← (Partition Scheme)

Pivot Strategy (Selection Problem) answers: Which element should we use as pivot?
Examples:
- First element
- Last element
- Random element
- Median-of-three
- Median-of-medians

This affects performance (balance)

Partition Scheme (Rearrangement Problem) answers: How do we rearrange elements around the pivot?
Examples:
- Lomuto partition
- Hoare partition
- 3-way partition (Dutch National Flag)

This affects:
- Number of swaps
- Constant factors
- Stability behavior

Example Flow

Suppose: `A = [8, 3, 5, 2, 7]`

Step 1: Pivot Strategy

Pick pivot:
- pivot = A[2] = 5

Step 2: Partition Scheme

Apply (e.g., Lomuto or Hoare): → [3, 2] 5 [8, 7]

This Separation Matters, Because you can mix and match:
| Pivot Strategy | Partition Scheme |
| -------------- | ---------------- |
| Random pivot   | Lomuto           |
| Median-of-3    | Hoare            |
| First element  | 3-way partition  |

**Performance Impact**

Pivot Strategy → affects:
- Recursion depth
- Balance of subarrays
- Time complexity (O(n log n) vs O(n²))

Partition Scheme → affects:
- Number of swaps
- Cache behavior
- Constant factors (real-world speed)

**Analogy**

Think of sorting like organizing people:
- Pivot Strategy = choosing a person as a reference
- Partition Scheme = how you physically arrange people around them

Although separate, they interact:
- Some schemes assume pivot is at a specific position
(e.g., Lomuto uses last element)
- Sometimes you:
    1. Choose pivot
    2. Swap it into a convenient position
    3. Run partition
