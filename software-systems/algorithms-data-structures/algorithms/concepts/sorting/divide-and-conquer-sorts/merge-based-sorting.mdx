
## Merge-Based Sorting(Structural Division)
**Merge-Based Sorting** is a family of sorting algorithms that follows the idea:

> **Divide the data into smaller structures, sort those structures, then merge them back together.**

The most important example is **Merge Sort**.

The phrase **Structural Division** emphasizes *how the input is divided*: instead of dividing according to the values of the elements, we divide the **structure of the input**—for example, an array or linked list—into smaller parts.
### The Core Idea

Suppose we have:

```text
[38, 27, 43, 3, 9, 82, 10]
```

Merge-based sorting performs two major operations:

```text
              [38, 27, 43, 3, 9, 82, 10]
                         |
                    DIVIDE
                         ↓
             [38, 27, 43] [3, 9, 82, 10]
                  |              |
               divide         divide
                  ↓              ↓
            [38] [27,43]    [3,9] [82,10]
                  ...
```

Eventually, every part contains one element:

```text
[38] [27] [43] [3] [9] [82] [10]
```

A single element is already sorted.

Then we **merge** sorted pieces:

```text
[38] + [27]
     ↓
[27, 38]

[27, 38] + [43]
        ↓
[27, 38, 43]

[3] + [9]
   ↓
[3, 9]

[82] + [10]
      ↓
[10, 82]
```

And finally:

```text
[27, 38, 43] + [3, 9, 10, 82]
                    ↓
        [3, 9, 10, 27, 38, 43, 82]
```

So the overall structure is:

```text
        DIVIDE
           ↓
    smaller structures
           ↓
        SORT
           ↓
         MERGE
           ↓
    larger sorted structure
```

### What Does "Structural Division" Mean?

There are different ways a sorting algorithm can divide its input.

In Structural division The algorithm divides according to the **position or structure** of the data.

For an array:

```text
[8, 3, 7, 4, 9, 2, 6, 5]
```

Merge Sort might divide it into:

```text
[8, 3, 7, 4]    [9, 2, 6, 5]
```

Then:

```text
[8, 3] [7, 4]    [9, 2] [6, 5]
```

The values don't determine where the division happens.

For example, `9` does not move to one side because it is larger. The algorithm simply divides the **structure**.

### Contrast with Value-Based Division

This distinction is particularly useful when studying sorting strategies.

**Structural division**

Merge Sort:

```text
[8, 3, 7, 4, 9, 2]

        ↓

[8, 3, 7] [4, 9, 2]
```

The division is based on **position**.

**Value-based division**

Quicksort uses a **pivot**:

```text
[8, 3, 7, 4, 9, 2]
          pivot = 7

smaller than 7      larger than 7
[3,4,2]             [8,9]
```

Here the partition depends on **element values**.

So:

| Approach      | How it divides                |
| ------------- | ----------------------------- |
| Merge Sort    | Structure/position            |
| Quicksort     | Element values around a pivot |
| Binary Search | Value comparison              |
| Counting Sort | Key/value range               |
| Radix Sort    | Digits/positions of keys      |

This is why Merge Sort can be described as **structural division**.

### Why Structural Division Is Useful

Structural division has an important advantage:** It does not care about the distribution of values.**

Consider:

```text
[1, 2, 3, 4, 5, 6, 7, 8]
```

Merge Sort still divides:

```text
[1,2,3,4] [5,6,7,8]
```

and continues recursively.

Now consider:

```text
[8,7,6,5,4,3,2,1]
```

It performs essentially the same structural divisions:

```text
[8,7,6,5] [4,3,2,1]
```

The data distribution doesn't affect the division process.

### The Big Picture

Merge-Based Sorting can be understood as a **divide-and-combine strategy**:

```text
                    INPUT
                      |
                      ↓
              Structural Division
                      |
            +---------+---------+
            |                   |
        Substructure        Substructure
            |                   |
        divide again        divide again
            |                   |
            +---------+---------+
                      |
                 size = 1
                      |
                      ↓
              already sorted
                      |
                      ↓
                   MERGE
                      |
                larger sorted
                   structure
                      |
                      ↓
                   MERGE
                      |
                      ↓
                 FINAL SORT
```

The key idea to remember is:

> **Merge Sort does not divide the data according to its values. It divides the input structure into smaller pieces, recursively sorts those pieces, and then uses an efficient merge operation to reconstruct the sorted structure.**

So if you are organizing sorting algorithms by **division strategy**, you can think of the family roughly like this:

```text
Sorting Algorithms
│
├── Comparison-Based Sorting
│   │
│   ├── Structural Division
│   │   └── Merge Sort
│   │
│   ├── Value-Based Partitioning
│   │   └── Quicksort
│   │
│   └── Incremental / Selection-Based
│       ├── Insertion Sort
│       └── Selection Sort
│
└── Non-Comparison-Based Sorting
    ├── Counting Sort
    ├── Radix Sort
    ├── Bucket Sort
    └── Hash Sort
```

This **"how does the algorithm divide or organize the input?"** viewpoint is useful because it connects Merge Sort directly to the broader **divide-and-conquer strategy**.

## Merge Sort
If we have a big list to sort, we can split it into halves: each half list becomes a sorting subproblem. To sort the big list, subproblem solutions (i.e., the sorted halves) can be merged in a single list using the merge algorithm. But how will we sort our two subproblems? They are themselves split into subsubproblems, sorted and merged. The new subsubproblems will also be split, sorted, and merged. The splitting continues until we hit the base case: a one-item list. A one-item list is already sorted!

Merge Sort is the textbook example of
Divide and Conquer. It breaks a list into individual elements (Divide), sorts them by merging (Conquer), and builds the final sorted list (Combine).

Idea:
 - Split array into halves
 - Recursively sort
 - Merge sorted halves

All D&C sorts follow:
$$
 T(n) = aT(n/b) + f(n)
$$
Where:
- a = number of subproblems
- n/b = size of each
- f(n) = cost of divide + combine

Examples:
| Algorithm  | Recurrence             | Key Cost       |
| ---------- | ---------------------- | -------------- |
| Merge Sort | 2T(n/2) + O(n)         | Merge step     |
| Quick Sort | T(k) + T(n-k-1) + O(n) | Partition step |

### Core Idea (Divide and Conquer)

* Divide: Split the array into two halves
* Conquer: Recursively sort each half
* Combine: Merge the two sorted halves into a single sorted array

Merge Sort Has Two Different Phases.

It is important not to think of Merge Sort as simply "divide and sort."

There are really two complementary operations:

```text
             Merge Sort
                 |
        +--------+--------+
        |                 |
      Divide             Merge
        |                 |
 recursively       combine sorted
        |              structures
        ↓                 ↓
   small pieces     sorted result
```

The **division** creates manageable structures.

The **merge** performs the actual ordering.

---

**The Divide Phase**

Consider:

```text
[38, 27, 43, 3, 9, 82, 10, 1]
```

Split approximately in half:

```text
[38, 27, 43, 3] [9, 82, 10, 1]
```

Split again:

```text
[38, 27] [43, 3] [9, 82] [10, 1]
```

Again:

```text
[38] [27] [43] [3] [9] [82] [10] [1]
```

Now every structure has size 1.

---

**The Merge Phase**

Now the algorithm works **bottom-up**.

First:

```text
[38] + [27]
```

Compare:

```text
38 vs 27
```

Take `27` first:

```text
[27, 38]
```

Then:

```text
[43] + [3]
```

Result:

```text
[3, 43]
```

Similarly:

```text
[9] + [82]
       ↓
[9, 82]

[10] + [1]
        ↓
[1, 10]
```

We now have:

```text
[27, 38]   [3, 43]   [9, 82]   [1, 10]
```

Merge again:

```text
[27,38] + [3,43]
```

Compare the first elements:

```text
27 vs 3
```

Take `3`.

```text
[3]
```

Then:

```text
27 vs 43
```

Take `27`.

```text
[3,27]
```

Then:

```text
38 vs 43
```

Take `38`.

Finally:

```text
[3,27,38,43]
```

The other side:

```text
[9,82] + [1,10]
```

produces:

```text
[1,9,10,82]
```

Finally:

```text
[3,27,38,43]
          +
[1,9,10,82]

          ↓

[1,3,9,10,27,38,43,82]
```
### The Merge Operation

The **merge operation** is the heart of Merge Sort.

Suppose we already have two sorted arrays:

```text
A = [3, 8, 15, 20]

B = [2, 5, 17, 30]
```

We maintain a pointer into each:

```text
A → 3
B → 2
```

Compare:

```text
3 vs 2
```

Take `2`.

```text
result = [2]
```

Move B:

```text
A → 3
B → 5
```

Compare:

```text
3 vs 5
```

Take `3`:

```text
result = [2,3]
```

Continue:

```text
2 < 3
3 < 5
5 < 8
8 < 15
15 < 17
17 < 20
20 < 30
```

Result:

```text
[2,3,5,8,15,17,20,30]
```

The important observation is:

> **We don't need to search through either array.**

Because both arrays are already sorted, we only need to inspect their current smallest elements.

### Why Is Merging Efficient?

Suppose:

```text
A = [1, 4, 7, 10]
B = [2, 3, 8, 12]
```

Every element is processed once.

Therefore:

```text
Merge complexity = O(n + m)
```

where:

* `n` = number of elements in A
* `m` = number of elements in B

If together they contain `N` elements:

```text
O(N)
```

This efficient merge operation is what makes Merge Sort powerful.

### Recursive Structure

Merge Sort naturally forms a recursion tree.

For `n = 8`:

```text
                         8
                    /         \
                   4           4
                 /   \       /   \
                2     2     2     2
               / \   / \   / \   / \
              1   1 1   1 1  1 1   1
```

The input size is approximately halved at every level.

Therefore, the number of levels is:

```text
log₂ n
```

At every level, all elements participate in merging:

```text
O(n)
```

So:

```text
O(n) × O(log n)
```

giving:

```text
O(n log n)
```

### Pseudocode
To sort a collection A, divide it evenly into two smaller collections, each of which is
then sorted. A final phase merges these two sorted collections back into a single collection of size n. A naïve implementation of this approach, shown here, uses far too
much extra storage:

``` [Pseudocode]
function merge_sort(list)
  if list.length = 1
    return list
  left ← list.first_half
  right ← list.last_half
  return merge(merge_sort(left), merge_sort(right))
```

```
SORT(A)
    if A has less than 2 elements then
        return A

    else if A has 2 elements then
        if A[0] > A[1] then
            swap A[0] and A[1]
        return A

    sub1 ← SORT(left half of A)
    sub2 ← SORT(right half of A)

    B ← MERGE(sub1, sub2)

    return B
END SORT

MERGE(sub1, sub2)
    create new array B

    while sub1 and sub2 are not empty do
        if first element of sub1 ≤ first element of sub2 then
            append first element of sub1 to B
        else
            append first element of sub2 to B

    append remaining elements of sub1 to B
    append remaining elements of sub2 to B

    return B
END MERGE
```

``` [Pseudocode]
SORT(A)
    copy ← copy of A (1)

    MERGE_SORT(copy, A, 0, n)

END SORT

MERGE_SORT(A, result, start, end) (2)
    if end - start < 2 then
        return

    if end - start = 2 then
        if result[start] > result[start + 1] then
            swap result[start] and result[start + 1]
        return

    mid ← (start + end) / 2

    MERGE_SORT(result, A, start, mid) (3)
    MERGE_SORT(result, A, mid, end)

    MERGE A[start .. mid - 1] and A[mid .. end - 1]
        into result[start .. end - 1] (4)

END MERGE_SORT
```
1. Make full copy of all elements.
2. Place elements of A[start,end) into result[start,end) in sorted order.
3. Sort results[start,mid) into A[start,mid).
4. Merge sorted subarrays in A back into result.

Notice that the recursive calls **swap the roles of `A` and `result`**:

```text
MERGE_SORT(result, A, start, mid)
MERGE_SORT(result, A, mid, end)
```

This is intentional. Instead of allocating a new temporary array at every recursive call, the algorithm uses the two arrays alternately as:

```text
A       → source
result  → destination
```

then:

```text
result  → source
A       → destination
```

This is an important implementation technique for making Merge Sort efficient while using the auxiliary array.

### Input/Output
The output of the sort is returned in place within the original collection A. The
internal storage copy is discarded.
### Visual recursion-tree explanation 
Think of Merge Sort as a tree growing downward, then collapsing upward.
1. Top level (original problem)
[8, 3, 5, 4, 7, 6, 1, 2]
2. Level 1
[8, 3, 5, 4]        [7, 6, 1, 2]
3. Level 2
[8, 3]   [5, 4]     [7, 6]   [1, 2]
4. Level 3 (leaves)
[8] [3] [5] [4]     [7] [6] [1] [2]

This is the divide phase — the tree grows downward.

Now the tree collapses upward:
- Leaves merge into size-2 arrays
- Size-2 arrays merge into size-4
- Size-4 arrays merge into size-8

Each level does:
-Linear work (merging)
- Over log n levels

That's where the famous O(n log n) comes from.

### Steps
**Phase 1: The 'Divide' Stage (Top-Down)**

The algorithm recursively splits the array in half until each sub-array contains only one element. A single element is considered 'sorted' by default.
|     |     |     |     |
| --- | --- | --- | --- |
| Level	 | Left Sub-array	 | Right Sub-array	 | Action |
| 1	 | [38, 27, 43, 3]	 | [9, 82, 10]	 | Split original array in half |
| 2 (Left)	 | [38, 27]	 | [43, 3]	 | Split the left half |
| 2 (Right)	 | [9, 82]	 | [10]	 | Split the right half |
| 3 (Final)	 | [38], [27], [43], [3]	 | [9], [82], [10]	 | All elements are now isolated |

**Step 2: Conquer (Sort Base Cases)**

Subarrays of length 1 are already sorted: [38], [27], [43], [3], [9], [82], [10]

Now, the algorithm merges the small pieces back together. During the merge, it compares the front elements of each list and places the smaller one first.

**Step 3: Merging individual elements into pairs**
|     |     |
| --- | --- |
| Merging Elements	 | Resulting Sorted Sub-array |
| [38] and [27]	 | [  27, 38] | 
|[43] and [3]	 | [3, 43] | 
|[9] and [82]	 | [9, 82] | 
|[10] and [10]	 | [10, 10] |

**Step 3: Merging pairs into larger blocks**

To merge [27, 38] and [3, 43], the engine compares 27 vs 3 (picks 3), then 27 vs 43 (picks 27), then 38 vs 43 (picks 38).
|     |     |
| --- | --- |
| Merging Sub-arrays	 | Resulting Sorted Sub-array |
| [27, 38] and [3, 43]	 | [3, 27, 38, 43] |
| [9, 82] and [10]	 | [9, 10, 82] |

**Step 4: The Final Merge (Global Solution)**

This final 'Combine' step merges the two remaining halves to produce the final sorted array.
|     |     |     |     |
| --- | --- | --- | --- |
| Left | Right Index	 | Comparison	 | Winner to Result Array |
| 27	 | 3	 | 3 &lt; 27	 | [3] |
| 27	 | 9	 | 9 &lt; 27	 | [3, 9] |
| 27	 | 10	 | 10 &lt; 27	 | [3, 9, 10] |
| 27	 | 82	 | 27 &lt; 82	 | [3, 9, 10, 27] |
| 38	 | 82	 | 38 &lt; 82	 | [3, 9, 10, 27, 38] |
| 43	 | 82	 | 43 &lt; 82	 | [3, 9, 10, 27, 38, 43] |
| End | 82	 | Remainder	 | [3, 9, 10, 27, 38, 43, 82] |

### Top-Down vs Bottom-Up Merge Sort

There are two common implementations.

### Top-down Merge Sort

Uses recursion:

```text
        input
          |
        split
       /     \
     sort    sort
      |        |
      +--merge-+
          |
        result
```

This is the version most people learn first.

---

### Bottom-up Merge Sort

Instead of recursively dividing, start with individual elements:

```text
[8] [3] [7] [4] [9] [2] [6] [5]
```

Merge pairs:

```text
[3,8] [4,7] [2,9] [5,6]
```

Merge again:

```text
[3,4,7,8] [2,5,6,9]
```

Merge:

```text
[2,3,4,5,6,7,8,9]
```

So:

```text
Bottom-up:

size 1
  ↓
size 2
  ↓
size 4
  ↓
size 8
  ↓
...
```

This avoids recursive calls and is often useful when implementing Merge Sort iteratively.

### Stability

Merge Sort can be **stable**.

Suppose:

```text
(John, 80)
(Ali, 80)
(Sara, 90)
```

If sorting by score, a stable sort preserves the original order of equal elements:

```text
(John, 80)
(Ali, 80)
(Sara, 90)
```

rather than changing the relative order of `John` and `Ali`.

This is achieved during merging by choosing the element from the left side first when the keys are equal.

```text
if left.key <= right.key
    take left
else
    take right
```

The `<=` is important for stability.
### Merge Sort on Linked Lists

Structural division becomes especially interesting with **linked lists**.

Suppose:

```text
10 → 3 → 7 → 2 → 8 → 5
```

We can split the linked list:

```text
10 → 3 → 7

2 → 8 → 5
```

Then recursively sort:

```text
3 → 7 → 10

2 → 5 → 8
```

Then merge:

```text
3 → 7 → 10
        +
2 → 5 → 8

        ↓

2 → 3 → 5 → 7 → 8 → 10
```

No array indexing is required.

This is one reason Merge Sort is a natural choice for linked lists.

### Analysis
Merge Sort completes the “merge” phase in O(n) time after recursively sorting the
left- and right-half of the range A[start, end), placing the properly ordered elements
in the array referenced as result.
Because copy is a true copy of the entire array A, the terminating base cases of the
recursion will work because it references the original elements of the array directly at
their respective index locations. This observation is a sophisticated one and is key to
the algorithm. In addition, the final merge step requires only O(n) operations,
which ensures the total performance remains O(n log n). Because copy is the only
extra space used by the algorithm, the total space requirement is O(n).
### Complexity
#### Time Complexity
To do this, 
1. **Counting operations**: we're first going to count the operations generated by each individual split step.
    * Say we have a big list of size n. When called, the `merge_sort` function performs the following operations:
        * Splits list in halves, which does not depend on list size: O(1),
        * A merge: we recall from sec. 3.1 that merge is O(n),
        * Two merge_sort recursive calls that are not counted(Operations performed by recursive calls are counted in the next split step!).
    * Since we keep the strongest term and don't count recursive calls, the time complexity of the function is O(n). 
    * Let's now count the time complexity of each split step:
        * Split step 1. The merge_sort function is called for a list of n items. The time complexity of this step is O(n).
        * Split step 2. The merge_sort function is called twice, each time for n/2 items. We find 2 × O(n/2) = O(n).
        * Split step 3. The merge_sort function is called four times, each time for n/4 items: 4 × O(n/4) = O(n).
        * Split step x. The merge_sort function is called 2x times, each for a list of n/2x items: 2x × O(n/2x) = O(n).
      * The split steps all have the same complexity of O(n). Merge Sort's time complexity is thus x × O(n), where x is the number of split steps necessary for its full execution(We can't ignore x because it's not a constant. If the list size n doubles, you'll need one more split step. If n quadruples, you'll need two more split steps.).
2. **Counting Steps**: Then, we'll count how many split steps there are in total.
    * How do we evaluate x? We know recursive functions stop to call themselves once they hit their base case. Our base
    case is a one-item list. We've also seen that split step x works on lists of n/2x items. Therefore:
      $$
      \frac{n}{2^x} = 1 → 2^x = n → x = \log_2 n.
      $$
    * Any process that reduces an input step-by-step, dividing it by a constant factor in each step, takes a logarithmic number of steps to fully reduce the input.

Merge Sort's time complexity is thus $(log_2 n \times O(n)) = O(n log n)$.
| Case    |                                        Time |
| ------- | ------------------------------------------: |
| Best    |                                `O(n log n)` |
| Average |                                `O(n log n)` |
| Worst   |                                `O(n log n)` |
| Space   | `O(n)` for the typical array implementation |

Unlike Quicksort, the usual Merge Sort does **not** degrade to `O(n²)` based on an unlucky pivot.

Unlike Quicksort, Merge Sort does not have a \(O(n^2)\) worst case under its standard implementation. this  means that **regardless of how the input is arranged**, Merge Sort still takes proportional to:

$$
n\log n
$$

For example, these all have the same asymptotic worst-case behavior:

```text
[1, 2, 3, 4, 5, 6, 7, 8]     already sorted
[8, 7, 6, 5, 4, 3, 2, 1]     reverse sorted
[4, 1, 7, 2, 8, 3, 6, 5]     random
```

This predictable behavior is one of Merge Sort's major strengths.

That's a huge improvement over the O(n^2) Selection Sort. Do you
remember the performance gap between log-linear and quadratic
algorithms we've seen last chapter in fig. 2.4? Even if a faster computer crunches the O(n^2) algorithm, it will end up slower than a computer crunching the O(n log n) algorithm:

See how slowly the number of required split steps increases with
the total number of items to sort:

| --------------- | ------ | -------------------- |
| 10              | 3.32   | 4                    |
| 100             | 6.64   | 7                    |

| 1,000,000       | 19.93  | 20                   |
| 1,000,000,000   | 29.89  | 30                   |

For big inputs, O(n log n) algorithms in slow computers are much faster than O(n2) algorithms in 1000× faster computers.

#### Space Complexity
Most sorting algorithms sort a collection in place without requiring any noticeable
extra storage. We now present Merge Sort, which offers O(n log n) behavior in the
worst case while using O(n) extra storage.

Merge Sort trades extra memory for guaranteed \(O(n\log n)\)  performance

Most sorting algorithms sort a collection in place, An **in-place sorting algorithm** rearranges the elements inside the original array, using only a small amount of additional memory.

For example:

```text
Before:
[8, 3, 5, 1, 9, 2]

After:
[1, 2, 3, 5, 8, 9]
```

The algorithm modifies the same array rather than creating another large array.

Examples include:

* Insertion Sort → \(O(1)\) extra space
* Selection Sort → \(O(1)\)
* Heap Sort → \(O(1)\)
* Quicksort → typically \(O(\log n)\) stack space

Merge Sort is different, **Merge Sort needs additional storage.**

The basic idea is:

```text
              [8 3 5 1 9 2]
                    ↓
             divide into halves
              /             \
          [8 3 5]          [1 9 2]
           /   \             /   \
        [8]   [3 5]       [1]  [9 2]
              ↓                  ↓
            [3 5]              [2 9]
               \                /
                \              /
                 [3 5 8]   [1 2 9]
                      \       /
                       \     /
                    [1 2 3 5 8 9]
```
Each recursive call of sort will require space equivalent to the size of the array, or
O(n), and there will be O(log n) such recursive calls; thus the storage requirement
for this naïve implementation is O(n log n). Fortunately there is a way to use only
O(n) storage, as we now discuss.

**Why does Merge Sort need \(O(n)\) extra storage?**

Suppose we need to merge:

```text
Left:  [3, 8]
Right: [1, 5]
```

We cannot simply overwrite the original elements without potentially destroying values that we still need.

So we use a temporary array:

```text
Left       Right       Temporary
[3, 8]     [1, 5]      [1, 3, 5, 8]
                         ↑
                    merged result
```

For \(n\) elements, the temporary storage can contain approximately \(n\) elements.

Therefore:

$$
\text{"Extra Space"} = O(n)
$$

This is the major space disadvantage of the standard array-based Merge Sort.

### Implementation
Merge Sort merges the left- and right-sorted subarrays using two indices i and j to
iterate over the left (and right) elements, always copying the smaller of A[i] and A[j]
into its proper location result[idx]. There are three cases to consider:
• The right side is exhausted (j ≥ end), in which case the remaining elements are
taken from the left side
• The left side is exhausted (i ≥ mid), in which case the remaining elements are
taken from from the right side
• The left and right side have elements; if A[i] < A[j], insert A[i] otherwise insert
A[j]
Once the for loop completes, result has the merged (and sorted) elements from
the original A[start, end).

Because copy is a true copy of the entire array A, the terminating base cases of the
recursion will work because it references the original elements of the array directly at
their respective index locations. This observation is a sophisticated one and is key to
the algorithm. In addition, the final merge step requires only O(n) operations,

The paragraph is explaining **why this particular implementation of Merge Sort is both \(O(n\log n)\) in time and \(O(n)\) in space**, and the key idea is the use of the two arrays `A` and `result`.

** 1. The merge phase takes \(O(n)\)**

After the recursive calls have sorted the two halves:

```text
left half       right half
[1, 4, 8]       [2, 3, 7]
```

the algorithm merges them:

```text
[1, 2, 3, 4, 7, 8]
```

It uses three indexes:

```text
i     → left half
j     → right half
idx   → result
```

Each element is examined and copied into `result` **once**.

Therefore:
$$
\text{Merge} = O(n)
$$

The important point is that the merge does **not** repeatedly scan the arrays.

---

** 2. Why does the recursion use `A` and `result` in reverse?**

This is the sophisticated part of the implementation.

The initial call is:

```python
copy = list(A)
mergesort_array(copy, A, 0, len(A))
```

So initially:

```text
A       → copy
result  → original A
```

But the recursive calls are:

```python
mergesort_array(result, A, start, mid)
mergesort_array(result, A, mid, end)
```

Notice that the arguments are reversed.

So the next level becomes:

```text
A       → original A
result  → copy
```

Then the next level reverses them again:

```text
A       → copy
result  → original A
```

Therefore, the two arrays **alternate their roles at every recursion level**.

```text
Level 0:
copy ──────────────→ source
A    ←────────────── result

Level 1:
A    ──────────────→ source
copy ←────────────── result

Level 2:
copy ──────────────→ source
A    ←────────────── result

Level 3:
A    ──────────────→ source
copy ←────────────── result
```

This avoids creating a new temporary array at every recursive call.

---

** 3. Why is `copy = list(A)` important?**

At the beginning:

```python
copy = list(A)
```

creates a **true copy** of the original array.

For example:

```text
A:
[8, 3, 5, 1]

copy:
[8, 3, 5, 1]
```

They contain the same values, but they are two separate arrays.

This gives the algorithm two complete storage areas:

```text
A       ← original array
copy    ← auxiliary array
```

The algorithm can therefore safely move data back and forth between them.

---

** 4. The clever part: the base cases**

Consider a range containing two elements:

```text
[8, 3]
```

The base case does:

```python
if end - start == 2:
    if result[start] > result[start + 1]:
        result[start], result[start + 1] = (
            result[start + 1],
            result[start],
        )
    return
```

The key is that **`result` already contains the correct original values** for that range.

Why?

Because `copy` was initialized as an exact copy of `A`:

```python
copy = list(A)
```

So at the bottom of the recursion, the algorithm doesn't need to reconstruct the original values. They already exist in one of the two arrays.

This is what the passage means by:

> “the terminating base cases of the recursion will work because it references the original elements of the array directly”

The two arrays act as alternating **source and destination buffers**.

---

** 5. Why is the total time \(O(n\log n)\)?**

Think of Merge Sort as a tree:

```text
                         n
                       /   \
                     n/2   n/2
                    / \     / \
                  n/4 n/4 n/4 n/4
                   ...
```

There are:

$$
O(\log n)
$$

levels.

At **each level**, the total amount of merging work is: $O(n)$

because every element participates in the merging at that level.

Therefore:

$$
O(n) \times O(\log n)
=
O(n\log n)
$$

The merge itself is linear, so it doesn't introduce an additional factor.

---

** 6. Why is the space \(O(n)\)?**

The algorithm creates only one additional full-size array:

```python
copy = list(A)
```

If `A` contains \(n\) elements:

```text
A       → n elements
copy    → n elements
```

The recursive calls don't create additional arrays proportional to \(n\). They only use a small amount of information such as:

```text
start
end
mid
i
j
idx
```

Therefore the auxiliary array dominates the space usage:

$$
\boxed{O(n)}
$$

There is also recursion-stack space, \(O(\log n)\), but:

$$
O(n) + O(\log n) = O(n)
$$

So the total auxiliary space remains:

$$
\boxed{O(n)}
$$

---

**The key idea to remember**

The clever part of this implementation is **not simply that it uses a copy**.

It is that **the original array and its copy alternate between being the source and destination at each recursion level**:

```text
             Merge Sort
                 │
        ┌────────┴────────┐
        ↓                 ↓
   source array       destination
        │                 │
        └────── merge ────┘
                 │
            swap roles
                 ↓
   destination becomes source
   source becomes destination
```

This allows the algorithm to perform all merging using **one \(O(n)\) auxiliary array**, rather than allocating a new temporary array during every merge.

** Final complexity**

| Property        |           Complexity |
| --------------- | -------------------: |
| Divide          | \(O(\log n)\) levels |
| Merge per level |             \(O(n)\) |
| **Total time**  |   **\(O(n\log n)\)** |
| Auxiliary array |             \(O(n)\) |
| Recursion stack |        \(O(\log n)\) |
| **Total space** |         **\(O(n)\)** |

### Usage and Applications
#### sort data that is stored externally in a file
Merge Sort can be used to efficiently sort data that
is stored externally in a file.

**Why is Merge Sort useful for external files?**

Suppose you have a file containing:

```text
500 GB of records
```

but your computer has only:

```text
16 GB RAM
```

You cannot load the entire file into memory and use an ordinary in-memory sorting algorithm.

Merge Sort is well suited to this situation because its **divide → sort → merge** structure can work with data stored on disk.

A simplified external merge sort looks like this:

```text
              Huge file
                  │
          divide into chunks
                  ↓
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Chunk A    Chunk B    Chunk C
       │          │          │
      sort       sort       sort
       ↓          ↓          ↓
    sorted A   sorted B   sorted C
       └──────────┼──────────┘
                  ↓
             merge files
                  ↓
            sorted file
```

For example:

```text
Input file
    ↓
Read manageable chunk
    ↓
Sort chunk in RAM
    ↓
Write sorted chunk to disk
    ↓
Repeat
    ↓
Merge sorted chunks
    ↓
Final sorted file
```

This is the fundamental idea behind **External Merge Sort**.

**Merge Sort sacrifices \(O(n)\) extra memory in exchange for guaranteed \(O(n\log n)\) sorting and an algorithmic structure that works particularly well with data stored outside main memory.**

That last point is why Merge Sort is much more than simply “another \(O(n\log n)\) sorting algorithm”: **its sequential merging behavior makes it especially suitable for external sorting.**

Of all the sorting algorithms, Merge Sort is the easiest one to convert to working
with external data. Next Example contains a full Java implementation using memory
mapping of data to efficiently sort a file containing binary-encoded integers. This
sorting algorithm requires the elements to all have the same size, so it can’t easily be
adapted to sort arbitrary strings or other variable-length elements.

    File copy = File.createTempFile("Mergesort", ".bin");

    copyFile(A, copy);

    RandomAccessFile src = new RandomAccessFile(A, "rw");
    RandomAccessFile dest = new RandomAccessFile(copy, "rw");

    FileChannel srcC = src.getChannel();
    FileChannel destC = dest.getChannel();

    MappedByteBuffer srcMap = srcC.map(
        FileChannel.MapMode.READ_WRITE,
        0,
        src.length()
    );

    MappedByteBuffer destMap = destC.map(
        FileChannel.MapMode.READ_WRITE,
        0,
        dest.length()
    );

    mergesort(
        destMap,
        srcMap,
        0,
        (int) A.length()
    );

    // The following two invocations are only needed on Windows.
    closeDirectBuffer(srcMap);
    closeDirectBuffer(destMap);

    src.close();
    dest.close();

static void mergesort(
        MappedByteBuffer A,
        MappedByteBuffer result,
        int start,
        int end
) throws IOException {

    // Less than two integers.
    if (end - start < 8) {
        return;
    }

    // Exactly two integers.
    if (end - start == 8) {
        result.position(start);

        int left = result.getInt();
        int right = result.getInt();

        if (left > right) {
            result.position(start);
            result.putInt(right);
            result.putInt(left);
        }

        return;
    }

    // Calculate the midpoint.
    int mid = (end + start) / 8 * 4;

    // Recursively sort left half.
    mergesort(result, A, start, mid);

    // Recursively sort right half.
    mergesort(result, A, mid, end);

    // Merge the two sorted halves.
    result.position(start);

    for (
        int i = start, j = mid, idx = start;
        idx < end;
        idx += 4
    ) {
        int Ai = A.getInt(i);
        int Aj = 0;

        if (j < end) {
            Aj = A.getInt(j);
        }

        if (j >= end || (i < mid && Ai < Aj)) {
            result.putInt(Ai);
            i += 4;
        } else {
            result.putInt(Aj);
            j += 4;
        }
    }
}

So the program can work with a very large file without explicitly loading the entire file into a Java array.

---

**4. The first `mergesort(File A)` method**

This method prepares the files and memory mappings.

**Step 1 — Create a temporary file**

```java
File copy = File.createTempFile("Mergesort", ".bin");
```

We need **two copies** of the data because the Merge Sort implementation alternates between two buffers.

Conceptually:

```text
Original file A
       │
       │ copy
       ▼
Temporary file
```

---

**Step 2 — Copy the original file**

```java
copyFile(A, copy);
```

Now:

```text
A:     [8][3][5][1]

copy:  [8][3][5][1]
```

Both files contain the same integers.

This is exactly the same idea as the previous in-memory implementation:

```python
copy = list(A)
```

except now the arrays have been replaced by **files**.

---

**5. Open both files**

```java
RandomAccessFile src = new RandomAccessFile(A, "rw");
RandomAccessFile dest = new RandomAccessFile(copy, "rw");
```

We open both files for reading and writing.

Then:

```java
FileChannel srcC = src.getChannel();
FileChannel destC = dest.getChannel();
```

A `FileChannel` gives us a channel through which the files can be mapped into memory.

---

**6. Memory-map the files**

```java
MappedByteBuffer srcMap = srcC.map(
    FileChannel.MapMode.READ_WRITE,
    0,
    src.length()
);
```

This maps the entire source file.

Similarly:

```java
MappedByteBuffer destMap = destC.map(
    FileChannel.MapMode.READ_WRITE,
    0,
    dest.length()
);
```

maps the temporary file.

Now we have:

```text
srcMap
   ↓
Original file A

destMap
   ↓
Temporary file
```

The important thing is that these are not ordinary Java arrays.

They are buffers backed by the files.

---

**7. The initial recursive call**

The code then calls:

```java
mergesort(
    destMap,
    srcMap,
    0,
    (int) A.length()
);
```

Notice something very important:

```text
A parameter       = destMap
result parameter  = srcMap
```

So initially:

```text
A      → temporary file
result → original file
```

This looks backwards, but it is intentional.

The two buffers **alternate roles during recursion**.

---

**8. Why are `start` and `end` byte offsets?**

This is different from the Python implementation.

Python used:

```text
start = element index
end   = element index
```

Here:

```text
start = byte offset
end   = byte offset
```

For example:

```text
Integer       Byte offset
-------       -----------
8             0
3             4
5             8
1             12
```

So:

```java
getInt(0)
```

reads the first integer.

```java
getInt(4)
```

reads the second integer.

```java
getInt(8)
```

reads the third integer.

---

**9. Why is the base case `< 8`?**

Each integer requires 4 bytes.

Therefore:

```text
1 integer = 4 bytes
2 integers = 8 bytes
```

So:

```java
if (end - start < 8) {
    return;
}
```

means:

> If this range contains fewer than two integers, it is already sorted.

For example:

```text
end - start = 4
```

means:

```text
[one integer]
```

No sorting is necessary.

---

**10. The two-element base case**

The next case is:

```java
if (end - start == 8) {
```

Exactly 8 bytes means:

```text
[two integers]
```

The code reads them:

```java
result.position(start);

int left = result.getInt();
int right = result.getInt();
```

Suppose:

```text
[8][3]
```

Then:

```text
left  = 8
right = 3
```

The algorithm checks:

```java
if (left > right)
```

and swaps them:

```text
[3][8]
```

The important detail is that the values are accessed through:

```java
result
```

rather than creating another temporary array.

---

**11. Calculating the midpoint**

The code uses:

```java
int mid = (end + start) / 8 * 4;
```

This deserves careful attention.

Because the indexes represent **byte offsets**, the midpoint needs to fall on a 4-byte integer boundary.

Conceptually:

```text
start                    end
  │                       │
  ▼                       ▼
  [ int ][ int ][ int ][ int ]
              ↑
             mid
```

The expression effectively calculates a midpoint aligned to a 4-byte integer.

A clearer equivalent way to understand it is:

```text
number of bytes
       ↓
number of integers
       ↓
split in half
       ↓
convert back to bytes
```

For example, with 8 integers:

```text
32 bytes
```

we want:

```text
16 bytes | 16 bytes
```

---

**12. Recursive sorting**

Now we get to the core:

```java
mergesort(result, A, start, mid);
mergesort(result, A, mid, end);
```

Notice the arguments are reversed.

Before:

```text
A      = destMap
result = srcMap
```

Inside the recursive calls:

```text
A      = srcMap
result = destMap
```

This is the same **alternating-buffer technique** from the previous implementation.

```text
Level 0:
source      = destMap
destination = srcMap

Level 1:
source      = srcMap
destination = destMap

Level 2:
source      = destMap
destination = srcMap
```

This avoids allocating another buffer for every recursive call.

---

**13. The merge operation**

After both halves have been recursively sorted:

```java
result.position(start);
```

the algorithm merges:

```text
A[start .. mid)
A[mid   .. end)
```

into:

```text
result[start .. end)
```

Suppose:

```text
Left half:   [3, 8]
Right half:  [2, 7]
```

The merge proceeds:

```text
Compare 3 and 2
→ write 2

Compare 3 and 7
→ write 3

Compare 8 and 7
→ write 7

Right half exhausted
→ write 8
```

Result:

```text
[2, 3, 7, 8]
```

---

**14. Understanding `i`, `j`, and `idx`**

The loop initializes:

```java
for (
    int i = start,
        j = mid,
        idx = start;
    idx < end;
    idx += 4
)
```

These three variables have different jobs:

```text
i
↓
current element in LEFT half

j
↓
current element in RIGHT half

idx
↓
next position in RESULT
```

For example:

```text
A:

start                mid                  end
  │                    │                    │
  ▼                    ▼                    ▼
 [3] [8]              [2] [7]
  ↑                    ↑
  i                    j

result:

 [ ] [ ] [ ] [ ]
  ↑
 idx
```

---

**15. Reading the two candidates**

```java
int Ai = A.getInt(i);
```

gets the current element from the left half.

Then:

```java
int Aj = 0;

if (j < end) {
    Aj = A.getInt(j);
}
```

gets the current element from the right half, if one still exists.

---

**16. Choosing which element to copy**

The most important condition is:

```java
if (j >= end || (i < mid && Ai < Aj)) {
```

There are two situations where we choose `Ai`.

**Case 1 — Right half is exhausted**

```java
j >= end
```

There is nothing left in the right half.

So we must take from the left:

```java
result.putInt(Ai);
```

**Case 2 — Left element is smaller**

```java
i < mid && Ai < Aj
```

For example:

```text
Left:  [3, 8]
Right: [5, 7]

3 < 5
```

so:

```text
result ← 3
```

Then:

```java
i += 4;
```

moves to the next integer in the left half.

---

**17. Otherwise, take from the right**

```java
else {
    result.putInt(Aj);
    j += 4;
}
```

For example:

```text
Left:  [3, 8]
Right: [2, 7]
```

Since:

```text
2 < 3
```

we write:

```text
result ← 2
```

and move `j` forward:

```java
j += 4;
```

---

**18. Complete merge example**

Suppose:

```text
Left:  [3, 8]
Right: [2, 7]
```

The pointers move like this:

```text
Step 1:

Left:  [3, 8]
        ↑
        i

Right: [2, 7]
        ↑
        j

2 < 3
→ result = [2]


Step 2:

Left:  [3, 8]
        ↑
        i

Right: [2, 7]
           ↑
           j

3 < 7
→ result = [2, 3]


Step 3:

Left:  [3, 8]
           ↑
           i

Right: [2, 7]
           ↑
           j

7 < 8
→ result = [2, 3, 7]


Step 4:

Right exhausted

→ result = [2, 3, 7, 8]
```
---

**19. Why does this work on a file?**

The key difference from normal Merge Sort is that:

```java
A.getInt(i)
```

doesn't necessarily mean:

> "Read an integer from a Java array."

Instead, `A` is a:

```java
MappedByteBuffer
```

that represents part of a file.

Likewise:

```java
result.putInt(idx)
```

writes the integer into the mapped destination file.

So the merge operation is effectively:

```text
             FILE A
        ┌──────────────┐
        │ 3  8  2  7   │
        └──────────────┘
              │
        getInt(i/j)
              │
              ▼
          Merge logic
              │
              ▼
        putInt(idx)
              │
        ┌──────────────┐
        │ 2  3  7  8   │
        └──────────────┘
          TEMP FILE
```

The operating system handles the actual memory pages behind the mapped buffers.

---

**20. Why use two files?**

This is essentially the external version of:

```text
A + copy
```

from the previous implementation.

We need two storage locations because Merge Sort needs to read from one location while writing the merged result to another.

```text
       Source
         │
         │ read
         ▼
      Merge
         │
         │ write
         ▼
     Destination
```

Then the roles are reversed during the next recursive level.

---

**21. Final complexity**

For \(n\) integers:

**Time**

There are: $O(\log n)$

levels of recursion.

At every level, the merge processes: $O(n)$

integers.

Therefore: $O(n\log n)$

**Extra space**

There is no Java `int[]` containing all the file data.

Instead, the algorithm uses a second file:

```text
copy
```

of the same size as the input.

Thus the auxiliary storage is: $\boxed{O(n)}$

where \(n\) is the number of integers.

---

**22. One important distinction**

There are actually **two different concepts of memory here**:

```text
                  Merge Sort
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
   Algorithmic space        OS/file mapping
          │                       │
       O(n) file              virtual memory
       copy buffer             pages loaded
```

`MappedByteBuffer` does **not** mean the entire file has to be physically loaded into RAM at once. The operating system manages the mapped pages.

So this approach is particularly useful when:

```text
File size >> available RAM
```

For example:

```text
10 GB binary file
        │
        ▼
Memory-mapped Merge Sort
        │
        ▼
OS manages file pages
        │
        ▼
Sorted 10 GB file
```

That is the main reason **Merge Sort is a natural choice for external sorting**: its sequential read/merge pattern works very well with data that lives in files rather than entirely in RAM.

## Compare Merge Sort vs Quick Sort
Merge Sort
- Splits the array evenly
- Does the hard work during merge
- Tree shape is predictable and balanced

Quick Sort
- Splits based on a pivot
- Does the hard work during partition
- Tree shape depends on how good your pivot is

Same Divide & Conquer family, very different personalities.
| Feature         | Merge Sort       | Quick Sort             |
| --------------- | ---------------- | ---------------------- |
| Paradigm        | Divide & Conquer | Divide & Conquer       |
| Division method | Split in halves  | Partition around pivot |
| Combine step    | Required (merge) | Not needed             |
| Space           | O(n)             | O(1)                   |
| Stability       | Stable           | Not stable             |
| Worst-case      | O(n log n)       | O(n²)                  |

### Merge Sort recursion tree
Example array:
[8, 3, 5, 4, 7, 6, 1, 2]
```
Divide phase (always balanced)
                [8 3 5 4 7 6 1 2]
               /                 \
        [8 3 5 4]               [7 6 1 2]
         /       \               /       \
     [8 3]      [5 4]         [7 6]      [1 2]
     /   \      /   \         /   \      /   \
   [8]  [3]   [5]  [4]      [7]  [6]   [1]  [2]
```
- Height of tree ≈ log n
- Every level processes all elements
- Shape never changes, no surprises

Combine phase (bottom-up)

Each level merges sorted arrays.

That's why:
- Work per level = O(n)
- Number of levels = O(log n)
- Total = O(n log n)

always Guaranteed.

### Quick Sort recursion tree (good pivot)
Same array, assume a good pivot (close to median).
```
                [8 3 5 4 7 6 1 2]
                      |
                    pivot = 5
                      |
          --------------------------------
          |                              |
      [3 4 1 2]                    [8 7 6]
           |                            |
        pivot = 3                   pivot = 7
           |                            |
     -----------                   ----------
     |         |                   |        |
   [1 2]      [4]                [6]       [8]
```
- Still roughly balanced
- Tree height ≈ log n
- Partitioning at each level costs O(n)
- So in the best/average case: Quick Sort = O(n log n)

### Quick Sort recursion tree (bad pivot)
Now imagine always picking the smallest or largest element as pivot.
```
[1 2 3 4 5 6 7 8]

pivot = 1

[ ]   [2 3 4 5 6 7 8]
        pivot = 2

[ ]   [3 4 5 6 7 8]
          pivot = 3
...
```
Tree becomes a chain:
```
height = n
work per level = n
total = O(n²)
```
This never happens to Merge Sort.

**Why Quick Sort is often faster in practice**

Even though Merge Sort has a guaranteed bound, Quick Sort often wins because:
- No extra merging arrays
- Better cache locality
- Less constant overhead
- Most pivots are "good enough"

It's a classic theoretical vs practical trade-off.

### Comparison Table
This comparison makes **Structural Division** clearer.

| Property              | Merge Sort        | Quicksort                                     |
| --------------------- | ----------------- | --------------------------------------------- |
| Division              | Structural        | Value-based                                   |
| Division mechanism    | Split into halves | Partition around pivot                        |
| Merge/Combine         | Explicit merge    | Usually no merge phase                        |
| Best                  | `O(n log n)`      | `O(n log n)`                                  |
| Average               | `O(n log n)`      | `O(n log n)`                                  |
| Worst                 | `O(n log n)`      | `O(n²)`                                       |
| Typical extra space   | `O(n)`            | `O(log n)` stack, depending on implementation |
| Stable                | Yes, normally     | Usually no                                    |
| Good for linked lists | Yes               | Less natural                                  |
| External sorting      | Excellent         | Less suitable                                 |

The fundamental difference is:

```text
Merge Sort:

STRUCTURE
   ↓
divide
   ↓
sort
   ↓
merge
```

while Quicksort is:

```text
VALUES
  ↓
choose pivot
  ↓
partition
  ↓
recursively sort partitions
```

| Aspect       | Merge Sort         | Quick Sort           |
| ------------ | ------------------ | -------------------- |
| Split        | Always in half     | Based on pivot       |
| Tree shape   | Always balanced    | Depends on pivot     |
| Worst case   | O(n log n)         | O(n²)                |
| Average case | O(n log n)         | O(n log n)           |
| Extra memory | Needs extra arrays | In-place             |
| Stability    | Stable             | Not stable (usually) |

**Tree intuition summary**

Merge Sort: "Perfect tree every time. I'll pay the merge cost."

Quick Sort: "Let me gamble on a pivot. If I win, I'm fast. If I lose, it hurts."

That recursion tree picture explains everything about their behavior.
