expressions is formulas that show how to compute a value.

The simplest expressions are **variables** and **constants**.

A **variable** represents a value to be computed as the program runs.

a **constant** represents a value that doesn’t change.

More complicated expressions apply operators to operands (which are themselves expressions).

In the expression `a + (b * c)`, the `+` operator is applied to the operands `a` and `(b * c)`, both of which are expressions in their own right.

An **expression** is a combination of:

- variables
- constants
- operators
- function calls

that **evaluates to a value**.

Examples

```
5
a
a + b
x * y + 3
++i
func()
```

Each of these produces a value.

Example:

```c
int x = 5 + 3;
```

Here `5 + 3`: is an expression that evaluates to 8.

## Lvalues and Rvalues

In C, expressions are classified as:

- **Lvalues**
- **Non-lvalues (rvalues)**

C does NOT have the rich value categories of C++ (like xvalues, prvalues, glvalues). C keeps it simpler.

Originally, in early C:

- **lvalue** = something that can appear on the left side of `=`
- **rvalue** = something that can only appear on the right

That’s where the names come from:

- L → left-hand side
- R → right-hand side

But modern C defines it more precisely. According to the C standard (ISO/IEC 9899), an **lvalue is An expression that designates an object**. designates means:

- Refers to a storage location
- Has an identifiable memory location(but not always)
- May have an address(`&` works)

An **lvalue** (pronounced "L-value") represents an object stored in computer memory, not a constant or the result of a computation. Variables are lvalues; expressions such as `10` or `2 * i` are not.

An lvalue is An expression that identifies a specific object in memory. If you can point to storage, it’s an lvalue. If it’s just a computed value floating in a register, it’s not.

Lvalue ≠ Modifiable Lvalue, Some lvalues cannot be assigned to.

{/*<!--Memory Model View-->*/}

Think of:

```c
int x = 5;
```

Memory:

```
Address 0x100 → 5
```

- x (as lvalue) → refers to address 0x100
- x (as value) → 5

The same syntax, different semantic role depending on context.

Example:

```c
const int x = 5;
```

x is an lvalue (it refers to storage), but not a modifiable lvalue.

This fails:

```c
x = 10;   // error
```

### Arrays and Lvalues

Array names are lvalues:

```c

```

a is an lvalue.
But:

```c
a = other_array;   // invalid
```

Why?
Because array lvalues are not modifiable lvalues.
They designate storage, but you cannot assign to them.

### Lvalue Conversion (Important Concept)

When an lvalue appears in most expressions, it is automatically converted to a value.
Example:

```c
int x = 5;
int y = x;
```

Here:

- x is an lvalue
- But its value (5) is used

This is called **lvalue-to-rvalue** conversion.
The storage location is replaced with its stored value.
This happens automatically except when:

- Used with &
- Used with sizeof
- Used as left side of assignment
- Used with \_Alignof
- Used with ++ or --

## Sequence points/Sequencing

C allows expressions like:

```c
i = i + 1;
```

But what about:

```c
i = i++ + 1;
```

Is that well-defined? To answer that, the language must define: When do side effects become visible? In what order are subexpressions evaluated?

That’s where **sequence points** / **sequencing** come in.

### C89 / C99 Model

In older standards (like ISO/IEC 9899 C89/C99):

A **sequence point** is: A point in execution where all side effects of previous evaluations are complete, and no side effects of subsequent evaluations have started.

Think of it as a synchronization barrier.

**Classic Sequence Points**

There is a sequence point:

1. **At the end of a full expression**:
   i = 3; // after semicolon
2. **After the left operand of**:
   - &&
   - ||
   - ?:
   - comma operator ,
3. At function call boundary (after argument evaluation, before entering function)

Between two sequence points: An object shall not be modified more than once, or modified and accessed for other purposes.

If violated → undefined behavior

**Example 1**

```c
i = i++;
```

Why?
Between sequence points:

- i++ modifies i
- i = modifies i again
- No sequence point between them

Result: Undefined behavior.

**Example 2**

```c
printf("%d %d\n", i, i++);
```

Arguments order is unspecified.

You read and modify i without sequencing.

Undefined behavior.

### Modern Model: Sequencing (C11+)

The old model was:

- Hard to formalize
- Ambiguous in complex expressions
- Difficult for compiler optimization models

So C11 introduced a cleaner system: **Sequencing relations**

Instead of "sequence points", we now have:
Three possible relationships between evaluations:

1. **Sequenced before**:
   One evaluation is guaranteed to complete before another begins.
2. **Unsequenced**:
   Evaluations may overlap or occur in any order.
3. **Indeterminately sequenced**:
   One happens before the other, but which one is unspecified.

Undefined behavior occurs if: A side effect on a scalar object is unsequenced relative to another side effect on the same object, or unsequenced relative to a value computation using that object.

If two operations touch the same variable and the language doesn’t guarantee an order, you are in undefined-behavior territory.

**Examples Under Modern Model**

**Well-defined**

```c
i = 1;
i++;
```

Semicolon → full expression → sequenced.

**Undefined**

```c
i = i++ + 1;
```

Why?

- i++ modifies i
- i is also read for assignment
- No sequencing relation
- Mod + read unsequenced

```c
f(i, i++);
```

Function argument evaluations are unsequenced relative to each other.
So:

- One reads i
- One modifies i
- Undefined behavior

**Well-defined (because of sequencing)**

```c
i && (i = 5);
```

Logical `&&` guarantees:

- Left operand evaluated first
- If true, right operand evaluated
- There is sequencing

The Most Important Safe Rule
Never:

- Modify a variable twice in one expression
- Modify and read it again without clear sequencing

If unsure, split the expression.

**Why Compilers Care**

Because undefined behavior allows optimizations like:

```c
i = i++ + 1;
```

Compiler may assume this never happens in correct code.
It may:

- Remove code
- Reorder operations
- Produce surprising results

**Key Difference Summary**
| Old Term | Modern Term |
| ---------------------------- | ----------------------------- |
| Sequence point | Sequenced-before relation |
| Between sequence points rule | Unsequenced side effects rule |

### Side Effects

We don’t normally expect operators to modify their operands, since operators in mathematics don’t. Writing `i + j` doesn’t modify either `i` or `j`; it simply computes the result of adding `i` and `j`.

Most C operators don’t modify their operands, but some do. We say that these operators have side effects, since they do more than just compute a value.

The simple assignment operator(`=`) has side effects; it modifies its left operand. Evaluating the expression `i = 0` produces the result `0` and—as a side effect—assigns `0` to `i`.

A **side effect** means the expression changes program state.

Common side effects:

- modifying a variable
- writing to memory
- calling a function
- performing I/O

Examples:

```c
i++;        // modifies i
x = 10;     // assignment
printf("hi"); // I/O
*p = 3;     // modifies memory
```

#### Division Operator

**Integer Division**

For integers:

```c
q = a / b;
```

C defines integer division as: **The quotient is truncated toward zero**. This rule has been guaranteed since C99. That means:

- Positive numbers → normal division
- Negative numbers → result moves toward 0 (not toward −∞)

When both of its operands are integers, the `/` operator "truncates" the result by dropping the fractional part.

Thus, the value of `1 / 2` is `0`, not `0.5`.

```c
i = 5;
j = 3;
printf("%d", i / j);
```

Both i and j are int, so integer division is used. `5 / 3 = 1`, Because integer division truncates toward zero, discarding the fractional part. `5 / 3 = 1.666`... → becomes `1`.

C Uses Truncation Toward Zero, Because most hardware (x86, ARM, RISC-V) implements:

- Integer division with truncation toward zero
- Remainder computed accordingly

So C matches hardware behavior.

**Division by Zero**

Using zero as the right operand of either `/` or `%` causes undefined behavior.

##### negative operand

The C89 standard states that if either operand is negative, the result of a division can be rounded either up or down. (For example, the value of -9 / 7 could be either –1 or –2).

In C99, the result of a division is always truncated toward zero (so -9 / 7 has the value –1).
| Expression | Result |
| ---------- | ------ |
| `7 / 3` | `2` |
| `-7 / 3` | `-2` |
| `7 / -3` | `-2` |
| `-7 / -3` | `2` |
Because:

```
-2.333... → truncated toward 0 → -2
```

#### Remainder operator

The value of `i % j` is the remainder when i is divided by j. For example:

1. the value of `10 % 3` is `1`.
2. the value of `12 % 4` is `0`.

**The `%` operator requires integer operands**; if either operand is not an integer, the program won’t compile.

```c
i = 5;
j = 3;
printf("%d", i % j);
```

The % operator gives the remainder of integer division.

```
5 % 3 = 2
```

Because:

```
5 = (3 × 1) + 2
```

**General rule:**

```
a = (a / b) * b + (a % b)
```

**Division by Zero**

Using zero as the right operand of either `/` or `%` causes undefined behavior.

```
a / 0
a % 0
```

##### negative operand

For integers:

```c
r = a % b;
```

If `a` or `b` is negative, the sign of `a % b` in C89 depends on the implementation, (For example, the value of `-9 % 7` could be either `–2 `or `5`).

**In C99, The standard guarantees this identity**:

```
a == (a / b) * b + (a % b)
```

Always true (if no overflow and b ≠ 0).

C defines:

```
remainder = a - (a / b) * b
```

the value of `a % b` has the same sign as `a`(The remainder has the same sign as the dividend (left operand))

**in C99+: The remainder always has the same sign as the dividend (the left operand).**

Examples:

```
-8 % 5  → negative
8 % -5  → positive
```

In both C89 and C99, the
goal is to ensure that the value of `(a / b) * b + a % b` will always be equal to `a` (and indeed, both standards guarantee that this is the case, provided that the value
of `a / b` is "representable"). The problem is that there are two ways for a / b and
a % b to satisfy this equality if either a or b is negative, as seen in C89, where either

1. -9 / 7 is –1 and -9 % 7 is –2, or
2. -9 / 7 is –2 and -9 % 7 is 5.

In the first case, (-9 / 7) _ 7 + -9 % 7 has the value –1 × 7 + –2 = –9, and in the second
case, (-9 / 7) _ 7 + -9 % 7 has the value –2 × 7 + 5 = –9. By the time C99 rolled
around, most CPUs were designed to truncate the result of division toward zero, so
this was written into the standard as the only allowable outcome.

| Expression | Result |
| ---------- | ------ |
| `7 % 3`    | `1`    |
| `-7 % 3`   | `-1`   |
| `7 % -3`   | `1`    |
| `-7 % -3`  | `-1`   |

| Expression | Result |
| ---------- | ------ |
| `7 % 5`    | `2`    |
| `-7 % 5`   | `-2`   |
| `7 % -5`   | `2`    |
| `-7 % -5`  | `-2`   |

Notice: The sign follows `a`, not `b`.

C remainder answers: "How far past the truncated division point are we?
So For `-1 / 5`: Truncated quotient = 0, So remainder must be what gets us back to `-1`. That remainder is `-1`.

Mathematics usually defines: r ≥ 0, So mathematically:

```
-7 mod 3 = 2
```

But C does not use mathematical modulo. It uses truncated division remainder.
That’s why:

```
-7 % 3 == -1   (in C)
```

In C:

```
%  ≠ mathematical modulo
%  = remainder after truncation toward zero
```

Example:

```
-7 / 3
```

Step 1: Real division

```
-7 / 3 = -2.333...
```

Step 2: Truncate toward 0

```
-2
```

Step 3: Compute remainder:

```

-7 = -6 + r
r = -1
```

So:

```
-7 % 3 == -1
```

#### Assignment Operators

Once the value of an expression has been computed, we’ll often need to store it in a variable for later use.

C’s `=` (**simple assignment**) operator is used for that purpose. For updating a value already stored in a variable, C provides an assortment of **compound assignment operators**.
| Operator | Meaning |
| -------- | ---------------------- |
| `=` | Simple assignment |
| `+=` | Add and assign |
| `-=` | Subtract and assign |
| `*=` | Multiply and assign |
| `/=` | Divide and assign |
| `%=` | Modulus and assign |
| `<<=` | Left shift and assign |
| `>>=` | Right shift and assign |
| `&=` | Bitwise AND and assign |
| `^=` | Bitwise XOR and assign |
| `=` | Bitwise OR and assign |

##### Simple Assignment

The effect of the assignment:

```
v = e
```

is to evaluate the expression `e` and copy its value into `v`.

'e' can be:

1. a constant,
   ```c
   i = 5; /* i is now 5 */
   ```
2. a variable,
   ```c
   j = i; /* j is now 5 */
   ```
3. **or a more complicated expression**:
   ```c
   k = 10 * i + j; /* k is now 55 */
   ```

If `v` and `e` don’t have the same type, then the value of `e` is converted to the type of `v`
as the assignment takes place:

```c
int i;
float f;
i = 72.99f; /* i is now 72 */
f = 136; /* f is now 136.0 */
```

In many programming languages, assignment is a statement; in C, however, assignment is an operator, just like `+`. In other words, the act of assignment produces a result, just as adding two numbers produces a result.

The value of an assignment `v = e` is the value of `v` after the assignment. Thus, the value of `i = 72.99f` is `72` (not `72.99`).

In C, the assignment operator `=` is an expression operator, not just a statement.
That means:

```
v = e
```

1. Stores the value of e into v
1. Produces the value that was stored
1. Has a type equal to the type of v
1. Has a side effect (modifies v)

Since assignment is an operator, several assignments can be chained together:

```c
i = j = k = 0;
```

The = operator is right associative, so this assignment is equivalent to

```c
i = (j = (k = 0));
```

The effect is to assign `0` first to `k`, then to `j`, and finally to `i`.

chained assignments could produce unexpected results as a result of type conversion:

```c
int i;
float f;
f = i = 33.3f;
```

`i` is assigned the value `33`, then `f` is assigned `33.0` (not `33.3`, as you might think).

In general, an assignment of the form `v = e` is allowed wherever a value of type
`v` would be permitted. In the following example, the expression `j = i` copies `i` to
`j`; the new value of `j` is then added to `1`, producing the new value of `k`:

```c
i = 1;
k = 1 + (j = i);

printf("%d %d %d\n", i, j, k); /* prints "1 1 2" */
```

this works because:

1. (j = i) stores i into j
2. The expression evaluates to the value assigned
3. That value participates in 1 + ...

So C treats:

```
v = e
```

as:

- An expression
- With side effects
- That yields a value

This makes C powerful but also makes reasoning about evaluation order essential.

Using the assignment operator in this fashion usually isn’t a good idea. "embedded assignments" can make programs hard to read. They can also be a source of subtle bug.

1. Reduced Readability

Compare:

```c
j = i;
k = 1 + j;
```

vs

````c
k = 1 + (j = i);
```c
The second forces the reader to mentally simulate side effects.

2. Hidden Side Effects

Embedded assignments hide state changes inside expressions.
That makes reasoning about code harder, especially in:
- Large expressions
- Macro expansions
- Conditional logic

3. Sequencing and Undefined Behavior

In C11 and later, the concept is sequenced before.
Undefined behavior happens when:
- A variable is modified
- And accessed again
- Without a sequencing relationship

Embedded assignments increase the chance of violating this rule.

C does NOT guarantee left-to-right evaluation of most operators.
For example:
```v
k = i + (i = 3);   // Undefined behavior
````

Why?
Because:

- i is modified
- i is also read
- There is no sequencing between those two operations

That violates C’s rule:
An object shall not be modified more than once, or modified and accessed, between sequence points without sequencing.

Result: undefined behavior.

**Subtle Real Bug Example**

This looks innocent:

```c
while ((c = getchar()) != EOF)
```

This is actually safe and idiomatic because:

- Assignment happens
- Result is compared
- No unsequenced access

But compare:

```c
if (a[i] = b[i] && i < n)
```

Now:

- Did you mean `==?`
- Did you mean `(a[i] = b[i]) && i < n?`
- Is `i` modified elsewhere?

Readability collapses quickly.

**Order of Evaluation Is the Core Problem**

In C:

- Function arguments: order unspecified
- `+`, `*`, etc.: order unspecified
- Only a few operators enforce sequencing:
  - `&&`
  - `||`
  - `?:`
  - `,`(comma operator)

So this:

```c
f(i, i = 2);   // Undefined behavior
```

is dangerous.
Embedded assignments amplify these hazards.

**When It Is Acceptable**

Common safe pattern:

```c
while ((line = read_line()) != NULL)
```

Why safe?

- Assignment fully evaluated
- Result used immediately
- No unsequenced reuse

Another safe one:

```c
if ((p = malloc(n)) == NULL)
```

Clear, conventional, readable.

**Professional Guideline**

✔ Acceptable:

```c
while ((c = getchar()) != EOF)
```

❌ Risky:

```c
total += (count = compute());
```

🚫 Dangerous:

```c
x = y + (y = 5);
```

##### Assignment and Lvalues

Most C operators allow their operands to be variables, constants, or expressions
containing other operators. The assignment operator, however, requires an **lvalue** as its left operand.

Since the assignment operator requires an lvalue as its left operand, it’s illegal
to put any other kind of expression on the left side of an assignment expression:

```
12 = i; /*** WRONG ***/
i + j = 0; /*** WRONG ***/
-i = j; /*** WRONG ***/
```

The compiler will detect errors of this nature, and you’ll get an error message such
as "invalid lvalue in assignment."

Assignment in C:

```
E1 = E2
```

- Modifies E1
- Produces the value stored
- But the result is not a modifiable lvalue

So:

```
a = b assigns b to a
```

The expression evaluates to the value assigned. That value is not an object you can assign into. It’s just a value. You cannot assign to a value.

In C (C11/C17): The result of an assignment expression: is not an lvalue.

In C: Assignment produces a value, not a location. So you cannot assign to the result of an assignment.

| Expression      | Valid in C? | Why                          |
| --------------- | ----------- | ---------------------------- |
| `a = b = 5;`    |             | Right side produces value    |
| `(a = b) = 5;`  | ❌          | Result is not an lvalue      |
| `*(p = q) = 5;` |             | `*` produces lvalue          |
| `(*p = 3) = 4;` | ❌          | Assignment result not lvalue |

##### Compound Assignment

Assignments that use the old value of a variable to compute its new value are common in C programs. The following statement, for example, adds 2 to the value
stored in i:

```c
i = i + 2;
```

C’s compound assignment operators allow us to shorten this statement and others
like it. Using the += operator, we simply write:

```c
i += 2; /* same as i = i + 2; */
```

The += operator adds the value of the right operand to the variable on the left. There are nine other compound assignment operators, including the following:

```
-= *= /= %= /* and others */
```

:::warning

When using the compound assignment operators, be careful not to switch the two
characters that make up the operator. Switching the characters may yield an
expression that is acceptable to the compiler but that doesn’t have the intended
meaning. For example, if you meant to write `i += j` but typed `i =+ j` instead, the program will still compile. Unfortunately, the latter expression is equivalent to
`i = (+j)`, which merely copies the value of `j` into `i`.

:::

{/*<!--Why the Language Is Designed This Way-->*/}

Compound assignments exist because:

1. They map efficiently to machine instructions(e.g., add [mem], reg)
2. They avoid re-evaluating complex lvalues
3. They avoid unintended double side effects

All compound assignment operators work in much the same way:

- `v += e` adds `v` to `e`, storing the result in `v`
- `v -= e` subtracts `e` from `v`, storing the result in `v`
- `v *= e` multiplies `v` by `e`, storing the result in `v`
- `v /= e` divides `v` by `e`, storing the result in `v`
- `v %= e` computes the remainder when `v` is divided by `e`, storing the result in `v`

###### Properties

The compound assignment operators have the same properties as the `=` operator.

**Compound assignment** means: "Take the object designated by the left operand, combine it with the right operand using operator `op`, convert back to the left operand’s type, and store the result."

And crucially: The left operand is located only once.

1. **Left Operand Must Be a Modifiable Lvalue**

You cannot write:

```
(x + y) += 3;   // error
5 += 2;         // error
```

Valid:

```
x += 3;
a[i] += 1;
*p += 2;
```

Because those designate modifiable objects.

2. **Left Operand Is Evaluated Exactly Once**

This is the most important semantic property.

```c
a[i++] += 10;
```

- `i++` happens once
- The array element is determined once
- Then modified

This prevents accidental double side effects.

3. **Right Operand Is Evaluated Once**

Like normal expressions, the right operand is evaluated once.

4. **Order of Evaluation Is Not Fully Specified**

In:

```c
a[i++] += f();
```

The order between evaluating `i++` and `f()` is unspecified.
However:

- The modification of `a[i++]` is sequenced after both operands are evaluated.
  So you must still avoid unsequenced side effects involving shared variables.

5. **Type Conversions Are Special**

This is subtle and important.
For:

```
E1 op= E2
```

The steps are conceptually:

1. Compute `E1` op `E2` using usual arithmetic conversions
2. Convert the result to the type of `E1`
3. Store into `E1`

This conversion back to `E1`’s type is mandatory.
Example:

```c
char c = 1;
c += 200;
```

- c promoted to int
- 1 + 200 = 201
- Converted back to char
- Stored

6. **Result of the Expression**

The result of a compound assignment expression:

- Is not an lvalue (in C)
- Has the type of the left operand
- Has the value stored

Example:

```c
int x = 5;
int y = (x += 3);
```

After:

```
x = 8
y = 8
```

But:

```
(x += 3) = 10;   // illegal in C
```

Because result is not an lvalue.

7. **Sequencing Rule**

The side effect of updating E1 is sequenced after:

- The value computations of E1
- The value computations of E2

So this is safe:

```c
x += x;
```

Because:

- Both values are computed first
- Then update happens
  But this is not safe:

```
x += x++;
```

Because:

- x++ modifies x
- x is also read
- No sequencing between those reads/modifications
- Undefined behavior

8. **Atomicity (Important Clarification)**

Compound assignment is not atomic.

```c
x += 1;
```

is not guaranteed to be atomic in multithreaded code.
It is:

1. Read
2. Compute
3. Write

Unless you use atomic types.

9. **Precedence and Associativity**

Compound assignments:

- Have lower precedence than arithmetic operators
- Have right-to-left associativity

Example:

```c
a += b += 2;
```

Parsed as:

```c
a += (b += 2);
```

So:

1. b += 2
2. a += result

3. **Interaction with Volatile**

For:

```c
volatile int v;

```

The compiler must:

- Perform a read of v
- Perform a write to v

It cannot optimize them away.
But it is still not atomic.

###### Difference between `E1 op= E2` and `E1 = op E2`

For compound assignment:

```
E1 op= E2
```

- E1 is evaluated exactly once
- Then the operation is performed
- Then result is stored

The compound assignment operators like:

```
+=  -=  *=  /=  %=  <<=  >>=  &=  ^=  |=
```

are not defined as simple textual replacements of:

```
v = v op e
```

They are similar, but not equivalent in all cases. because:

Think of:

```
E1 op= E2
```

as conceptually:

```
temp = &E1;
*temp = *temp op E2;
```

Not as textual substitution.
That is closer to how compilers implement it.

Never assume:

```
v op= e
```

is safe to replace with:

```
v = v op e
```

when v has side effects.

1. **Operator Precedence**

Consider:

```c
i *= j + k;
```

This means:

```c
i = i * (j + k);
```

NOT:

```c
i = i * j + k;
```

Because:

- `*=` has lower precedence than `+`.
- So `j + k` is grouped first.

2. **v Is Evaluated Only Once**

The C standard (C11/C17 in ISO/IEC 9899) says:
For:

```
E1 op= E2
```

It is equivalent to:

```
E1 = E1 op E2
```

except that E1 is evaluated only once.

In:

```c
v += e;
```

The expression `v` is evaluated exactly once.

But in:

```c
v = v + e;
```

The expression `v` is evaluated twice.

If `v` has side effects, this changes behavior.

Any side effect caused by evaluating v will occur twice in the latter case. In the following example, i is incremented once:

```c
a[i++] += 2;
```

If we use = instead of +=, here's what the statement will look like:

```c
a[i++] = a[i++] + 2;
```

The value of i is modified as well as used elsewhere in the statement, so the effect
of executing the statement is undefined. It's likely that i will be incremented
twice, but we can't say with certainty what will happen.

<details>
    <summary>Example: Array Index with Side Effecty</summary>

```c
a[i++] += 10;
```

This means:

1. Evaluate i++ once
2. Use that index
3. Add 10
4. Store result
5. Increment i once

Now compare naive expansion:

```c
a[i++] = a[i++] + 10;   // NOT equivalent
```

Now:

- i++ happens twice
- You modify i twice
- Very likely undefined behavior

Completely different program.

Let’s assume:

```
int a[5] = {0, 10, 20, 30, 40};
int i = 1;
```

**Case 1: a[i++] += 10;**

Step 1: Evaluate `i++`

- Current `i = 1`
- `i++` yields `1`
- Then increments `i` → now `i = 2`

So we are modifying: `a[1]`

Step 2: Fetch current value of `a[1]`

```

```

Step 3: Add 10

```

```

Step 4: Store back into `a[1]`

Now:

```

```

Final State

```

```

Only one increment occurred.

**Case 2: a[i++] = a[i++] + 10;**

Initial state again:

```

a = {0, 10, 20, 30, 40}
```

⚠ Important: This is Undefined Behavior, Why? Because:

- `i++` appears twice
- Both modify i
- There is no sequencing between them
- Two modifications of `i` are unsequenced

According to the C standard (ISO/IEC 9899): Modifying a scalar object multiple times without sequencing → undefined behavior.

So the program has no defined meaning.

###### Increment and Decrement Operators

Two of the most common operations on a variable are "incrementing" (adding 1)
and "decrementing" (subtracting 1).

We can, of course, accomplish these tasks by writing

```c
i = i + 1;
j = j - 1;
```

The compound assignment operators allow us to condense these statements a bit:

```c
i += 1;
j -= 1;
```

But C allows increments and decrements to be shortened even further, using the `++`
(increment) and `--` (decrement) operators.

```c
i++;
j--;
```

`++` adds 1 to its operand, whereas `--` subtracts 1.

With modern compilers, using `++` and `--` won’t make a compiled program any
smaller or faster(than for example `i = i + 1`); the continued popularity of these operators stems mostly from
their brevity and convenience.

The increment `++` and decrement `--` operations can be applied to floating-point numbers as well as integers. In practice, however, it’s fairly rare to increment or decrement a float variable.

**`++` and `--` can be used as**:

1. **prefix** operators (`++i` and `--i`, for example)
2. **postfix** operators (`i++` and `i--`).

like the assignment operators, `++` and `--` have side effects: they modify the values of their operands.

Evaluating the expression `++i` (a "pre-increment") yields `i + 1` and—as a side effect—increments `i` by `1`.

```c
i = 1;
printf("i is %d\n", ++i); /* prints "i is 2" */
printf("i is %d\n", i); /* prints "i is 2" */
```

Evaluating the expression `i++` (a "post-increment") produces the result `i`, but causes `i` to be incremented afterwards:

```c
i = 1;
printf("i is %d\n", i++); /* prints "i is 1" */
printf("i is %d\n", i); /* prints "i is 2" */
```

As these examples illustrate, `++i` means "increment i immediately," while `i++` means "use the old value of `i` for now, but increment `i` later." How much later? The C standard doesn’t specify a precise time,
but it’s safe to assume that i will be incremented before the next statement is executed.

The -- operator has similar properties:

```c
i = 1;
printf("i is %d\n", --i); /* prints "i is 0" */
printf("i is %d\n", i); /* prints "i is 0" */

i = 1;
printf("i is %d\n", i--); /* prints "i is 1" */
printf("i is %d\n", i); /* prints "i is 0" */
```

When `++` or `--` is used more than once in the same expression, the result can often be hard to understand. Consider the following statements:

```c
i = 1;
j = 2;
k = ++i + j++;
```

What are the values of i, j, and k after these statements are executed? Since i is
incremented before its value is used, but j is incremented after it is used, the last
statement is equivalent to

```c
i = i + 1;
k = i + j;
j = j + 1;
```

so the final values of i, j, and k are 2, 3, and 4, respectively. In contrast, executing
the statements

```c
i = 1;
j = 2;
k = i++ + j++;
```

will give i, j, and k the values 2, 3, and 3, respectively.

the postfix versions of `++` and `--` have higher precedence than
unary plus and minus and are left associative. The prefix versions have the same
precedence as unary plus and minus and are right associative.

From highest to lower:
| Level | Operators | Associativity |
| ------- | ------------------------------------ | ------------- |
| Postfix | `x++  x--  ()  []  .  ->` | Left-to-right |
| Unary | `++x  --x  +  -  !  ~  *  &  sizeof` | Right-to-left |

So:

- Postfix ++/-- bind tighter
- Prefix ++/-- share precedence with unary + and -

Precedence determines grouping, not evaluation order.

For Example:

```
-x++
```

Because postfix has higher precedence than unary minus, it parses as:

```
-(x++)
```

NOT:

```
(-x)++
```

The second form is illegal anyway.

Postfix Is Left-Associative, Postfix operators group left to right.

Example:

```
a[i]++
```

Parsed as:

```
(a[i])++
```

And:

```
*p++
```

Parsed as:

```
*(p++)
```

NOT:

```
(*p)++
```

Because postfix binds tighter than unary \*.

This is one of the most important C parsing rules.

Prefix Is Right-Associative, Prefix operators group right to left.

Example:

```
++*p
```

Since prefix operators are right-associative:

```
++(*p)
```

Because `*p` is formed first (unary level), then `++` applies.

Another example:

```
- -x
```

Parsed as:

```
-(-x)
```

Right-to-left grouping.

**Summary Table**
| Operator | Type | Precedence | Associativity |
| -------- | ------- | ------------------- | ------------- |
| `x++` | Postfix | Higher | Left-to-right |
| `x--` | Postfix | Higher | Left-to-right |
| `++x` | Prefix | Lower (unary level) | Right-to-left |
| `--x` | Prefix | Lower (unary level) | Right-to-left |

### Relational (Comparison) Operators

Used to compare values.
| Operator | Meaning |
| -------- | --------------------- |
| `<` | Less than |
| `>` | Greater than |
| `<=` | Less than or equal |
| `>=` | Greater than or equal |
| `==` | Equal to |
| `!=` | Not equal to |

C’s relational operators correspond to the `<`, `>`, `≤`, and `≥` operators of
mathematics, except that they produce `0 (false)` or `1 (true)` when used in expressions. For example, the value of `10 < 11` is `1`; the value of `11 < 10` is `0`.

The relational operators can be used to compare integers and floating-point
numbers, with operands of mixed types allowed. Thus, `1 < 2.5` has the value `1`,
while `5.6 < 4` has the value `0`.

The precedence of the relational operators is lower than that of the arithmetic
operators; for example, `i + j < k - 1` means `(i + j) < (k - 1)`.

The relational operators are left associative.

**Equality Operators**

Although the relational operators are denoted by the same symbols as in many
other programming languages, the equality operators have a unique appearance . The "equal to" operator is two adjacent `=` characters, not one, since a
single `=` character represents the assignment operator. The "not equal to" operator
is also two characters: `!` and `=`.

Like the relational operators, the equality operators are left associative and
produce either 0 (false) or 1 (true) as their result. However, the equality operators
have lower precedence than the relational operators. For example, the expression

```
i < j == j < k
```

is equivalent to

```
(i < j) == (j < k)
```

which is true if `i < j` and `j < k` are both `true` or both `false`.

### Logical Operators

Used for logical expressions.

The `!` operator is unary, while `&&` and `||` are binary.
| Operator | Meaning |
| -------- | ----------- |
| `&&` | Logical AND |
| `||` | Logical OR |
| `!` | Logical NOT |

The logical operators produce either 0 or 1 as their result. Often, the operands
will have values of 0 or 1, but this isn’t a requirement; the logical operators treat
any nonzero operand as a true value and any zero operand as a false value.
The logical operators behave as follows:

- `!expr` has the value `1` if `expr` has the value `0`.
- `expr1 && expr2` has the value `1` if the values of `expr1` and `expr2` are both nonzero.
- `expr1 || expr2` has the value `1` if either `expr1` or `expr2` (or both) has a nonzero value.

In all other cases, these operators produce the value 0.

The `!` operator has the same precedence as the unary plus and minus operators. The precedence of `&&` and `||` is lower than that of the relational and equality
operators; for example, `i < j && k == m` means `(i < j) && (k == m)`. The !
operator is right associative; && and || are left associative.

### Conditional (Ternary) Operator

C also provides an operator that allows an expression to produce one of two values depending on the value of a condition.

The conditional operator consists of two symbols (`?` and `:`), which must be used together in the following way:

```
expr1 ? expr2 : expr3
```

`expr1`, `expr2`, and `expr3` can be expressions of any type. The resulting expression is said to be a conditional expression.

| Operator | Meaning                |
| -------- | ---------------------- |
| `?:`     | Conditional expression |

The conditional operator is unique among C operators in that it requires three operands instead of one or two. For this reason, it is often referred to as a **ternary operator**.

The conditional expression `expr1 ? expr2 : expr3` should be read "if expr1 then expr2 else expr3." The expression is evaluated in stages:

1. `expr1` is evaluated first;
2. if its value isn’t zero, then `expr2` is evaluated, and its value is the value of the entire conditional expression.
3. If the value of `expr1` is zero, then the value of `expr3` is the value of the conditional.

**Precedence of the Conditional Operator**

The conditional operator ?: has very low precedence—it is near the bottom of the precedence table. It has lower precedence than most operators, including:

- Arithmetic: `+ - \* / %`
- Relational: `< > <= >=`
- Equality: `== !=`
- Logical: `&& ||`
- Assignment: `= += -=` (⚠️ actually assignment is even lower)

Simplified Precedence Order (high → low)
| Level | Operators | | |
| -------- | ----------- | - | - |
| High | `* / %` | | |
| | `+ -` | | |
| | `< <= > >=` | | |
| | `== !=` | | |
| | `&&` | | |
| | `          |   |` |
| ⬇️ Low | `?:` | | |
| Very Low | `=` | | |

**Associativity**

The conditional operator is right-to-left associative

```c
a ? b : c ? d : e;
```

is interpreted as:

```c
a ? b : (c ? d : e);
```

Example 1

```c
int x = 5;
int y = 10;

int z = x > y ? x : y + 1;
```

Interpretation: Because `+` has higher precedence than `?::`

```c
z = (x > y) ? x : (y + 1);
```

Example 2

```c
int z = a + b > c ? a : b;
```

Interpretation

```c
z = ((a + b) > c) ? a : b;
```

Example 3 (tricky)

```c
int z = a ? b : c + d;
```

Interpretation

```c
z = a ? b : (c + d);
```

Interaction with Assignment

```c
int x;
x = a > b ? a : b;
```

This works because:

```c
x = (a > b ? a : b);
```

Since = has lower precedence than ?:.

**Common Pitfall**

```c
int x = a > b ? a : b + 1;
```

Many think:

```c
(x = (a > b ? a : b)) + 1   // ❌ WRONG
```

Correct:

```c
x = (a > b) ? a : (b + 1);
```

| `&` | Isolates the field |

- network packet headers
- CPU instruction decoding
- hardware registers

#### Absolute Value Using Bitwise
a branchless, bitwise trick to compute the absolute value of an int, which avoids if statements and works even for INT_MIN.

```c
#include <stdio.h>
#include <limits.h>

int abs_bitwise(int i) {
    int mask = i >> (sizeof(int)*8 - 1); // all 1s if i<0, all 0s if i>=0
    return (i + mask) ^ mask;
}

int main() {
    int a = -17;
    int b = 42;
    int c = INT_MIN;

    printf("abs(-17) = %d\n", abs_bitwise(a));
    printf("abs(42)  = %d\n", abs_bitwise(b));
    printf("abs(INT_MIN) = %u\n", (unsigned)abs_bitwise(c));

    return 0;
}
```
How It Works
1. `mask = i >> 31` (assuming 32-bit int) 
    - If `i >= 0` → mask = 0 
    - If `i < 0` → mask = -1 (all bits 1) 
2. `(i + mask) ^ mask `
    - If `i >= 0`: `(i + 0) ^ 0 = i` → stays positive 
    - If `i < 0`: (`i - 1) ^ -1 = -i` → flips bits + adds 1 → two’s complement 
3. Works for `INT_MIN` in unsigned context, giving `2147483648`.

Step by Step

Case 1: i = -5 (8-bit example)

Step 1: Represent -5 in 8-bit two’s complement
- i = -5 → 11111011

Step 2: Compute mask = i >> 7
- Arithmetic shift (sign-extended) 
- -5 >> 7 = 11111111 → mask = -1 

Step 3: Compute (i + mask)
```
i + mask = 11111011 + 11111111
          = 11111010  (overflow ignored)
```
Step 4: XOR with mask
```
(i + mask) ^ mask = 11111010 ^ 11111111
                  = 00000101 → 5
```
✅ Absolute value of -5 is 5

Case 2: i = 5 (8-bit example)

Step 1: i in binary
- i = 5 → 00000101

Step 2: Compute mask = i >> 7
- `5 >> 7` = 0 → mask = 00000000

Step 3: Compute (i + mask)
- i + mask = 00000101 + 00000000 = 00000101
Step 4: XOR with mask
```
(i + mask) ^ mask = 00000101 ^ 00000000 = 00000101 → 5
```
✅ Absolute value of 5 is 5

Advantages
- No branches → good for performance-critical code
- Works for all integers including INT_MIN (in unsigned context)
- Pure integer operations, no function calls

### Operators Precedence and Associativity

When an expression contains more than one operator, its interpretation may not be
immediately clear. For example, does `i + j * k` mean "add i and j, then multiply
the result by k," or does it mean "multiply j and k, then add i"? One solution to
this problem is to add parentheses, writing either `(i + j) * k` or `i + (j * k)`.

As
a general rule, C allows the use of parentheses for grouping in all expressions.

What if we don’t use parentheses, though? Will the compiler interpret `i + j * k` as

1. `(i + j) * k` or
2. `i + (j * k)`?

Like many other languages, C uses operator precedence rules to resolve this potential ambiguity.

Operators follow a strict precedence and associativity order.

The arithmetic operators have the following relative precedence:

```
Highest: + -   (unary)
         * / %
Lowest:  + -    (binary)
```

Operators listed on the same line (such as + and -) have equal precedence.

When two or more operators appear in the same expression, we can determine
how the compiler will interpret the expression by repeatedly putting parentheses
around subexpressions, starting with high-precedence operators and working down
to low-precedence operators. The following examples illustrate the result:

```
i + j * k is equivalent to i + (j * k)
-i * -j is equivalent to (-i) * (-j)
+i + j / k is equivalent to (+i) + (j / k)
```

Operator precedence rules alone aren’t enough when an expression contains two
or more operators at the same level of precedence. In this situation, the **associativity** of the operators comes into play.

An operator is said to be **left associative** if it groups from left to right.

The binary arithmetic operators (\*, /, %, +, and -) are all left associative, so

```
i - j - k is equivalent to (i - j) - k
i * j / k is equivalent to (i * j) / k
```

An operator is **right associative** if it groups from right to left. The unary arithmetic operators (+ and -) are both right associative, so

```
- + i is equivalent to -(+i)
```

### Order of Subexpression Evaluation

The rules of operator precedence and associativity allow us to break any C expression into subexpressions—to determine uniquely where the parentheses would go if the expression were fully parenthesized. these rules don't always
allow us to determine the value of the expression, which may depend on the order in which its subexpressions are evaluated.

Most expressions have the same value regardless of the order in which their subexpressions are evaluated.

C doesn't define the order in which subexpressions are evaluated (with the exception of subexpressions involving the logical and, logical or, conditional, and comma operators).

**In C: The order in which subexpressions are evaluated is mostly unspecified**. Except where the standard explicitly guarantees sequencing. This gives compilers freedom to optimize aggressively.

**Unspecified** means: The compiler may choose any order, and different compilers (or even different optimization levels) may choose different orders.

Thus, in the expression `(a + b) * (c - d)` we don't know whether `(a + b`) will be evaluated before `(c - d)`.

The effect of executing the second statement is undefined; the C standard doesn’t
say what will happen. With most compilers, the value of `c` will be either `6` or `2`. If
the subexpression `(b = a + 2)` is evaluated first, `b` is assigned the value `7` and `c` is
assigned `6`. But if `(a = 1)` is evaluated first, `b` is assigned `3` and `c` is assigned `2`.

Avoid writing expressions that access the value of a variable and also modify the
variable elsewhere in the expression. The expression `(b = a + 2) - (a = 1)`
accesses the value of `a` (in order to compute `a + 2`) and also modifies the value of
a (by assigning it `1`). Some compilers may produce a warning message such as
"operation on `a` may be undefined" when they encounter such an expression.

To prevent problems, it's a good idea to avoid using the assignment operators in subexpressions; instead, use a series of separate assignments. For example, the statements above could be rewritten as

```c
a = 5;
b = a + 2;
a = 1;
c = b - a;
```

The value of `c` will always be `6` after these statements are executed.

Besides the assignment operators, the only operators that modify their operands are increment and decrement. When using these operators, be careful that your expressions don't depend on a particular order of evaluation. In the following
example, j may be assigned one of two values:

```c
i = 2;
j = i * i++;
```

It's natural to assume that j is assigned the value 4. However, the effect of executing the statement is undefined, and j could just as well be assigned 6 instead. Here's the scenario:

1. The second operand (the original value of i) is fetched, then i is incremented.
2. The first operand (the new value of i) is fetched.
3. The new and old values of i are multiplied, yielding 6.

"Fetching" a variable means to retrieve the value of the variable from memory. A later change to the variable won't affect the fetched value, which is typically stored in a special location (known as a register) inside the CPU.

Example:

```
int x = f() + g();
```

C does NOT guarantee whether:

- `f()` runs first
- or `g()` runs first

Both are allowed.

C defines:

- How expressions group (precedence)
- NOT when subexpressions run

Evaluation order is mostly unspecified. If side effects overlap without sequencing → undefined behavior.

The Golden Rule for Advanced C:Never modify a variable more than once in a single expression unless sequencing is guaranteed.

Bad:

```c
i = i++ + ++i;
```

Good:

```c
i++;
i++;
```

C Is Designed This Way, Because C prioritizes:

- Performance
- Optimization freedom
- Mapping closely to hardware

Strict left-to-right rules would limit compiler optimizations.

##### The Modern C Model: Sequencing (C11 and later)

C uses the concept of:

- **Sequenced before**
- **Unsequenced**
- **Indeterminately sequenced**

1. **Sequenced Before**

If A is sequenced before B:

- A finishes completely
- All its side effects are done
- Then B starts

Example:

```
a = b;
```

The right-hand side (b) is sequenced before the assignment to a.

2. **Unsequenced**

If two operations are unsequenced:

- The compiler may interleave them
- If they modify the same object → undefined behavior

Example:

```
i = i++ + 1;   // undefined behavior
```

Why? Because:

- i++ modifies i
- i is also read for the addition
- These are unsequenced relative to each other

The standard says: If a scalar object is modified more than once, or modified and read without sequencing, the behavior is undefined.

3. **Indeterminately Sequenced**

One happens before the other, but you don’t know which.
Example:

```
f(), g();
```

Comma operator guarantees:

- f() is sequenced before g()
  But in:

```
f() + g();
```

They are unsequenced.

##### Places Where C Guarantees Order

Here are the important guaranteed sequencing points:

1. **Logical AND &&**

Left operand is evaluated first.
If false → right operand is NOT evaluated.

```c
a && b
```

a is sequenced before b.

2. **Logical OR ||**

Left operand first.
If true → right operand skipped.

3. **Conditional Operator ?:**

cond ? x : y

- cond evaluated first
- Only one of x or y evaluated

4. **Comma Operator ,**

```c
a, b
```

a is sequenced before b.

5. **Function Call**

In:

```c
f(a, b, c);
```

- The arguments are evaluated in unspecified order.
- But each argument is fully evaluated before entering f.

So:

```c
f(i++, i++);
```

Undefined behavior:
Two modifications of i, unsequenced.

6. **Assignment**

In:

```c
a = b;
```

- b is evaluated first
- Then assignment happens

But in:

```c
a = f() + g();
```

f() and g() order is unspecified.

So, Unless you see:

- `&&`
- `||`
- `?:`
- comma operator
- separate statements

Assume subexpressions may be evaluated in any order.

| Operator              | Operand Order Guaranteed? |     |               |
| --------------------- | ------------------------- | --- | ------------- |
| `+ - * /`             | ❌ No                     |     |               |
| `&&`                  | ✅ Left first             |     |               |
| `                     |                           | `   | ✅ Left first |
| `?:`                  | ✅ Condition first        |     |               |
| `,` (operator)        | ✅ Left first             |     |               |
| Function arguments    | ❌ No                     |     |               |
| Assignment RHS vs LHS | RHS before assignment     |     |               |

##### Undefined behaviors

According to the C standard, statements such as `c = (b = a + 2) - (a = 1);` and `j = i * i++;` cause undefined behavior, which is different from implementation-defined behavior. When a program ventures into the realm of undefined behavior, all bets are off. The program may behave differently when compiled with different compilers. But that's not the only thing that can happen. The program may not compile in the first place, if it compiles it may not run, and if it does run, it may crash, behave erratically, or produce meaningless results. In other words, undefined behavior should be avoided like the plague.

1. Example 1

```c
i = i++ + 1;
```

Undefined behavior.

2. Example 2

```c
printf("%d %d\n", i, i++);
```

Undefined behavior.
Arguments are unsequenced relative to each other.

3. Example 3

```c
a[i] = i++;
```

Undefined behavior.

Example:

```c

```

Precedence says:

```c

```

But evaluation order?
The compiler may evaluate:

### Compiler-implementation perspective

C operators from a compiler-implementation perspective rather than a language-user perspective., This is how a compiler actually handles operators internally.

**Precedence Is Not Stored as a Table**

Although textbooks show a precedence table, the ISO C standard does not define precedence directly.

Instead, precedence emerges from the grammar hierarchy.

For example (simplified ISO grammar):

```
multiplicative-expression:
    cast-expression
    multiplicative-expression * cast-expression
    multiplicative-expression / cast-expression
```

```
additive-expression:
    multiplicative-expression
    additive-expression + multiplicative-expression
```

Because additive-expression depends on multiplicative-expression, \* binds tighter than +.

Precedence = grammar nesting depth.

**How Real Compilers Parse Operators**

Modern C compilers like: GCC, Clang, MSVC, use one of these techniques:

1. Recursive Descent Parsing (Clang)

Clang uses a hand-written recursive descent parser. Each precedence level is implemented as a separate function:

```
ParseExpression()
ParseAssignmentExpression()
ParseConditionalExpression()
ParseLogicalOrExpression()
ParseLogicalAndExpression()
ParseInclusiveOrExpression()
...
ParseMultiplicativeExpression()
ParseCastExpression()
ParseUnaryExpression()
ParsePostfixExpression()
ParsePrimaryExpression()
```

Each function:

- Parses left operand
- Checks if next token is a valid operator at that level
- Builds AST node
- Recurses
  This naturally enforces precedence.

2. Precedence Climbing / Pratt Parsing

Some compilers use:

- Operator-precedence parsing
- Pratt parsing
- Precedence climbing

Here operators are assigned numeric binding powers:

Example internal table:
| Operator | Left BP | Right BP |
| -------- | ------- | -------- |
| `*` | 60 | 61 |
| `+` | 50 | 51 |
| `=` | 10 | 9 |

Right-associativity is handled by slightly lowering right binding power.
This approach is compact and elegant.

#### Associativity Implementation

Associativity is determined by grammar or binding power.

Left associative

```
a - b - c

```

Parsed as:

```
(a - b) - c
```

In recursive descent:

```
left = parseHigherLevel()
while (next_token == '-') {
    op = '-'
    right = parseHigherLevel()
    left = new BinaryNode(op, left, right)
}
return left
```

Right associative (assignment)

```
a = b = c
Parsed as:
a = (b = c)
```

Implementation:

```
left = parseConditional()
if (next_token == '=') {
    op = '='
    right = parseAssignment()
    return new AssignNode(left, right)
}
return left
```

Notice recursion instead of loop → gives right associativity.

### Common Operator Pitfalls

#### Precedence vs Evaluation Order

❌ Misconception
Higher precedence ⇒ evaluated first.
✔ Reality
Precedence affects grouping, not execution order.
Example:
f() + g();
The tree is:

- / \
   f() g()
  But the compiler may call:

* f() first
* or g() first
  Order is unspecified (except where sequencing rules apply).
  🚨 Dangerous Example
  int i = 0;
  i = i++ + 1;
  This causes undefined behavior because i is modified twice without proper sequencing.

#### Undefined Behavior from Multiple Modifications

Example:
i = i++ + ++i;
Why undefined?

- i++ modifies i
- ++i modifies i
- No sequencing between them
  The C standard does not define which happens first.
  Rule:
  Between two sequence points (or sequencing rules in C11+), a scalar object must not be modified more than once.

#### Assignment Inside Conditions

Classic bug:
if (x = y)
This assigns y to x, then tests x.
Not a compiler error.
Advanced issue:
while (c = getchar() != EOF)
This is parsed as:
while (c = (getchar() != EOF))
Because != has higher precedence than =.
Correct version:
while ((c = getchar()) != EOF)

#### Bitwise vs Logical Operators

Confusion:
if (a & b)
vs
if (a && b)
Differences:
& &&
Bitwise Logical
No short-circuit Short-circuit
Always evaluates both May skip right side
Dangerous example:
if (ptr != NULL & ptr->value > 0)
This may dereference NULL because & does not short-circuit.
Correct:
if (ptr != NULL && ptr->value > 0)

#### Signed vs Unsigned Arithmetic

Example:
unsigned int a = 1;
int b = -2;
if (b < a)
What happens?
b is converted to unsigned before comparison.
So -2 becomes a large positive number.
Result may surprise you.

#### Integer Promotions

Example:
char c = 200;
if (c == 200)
If char is signed:

- c becomes negative
- comparison fails
  Because integer promotions apply before comparison.

#### Shift Operator Undefined Behavior

Left shift UB:

```c
int x = 1 << 31;
```

If int is 32-bit signed:

- shifting into sign bit → undefined behavior
  Right shift of negative values:

```c
int x = -8 >> 1;
```

Implementation-defined:

- Arithmetic shift?
- Logical shift?
  Depends on compiler.

#### Precedence Confusion with ?:

Example:
a ? b : c + d
Is parsed as:
a ? b : (c + d)
Because + has higher precedence than ?:.
But:
a + b ? c : d
Is parsed as:
(a + b) ? c : d
Conditional operator binds very low.

#### Comma Operator vs Comma Separator

These are different:
Comma separator:
int a = 1, b = 2;
Comma operator:
x = (a = 3, a + 2);
The comma operator has the lowest precedence.
Pitfall:
if (a = 1, b == 2)
Parsed as:
if ((a = 1), (b == 2))
Condition depends only on b == 2.

#### sizeof Does Not Evaluate Its Operand

Example:
int i = 10;
sizeof(i++);
i is NOT incremented.
Except when operand is a VLA (variable-length array).
Advanced pitfall:
sizeof is an operator, not a function.

#### Macro Pitfalls with Operators

Bad macro:
#define SQUARE(x) x _ x
Usage:
SQUARE(1 + 2)
Expands to:
1 + 2 _ 1 + 2
Which equals 5, not 9.
Correct:
#define SQUARE(x) ((x) \* (x))

#### Operator Precedence in Macros (Advanced)

Even this can fail:
#define INC(x) ++x
Used as:
INC(a) _ 2
Expands to:
++a _ 2
May change meaning depending on context.

#### Floating-Point Comparison

if (a == b)
May fail due to rounding.
Better:
fabs(a - b) < epsilon

#### Logical Short-Circuit Assumptions

Short-circuiting guarantees:
if (p && p->next)
Safe.
But in expressions like:
x = p && p->next;
The result is 0 or 1, not pointer value.

#### Sequence Point Misunderstandings (Modern C)

C11 replaced "sequence points" with "sequencing".
Example:
a[i] = i++;
Undefined behavior.
Even though it looks simple.

1️⃣6️⃣ Pointer Arithmetic Pitfalls
int arr[5];
int _p = arr;
p + 1
Moves by sizeof(int) bytes, not 1 byte.
But:
(char_)p + 1
Moves 1 byte.

1️⃣7️⃣ Comparison Chaining
C does NOT support mathematical chaining:
if (0 < x < 10)
Parsed as:
(0 < x) < 10
Which is almost always true.
Correct:
if (0 < x && x < 10)

1️⃣8️⃣ Mixing Bitwise and Equality
if (flags & FLAG == 0)
Parsed as:
flags & (FLAG == 0)
Because == has higher precedence than &.
Correct:
if ((flags & FLAG) == 0)

## Logical Expressions

Several of C’s statements, including the if statement, must test the value of an
expression to see if it is "true" or "false." For example, an if statement might need
to test the expression `i < j`; a true value would indicate that i is less than j.

In many programming languages, an expression such as `i < j` would have a special "Boolean" or "logical" type. Such a type would have only two values, false and true. In C, however, a comparison such as `i < j` yields an integer: either 0 (false)
or 1 (true).

C’s relational operators correspond to the `<`, `>`, `≤`, and `≥` operators of
mathematics, except that they produce `0 (false)` or `1 (true)` when used in expressions. For example, the value of `10 < 11` is `1`; the value of `11 < 10` is `0`.

The expression

```
i < j < k
```

is legal in C, but doesn’t have the meaning that you might expect. Since the `<` operator is left associative, this expression is equivalent to

```
(i < j) < k
```

In other words, the expression first tests whether `i` is less than `j`; the `1` or `0` produced by this comparison is then compared to `k`. The expression does not test whether `j` lies between `i` and `k`.

Using the fact that the relational and equality operators return integer values. the value of the expression

```
(i >= j) + (i == j)
```

is either `0`, `1`, or `2`, depending on whether `i` is less than, greater than, or equal to j, respectively.

More complicated logical expressions can be built from simpler ones by using the
logical operators: `and`, `or`, and `not` .

Both `&&` and `||` perform "short-circuit" evaluation of their operands. That is,
these operators first evaluate the left operand, then the right operand. If the value of
the expression can be deduced from the value of the left operand alone, then the
right operand isn’t evaluated. Consider the following expression:

```c
(i != 0) && (j / i > 0)
```

To find the value of this expression,

1. we must first evaluate `(i != 0)`.
2. If `i` isn’t equal to `0`, then we’ll need to evaluate `(j / i > 0)` to determine whether the entire expression is true or false.
3. However, if `i` is equal to `0`, then the entire expression must be false, so there’s no need to evaluate `(j / i > 0)`.

The advantage of short-circuit evaluation is apparent—without it, evaluating the expression would have caused a division by zero.

Be wary of side effects in logical expressions. Thanks to the short-circuit nature of
the `&&` and `||` operators, side effects in operands may not always occur. Consider
the following expression:

```
i > 0 && ++j > 0
```

Although `j` is apparently incremented as a side effect of evaluating the expression,
that isn’t always the case. If `i > 0` is false, then `++j > 0` is not evaluated, so `j` isn’t
incremented.

The problem can be fixed by changing the condition to `++j > 0 &&
i > 0` or, even better, by incrementing `j` separately.

## Conditional Expressions

A conditional expression (also called the ternary operator) lets you choose between two values based on a condition.

Syntax

```
condition ? expression1 : expression2;
```

- If condition is true (nonzero) → result is expression1
- If condition is false (0) → result is expression2

The following example illustrates the conditional operator:

```c
int i, j, k;

i = 1;
j = 2;

k = i > j ? i : j; /* k is now 2 */
k = (i >= 0 ? i : 0) + j; /* k is now 3 */
```

1. **The conditional expression `i > j ? i **: j` in the first assignment to k returns the value of either i or j, depending on which one is larger. Since i has the value 1 and j has the value 2, the `i > j` comparison fails, and the value of the conditional is 2, which is assigned to k.
2. **In the second assignment to k, the `i >= 0` comparison succeeds; the conditional expression (`i >= 0 ? i **: 0`) has the value 1, which is then added to j to produce 3. The parentheses are necessary,

the precedence of the conditional operator is less than that of the other operators we’ve dis-
cussed so far, with the exception of the assignment operators.
