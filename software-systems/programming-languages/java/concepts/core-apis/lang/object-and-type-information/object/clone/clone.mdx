{/* # Java `clone()`: A Detailed Guide */}

Java's `clone()` method is intended to create a copy of an existing object. However, it has some unusual design decisions that make it easy to use incorrectly, especially when an object contains references to other objects.

Understanding `clone()` is important when studying Java object design, inheritance, encapsulation, immutability, and defensive copying.

## Overview of Java `clone()`

The `clone()` method is declared in `java.lang.Object`, which is the root class of Java's class hierarchy.

Its declaration is:

```Java
protected native Object clone() throws CloneNotSupportedException;
```

Let's understand its parts.

| Part                                | Meaning                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------- |
| `protected`                         | The method is not generally accessible to unrelated classes.                                      |
| `native`                            | Its implementation is provided by the JVM's native runtime rather than ordinary Java method code. |
| `Object`                            | The declared return type is the general `Object` type.                                            |
| `throws CloneNotSupportedException` | Cloning can fail when the object's class does not support it.                                     |

### The role of `Cloneable`

Java defines the marker interface `java.lang.Cloneable`.

```Java
public interface Cloneable {
}
```

It has no methods. A class implements it to indicate that `Object.clone()` is permitted to make a field-by-field copy of instances of that class.

Normally, an interface tells you what operations an object supports. Cloneable is different: it acts as a signal that changes the behavior of a method in the object's superclass.

Consider:

```Java
class Student implements Cloneable {
    int id;
    String name;
}
```

Implementing `Cloneable` does not automatically generate a public `clone()` method or make the inherited protected method publicly accessible.

It simply allows the `Object.clone()` mechanism to proceed without throwing `CloneNotSupportedException`, assuming the actual object's class implements the interface.

The interface itself does nothing directly. It has no methods to implement.

However, when `Object.clone()` executes, it checks whether the object's runtime class implements `Cloneable`.

Conceptually, its behavior is like this pseudocode:

```
protected Object clone()
        throws CloneNotSupportedException {

    if (this object's class implements Cloneable) {
        return a field-by-field copy of this object;
    }

    throw new CloneNotSupportedException();
}
```

This is explanatory pseudocode, not the actual implementation of `Object.clone()`.

The important point is that the marker interface influences the behavior of a method declared elsewhere.

Without `Cloneable`, invoking `Object.clone()` normally throws `CloneNotSupportedException`.

## How `clone()` works

Imagine that we have an object representing a student.

```Java
class Student implements Cloneable {
    int id;
    String name;

    Student(int id, String name) {
        this.id = id;
        this.name = name;
    }
}
```

Conceptually, cloning creates a new object and copies the original object's fields into it.

```
┌────────────────────────────────────────────────────────────────────┐          
│Before cloning                                                      │          
│                 ┌──────────────────────────┐                       │            
│                 |         Student A        |                       │          
│                 |          id = 101        |                       │          
│                 |        name → "Mona"     |                       │          
│                 └──────────────────────────┘                       │         
│────────────────────────────────────────────────────────────────────│          
│After cloning                                                       │          
│ ┌──────────────────────────┐    ┌─────────────────────────────┐    │          
│ │                          │    │                             │    │          
│ │       Student A          │    │         Student B           │    │          
│ │       id = 101           │    │         id = 101            │    │          
│ │     name → "Mona"        │    │       name → "Mona"         │    │          
│ │                          │    │                             │    │          
│ └──────────────────────────┘    └─────────────────────────────┘    │          
│                                                                    │          
│ The two Student objects are distinct.Their corresponding fields    |
| initially contain the same values. For reference fields, that means|
| the references are copied, not necessarily the referenced objects. │          
└────────────────────────────────────────────────────────────────────┘                                                                                                                                                          
```

## Basic implementation
Suppose you want to implement Cloneable in a class whose superclass
provides a well-behaved clone method. First call super.clone. The object you
get back will be a fully functional replica of the original. Any fields declared in
your class will have values identical to those of the original. If every field contains
a primitive value or a reference to an immutable object, the returned object may be
exactly what you need, in which case no further processing is necessary

```Java
class Student implements Cloneable {
    int id;
    String name;

    Student(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public Student clone() {
        try {
            return (Student) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}

public class Main {
    public static void main(String[] args) {
        Student original = new Student(101, "Mona");
        Student copy = original.clone();

        System.out.println(original == copy); // false
        System.out.println(copy.id);           // 101
        System.out.println(copy.name);         // Mona
    }
}
```

Notice three important details:

- `super.clone()` invokes the cloning mechanism inherited from `Object`.
- The result is cast to `Student` in this example because `Object.clone()` declares its return type as `Object`.
- The override uses a covariant return type: `Student` instead of `Object`(because Java supports covariant return types).. In other
words, an overriding method’s return type can be a subclass of the overridden
method’s return type. This eliminates the need for casting in the client.  This makes the method more convenient for callers.

The cast inside `clone()` is safe under this implementation because `Object.clone()` creates a copy with the same runtime class as the original object. If a subclass inherits this implementation, the copied object is still an instance of that subclass.

### `try-catch`
The passage highlights a small but frustrating Java API design decision: `Object.clone()` declares a checked exception even when the programmer knows cloning should succeed.

Let's understand why the `try-catch` is required, why the exception is unnecessary in this case, and what Effective Java recommends doing about it.

#### Why does `super.clone()` require `try-catch`?

Suppose we implement `PhoneNumber` like this:

```Java
public final class PhoneNumber implements Cloneable {
    private final short areaCode;
    private final short prefix;
    private final short lineNum;

    public PhoneNumber(short areaCode, short prefix, short lineNum) {
        this.areaCode = areaCode;
        this.prefix = prefix;
        this.lineNum = lineNum;
    }

    @Override
    public PhoneNumber clone() {
        try {
            return (PhoneNumber) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

The important part is:

```Java
return (PhoneNumber) super.clone();
```

Java's `Object` class declares the method as:

```Java
protected native Object clone()
        throws CloneNotSupportedException;
```

`CloneNotSupportedException` is a checked exception. The compiler requires you to either catch it or declare it in your method's `throws` clause.

Therefore, this code won't compile:

```Java
@Override
public PhoneNumber clone() {
    return (PhoneNumber) super.clone(); // Compilation error
}
```

The compiler doesn't automatically determine that cloning will succeed based on `implements Cloneable`.

#### 2. Why do we know cloning should succeed?

Look at the class declaration:

```Java
public final class PhoneNumber implements Cloneable
```

Two details matter:

- `implements Cloneable` permits the default `Object.clone()` implementation to clone instances of this class.
- `final` prevents subclasses from extending the class and introducing unexpected behavior into the cloning hierarchy.

For this class, `super.clone()` should succeed under normal operation. The `CloneNotSupportedException` catch is effectively handling a situation that the class's design says should not occur.

That is why the example uses:

```Java
catch (CloneNotSupportedException e) {
    throw new AssertionError(e);
}
```

An `AssertionError` communicates that an assumption about the program has been violated. It avoids pretending that the exception is an ordinary recoverable condition.

#### Why is this boilerplate evidence of poor API design?

Imagine if Java had designed the method like this:

```Java
protected native Object clone();
```

Without the checked exception, the implementation would be simpler:

```Java
@Override
public PhoneNumber clone() {
    return (PhoneNumber) super.clone();
}
```

No `try-catch` block would be needed.

The problem is that `Object.clone()` is a general-purpose method: it can fail when the object's class doesn't implement `Cloneable`. But Java represents this possibility using a checked exception even in cases where the programmer can establish that failure is impossible under the class's intended design.

This creates unnecessary boilerplate:

```
Known condition:
    PhoneNumber implements Cloneable
             |
             v
    Cloning should succeed
             |
             v
But the compiler still requires:
    try {
        super.clone();
    } catch (CloneNotSupportedException e) {
        ...
    }
```

The compiler sees the method's declared exception, not the programmer's reasoning about the specific class.

#### Why should `CloneNotSupportedException` have been unchecked?

Java exceptions fall into two broad categories:

| Checked exception                                               | Unchecked exception                                                                    |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Must be caught or declared                                      | Does not need to be caught or declared                                                 |
| Compiler enforces handling                                      | Compiler does not enforce handling                                                     |
| Suitable when callers can reasonably recover or need to respond | Often used for programming errors or conditions that do not warrant mandatory handling |

`CloneNotSupportedException` signals that the object doesn't support the requested cloning operation. In the ordinary `Object.clone()` mechanism, this depends on whether the object's class implements `Cloneable`.

The Effective Java author's argument is that this is not a good reason to force every caller or override to handle a checked exception. In particular, classes that implement `Cloneable` must still write boilerplate even when failure is not expected.

Had the exception been unchecked, the general cloning mechanism could still report failure, but callers would not be forced to handle it.

#### Why not declare `throws CloneNotSupportedException` instead?

You could write:

```Java
@Override
public PhoneNumber clone() throws CloneNotSupportedException {
    return (PhoneNumber) super.clone();
}
```

This is legal, but it pushes the inconvenience to every caller:

```Java
try {
    PhoneNumber copy = original.clone();
} catch (CloneNotSupportedException e) {
    // Handle an exception that should not occur here.
}
```

For a class that guarantees support for cloning, that is usually worse than catching the exception internally and converting it to an `AssertionError`.

#### The practical rule

For a conventional `clone()` implementation that uses `super.clone()` and where cloning failure is impossible by design, use this pattern:

```Java
@Override
public PhoneNumber clone() {
    try {
        return (PhoneNumber) super.clone();
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

This handles the checked exception at the point where the class can reason about it.

One final distinction: this pattern only addresses the exception. It does not guarantee that cloning is a good design choice or that the result is a deep copy. For a simple immutable value class such as `PhoneNumber`, a separate `clone()` method is generally unnecessary because callers can safely share the same instance.

Main takeaway: the `try-catch` exists because `Object.clone()` declares a checked exception. When a class's design guarantees that the exception should never occur, converting it to an `AssertionError` is a conventional way to handle the awkward API.

The `AssertionError` pattern is appropriate when a class implements `Cloneable` and its own cloning implementation calls `super.clone()`: under those conditions, the checked exception should not occur. It avoids forcing callers to handle an exception that indicates a programming or class-design inconsistency.

## Shallow copy vs. deep copy

This is the most important concept to understand about `clone()`.

By default, `Object.clone()` performs a shallow, field-by-field copy. It does not recursively clone objects referenced by fields.

Primitive fields are copied by value. Reference fields are copied as references.

### Shallow copy

Consider a student that has a mutable `Address` object.

```Java
class Address {
    String city;

    Address(String city) {
        this.city = city;
    }
}

class Student implements Cloneable {
    int id;
    String name;
    Address address;

    Student(int id, String name, Address address) {
        this.id = id;
        this.name = name;
        this.address = address;
    }

    @Override
    public Student clone() {
        try {
            return (Student) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Now create a copy:

```Java
Address address = new Address("Cairo");

Student original = new Student(101, "Mona", address);
Student copy = original.clone();

System.out.println(original == copy);               // false
System.out.println(original.address == copy.address); // true
```

The first comparison is `false` because cloning created a different `Student` object. The second is `true` because both student objects refer to the same `Address`.

ASCII diagram:

```
original ──────> Student A
                   id = 101
                   name ──────────┐
                   address ───┐   │
                              │   │
copy ───────────> Student B   │   │
                   id = 101   │   │
                   name ──────┼───┘
                   address ───┘
                              |
                              v
                         Address
                         city = "Cairo"
```

The `String` reference is also copied, but strings are immutable, so sharing the same string instance is normally harmless.

Now observe the consequence of modifying the address:

```Java
copy.address.city = "Alexandria";

System.out.println(original.address.city);
// Alexandria
```

Changing the address through the copy also affects what the original observes.

A shallow copy separates the outer object, not the mutable object graph reachable from it.

### Deep copy

A deep copy creates independent copies of the mutable objects that must not be shared.

For the example above:

```Java
@Override
public Student clone() {
    try {
        Student copy = (Student) super.clone();

        if (address != null) {
            copy.address = new Address(address.city);
        }

        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

Now:

```Java
Student original = new Student(
    101, "Mona", new Address("Cairo")
);

Student copy = original.clone();

System.out.println(original == copy);                 // false
System.out.println(original.address == copy.address); // false

copy.address.city = "Alexandria";

System.out.println(original.address.city); // Cairo
System.out.println(copy.address.city);     // Alexandria
```

ASCII diagram:

```
original ──────> Student A
                   address ──────> Address A
                                     city = Cairo

copy ──────────> Student B
                   address ──────> Address B
                                     city = Cairo
```

The two addresses now have independent identities and mutable state.

However, deep copying is not always as simple as copying every referenced object. Consider:

- An object graph containing cycles.
- Two fields that intentionally refer to the same object.
- Immutable objects that are safe to share.
- Resources such as sockets, files, threads, or database connections that cannot meaningfully be duplicated by copying fields.

A correct deep-copy strategy must preserve the class's intended invariants and sharing relationships, not blindly duplicate everything.
#### Comparison

| Property                          | Shallow copy    | Deep copy                                     |
| --------------------------------- | --------------- | --------------------------------------------- |
| Creates a new outer object        | Yes             | Yes                                           |
| Copies primitive fields           | Yes             | Yes                                           |
| Copies reference values           | Yes             | Yes, with additional work                     |
| Shares referenced mutable objects | Usually         | Avoids sharing where independence is required |
| Implementation complexity         | Low             | Higher                                        |
| Risk of unintended shared state   | Higher          | Lower, if correctly implemented               |
| Performance                       | Usually cheaper | Depends on object graph size                  |

One subtle point: `clone()` does not inherently mean deep copy. Calling `super.clone()` gives you the shallow-copy behavior. You must explicitly decide whether to copy nested objects.

### Deep Copying Complex Object Graphs        
#### Recursive Deep Copy
It is not always sufficient merely to call clone recursively,  For example,
suppose you are writing a clone method for a hash table whose internals consist
of an array of buckets, each of which references the first entry in a linked list of
key-value pairs. For performance, the class implements its own lightweight singly
linked list instead of using java.util.LinkedList internally:
```Java
public class HashTable implements Cloneable {
    private Entry[] buckets;

    private static class Entry {
        final Object key;
        Object value;
        Entry next;

        Entry(Object key, Object value, Entry next) {
            this.key = key;
            this.value = value;
            this.next = next;
        }
    }
}
```

Suppose you merely clone the bucket array recursively, as we did for Stack:
```Java
@Override
public HashTable clone() {
    try {
        HashTable result = (HashTable) super.clone();
        result.buckets = buckets.clone();
        return result;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

At first glance, this seems reasonable:

1. Clone the `HashTable` object.
2. Clone its `buckets` array.
3. Return the result.

But `buckets.clone()` creates a new array, not copies of the entries referenced by the array.

For example, assume the original has this bucket:

```
Original table                    Cloned table
+------------------+              +------------------+
| buckets ---------|--+           | buckets ---------|--+
+------------------+  |           +------------------+  |
                      |                                 |
                      v                                 v
                +-----------+                     +-----------+
                | Array     |                     | Array     |
                | bucket 0 -|----+                | bucket 0 -|----+
                +-----------+    |                +-----------+    |
                                 |                                 |
                                 v                                 v
                              Entry A <--------------------------+
                                 |
                                 v
                              Entry B
                                 |
                                 v
                                null
```

The arrays are different, but both arrays point to the same linked list.

If the clone changes an entry's value, the original sees the change too:

```Java
// Illustrative operation on the cloned table:
clonedTable.put("language", "Java");

// If the update modifies a shared Entry object,
// the original table may now also report "Java".
```

Depending on the operation, shared entries can cause even worse problems. Removing an entry or changing a `next` pointer in a shared list can affect both tables, potentially corrupting their logical contents.

The result is shared mutable state, which makes the two tables behave as though they were independent when they are not.

To fix this problem, you’ll have to copy the linked
list that comprises each bucket. Here is one common approach:

The private class HashTable.Entry has been augmented to support a “deep
copy” method. The clone method on HashTable allocates a new buckets array of
the proper size and iterates over the original buckets array, deep-copying each
nonempty bucket. The deepCopy method on Entry invokes itself recursively to
copy the entire linked list headed by the entry.
```Java
Entry deepCopy() {
    return new Entry(
        key,
        value,
        next == null ? null : next.deepCopy()
    );
}
@Override
public HashTable clone() {
    try {
        HashTable result = (HashTable) super.clone();

        result.buckets = new Entry[buckets.length];

        for (int i = 0; i < buckets.length; i++) {
            if (buckets[i] != null) {
                result.buckets[i] = buckets[i].deepCopy();
            }
        }

        return result;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```
`deepCopy()` creates a new entry with:

- The same `key` reference.
- The same `value` reference.
- A `next` reference pointing to a recursively copied entry, or `null` if this is the last entry.

Notice that every bucket is handled independently. An empty bucket stays empty; a nonempty bucket gets its own copied linked list.

This solves the shared-entry problem. However, there is a subtle distinction: the nodes are copied, but the `key` and `value` objects are not recursively copied. That is usually acceptable for a hash table clone when the intended semantics are to duplicate the table's internal structure while retaining references to the original keys and values.

If keys or values are mutable and the cloning contract requires them to be independent too, additional copying is needed.

The recursive version is elegant, but consider a bucket containing one million entries.

Every call to `deepCopy()` must remain active until the recursive call for the remaining list returns. Each call consumes a stack frame.

```
deepCopy(Entry 1)
    deepCopy(Entry 2)
        deepCopy(Entry 3)
            deepCopy(Entry 4)
                ...
                    deepCopy(Entry 1,000,000)
```

The problem is that the Java call stack has a finite size. A sufficiently long list can cause a `StackOverflowError`.

The time complexity is $O(n)$, but the auxiliary stack space is also $O(n)$, where $n$ is the number of entries in the bucket.
#### Iterative Deep Copy
For potentially long lists, iteration avoids this risk.

To prevent this from happening, you can
replace the recursion in `deepCopy` with iteration:
```Java
// Iteratively copy the linked list headed by this Entry.
Entry deepCopy() {
    Entry result = new Entry(key, value, next);

    for (Entry p = result; p.next != null; p = p.next) {
        p.next = new Entry(
            p.next.key,
            p.next.value,
            p.next.next
        );
    }

    return result;
}
```
This code is slightly less intuitive because it initially copies only the first node and temporarily points to the original remainder of the list. The loop progressively replaces those original references with new nodes.

Let's trace it.

Suppose the original list is:

```
A ---> B ---> C ---> null
```

Step 1: Create the first node.

```
Entry result = new Entry(key, value, next);
```

Initially:

```
result
  |
  v
 A' ---> B ---> C ---> null
```

`A'` is new, while `B` and `C` are still original nodes.

Step 2: Copy the second node.

The loop executes:

```
p.next = new Entry(
    p.next.key,
    p.next.value,
    p.next.next
);
```

Initially, `p` points to `A'`. Its `next` points to original `B`, so the statement creates `B'`:

```
result
  |
  v
 A' ---> B' ---> C ---> null
```

Step 3: Advance and copy the third node.

The loop advances `p` to `B'`. Since `B'.next` points to original `C`, the next iteration creates `C'`:

```
result
  |
  v
 A' ---> B' ---> C' ---> null
```

Step 4: Finish.

`p.next` is now `null`, so the loop stops and returns `result`.

The final copied list has no links to the original list's entry nodes.

**Recursive vs. iterative copying**

| Property                              | Recursive version | Iterative version                       |
| ------------------------------------- | ----------------- | --------------------------------------- |
| Time complexity                       | $O(n)$        | $O(n)$                              |
| Auxiliary call-stack space            | $O(n)$        | $O(1)$                              |
| New entry nodes                       | $n$           | $n$                                 |
| Risk of stack overflow for long lists | Yes               | Avoids recursion-related stack overflow |
| Ease of understanding                 | Often simpler     | Requires tracing pointer updates        |

Both methods create a new node for every entry. The iterative method does not reduce the number of objects allocated; it reduces the auxiliary stack space.

---

This example illustrates three distinct levels of copying:

Level 1: Copy the hash table object

`super.clone()` creates a separate `HashTable`, but initially copies its field references.

Level 2: Copy the bucket array and linked-list nodes

`buckets.clone()` copies only the array. A correct independent structure also needs a new array and new `Entry` nodes.

Level 3: Copy keys and values, if required

The shown implementation retains references to existing keys and values. Copy these too only if the required semantics demand independent key/value objects and those objects can meaningfully be copied.

This example illustrates a crucial lesson about Java cloning: copying the outer data structure does not necessarily copy the mutable objects reachable through it. To make a clone independent, you must understand the entire object graph and decide which objects can safely be shared and which must be copied.

One more subtlety: the iterative algorithm assumes the bucket is an ordinary acyclic linked list. If the structure could contain cycles or shared nodes between buckets, blindly copying each list independently might not preserve the original graph's relationships. Such structures require a more general graph-copying strategy, often using an identity-based map from original nodes to copied nodes.

The key takeaway: a correct clone requires deliberate decisions about which references may be shared and which must be duplicated. For linked structures, iteration is often preferable to recursion because it avoids consuming one Java stack frame per node. For new Java APIs, a copy constructor or factory can make these copying rules clearer than `clone()`.

#### Rebuilding State Through Higher-Level Methods
a third approach to deep cloning complex mutable objects: instead of manually copying every internal data structure, you create a shallow clone, reset its internal state, and rebuild that state using the class's normal public or internal methods.

Suppose a hash table stores key-value mappings using an array of buckets, where each bucket contains a linked list of entries.

Before cloning:

```
Original HashTable
    |
    v
  buckets
    |
    +----> [A:1] -> [B:2] -> null
    |
    +----> [C:3] -> null
    |
    +----> null
```

Calling `super.clone()` copies the fields, but only copies references to objects.

```
After super.clone()

Original HashTable          Cloned HashTable
       |                           |
       v                           v
    buckets --------------------> buckets
                same array
```

Both tables now refer to the same bucket array and linked-list nodes. If you modify the cloned table's internal structure, you may accidentally affect the original.

We need to replace the shared mutable state.

The approach has three steps:

1. Call `super.clone()` to create an object of the correct runtime class.
2. Replace the cloned object's internal data structures with fresh, empty ones.
3. Reinsert the original table's entries using `put(key, value)`.
##### Resetting the Cloned Object
Conceptually:

```Java
@Override
public HashTable clone() {
    try {
        HashTable copy = (HashTable) super.clone();

        // Discard the shared bucket array.
        copy.buckets = new Entry[buckets.length];

        // Rebuild the cloned table using its normal operation.
        for (Entry entry : entries()) {
            copy.put(entry.key, entry.value);
        }

        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```
After rebuilding:

```
Original HashTable          Cloned HashTable
       |                           |
       v                           v
  Original buckets             New buckets
       |                           |
       v                           v
    [A:1] -> [B:2]              [A:1] -> [B:2]
       |                           |
       +---- separate nodes -------+
```

The nodes and bucket arrays are independent, although the key and value objects may still be shared.

##### Reconstructing State with put()
The `put()` method already knows how to maintain the hash table's internal rules, such as:

- Calculating the bucket index from a key's hash code.
- Creating new entries and linking them into a bucket.
- Handling collisions.
- Updating an existing mapping.
- Maintaining any size counters or other bookkeeping.

Instead of duplicating this logic inside `clone()`, we reuse the class's existing behavior.

This is an example of reusing higher-level operations to reconstruct an object's state, rather than manipulating its implementation details directly.

##### Performance and Maintainability Trade-offs

| Aspect              | Direct deep copy                                 | Rebuild using `put()`                                        |
| ------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| Implementation      | Manipulates internal nodes and links             | Reuses existing operations                                   |
| Performance         | Usually faster; avoids repeated insertion work   | Usually slower due to repeated hashing and insertion         |
| Maintainability     | Tightly coupled to internal representation       | Can be easier to maintain                                    |
| Invariant handling  | Must correctly reproduce all internal invariants | Existing methods can maintain invariants                     |
| Object independence | Must explicitly copy mutable structures          | Achieved by rebuilding them                                  |
| Key/value copying   | Depends on implementation                        | Usually shares key/value references unless explicitly copied |

Both approaches can produce an independent internal structure. Neither automatically deep-copies the objects referenced by the keys and values.

While this approach is clean, it is
antithetical to the whole Cloneable architecture because **it blindly overwrites the
field-by-field object copy that forms the basis of the architecture**.

`super.clone()` has already copied the object's fields. In this approach, we immediately throw away the copied bucket-array reference and rebuild the table.

```
super.clone()
     |
     v
Shallow field-by-field copy
     |
     v
Discard copied mutable state
     |
     v
Allocate fresh state
     |
     v
Rebuild through put()
```

This conflicts with the basic design of `Cloneable`, where `Object.clone()` is intended to provide the initial field-by-field copy and the overriding method repairs any state that must not be shared.

The criticism is not that rebuilding is incorrect. It is that we are doing extra work to undo much of the copying that `super.clone()` just performed.

There are also practical concerns:

- `put()` may have side effects or depend on fields that have not yet been reset.
- Rebuilding may not preserve every internal detail, such as a particular capacity or iteration order, unless the implementation explicitly accounts for it.
- In a non-final class, invoking overridable methods during cloning can be risky because a subclass might override them in ways that assume a fully initialized object.

The main takeaway: rebuilding through `put()` prioritizes reuse and clarity over speed. It can be a reasonable cloning technique, but for new Java APIs, a copy constructor or static copy factory is generally a clearer way to express copying without fighting the `Cloneable` architecture.

#### Cycles or Shared objects
So far, our linked-list examples have assumed a simple, acyclic structure. Real object graphs can be more complicated.

Consider this graph:

```
Original
   |
   v
  Node A ------> Node B
     ^              |
     |              |
     +--------------+

Node A also has a reference to Node C
Node B and Node C both reference the same Node D
```

Two issues arise:

- Cycles: a node eventually references itself, directly or indirectly. Naive recursive copying can loop forever.
- Shared references: two fields refer to the same object. Naively copying that object twice can destroy the original sharing relationship.

For a general object graph, use an identity map to record the original-to-copy relationship.

Conceptually:

```
Identity map

Original object  ->  Copied object
Node A           ->  Node A'
Node B           ->  Node B'
Node D           ->  Node D'
```

When the copy algorithm encounters an object it has already copied, it reuses the recorded copy instead of creating another one. This preserves cycles and shared references.

A Java implementation commonly uses an `IdentityHashMap<Object, Object>` for this purpose, along with type-specific copying logic.

Choose this strategy when: the object graph can contain cycles or when preserving shared references is part of the required semantics.

#### Choosing a Deep-Copy Strategy
When you clone a complex mutable object, the main question is not simply how do I copy every field? It is:

Which parts of the object must be independent, which parts can safely be shared, and what is the safest and simplest way to create that copy?

For example, consider a `HashTable` containing an array of buckets, linked-list nodes, keys, and values. These objects form a graph of references, and copying every reference is not the same as copying the objects themselves.

##### Understand what needs to be copied

Consider this object structure:

```
HashTable
    |
    v
  buckets[]
    |
    +----> Entry A ----> Entry B
    |          |            |
    |          v            v
    |         Key A        Key B
    |          |            |
    |          v            v
    |        Value A      Value B
    |
    +----> Entry C
               |
               v
             Key C
```

Suppose we clone the hash table. We need to decide what happens to each part.

| Object or field            | Typical copying decision         | Why?                                                                              |
| -------------------------- | -------------------------------- | --------------------------------------------------------------------------------- |
| Bucket array               | Copy                             | The original and clone must not rearrange the same buckets.                       |
| Linked-list entries        | Copy                             | Changing links in one table must not affect the other.                            |
| Keys                       | Often share                      | Keys are commonly immutable, such as `String`, or treated as stable identifiers.  |
| Values                     | Depends                          | Mutable values may need their own copies if the tables must be fully independent. |
| Configuration objects      | Often share if immutable         | Immutable objects can safely be shared.                                           |
| Caches and temporary state | Rebuild, reset, or share if safe | These fields may not be part of the object's essential state.                     |

Notice that deep copying does not necessarily mean copying every object reachable from the original. It means copying the mutable state that must be independent under the intended copy contract.

For instance, if a key is a `String`, sharing the key is safe because strings are immutable. If a value is a mutable `ArrayList`, sharing it means changes to the list can be observed through both tables.

##### Strategy A: Recursive deep copying

Each node creates a copy of itself and recursively copies the next node.

```
static class Entry {
    final Object key;
    Object value;
    Entry next;

    Entry(Object key, Object value, Entry next) {
        this.key = key;
        this.value = value;
        this.next = next;
    }

    Entry deepCopy() {
        return new Entry(
            key,
            value,
            next == null ? null : next.deepCopy()
        );
    }
}
```

For a linked list:

```
Original: A -> B -> C -> null

Copy A
  |
  +-- Copy B
        |
        +-- Copy C
              |
              +-- null

Result:   A' -> B' -> C' -> null
```

Advantages

- Short and easy to understand.
- Naturally follows the structure of the data.
- Useful for small, bounded recursive structures.

Disadvantages

- Every node adds another method call to the call stack.
- A very long linked list can cause `StackOverflowError`.
- Does not automatically handle cycles or preserve shared references in a general object graph.

Choose it when: the structure is naturally recursive and its depth is safely bounded, such as a small tree.

##### Strategy B: Iterative deep copying

Instead of recursively copying the next node, use a loop.

```
Entry deepCopy() {
    Entry copy = new Entry(key, value, next);

    for (Entry current = copy;
         current.next != null;
         current = current.next) {

        Entry next = current.next;

        current.next = new Entry(
            next.key,
            next.value,
            next.next
        );
    }

    return copy;
}
```

The algorithm walks through the list and replaces each shared node reference with a new node.

```
Original: A -> B -> C -> null
             |    |    |
             v    v    v
Copy:     A' -> B' -> C' -> null
```

The copied nodes are independent; the key and value references are still shared.

| Property                    | Complexity |
| --------------------------- | ---------- |
| Time                        | $O(n)$ |
| Auxiliary space             | $O(1)$ |
| Additional call-stack depth | $O(1)$ |

Choose it when: you are copying a long linked list or another structure that can be traversed iteratively, and you want to avoid recursive stack growth.

##### Strategy C: Rebuild state using higher-level methods

Here, `clone()` creates a shallow clone, replaces the bucket array, and reinserts all mappings through `put()`.

```
@Override
public HashTable clone() {
    try {
        HashTable copy = (HashTable) super.clone();

        // Replace the shared mutable array.
        copy.buckets = new Entry[buckets.length];

        // Rebuild the table by traversing the original.
        for (Entry head : buckets) {
            for (Entry e = head; e != null; e = e.next) {
                copy.put(e.key, e.value);
            }
        }

        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

This assumes the class provides a compatible `put()` method and that resetting `buckets` also leaves any other bookkeeping fields in a valid state. Depending on the implementation, fields such as `size`, thresholds, and capacity-related metadata may need attention.

Advantages

- Reuses existing insertion logic.
- Can be easier to maintain when internal structures are complicated.
- Lets normal operations establish the data structure's invariants.

Disadvantages

- May be slower because every mapping is inserted again.
- Can accidentally invoke overridable methods during cloning.
- Must correctly reset all state before rebuilding.

Choose it when: reusing well-tested operations is more valuable than minimizing copying overhead, and you can safely reconstruct the object's state.

Remember that calling `put()` does not automatically deep-copy mutable keys or values.

##### Strategy D: Copy constructor or static copy factory

For new Java APIs, this is often the clearest choice because copying is explicitly defined rather than relying on `Object.clone()`.

```
public class ShoppingCart {
    private final List<String> items;

    public ShoppingCart(ShoppingCart original) {
        this.items = new ArrayList<>(original.items);
    }

    public static ShoppingCart copyOf(ShoppingCart original) {
        return new ShoppingCart(original);
    }

    public void addItem(String item) {
        items.add(item);
    }

    public List<String> getItems() {
        return List.copyOf(items);
    }

    public static void main(String[] args) {
        ShoppingCart original = new ShoppingCart(
            new ShoppingCart(List.of("Book", "Pen"))
        );

        ShoppingCart copy = ShoppingCart.copyOf(original);
        copy.addItem("Notebook");

        System.out.println(original.getItems()); // [Book, Pen]
        System.out.println(copy.getItems());     // [Book, Pen, Notebook]
    }

    private ShoppingCart(List<String> items) {
        this.items = new ArrayList<>(items);
    }
}
```

This example copies the list but shares its `String` elements, which is safe because strings are immutable.

For mutable elements, the constructor would need to copy each element as well, according to the class's copy contract.

Advantages

- Explicitly defines which fields are copied or shared.
- Works naturally with `final` fields.
- Does not require `Cloneable` or checked `CloneNotSupportedException`.
- Can validate the source and establish a valid object state.

Disadvantages

- You must implement the desired copy behavior.
- Inheritance needs deliberate handling: a base-class copy constructor does not automatically copy subclass-specific fields.
- Deep-copying arbitrary object graphs can still be complex.

Choose it when: designing a new class or API where you control the copying contract.

##### How to choose: a decision table

| Situation                                              | Recommended strategy                        | Main reason                                |
| ------------------------------------------------------ | ------------------------------------------- | ------------------------------------------ |
| Small, bounded recursive structure                     | Recursive copying                           | Simple and readable                        |
| Long linked list                                       | Iterative copying                           | Avoids recursive stack growth              |
| Complex data structure with reliable insertion methods | Rebuild through higher-level methods        | Reuses established invariants              |
| New class or public API                                | Copy constructor or static copy factory     | Explicit, maintainable copy contract       |
| Arbitrary graph with cycles and shared references      | Identity-map-based graph copying            | Preserves graph relationships              |
| Immutable objects                                      | Share references where the contract permits | No mutable state needs independent copying |
| Performance-critical structure                         | Direct copying, after profiling             | Avoids unnecessary reconstruction overhead |

##### A practical decision process

Use this sequence when designing a copy operation:

1. Step 1 — Define independence

Which mutations to the copy must not affect the original? Copy the mutable state that would otherwise violate that requirement.

2. Step 2 — Examine the structure

Is it a simple list, a tree, or a general graph with cycles and shared references? Choose an algorithm that handles the actual structure.

3. Step 3 — Choose the copying mechanism

Prefer copy constructors or static factories for new APIs. For legacy `clone()` implementations, choose recursive copying, iterative copying, or reconstruction according to the structure and constraints.

4. Step 4 — Check correctness and cost

Verify reference independence, preserved invariants, cycle handling if necessary, and time and space complexity.

## Importance of `clone()`

Why does Java have this mechanism in the first place?

### Duplicating an existing object's state

Sometimes an object has already been configured with many values. Creating an equivalent object from scratch may require repeating that configuration.

For example:

```Java
ReportOptions original = ...;
ReportOptions copy = original.clone();
```

This can be convenient when the original object represents a complex configuration that must be duplicated.

### Preserving an object's runtime type

The `Object.clone()` mechanism creates an object with the same runtime class as the original.

Suppose a class hierarchy contains:

```Java
Shape
  |
  +-- Circle
  |
  +-- Rectangle
```

A cloning implementation inherited by `Circle` can produce another `Circle`, rather than accidentally creating a generic `Shape`, provided the implementation and the class hierarchy are compatible with cloning.

This can be useful in polymorphic systems, although constructors or copy factories may offer a clearer design.

### Supporting independent modification

Copying an object allows a caller to modify a working copy without changing the original's own fields.

This benefit is strongest when the class is immutable or its copying policy correctly isolates mutable state.

### Supporting legacy APIs

Some older Java libraries and frameworks use `Cloneable` and `clone()`. Understanding the mechanism is therefore important when maintaining existing code, implementing compatible classes, or reviewing code that inherits cloning behavior.

### Understanding object identity

Cloning is a useful way to understand the distinction between:

- Equality: two objects have equivalent values.
- Identity: two references point to the same object.

For example:

```Java
Student copy = original.clone();

System.out.println(original == copy);        // false
System.out.println(original.equals(copy));   // Depends on equals()
```

If `Student` does not override `equals()`, the inherited implementation from `Object` compares identity, so the second expression is also `false`.

Cloning does not automatically make two objects logically equal. That depends on the class's equality contract.

## Benefits of overriding `clone()`

Overriding `clone()` is not always necessary, but when a class chooses to support cloning, a thoughtful override offers several advantages.

### Public accessibility

The inherited `Object.clone()` is `protected`. An override can expose it as `public`.

```Java
@Override
public Student clone() {
    // ...
}
```

Callers can then write:

```Java
Student copy = original.clone();
```

without needing to create a subclass just to access the method.

### A more specific return type

Returning `Student` instead of `Object` avoids forcing callers to cast.

Without a covariant return type:

```Java
Student copy = (Student) original.clone();
```

With a covariant return type:

```Java
Student copy = original.clone();
```

### Correct handling of mutable fields

An override can perform the shallow copy first, then duplicate selected mutable fields.

```Java
@Override
public Student clone() {
    try {
        Student copy = (Student) super.clone();

        copy.address = address == null
                ? null
                : new Address(address.city);

        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

### Preserving invariants

An override can ensure that copied fields satisfy the class's invariants, provided the cloning design permits those corrections.

For example, it might copy a mutable collection rather than share it:

```Java
copy.tags = new ArrayList<>(tags);
```

This gives the original and copy separate lists, though the list elements are still shared unless they are copied separately.

### Simplifying callers

A well-designed cloning method hides the copying policy behind one operation. Callers do not have to know which fields need independent copies.

There is an important qualification, however: if the cloning contract is unclear, this convenience can hide surprising sharing behavior instead of simplifying the design.

## Common usage of `clone()`

Cloning is useful in some specific situations, but it is not the default choice for every object-copying requirement.

### Copying configuration objects

Imagine an application that creates multiple report configurations from a common template.

```Java
class ReportOptions implements Cloneable {
    String format;
    int pageSize;
    boolean includeHeader;

    ReportOptions(String format, int pageSize,
                  boolean includeHeader) {
        this.format = format;
        this.pageSize = pageSize;
        this.includeHeader = includeHeader;
    }

    @Override
    public ReportOptions clone() {
        try {
            return (ReportOptions) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Usage:

```Java
ReportOptions template =
        new ReportOptions("PDF", 20, true);

ReportOptions customerReport = template.clone();
ReportOptions adminReport = template.clone();

customerReport.pageSize = 10;
adminReport.includeHeader = false;
```

Because the fields here are primitives and an immutable `String` reference, shallow copying is sufficient for this particular design.

### Copying arrays

Java arrays have a public `clone()` method that returns a shallow copy of the array.

```Java
int[] original = {10, 20, 30};
int[] copy = original.clone();

copy[0] = 99;

System.out.println(original[0]); // 10
System.out.println(copy[0]);     // 99
```

For primitive arrays, the elements are copied by value.

For arrays of object references, the array itself is new, but its elements are initially shared:

```Java
Address[] original = {
    new Address("Cairo")
};

Address[] copy = original.clone();

System.out.println(original == copy);           // false
System.out.println(original[0] == copy[0]);      // true
```

This is a common and useful example of shallow copying.

Calling clone on an array returns an array whose runtime and compile-time types
are identical to those of the array being cloned. This is the preferred idiom to
duplicate an array. In fact, arrays are the sole compelling use of the clone facility.

### Copying a collection's structure

Suppose you want a separate list with the same elements:

```Java
List<String> original =
        new ArrayList<>(List.of("Java", "SQL"));

List<String> copy = new ArrayList<>(original);
```

This is generally preferable to cloning the `ArrayList` itself. It explicitly communicates that you want a new list containing the existing elements.

For a list of mutable objects, this constructor does not deep-copy the elements.

### Prototype-based object creation

A prototype pattern creates new objects from an existing configured instance. A class may implement this pattern using `clone()`, particularly in legacy designs.

For example:

```
Configured prototype
        |
        +----> New object A
        |
        +----> New object B
        |
        +----> New object C
```

However, a dedicated copy constructor or factory can implement the same pattern with clearer semantics.

### Copying objects in legacy frameworks

Some existing systems use cloning to copy domain objects, graphical objects, or framework-managed objects.

When working with such systems, examine whether cloning is shallow, whether subclasses override it correctly, and whether fields representing external resources are safe to copy.

Do not assume that every Java object can or should be cloned.

## Java `clone()` and Inheritance

### `super.clone()` similar to constructor chaining

In Java, constructors commonly chain to superclass constructors using `super(...)`.

```Java
class Animal {
    Animal() {
        System.out.println("Animal constructor");
    }
}

class Dog extends Animal {
    Dog() {
        super();
        System.out.println("Dog constructor");
    }
}
```

Creating a `Dog` invokes the constructor chain:

```
new Dog()
   |
   v
Animal()
   |
   v
Dog()
```

Each class participates in initializing the object.

Cloning has a related convention: each class that overrides `clone()` should normally call its superclass's `clone()` implementation.

```Java
class Animal implements Cloneable {
    @Override
    public Animal clone() {
        try {
            return (Animal) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

The key difference is that Java does not enforce this convention. The compiler allows a `clone()` implementation to create a new instance using a constructor instead.

### Using a constructor in `clone()`

Consider this implementation:

```Java
class Animal implements Cloneable {
    private String name;

    Animal(String name) {
        this.name = name;
    }

    @Override
    public Animal clone() {
        return new Animal(name); // Incorrect cloning pattern for an extensible class
    }
}
```

For an `Animal`, this appears to work:

```Java
Animal original = new Animal("Buddy");
Animal copy = original.clone();

System.out.println(copy.getClass()); // class Animal
```

But what happens when we create a subclass?

```Java
class Dog extends Animal {
    private String breed;

    Dog(String name, String breed) {
        super(name);
        this.breed = breed;
    }
}
```

Now clone a `Dog`:

```Java
Dog original = new Dog("Buddy", "Labrador");

Animal copy = original.clone();

System.out.println(original.getClass()); // class Dog
System.out.println(copy.getClass());     // class Animal
```

The result is an `Animal`, not a `Dog`!

Why? Because the inherited `Animal.clone()` explicitly executes:

```Java
return new Animal(name);
```

It creates an `Animal` regardless of the original object's runtime class.

The `Dog` portion of the original object—including `breed`—is lost.

So, if a class’s clone method returns an instance that is not obtained by calling `super.clone` but by calling a constructor, the compiler won’t complain, but if
a subclass of that class calls `super.clone`, the resulting object will have the
wrong class, preventing the subclass from clone method from working properly.

### `super.clone()`

Now change the implementation to use `super.clone()`:

```Java
class Animal implements Cloneable {
    private String name;

    Animal(String name) {
        this.name = name;
    }

    @Override
    public Animal clone() {
        try {
            return (Animal) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

The subclass can inherit this implementation:

```Java
class Dog extends Animal {
    private String breed;

    Dog(String name, String breed) {
        super(name);
        this.breed = breed;
    }
}
```

Test it:

```Java
public class Main {
    public static void main(String[] args) {
        Dog original = new Dog("Buddy", "Labrador");

        Animal copy = original.clone();

        System.out.println(original.getClass()); // class Dog
        System.out.println(copy.getClass());     // class Dog
    }
}
```

Even though `Animal.clone()` calls `super.clone()`, the copied object's runtime class remains `Dog`.

Conceptually, the process looks like this:
```
Original object

Runtime class: `Dog`
      ↓
`Animal.clone()` calls `super.clone()`
      ↓
Copied object

Runtime class: `Dog` — preserved
```
`Object.clone()` creates an object of the same runtime class as the original, then copies its fields. It does not simply execute `new Animal(...)`.

However, the copied `Dog` still needs to handle any mutable fields it introduces. Preserving the runtime class does not automatically make the copy deep.

So explains an important rule for inheritance and `clone()`: a non-final class should normally implement `clone()` by calling `super.clone()`, because this preserves the actual runtime class of the object being cloned.

If the class creates its copy by calling a constructor instead, the code may work for that class but fail when a subclass inherits its `clone()` implementation.

---

**Why does every subclass need to follow the convention?**

Suppose the hierarchy is:

```
Animal
  |
  +-- Dog
        |
        +-- ServiceDog
```

Each class may add its own fields.

| Class        | Additional state  |
| ------------ | ----------------- |
| `Animal`     | `name`            |
| `Dog`        | `breed`           |
| `ServiceDog` | `trainingRecords` |

A correctly chained cloning implementation can preserve all three classes' fields through `super.clone()`.

But if `Animal.clone()` uses `new Animal(name)`, the chain breaks at the bottom. Neither `Dog` nor `ServiceDog` can recover the original runtime class by simply calling `super.clone()`.

Also, if `ServiceDog` introduces a mutable list such as `trainingRecords`, it should override `clone()` to copy that list appropriately. `super.clone()` alone only copies the list reference.

The convention therefore serves two purposes:

1. Preserve the object's runtime class.
2. Allow subclasses to extend the cloning process to handle their own state.

### Final class

A `final` class cannot be subclassed.

```Java
final class Color {
    private final int red;
    private final int green;
    private final int blue;

    Color(int red, int green, int blue) {
        this.red = red;
        this.green = green;
        this.blue = blue;
    }

    public Color clone() {
        return new Color(red, green, blue);
    }
}
```

This implementation creates a new `Color` through its constructor rather than calling `super.clone()`.

Because `Color` is final, no subclass can inherit this implementation and expect it to preserve a more specific runtime class.

However, notice something important: this `Color` class does not implement `Cloneable`. That is appropriate because its `clone()` method does not rely on `Object.clone()`.

The method is simply a custom copying operation.

**What if the final class does implement `Cloneable`?**

It is possible, but unnecessary in this example:

```Java
final class Color implements Cloneable {
    // ...
}
```

If `Color.clone()` uses `new Color(...)` and never invokes `super.clone()`, it does not need `Cloneable` for that operation. The marker interface would not be contributing anything to the custom copying behavior.

### Why extendable classes should avoid `Cloneable`

An extendable class is a class that is not `final` and is designed to be subclassed.

Suppose you are designing a class called `Document` that other developers may extend.

```Java
public class Document implements Cloneable {
    private String title;

    public Document(String title) {
        this.title = title;
    }

    @Override
    public Document clone() {
        try {
            return (Document) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```
Should `Document` implement `Cloneable`?

Now another developer extends it:

```Java
public class SecureDocument extends Document {
    private byte[] encryptionKey;

    public SecureDocument(String title, byte[] encryptionKey) {
        super(title);
        this.encryptionKey = encryptionKey.clone();
    }
}
```

Because `Document` implements `Cloneable`, `SecureDocument` inherits that interface too. Its instances are therefore eligible for `Object.clone()`.

But eligibility is not the same as correct cloning. The inherited `clone()` only makes a shallow copy of `encryptionKey`, so the original and the clone would share the same array unless the subclass overrides `clone()` and copies that array.

The superclass has effectively made cloning part of the inheritance hierarchy, even though it cannot know how every future subclass should copy its additional state.

This is why Effective Java recommends that an extendable class generally avoid implementing `Cloneable`, because doing so commits the class to a cloning policy that can constrain its subclasses.

The important distinction is:

- `Cloneable` is a marker interface that affects the behavior of `Object.clone()`.
- `clone()` is a method that a class can override to define how cloning is exposed and handled.

An extendable class has two reasonable design choices:

1.  Choice A — Allow subclasses to decide whether they support cloning
2. Choice B — Explicitly prohibit cloning for the entire hierarchy

### Protected `clone()` as an extension hook

An extension hook is a protected method that gives subclasses a controlled way to participate in a superclass's behavior.

For example:

```Java
public class Document {
    private String title;

    public Document(String title) {
        this.title = title;
    }

    @Override
    protected Document clone() throws CloneNotSupportedException {
        return (Document) super.clone();
    }
}
```

Now imagine two subclasses.

Subclass A: supports cloning

```
public class CloneableDocument extends Document
        implements Cloneable {

    public CloneableDocument(String title) {
        super(title);
    }

    @Override
    public CloneableDocument clone() {
        try {
            return (CloneableDocument) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Because the runtime class implements `Cloneable`, the call to `Object.clone()` can succeed.

Subclass B: does not support cloning

```
public class ReadOnlyDocument extends Document {
    public ReadOnlyDocument(String title) {
        super(title);
    }
}
```

This class does not implement `Cloneable`. It simply provides a protected method that delegates to `Object.clone()`. Calling the inherited protected `clone()` from within an appropriate subclass context ultimately reaches `Object.clone()`, which throws `CloneNotSupportedException`.

The superclass's method acts as a bridge to `Object.clone()`. The runtime class's implementation of `Cloneable` determines whether the standard cloning operation succeeds.

This approach gives each subclass the freedom to opt in or opt out.

What happens now?

- If a subclass implements `Cloneable`, the call to `Object.clone()` can succeed.
- If the runtime class does not implement `Cloneable`, the call throws `CloneNotSupportedException`.
- The protected method allows subclasses to decide how to expose cloning, or whether to expose it at all.

The return type `Document` is a covariant return type: it narrows the return type from `Object` to `Document`.

Why keep `throws CloneNotSupportedException` here when the public method omitted it earlier? Because this protected method is an extension hook, not necessarily a promise that cloning always succeeds. It preserves the ability to reject cloning when the runtime class does not support it.

Choose this option when:

- Your class is designed for inheritance.
- Some subclasses may benefit from cloning while others should not support it.
- You want subclasses to control their own cloning policy.

### Letting subclasses opt into cloning

Let's complete the previous example.

Superclass — no `Cloneable` commitment

```
public class Document {
    protected String title;

    public Document(String title) {
        this.title = title;
    }

    @Override
    protected Document clone()
            throws CloneNotSupportedException {
        return (Document) super.clone();
    }
}
```

Subclass A — opts into cloning

```
public class CloneableDocument extends Document
        implements Cloneable {

    public CloneableDocument(String title) {
        super(title);
    }

    @Override
    public CloneableDocument clone() {
        try {
            return (CloneableDocument) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

`CloneableDocument` implements `Cloneable`, exposes a public `clone()`, and removes the checked exception from its public signature.

Subclass B — does not opt in

```
public class NonCloneableDocument extends Document {
    public NonCloneableDocument(String title) {
        super(title);
    }
}
```

This subclass does not implement `Cloneable`. The inherited protected method ultimately calls `Object.clone()`, which rejects cloning for this runtime class.

The important idea is that the superclass offers the possibility of cloning without forcing every subclass to adopt it.

In a real subclass with mutable fields, the subclass must also override `clone()` and copy those fields appropriately. Simply implementing `Cloneable` makes `Object.clone()` eligible to run; it does not make a shallow copy deep or otherwise correct.

### Prohibiting cloning with a `final clone()`

Sometimes a superclass should guarantee that cloning is not supported by any subclass. In that case, it can use the alternative recommended by Effective Java:

```
public class Document {
    private String title;

    public Document(String title) {
        this.title = title;
    }

    @Override
    protected final Object clone()
            throws CloneNotSupportedException {
        throw new CloneNotSupportedException();
    }
}
```

Let's understand the three important parts.

| Part          | Purpose                                                                          |
| ------------- | -------------------------------------------------------------------------------- |
| `protected`   | Makes the method available to subclasses without making it a public cloning API. |
| `final`       | Prevents subclasses from overriding the method to provide cloning.               |
| Always throws | Explicitly rejects cloning.                                                      |

Why is `final` necessary?

Without it, a subclass could override `clone()` and implement `Cloneable`, thereby establishing its own cloning behavior. Declaring the rejecting method `final` prevents that override.

This is a deliberate design decision: the superclass prohibits cloning throughout the hierarchy, rather than leaving the decision to individual subclasses.

One nuance: `final clone()` prevents overriding the method, but it does not make the object immutable or prevent every possible form of copying. A subclass could still provide a separate copy constructor or factory unless the broader API design prevents it.

**Why is this called a degenerate implementation?**

A normal `clone()` method attempts to produce a copy. This one always throws an exception, so it intentionally provides no cloning functionality.

It also does not implement `Cloneable`. The `final` method prevents subclasses from replacing the rejection policy with a different `clone()` implementation.

**When to choose this option**

Choose it when:

- Your class is designed for inheritance.
- Cloning is not a supported operation for the class or any subclass.
- You want to enforce that policy rather than relying on documentation.

---

There are actually three distinct designs worth separating:

| Design                                                        | Superclass implements `Cloneable`? | Subclasses can support cloning?      | Purpose                                            |
| ------------------------------------------------------------- | ---------------------------------- | ------------------------------------ | -------------------------------------------------- |
| Cloneable concrete class                                      | Yes                                | Usually yes, with care               | The class itself supports cloning                  |
| Extendable class with a working protected `clone()`           | No                                 | Yes                                  | Subclasses choose whether to implement `Cloneable` |
| Extendable class with a `protected final` rejecting `clone()` | No                                 | No, not through overriding `clone()` | Cloning is prohibited throughout the hierarchy     |

The second design is particularly subtle. The superclass provides a working method implementation without making the `Cloneable` promise itself. The runtime subclass determines whether `Object.clone()` will permit copying.

### The design rule

| Class design                                                      | Recommended approach                                     |
| ----------------------------------------------------------------- | -------------------------------------------------------- |
| Non-final class using the conventional cloning mechanism          | Call `super.clone()` and handle mutable state            |
| Subclass that adds mutable fields                                 | Override `clone()` and copy its additional mutable state |
| Final class with a custom copy implementation using a constructor | No need for `Cloneable`                                  |
| New API where copying behavior should be explicit                 | Prefer a copy constructor or static copy factory         |

The last option is often the simplest for new Java code:

```
Dog copy = new Dog(original);
```

A copy constructor lets the class explicitly decide what to copy without relying on the unusual rules of `Object.clone()`.

The central lesson: `super.clone()` is a convention that enables inheritance-friendly cloning. Java does not enforce it, but violating it in a non-final class can break the cloning behavior expected by subclasses.

---


```
Are you designing a class that supports cloning?
|
+-- Yes, and the class is final
|   |
|   +-- Provide a public clone()
|       - Omit CloneNotSupportedException
|       - Handle unexpected failure internally
|
+-- The class is extendable
    |
    +-- Should subclasses decide whether to support cloning?
    |   |
    |   +-- Yes
    |   |   - Do not implement Cloneable in the superclass
    |   |   - Provide a protected clone() extension hook
    |   |   - Let subclasses opt in by implementing Cloneable
    |   |
    |   +-- No
    |       - Do not implement Cloneable
    |       - Provide a protected final clone()
    |       - Always throw CloneNotSupportedException
```

| Guideline                                               | Main purpose                                          | When to apply                                       |
| ------------------------------------------------------- | ----------------------------------------------------- | --------------------------------------------------- |
| Omit `CloneNotSupportedException` from public `clone()` | Simplify the caller's experience                      | The class promises cloning will work                |
| Avoid `Cloneable` in extendable superclasses            | Avoid imposing a cloning policy on subclasses         | Subclasses may have different copying requirements  |
| Provide protected `clone()` as an extension hook        | Let subclasses opt into cloning                       | The superclass permits but does not require cloning |
| Use protected final rejecting `clone()`                 | Prevent subclasses from overriding the cloning policy | The entire hierarchy must prohibit `clone()`        |


For modern Java development, consider whether you need `clone()` at all. A copy constructor or static copy factory often expresses the copying contract more clearly:

```
Document copy = new Document(original);
```

This approach avoids `Cloneable`'s inheritance complications and allows you to explicitly decide how to copy mutable fields.

Keep the `clone()` guidelines in your knowledge base because they are important when maintaining existing Java APIs and understanding Effective Java. The central lesson is that cloning is not merely an object-copying operation; it is also an inheritance and API-design decision.

## Java `clone()` and Immutablity

Immutable classes generally should not provide a `clone()` method because cloning an immutable object usually provides no benefit while potentially wasting memory and CPU time.

**Why is cloning unnecessary for immutable objects?**

An immutable object cannot change its observable state after construction. Therefore, multiple references can safely share the same instance.

Consider this immutable Java class:

```Java
public final class Money {
    private final int amount;
    private final String currency;

    public Money(int amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public int getAmount() {
        return amount;
    }

    public String getCurrency() {
        return currency;
    }
}
```

Suppose we create a `Money` object:

```Java
Money original = new Money(100, "USD");
```

If we want another reference to the same immutable value, we can simply write:

```Java
Money copy = original;

System.out.println(original == copy); // true
```

Both references point to the same object, and that is safe because neither reference can modify its state.

```
original --------+
                 |
                 v
              +----------------+
              | Money          |
              | amount = 100   |
              | currency= USD  |
              +----------------+
                 ^
                 |
copy -------------+
```

No additional object needs to be allocated.

**What happens if we provide `clone()`?**

Imagine that `Money` implements `Cloneable` and provides a public `clone()` method.

```Java
@Override
public Money clone() {
    try {
        return (Money) super.clone();
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

Now consider:

```Java
Money original = new Money(100, "USD");
Money copy = original.clone();

System.out.println(original == copy); // false
System.out.println(original.getAmount() == copy.getAmount()); // true
```

The values are identical, but Java has allocated a second object unnecessarily.

```
original -------> +----------------+
                  | Money          |
                  | amount = 100   |
                  | currency = USD |
                  +----------------+

copy ------------> +----------------+
                   | Money          |
                   | amount = 100   |
                   | currency = USD |
                   +----------------+
```

The extra allocation consumes memory and adds work for the garbage collector, without providing any additional safety.

**Why this matters for performance**

Imagine an application processing millions of immutable objects.

If code repeatedly clones immutable objects, it can create substantial unnecessary allocation:

```Java
// Wasteful if Money is immutable.
Money result = original.clone();
```

Instead, share the reference:

```Java
// Safe when sharing the immutable instance is permitted.
Money result = original;
```

The second approach avoids creating another object.

This is one reason immutable types are useful in concurrent programs: threads can share the same immutable instance without needing synchronization to protect its state.

**What about a copy constructor or static factory?**

The same principle applies to other copying APIs.

For an immutable class, a copy constructor might simply reuse the fields:

```Java
public Money(Money original) {
    this.amount = original.amount;
    this.currency = original.currency;
}
```

But this still allocates a new object without providing a meaningful benefit.

A copy factory can instead return the original instance:

```Java
public static Money copyOf(Money original) {
    return original;
}
```

This is safe for the immutable `Money` class shown above, provided that returning the same instance is consistent with the factory's documented contract.

Some Java APIs make similar optimizations, but you should not assume every copy factory or library method returns the original instance.

---

**When does this rule apply?**

| Object type                                             | Should it provide `clone()`?         | Reason                                         |
| ------------------------------------------------------- | ------------------------------------ | ---------------------------------------------- |
| Immutable value object                                  | Generally no                         | Sharing the original is safe                   |
| Mutable object                                          | Possibly, but cautiously             | An independent copy may be useful              |
| Immutable object with a documented identity requirement | Depends on the contract              | A distinct instance may be explicitly required |
| New class with an ordinary copying requirement          | Prefer a copy constructor or factory | Copying semantics are easier to define         |

One subtle point: a class is not truly immutable just because its fields are `final`. A `final List<String>` field, for example, can still refer to a mutable list. To benefit from immutable sharing, the object's observable state must genuinely be protected against modification.

The design principle: if two references can safely share the same immutable object, creating a second identical object is usually unnecessary. Avoid `clone()` in immutable classes unless there is a specific, documented reason to require a distinct instance.

## Java `clone()` and Mutablity
### `final` mutable fields
A serious limitation of Java's `clone()` mechanism: if a class has a `final` field referencing a mutable object, it is difficult to create an independent clone of that object.

The problem is not that `final` prevents the object from changing. It prevents the field from being reassigned to a different object after initialization. Let's examine why that matters.

Consider a class that contains a list of elements:

```Java
public class ShoppingCart implements Cloneable {
    private final List<String> elements = new ArrayList<>();

    public void add(String item) {
        elements.add(item);
    }

    @Override
    public ShoppingCart clone() {
        try {
            ShoppingCart copy = (ShoppingCart) super.clone();

            // Problem: cannot assign to a final field
            copy.elements = new ArrayList<>(elements);

            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

This code does not compile because `elements` is `final`.

The intended operation is to give the cloned cart its own list, but Java prohibits this assignment:

```
copy.elements = new ArrayList<>(elements);
```

Why? Because `final` means the field can be assigned only as permitted during initialization, such as in a field initializer or constructor. A `clone()` method is neither.

---

**Why does `super.clone()` make this awkward?**

Normally, `Object.clone()` creates an object without invoking the class's constructors in the usual way. It copies the field values from the original object.

Suppose the original cart looks like this:

```
Original ShoppingCart
+----------------------------+
| elements ------------------|----+
+----------------------------+    |
                                  v
                            +-------------+
                            | ArrayList   |
                            | "Book"      |
                            | "Pen"       |
                            +-------------+
```

After `super.clone()`, the result is:

```
Original ShoppingCart               Cloned ShoppingCart
+----------------------------+      +----------------------------+
| elements ------------------|--+   | elements ------------------|--+
+----------------------------+  |   +----------------------------+  |
                                |                                  |
                                v                                  v
                          +---------------------------------------------+
                          |              Same ArrayList                |
                          | "Book"                                     |
                          | "Pen"                                      |
                          +---------------------------------------------+
```

Both carts refer to the same list. This is a shallow copy.

If you add an item to the cloned cart, the original cart sees it too.

```
ShoppingCart original = new ShoppingCart();
original.add("Book");

ShoppingCart copy = original.clone();
copy.add("Pen");

// Both carts now contain "Book" and "Pen".
```

To avoid that sharing, the clone needs a separate list. But the `final` field prevents the normal post-cloning reassignment needed to achieve it.

---

**Why does this create a conflict between `final` and `clone()`?**

This is a fundamental problem: like serialization, the Cloneable architecture is
incompatible with normal use of final fields referring to mutable objects.

These two design goals pull in opposite directions:

| Design goal                                     | What it requires                                     |
| ----------------------------------------------- | ---------------------------------------------------- |
| Use `final` for the list reference              | The field cannot be reassigned after initialization  |
| Make a shallow clone using `super.clone()`      | The original list reference is copied into the clone |
| Make the clone independent                      | The clone needs a different list reference           |
| Reassign the clone's list after `super.clone()` | Prohibited for a `final` field                       |

The difficulty is specific to this copying mechanism. Java has no ordinary assignment you can perform inside `clone()` to replace the copied `final` field with a newly allocated mutable object.

The same tension appears with Java serialization mechanisms that reconstruct objects without invoking their constructors in the usual way. Custom serialization can sometimes address field reconstruction, but the underlying design problem remains.

---

**What about immutable objects?**

A `final` reference to a mutable object is not inherently wrong. The question is whether the referenced state can change and whether sharing it is safe.

Consider these cases:

| Field                                 | Safe to share between clones?       | Reason                                            |
| ------------------------------------- | ----------------------------------- | ------------------------------------------------- |
| `final String name`                   | Yes                                 | `String` is immutable                             |
| `final int id`                        | Yes                                 | Primitive value is copied                         |
| `final List<String> elements`         | Depends on the contract             | The list itself is mutable                        |
| `final List<ImmutableValue> elements` | Depends on the list's mutability    | Immutable elements do not make the list immutable |
| `final List<MutableValue> elements`   | Usually not for an independent copy | Both the list and its elements may be mutable     |

If the class is genuinely immutable and sharing all referenced objects is safe, a shallow copy might be acceptable. In that case, the field's `final` modifier is not a problem for copying semantics—but the clone itself may be unnecessary.

#### Solution 1: remove `final` from the field

If you need conventional cloning and a deep copy of the list, the direct solution is to make the reference non-final:

```Java
import java.util.ArrayList;
import java.util.List;

public class ShoppingCart implements Cloneable {
    private List<String> elements = new ArrayList<>();

    public void add(String item) {
        elements.add(item);
    }

    public List<String> getElements() {
        return List.copyOf(elements);
    }

    @Override
    public ShoppingCart clone() {
        try {
            ShoppingCart copy = (ShoppingCart) super.clone();

            // Give the clone an independent list.
            copy.elements = new ArrayList<>(elements);

            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    public static void main(String[] args) {
        ShoppingCart original = new ShoppingCart();
        original.add("Book");

        ShoppingCart copy = original.clone();
        copy.add("Pen");

        System.out.println(original.getElements()); // [Book]
        System.out.println(copy.getElements());     // [Book, Pen]
    }
}
```

Now the clone receives a new list, and the original remains unchanged.

Notice that `new ArrayList<>(elements)` creates a new list but only copies the list's element references. This is sufficient for `String` elements because strings are immutable. If the list contained mutable objects, those elements would still be shared unless they were copied separately.

The trade-off is that removing `final` weakens the field's design guarantees. It becomes possible for other code inside the class to reassign the list reference accidentally.

#### Solution 2: use a copy constructor instead

For new Java classes, a copy constructor usually avoids this problem entirely.

```Java
import java.util.ArrayList;
import java.util.List;

public class ShoppingCart {
    private final List<String> elements;

    public ShoppingCart() {
        this.elements = new ArrayList<>();
    }

    public ShoppingCart(ShoppingCart original) {
        this.elements = new ArrayList<>(original.elements);
    }

    public void add(String item) {
        elements.add(item);
    }

    public List<String> getElements() {
        return List.copyOf(elements);
    }

    public static void main(String[] args) {
        ShoppingCart original = new ShoppingCart();
        original.add("Book");

        ShoppingCart copy = new ShoppingCart(original);
        copy.add("Pen");

        System.out.println(original.getElements()); // [Book]
        System.out.println(copy.getElements());     // [Book, Pen]
    }
}
```

Here, `final` remains intact because the constructor assigns `elements` exactly once for each newly created object.

The copy constructor controls how the new object's state is initialized, so it can create an independent list without relying on `Object.clone()`.

#### Summary
A fundamental tension in the `Cloneable` architecture is:

- `final` fields help enforce object invariants.
- `Object.clone()` copies fields first, then gives the overriding method an opportunity to repair the copied state.
- Repairing a copied `final` reference to a mutable object is not possible through ordinary Java assignment.
- Removing `final` to accommodate cloning may weaken the class's design.

Recommendation: don't remove `final` merely to support `clone()` unless you have a compelling reason to preserve a legacy cloning API. For new Java code, prefer a copy constructor or static factory. It lets you keep `final` fields and explicitly control whether mutable objects are shared or independently copied.
## Java `clone()` and Thread Safety

The relationship between `clone()` and thread safety comes down to one important distinction:

Creating a copy of an object does not automatically make that copy thread-safe, and cloning an object while another thread modifies it does not guarantee a consistent snapshot.

To understand why, we need to look at object sharing, mutable state, concurrent access, and the Java Memory Model.

An important concurrency rule: if a class is thread-safe and implements `Cloneable`, its `clone()` method must follow the class's synchronization policy. The reason is simple: `Object.clone()` is not synchronized, so calling it does not automatically protect the object from concurrent modifications while its fields are being copied.

### What does cloning have to do with threads?

Suppose an application has a mutable configuration object shared by several threads.

```Java
class AppConfig implements Cloneable {
    int maxConnections;
    List<String> allowedHosts = new ArrayList<>();

    @Override
    public AppConfig clone() {
        try {
            return (AppConfig) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Initially, imagine that one thread creates the configuration and another thread reads it.

```
                 AppConfig
                /         \
          Thread A       Thread B
           writes         reads
```

If multiple threads access the same mutable object without appropriate synchronization, a data race may occur.

One proposed solution is to clone the configuration and give each thread its own copy.

```
AppConfig threadConfig = sharedConfig.clone();
```

This can help, but only if the copy is created safely and the copied state is independent enough for the intended use.

With the implementation above, `allowedHosts` is still shared between the original and the copy.

```
sharedConfig ──> AppConfig A ──┐
                               |
                               v
                          ArrayList
                               ^
                               |
threadConfig ──> AppConfig B ──┘
```

If one thread modifies the list through `threadConfig` while another accesses it through `sharedConfig`, the original concurrency problem remains.

### Why isn't `super.clone()` already synchronized?

The `clone()` method declared in `Object` is not synchronized.

Calling it from a synchronized method does not change that fact. Instead, the overriding method acquires the lock before making the call:

```
@Override
public synchronized BankAccount clone() {
    try {
        return (BankAccount) super.clone();
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

The sequence is:

1. Acquire the original object's monitor.
2. Invoke `super.clone()` while holding that monitor.
3. Copy the object's fields.
4. Return the clone.
5. Release the original object's monitor.

Note that synchronization protects the original object's state while copying. The new clone does not automatically inherit a locked monitor, and the original's monitor is not the clone's monitor.
### Cloning does not make a class thread-safe

Does synchronizing `clone()` make the clone thread-safe? No, not by itself. It ensures that the copy operation coordinates with other operations that use the same monitor. It does not automatically establish thread safety for the resulting object.

For example, if the original contains a mutable list:

```
private final List<String> names = new ArrayList<>();
```

`super.clone()` copies the reference to that list. Both objects will still share it.

```
Original.names --------+
                       |
                       v
                   Shared List
                       ^
                       |
Clone.names -----------+
```

Even if cloning is synchronized, both objects share the same mutable list. Changes through either reference can affect the other object.

A correct cloning implementation must separately address mutable fields, as discussed in the earlier deep-copy examples.

There is also a memory-model detail: synchronization is useful only when concurrent operations follow a compatible synchronization policy. If another method modifies the fields without acquiring the same monitor, synchronizing `clone()` alone does not protect against that method.

Consider this example:

```
class Counter implements Cloneable {
    int value;

    @Override
    public Counter clone() {
        try {
            return (Counter) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    void increment() {
        value++;
    }
}
```

Suppose two threads share one `Counter`:

```
Counter counter = new Counter();
```

Both threads call:

```
counter.increment();
```

The operation `value++` is not atomic. It involves reading the value, adding one, and writing the result. Concurrent increments can interfere with one another.

Cloning the counter does not fix the thread-safety problem in the original object.

Even if each thread receives its own clone, the original counter's updates remain unsafe if the original is still shared and modified concurrently.

There are three separate questions to consider:

| Question                                                                           | What cloning guarantees                 |
| ---------------------------------------------------------------------------------- | --------------------------------------- |
| Does the clone have a different outer-object identity?                             | Yes, with conventional `Object.clone()` |
| Are mutable nested objects independent?                                            | Not by default                          |
| Is the original object's state copied consistently during concurrent modification? | Not guaranteed                          |

These are three different concerns: object identity, state independence, and concurrency correctness.

### Cloning during concurrent modification
{/* The biggest problem: cloning during concurrent modification */}
Consider a configuration containing two related fields:

```
class TransferConfig implements Cloneable {
    int sourceAccount;
    int destinationAccount;

    @Override
    public TransferConfig clone() {
        try {
            return (TransferConfig) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Suppose the configuration should always represent one of these valid states:

```
State A:
sourceAccount      = 100
destinationAccount = 200

State B:
sourceAccount      = 300
destinationAccount = 400
```

Thread A updates the configuration:

```
config.sourceAccount = 300;
config.destinationAccount = 400;
```

At the same time, Thread B clones it:

```
TransferConfig copy = config.clone();
```

Without synchronization, Thread B is not guaranteed to observe a consistent pair of values. It might copy `sourceAccount = 300` and `destinationAccount = 200`, producing a combination that was never intended as a valid configuration.

The precise outcome depends on the interleaving and the Java Memory Model. The example illustrates why individually copying fields is not equivalent to taking an atomic snapshot of the whole object.

The key issue is that `Object.clone()` does not automatically acquire a lock or establish a happens-before relationship with concurrent writes.

**Another Example**

Imagine a thread-safe class representing a bank account. It maintains two related fields:

```
public class BankAccount implements Cloneable {
    private int balance;
    private int transactionCount;

    public synchronized void deposit(int amount) {
        balance += amount;
        transactionCount++;
    }

    @Override
    public BankAccount clone() {
        try {
            return (BankAccount) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

The `deposit()` method is synchronized, but `clone()` is not.

Suppose the original account has:

```
balance         = 100
transactionCount = 5
```

A thread calls `deposit(50)` while another thread clones the account.

The deposit operation updates both fields under the account's monitor. However, the unsynchronized `clone()` method does not acquire that monitor, so it can overlap with the deposit.

Conceptually, the clone might observe an inconsistent combination:

```
Original account during deposit:

balance          = 150
transactionCount = 5  <- update not completed yet

Clone could copy these intermediate values
```

This is an illustrative interleaving, not a guarantee that a particular execution will produce it. The important point is that the unsynchronized cloning operation has no guarantee of observing a consistent snapshot of the related fields.

### Synchronize both mutation and cloning

One possible approach is to protect all relevant state with the same lock.

```
class TransferConfig implements Cloneable {
    private int sourceAccount;
    private int destinationAccount;

    public synchronized void update(int source, int destination) {
        this.sourceAccount = source;
        this.destinationAccount = destination;
    }

    @Override
    public synchronized TransferConfig clone() {
        try {
            return (TransferConfig) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    public synchronized String describe() {
        return sourceAccount + " -> " + destinationAccount;
    }
}
```

Here, both `update()` and `clone()` acquire the same object's intrinsic monitor.

```
Thread A                         Thread B
--------                         --------
update() acquires lock
source = 300
destination = 400
update() releases lock
                                 clone() acquires lock
                                 copies both fields
                                 clone() releases lock
```

The cloning operation cannot overlap with an `update()` that uses that same monitor.

Important: This only works if every operation that mutates or reads the related state follows the same synchronization discipline. Making `clone()` synchronized alone is insufficient if writers do not use the same lock.

Also, the returned clone has its own monitor. Synchronizing on the original does not synchronize operations on the clone. If the clone has mutable state accessed by multiple threads, its own concurrency requirements must still be addressed.

For BankAccount Example

If the class protects its mutable state using the object's intrinsic monitor, synchronize cloning on that same monitor.

```
public class BankAccount implements Cloneable {
    private int balance;
    private int transactionCount;

    public synchronized void deposit(int amount) {
        balance += amount;
        transactionCount++;
    }

    @Override
    public synchronized BankAccount clone() {
        try {
            return (BankAccount) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

The important change is:

```
public synchronized BankAccount clone()
```

Now both `deposit()` and `clone()` acquire the same monitor: `this`.

```
                 Original BankAccount
                          |
                Shared intrinsic monitor
                          |
              +-----------+-----------+
              |                       |
              v                       v
       deposit()                 clone()
       synchronized              synchronized
              |                       |
              +---- only one at a time
```

If a deposit is already executing, cloning waits until the deposit releases the monitor. If cloning starts first, the deposit waits until cloning finishes.

The clone therefore cannot overlap with a synchronized update performed under the same monitor.


### Shallow cloning and thread safety of nested objects

Let's return to the earlier `AppConfig` example:

```
class AppConfig implements Cloneable {
    int maxConnections;
    List<String> allowedHosts = new ArrayList<>();

    @Override
    public AppConfig clone() {
        try {
            return (AppConfig) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Even if cloning occurs safely, this code still shares the list.

```
AppConfig original = new AppConfig();
AppConfig copy = original.clone();

copy.allowedHosts.add("example.com");
```

The original and copy refer to the same mutable `ArrayList`. If other threads access that list concurrently, cloning has not isolated them from one another.

If the desired contract is independent list structure, copy it explicitly:

```
@Override
public synchronized AppConfig clone() {
    try {
        AppConfig copy = (AppConfig) super.clone();
        copy.allowedHosts = new ArrayList<>(allowedHosts);
        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

This protects the copy operation only if every operation that modifies `allowedHosts` also synchronizes on the original `AppConfig` instance.

The new list is independent, but its elements are shared references. Here that is safe for `String` elements because strings are immutable.

For mutable elements, you may need to copy each element too. And if the original list is concurrently modified without following the same synchronization discipline, even constructing the copied list can fail or produce an inconsistent result.

### 6. What about the Java Memory Model and safe publication?

Even a correctly created clone must be made visible to other threads safely.

For example:

```
private static AppConfig sharedCopy;

public static void publish(AppConfig copy) {
    sharedCopy = copy;
}
```

If one thread writes `sharedCopy` while another reads it without synchronization, a data race exists on the reference. The reader is not guaranteed to observe the write promptly or to have the required visibility guarantees for the object's state.

Common safe-publication mechanisms include:

- Storing the reference in a `volatile` field.
- Publishing it under a shared lock.
- Initializing it in a safely constructed object before making that object accessible.
- Using appropriate concurrent data structures, such as `AtomicReference`.

For example:

```
private static volatile AppConfig sharedCopy;

public static void publish(AppConfig copy) {
    sharedCopy = copy;
}
```

The volatile write and a subsequent volatile read establish a happens-before relationship for actions that occurred before the write. This helps ensure that the reader sees the state established before publication.

However, safe publication does not make subsequent mutations thread-safe. If multiple threads continue modifying `AppConfig` or its nested list, those accesses still need appropriate coordination.

### 7. A better alternative: immutable snapshots

For configuration objects that many threads read, an immutable snapshot is often simpler than cloning a mutable object.

```
import java.util.List;

public record AppConfig(
        int maxConnections,
        List<String> allowedHosts) {

    public AppConfig {
        allowedHosts = List.copyOf(allowedHosts);
    }
}
```

A record is not automatically deeply immutable, but this example makes a defensive copy of the list. Since the elements are immutable strings, the resulting configuration has no exposed mutable state through that list.

You can create a replacement configuration instead of mutating the existing one:

```
AppConfig oldConfig = new AppConfig(
        100,
        List.of("api.example.com")
);

AppConfig newConfig = new AppConfig(
        200,
        List.of("api.example.com", "admin.example.com")
);
```

Threads that already hold `oldConfig` continue to see its original values. Threads that receive `newConfig` see the new configuration.

This approach avoids concurrent mutation of the configuration itself. You still need to publish the new reference safely, for example through a `volatile` field or `AtomicReference`.

### When should you synchronize `clone()`?

| Situation                                                              | Synchronize `clone()`?                  | Reason                                                                              |
| ---------------------------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------- |
| Thread-safe class protects state using `synchronized` instance methods | Usually yes                             | Cloning should coordinate with those methods using the same monitor.                |
| Thread-safe class uses a different lock                                | Coordinate with that lock instead       | Synchronizing on `this` may not protect the state.                                  |
| Immutable class                                                        | Often unnecessary for state consistency | Its state cannot change after construction, though its copy contract still matters. |
| Class is not thread-safe                                               | Not automatically necessary             | Synchronization does not make an otherwise unsafe class thread-safe.                |
| Class uses atomic fields or lock-free algorithms                       | Depends on its consistency requirements | A coordinated snapshot may require more than simply synchronizing `clone()`.
### 8. Quick comparison

| Technique                                             | Safe concurrent snapshot?                              | Independent mutable state?                 |
| ----------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------ |
| Plain `super.clone()`                                 | Not guaranteed                                         | No, not for nested objects                 |
| Synchronized clone only                               | Only if writers use the same lock                      | No, not by itself                          |
| Synchronized clone and synchronized mutations         | Yes, for state consistently protected by the same lock | Only if mutable fields are copied          |
| Deep copy under a consistent synchronization strategy | Can be                                                 | Yes, for the mutable state actually copied |
| Immutable snapshot with safe publication              | Generally the simplest approach                        | Yes, if immutability is properly enforced  |

### 9. Design guidelines

When considering `clone()` in multithreaded Java code:

1. Do not assume cloning makes an object thread-safe. Thread safety is a property of how state is accessed and modified.
2. Coordinate cloning with mutation. If a consistent snapshot is required, use a shared synchronization strategy or another snapshot mechanism.
3. Examine nested mutable fields. A shallow copy may leave threads sharing the same collections or domain objects.
4. Publish the clone safely. Correct construction alone does not eliminate visibility issues.
5. Consider immutable snapshots. For read-heavy configuration and value objects, immutability often simplifies concurrent access considerably.

The central principle is that cloning solves an object-copying problem, while thread safety solves a concurrent-access problem. They can work together, but neither guarantees the other.

The key takeaway: If a thread-safe class uses a monitor to protect its mutable state, its `clone()` method generally needs to acquire that same monitor while copying the state. But synchronization and deep copying solve different problems: synchronization protects the copying process from concurrent updates, while deep copying determines which mutable objects the original and clone share.

## Java `clone()` vs. Serialization

Java's `clone()` and serialization are two different mechanisms that can be used to duplicate an object's state, but they work in fundamentally different ways.

- Cloning creates a new object by copying the original object's fields.
- Serialization converts an object's state into a byte stream. Deserialization reconstructs an object from that stream.

Serialization is sometimes used to make a deep copy of an object graph, while `Object.clone()` normally creates a shallow copy.

Understanding the differences is useful when designing Java classes, copying complex object graphs, working with legacy code, and deciding how to preserve object state.

### 1. How `clone()` works

Consider a simple Java class:

```Java
class Employee implements Cloneable {
    int id;
    String name;

    Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public Employee clone() {
        try {
            return (Employee) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Usage:

```Java
Employee original = new Employee(101, "Mona");
Employee copy = original.clone();

System.out.println(original == copy); // false
System.out.println(copy.name);        // Mona
```

The JVM creates a new `Employee` instance and copies its fields. Primitive fields are copied by value, and reference fields are copied as references.

For example:

```
original ──> Employee A
                id = 101
                name ─────┐
                          |
                          v
                      "Mona"
                          ^
                          |
copy ───────> Employee B  |
                id = 101  |
                name ─────┘
```

The two employee objects are distinct, but they can share referenced objects. This is called a shallow copy.

### 2. How serialization works

Java serialization allows a serializable object's state to be written to a byte stream and later reconstructed.

The traditional Java mechanism uses:

- `Serializable` — a marker interface.
- `ObjectOutputStream` — writes objects to a stream.
- `ObjectInputStream` — reads and reconstructs objects.

Here is a basic example:

```Java
import java.io.Serializable;

class Employee implements Serializable {
    private static final long serialVersionUID = 1L;

    int id;
    String name;

    Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }
}
```

To serialize an object, you write it to a stream:

```Java
ObjectOutputStream out =
        new ObjectOutputStream(outputStream);

out.writeObject(original);
out.close();
```

To reconstruct the object, you read it from an input stream:

```Java
ObjectInputStream in =
        new ObjectInputStream(inputStream);

Employee restored = (Employee) in.readObject();
in.close();
```

Here, `outputStream` and `inputStream` represent appropriately configured streams, such as byte-array streams or file streams.

The reconstructed object is distinct from the original in-memory object. For ordinary serializable object graphs, serialization preserves the graph's reference relationships rather than simply copying each field independently.

Serialization is also used for persistence, communication, and interoperability with compatible Java serialization streams. It is not merely an object-copying mechanism.

### 3. The key difference: shallow copy vs. deep copy

Let's use an employee with a mutable address.

```Java
class Address implements java.io.Serializable {
    private static final long serialVersionUID = 1L;

    String city;

    Address(String city) {
        this.city = city;
    }
}
```

The employee now contains an `Address` reference:

```Java
class Employee implements Cloneable, java.io.Serializable {
    private static final long serialVersionUID = 1L;

    int id;
    String name;
    Address address;

    Employee(int id, String name, Address address) {
        this.id = id;
        this.name = name;
        this.address = address;
    }

    @Override
    public Employee clone() {
        try {
            return (Employee) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

#### Using `clone()`

```Java
Employee original = new Employee(
    101, "Mona", new Address("Cairo")
);

Employee copy = original.clone();

System.out.println(original == copy);                 // false
System.out.println(original.address == copy.address); // true

copy.address.city = "Alexandria";

System.out.println(original.address.city); // Alexandria
```

The employee was copied, but the address was not. Both employees share the same mutable address.

#### Using serialization

If we serialize `original` and then deserialize it into `copy`, the address is reconstructed as part of the serialized object graph.

```
Before serialization:

original ──> Employee A ──> Address A
                                city = Cairo

After serialization and deserialization:

original ──> Employee A ──> Address A
                                city = Cairo

copy ──────> Employee B ──> Address B
                                city = Cairo
```

The reconstructed address is distinct from the original address, assuming it is part of the serialized graph and is not deliberately replaced or shared through custom serialization logic.

Changing `copy.address.city` to `"Alexandria"` will therefore not change the original address.

Why? Serialization reconstructs the serialized object graph, including ordinary non-transient object references. This often gives you deep-copy-like behavior without manually writing code to copy every nested object.

However, serialization is not automatically a universal deep-copy solution: `transient` fields, static state, custom serialization, `writeReplace`/`readResolve`, and external resources can change the result.

### 4. Complete serialization-based deep-copy example

The following utility serializes an object to memory and deserializes it to produce a copy.

```Java
import java.io.*;

public class SerializationCopy {

    @SuppressWarnings("unchecked")
    public static <T extends Serializable> T deepCopy(T original)
            throws IOException, ClassNotFoundException {

        ByteArrayOutputStream bytes = new ByteArrayOutputStream();

        try (ObjectOutputStream out =
                     new ObjectOutputStream(bytes)) {
            out.writeObject(original);
        }

        try (ObjectInputStream in = new ObjectInputStream(
                new ByteArrayInputStream(bytes.toByteArray()))) {
            return (T) in.readObject();
        }
    }
}
```

Usage:

```Java
Employee original = new Employee(
    101, "Mona", new Address("Cairo")
);

Employee copy = SerializationCopy.deepCopy(original);

System.out.println(original == copy);                 // false
System.out.println(original.address == copy.address); // false

copy.address.city = "Alexandria";

System.out.println(original.address.city); // Cairo
System.out.println(copy.address.city);     // Alexandria
```

Both `Employee` and `Address` must implement `Serializable`, as must the other reachable objects that need to be serialized. Otherwise, serialization can fail with `NotSerializableException`.

This technique is useful for learning how object graphs are reconstructed, but it is usually not the preferred way to copy ordinary application objects.

### 5. Important differences

| Feature                                      | `clone()`                                                                     | Serialization and deserialization                                             |
| -------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Main purpose                                 | Copy an existing object                                                       | Convert object state to bytes and reconstruct it                              |
| Typical copy behavior                        | Shallow by default                                                            | Reconstructs the serialized object graph                                      |
| Requires `Cloneable`                         | For conventional `Object.clone()`                                             | No                                                                            |
| Requires `Serializable`                      | No                                                                            | Yes, for ordinary serialized classes                                          |
| Copies nested objects independently          | Only if explicitly implemented                                                | Usually, for objects included in the serialized graph                         |
| Preserves shared references inside the graph | Shallow copying preserves copied references; custom deep copying is up to you | Yes, ordinarily preserves graph reference relationships                       |
| Handles cycles                               | A shallow copy does not traverse the graph                                    | Yes, the serialization mechanism supports cyclic graphs                       |
| Constructor behavior                         | `Object.clone()` does not invoke constructors normally                        | Deserialization does not invoke constructors of serializable classes normally |
| Performance                                  | Usually cheaper for shallow copies                                            | Usually more expensive due to stream processing                               |
| External resources                           | May copy references to resources                                              | Does not automatically recreate independent external resources                |
| Main risks                                   | Incorrect copying of mutable fields                                           | Compatibility, security, performance, and serialization-specific behavior     |

### 6. Important pitfalls of serialization-based copying

#### A. Every required nested object must be serializable

```Java
class Address {
    String city;
}
```

If an `Employee` contains an `Address` like this, but `Address` does not implement `Serializable`, ordinary serialization of the employee will fail.

#### B. `transient` fields are not ordinarily serialized

```Java
private transient String temporaryToken;
```

After deserialization, this field will have its default value unless custom deserialization code restores it. This can make a serialization-based copy differ from the original.

#### C. Object identity relationships are preserved

Suppose two fields point to the same object before serialization:

```
Employee
   |       |
   v       v
 address1  address2
      \   /
       Address A
```

Ordinary serialization preserves that shared relationship when reconstructing the graph:

```
Employee copy
   |       |
   v       v
 address1  address2
      \   /
       Address B
```

This is often desirable. A deep copy does not necessarily mean duplicating every reference independently; it means creating the intended independent object graph while preserving meaningful relationships.

#### D. Deserialization has security implications

Java native serialization should not be used casually with untrusted input. Deserialization can trigger application code and expose security vulnerabilities. If it is necessary, use appropriate serialization filters and strict input controls. Do not use it as a convenient general-purpose copying technique for arbitrary objects.

#### E. Performance and maintainability

Serialization creates and processes a byte stream, and it requires classes to follow serialization rules. For ordinary domain objects, a copy constructor is often simpler, faster, and easier to maintain.

### 7. Which technique should you choose?

Use `clone()`

When maintaining an existing class that deliberately implements `Cloneable`, and its cloning contract is well-defined.

Use a copy constructor or factory

When building a new Java API and you need explicit control over which fields are shared or copied. This is generally my recommendation for ordinary application objects.

Use serialization

When you actually need serialization—for example, persistence or compatible data exchange—or when a carefully controlled legacy system has a justified serialization-based copying requirement.

The central lesson is that `clone()` and serialization are mechanisms, not guarantees of deep copying. `clone()` starts with a shallow field copy, while serialization reconstructs a serialized object graph. For new Java code, explicit copying through constructors or factories is usually the clearest way to define the exact behavior you need.

## Design guidelines

The following guidelines are particularly important when designing new Java classes.

### Guideline 1: Prefer copy constructors or static factories for new APIs

{/* Effective Java, Item 13, Override clone judiciously, recommends caution with `Cloneable` and `clone()`. */}

A copy constructor makes the copy operation explicit:

```Java
class Address {
    private final String city;

    Address(String city) {
        this.city = city;
    }

    Address(Address source) {
        this.city = source.city;
    }
}
```

A containing object can then define its copying policy:

```Java
class Student {
    private final int id;
    private final String name;
    private final Address address;

    Student(int id, String name, Address address) {
        this.id = id;
        this.name = name;
        this.address = address;
    }

    Student(Student source) {
        this.id = source.id;
        this.name = source.name;
        this.address = source.address == null
                ? null
                : new Address(source.address);
    }
}
```

This example deliberately creates a new `Address`. If sharing an address is the intended design, the constructor could instead reuse the reference.

You can also expose a named factory:

```Java
public static Student copyOf(Student source) {
    return new Student(source);
}
```

The copy constructor and factory do not require `Cloneable`, do not require catching `CloneNotSupportedException`, and can define their behavior directly.

### Guideline 2: Document the copying semantics

A method named `clone()` does not tell the caller whether nested mutable objects are shared.

Document whether the copy is:

- Shallow or deep.
- Independent with respect to mutable fields.
- Allowed to share immutable objects.
- Expected to preserve object identity relationships inside a graph.

Clear semantics matter more than the method name.

When documenting a copy operation, answer three questions:

1. What is new? Which object instances and collections are newly created?
2. What is shared? Which references still point to the same objects?
3. What is independent? Which changes to the copy are guaranteed not to affect the original?

For Java's `clone()` specifically, this is particularly important because `super.clone()` only performs a shallow field-by-field copy. If you override `clone()` to implement deep copying, document precisely which mutable fields are copied independently.

Bottom line: Good copying documentation describes observable behavior, not merely the implementation technique. A caller should be able to use `copy()` correctly without reading the method's source code.

#### Example: Documenting an order-copying API
Let's use a realistic Java backend example: copying an e-commerce order before modifying it. This is a good example because an order contains nested mutable objects, and unclear copying semantics can cause serious bugs.

Suppose an order contains:

- An order ID.
- A list of order items.
- A shipping address.

```Java
class Order {
    String orderId;
    List<OrderItem> items;
    Address shippingAddress;
}
```

Now imagine another developer writes:

```Java
Order draft = original.copy();
draft.items.clear();
```

What should happen to `original.items`?

There are two possible contracts:

- Shallow copy: The original and draft share the same list. Clearing the draft's list also clears the original's list.
- Independent copy: The draft has its own list, so clearing it does not affect the original.

If the API does not document this behavior, developers may make incorrect assumptions.

Let's implement a copy operation with clearly defined semantics.

Order.java

```Java
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

public class Order {
    private final String orderId;
    private final List<OrderItem> items;
    private final Address shippingAddress;

    public Order(
            String orderId,
            List<OrderItem> items,
            Address shippingAddress) {
        this.orderId = Objects.requireNonNull(orderId);
        this.items = new ArrayList<>(items);
        this.shippingAddress = shippingAddress;
    }

    /**
     * Creates an independent draft of this order.
     *
     * Copying semantics:
     * - The order ID is shared as an immutable String value.
     * - The item list is copied.
     * - Each OrderItem is copied.
     * - The shipping address is copied.
     * - Changes to the copied order's items or address
     *   do not affect this order.
     *
     * @return a new Order with independent mutable state
     */
    public Order copy() {
        List<OrderItem> copiedItems = items.stream()
                .map(OrderItem::new)
                .toList();

        Address copiedAddress =
                new Address(shippingAddress);

        return new Order(
                orderId,
                copiedItems,
                copiedAddress
        );
    }

    public List<OrderItem> getItems() {
        return items;
    }

    public Address getShippingAddress() {
        return shippingAddress;
    }
}
```

For this example, assume `OrderItem` and `Address` provide copy constructors:

```Java
class OrderItem {
    String product;
    int quantity;

    OrderItem(OrderItem source) {
        this.product = source.product;
        this.quantity = source.quantity;
    }
}

class Address {
    String city;

    Address(String city) {
        this.city = city;
    }

    Address(Address source) {
        this.city = source.city;
    }
}
```

The documentation tells callers exactly which objects are shared and which are copied.

One implementation detail: `Stream.toList()` returns an unmodifiable list in modern Java. If the copied order is intended to support adding and removing items, construct a mutable list instead:

```Java
List<OrderItem> copiedItems = new ArrayList<>();

for (OrderItem item : items) {
    copiedItems.add(new OrderItem(item));
}
```

This is an example of why documentation and implementation must agree.
```

Original order
+-------------------
|Order A
|
|orderId = "ORD-101"
|items → List A
|address → Address A
+--------------------
↓ copy() ↓
↓        ↓
Copied draft
+-------------------
|Order B
|
|orderId = "ORD-101"
|items → List B → copied items
|address → Address B
+-------------------
List B and Address B are independent of List A and Address A. The immutable order ID can be shared.
```
**Testing the documented contract**

The documentation is useful only if the implementation satisfies it.

```Java
public class Main {
    public static void main(String[] args) {
        List<OrderItem> items = new ArrayList<>();
        items.add(new OrderItem(new OrderItemData("Laptop", 1)));

        Order original = new Order(
                "ORD-101",
                items,
                new Address("Cairo")
        );

        Order draft = original.copy();

        draft.getItems().get(0).quantity = 3;
        draft.getShippingAddress().city = "Alexandria";

        // Original state must remain unchanged.
        assert original.getItems().get(0).quantity == 1;
        assert original.getShippingAddress().city.equals("Cairo");
    }
}
```

The `OrderItemData` helper in that snippet is unnecessary if you construct the initial item directly. The essential test is that modifying the copied item's quantity and address leaves the original unchanged. In production, use JUnit assertions rather than Java's `assert` unless assertions are explicitly enabled.

---

**What should the documentation say in different scenarios?**

Here are examples of useful copying contracts.

| Copying behavior       | Example documentation                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Shallow copy           | “Creates a new order object, but shares its item list and shipping address with the original.”                                     |
| Independent collection | “Creates a new item list. The list elements are shared with the original.”                                                         |
| Deep copy              | “Copies the item list, each mutable item, and the shipping address. Mutations to these copied objects do not affect the original.” |
| Immutable object       | “Returns an equivalent immutable value. The implementation may return the same instance.”                                          |
| Resource-owning object | “Copies configuration only; the underlying connection is shared and is not duplicated or independently owned.”                     |

These contracts are not interchangeable. Choose the one that matches the actual implementation and the guarantees callers need.

### Guideline 3: Use `super.clone()` when implementing conventional cloning

If your class deliberately supports the standard cloning protocol, calling `super.clone()` is generally the expected approach.

```Java
@Override
public Student clone() {
    try {
        Student copy = (Student) super.clone();
        // Copy or adjust fields as needed.
        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

This allows the mechanism to produce the correct runtime class, rather than manually constructing a new base-class instance.

### Guideline 4: Handle mutable fields deliberately

For each field, decide how copying should work.

| Field type                                | Typical copying decision                                   |
| ----------------------------------------- | ---------------------------------------------------------- |
| Primitive (`int`, `boolean`)              | Copy the value                                             |
| Immutable object (`String`, `Integer`)    | Share the reference                                        |
| Mutable array                             | Clone or copy elements according to requirements           |
| Mutable collection                        | Create a new collection if independent structure is needed |
| Mutable domain object                     | Share, copy, or deep-copy according to the contract        |
| File, socket, thread, database connection | Usually do not duplicate by copying the reference          |

This table describes typical choices, not universal rules. For example, a mutable collection can intentionally be shared when it represents shared state.

### Guideline 5: Keep the inheritance contract consistent

If a class is designed for inheritance and supports cloning, subclasses may need to copy their own additional mutable fields.

Consider:

```
BaseDocument
    |
    +-- ReportDocument
            |
            +-- FinancialReport
```

A cloning implementation in `BaseDocument` cannot automatically know how to independently copy every mutable field introduced by future subclasses.

If subclasses override `clone()`, each override must follow a consistent contract and correctly handle the superclass state.

This complexity is one reason copy constructors are often easier to maintain.

The key point is that a superclass's `clone()` method can copy fields it knows nothing about, but it cannot automatically make the mutable objects referenced by subclass fields independent.

Suppose `BaseDocument` contains a title and provides a public `clone()` method.

```Java
class BaseDocument implements Cloneable {
    protected String title;

    public BaseDocument(String title) {
        this.title = title;
    }

    @Override
    public BaseDocument clone() {
        try {
            return (BaseDocument) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Notice that `super.clone()` creates an object with the same runtime class as the original object. If the original object is a `ReportDocument`, the cloned object is also a `ReportDocument`.

However, `BaseDocument` only performs a shallow copy. It does not know what additional fields subclasses might introduce.

Now `ReportDocument` adds a mutable list of sections.

```Java
import java.util.ArrayList;
import java.util.List;

class ReportDocument extends BaseDocument {
    protected List<String> sections;

    public ReportDocument(String title) {
        super(title);
        this.sections = new ArrayList<>();
    }
}
```

Let's clone a report:

```Java
ReportDocument original = new ReportDocument("Annual Report");
original.sections.add("Introduction");

ReportDocument copy = original.clone();

copy.sections.add("Financial Results");

System.out.println(original.sections);
```

Output:

```
[Introduction, Financial Results]
```

Why did the original change? Because `ReportDocument` inherited `BaseDocument.clone()` without overriding it. The inherited method called `Object.clone()`, which copied the `sections` reference rather than creating a new list.

The object graph looks like this:

```
original ──> ReportDocument A
                |
                +── sections ──┐
                               |
                               v
                          ArrayList
                          ["Introduction",
                           "Financial Results"]
                               ^
                               |
copy ──────> ReportDocument B  |
                |              |
                +── sections ──┘
```

There are two distinct report objects, but only one list.

**Fix the problem by overriding `clone()` in every subclass***

`ReportDocument` must override `clone()` to copy its own mutable fields.

```Java
@Override
public ReportDocument clone() {
    ReportDocument copy = (ReportDocument) super.clone();

    // Create an independent list.
    copy.sections = new ArrayList<>(sections);

    return copy;
}
```

Now `ReportDocument` cloning works correctly:

```
original ──> ReportDocument A
                |
                +── sections ──> List A
                                  ["Introduction"]

copy ──────> ReportDocument B
                |
                +── sections ──> List B
                                  ["Introduction"]
```

But what happens when another subclass adds more mutable state? Suppose `FinancialReport` extends `ReportDocument` and adds a mutable list of financial notes.

```Java
class FinancialReport extends ReportDocument {
    private List<String> financialNotes;

    public FinancialReport(String title) {
        super(title);
        this.financialNotes = new ArrayList<>();
    }
}
```

Even though `ReportDocument.clone()` now correctly copies `sections`, `financialNotes` is still shallow-copied.

If `FinancialReport` inherits that method without overriding it, this code demonstrates the problem:

```Java
FinancialReport original =
        new FinancialReport("Annual Financial Report");

// Assume the original has some financial notes.
FinancialReport copy = original.clone();

// The inherited clone method has not copied financialNotes.
```

The actual cloned object is a `FinancialReport`, but the `financialNotes` field still points to the original list.

Each subclass is responsible for copying the mutable state it introduces.

**Complete implementation: every class handles its own fields**

Here is the corrected hierarchy.

BaseDocument.java

```Java
class BaseDocument implements Cloneable {
    protected String title;

    public BaseDocument(String title) {
        this.title = title;
    }

    @Override
    public BaseDocument clone() {
        try {
            return (BaseDocument) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

ReportDocument.java

```Java
import java.util.ArrayList;
import java.util.List;

class ReportDocument extends BaseDocument {
    protected List<String> sections;

    public ReportDocument(String title) {
        super(title);
        this.sections = new ArrayList<>();
    }

    @Override
    public ReportDocument clone() {
        ReportDocument copy = (ReportDocument) super.clone();

        // Copy the mutable state introduced here.
        copy.sections = new ArrayList<>(sections);

        return copy;
    }
}
```

FinancialReport.java

```Java
import java.util.ArrayList;
import java.util.List;

class FinancialReport extends ReportDocument {
    private List<String> financialNotes;

    public FinancialReport(String title) {
        super(title);
        this.financialNotes = new ArrayList<>();
    }

    @Override
    public FinancialReport clone() {
        FinancialReport copy =
                (FinancialReport) super.clone();

        // Copy the mutable state introduced here.
        copy.financialNotes =
                new ArrayList<>(financialNotes);

        return copy;
    }
}
```
When you execute:

```
FinancialReport copy = original.clone();
```

Java dispatches to `FinancialReport.clone()`, which calls `ReportDocument.clone()`, which calls `BaseDocument.clone()`.

The resulting sequence is:

1\. `BaseDocument.clone()`

Creates the shallow object copy, including the inherited `title` reference.

2\. `ReportDocument.clone()`

Creates an independent `sections` list.

3\. `FinancialReport.clone()`

Creates an independent `financialNotes` list.

The final object has independent mutable lists at both subclass levels.

---

**Test the complete implementation**

Add getters or test code inside the classes to access the fields, then run:

```Java
FinancialReport original =
        new FinancialReport("Annual Report");

original.sections.add("Introduction");
original.financialNotes.add("Revenue increased");

FinancialReport copy = original.clone();

copy.sections.add("Conclusion");
copy.financialNotes.add("Expenses decreased");

System.out.println(original.sections);
System.out.println(copy.sections);

System.out.println(original.financialNotes);
System.out.println(copy.financialNotes);
```

Expected output:

```
[Introduction]
[Introduction, Conclusion]

[Revenue increased]
[Revenue increased, Expenses decreased]
```

Each mutable list is now independent.

---

**The important limitation**

Even this implementation only makes shallow copies of each list. If a list contains mutable objects rather than strings, those objects are still shared.

For example:

```
copy.sections = new ArrayList<>(sections);
```

copies the list structure, not the objects inside it.

Also, this approach depends on every subclass correctly overriding `clone()`. A future subclass can introduce a new mutable field and forget to copy it.

That is the central inheritance problem: the superclass cannot anticipate the copying requirements of subclasses written later.

For new Java APIs, a copy constructor or explicit copy factory is often easier to maintain because each constructor can clearly define how the object's state is copied, without relying on every subclass to follow the `clone()` protocol.

### Guideline 6: Consider immutability

If an object is immutable, copying it may not be necessary at all.

```Java
String original = "Java";
String reference = original;
```

Both variables safely refer to the same immutable string. Creating another identical string object generally adds no value.

For an immutable value class, returning `this` from a copy-like factory can sometimes be appropriate, provided the API's contract permits it.

This is safe when the object cannot be changed in a way that affects its observable state and when the API contract allows the returned object to be the same instance.

Consider a class representing a geographical coordinate.

```Java
public final class Coordinate {
    private final double latitude;
    private final double longitude;

    public Coordinate(double latitude, double longitude) {
        this.latitude = latitude;
        this.longitude = longitude;
    }

    public double latitude() {
        return latitude;
    }

    public double longitude() {
        return longitude;
    }
}
```

This class is designed to be immutable:

- The class is `final`, so subclasses cannot introduce mutable behavior.
- Its fields are `private final`.
- Its constructor initializes the fields.
- It provides no methods that modify its state.
- Its fields are primitive values, so there are no mutable objects exposed through references.

Once a `Coordinate` is created, its latitude and longitude cannot change.

Now suppose we want a method named `copy()`.

A straightforward implementation would be:

```Java
public Coordinate copy() {
    return new Coordinate(latitude, longitude);
}
```

Every call allocates a new object, even though the new coordinate has exactly the same value and cannot be modified.

We can instead write:

```Java
public Coordinate copy() {
    return this;
}
```

Here, `this` means the current object.

**What happens when we call `copy()`?**

```Java
public class Main {
    public static void main(String[] args) {
        Coordinate original = new Coordinate(30.0444, 31.2357);

        Coordinate copy = original.copy();

        System.out.println(original == copy); // true

        System.out.println(copy.latitude());  // 30.0444
        System.out.println(copy.longitude()); // 31.2357
    }
}
```
Because `copy()` returns `this`, both variables refer to the exact same object.

```
original ──────┐
               |
               v
        +--------------------+
        | Coordinate         |
        | latitude  = 30.0444|
        | longitude = 31.2357|
        +--------------------+
               ^
               |
copy ──────────┘
```

Compare that with creating a new object:

```Java
public Coordinate copy() {
    return new Coordinate(latitude, longitude);
}
```

```
original ──────> Coordinate A
                  latitude  = 30.0444
                  longitude = 31.2357

copy ──────────> Coordinate B
                  latitude  = 30.0444
                  longitude = 31.2357
```

Both implementations produce the same coordinate value, but their identity differs.

| Expression                            | `return this` | `return new Coordinate(...)` |
| ------------------------------------- | ------------- | ---------------------------- |
| `original == copy`                    | `true`        | `false`                      |
| Same coordinate values                | Yes           | Yes                          |
| New object allocated                  | No            | Yes                          |
| Safe if the object is truly immutable | Yes           | Yes                          |
| Preserves distinct object identity    | No            | Yes                          |

The performance benefit is avoiding an unnecessary allocation. Whether that matters in practice depends on how often the method is called and how expensive object creation is.

---

Why this does not work for mutable objects

Consider a mutable configuration class:

```Java
public class MutableConfig {
    private String host;

    public MutableConfig(String host) {
        this.host = host;
    }

    public void setHost(String host) {
        this.host = host;
    }

    public String host() {
        return host;
    }

    public MutableConfig copy() {
        return this; // Dangerous for a copy operation
    }
}
```

Now:

```Java
MutableConfig original = new MutableConfig("server-a");
MutableConfig copy = original.copy();

copy.setHost("server-b");

System.out.println(original.host()); // server-b
```

The caller expected a copy, but modifying it changed the original because both variables refer to the same mutable object.

The correct implementation would create a new instance:

```Java
public MutableConfig copy() {
    return new MutableConfig(host);
}
```

Now changes to the copied configuration do not affect the original.

The rule is not simply that immutable objects can return `this` and mutable objects cannot. The important questions are whether sharing is safe and whether the method's documented contract permits returning the same instance.

---

**relation to `copyOf()` and Java APIs**

A copy-like factory often uses a name such as `copyOf()`:

```Java
public static Coordinate copyOf(Coordinate source) {
    return source;
}
```

This is valid for the immutable `Coordinate` class because the factory can safely reuse the instance. The factory should document that it may return the original object.

A related example from the Java standard library is `List.copyOf()`:

```Java
List<String> names = List.of("Mona", "Ali");

List<String> snapshot = List.copyOf(names);
```

The returned list is unmodifiable, and its elements are shared references. Because `String` is immutable, sharing the elements is safe.

However, do not assume `List.copyOf()` always returns the same list instance you pass in. Its API does not promise identity preservation, and mutable input collections can require a distinct unmodifiable snapshot.

---

**The design guideline**

Use `return this` for a copy-like method when all of the following hold:

1. The object is genuinely immutable, including its reachable state as observed through its public API.
2. Sharing the same instance is safe for all callers.
3. The API contract permits returning the original instance.
4. Callers do not rely on receiving a distinct object.

This is also why immutable objects and cloning are closely related design topics: immutability often eliminates the need to copy an object at all.

### Guideline 7: Avoid exposing cloning accidentally

Implementing `Cloneable` can have implications for subclasses. Inheriting a public cloning method may expose behavior that the subclass did not intend to support.

For classes that are not intended to be cloned, do not implement `Cloneable` merely because it seems convenient.

### Omitting `CloneNotSupportedException`
The `clone()` method inherited from `Object` declares a checked exception:

```Java
protected native Object clone() throws CloneNotSupportedException;
```

Because `CloneNotSupportedException` is a checked exception, callers of this method must catch it or declare it.

A checked exception affects every caller that must handle it. However, if your class explicitly supports cloning, its public API generally should not force callers to handle an exception that should never occur during normal operation.

For example:

```Java
public class Point implements Cloneable {
    private int x;
    private int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    @Override
    public Point clone() {
        try {
            return (Point) super.clone();
        } catch (CloneNotSupportedException e) {
            // Point implements Cloneable, so this should not happen.
            throw new AssertionError(e);
        }
    }
}
```

Usage:

```Java
Point original = new Point(10, 20);
Point copy = original.clone(); // No checked-exception handling required.
```

Notice two decisions:

- The method is `public`, so callers can invoke it directly.
- It returns `Point`, rather than `Object`, so callers do not need a cast.

Java allows an overriding method to omit a checked exception declared by the original method. It does not allow the override to introduce a broader checked exception.

Why catch the exception and throw `AssertionError`?

Under the standard `Object.clone()` behavior, a `CloneNotSupportedException` should not occur when the runtime class implements `Cloneable`. If it does occur, something has violated the expected contract, so treating it as an unexpected error is reasonable.

This is different from silently swallowing the exception or returning `null`, both of which would hide a failure.

Guideline: If a public `clone()` method promises to work, omit `throws CloneNotSupportedException` and handle the theoretically unexpected exception internally.

### Regenerate Unique Identifiers
If the class contains only primitive fields or refer-
ences to immutable objects, then it is likely the case that no fields need to be fixed.
There are exceptions to this rule. For example, a field representing a serial number
or other unique ID will need to be fixed even if it is primitive or immutable.

 primitive field can still need fixing if its meaning requires uniqueness.

Consider:

```
public class Document implements Cloneable {
    private long serialNumber;
    private String title;

    public Document(long serialNumber, String title) {
        this.serialNumber = serialNumber;
        this.title = title;
    }

    @Override
    public Document clone() {
        try {
            Document copy = (Document) super.clone();

            // Problem: serialNumber is still duplicated!
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

After cloning:

```
Original Document             Cloned Document
-----------------             ---------------
serialNumber = 1001           serialNumber = 1001
title = "Java"                title = "Java"
```

If the serial number must uniquely identify a document, this clone is invalid even though every field was copied correctly at the memory level.

You must assign a new identity according to the application's rules:

```
@Override
public Document clone() {
    try {
        Document copy = (Document) super.clone();
        copy.serialNumber = SerialNumbers.next();
        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

Here, `SerialNumbers.next()` is an illustrative application-specific ID generator. It must provide the required uniqueness guarantees, including under concurrency if multiple threads can create documents simultaneously.

The same principle applies to immutable references. An immutable UUID is safe to share as an object, but if it represents an entity's unique identity, the cloned entity may need a newly generated UUID.

The distinction is between technical mutability and semantic meaning. A field does not need to be mutable to require a different value in the clone.

## Common `clone()` pitfalls

These are the most important problems to recognize during code review and technical interviews.

### Pitfall 1: Assuming `Cloneable` declares `clone()`

It does not.

```Java
class Student implements Cloneable {
}
```

This does not provide a public `Student.clone()` method. `Object.clone()` remains protected unless a class overrides it with broader access.

The Cloneable interface was intended as a mixin interface for classes to
advertise that they permit cloning. Unfortunately, it fails to serve this purpose. Its
primary flaw is that it lacks a clone method, and Object’s clone method is protected. You cannot, without resorting to reflection, invoke clone on an
object merely because it implements Cloneable. Even a reflective invocation may
fail, because there is no guarantee that the object has an accessible clone method.

This is one of the biggest design problems with Java's `Cloneable` interface: it advertises that an object can be cloned, but it does not provide a method that lets you clone that object.

A mixin interface is an interface that allows a class to declare that it supports some additional capability alongside its main purpose.

For example, Java's `Comparable` interface provides a way for objects to advertise that they can be compared:

```Java
public interface Comparable<T> {
    int compareTo(T other);
}
```

A class implements `Comparable` and provides the required method:

```Java
public class Product implements Comparable<Product> {
    private final int price;

    public Product(int price) {
        this.price = price;
    }

    @Override
    public int compareTo(Product other) {
        return Integer.compare(this.price, other.price);
    }
}
```

Now a caller can use the capability through the interface:

```Java
Product first = new Product(100);
Product second = new Product(200);

System.out.println(first.compareTo(second)); // Negative number
```

The interface both advertises the capability and defines how to use it.

Conceptually, `Cloneable` was intended to work similarly:

```Java
public class Product implements Cloneable {
    // This class advertises that it permits cloning.
}
```

But here is the problem: `Cloneable` does not declare a `clone()` method.

**The surprising design of `Cloneable`**

The relevant declarations look like this:

```Java
public interface Cloneable {
    // No methods!
}
```

Meanwhile, `clone()` is declared in `Object`:

```Java
protected native Object clone()
        throws CloneNotSupportedException;
```

There are three important details here.

| Detail                              | Meaning                                                                                                                      |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `Cloneable` has no methods          | It declares no operation that callers can invoke.                                                                            |
| `Object.clone()` is `protected`     | Ordinary callers cannot invoke it through an arbitrary object reference.                                                     |
| `Object.clone()` checks `Cloneable` | The default implementation throws `CloneNotSupportedException` if the object's runtime class does not implement `Cloneable`. |

Notice the distinction: implementing `Cloneable` affects whether `Object.clone()` permits cloning, but it does not make `clone()` publicly accessible.

**Why implementing `Cloneable` is not enough?**

Consider this example:

```Java
class Product implements Cloneable {
    private final String name;

    public Product(String name) {
        this.name = name;
    }
}
```

Now try to clone a product:

```Java
public class Main {
    public static void main(String[] args) {
        Product original = new Product("Laptop");

        // Compilation error:
        // clone() has protected access in Object
        Product copy = (Product) original.clone();
    }
}
```

Even though `Product` implements `Cloneable`, this code does not compile. Why? The compiler checks whether `clone()` is accessible at the call site. Since `Product` has not exposed a public `clone()` method, the inherited `protected` method cannot be called this way from an unrelated class.

The class has effectively announced:

> "I permit cloning."

But it has not provided ordinary callers with a public way to request a clone.

Solution: The conventional approach is to override `clone()` explicitly if your class intentionally supports the protocol and make it public.

```Java
class Product implements Cloneable {
    private final String name;

    public Product(String name) {
        this.name = name;
    }

    @Override
    public Product clone() {
        try {
            return (Product) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }

    @Override
    public String toString() {
        return "Product{name='" + name + "'}";
    }
}

public class Main {
    public static void main(String[] args) {
        Product original = new Product("Laptop");
        Product copy = original.clone();

        System.out.println(original);
        System.out.println(copy);

        System.out.println(original == copy); // false
    }
}
```

Three things make this work:

1. `implements Cloneable` tells `Object.clone()` that cloning is permitted.
2. `public Product clone()` exposes cloning to callers.
3. `super.clone()` delegates to the built-in copying mechanism.

The return type `Product` is also an example of a covariant return type: the override returns a more specific type than `Object`, so callers do not need a cast.

For this simple class, the copied `Product` has the same `name` reference. That is safe because `String` is immutable. If the class contained mutable objects, additional copying might be necessary.

---

**Why doesn't Java just put `clone()` in `Cloneable`?**

A better-designed interface might have looked like this:

```Java
interface Cloneable {
    Object clone();
}
```

Then implementing the interface would require the class to provide the method, and callers could invoke it through a `Cloneable` reference.

However, that is not how Java's actual interface works. `Cloneable` is a marker interface: its purpose is to signal a property, rather than declare operations.

Changing the original design would also have compatibility implications for existing Java classes and libraries.

The result is an unusual arrangement:
```
`Cloneable`

Marker interface — no methods
↓
Signals permission to

`Object.clone()`

Protected method — performs the default shallow copy
↓
Must be exposed by an override for ordinary callers

Public `clone()`

The API that callers can invoke
```

---

**Why reflection does not solve the problem reliably**

Reflection can sometimes bypass ordinary access restrictions, but it does not guarantee that cloning will work.

For example:

```Java
Method method = product.getClass().getMethod("clone");
```

`getMethod()` looks for a public method. If `Product` has not exposed a public `clone()`, this lookup will fail.

Using `getDeclaredMethod("clone")` instead searches for a method declared directly by that class, including non-public methods. But it can still fail if the class does not declare such a method, and invoking a non-public method can be restricted by Java's access-control rules and module boundaries.

Reflection therefore does not turn `Cloneable` into a reliable, universal cloning API.

---

The design lesson

The deeper point is that Java separates two responsibilities that a capability interface would normally combine:

| Responsibility                                | Java's cloning mechanism           |
| --------------------------------------------- | ---------------------------------- |
| Advertise permission to clone                 | `Cloneable`                        |
| Perform the default copy                      | `Object.clone()`                   |
| Make cloning accessible to callers            | A public override of `clone()`     |
| Decide whether nested mutable state is copied | The class's cloning implementation |

This separation makes the API awkward. A class can implement `Cloneable` without providing a useful public cloning operation, and a public `clone()` implementation can still produce an incorrect copy if it mishandles mutable fields.

For new Java APIs, a copy constructor or static copy factory is often clearer:

```Java
public class Product {
    private final String name;

    public Product(String name) {
        this.name = name;
    }

    public Product(Product original) {
        this.name = original.name;
    }
}
```

Usage:

```Java
Product original = new Product("Laptop");
Product copy = new Product(original);
```

This approach does not require `Cloneable`, does not depend on `Object.clone()`'s access rules, and makes the copying behavior explicit.

Main takeaway: `Cloneable` is a permission marker, not a cloning API. It indicates that `Object.clone()` may proceed, but it does not guarantee that callers can invoke `clone()` or that the resulting copy will have the desired copying semantics.

### Pitfall 2: Forgetting `Cloneable`

```Java
class Student {
    @Override
    public Student clone() {
        try {
            return (Student) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

This class does not implement `Cloneable`. Calling `super.clone()` therefore throws `CloneNotSupportedException`.

Solution: Either implement `Cloneable` as part of a deliberate cloning contract or use a copy constructor/factory instead.

### Pitfall 3: Accidentally sharing mutable state

```Java
class Team implements Cloneable {
    List<String> members = new ArrayList<>();

    @Override
    public Team clone() {
        try {
            return (Team) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}
```

Now:

```Java
Team original = new Team();
original.members.add("Mona");

Team copy = original.clone();
copy.members.add("Ali");

System.out.println(original.members);
// [Mona, Ali]
```

Both objects refer to the same list.

If independent list structure is required, add:

```Java
copy.members = new ArrayList<>(members);
```

Remember that the list's elements remain shared if they are mutable objects.

### Pitfall 4: Returning `new BaseClass(...)` from a cloning method

Suppose `Shape.clone()` constructs a new `Shape` explicitly. If a `Circle` inherits that method, the result may be a `Shape`, not a `Circle`, violating the expectation that cloning preserves the runtime type.

Solution: Conventional cloning uses `super.clone()` to preserve the runtime class. If you choose copy constructors or factories instead, design them explicitly for the inheritance or polymorphism requirements.

### Pitfall 5: Forgetting subclass fields

Suppose a superclass correctly clones its fields, but a subclass adds a mutable list and inherits the cloning method without copying that list.

The subclass's list reference is still shared.

A subclass override might do this:

```Java
@Override
public ReportDocument clone() {
    ReportDocument copy = (ReportDocument) super.clone();
    copy.sections = new ArrayList<>(sections);
    return copy;
}
```

This assumes the superclass method already follows a safe cloning contract. The subclass must also respect any superclass invariants and exception-handling conventions.

### Pitfall 6: Trying to clone final mutable fields

Consider:

```Java
class Team implements Cloneable {
    private final List<String> members = new ArrayList<>();
}
```

After `super.clone()`, the cloned object's `members` field points to the original list. Because the field is `final`, ordinary Java assignment cannot replace it with a new list inside `clone()`.

This makes a deep-copy implementation difficult with conventional field-by-field cloning.

Solution: Prefer a copy constructor that initializes the final field with a new collection:

```Java
Team(Team source) {
    this.members = new ArrayList<>(source.members);
}
```

This is a particularly strong reason to prefer copy constructors for classes with final references to mutable objects.

### Pitfall 7: Using `clone()` on resources

Copying a reference to a socket or file handle does not create a new socket or open a new file independently.

Both objects may end up referring to the same external resource, which can cause confusing lifecycle and ownership bugs.

Solution: Define explicit resource-specific duplication or sharing behavior. Some resources cannot be duplicated meaningfully at all.

### Pitfall 8: Assuming cloning is thread-safe

Cloning does not automatically make an object thread-safe or guarantee a consistent snapshot when another thread modifies the original during copying.

For example, a mutable collection may change while its reference is copied or while a custom deep copy traverses its contents.

Solution: Use appropriate synchronization, immutable state, or another snapshot strategy when concurrent mutation is possible.

### Pitfall 9: Confusing cloning with serialization

Serialization-based copying can sometimes be used to duplicate an object graph, but it introduces different constraints, overhead, and security considerations.

It is not equivalent to calling `clone()`, and it is rarely the best default solution for ordinary object copying.

### Pitfall 10: Assuming `clone()` invokes constructors

The conventional `Object.clone()` mechanism creates an object without invoking the class's constructors in the normal way used by `new`.

Therefore, do not rely on constructor logic to initialize or validate the copied object. The cloning implementation must preserve the class's invariants itself.

###  Calling Overridable Methods During Cloning
a `clone()` method must not call an overridable method on the object being cloned before that object's state is fully initialized.

The rule is closely related to constructor design and inheritance.

An overridable method is an instance method that a subclass can replace with its own implementation.

For example:

```
class HashTable {
    public void put(String key, String value) {
        // Insert a key-value mapping.
    }
}

class AuditedHashTable extends HashTable {
    @Override
    public void put(String key, String value) {
        System.out.println("Inserting: " + key);
        super.put(key, value);
    }
}
```

Here, `HashTable.put()` is overridable because it is public and not declared `final`.

Suppose the subclass maintains additional state:

```
class AuditedHashTable extends HashTable {
    private List<String> auditLog = new ArrayList<>();

    @Override
    public void put(String key, String value) {
        auditLog.add(key); // Uses subclass-specific state.
        super.put(key, value);
    }
}
```

Imagine the superclass implements `clone()` by rebuilding the hash table through calls to `put()`:

```
@Override
public HashTable clone() {
    try {
        HashTable copy = (HashTable) super.clone();

        copy.resetBuckets();

        for (Entry e : entries()) {
            copy.put(e.key, e.value); // Dangerous if overridable
        }

        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

The problem is that `super.clone()` copies fields, but it does not run constructors or reinitialize the subclass's fields.

Let's follow what happens.

1. `super.clone()` creates the copy

The clone has the runtime class `AuditedHashTable`, but its fields are shallow-copied. Its `auditLog` initially points to the same list as the original.

2. The superclass calls `copy.put()`

Dynamic dispatch selects `AuditedHashTable.put()`, even though the call appears inside `HashTable.clone()`.

3. The subclass method modifies `auditLog`

Because the list is still shared, the insertion may modify the original object's audit log too. The clone can also be corrupted if the subclass's state is not ready for the operation.

The original and clone might end up sharing mutable state or having inconsistent state. The bug can be subtle because the clone may appear correct in simple tests.

---

**Why doesn't `clone()` initialize subclass fields?**

Consider a normal constructor:

```
AuditedHashTable() {
    auditLog = new ArrayList<>();
}
```

A normal construction process initializes the superclass and subclass state according to Java's constructor rules.

But `Object.clone()` does not create the object by invoking its constructors. It creates a field-by-field copy of the existing object.

```
Normal construction
-------------------
Allocate object
    |
    v
Initialize fields and run constructors
    |
    v
Fully constructed object


Cloning
-------
Copy existing object's fields
    |
    v
Shallow clone exists
    |
    v
Superclass clone() continues
    |
    v
Subclass-specific clone repair may not have happened yet
```

Therefore, a superclass cannot assume that subclass-specific mutable state has already been independently copied.

This is why the same rule applies to constructors: do not call overridable methods during construction when subclasses may depend on state that has not yet been initialized.

---

One remmedy to this is making the `put()` operation used during cloning either `final` or `private`:
1. Option A: Make `put()` final

    ```
    public final void put(String key, String value) {
        // Insert a mapping using superclass-controlled logic.
    }
    ```

    A subclass cannot override this method. Calls from `clone()` therefore cannot dispatch to a subclass-specific implementation of `put()`.

    Use this when the operation is intended to be part of the class's public API but must not be overridden.

2. Option B: Use a private helper

    ```
    public void put(String key, String value) {
        putInternal(key, value);
    }

    private void putInternal(String key, String value) {
        // Insert a mapping using superclass-controlled logic.
    }
    ```

    The cloning code calls the private helper:

    ```
    copy.putInternal(e.key, e.value);
    ```

    A private method cannot be overridden. The superclass can therefore use its own implementation without accidentally invoking a subclass's replacement.

    This is often the more flexible design when subclasses should still be allowed to override the public `put()` method for ordinary use.

| Approach                        | Can subclasses override the public operation? | Safe for internal cloning calls?           |
| ------------------------------- | --------------------------------------------- | ------------------------------------------ |
| Public overridable `put()`      | Yes                                           | Potentially dangerous                      |
| Public `final put()`            | No                                            | Yes, for dispatch concerns                 |
| Public `put()` + private helper | Yes                                           | Yes, if `clone()` calls the private helper |

These approaches prevent the specific danger of virtual dispatch. They do not automatically solve every cloning problem; mutable fields and subclass state must still be handled correctly.

---

The key takeaway: `super.clone()` gives you a shallow copy of the entire object, including subclass fields, but it does not give subclasses an opportunity to repair those fields first. If `clone()` invokes an overridable method, that method can run against shared or inconsistent state. Use a `final` method or a private helper when cloning requires an internal operation that must not be overridden.

## `clone()` vs. other copying techniques

Java provides several ways to copy an object. Choosing the right one depends on the desired semantics.

| Technique                   | Main benefit                                               | Main limitation                                                        |
| --------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| `Object.clone()`            | Preserves runtime class; starts with a field-by-field copy | Requires `Cloneable`; shallow by default; inheritance can be difficult |
| Copy constructor            | Explicit, easy-to-understand copying policy                | Must be implemented for each desired type                              |
| Static factory (`copyOf`)   | Expressive API; can reuse immutable instances              | Requires a defined factory contract                                    |
| Manual field copying        | Full control over copied fields                            | Verbose; must be maintained as the class evolves                       |
| Serialization-based copying | Can copy serializable object graphs                        | More overhead, restrictions, and complexity                            |
| Immutable objects           | Often eliminate the need for copying                       | Requires immutable design                                              |

## Recommended approach for modern Java

For a new class, prefer a copy constructor or a static factory unless there is a specific reason to support the `Cloneable` protocol.

For example:

```Java
public final class ServerConfig {
    private final String host;
    private final int port;
    private final List<String> allowedOrigins;

    public ServerConfig(
            String host,
            int port,
            List<String> allowedOrigins) {
        this.host = host;
        this.port = port;
        this.allowedOrigins = new ArrayList<>(allowedOrigins);
    }

    public ServerConfig(ServerConfig source) {
        this(
            source.host,
            source.port,
            source.allowedOrigins
        );
    }
}
```

The constructor creates a new list, so the copied configuration does not share its collection structure with the original.

Because `String` is immutable, sharing the strings inside the list is safe. If the list held mutable objects, additional copying might be necessary.

The example is intentionally a partial implementation: in a production class, you would also validate constructor arguments and decide whether to expose the collection through a defensive, unmodifiable view.

## Testing a cloning implementation

A good cloning test should verify more than whether the returned object is non-null.

For the `Student` and `Address` example, test these properties:

```Java
Student original = new Student(
    101, "Mona", new Address("Cairo")
);

Student copy = original.clone();

// 1. Different outer object
assert original != copy;

// 2. Same initial values
assert original.id == copy.id;
assert original.name.equals(copy.name);

// 3. Independent mutable state, if required
assert original.address != copy.address;

// 4. Changes to the copy do not affect the original
copy.address.city = "Alexandria";
assert original.address.city.equals("Cairo");
```

These checks assume the deep-copy implementation shown earlier.

For a hash table, test that:

1. The clone initially contains the same mappings.
2. Adding or removing an entry in the clone does not change the original.
3. Mutating a value in the clone does not affect the original if independent values are promised.
4. Shared references and cycles are preserved when required by the copy contract.
5. The cloned object remains valid after its internal state changes.

The third test is especially important: independent bucket arrays and entry nodes do not guarantee independent mutable values.


A complete test suite should also consider:

- Null reference fields.
- Empty collections.
- Subclass instances.
- Nested mutable objects.
- Cyclic object graphs, if supported.
- Equality and hash-code behavior after copying.
- Concurrent access, if the class is used by multiple threads.

## Summary the main rules for implementing `clone()
The key idea is that `super.clone()` creates the initial copy, but your class is responsible for making that copy valid, independent where necessary, and consistent with its design.
### 1. Override `clone()` as a public method with the class's own return type

all classes that implement Cloneable should override clone with a
public method whose return type is the class itself.

`Object.clone()` is `protected` and returns `Object`. If your class supports cloning, expose it through a public method and use a covariant return type.

There is no need to cast the result or handle `CloneNotSupportedException`.

The method is public because the class promises to support cloning. The return type `Point` makes that promise easier to use.

### 2. Call `super.clone()` first

The standard implementation of `Object.clone()` creates a shallow, field-by-field copy of the object while preserving its runtime class.

Primitive values are copied. References are copied as references, so both objects point to the same array.

This is why calling `super.clone()` is only the starting point.

### 3. Fix fields that require independent state

After `super.clone()`, examine the fields and decide whether sharing each referenced object is acceptable.

Typically, this means copying
any mutable objects that comprise the internal “deep structure” of the object and
replacing the clone’s references to these objects with references to their copies.

While these internal copies can usually be made by calling clone recursively, this
is not always the best approach.

When a field refers to another mutable object, you might call that object's `clone()` method to create an independent copy.

For example:

```
copy.address = address.clone();
```

This only works if `address` supports cloning and its own `clone()` correctly handles its mutable fields.

Recursive cloning is not always ideal because:

- The referenced class might not implement `Cloneable`.
- Its `clone()` method might not be accessible.
- It might perform only a shallow copy.
- The object graph might contain cycles or shared references that require special handling.
- Copy constructors or static copy factories may express the intended copy behavior more clearly.

For example, a general object graph with cycles often needs an identity map to ensure each original object maps to exactly one copied object.

Guideline: Use recursive cloning when the referenced types support it and their copy contracts are correct. Otherwise, use an appropriate copy constructor, factory, or explicit copying algorithm.

If a class contains only primitive fields and references to immutable objects then it is likely the case that no fields need to be fixed, a shallow copy is often sufficient.

However, consider whether cloning an immutable class is useful at all. Since immutable objects cannot be modified, sharing the original object or providing a copy factory may be simpler than allocating another instance.

There are exceptions to this rule. For example, a field representing a serial number
or other unique ID will need to be fixed even if it is primitive or immutable

The same principle applies to immutable references. An immutable UUID is safe to share as an object, but if it represents an entity's unique identity, the cloned entity may need a newly generated UUID.

The distinction is between technical mutability and semantic meaning. A field does not need to be mutable to require a different value in the clone.

Use this checklist when implementing or reviewing a class that supports cloning.

    The marker interface enables the conventional cloning mechanism.

- Override clone() with appropriate accessibility

    A public override is convenient for clients.

- Use a covariant return type

## Alternatives to `clone()`
unless you are forced to support `clone()`, prefer a copy constructor or a copy factory. They provide a simpler, safer, and more flexible way to create copies of objects.

THis does not mean that `clone()` can never work. The point is that its complexity and historical design problems often outweigh its benefits.

### Why is `clone()` so complicated?

Recall the typical implementation:

```Java
@Override
public MyClass clone() {
    try {
        MyClass copy = (MyClass) super.clone();

        // Repair mutable fields if necessary.
        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

Even this simple method has several concerns:

- The class must implement `Cloneable`.
- You must call `super.clone()` to get the expected field-by-field copy.
- You must handle `CloneNotSupportedException`, even when you expect it never to happen.
- You must determine whether mutable fields need deep copying.
- You must be careful about inheritance, object invariants, and thread safety.
- You must consider whether copying a field is appropriate at all, such as when it contains a unique ID.

A copy constructor can express the same intention much more directly.

Java provides two common alternatives to the `Cloneable` / `clone()` mechanism:

1. Copy constructors — create a new object by passing an existing object to a constructor.
2. Static copy factories — create a new object by calling a static method that accepts an existing object.

Both let you control how the copy is created using ordinary Java code, without relying on `Object.clone()`.

### Copy constructors

A copy constructor is a constructor that takes an object of the same class, or sometimes a compatible interface or type, and uses it to initialize a new instance.

#### Basic example

```Java
public class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    // Copy constructor
    public Point(Point original) {
        this.x = original.x;
        this.y = original.y;
    }

    public void print() {
        System.out.println("(" + x + ", " + y + ")");
    }

    public static void main(String[] args) {
        Point original = new Point(10, 20);
        Point copy = new Point(original);

        original.print(); // (10, 20)
        copy.print();     // (10, 20)

        System.out.println(original == copy); // false
    }
}
```

Although both objects contain the same coordinates, they are distinct objects in memory.

```
original ──> Point { x = 10, y = 20 }

copy     ──> Point { x = 10, y = 20 }
```

The constructor initializes the new object directly. It does not call `super.clone()`, implement `Cloneable`, or handle `CloneNotSupportedException`.

Important: A copy constructor does not automatically guarantee a deep copy. You decide which fields to copy, which mutable objects to duplicate, and which references may safely be shared. Here, `String` is immutable, so sharing `name` is fine.

#### Copying Mutable Fields

Copying primitive fields and immutable objects is relatively straightforward. The more important design decision is what to do with mutable objects.

Consider a class containing a list:

```Java
import java.util.ArrayList;
import java.util.List;

public class Student {
    private final String name;
    private final List<Integer> grades;

    public Student(String name, List<Integer> grades) {
        this.name = name;
        this.grades = new ArrayList<>(grades);
    }

    public Student(Student original) {
        this.name = original.name;
        this.grades = new ArrayList<>(original.grades);
    }

    public void addGrade(int grade) {
        grades.add(grade);
    }

    public List<Integer> getGrades() {
        return new ArrayList<>(grades);
    }

    public static void main(String[] args) {
        Student original =
                new Student("Ali", List.of(80, 90));

        Student copy = new Student(original);

        copy.addGrade(100);

        System.out.println(original.getGrades()); // [80, 90]
        System.out.println(copy.getGrades());     // [80, 90, 100]
    }
}
```

The key line is:

```Java
this.grades = new ArrayList<>(original.grades);
```

It creates a separate list for the copied student.

```
original ──> Student ──> grades ──> [80, 90]

copy     ──> Student ──> grades ──> [80, 90, 100]
```

The `String` reference can be shared because strings are immutable. The list is copied because it is mutable.

Important: This example copies the list structure, not arbitrary mutable objects inside it. If the list contained mutable objects, those elements would still be shared unless the constructor copied them too.

#### Copying final Fields
Consider:

```
private final List<Integer> grades;
```

After `super.clone()`, the copied object initially refers to the same list as the original. A proper independent copy would need to replace that reference with a new list.

But because `grades` is `final`, ordinary Java code cannot reassign it in the clone method.

A copy constructor can initialize it correctly from the start:

```
public Student(Student original) {
    this.grades = new ArrayList<>(original.grades);
}
```

This is a major design advantage: you can maintain immutability and establish the object's state through normal construction.

#### Conversion Constructors
Furthermore, a copy constructor or factory can take an argument whose type
is an interface implemented by the class. For example, by convention all general-
purpose collection implementations provide a constructor whose argument is of
type Collection or Map. Interface-based copy constructors and factories, more
properly known as conversion constructors and conversion factories, allow the
client to choose the implementation type of the copy rather than forcing the client
to accept the implementation type of the original.


A conventional copy constructor often accepts the same class:

```
public Yum(Yum original) { ... }
```

But a constructor can instead accept an interface implemented by the source object. That lets the caller choose the implementation of the copy.

Consider Java's collection interfaces.

Example: `HashSet` to `TreeSet`

A `HashSet` does not maintain sorted iteration order. A `TreeSet` maintains its elements in sorted order.

```
import java.util.HashSet;
import java.util.Set;
import java.util.TreeSet;

public class SetCopyDemo {
    public static void main(String[] args) {
        Set<Integer> original =
                new HashSet<>(Set.of(30, 10, 20));

        // Conversion constructor
        TreeSet<Integer> sortedCopy =
                new TreeSet<>(original);

        System.out.println(original);
        System.out.println(sortedCopy); // [10, 20, 30]
    }
}
```

What happened?

`HashSet<Integer>`

Source collection

Pass it as a `Set<Integer>`

`new TreeSet<>(original)`

New collection with sorted ordering

The constructor accepts a `Set` (or more generally, a suitable collection interface) rather than requiring a `HashSet`. It can therefore consume different set implementations.

This gives the caller control over the desired result:

```
Set<Integer> original = new HashSet<>();

Set<Integer> hashCopy = new HashSet<>(original);
Set<Integer> sortedCopy = new TreeSet<>(original);
```

Both copies are sets, but they use different implementations and have different ordering behavior.

The `TreeSet` constructor is a conversion constructor because it can convert a source collection into a different concrete implementation. A static factory that does the same is called a conversion factory.

Note that this example copies the collection structure, not necessarily the objects inside it. If the elements are mutable, both collections may still reference the same element objects.

#### Advantages of copy constructors

- Explicit initialization: You decide exactly how every field is initialized.
- Works naturally with `final` fields: Fields can be assigned during construction.
- No checked cloning exception: No `CloneNotSupportedException`.
- No casts: You get an object of the expected type.
- Supports deep copying: You can copy mutable objects according to your class's requirements.
- Supports conversion: A constructor can accept an interface and create a different implementation.

**A conversion constructor**

For example, Java's `TreeSet` can be constructed from another collection:

```Java
Set<Integer> original =
        new HashSet<>(List.of(30, 10, 20));

TreeSet<Integer> sortedCopy = new TreeSet<>(original);

System.out.println(sortedCopy); // [10, 20, 30]
```

This is more flexible than `clone()`: the original implementation is a `HashSet`, but the new object is a `TreeSet`.

#### Limitations of copy constructors

Copy constructors are not perfect:

- A constructor taking `MyClass` does not automatically copy subclasses' additional fields.
- You must explicitly decide how mutable fields are copied.
- A constructor cannot be overridden like an instance method, so it does not provide runtime-polymorphic copying by itself.
- A copy constructor can only use the source object's accessible state. For unrelated classes, this may require public accessors or another supported copying API.

These limitations become especially relevant when designing class hierarchies and libraries.

### Static copy factories

A static copy factory is a static method that creates and returns a new object based on an existing object.

For example:

```Java
public class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    // Static copy factory
    public static Point copyOf(Point original) {
        return new Point(original.x, original.y);
    }

    public static void main(String[] args) {
        Point original = new Point(10, 20);
        Point copy = Point.copyOf(original);

        System.out.println(original == copy); // false
    }
}
```

Usage:

```Java
Point copy = Point.copyOf(original);
```

The factory creates a new object and returns it. It can use a copy constructor internally, but it doesn't have to.

```
                    copyOf(original)
                           |
                           v
                   Create a new Point
                           |
                           v
                       Return copy
```

#### Why use a factory instead of a constructor?

The main advantage is control over object creation.

A static factory can:

- Have a descriptive name such as `copyOf()`, `from()`, or `deepCopyOf()`.
- Choose which implementation to return.
- Validate the input before copying.
- Return a cached instance when sharing an existing object is appropriate.
- Select between shallow and deep copying strategies.
- Accept an interface rather than a concrete class.

For example, suppose a class has multiple copying options:

```Java
public class Document {
    // Document fields and constructors omitted

    public static Document copyOf(Document original) {
        // Create an independent copy.
        return new Document(original);
    }

    public static Document deepCopyOf(Document original) {
        // Create a copy including independently copied
        // mutable objects contained in the document.
        return new Document(original, true);
    }

    private Document(Document original) {
        // Copy ordinary state.
    }

    private Document(Document original, boolean deepCopy) {
        // Copy state according to the selected strategy.
    }
}
```

Here, the constructors are illustrative placeholders for the document's actual copying logic. The important point is that factory names communicate the intended operation more clearly than a generic `clone()` call.

#### Static factories and interfaces

A static factory can also accept an interface to make conversion easier:

```Java
import java.util.Collection;
import java.util.List;
import java.util.ArrayList;

public class Names {
    public static List<String> copyOf(
            Collection<String> source) {
        return new ArrayList<>(source);
    }
}
```

Usage:

```Java
Collection<String> source = List.of("Ali", "Mona");

List<String> copy = Names.copyOf(source);
```

The factory accepts any compatible `Collection<String>`, not just one specific collection implementation.

In this example, it returns an `ArrayList`. A different factory could return another implementation depending on the desired behavior.

One nuance: the method is named `copyOf`, but the return type and copying behavior are decisions made by the API designer. A factory can return an existing immutable object when sharing is safe, so its name and documentation should make the contract clear.

#### Conversion Factories

#### Limitations of static copy factories

- They require an explicit method call rather than `new`.
- A factory's name and documentation must make its copying behavior clear.
- Like copy constructors, they need an intentional strategy for mutable fields and subclass state.
- A static method cannot be overridden polymorphically. A class can hide a static method, but that is not the same as overriding an instance method.

### Why copy constructors and factories are better

| Concern                       | `clone()`                                            | Copy constructor / factory                                |
| ----------------------------- | ---------------------------------------------------- | --------------------------------------------------------- |
| Object creation               | Relies on the special `Object.clone()` mechanism     | Uses ordinary Java construction                           |
| `Cloneable`                   | Required for the standard cloning mechanism          | Not required                                              |
| Checked exception             | `CloneNotSupportedException` may need handling       | No cloning-related checked exception                      |
| Type casting                  | Often needed when calling `super.clone()`            | Usually unnecessary                                       |
| `final` fields                | Difficult to replace copied references after cloning | Can be initialized normally                               |
| Mutable fields                | Must be carefully repaired after shallow copying     | Copying strategy is explicit                              |
| Naming and behavior           | Constrained by the `clone()` convention              | Can use meaningful names and custom behavior              |
| Different implementation type | Does not naturally support this                      | Can accept an interface and return another implementation |

### Copy constructor vs. static copy factory
Both approaches create a new object from an existing one, but they use different syntax.

Copy constructor

A constructor receives another object of the same class and initializes the new instance from it.

```
public Yum(Yum original) {
    // Copy the relevant state.
}
```

Usage:

```
Yum copy = new Yum(original);
```

Copy factory

A static method receives the original object and returns a newly created copy.

```
public static Yum newInstance(Yum original) {
    return new Yum(original);
}
```

Usage:

```
Yum copy = Yum.newInstance(original);
```

The factory can have a more descriptive name, select a particular implementation, or apply additional creation logic. A constructor is often the most straightforward option when the copying behavior is simple.

| Feature                      | Copy constructor                      | Static copy factory                                |
| ---------------------------- | ------------------------------------- | -------------------------------------------------- |
| Example                      | `new Point(original)`                 | `Point.copyOf(original)`                           |
| Creation mechanism           | Constructor                           | Static method                                      |
| Naming flexibility           | No; name must match the class         | Yes                                                |
| Return type                  | Always the class being constructed    | Can return an interface or another compatible type |
| Implementation choice        | Fixed by the constructor being called | Can choose an implementation at runtime            |
| Validation and custom logic  | Yes                                   | Yes                                                |
| Supports deep copying        | Yes                                   | Yes                                                |
| Supports `final` fields      | Yes                                   | Yes, through construction                          |
| Can return a cached instance | No; creates a new instance            | Yes, when appropriate                              |
| Requires `Cloneable`         | No                                    | No                                                 |

### Which one should you choose?

**Choose a copy constructor**

Use a copy constructor by default

When you want a straightforward, explicit copy of an object and can define how its fields should be initialized.

Use it when the purpose is straightforward: initialize a new instance from an existing one.

```
User copy = new User(original);
```

**Choose a static copy factory**

Use it when a meaningful method name, implementation selection, validation, or a specialized copying policy improves the API.

Use a copy factory when creation needs flexibility

For example, when a named operation is clearer, a specific implementation must be selected, or the factory needs to apply additional rules.

```
User copy = User.copyOf(original);
```

Implement `clone()` when compatibility or inheritance requires it

Choose `clone()` only when justified

You may need it to maintain compatibility with an existing API or to extend a class whose contract already supports cloning.

If you extend a class that already supports cloning, you may need to preserve that contract. Carefully implement the clone method and handle mutable state.

One subtlety: if a class is designed for inheritance, a copy constructor taking only its own type does not automatically copy arbitrary subclass state. Copying an unknown subtype needs an explicit design. This is another reason to think carefully about the API rather than assuming one copying mechanism fits every class.

## Key takeaways

- Importance: Cloning provides a way to duplicate an existing object's state while preserving its runtime class.
- Benefits of overriding: You can expose a convenient public API, return a specific type, and define how mutable fields are copied.
- Common usage: Legacy APIs, array duplication, configured prototypes, and classes that deliberately support cloning.
- Design guidelines: Prefer copy constructors or static factories for new APIs, document copying semantics, and handle mutable fields explicitly.
- Common pitfalls: Forgetting `Cloneable`, assuming a shallow copy is deep, mishandling subclasses or final mutable fields, and copying resources incorrectly.

The most important principle is this: creating a new object is not the same as creating an independent copy of its state. A sound copying design must make that distinction explicit.

Given all the problems associated with Cloneable, new interfaces should not
extend it, and new extendable classes should not implement it. While it’s less
harmful for final classes to implement Cloneable, this should be viewed as a performance optimization, reserved for the rare cases where it is justified.
As a rule, copy functionality is best provided by constructors or factories. A nota-
ble exception to this rule is arrays, which are best copied with the clone method.
