{/* # Java Virtual Machine (JVM): Overview */}
Since the first release of Java in the 1990s, the JVM has been the true success factor for the Java
programming language. With Java and the JVM, the concept of “write once, run anywhere” was born.
Java developers can write their programs once and allow the JVM to ensure the code runs on devices
the JVM is installed on. The JVM also makes Java a platform-independent language. 

The Java Virtual Machine (JVM) is the runtime environment responsible for executing Java bytecode. It loads compiled classes, manages memory, executes instructions, handles garbage collection, and provides services that help Java applications run across different operating systems and hardware platforms.

At the core, the JVM sits between your Java bytecode and your computer. As illustrated next, we develop
our Java source code in an IDE, and our work is saved as .java files. We use the Java compiler to
convert our Java source code to bytecode; the resulting files are .class files. We then use the JVM
to run our bytecode on our computer:
```
                               </>
                        Java source code
                         HelloWorld.java
                               ↓
                     Java compiler (`javac`)
                               ↓
                         Java bytecode
                        HelloWorld.class
                               ↓                         
                Executed by a platform-specific JVM
                               ↓ 
                            Computer
```
It is important to realize that Java is different from typical compile-and-execute languages where
source code is fed into a compiler, which then produces a .exe file (for Windows), a .app file (for
(macOS), or ELF files (for Linux). This impressive process is much more complex than it seems.

The most important idea to understand is this:

Java source code is compiled into bytecode, and the JVM executes that bytecode on the target platform.

## What problem does the JVM solve?

Without the JVM, developers would generally need to compile programs separately for different operating systems and processor architectures.

Java takes a different approach.
```
                               </>
                        Java source code
                         HelloWorld.java
                               ↓
                     Java compiler (`javac`)
                               ↓
                         Java bytecode
                        HelloWorld.class
                               ↓                         
                Executed by a platform-specific JVM
   ---------------      ---------------     ---------------
   |   Windows   |      |    Linux    |     |     macOS   |
   | Windows JVM |      |  Linux JVM  |     |  macOS JVM  |
   --------------       ---------------     ---------------
```
The same `.class` bytecode can generally run on different platforms, provided compatible JVM implementations are available and the application does not depend on platform-specific features.

This is the foundation of Java's write once, run anywhere principle.

## Example
Let’s take a closer look at what is going on with regard to the JVM, using a basic example. In the
following code, we implement a simple loop that prints to the console. It is presented so that we can
see how the JVM handles Java code:
```Java
// Chapter1
// Example 1
public class CH1EX1 {
    public static void main(String[] args) {

        System.out.println("Basic Java loop.");

        // Basic loop example
        for (int i = 1; i <= 5; i++) {
            System.out.println("1 x " + i + " = " + i);
        }
    }
}
```
We can use the Java compiler to compile our code into a .class file, which will be formatted as
bytecode. Let’s open a terminal window, navigate to our project’s src folder as shown next, and use
the ls command to reveal our .java file:
```
$ cd src
$ ls
CH1EX1.java
```
Now that we are in the proper folder, we can use javac to convert our source code to bytecode. As
you can see next, this created a .class file:
```
$ javac CH1EX1.java
$ ls
CH1EX1.class CH1EX1.java
$
```
Next, we can use the Java Printer tool (javap) to print a decompiled version of our bytecode. As
you can see next, we can use the javap command without any parameters:
```
javap CH1EX1.class
Compiled from "CH1EX1.java"

public CH1EX1();
public static void main(java.lang.String[]);
}
```
As you can see, our use of the javap command simplified the printing of the decompiled bytecode.
Now, let’s use the -c parameter to reveal the bytecode:
```
$ javap -c CH1EX1.class
```

## JVM vs. JRE vs. JDK

These three terms describe different parts of the Java ecosystem.

| Component | Purpose                                           | Examples                                                    |
| --------- | ------------------------------------------------- | ----------------------------------------------------------- |
| JVM       | Executes Java bytecode                            | Class loading, execution, garbage collection                |
| JRE       | Runtime environment for running Java applications | JVM plus runtime libraries and supporting files             |
| JDK       | Development kit for building Java applications    | Runtime components plus tools such as `javac` and `javadoc` |

Conceptually:

```
JDK
├── Development tools
│   ├── javac
│   ├── javadoc
│   └── jdb
└── Runtime components
    ├── JVM
    └── Java libraries
```

Modern Java distributions may package these components differently, and a separate JRE installation is not necessarily provided.

For example:

```
javac HelloWorld.java  # Compile source code
java HelloWorld        # Launch the application
```

The first command uses a JDK tool. The second launches the Java runtime, which uses the JVM to execute the program.

## The main components of the JVM

A useful way to understand the JVM is to divide it into five major areas.

- The Class Loader Subsystem loads classes into the JVM.
- The Runtime Data Areas provide memory and execution state for the application. Some areas are shared across threads; others are per-thread.
- The Execution Engine executes bytecode, compiles frequently executed code, and coordinates garbage collection.
- JNI and native libraries allow Java applications to interact with native code. They are not simply the next sequential execution stage after the execution engine; the arrows above illustrate a conceptual relationship, not a literal execution pipeline.

These are conceptual relationships, not a strict diagram of every implementation detail. For example, garbage collection operates on managed memory, and native code can be invoked through JNI.

### 1. Class Loader Subsystem

The class loader subsystem brings class definitions into the JVM.

It performs three major phases:

1. Loading: Finds the binary representation of a class and creates its runtime representation.
2. Linking: Verifies the bytecode, prepares static storage, and resolves symbolic references as needed.
3. Initialization: Executes class initialization code, including static field initializers and static initialization blocks.

For example:

```
class Configuration {
    static int timeout = 30;

    static {
        System.out.println("Configuration initialized");
    }
}
```

When `Configuration` is initialized, its static initialization code runs according to Java's class initialization rules.

Java also uses different class loaders, including the bootstrap, platform, and application class loaders in standard modern Java implementations. Custom class loaders can load classes from additional sources.

Why it matters: Class loading affects application startup, plugin systems, dependency isolation, application servers, and frameworks such as Spring.

### 2. Runtime Data Areas

The JVM uses several memory areas to support program execution.

| Memory area         | Shared or per-thread?            | Main responsibility                                                    |
| ------------------- | -------------------------------- | ---------------------------------------------------------------------- |
| Heap                | Shared                           | Stores objects and arrays                                              |
| Method area         | Shared                           | Stores class-level structures and runtime metadata                     |
| Java stack          | Per-thread                       | Holds method frames, local variables, and intermediate execution state |
| PC register         | Per-thread                       | Tracks the current bytecode instruction for the executing thread       |
| Native method stack | Typically per-thread, where used | Supports native method execution                                       |

The method area is an abstract JVM specification concept. In HotSpot, much class metadata is stored in native memory through a mechanism called Metaspace.

#### Example: Objects and references

```
class Person {
    String name;

    Person(String name) {
        this.name = name;
    }
}

public class Main {
    public static void main(String[] args) {
        Person person = new Person("Alice");
        System.out.println(person.name);
    }
}
```

Conceptually, the memory relationships look like this:

```
Java Stack (main thread)       Heap
┌─────────────────────┐       ┌─────────────────────┐
│ person ─────────────────────>│ Person object      │
│                     │       │ name ──────────────────┐
└─────────────────────┘       └─────────────────────┘  │
                                                       v
                                              ┌─────────────────┐
                                              │ String "Alice"  │
                                              └─────────────────┘
```

This is a simplified illustration. The JVM does not guarantee that every object will always occupy a separate physical heap allocation; optimizations may change how objects are represented or allocated.

The key distinction is that `person` is a local reference variable, while the `Person` instance is an object. The reference is not itself the object.

### 3. Execution Engine

The execution engine runs the program's bytecode.

It has three important responsibilities.

1. Interpreter

    Executes bytecode instructions. Interpretation allows code to begin running without first compiling every method into native machine code.

2. Just-in-Time (JIT) compiler

    Compiles frequently executed code into native machine code, often applying optimizations based on runtime observations.

    For example, a method that runs millions of times in a loop may be compiled and optimized after the JVM identifies it as hot code.

3. Garbage collector (GC)

    Reclaims memory occupied by objects that are no longer reachable through the relevant garbage-collection roots.

    Garbage collection reduces the need for developers to explicitly free ordinary Java heap objects, but it does not eliminate every memory-management responsibility. Applications can still suffer from memory leaks when unnecessary references keep objects reachable.

### 4. Java Native Interface (JNI)

JNI allows Java code to interact with native code, commonly written in C or C++.

Typical uses include:

- Integrating with an existing native library.
- Accessing operating-system or hardware functionality unavailable through standard Java APIs.
- Implementing performance-sensitive functionality when native code is appropriate.

JNI introduces additional complexity, including native memory management, platform dependence, and potential process crashes caused by native-code errors.

### 5. Native libraries

Native libraries contain platform-specific machine code. The JVM can use them when Java applications call native functionality.

Unlike ordinary Java bytecode, native libraries generally need to match the target operating system and processor architecture.

## How the JVM executes a Java program

Consider this example:

```
public class Main {
    public static void main(String[] args) {
        int a = 10;
        int b = 20;

        int result = a + b;

        System.out.println(result);
    }
}
```

### Step 1: Compilation

Run:

```
javac Main.java
```

The compiler produces `Main.class`, which contains JVM bytecode.

You can inspect it using:

```
javap -c Main
```

The output includes bytecode instructions for loading values, adding them, and invoking `println`. Exact instructions depend on the compiled class and Java compiler version.

### Step 2: Class loading

Run:

```
java Main
```

The JVM locates and loads the required class definitions, including `Main` and classes needed by the program.

### Step 3: Verification and linking

The JVM verifies bytecode and prepares class structures. It also resolves symbolic references according to JVM linking rules.

This helps ensure that bytecode follows the structural and type-safety rules expected by the virtual machine, though it is not a substitute for application security.

### Step 4: Class initialization

The JVM initializes classes when required by Java's initialization rules. The `main` method is then invoked for the application entry point.

### Step 5: Execution

The execution engine interprets bytecode and may compile frequently executed code into native machine code.

In this example, the result is `30`.

### Step 6: Memory management

During execution, the JVM manages memory used by objects and other runtime structures. Objects that become unreachable may eventually be reclaimed by garbage collection.

## Interpreter vs. JIT compiler

| Feature            | Interpreter                                          | JIT compiler                                   |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------- |
| How it works       | Executes bytecode instructions                       | Compiles bytecode into native machine code     |
| Startup            | Can begin executing code quickly                     | Compilation adds overhead                      |
| Repeated execution | May incur interpretation overhead                    | Optimized code can execute more efficiently    |
| Runtime adaptation | Limited compared with compilation-based optimization | Can optimize using observed execution behavior |

Modern JVMs commonly use a combination of interpretation and compilation rather than choosing only one.

HotSpot, for example, supports tiered compilation, where code can move through different execution and compilation levels as the JVM gathers information about its behavior.

Important: JIT compilation is not guaranteed to make every Java program faster. Short-lived programs may finish before compilation benefits outweigh their costs.

## JVM memory management and garbage collection

Garbage collection is one of the JVM's most important services.

Consider:

```
public class Main {
    public static void main(String[] args) {
        Person person = new Person("Alice");

        person = null;
    }
}

class Person {
    String name;

    Person(String name) {
        this.name = name;
    }
}
```

After `person = null`, the local variable no longer refers to the `Person` instance. If no other reachable reference points to that instance, it becomes eligible for garbage collection.

```
Before:
person ──────> Person object

After:
person ──────> null

Person object:
No reachable references
        |
        v
Eligible for garbage collection
```

Eligibility does not mean immediate collection. The JVM decides when and how to reclaim the memory.

### Important JVM memory topics

- Heap sizing: `-Xms` sets the initial heap size and `-Xmx` sets the maximum heap size.
- Garbage-collection algorithms: Different collectors make different trade-offs involving throughput, pause times, and memory usage.
- Stack overflow: Excessive method recursion can exhaust a thread's stack.
- Out of memory: Heap, Metaspace, or other memory exhaustion can produce different errors.
- Memory leaks: Objects that are no longer useful but remain reachable may continue consuming memory.

For example:

```
java -Xms256m -Xmx1g Main
```

This configures an initial heap size of 256 MB and a maximum heap size of 1 GB, subject to the JVM implementation and environment.

## JVM, operating system, and CPU

The JVM is a process running on the operating system, not a replacement for the operating system.

```
Java Application
       |
       v
Java Libraries
       |
       v
JVM Runtime
  ├── Bytecode execution
  ├── JIT compilation
  ├── Memory management
  └── Thread coordination
       |
       v
Operating System
  ├── Processes and threads
  ├── Virtual memory
  ├── Files and networking
  └── System calls
       |
       v
CPU and Physical Memory
```

The JVM uses operating-system facilities for tasks such as creating and scheduling threads, allocating native memory, and performing file or network operations.

When the JIT compiler produces native machine code, the CPU executes that code directly. The JVM continues to provide runtime services around that execution.

This relationship is particularly useful to understand when studying Linux, Java performance, concurrency, and backend application deployment.

## JVM options and diagnostic tools

Java developers can inspect and configure JVM behavior using command-line options and diagnostic utilities.

| Tool or option   | Purpose                                                   |
| ---------------- | --------------------------------------------------------- |
| `java -version`  | Displays the Java runtime version                         |
| `javac -version` | Displays the Java compiler version                        |
| `javap -c Main`  | Disassembles class bytecode                               |
| `jcmd`           | Sends diagnostic commands to a running JVM                |
| `jstack`         | Captures thread stack traces                              |
| `jmap`           | Provides heap-related inspection and dump capabilities    |
| `jstat`          | Reports selected JVM performance statistics               |
| `-Xms`, `-Xmx`   | Configure heap sizing                                     |
| `-Xlog:gc`       | Enables garbage-collection logging on modern HotSpot JVMs |

Some diagnostic tools and options vary across Java versions and implementations. In production environments, permissions, container limits, and diagnostic overhead also matter.

## JVM implementations

The JVM is a specification, not a single product.

Common implementations include:

- Eclipse Temurin — a widely used OpenJDK distribution.
- Oracle JDK — Oracle's Java development kit.
- OpenJDK — the open-source Java development kit project and its implementations.

HotSpot is a prominent JVM implementation used by many OpenJDK-based distributions. Other JVM implementations exist, with different performance characteristics, deployment targets, and capabilities.

The JVM specification defines expected behavior; a particular implementation determines many internal details, such as JIT compilation strategies and garbage-collection algorithms.

## 10. Recommended JVM study roadmap

Given your Java backend focus, I would study the JVM in the following order.

1\. JVM fundamentals

JVM vs. JRE vs. JDK, bytecode, class files, JVM specification, HotSpot.

Start here

2\. Class loading and linking

Class loaders, delegation, verification, initialization, classpath and module path.

3\. JVM memory model and runtime areas

Heap, stacks, Metaspace, object allocation, references, escape analysis, Java Memory Model.

4\. Execution engine and JIT

Interpretation, tiered compilation, inlining, deoptimization, profiling and warm-up.

5\. Garbage collection

GC roots, object reachability, generational collection, G1, ZGC, pause times and heap tuning.

6\. Threads and concurrency

Platform threads, virtual threads, synchronization, visibility, happens-before and thread dumps.

7\. JVM performance and production diagnostics

JFR, JDK Mission Control, async-profiler, heap dumps, allocation profiling and container-aware tuning.

For backend development, prioritize memory management, garbage collection, class loading, JIT compilation, concurrency, and production diagnostics. These topics help explain slow application startup, high CPU usage, long GC pauses, memory leaks, and performance differences between development and production.

The central takeaway: The JVM is both a bytecode execution environment and a sophisticated runtime system. Understanding how it loads classes, manages memory, executes code, and coordinates threads makes it much easier to build and troubleshoot reliable Java applications.
