In a **Distributed Systems** context, a **Reactive System** is an architectural approach for building systems that remain:

* **Responsive**
* **Resilient**
* **Elastic**
* **Message-Driven**

even under:

* failures,
* high load,
* network latency,
* partial outages,
* and changing traffic patterns.

The idea comes from the Reactive Manifesto.

**Mental Model**

Think of reactive systems as:

```text
Distributed Systems
    +
Asynchronous Messaging
    +
Failure Isolation
    +
Elastic Scaling
    +
Non-Blocking Processing
    +
Event-Driven Communication
```

## Why Reactive Systems Exist

Traditional distributed systems often fail because:

* threads block waiting for I/O,
* services tightly depend on each other,
* one slow service causes cascading failures,
* systems cannot scale dynamically,
* failures spread through the system.

Reactive systems solve this by designing the system around:

* asynchronous communication,
* isolation,
* event-driven interactions,
* non-blocking processing,
* and failure containment.

## Core Characteristics of Reactive Systems

The Reactive Manifesto defines 4 core properties.

### 1. Responsive

The system should respond quickly and consistently.

Even during:

* load spikes,
* failures,
* slow downstream services.

Example:

* API still returns quickly even when one microservice is slow.

Techniques:

* caching,
* async processing,
* load balancing,
* backpressure,
* circuit breakers.

---

### 2. Resilient

The system remains functional despite failures.

In distributed systems:

* failures are normal,
* machines crash,
* networks partition,
* containers restart.

Reactive systems assume failure WILL happen.

Techniques:

* supervision,
* retries,
* replication,
* isolation,
* bulkheads,
* self-healing.

Example:

* One failed node does not crash the whole cluster.

---

### 3. Elastic

The system scales automatically according to load.

Instead of:

* vertical scaling,
* giant servers,
* fixed thread pools,

reactive systems prefer:

* horizontal scaling,
* distributed workloads,
* stateless services,
* message queues.

Example:

* Kafka consumers scale from 2 → 50 during traffic spikes.

---

### 4. Message-Driven

Components communicate asynchronously using messages/events.

This is the FOUNDATION of reactive systems.

Instead of:

```text
Service A calls Service B and waits
```

Reactive systems prefer:

```text
Service A sends message/event
Service B processes asynchronously
```

Benefits:

* loose coupling,
* location transparency,
* fault isolation,
* elasticity,
* async execution.

Typical technologies:

* Apache Kafka
* RabbitMQ
* Apache Pulsar
* NATS

## Reactive Systems vs Reactive Programming

These are related but NOT identical.

## Reactive Programming

Reactive programming is a coding style for handling:

* asynchronous streams,
* events,
* non-blocking pipelines.

Examples:

* Project Reactor
* RxJava
* RxJS

It helps implement reactive systems.

## Relationship Between Key Concepts

### Reactive Systems

High-level distributed architecture philosophy.

Uses:

* async communication,
* messaging,
* non-blocking execution,
* event-driven processing.

Reactive systems are NOT just:

* async code,
* callbacks,
* event loops.

They are a FULL distributed architecture philosophy.

A system is reactive when the WHOLE architecture is designed for:

* responsiveness,
* resilience,
* elasticity,
* message-driven communication.

---

### Event-Driven Architecture (EDA)

Architectural style where events trigger actions.

Reactive systems are usually event-driven.

Example:

```text
OrderCreated event
    ↓
Inventory Service
    ↓
Payment Service
    ↓
Notification Service
```

---

### Asynchronous Systems

Operations do not wait synchronously.

Example:

```text
Send request
Continue execution
Handle response later
```

Reactive systems heavily depend on async execution.

---

### Non-Blocking Systems

Threads do not wait for I/O.

Instead of:

```text
thread waits for DB response
```

You get:

```text
register callback
thread becomes free
resume later when data arrives
```

This is critical for scalability.

---

## Example: Traditional vs Reactive Request Handling

### Traditional Blocking Model

```text
Request
  ↓
Thread allocated
  ↓
Wait for DB
  ↓
Wait for network
  ↓
Wait for another service
  ↓
Return response
```

Problems:

* wasted threads,
* thread exhaustion,
* poor scalability.

---

### Reactive Model

```text
Request
  ↓
Non-blocking async operations
  ↓
Thread released
  ↓
System notified when data arrives
  ↓
Any available worker continues processing
```

## Backpressure

Reactive systems must control producer/consumer speed mismatch.

Problem:

```text
Producer generates 1M events/sec
Consumer handles 10k/sec
```

Without control:

* memory explosion,
* queue overflow,
* crashes.

Reactive systems introduce: **Backpressure**

Consumer tells producer: "slow down"

or "I can handle only N items now"

Reactive Streams specification standardizes this.


## Reactive Streams

A standard for:

* async stream processing,
* non-blocking streams,
* backpressure.

Implemented by:

* Project Reactor
* RxJava
* Akka Streams

## Actor Model in Reactive Systems

A common reactive architecture pattern.

Actors:

* communicate via messages,
* keep isolated state,
* process one message at a time.

Benefits:

* avoids shared mutable state,
* fault isolation,
* easier concurrency.

Frameworks:

* Akka
* Orleans

Microservices need:

* fault isolation.

Reactive patterns commonly used:

* API Gateway
* Circuit Breaker

## Reactive Systems and Kafka

Kafka fits VERY naturally here.

Kafka enables:

* asynchronous communication,
* event streaming,
* decoupling,
* scalability,
* replayability.

Reactive systems often use Kafka as:

* event backbone,
* stream transport,
* buffering layer.

Example:

```text

    ↓ emits event
Kafka
    ↓
Analytics Service
Fraud Service
Recommendation Service
Notification Service
```
