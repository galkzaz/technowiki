## Structure of C Programs
The General Form of a Simple Program
```
directives
int main(void)
{
  statements
}
```

for example

```c
#include <stdio.h>

int main(void)
{
    printf("Hello, world!\n");
    return 0;
}
```
A typical C program has the following components:

- **Preprocessor Directives**
  (editing commands that modify the program prior to compilation)
- **Global Declarations**
  (variables and functions that are accessible throughout the program)
- **Functions**
  (named blocks of executable code, of which main is an example)
- **Statements and Expressions**
  (commands to be performed when the program is run). 
- **Comments**
  (text that is ignored by the compiler)

### Directives
Before a C program is compiled, it is first edited by a preprocessor. Commands intended for the preprocessor are called directive.

Preprocessor directives are instructions to the C preprocessor, executed before compilation. They are used to:
- Include libraries
- Define constants and macros
- Conditional compilation

All preprocessor directives start with #:
```
#include <stdio.h>    // Include standard input/output library
#define PI 3.14159    // 
```
This directive states that the information in \<stdio.h\> is to be "included" into
the program before it is compiled. \<stdio.h\> contains information about C’s
standard I/O library. C has a number of headers like \<stdio.h\>; each contains
information about some part of the standard library. The reason we’re including
\<stdio.h\> is that C, unlike some programming languages, has no built-in
"read" and "write" commands. The ability to perform input and output is provided
instead by functions in the standard library.

Directives 
- always begin with a # character, which distinguishes them from
other items in a C program. 
- By default, directives are one line long; there’s no
semicolon or other special marker at the end of a directive.

**Common Directives**
| Directive                       | Purpose                        |
| ------------------------------- | ------------------------------ |
| `#include`                      | Include header files           |
| `#define`                       | Define macros or constants     |
| `#ifdef` / `#ifndef` / `#endif` | Conditional compilation        |
| `#pragma`                       | Compiler-specific instructions |

#### Header Files
Header files (.h) contain:
- Function prototypes
- Macro definitions
- Data type definitions
- External variable declarations

They allow modular programming and code reuse.

Example: math.h, stdio.h, string.h
```c
#include <stdio.h>
#include <string.h>
```
### Global Declarations
Global declarations appear outside all functions and are accessible throughout the program. They typically include:
- Global variables
- Function prototypes
- Enumerations, typedefs, and structures

Example
```c
int globalCounter = 0;  // Global variable

void incrementCounter(void); // Function prototype
```
Avoid excessive use of global variables; prefer local scope for modularity.

Function prototypes allow functions to be defined after main.

### Functions
#### Main Function
Although a C program may consist of many functions, only the main function is mandatory. main is special: it gets called automatically when the program is executed.

Every C program must have a main() function, which serves as the entry point:
```c
int main(void) {
    printf("Hello, world!\n");
    return 0;
}
```
Characteristics:
- Return type is typically int
- Parameters can be void (no arguments) or int argc, char *argv[] for command-line arguments
- return 0; signals successful program execution to the OS

the main is a function returns a status code that is given to the operating system when the program terminates.

The word int just before main indicates that the main function returns an integer value. The word void in parentheses indicates that main has no arguments.

The statement
```c
return 0;
```
has two effects: 
- it causes the main function to terminate (thus ending the program).
- and it indicates that the main function returns a value of 0.

If there’s no return statement at the end of the main function, the program
will still terminate. However, many compilers will produce a warning message
(because the function was supposed to return an integer but failed to).

#### User-Defined Functions
Functions are like "procedures" or "subroutines" in other programming languages—they’re the building blocks from which programs are constructed. In fact,
a C program is little more than a collection of functions. Functions fall into two
categories: 
- those written by the programmer 
- and those provided as part of the C implementation(called library functions, since they belong to a "library" of functions that are supplied with the compiler).

The term "function" comes from mathematics, where a function is a rule for computing a value when given one or more arguments:
$$
f(x) = x + 1\\\\
g(y, z) = y^2 - z^2
$$
C uses the term "function" more loosely. In C, a function is simply a series of
statements that have been grouped together and given a name. 

Some functions compute a value; some don’t. 
- A function that computes a value uses the return statement to specify what value it "returns". For example, a function that adds 1 to its argument might execute the statement
```c
return x + 1;
```
while a function that computes the difference of the squares of its arguments might execute the statement
```c
return y * y - z * z;
```

Functions break a program into modular, reusable units:
```c
int add(int a, int b) {
    return a + b;
}
```
Function Structure:
1. Return type: Type of value returned (int, float, void, etc.)
2. Function name: Identifier used to call the function
3. Parameters (formal arguments): Inputs to the function
4. Function body: Statements enclosed in { }

### Statements and Expressions
A statement is a command to be executed when the program runs.

A C program consists of statements executed in sequence:
#### Expression Statements
```c
x = y + 5;       // Assignment
sum = add(a, b); // Function call
```
add(a, b) is the function call. Asking a function to perform its assigned task is known as calling
the function.
#### Compound Statements
```c
Blocks of statements enclosed in { }:
{
    int i;
    for (i = 0; i < 10; i++)
        printf("%d ", i);
}
```
#### Control Statements
Control the flow of execution:
- Conditional Statements: if, else, switch
- Loops: for, while, do-while
- Jump Statements: break, continue, return, goto (rarely recommended)

### Comments
Comments provide explanations for human readers and are ignored by the compiler:

### Example of a Complete C Program
```c 
#include <stdio.h>
#define PI 3.14159

// Global variable
int count = 0;

// Function prototype
void greet(void);

int main(void) {
    greet();                  // Call user-defined function
    printf("PI = %.2f\n", PI); // Access macro
    return 0;                  // Return success to OS
}

void greet(void) {
    printf("Hello, C Programmer!\n");
    count++;  // Increment global variable
}
```
Explanation of Structure:
1. Preprocessor directives (#include, #define)
2. Global declaration (count)
3. Function prototype (greet)
4. main() function with statements
5. User-defined function (greet)

### Layout of a C Program
We can think of a C program as a series of tokens: groups of characters that can’t
be split up without changing their meaning. 
- Identifiers and keywords are tokens.
- So are operators like + and -, 
- punctuation marks such as the comma and semicolon, 
- and string literals. 
 
For example, the statement
```c
printf("Height: %d\n", height);
```
consists of seven tokens:
```
printf ( "Height: %d\n" ,  height )  ;
  (1) (2)    (3)       (4)  (5)  (6)(7)
```
Tokens (1) and (5) are identifiers, token (3) is a string literal, and tokens (2), (4), (6), and (7) are punctuation marks.

The amount of space between tokens in a program isn’t critical in most cases.
At one extreme, tokens can be crammed together with no space between them at
all, except where this would cause two tokens to merge into a third token.

we could put the entire main function on a single
line. We can’t put the whole program on one line, though, because each prepro-
cessing directive requires a separate line.

C allows us to insert any amount of space—blanks, tabs, and new-line characters between tokens. This rule has several important consequences for program layout:
- Statements can be divided over any number of lines. The following statement,
for example, is so long that it would be hard to squeeze it onto a single line:
```c
printf("Dimensional weight (pounds): %d\n",
       (volume + INCHES_PER_POUND - 1) / INCHES_PER_POUND);
```
- Space between tokens makes it easier for the eye to separate them. For this
reason,  usually put a space before and after each operator:
```c
volume = height * length * width;
```
some also put a space after each comma. Some programmers go even further, putting spaces around parentheses and other punctuation.
- Indentation can make nesting easier to spot. For example, we should indent
declarations and statements to make it clear that they’re nested inside main.
- Blank lines can divide a program into logical units, making it easier for the
reader to discern the program’s structure. A program with no blank lines is as
hard to read as a book with no chapters.

Although extra spaces can be added between tokens, it’s not possible to add space within a token without changing the meaning of the program or causing an error. Writing
```
fl oat fahrenheit, celsius; /*** WRONG ***/
```
or
```
fl
oat fahrenheit, celsius; /*** WRONG ***/
```
produces an error when the program is compiled

Putting a space inside a string literal is allowed, although it changes the meaning of the string. 

putting a new-line character in a string (in other words, splitting the string over two lines) is illegal:
```
printf("To C, or not to C:
that is the question.\n"); /*** WRONG ***/
```
Continuing a string from one line to the next requires a special technique
## Compiling and Linking

to convert the program to a form that the machine can execute, that usually involves three steps:Preprocessing,Compiling,Linking.

```
C source
   ↓
[ Preprocessor ]   → expanded C
   ↓
[ Compiler ]       → object code (.o)
   ↓
[ Linker ]         → executable
```

Regardless of the compilation method used, every C program conceptually passes through the same fundamental stages.

```
C Source Code (.c)
        │
        ▼
+------------------+
| Preprocessor     |
| (#include, macro)|
+------------------+
        │
        ▼
+------------------+
| Compiler         |
| (C → Assembly)   |
+------------------+
        │
        ▼
+------------------+
| Assembler        |
| (Assembly → .o)  |
+------------------+
        │
        ▼
+------------------+
| Linker           |
| (.o + libraries) |
+------------------+
        │
        ▼
Executable Program
```

This pipeline is logically fixed; different compilation methods differ in how often and how explicitly each stage is invoked.

Splitting thsi process into 3 steps gives:

- Modularity: recompile only changed files
- Performance: link optimized object code
- Portability: same source, different compilers/targets
- Abstraction: programmers don’t think in machine code

### Preprocessing

The program is first given to a preprocessor, which obeys
commands that begin with # (known as directives). A preprocessor is a bit like
an editor; it can add things to the program and make modifications.

```
gcc -E hello.c > hello.i
```

```
hello.c  ──▶  hello.i   (expanded C source)
```

Preprocessing does:

- Handles all lines starting with # (preprocessor directives)
- Produces a pure C file with no macros or includes left
- Removes comments
- Expands macros
- Removes empty lines
- Removes whitespace
- Removes preprocessor directives
- Removes all other directives

Main tasks

- #include → literally copies header file contents into the source
- #define → macro expansion
- #if / #ifdef → conditional compilation

### Compiling

The modified program now goes to a compiler, which translates it
into machine instructions (object code). The program isn’t quite ready to run
yet, however.

```
gcc -c hello.c
```

```
hello.i  ──▶  hello.o   (object file)
```

Compiling does

- Translates preprocessed C code into machine-level instructions
- Checks syntax, types, semantics
- Performs optimizations
- Produces object code, not a runnable program yet

Internally, this includes

- Lexical analysis
- Parsing
- Semantic analysis
- Optimization
- Code generation

important

- hello.o may contain unresolved symbols (e.g., printf)
- Each .c file becomes one object file

### Linking

In the final step, a linker combines the object code produced by the
compiler with any additional code needed to yield a complete executable program. This additional code includes library functions (like printf) that are
used in the program.

```
gcc hello.o -o hello
```

```
hello.o + libc + startup code  ──▶  hello (executable)
```

Linking does

- Combines object files into a single executable
- Resolves references to:
  ◦ Library functions (printf, malloc)
  ◦ Other object files
- Assigns final memory addresses

There are two type of linking

- Static linking: library code copied into executable
- Dynamic linking: executable refers to shared libraries (.so)

### Static and Dynamic Linking

| Aspect                               | Static Linking    | Dynamic Linking          |
| ------------------------------------ | ----------------- | ------------------------ |
| When linking happens                 | **Compile time**  | **Run time**             |
| Where library code lives             | Inside executable | Shared libraries (`.so`) |
| Executable size                      | Large             | Small                    |
| Memory sharing                       | ❌ No             | ✅ Yes                   |
| Update libraries without recompiling | ❌ No             | ✅ Yes                   |
| Failure time                         | Build time        | Program start / runtime  |

## Compilation Approaches(Compilation Methods/Workflows)(Ways to Compile C Code)

Compiling a C program is not a single, uniform process but can be carried out in several distinct ways depending on the size of the program, the target platform, performance requirements, and development workflow. Although the underlying compilation stages (preprocessing, compilation, assembly, and linking) remain the same, the manner in which these stages are invoked and coordinated may vary significantly.

The C language supports multiple compilation approaches ranging from simple single-step compilation to complex multi-target build systems. The choice of compilation method depends on program scale, performance requirements, development environment, and deployment constraints. Mastery of these compilation models is essential for professional C programming and systems-level software development.

Understanding these workflows enables programmers to:

- Predict build performance
- Diagnose compilation and linking errors
- Choose appropriate deployment strategies
- Design scalable software systems

### Direct (Single-Step) Compilation

In direct compilation, the entire compilation pipeline is executed through a single command. The compiler internally invokes the preprocessor, compiler, assembler, and linker.

```
gcc hello.c -o hello
```

```
hello.c
   │
   ▼
gcc[ Preprocess → Compile → Assemble → Link ]
   │
   ▼
hello (executable)

```

**Characteristics**

- Simple and convenient
- Suitable for small programs and instructional use
- No explicit control over intermediate files

Limitations

- Inefficient for large programs
- Recompiles all source code even when only one file changes

### Separate Compilation

In separate compilation, each source file is compiled independently into an object file. The object files are later combined during the linking stage.

```
gcc -c file1.c
gcc -c file2.c
gcc file1.o file2.o -o program
```

```
file1.c        file2.c        file3.c
   │              │              │
   ▼              ▼              ▼
file1.o        file2.o        file3.o
        \          |          /
         \         |         /
          ▼        ▼        ▼
                Linker
                  │
                  ▼
             program
```

**Characteristics**

- Enables modular program design
- Supports incremental compilation
- Fundamental to large-scale software development

Advantages

- Reduced compilation time
- Clear separation of compilation and linking errors
- Encourages abstraction through header files

### Incremental Compilation Using Build Systems

In large projects, compilation is usually controlled by a build system that automatically determines which files need recompilation based on dependency analysis.

```
make
```

**Characteristics**

- Automates separate compilation
- Tracks dependencies between source and header files
- Minimizes unnecessary recompilation(Minimizes redundant work)
- Scales to thousands of source files

Common Tools

- Make
- CMake
- Meson

```
   Build Configuration
  (Makefile / CMakeLists)
           │
           ▼
    Dependency Analysis
            │
┌───────────┴─────────────┐
▼                         ▼
Compile Changed Files  Skip Unchanged
│
▼
Updated Object Files
│
▼
Linker
│
▼
Final Executable
```

### Cross-Compilation

Cross-compilation occurs when the compilation host and the execution target are different architectures or operating systems.

```
arm-none-eabi-gcc hello.c -o hello
```

Use Cases

- Embedded systems
- Firmware development
- Operating system kernels

Challenges

- ABI compatibility
- Availability of target libraries
- Debugging complexity

### Static Compilation

In static compilation, all library code required by the program is linked into the executable at compile time.

```
gcc -static hello.c -o hello
```

```
Object Files (.o)      Static Libraries (.a)
        │                       │
        └───────────┬───────────┘
                    ▼
                 Linker
                    │
                    ▼
        Fully Self-Contained Executable
```

**Characteristics**

- Produces self-contained executables
- Eliminates runtime library dependencies

Trade-offs

- Larger executable size
- No automatic library updates
- Increased memory usage per process

### Dynamic Compilation (Dynamic Linking)

In dynamic compilation (more precisely, dynamic linking), library code is not embedded in the executable. Instead, it is resolved at program load time or during execution.

```
gcc hello.c -o hello
```

Build-Time View

```
Object Files (.o)
        │
        ▼
     Linker
        │
        ▼
Executable + Library References
```

Run-Time View

```
Executable
    │
    ▼
Dynamic Loader (ld-linux)
    │
    ├── libc.so
    ├── libm.so
    └── other shared libraries
```

**Characteristics**

- Libraries loaded at runtime
- Smaller executables
- Shared libraries across processes
- Requires runtime loader support

### Debug and Optimized Compilation

#### Debug Compilation

```
gcc -g -O0 hello.c -o hello
```

- Includes debugging symbols
- Minimizes optimizations to preserve source-level behavior

#### Optimized (Release) Compilation

```
gcc -O2 hello.c -o hello
```

- Improves performance and code size
- Optimization may alter control flow, inline functions, or remove variables, complicating debugging.

Debug Build

```
Source Code
    │
    ▼
Compiler (-O0 -g)
    │
    ▼
Executable with Debug Symbols
```

Optimized Build

```
Source Code
    │
    ▼
Compiler (-O2 / -O3)
    │
    ▼
Optimized Executable
```

### Multi-Target and Multi-Configuration Compilation

Modern build systems allow the same source code to be compiled into multiple configurations (e.g., debug/release, static/dynami) or for multiple platforms. i.e

- Debug vs Release builds
- x86 vs ARM binaries

```
Host System (x86_64)
        │
        ▼
Cross-Compiler (ARM GCC)
        │
        ▼
   ARM Binary
        │
        ▼
Target System (ARM Device)
```

- Compilation and execution occur on different machines
- Requires target-specific libraries and ABI support

This approach is essential for portable and scalable software systems.

### Runtime and Just-in-Time Compilation

Although C is traditionally compiled ahead-of-time, some systems support compiling C code during program execution.

Examples

- TinyCC (in-memory compilation)
- LLVM-based JIT compilation

Applications

- Dynamic code generation
- Plugin systems
- Scientific computing

### Comparison of Different Compilation Methods

| Compilation Method                 | Description                             | Typical Command        | Advantages                    | Disadvantages                  | Typical Use                |
| ---------------------------------- | --------------------------------------- | ---------------------- | ----------------------------- | ------------------------------ | -------------------------- |
| **Direct compilation**             | All stages executed in one step         | `gcc hello.c -o hello` | Simple, fast to use           | Inefficient for large programs | Small programs, teaching   |
| **Separate compilation**           | Each source file compiled independently | `gcc -c file.c`        | Modular, faster rebuilds      | More complex workflow          | Medium-large projects      |
| **Build-system-based compilation** | Automated dependency tracking           | `make`, `cmake`        | Scalable, maintainable        | Requires configuration         | Large software systems     |
| **Cross-compilation**              | Host and target differ                  | `arm-none-eabi-gcc`    | Enables embedded development  | Debugging complexity           | Embedded systems           |
| **Static compilation**             | Libraries linked at build time          | `gcc -static`          | Self-contained binary         | Large executables              | Containers, recovery tools |
| **Dynamic compilation (linking)**  | Libraries resolved at runtime           | default `gcc`          | Small binaries, shared memory | Runtime dependency errors      | General-purpose software   |
| **Debug compilation**              | Optimizations disabled, symbols added   | `-g -O0`               | Easier debugging              | Slower execution               | Development                |
| **Optimized compilation**          | Aggressive optimization                 | `-O2`, `-O3`           | High performance              | Harder debugging               | Production builds          |

```
gcc main.c add.c -o program
```

- Compiler recompiles both files every time
- Acceptable for small programs

Separate compilation

```
gcc -c add.c
gcc -c main.c
gcc add.o main.o -o program
```

- If main.c changes, add.c need not be recompiled
- Demonstrates modular compilation

## C Compilation Tools

The process of compiling a C program involves a toolchain—a coordinated set of software tools that transform human-readable source code into executable machine instructions. Although the compilation process is often invoked through a single command, it conceptually consists of multiple stages, each supported by specialized tools.

Compiling C code is not performed by a single tool but by a coordinated toolchain. The compiler, preprocessor, assembler, linker, and build systems each play a distinct role in transforming source code into an executable program. Understanding these tools and their interactions is essential for effective systems programming, performance tuning, and debugging.

### C Compilers

A C compiler is the central tool in the compilation pipeline. It translates C source code into machine-dependent object code, typically through several internal phases such as lexical analysis, parsing, semantic analysis, optimization, and code generation.

#### GNU Compiler Collection (GCC)

- Command: gcc
- Platform support: Unix/Linux, BSD, Windows (via MinGW)
- **Characteristics**:
  ◦ Mature and widely deployed
  ◦ Supports extensive optimization options
  ◦ Provides support for multiple architectures and languages
- Commonly used in operating systems, embedded systems, and open-source software

Example:

```
gcc hello.c -o hello
```

#### Clang / LLVM Compiler

- Command: clang
- Architecture: Modular compiler framework based on LLVM
- **Characteristics**:
  ◦ High-quality diagnostics and error messages
  ◦ Faster compilation for large codebases
  ◦ Used by macOS, FreeBSD, and Android toolchains
- Increasingly adopted in modern systems software

Example:

```
clang hello.c -o hello
```

#### Microsoft Visual C Compiler (MSVC)

- Command: cl.exe
- Platform: Microsoft Windows
- **Characteristics**:
  ◦ Native Windows ABI and runtime
  ◦ Required for many Windows system libraries
  ◦ Integrated with Visual Studio
- Not directly compatible with GCC/Clang object formats

#### Specialized and Lightweight Compilers

- Tiny C Compiler (TCC)
  ◦ Emphasizes extremely fast compilation
  ◦ Often used for scripting, education, or embedded environments
- Intel C Compiler (ICC/ICX)
  ◦ Optimized for Intel architectures
  ◦ Common in high-performance computing (HPC)

### Preprocessor

The C preprocessor is responsible for handling preprocessing directives before compilation.

Responsibilities:

- Macro expansion (#define)
- File inclusion (#include)
- Conditional compilation (#if, #ifdef)
- Comment removal
  Invocation:

```
gcc -E hello.c > hello.i
```

The output of the preprocessor is a pure C source file with all directives resolved.

### Assembler

The assembler converts assembly language into machine code. While typically invoked implicitly by the compiler, it can be accessed explicitly.

Example:

```
gcc -S hello.c      # generate assembly
as hello.s          # assemble into object code
ld hello.o -o hello # link into executable
```

Assemblers are architecture-specific and produce object files (.o).

### Linker

The linker combines one or more object files and libraries into a final executable.

Responsibilities:

- Symbol resolution
- Address relocation
- Library inclusion (static or dynamic)
- Generation of executable formats (e.g., ELF)

Invocation:

```
gcc hello.o -o hello
```

The linker may also be invoked directly using ld, though this is uncommon in practice.

### Libraries and Supporting Tools

#### Static and Shared Libraries

- Static libraries (.a) are archived object files linked at build time
- Shared libraries (.so) are linked dynamically at runtime

#### pkg-config

A utility that supplies compiler and linker flags for installed libraries.

Example:

```
pkg-config --cflags --libs gtk4
```

### Build Systems

Large C programs require automated tools to manage compilation across many source files.

#### Make

- Uses declarative rules in a Makefile
- Tracks dependencies and minimizes recompilation
- Long-standing and widely used

#### CMake

- Platform-independent build system generator
- Produces Makefiles or Ninja files
- Common in modern cross-platform projects

#### Meson and Ninja

- Meson: high-level build description
- Ninja: low-level, fast build executor
- Designed for speed and correctness

### Cross-Compilation Toolchains

A cross-compiler generates executables for a target architecture different from the host system.

Example:

```
arm-none-eabi-gcc hello.c -o hello
```

Cross-compilation is essential for embedded systems, firmware, and kernel development.

## Variables and Scope
Most programs need to perform a series of calculations before producing output, and thus need a way to store data temporarily during program execution. In C, as in most programming languages, these storage locations are called variables.

### Types
Every variable must have a type, which specifies what kind of data it will hold. C
has a wide variety of types. For now, we’ll limit ourselves to just two: int and
float. Choosing the proper type is critical, since the type affects how the variable
is stored and what operations can be performed on the variable. The type of a
numeric variable determines the largest and smallest numbers that the variable can
store; it also determines whether or not digits are allowed after the decimal point.
A variable of type int (short for integer) can store a whole number such as 0,
1, 392, or –2553. The range of possible values is limited, though. The largest int
value is typically 2,147,483,647 but can be as small as 32,767.
A variable of type float (short for floating-point) can store much larger
numbers than an int variable. Furthermore, a float variable can store numbers
with digits after the decimal point, like 379.125. float variables have drawbacks,
however. Arithmetic on float numbers may be slower than arithmetic on int
numbers. Most significantly, the value of a float variable is often just an approx-
imation of the number that was stored in it. If we store 0.1 in a float variable, we
may later find that the variable has a value such as 0.09999999999999987, thanks
to rounding error.

## Comments
Every program should contain identifying information: the program name, the date written,the author, the purpose of the program, and so forth. In C, this information is placed in comments.

Comments provide explanations for human readers and are ignored by the compiler:
```c
// Single-line comment
/* Multi-line
   comment */
```
- Single-line: `//`
- Multi-line: `/* */`
  - The symbol /* marks the beginning of a comment and the symbol */ marks the end.

Comments may appear almost anywhere in a program, either on separate lines or on the same lines as other program text.

### Multi-line Comments
Comments may extend over more than one line; once it has seen the /* symbol, the compiler reads (and ignores) whatever follows until it encounters the */ symbol. If we like, we can combine a series of short comments into one long comment:
```c
/* Name: pun.c
Purpose: Prints a bad pun.
Author: K. N. King */
```
A comment like this can be hard to read, though, because it’s not easy to see where the comment ends. Putting */ on a line by itself helps:
```c
/* Name: pun.c
Purpose: Prints a bad pun.
Author: K. N. King
*/
```
Even better, we can form a “box” around the comment to make it stand out:
```c
/**********************************************************
* Name: pun.c                                             *
* Purpose: Prints a bad pun.                              *
* Author: K. N. King                                      *
**********************************************************/
```
Programmers often simplify boxed comments by omitting three of the sides:
```c
/*
* Name: pun.c
* Purpose: Prints a bad pun.
* Author: K. N. King
*/
```
A short comment can go on the same line with other program code:
```c
int main(void) /* Beginning of main program */
```
A comment like this is sometimes called a "winged comment".

Forgetting to terminate a comment may cause the compiler to ignore part of your
program. Consider the following example:
```c
printf("My "); /* forgot to close this comment...
printf("cat ");
printf("has "); /* so it ends here */
printf("fleas");
```
Because we’ve neglected to terminate the first comment, the compiler ignores the middle two statements, and the example prints "My fleas" only.

### Single-line Comments
C99 provides a second kind of comment, which begins with // (two adjacent slashes).

Single-line comments start with two forward slashes (//) and continue until the end of the line. They are useful for short explanations or notes within the code.
```c
// This is a comment
```
This style of comment ends automatically at the end of a line. To create a comment
that’s more than one line long, we can either use the older comment style (/* … */) or else put // at the beginning of each comment line:
```c
// Name: pun.c
// Purpose: Prints a bad pun.
// Author: K. N. King
```
The newer comment style has a couple of important advantages. 
- First, because a
comment automatically ends at the end of a line, there’s no chance that an untermi-
nated comment will accidentally consume part of a program. 
- Second, multiline
comments stand out better, thanks to the // that’s required at the beginning of
each line.
### Best Practices:
- Use comments to explain why, not what
- Keep comments concise and relevant
