## Dijkstra's semaphore proposal
By the mid-1960s, people had already discovered:
- Busy waiting (Peterson, TSL, XCHG) → wastes CPU, priority inversion
- sleep / wakeup → lost wakeups
- Wakeup bits → do not scale (finite memory)

E. W. Dijkstra (1965) suggested using an
integer variable to count the number of wakeups saved for future use. In his initial
proposal, a new variable type, which he called a semaphore, was introduced. A semaphore could have the value 0, indicating that no wakeups were saved, or some
positive value if one or more wakeups were pending.

Dijkstra proposed having two operations on semaphores, now usually called
down and up (generalizations of sleep and wakeup, respectively).

In Dijkstra's original paper, he used the names P and V instead of
down and up, respectively. Since these have no mnemonic significance to people
who do not speak Dutch and only marginal significance to those people who do—
Proberen (try) and Verhogen (raise, make higher)—we will use the terms down and
up instead.

A **semaphore** is an integer variable shared between processes, with two atomic operations:
- P (from proberen — “to test”)
- V (from verhogen — “to increment”)

No other operations are allowed. Formally:
```
Semaphore S is an integer ≥ 0
```
You are not allowed to read or write it directly.

1. The down operation on a semaphore: 
    - checks to see if the value is greater than 0. 
    - If so, it decrements the value (i.e., uses up one stored wakeup) and just continues. 
        ```
        P(S):
            while S == 0:
                sleep
            S = S - 1
        ```
    - If the value is 0, the process is put to sleep without completing the down for the moment. 
    - Checking the value, changing it, and possibly going to sleep, are all done as a single, indivisible atomic action(The test, decrement, and sleep are atomic.). 
1. The up operation 
    - increments the value of the semaphore addressed. 
    - If one (or more) processes were sleeping on that semaphore, unable to complete an earlier down operation, one of them is chosen by the system (e.g., at random) and is allowed to complete its down. 
        ```
        V(S):
            S = S + 1
            if some process is sleeping on S:
                wake one of them
        ```
    - After an up on a semaphore with processes sleeping on it, the semaphore will still have the value of 0. However, there will be one fewer process sleeping on it. 
    - The operation of incrementing the semaphore and waking up one process is also indivisible. No process ever blocks doing an up, just as no process ever blocks doing a wakeup in the earlier model.

It is guaranteed that once a semaphore operation has
started, no other process can access the semaphore until the operation has completed or blocked. This atomicity is absolutely essential to solving synchronization
problems and avoiding race conditions. Atomic actions, in which a group of related
operations are either all performed without interruption or not performed at all, are
extremely important in many other areas of computer science as well.

Dijkstra's insight: Synchronization is counting, not signaling. Instead of remembering that something happened, we must remember how many times it happened.

Dijkstra's semaphore is an integer synchronization primitive accessed only through atomic P and V operations; by counting events rather than signaling them, it avoids busy waiting and lost wakeups and enables correct solutions to mutual exclusion and resource allocation problems.

Dijkstra was strict:
- No reading the value
- No setting the value
- No conditional checks
- Only P and V

Why? Because:
-  Any extra access breaks atomicity
-  Leads straight back to lost wakeups

This discipline is what makes semaphores correct.

## semaphores
A semaphore is a synchronization primitive used to:
- Control access to shared resources
- Prevent race conditions
- Coordinate concurrent processes/threads


**Mathematical Definition**

A semaphore S is an integer variable accessed only via two atomic operations:
1. **wait(S) (also called P or down)**
```
S = S - 1
if S < 0 → block the process
```
2. **signal(S) (also called V or up)**
```
S = S + 1
if S ≤ 0 → wake up one blocked process
```
The key idea: The decrement and test must be atomic.

Semaphores Solves this problem:
- Critical section protection
- Producer–Consumer problem
- Readers–Writers problem
- Dining Philosophers
- Process synchronization

## Types of Semaphores
Semaphore: A synchronization primitive that can be used to control access:
    • Binary semaphore (mutex): 0 or 1, used for mutual exclusion.
    • Counting semaphore: Can be used to track the number of allowed concurrent accesses.

We usually use:
1. mutex – protects access to a shared counter (read_count) that tracks the number of readers currently reading.
2. wrt – ensures exclusive access for writers.

### Binary Semaphore (Mutex-like)
- Value: 0 or 1
- Used for mutual exclusion

```
sem mutex = 1;

P(mutex);   // enter critical section
critical();
V(mutex);   // exit
```
Guarantees:
- Only one process inside

### Counting Semaphore (Resource Pool)
- Value: 0..N
- Controls access to N identical resources

```
sem empty = N;
sem full  = 0;
```
Tracks:
-  Number of empty slots
-  Number of full slots
This is exactly what wakeup bits failed to do.

Example:
- Printer pool (3 printers)
- Semaphore initialized to 3

## Solving the Producer-Consumer Problem Using Semaphores
Semaphores solve the lost-wakeup problem To make
them work correctly, it is essential that they be implemented in an indivisible way.

The normal way is to implement up and down as system calls, with the operating
system briefly disabling all interrupts while it is testing the semaphore, updating it,
and putting the process to sleep, if necessary. As all of these actions take only a
few instructions, no harm is done in disabling interrupts. 

If multiple CPUs are being used:
- each semaphore should be protected by a lock variable, with the ``TSL`` or
``XCHG`` instructions used to make sure that only one CPU at a time examines the
semaphore.
- Be sure you understand that using TSL or XCHG to prevent several CPUs from
accessing the semaphore at the same time is quite different from the producer or
consumer busy waiting for the other to empty or fill the buffer. The semaphore
operation will take only a few nanoseconds, whereas the producer or consumer
might take arbitrarily long.

Producer:
```
P(empty);
P(mutex);
insert_item();
V(mutex);
V(full);
```
Consumer:
```
P(full);
P(mutex);
remove_item();
V(mutex);
V(empty);
```
Why this is perfect:
- No lost wakeups
- No deadlock
- No starvation (with fair scheduling)
- Scales to m producers / n consumers

This solution uses three semaphores: 
1. one called **full** for counting the number of
slots that are full, 
2. one called **empty** for counting the number of slots that are empty,
3. and one called **mutex** to make sure the producer and consumer do not access the
buffer at the same time. 

```
mutex  → protects buffer
empty  → counts empty slots
full   → counts filled slots
```
Full is initially 0, empty is initially equal to the number of
slots in the buffer, and mutex is initially 1.

Semaphores that are initialized to 1 and
used by two or more processes to ensure that only one of them can enter its critical
region at the same time are called **binary semaphores**. If each process does a
down just before entering its critical region and an up just after leaving it, mutual
exclusion is guaranteed.

#define N 100 / * number of slots in the buffer * /
typedef int semaphore; / * semaphores are a special kind of int * /

semaphore mutex = 1; / * controls access to critical region * /
semaphore empty = N; / * counts empty buffer slots * /
semaphore full = 0; / * counts full buffer slots * /

void producer(void)
{
    int item;
    while (TRUE) { / * TRUE is the constant 1 * /
        item = produce_item( ); /* generate something to put in buffer * /
        down(&empty); / * decrement empty count * /
        down(&mutex); / * enter critical region * /
        insert_item(item); / * put new item in buffer * /
        up(&mutex); /* leave critical region * /
        up(&full); /* increment count of full slots * /
    }
}
void consumer(void)
{
    int item;
    while (TRUE) { / * infinite loop * /
        down(&full); / * decrement full count * /
        down(&mutex); / * enter critical region * /
        item = remove_item( ); /* take item from buffer * /
        up(&mutex); /* leave critical region * /
        up(&empty); /* increment count of empty slots * /
        consume_item(item); / * do something with the item * /
    }
}

```c title='Complete semaphore-based solution'
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <unistd.h>

#define N 2

int buffer[N];
int in = 0, out = 0;

sem_t mutex;
sem_t empty;
sem_t full;

// Producer
void* producer(void* arg)
{
    int id = *(int*)arg;

    sleep(1);
    printf('Producer %d: producing item\n', id);

    sem_wait(&empty);    // wait for empty slot
    sem_wait(&mutex);    // enter critical section

    buffer[in] = id;
    in = (in + 1) % N;

    printf('Producer %d: inserted item\n', id);

    sem_post(&mutex);    // exit critical section
    sem_post(&full);     // signal item available

    return NULL;
}

// Consumer
void* consumer(void* arg)
{
    int item;

    for (int i = 0; i < 2; i++) {
        sem_wait(&full);     // wait for item
        sem_wait(&mutex);    // enter critical section

        item = buffer[out];
        out = (out + 1) % N;

        printf('Consumer: consumed item %d\n', item);

        sem_post(&mutex);    // exit critical section
        sem_post(&empty);    // signal empty slot
    }

    return NULL;
}

int main(void)
{
    pthread_t p1, p2, c;
    int id1 = 1, id2 = 2;

    sem_init(&mutex, 0, 1);
    sem_init(&empty, 0, N);
    sem_init(&full, 0, 0);

    pthread_create(&c, NULL, consumer, NULL);
    pthread_create(&p1, NULL, producer, &id1);
    pthread_create(&p2, NULL, producer, &id2);

    pthread_join(p1, NULL);
    pthread_join(p2, NULL);
    pthread_join(c, NULL);

    sem_destroy(&mutex);
    sem_destroy(&empty);
    sem_destroy(&full);

    return 0;
}

```

## The Readers and Writers Problem Using Semaphores
The producers-consumers problem is useful for modeling two processes (or
threads) that exchange blocks of data while sharing a buffer. Another famous problem is the readers and writers problem (Courtois et al., 1971), which models access to a database. 

Imagine, for example, an airline reservation system, with many competing processes wishing to read and write it. It is acceptable to have multiple processes reading the database at the same time, but if one process is updating (writing) the database, no other processes may have access to the database, not even readers. 

The question is how do you program the readers and the writers?

The Readers-Writers Problem is a classic synchronization problem in operating systems:
    • Multiple readers can read the shared data simultaneously without interfering with each other.
    • Writers require exclusive access: only one writer can write at a time, and no reader can read while a writer is writing.

The Goal is to void race conditions while allowing maximum concurrency.

### Reader-priority
Reader priority is a strategy where readers have priority over writers. This means that if there are readers waiting to read, writers must wait until all readers have finished reading before they can write.

We’ll describe the first variant (Reader-priority), where readers can starve writers if many readers keep coming.
```
Time -->
R1      [Reading]
R2      [Reading]
W1             [Waiting]
R3             [Waiting]
R1, R2 done
W1      [Writing]
```
    • Multiple readers can read simultaneously.
    • Writers must wait until all readers finish.
    • No two writers can write at the same time.

In this solution, the first reader to get access to the database does a down on the semaphore db. Subsequent readers merely increment a counter, rc. As readers leave, they decrement the counter, and the last to leave does an up on the semaphore, allowing a blocked writer, if there is one, to get in.

The solution presented here implicitly contains a subtle decision worth noting. Suppose that while a reader is using the database, another reader comes along. Since having two readers at the same time is not a problem, the second reader is admitted. Additional readers can also be admitted if they come along.

Now suppose a writer shows up. The writer may not be admitted to the database, since writers must have exclusive access, so the writer must be suspended. Later, additional readers show up. As long as at least one reader is still active, subsequent readers are admitted. As a consequence of this strategy, as long as there is a steady supply of readers, they will all get in as soon as they arrive. The writer will be kept suspended until no reader is present. If a new reader arrives, say, every
2 sec, and each reader takes 5 sec to do its work, the writer will never get in. Obvi-
ously, this is not a satisfactory situation.

To avoid this situation, the program could be written slightly differently: when a reader arrives and a writer is waiting, the reader is suspended behind the writer instead of being admitted immediately. In this way, a writer has to wait for readers that were active when it arrived to finish but does not have to wait for readers that came along after it. The disadvantage of this solution is that it achieves less concurrency and thus lower performance. Courtois et al. present a solution that gives
priority to writers

```
typedef int semaphore; / * use your imagination * /
semaphore mutex = 1; / * controls access to rc * /
semaphore db = 1; / * controls access to the database * /
int rc = 0; /* # of processes reading or wanting to * /
void reader(void)
{
while (TRUE) { / * repeat forever * /
down(&mutex); / * get exclusive access to rc * /
rc = rc + 1; /* one reader more now * /
if (rc == 1) down(&db); /* if this is the first reader ... * /
up(&mutex); /* release exclusive access to rc * /
read data base( ); /* access the data * /
down(&mutex); / * get exclusive access to rc * /
rc = rc < 1; /* one reader fewer now * /
if (rc == 0) up(&db); /* if this is the last reader ... * /
up(&mutex); /* release exclusive access to rc * /
use data read( ); /* noncritical region * /
}
}
void writer(void)
{
while (TRUE) { / * repeat forever * /
think up data( ); /* noncritical region * /
down(&db); / * get exclusive access * /
write data base( ); /* update the data * /
up(&db); /* release exclusive access * /
}
}
```
**Shared variables:**
```
int read_count = 0;       // number of readers currently reading
Semaphore mutex = 1;       // for protecting read_count
Semaphore wrt = 1;         // allows exclusive writer access
```
**Reader Process**
```
do {
    // Entry section
    wait(mutex);              // lock mutex to update read_count
    read_count++;
    if (read_count == 1)      // first reader locks the writer
        wait(wrt);
    signal(mutex);            // release mutex

    // Critical section: Reading
    read_data();

    // Exit section
    wait(mutex);
    read_count--;
    if (read_count == 0)      // last reader releases writer
        signal(wrt);
    signal(mutex);

    // Remainder section
    do_other_stuff();
} while (true);
```
**Writer Process**
```
do {
    wait(wrt);          // writer requests exclusive access
    write_data();       // critical section: writing
    signal(wrt);        // release exclusive access

    do_other_stuff();
} while (true);
```
How It Works
1. read_count tracks active readers.
2. First reader locks wrt so writers cannot access.
3. Last reader releases wrt, allowing writers.
4. Writers always lock wrt before writing; ensures exclusive access.

Concurrency:
    • Multiple readers → allowed concurrently.
    • Writer → exclusive access; readers must wait if a writer is writing.

This implementation gives priority to readers.If readers keep arriving continuously: Writers might starve forever.
#### C program implementing the Readers-Writers problem
```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <semaphore.h>
#include <unistd.h>

#define NUM_READERS 5
#define NUM_WRITERS 2

// Shared data
int shared_data = 0;
int read_count = 0;

// Semaphores
sem_t mutex;   // protects read_count
sem_t wrt;     // controls access to shared_data

// -------------------- READER --------------------
void* reader(void* arg) {
    int id = *((int*)arg);

    while (1) {
        // Entry Section
        sem_wait(&mutex);
        read_count++;

        if (read_count == 1) {
            // First reader locks writers
            sem_wait(&wrt);
        }

        sem_post(&mutex);

        // Critical Section (Reading)
        printf("Reader %d is reading: shared_data = %d\n", id, shared_data);
        sleep(1);

        // Exit Section
        sem_wait(&mutex);
        read_count--;

        if (read_count == 0) {
            // Last reader releases writers
            sem_post(&wrt);
        }

        sem_post(&mutex);

        sleep(1);  // Remainder section
    }

    return NULL;
}

// -------------------- WRITER --------------------
void* writer(void* arg) {
    int id = *((int*)arg);

    while (1) {
        // Entry Section
        sem_wait(&wrt);

        // Critical Section (Writing)
        shared_data++;
        printf("Writer %d is writing: shared_data = %d\n", id, shared_data);
        sleep(2);

        // Exit Section
        sem_post(&wrt);

        sleep(2);  // Remainder section
    }

    return NULL;
}

// -------------------- MAIN --------------------
int main() {
    pthread_t readers[NUM_READERS];
    pthread_t writers[NUM_WRITERS];

    int reader_ids[NUM_READERS];
    int writer_ids[NUM_WRITERS];

    // Initialize semaphores
    sem_init(&mutex, 0, 1);
    sem_init(&wrt, 0, 1);

    // Create reader threads
    for (int i = 0; i < NUM_READERS; i++) {
        reader_ids[i] = i + 1;
        pthread_create(&readers[i], NULL, reader, &reader_ids[i]);
    }

    // Create writer threads
    for (int i = 0; i < NUM_WRITERS; i++) {
        writer_ids[i] = i + 1;
        pthread_create(&writers[i], NULL, writer, &writer_ids[i]);
    }

    // Join threads (infinite loop, so program runs forever)
    for (int i = 0; i < NUM_READERS; i++)
        pthread_join(readers[i], NULL);

    for (int i = 0; i < NUM_WRITERS; i++)
        pthread_join(writers[i], NULL);

    // Destroy semaphores
    sem_destroy(&mutex);
    sem_destroy(&wrt);

    return 0;
}
```
- `mutex`
    * Protects read_count from race conditions.
    * Without it: Two readers updating read_count simultaneously would corrupt it.
- `wrt`: Ensures:
    * Only one writer writes at a time
    * No reader reads while a writer is writing

## Implementaions of Semaphores in linux
Linux has multiple types of synchronization primitives, and the implementation differs between:
- User space
- Kernel space

Linux POSIX semaphores (sem_t) are not implemented entirely in the kernel — rather:
 - The glibc (C library) provides the sem_init, sem_wait, sem_post, etc. API.
 - These calls operate mostly in user space using atomic operations.
 - Only when contention occurs do they make a futex system call into the kernel. 
In other words:
Linux semaphores are built on top of futexes, using the futex interface to block and wake threads efficiently. 

📦 2) What is a Futex?
A futex (“fast userspace mutex”) is a kernel system call that programs use to build synchronization primitives such as:
 - Semaphores
 - Mutexes
 - Condition variables
 - Read-write locks
A futex is simply:
A four-byte integer in shared memory that both user space and the kernel understand. 
Futex operations
The futex syscall generally takes three key parameters:
futex(uaddr, FUTEX_WAIT, val, timeout);
futex(uaddr, FUTEX_WAKE, nr_wake);
Where:
 - uaddr = address of the futex word in user memory
 - FUTEX_WAIT = “block if value equals expected”
 - FUTEX_WAKE = “wake up N waiters” 
Key design point
 - Uncontended fast path: all work happens in user space with atomics (no syscall).
 - Contended path: the thread issues FUTEX_WAIT → enters kernel wait queue.
 - Waker threads issue FUTEX_WAKE → kernel wakes N threads. 
This hybrid design avoids expensive syscalls in the common uncontended case.

🛠️ 3) The futex() System Call Implementation Path
User-space perspective
The first thing semaphores do is manipulate a counter:
```
if (atomic_decrement_if_positive(&sem->value)) {
    // success without kernel
} else {
    futex(uaddr, FUTEX_WAIT, expected_value, NULL);
}
```
If the counter is zero, the thread issues a FUTEX_WAIT syscall. 
Kernel inspection of futex
When the kernel receives a futex() syscall (e.g., FUTEX_WAIT or FUTEX_WAKE), it enters code in the futex subsystem:
📌 Entry is typically in:
 - kernel/futex/core.c
 - kernel/futex/waitwake.c
Links to actual source on GitHub:
🔗 futex core: https://github.com/torvalds/linux/blob/master/kernel/futex/core.c 
🔗 wait & wake code: https://github.com/torvalds/linux/blob/master/kernel/futex/waitwake.c 
Rough outline of the kernel path
```
int sys_futex(u32 __user *uaddr, int futex_op, u32 val, ...) {
    if (op == FUTEX_WAIT) {
        hash_bucket = hash_futex(uaddr);     // pick a hash bucket
        spin_lock(&hash_bucket->lock);

        if (get_user(uval, uaddr) != expected)
            return -EAGAIN;                  // value changed → user should retry

        queue_me_on_waitqueue(&queue, hash_bucket);
        spin_unlock(&hash_bucket->lock);

        schedule();                          // block this thread
        return 0;
    }

    if (op == FUTEX_WAKE) {
        hash_bucket = hash_futex(uaddr);
        spin_lock(&hash_bucket->lock);

        wake_up_n_waiters(hash_bucket, nr_wake);

        spin_unlock(&hash_bucket->lock);
        return nr_wake;
    }
    // other futex ops exist...
}
```
This is a simplification but captures the main idea:
    1. The kernel hashes the futex word's address to find a wait queue.
    2. On FUTEX_WAIT, the kernel safely checks the value and enqueues the thread if needed.
    3. On FUTEX_WAKE, it wakes up waiters.
All of this happens inside the kernel.

1️⃣ Design: futex-based semaphore
We implement Dijkstra's semaphore:
S >= 0
P(S): wait / down
V(S): signal / up
Key idea (Linux-style):
 - The semaphore value is an atomic integer
 - Fast path:
        ◦ Try to decrement atomically
        ◦ If success → stay in user space
 - Slow path:
        ◦ If value < 0 → sleep using futex(FUTEX_WAIT)
 - Wakeup:
        ◦ Increment value
        ◦ Call futex(FUTEX_WAKE) to wake one waiter

P operation (sem_wait)
```c
void sem_wait(sem_t *s)
{
    int old;

    while (1) {
        old = __atomic_load_n(&s->value, __ATOMIC_RELAXED);

        if (old > 0) {
            if (__atomic_compare_exchange_n(
                    &s->value, &old, old - 1,
                    0, __ATOMIC_ACQUIRE, __ATOMIC_RELAXED))
                return;  // fast path success
        } else {
            // Sleep while value == 0
            futex_wait(&s->value, 0);
        }
    }
}
```
✔ atomic decrement
✔ no busy waiting
✔ blocks correctly

V operation (sem_post)
```c
void sem_post(sem_t *s)
{
    int old = __atomic_fetch_add(&s->value, 1, __ATOMIC_RELEASE);

    if (old == 0) {
        // Someone might be waiting
        futex_wake(&s->value, 1);
    }
}
```
✔ increments count
✔ wakes exactly one waiter
