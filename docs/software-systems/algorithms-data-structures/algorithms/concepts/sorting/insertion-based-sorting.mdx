## Insertion-Based Sorts
### Insertion Sort
Insertion Sort repeatedly invokes an insert helper function to ensure A[0, i] is properly sorted; eventually, i reaches the rightmost element, sorting A entirely.

#### Core idea
- You build the sorted array one element at a time.
- The left part of the array is always sorted
- You take the next element (the key)
- You insert it into its correct position in the sorted part by shifting larger elements to the right

Figure shows how Insertion Sort operates on an unordered collection A of size n = 16. The 15 rows that follow depict the state of A after each invocation of insert.
![The progression of Insertion Sort on a small array](/docs/assets/software-systems/data-structures-and-algorithms/algorithms/sorting/the-progression-of-insertion-sort-on-a-small-array.png)
A is sorted in place by incrementing pos = 1 up to n − 1 and inserting the element A[pos] into its rightful position in the growing sorted region A[0, pos], demarcated on the right by a bold vertical line. The elements shaded in gray were shifted to the right to make way for the inserted element; in total, Insertion Sort executed 60 neighboring transpositions (a movement of just one place by an element).

#### High-level description
Given an array A[0…n−1]:
1. Assume A[0] is already sorted.
2. For each index i=1 to n−1:
    * Store A[i] as key
    * Compare key with elements to its left
    * Shift all elements larger than key one position to the right
    * Insert key into the gap that remains
    
Loop invariant: At the start of each iteration of the outer loop, the subarray A[0..i−1] is sorted and contains the same elements as originally, just in sorted order. This invariant is:
- True initially (single element)
- Maintained by insertion
- Guarantees correctness at termination

###### Basic Implementation
<details>
<summary>Basic Implementation</summary>

```c
#include <stdio.h>

void insertion_sort(int arr[], int n);
void print_array(int arr[], int n);

int main(void) {
  int arr[] = {5, 2, 4, 6, 1, 3};

  int n = sizeof(arr) / sizeof(arr[0]);

  insertion_sort(arr, n);

  printf('Sorted array: ');
  print_array(arr, n);

  return 0;
}

void insertion_sort(int arr[], int n) {
  int i, key, j;
  for (i = 1; i < n; i++) {
    key = arr[i];
    j = i - 1;
    // Shifts elements greater than key to the right
    while (j >= 0 && arr[j] > key) {
      arr[j + 1] = arr[j];
      j = j - 1;
    }
    // Inserts key into proper location
    arr[j + 1] = key;
  }
}

void print_array(int arr[], int n) {
  for (int i = 0; i < n; i++)
    printf('%d ', arr[i]);

  printf('\n');
}
```

#### Analysis
Much real-world data is already partially sorted, so optimism and realism might
coincide to make Insertion Sort an effective algorithm to use. The efficiency of
Insertion Sort increases when duplicate items are present, since there are fewer
swaps to perform.

from Pesudocode above, The cost depends entirely on how many times the inner while-loop runs.


##### Time Complexity
The optimal performance occurs when the array is already sorted, and arrays sorted in reverse order produce the worst performance for Insertion Sort. If the array is already mostly sorted, Insertion Sort does well because there is less need to transpose elements.

**Why It’s Quadratic**

Insertion sort performs a number of inversions-based operations.
An inversion is a pair:
```
(i,j) such that i<j and A[i]>A[j] 
```
Insertion sort performs exactly as many shifts as there are inversions.
- Worst case: ~ n²/2 inversions
- Best case: 0 inversions
- Average case: ~ n²/4 inversions

This gives a deeper structural explanation of the complexity.

Insertion sort is fast when the number of inversions is small.

More inversions → more shifts → slower.

###### best case
the best case happens when the array is already sorted.

In the best case, each of the n items is in its proper place and thus Insertion Sort takes linear time, or O(n). 

Example:
```
[1, 2, 3, 4, 5, 6]
```
For each i, the condition A[j] > key fails immediately. So the inner loop runs only once per iteration.

**Counting operations**

1. Outer loop runs n-1 times.
2. Inner loop does 1 comparison each time.

Total: Θ(n)

This is why insertion sort is excellent for nearly sorted arrays.

This may seem to be a trivial point to raise (how often are you going to sort a set of already sorted elements?), but it is important because Insertion Sort is the only comparison-based sorting algorithm that has this best case behavior.

###### average case
Assume Input is a random permutation.

On average:
- The key will move halfway through the sorted prefix.
- About i/2 comparisons per iteration.

Total comparisons:
$$
\sum_{i=1}^{n-1} \frac{i}{2}
=
\frac{1}{2} \sum_{i=1}^{n-1} i
=
\frac{1}{2} \cdot \frac{n(n-1)}{2}
=
\frac{n(n-1)}{4}
$$
Which simplifies to: $Θ(n^2)$

Unfortunately, Insertion Sort is too conservative when all n items are distinct and the array is randomly organized (i.e., all permutations of the data are equally likely) because each item starts on average n/3 positions in the array from its final position.

In the average and worst case, each of the n items must be transposed a linear number of positions, thus Insertion Sort requires $Θ(n^2)$ quadratic time.

###### worst case
The worst case happens when the array is reverse sorted. Example:
```
[6, 5, 4, 3, 2, 1]
```
Each new element must move all the way to the front.

**Counting operations**

For each i, the key is compared with all i previous elements.

Number of comparisons:
```
1 + 2 + 3 + ... + (n-1)

```
This is: $\sum_{i=1}^{n-1} i = \frac{n(n-1)}{2}$

Which is: $Θ(n^2)$

| Case    | Condition      | Comparisons | Time Complexity |
| ------- | -------------- | ----------- | --------------- |
| Best    | Already sorted | ~ n         | Θ(n)            |
| Average | Random order   | ~ n²/4      | Θ(n²)           |
| Worst   | Reverse sorted | ~ n²/2      | Θ(n²)           |

##### Space Complexity
Insertion sort is In-place: O(1) extra space (or O(record_size) for value-based)
- No recursion
- No auxiliary arrays

Insertion Sort requires very little extra space to function; it only needs to reserve
space for a single element. 

For value-based representations, most language libraries
offer a block memory move function to make transpositions more efficient.


##### Stability
insertion sort is stable, Insertion sort does not move equal elements past each other. the Condition:
```
while A[j] > key
```
- If A[j] == key, the loop stops
- The earlier element stays first

**Example setup: duplicate keys with identities**

We’ll sort by key only, but each element has an ID so we can track order.
```
Input array (with identities)
Index:  0      1      2      3      4
A =   (3,A)  (1,B)  (3,C)  (2,D)  (3,E)
         ↑            ↑            ↑
        same key = 3, different identities
```
Desired sorted order by key:
```
(1,B), (2,D), (3,A), (3,C), (3,E)
```
Notice: A → C → E order preserved

**Stable Insertion Sort (correct)**
Key comparison
```c
while (j >= 0 && A[j].key > key)
```
Step-by-step trace
1. Pass i = 2 (key = (3,C))
```
Sorted prefix: (1,B), (3,A)
Compare (3,A) > (3,C)?  NO
→ stop
Insert after (3,A)
```
Result:
```
(1,B), (3,A), (3,C)
```
1. Pass i = 4 (key = (3,E))
```
Compare (3,C) > (3,E)? NO
Insert after (3,C)
```
Final:
```
(1,B), (2,D), (3,A), (3,C), (3,E)
```
Stable: relative order preserved
```
Before:
[ (3,A) ][ (3,C) ]

Comparison:
3 > 3 ?  false

After:
[ (3,A) ][ (3,C) ]
```
**Unstable version (classic exam trap)**

Change one character:
```c
while (j >= 0 && A[j].key >= key)
```
What goes wrong?

1. Pass i = 2 (key = (3,C))
```
Compare (3,A) >= (3,C)? YES
Shift (3,A) right
Insert (3,C) before (3,A)
```
Result:
```
(1,B), (3,C), (3,A)
```
Order reversed

Final result:
```
(1,B), (2,D), (3,E), (3,C), (3,A)
```
Unstable
```
Before:
[ (3,A) ][ (3,C) ]

Comparison:
3 >= 3 ? true

Shift:
[ (3,A) ][ (3,A) ]

Insert:
[ (3,C) ][ (3,A) ]
```

##### External-Memory Analysis
Insertion sort is a disk-based sorting algorithm that reads and writes data in blocks. It is similar to the in-memory insertion sort, but it is optimized for disk access. The algorithm works by reading a block of data from disk, sorting it in memory, and then writing it back to disk. This process is repeated until the entire file is sorted.

**Model Assumptions (External Memory Model)**
- Data stored in blocks of size B
- Total number of elements: n
- Each block contains B elements
- I/O cost measured in block transfers
- Disk access is much more expensive than RAM

Number of blocks:$\frac{n}{B}$

**Worst-Case Behavior on Disk**

Insertion sort shifts elements one-by-one.
Worst case:
- Each insertion may shift up to i elements
- Shifts may span multiple disk blocks
- Each shift may require reading + writing a block

Worst-case total element movements:
$\frac{n(n-1)}{2}$

Worst-case I/O cost (block level):
Each block holds B elements.
So:
$\text{I/O Cost}=\Theta(n^2/B)$ 

**Why This Is Bad**

Quadratic behavior becomes catastrophic on disk:
- Random access
- Repeated block rewrites
- Poor locality

Insertion sort is not I/O efficient.

**Comparison with External Merge Sort**

**External merge sort:**

$\Theta(\frac{n}{B} \times \log(\frac{M}{B}) \times \frac{n}{B})$ 

where:
- M = main memory size

This is dramatically better.

Best Case on Disk

If input is already sorted:
- Sequential scan only
- No block shifts

I/O cost:
$\Theta(n/B)$ 

So insertion sort is:
- Very good for nearly sorted disk data
- Terrible for random large datasets

🔎 Real Systems Mapping
| System       | Why insertion sort may be used    |
| ------------ | --------------------------------- |
| Databases    | Sorting small in-memory buffers   |
| OS           | Small scheduling queues           |
| Compilers    | Symbol tables with few entries    |
| Hybrid sorts | Used when partitions become small |

But for large disk-based datasets:  External merge sort is preferred.

#### Value-based Sorting
There are two storage models:
1. Pointer-based: Array stores pointers:
```
[ p1 ][ p2 ][ p3 ]
```
Sorting swaps pointers only.

2. Value-based: Array stores actual records:
```
[ record1 ][ record2 ][ record3 ]
```
Sorting must move the entire record in memory.

Example:
```c
typedef struct {
    int id;
    char name[50];
    double salary;
} Employee;

Employee arr[1000];
```
Each element might be 64 bytes or more.
Now shifting one element means copying all 64 bytes.

Algorithmically, insertion sort is unchanged:
```
for i = 1 to n-1
    key = A[i]
    shift larger elements right
    insert key
```
But for value-based storage:
- You copy full records
- You use memmove
- Memory cost dominates runtime

Suppose each record is 16 bytes:
```
| rec0 | rec1 | rec2 | rec3 |
```
When inserting rec2:
1. Copy rec2 into temporary buffer
2. Shift rec1 right (16 bytes)
3. Insert rec2
```
B:
[ rec0 ][ rec1 ][ rec2 ][ rec3 ]

Insert rec2:
           ↓ copy to key
[ rec0 ][ rec1 ][ rec1 ][ rec3 ]
               ↑ memmove
[ rec0 ][ rec2 ][ rec1 ][ rec3 ]
```
So every shift = block copy.

| Property      | Value                          |
| ------------- | ------------------------------ |
| Storage model | Value-based (record blocks)    |
| In-place      | Yes (O(s) extra space)         |
| Stable        | Yes                            |
| Best case     | Θ(n)                           |
| Worst case    | Θ(n²)                          |
| Disk-friendly | Reasonable (sequential access) |

###### Solution

####### C Language

When A is represented using value-based storage, it is packed into n rows of a fixed element size of s bytes. Manipulating the values requires a comparison function as well as the means to copy values from one location to another. 

Following code shows a suitable C program that uses memmove to transfer the underlying bytes efficiently for a set of contiguous entries in A.

What this code sorts:
- Contiguous block of memory
- n records
- Each record has fixed size elem_size
- Ordering decided by a comparator cmp

In insertion sort, elements are shifted within overlapping regions; therefore memmove must be used instead of memcpy.

During insertion sort, memory regions overlap:
```
Before shift:
| A[j] | A[j+1] | key |

After shift:
| A[j] | A[j]   | key |
```
- memcpy → undefined behavior, 
- memmove → guaranteed safe, memmove used to shift elements safely,

```c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>
#include <string.h>

#define STR_SIZE 5

void insertion_sort_value(void *base, int n, int s,
		 int(*cmp)(const void *,const void *));

int str_cmp(const void *a, const void *b) {
    return strncmp(a, b, STR_SIZE);
}

int main(void) {
    char words[][STR_SIZE] = {
        "eagl",
        "cat\0",
        "ant\0",
        "dog\0",
        "ball"
    };

    int n = sizeof(words) / sizeof(words[0]);

    insertion_sort_value(words, n, STR_SIZE, str_cmp);

    for (int i = 0; i < n; i++)
        printf("%s\n", words[i]);

    return 0;
}

/** Sort the value-based array using Insertion Sort. */
void insertion_sort_value(void *base, int n, int s,
		 int(*cmp)(const void *,const void *)) {
  int j;
  void *saved = malloc (s);
  for (j = 1; j < n; j++) {
    /* start at end, work backward until smaller element or i < 0. */
    int i = j-1;
    void *value = base + j*s;
    while (i >= 0 && cmp(base + i*s, value) > 0) { i--; }

    /* If already in place, no movement needed. Otherwise save value to be
     * inserted and move as a LARGE block intervening values.  Then insert
     * into proper position. */
    if (++i == j) continue;

    memmove (saved, value, s);
    memmove (base+(i+1)*s, base+i*s, s*(j-i));
    memmove (base+i*s, saved, s);

  }
  free (saved);
}

```

while (cmp(B + j*elem_size, key) > 0)

```c
void insertion_sort_value_1(void *base, size_t n, size_t elem_size,
                            int (*cmp)(const void *, const void *)) {
  unsigned char *B = base;
  unsigned char *key = malloc(elem_size);
  if (!key)
    return;

  for (size_t i = 1; i < n; i++) {
    /* copy B[i] into key */
    memcpy(key, B + i * elem_size, elem_size);

    ssize_t j = i - 1;

    /* shift larger elements to the right */
    while (j >= 0 && cmp(B + j * elem_size, key) > 0) {

      memmove(B + (j + 1) * elem_size, B + j * elem_size, elem_size);
      j--;
    }

    /* insert key */
    memcpy(B + (j + 1) * elem_size, key, elem_size);
  }

  free(key);
}
```

###### Complexity
Time Complexity (Still the Same Asymptotically)

Algorithmic complexity does not change:

| Case    | Time  |
| ------- | ----- |
| Best    | Θ(n)  |
| Average | Θ(n²) |
| Worst   | Θ(n²) |
BUT… Each shift costs Θ(record_size) bytes. So actual work becomes: Θ(n2⋅s)

Where:
- s = size of each record in bytes

If records are large, performance drops dramatically.

Value-based insertion sort has:
- Excellent cache locality
    * Sequential memory access
    * CPU cache friendly
- Large memory traffic
    * Big records mean heavy copying

If records are on disk:
- Worst-case shifts: n(n−1)/2
- Block transfers: Θ(n^2/B) 

Very inefficient for large datasets.

Insertion sort cost is proportional to:
$$
\text{# inversions} \times \text{record size}
$$

So performance depends on:
- Disorder level
- Memory layout
- Record width

Insertion sort for value-based data:
- Same algorithmic structure
- Physically moves full records
- Stable
- In-place
- Adaptive
- Cache-friendly
- Quadratic worst-case
- Poor for large disk-based data

Value-Based Insertion Sort is ideal when:
- Data fits in RAM
- Array is small
- Array is nearly sorted
- Records are small
- Used inside hybrid algorithms

Example:
- Sorting small partitions in quicksort
- TimSort short runs
- In-memory database buffers

Insertion Sort operates inefficiently for value-based data because of the amount of
memory that must be shifted to make room for a new value.

###### Why Value-Based Sorting Is Dangerous
When records are large:
- **Swapped key field only, not full struct**
- **memcpy incorrectly**
- **Overlapping copy corrupted adjacent entries**
- **Pointers swapped but backing data not updated**
- **Clients desynchronized**

### Real Production Bugs
#### Java Comparator Contract Violation
In Java, Comparator must be:
- Transitive
- Anti-symmetric
- Consistent with equals
Bad comparator example:
return a.age - b.age;
Overflow can break ordering.
Real consequence:
- Arrays.sort() throws IllegalArgumentException
- TimSort detects comparator cycles
Seen in:
- Android bug reports
- Financial trading systems

In C++ std::sort requires strict weak ordering.
Comparator returning inconsistent results caused:
- Infinite loops
- Segmentation faults
Observed in:
- High-frequency trading code
- Game engines
