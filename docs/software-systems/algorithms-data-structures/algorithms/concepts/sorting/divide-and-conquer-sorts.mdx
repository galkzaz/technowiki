**Divide-and-Conquer (D&C)** is a problem-solving paradigm used heavily in sorting.

**Divide-and-Conquer sorting** is a general paradigm that divides a problem, solves subproblems, and combines results.

**Core structure:**
```
Divide → Conquer → Combine
```
Meaning:
1. **Divide**: Break the array into smaller subarrays
2. **Conquer**: Recursively sort those subarrays
3. **Combine**: Merge results into a final sorted array

Two ways to "divide" in D&C sorting:

1. **Structural Division (Merge Sort)**
    - Divide by index (middle)
    - Data is not rearranged initially
    - Fix happens in combine phase

2. **Value-Based Division (Partitioning)**
    - Divide by value (pivot)
    - Data is rearranged immediately
    - No combine phase needed

We can classify sorting algorithms:
```
Divide-and-Conquer Sorts
│
├── Merge-Based (need combine step)
│   └── Merge Sort
│
└── Partition-Based (no combine step)
    └── Quick Sort
```

## Partition-Based Sorting

**(Partition-Based Sorting** is a core algorithmic paradigm where an array is rearranged (partitioned) around a **pivot** element, and then sorting is achieved by recursively applying the same idea to subarrays.

This idea is most famously used in **Quicksort**, but the partitioning technique itself appears in many algorithms (selection, median finding, etc.).

### Core Idea
The fundamental operation is: Partition the array so that:
- `Elements < pivot` go to the left
- `Elements > pivot` go to the right
- Pivot ends up in its final sorted position

After one partition step:
```
[ smaller elements | pivot | larger elements ]
```
Then recursively:
- Sort left part
- Sort right part

**Why Partition-Based Sorting Works**

Key invariant after partition:
```
Left side ≤ pivot ≤ Right side
```
This guarantees:
- Pivot is in final sorted position
- Subproblems are independent

<!--A **partition-based sort** is a **Divide-and-Conquer** algorithm where the divide step rearranges the array such that no combine step is needed.-->
A **partition-based sort** is a specialized form of **Divide-and-Conquer** where the division step rearranges the array around a pivot, eliminating the need for a combine step.

The Combine Step is the Key Differentiator

Merge Sort:
- Heavy combine step
- Must merge arrays → O(n)

Quick Sort:
- No combine step
- Work is done during partition

This leads to the key classification: Partition-Based Sorting (Special Case of D&C)

How Quick Sort Fits: Step-by-step:
1. Partition
    ```
    [ elements < pivot | pivot | elements > pivot ]
    ```
2. Pivot is already in final position
3. Recursively sort:
    - Left subarray
    - Right subarray
4. No merge required

Partition-based sorting introduces a powerful reusable pattern: Partition Pattern:
- Choose pivot
- Rearrange elements
- Return pivot index

Used in:
- Quick Sort
- Quickselect
- Median of medians
- Dutch National Flag

## Merge Sort
If we have a big list to sort, we can split it into halves: each half list becomes a sorting subproblem. To sort the big list, subproblem solutions (i.e., the sorted halves) can be merged in a single list using the merge algorithm. But how will we sort our two subproblems? They are themselves split into subsubproblems, sorted and merged. The new subsubproblems will also be split, sorted, and merged. The splitting continues until we hit the base case: a one-item list. A one-item list is already sorted!

Merge Sort is the textbook example of
Divide and Conquer. It breaks a list into individual elements (Divide), sorts them by merging (Conquer), and builds the final sorted list (Combine).

Idea:
 - Split array into halves
 - Recursively sort
 - Merge sorted halves

All D&C sorts follow:
$$
 T(n) = aT(n/b) + f(n)
$$
Where:
- a = number of subproblems
- n/b = size of each
- f(n) = cost of divide + combine

Examples:
| Algorithm  | Recurrence             | Key Cost       |
| ---------- | ---------------------- | -------------- |
| Merge Sort | 2T(n/2) + O(n)         | Merge step     |
| Quick Sort | T(k) + T(n-k-1) + O(n) | Partition step |

### Core Idea (Divide and Conquer)

* Divide: Split the array into two halves
* Conquer: Recursively sort each half
* Combine: Merge the two sorted halves into a single sorted array

### Psuedocode
``` [Psuedocode]
function merge_sort(list)
  if list.length = 1
    return list
  left ← list.first_half
  right ← list.last_half
  return merge(merge_sort(left), merge_sort(right))
```

### Visual recursion-tree explanation 
Think of Merge Sort as a tree growing downward, then collapsing upward.
1. Top level (original problem)
[8, 3, 5, 4, 7, 6, 1, 2]
2. Level 1
[8, 3, 5, 4]        [7, 6, 1, 2]
3. Level 2
[8, 3]   [5, 4]     [7, 6]   [1, 2]
4. Level 3 (leaves)
[8] [3] [5] [4]     [7] [6] [1] [2]

This is the divide phase — the tree grows downward.

Now the tree collapses upward:
- Leaves merge into size-2 arrays
- Size-2 arrays merge into size-4
- Size-4 arrays merge into size-8

Each level does:
-Linear work (merging)
- Over log n levels

That's where the famous O(n log n) comes from.

### Steps
**Phase 1: The 'Divide' Stage (Top-Down)**

The algorithm recursively splits the array in half until each sub-array contains only one element. A single element is considered 'sorted' by default.
|     |     |     |     |
| --- | --- | --- | --- |
| Level	 | Left Sub-array	 | Right Sub-array	 | Action |
| 1	 | [38, 27, 43, 3]	 | [9, 82, 10]	 | Split original array in half |
| 2 (Left)	 | [38, 27]	 | [43, 3]	 | Split the left half |
| 2 (Right)	 | [9, 82]	 | [10]	 | Split the right half |
| 3 (Final)	 | [38], [27], [43], [3]	 | [9], [82], [10]	 | All elements are now isolated |

**Step 2: Conquer (Sort Base Cases)**

Subarrays of length 1 are already sorted: [38], [27], [43], [3], [9], [82], [10]

Now, the algorithm merges the small pieces back together. During the merge, it compares the front elements of each list and places the smaller one first.

**Step 3: Merging individual elements into pairs**
|     |     |
| --- | --- |
| Merging Elements	 | Resulting Sorted Sub-array |
| [38] and [27]	 | [  27, 38] | 
|[43] and [3]	 | [3, 43] | 
|[9] and [82]	 | [9, 82] | 
|[10] and [10]	 | [10, 10] |

**Step 3: Merging pairs into larger blocks**

To merge [27, 38] and [3, 43], the engine compares 27 vs 3 (picks 3), then 27 vs 43 (picks 27), then 38 vs 43 (picks 38).
|     |     |
| --- | --- |
| Merging Sub-arrays	 | Resulting Sorted Sub-array |
| [27, 38] and [3, 43]	 | [3, 27, 38, 43] |
| [9, 82] and [10]	 | [9, 10, 82] |

**Step 4: The Final Merge (Global Solution)**

This final 'Combine' step merges the two remaining halves to produce the final sorted array.
|     |     |     |     |
| --- | --- | --- | --- |
| Left | Right Index	 | Comparison	 | Winner to Result Array |
| 27	 | 3	 | 3 &lt; 27	 | [3] |
| 27	 | 9	 | 9 &lt; 27	 | [3, 9] |
| 27	 | 10	 | 10 &lt; 27	 | [3, 9, 10] |
| 27	 | 82	 | 27 &lt; 82	 | [3, 9, 10, 27] |
| 38	 | 82	 | 38 &lt; 82	 | [3, 9, 10, 27, 38] |
| 43	 | 82	 | 43 &lt; 82	 | [3, 9, 10, 27, 38, 43] |
| End | 82	 | Remainder	 | [3, 9, 10, 27, 38, 43, 82] |

###  time complexity
To do this, 
1. Counting operations: we're first going to count the operations generated by each individual split step.
    * Say we have a big list of size n. When called, the `merge_sort` function performs the following operations:
        * Splits list in halves, which does not depend on list size: O(1),
        * A merge: we recall from sec. 3.1 that merge is O(n),
        * Two merge_sort recursive calls that are not counted(Operations performed by recursive calls are counted in the next split step!).
    * Since we keep the strongest term and don't count recursive calls, the time complexity of the function is O(n). 
    * Let's now count the time complexity of each split step:
        * Split step 1. The merge_sort function is called for a list of n items. The time complexity of this step is O(n).
        * Split step 2. The merge_sort function is called twice, each time for n/2 items. We find 2 × O(n/2) = O(n).
        * Split step 3. The merge_sort function is called four times, each time for n/4 items: 4 × O(n/4) = O(n).
        * Split step x. The merge_sort function is called 2x times, each for a list of n/2x items: 2x × O(n/2x) = O(n).
      * The split steps all have the same complexity of O(n). Merge Sort's time complexity is thus x × O(n), where x is the number of split steps necessary for its full execution(We can't ignore x because it's not a constant. If the list size n doubles, you'll need one more split step. If n quadruples, you'll need two more split steps.).
2. Counting Steps: Then, we'll count how many split steps there are in total.
    * How do we evaluate x? We know recursive functions stop to call themselves once they hit their base case. Our base
    case is a one-item list. We've also seen that split step x works on lists of n/2x items. Therefore:
      $$
      \frac{n}{2^x} = 1 → 2^x = n → x = \log_2 n.
      $$
    * Any process that reduces an input step-by-step, dividing it by a constant factor in each step, takes a logarithmic number of steps to fully reduce the input.

Merge Sort's time complexity is thus $(log_2 n \times O(n)) = O(n log n)$.

That's a huge improvement over the O(n2) Selection Sort. Do you
remember the performance gap between log-linear and quadratic
algorithms we've seen last chapter in fig. 2.4? Even if a faster computer crunches the O(n2) algorithm, it will end up slower than a computer crunching the O(n log n) algorithm:

See how slowly the number of required split steps increases12 with
the total number of items to sort:

| Input size (n) | log₂ n | Split steps required |
| --------------- | ------ | -------------------- |
| 10              | 3.32   | 4                    |
| 100             | 6.64   | 7                    |
| 1,024           | 10.00  | 10                   |
| 1,000,000       | 19.93  | 20                   |
| 1,000,000,000   | 29.89  | 30                   |

For big inputs, O(n log n) algorithms in slow computers are much faster than O(n2) algorithms in 1000× faster computers.
| Input Size | Quadratic | Log-linear |
| --- | --- | --- |
| 196 (countries in the world) | 38 ms | 2 s |
| 44K (airports in the world) | 32 min | 12 min |
| 171K (English dictionary words) | 8 hours | 51 min |
| 1M (inhabitants of Hawaii) | 12 days | 6 hours |
| 19M (inhabitants of Florida) | 11 years | 6 days |
| 130M (books ever published) | 500 years | 41 days |
| 4.7G (web pages of the Internet) | 700K years | 5 years |

  #include <stdio.h>

  void merge(int arr[], int l, int m, int r) {
      int n1 = m - l + 1;
      int n2 = r - m;

      int L[n1], R[n2];

      for (int i = 0; i < n1; i++)
          L[i] = arr[l + i];
      for (int j = 0; j < n2; j++)
          R[j] = arr[m + 1 + j];

      int i = 0, j = 0, k = l;

      while (i < n1 && j < n2) {
          if (L[i] <= R[j])
              arr[k++] = L[i++];
          else
              arr[k++] = R[j++];
      }

      while (i < n1)
          arr[k++] = L[i++];

      while (j < n2)
          arr[k++] = R[j++];
  }

  void mergeSort(int arr[], int l, int r) {
      if (l < r) {
          int m = l + (r - l) / 2;
          mergeSort(arr, l, m);
          mergeSort(arr, m + 1, r);
          merge(arr, l, m, r);
      }
  }

  int main() {
      int arr[] = {38, 27, 43, 3, 9, 82, 10};
      int n = sizeof(arr) / sizeof(arr[0]);

      mergeSort(arr, 0, n - 1);

      for (int i = 0; i < n; i++)
          printf('%d ', arr[i]);

      return 0;
  }

  def merge_sort(arr):
      if len(arr) <= 1:
          return arr

      mid = len(arr) // 2
      left = merge_sort(arr[:mid])
      right = merge_sort(arr[mid:])

      return merge(left, right)

  def merge(left, right):
      result = []
      i = j = 0

      while i < len(left) and j < len(right):
          if left[i] <= right[j]:
              result.append(left[i])
              i += 1
          else:
              result.append(right[j])
              j += 1

      result.extend(left[i:])
      result.extend(right[j:])
      return result

  arr = [38, 27, 43, 3, 9, 82, 10]
  sorted_arr = merge_sort(arr)
  print(sorted_arr)

  fn merge_sort(arr: &mut Vec<i32>) {
      let n = arr.len();
      if n <= 1 {
          return;
      }

      let mid = n / 2;
      let mut left = arr[..mid].to_vec();
      let mut right = arr[mid..].to_vec();

      merge_sort(&mut left);
      merge_sort(&mut right);

      merge(arr, &left, &right);
  }

  fn merge(arr: &mut Vec<i32>, left: &Vec<i32>, right: &Vec<i32>) {
      let mut i = 0;
      let mut j = 0;
      let mut k = 0;

      while i < left.len() && j < right.len() {
          if left[i] <= right[j] {
              arr[k] = left[i];
              i += 1;
          } else {
              arr[k] = right[j];
              j += 1;
          }
          k += 1;
      }

      while i < left.len() {
          arr[k] = left[i];
          i += 1;
          k += 1;
      }

      while j < right.len() {
          arr[k] = right[j];
          j += 1;
          k += 1;
      }
  }

## Quick Sort

## Compare Merge Sort vs Quick Sort
Merge Sort
- Splits the array evenly
- Does the hard work during merge
- Tree shape is predictable and balanced

Quick Sort
- Splits based on a pivot
- Does the hard work during partition
- Tree shape depends on how good your pivot is

Same Divide & Conquer family, very different personalities.
| Feature         | Merge Sort       | Quick Sort             |
| --------------- | ---------------- | ---------------------- |
| Paradigm        | Divide & Conquer | Divide & Conquer       |
| Division method | Split in halves  | Partition around pivot |
| Combine step    | Required (merge) | Not needed             |
| Space           | O(n)             | O(1)                   |
| Stability       | Stable           | Not stable             |
| Worst-case      | O(n log n)       | O(n²)                  |

### Merge Sort recursion tree
Example array:
[8, 3, 5, 4, 7, 6, 1, 2]
```
Divide phase (always balanced)
                [8 3 5 4 7 6 1 2]
               /                 \
        [8 3 5 4]               [7 6 1 2]
         /       \               /       \
     [8 3]      [5 4]         [7 6]      [1 2]
     /   \      /   \         /   \      /   \
   [8]  [3]   [5]  [4]      [7]  [6]   [1]  [2]
```
- Height of tree ≈ log n
- Every level processes all elements
- Shape never changes, no surprises

Combine phase (bottom-up)

Each level merges sorted arrays.

That's why:
- Work per level = O(n)
- Number of levels = O(log n)
- Total = O(n log n)

always Guaranteed.

### Quick Sort recursion tree (good pivot)
Same array, assume a good pivot (close to median).
```
                [8 3 5 4 7 6 1 2]
                      |
                    pivot = 5
                      |
          --------------------------------
          |                              |
      [3 4 1 2]                    [8 7 6]
           |                            |
        pivot = 3                   pivot = 7
           |                            |
     -----------                   ----------
     |         |                   |        |
   [1 2]      [4]                [6]       [8]
```
- Still roughly balanced
- Tree height ≈ log n
- Partitioning at each level costs O(n)
- So in the best/average case: Quick Sort = O(n log n)

### Quick Sort recursion tree (bad pivot)
Now imagine always picking the smallest or largest element as pivot.
```
[1 2 3 4 5 6 7 8]

pivot = 1

[ ]   [2 3 4 5 6 7 8]
        pivot = 2

[ ]   [3 4 5 6 7 8]
          pivot = 3
...
```
Tree becomes a chain:
```
height = n
work per level = n
total = O(n²)
```
This never happens to Merge Sort.

**Why Quick Sort is often faster in practice**

Even though Merge Sort has a guaranteed bound, Quick Sort often wins because:
- No extra merging arrays
- Better cache locality
- Less constant overhead
- Most pivots are "good enough"

It's a classic theoretical vs practical trade-off.

### Comparison Table
| Aspect       | Merge Sort         | Quick Sort           |
| ------------ | ------------------ | -------------------- |
| Split        | Always in half     | Based on pivot       |
| Tree shape   | Always balanced    | Depends on pivot     |
| Worst case   | O(n log n)         | O(n²)                |
| Average case | O(n log n)         | O(n log n)           |
| Extra memory | Needs extra arrays | In-place             |
| Stability    | Stable             | Not stable (usually) |

**Tree intuition summary**

Merge Sort: "Perfect tree every time. I'll pay the merge cost."

Quick Sort: "Let me gamble on a pivot. If I win, I'm fast. If I lose, it hurts."

That recursion tree picture explains everything about their behavior.
