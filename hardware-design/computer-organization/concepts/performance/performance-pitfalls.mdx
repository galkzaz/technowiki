## Pitfall: Using one factor of the performance equation as a performance metric
There is a reliable method of determining and reporting performance by using
the execution time of real programs as the metric. This execution time is related to
other important measurements we can make by the following equation

$$
\text{Time(Seconds/Program)}=\frac{\text(Instructions)}{\text{Program}} \times \frac{\text{Clock cycles}}{\text{Instruction}} \times \frac{\text{Seconds}}{\text{Clock cycle}}
$$

More compactly:
$$
\text{Execution Time} = \text{IC} \times \text{CPI} \times \text{Clock Cycle}
$$
Or:
$$
\text{Execution Time} = \frac{\text{IC} \times \text{CPI}}  {\text{Clock Rate}}
$$
Individually the factors do not determine performance: only the product, which equals execution time, is a reliable measure of performance.

🔎 What Each Term Means
1️⃣ Instruction Count (IC)
Number of instructions executed by the program.
Depends on:
- Algorithm
- Compiler
- ISA

2️⃣ CPI (Cycles Per Instruction)
Average number of clock cycles per instruction.
Depends on:
- Pipeline design
- Cache misses
- Branch prediction
- Out-of-order execution

3️⃣ Clock Cycle (or Clock Rate)
Clock cycle = 1 / Clock frequency.
Depends on:
- Technology
- Pipeline depth
- Voltage
- Circuit design

🎯 Why This Equation Is So Important
Because it shows:
Performance is NOT just clock speed.
All three factors matter.

🧠 How It Connects to Earlier Topics
This equation explains:
🔹 Why MIPS is misleading
MIPS ignores Instruction Count.
🔹 Why clock speed alone is misleading
High GHz doesn’t guarantee low CPI.
🔹 Why Amdahl’s Law works
Amdahl describes improvements to parts of IC or CPI.

📊 Simple Example
Suppose:
IC = 1 billion
CPI = 2
Clock = 2 GHz
  Execution Time=2B1B×2​=1 second 

Now improve CPI to 1.5:
  Execution Time=2B1B×1.5​=0.75 seconds 
25% faster.

Now increase clock to 3 GHz instead:
  Execution Time=3B1B×2​=0.67 seconds 
33% faster.

🔥 Deep Insight
Each term corresponds to a design domain:
Term	Controlled By
IC	Algorithm, Compiler, ISA
CPI	Microarchitecture
Clock	Circuit design
This is why computer architecture sits between:
- Software
- Hardware circuits

🧩 Why Execution Time Is the Only Safe Metric
Because it includes:
- Instruction count
- CPI
- Clock rate
Any metric that ignores one of these (like MIPS) can mislead.
That’s why standardized benchmarks like
SPEC CPU 2017
report normalized execution time.

🟢 Clean Summary
  Execution Time=IC×CPI×Clock Cycle​ 
This equation:
- Connects hardware and software
- Explains performance tradeoffs
- Justifies Amdahl’s Law
- Prevents performance fallacies

Execution time is the only valid and unimpeachable measure of
performance. Many other metrics have been proposed and found wanting.
Sometimes these metrics are flawed from the start by not reflecting
execution time; other times a metric that is sound in a limited context
is extended and used beyond that context or without the additional
clarification needed to make it valid.

That means:
👉 The best way to judge how fast a computer is… is to measure how long it takes to run real programs.

Why execution time is the "gold standard"
Performance is fundamentally about how long a program takes to finish.
If Computer A runs a program in 2 seconds and Computer B takes 4 seconds, A is twice as fast. That’s clear, direct, and meaningful.
Nothing else matters more than:
Execution time = total time to complete the program

Why other metrics can be misleading
Other measurements (like MIPS, clock rate, etc.) try to estimate performance indirectly. They often fail for one of two reasons:
1️⃣ They don’t actually measure time
For example:
- MIPS (Millions of Instructions Per Second)
Sounds good — more instructions per second must mean faster, right?
❌ Not necessarily.
Some machines use:
- Fewer, powerful instructions
- Others use many simple instructions
So one machine might have a lower MIPS but still finish the program faster.

2️⃣ They’re valid in limited contexts — but get misused
Some metrics are meaningful only under specific conditions.
For example:
- CPI (Cycles Per Instruction) is useful
- Clock rate is useful
- Instruction count is useful
But none of them alone determines performance.
That’s why we use the full equation:
  Cycles CycleExecution Time=ProgramInstructions​×InstructionClock Cycles​×Clock CycleSeconds​ 
In simpler terms:
Execution Time = Instruction Count × CPI × Clock Cycle Time
All three matter together.

The key idea
A computer can:
- Increase clock rate but increase CPI
- Reduce CPI but increase instruction count
- Increase MIPS but run slower overall
Only execution time tells you the real truth.

Why this matters
If engineers optimize the wrong metric (like MIPS), they may:
- Think they improved performance
- Actually make the program slower
This is why the text calls execution time "unimpeachable" — meaning:
- It cannot be argued against
- It directly measures what we care about

**Analogy**

🍳 Cooking Analogy
Imagine two chefs making the same dish.
We care about:
How long until the dish is ready?
That’s execution time.

🍽 Chef A
- Does 100 cooking steps
- Each step takes 1 minute
- Total time = 100 minutes
🍽 Chef B
- Does 200 smaller steps
- Each step takes 20 seconds
- Total time = 67 minutes

Now imagine someone says:
"Chef B is worse! He does fewer big steps per minute!"
That’s like using MIPS.
Chef B might:
- Do more steps
- Or fewer steps per minute
- Or work differently
But none of that matters.
What matters is:
👉 Who finishes first?
Chef B wins because the total cooking time is shorter.

| CPU Term                     | Cooking Analogy                                  | Explanation                                          |
| ---------------------------- | ------------------------------------------------ | ---------------------------------------------------- |
| Instruction Count (IC)       | Number of cooking steps                          | More steps = more work to do                         |
| CPI (Cycles Per Instruction) | Time per step                                    | How long each step takes depends on chef skill/tools |
| Clock Cycle Time             | Timer granularity or efficiency of each "action" | Faster tools (oven, knife) reduce time per step      |
| Execution Time               | Total cooking time                               | What really matters — when the dish is ready         |
Example:
- Chef A: 100 steps × 1 min per step → 100 min
- Chef B: 200 steps × 0.33 min per step → 66 min
Even though Chef B does more steps, total time is less because each step is faster.

🚗 Driving Analogy
Imagine you’re driving 100 km.
We care about:
How long until you arrive?
Not:
- How many gear shifts per minute
- How many wheel rotations per second
- How many pedal presses per hour
Those are like MIPS, clock rate, CPI — internal activity measurements.

🚘 Car A
- Engine spins very fast
- Shifts gears constantly
- Very high "activity"
But it takes 2 hours to arrive.
🚘 Car B
- Engine spins slower
- Fewer gear shifts
- Lower "activity"
But it takes 1.5 hours to arrive.
Which car is better?
The one that arrives faster.

| CPU Term               | Driving Analogy                             | Explanation                                           |
| ---------------------- | ------------------------------------------- | ----------------------------------------------------- |
| Instruction Count (IC) | Number of "actions" needed to finish 100 km | Gear shifts, turns, stops — total work to get there   |
| CPI                    | Time per action                             | How long each maneuver takes                          |
| Clock Cycle Time       | Vehicle responsiveness                      | Faster car or smoother engine reduces time per action |
| Execution Time         | Total travel time                           | What passengers care about — when you arrive          |

Example:
- Car A: 100 maneuvers × 1.2 min per maneuver → 120 min
- Car B: 120 maneuvers × 0.7 min per maneuver → 84 min
Car B does more maneuvers, but total trip is faster.

## Pitfall: Using a subset of the performance equation as a performance metric
Another common mistake is to use only two of the three factors to compare performance. Although using two of the three factors may be valid in a limited context, the concept is also
easily misused. Indeed, nearly all proposed alternatives to the use of time as the
performance metric have led eventually to misleading claims, distorted results, or
incorrect interpretations.

The full CPU performance equation is:
  Execution Time=IC×CPI×Clock Cycle 
Or equivalently:
 Performance=Execution Time1​ 
If you ignore any one of these three:
- Instruction Count (IC)
- CPI
- Clock rate
You can easily be misled.

🚨 Why This Is Dangerous
Because performance depends on all three together.
Changing one factor often affects the others.

⚠️ Classic Example: MIPS
MIPS = Million Instructions Per Second
$$
\text{MIPS}=\frac{Clock Rate​}{CPI \times 10^6}
$$
Notice what is missing?
👉 Instruction Count (IC)
MIPS measures how fast instructions are executed,
not how many instructions are required.

🔎 Why MIPS Can Mislead
Imagine two processors running the same task.

Machine A
- Clock = 4 GHz
- CPI = 2
- IC = 1 billion
Execution time:
$$
T=\frac{1B \times 2}{4B}=0.5 \text{seconds}
$$
MIPS:
$$
\frac{4 B}{2} = 2000 \text{MIPS}
$$

Machine B
- Clock = 3 GHz
- CPI = 1
- IC = 1.2 billion
Execution time:
$$
T=\frac{1.2B \times 1}{3B}=0.4 \text{seconds}
$$
MIPS:
$$
\frac{3B}{1} = 3000 \text{MIPS}
$$

Result:
Machine B has higher MIPS and is faster.
So far fine.
But now watch this.

🔥 The Real Problem: Different Instruction Sets
Suppose:
- Machine C uses complex instructions
- It needs fewer instructions (IC smaller)
- But CPI is higher
MIPS might be lower…
Yet execution time may be shorter.
So a machine with lower MIPS can run programs faster.
That completely breaks the intuition that:
"Higher MIPS means faster."

There are three problems with using MIPS as a measure for comparing computers:
MIPS?
 MIPS=CPI×106Clock Rate​ 
It measures:
How many million instructions per second are executed.
It does NOT measure how long the program takes.
That’s the root problem.

🚨 Problem 1: Different Instruction Sets
MIPS ignores instruction complexity.
Two machines may solve the same problem but:
- Machine A needs 1 billion instructions
- Machine B needs 500 million instructions
Even if both have the same MIPS rating,
the one using fewer instructions may finish faster.
This is why we cannot compare:
- x86 vs ARM
- CISC vs RISC
Using MIPS alone.
Different ISAs require different instruction counts.
That’s why benchmarks like
SPEC CPU 2017
compare execution time instead.

🚨 Problem 2: MIPS Changes Per Program
From:
 MIPS=CPI×106Clock Rate​ 
Clock rate is fixed for a CPU.
But CPI varies depending on:
- Memory behavior
- Branch behavior
- Instruction mix
- Cache misses
So MIPS varies between programs.
Example:
Suppose:
Clock = 3 GHz
Program A:
CPI = 1
MIPS=3000 
Program B:
CPI = 5
MIPS=600 
Same machine. Huge difference.
So a machine cannot have a single "MIPS rating".
In fact, in SPEC CPU2006 measurements on
Intel Core i7,
CPI varied by a factor of 5 across benchmarks.
Therefore MIPS varied by factor of 5 as well.

🚨 Problem 3 (Most Important): MIPS Can Increase While Performance Decreases
This is the most dangerous case.
Suppose a new compiler:
- Uses more instructions
- But each instruction is simpler and faster
So:
- CPI decreases
- Instruction count increases
From formula:
MIPS=CPIClock​ 
If CPI decreases → MIPS increases.
But execution time depends on:
 Execution Time=IC×CPI/Clock 
If IC increases a lot, execution time may increase.
So you can get:
- Higher MIPS
- Worse performance
That completely breaks intuition.

🔥 Numerical Example
Old version:
IC = 1 billion
CPI = 2
Clock = 2 GHz
Execution time:
 second=(1B×2)/2B=1 second 
MIPS:
=2000/2=1000 

New version:
IC = 2 billion
CPI = 1
Clock = 2 GHz
Execution time:
 second=(2B×1)/2B=1 second 
Performance same.
But MIPS:
=2000/1=2000 
MIPS doubled.
Performance did NOT improve.
Even worse cases are possible where:
MIPS increases
but execution time gets worse.

🎯 The Core Lesson
MIPS ignores instruction count.
Performance depends on:
IC×CPI×Clock 
MIPS only includes:
Clock/CPI 
So it tells only part of the story.

🧠 Why This Matters in Architecture
This pitfall is emphasized in
Computer Organization and Design
Because historically:
- Vendors advertised high MIPS numbers
- Consumers assumed higher MIPS = faster
- That was often false
Today we use:
- Execution time
- SPEC benchmarks
- Performance per watt
Instead.

🟢 Clean Summary of the Three Problems
- Cannot compare different ISAs
- MIPS changes across programs
3️⃣ MIPS can increase even when performance does not
Therefore:
MIPS is not a reliable performance metric.
Only execution time for real programs is trustworthy.

🎯 Why Time Is the Only Reliable Metric
Time includes:
- Instruction count
- CPI
- Clock
All together.
That’s why:
Execution time is the only correct performance metric.
This is emphasized in
Computer Organization and Design

⚡ Other Partial Metrics That Mislead
- Clock Rate Alone
Higher GHz ≠ faster machine
(because CPI and IC differ)
- CPI Alone
Lower CPI ≠ faster
(if clock rate is lower)
3️⃣ Instruction Count Alone
Fewer instructions ≠ faster
(if CPI or clock changes)

🧠 Real-World Example
In the early 2000s:
- Some CPUs marketed very high GHz
- But had deep pipelines and high CPI
- Competitors with lower GHz sometimes ran real programs faster
This is why raw clock speed marketing eventually disappeared.
Companies like:
- Intel
- AMD
Shifted to talking about overall benchmark performance instead.

📊 The Correct Way to Compare
Always compare:
     Execution Time for the SAME program 
Or use standardized benchmarks like:
- SPEC CPU 2017
Which report normalized execution time.

🟢 The Deep Lesson
If you use only a subset of the equation:
You risk:
- Misleading marketing claims
- Wrong architectural decisions
- Incorrect academic conclusions

🧾 Clean Summary
Performance depends on:
IC×CPI×Clock 
Using only:
- Clock rate
- MIPS
- CPI
Is incomplete and potentially misleading.
The only safe metric is:
 Execution Time
