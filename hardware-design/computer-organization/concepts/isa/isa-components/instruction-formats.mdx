## Instruction Formats
Instructions are kept in the computer as a series of high and low electronic
signals and may be represented as numbers. In fact, each piece of an instruction
can be considered as an individual number, and placing these numbers side by
side forms the instruction. The `32` registers of RISC-V are just referred to by their
number, from `0` to `31`.

instruction format is A
form of representation of
an instruction composed
of fields of binary
numbers.

An **instruction format** refers to the layout or structure of a machine-level instruction, which consists of several fields that hold different types of information. Each field in an instruction has a specific role in telling the CPU what operation to perform, where the operands are located, and how to access them.

To distinguish it from assembly language, we call the numeric version of instructions **machine language** and a sequence of such instructions **machine code**.

**machine language** is a Binary representation used for communication within a computer system.

**Instruction format** defines how a machine instruction is encoded in binary.

It specifies the bit-level layout of fields such as:
- Opcode
- Source operands
- Destination operands
- Immediate values
- Function specifiers

The typical components of an instruction format include:
- **Opcode**: The procedure that is to be completed (e.g., addition, subtraction).
- **Operands**: The data or addresses being used.
- **Addressing Modes**: How the operands are accessed (e.g., direct, indirect).

The instruction format is important to how the CPU retrieves, interprets, and performs instructions, and is an important topic in microprocessor architecture.

**Instruction format** directly affects:
- Decoder complexity
- Pipeline design
- Code density
- Performance
- Energy consumption

**Instruction format** design is one of the most critical architectural decisions.
It influences:
- Hardware simplicity
- Compiler efficiency
- Code density
- Power consumption
- Scalability
- Long-term architectural evolution

A well-designed instruction format balances:
- Regularity
- Simplicity
- Encoding efficiency
- Extensibility

Understanding instruction formats deeply prepares you for:
- Pipeline design
- Decoder implementation
- Performance modeling
- ISA design research

### RISC-V Instruction Formats
RISC-V is a **RISC (Reduced Instruction Set Computer)** architecture, so its instructions are fixed-length (32 bits) and highly regular.

RISC-V instruction takes exactly 32 bits—a word, or one half of a doubleword. In keeping with our design principle that
simplicity favors regularity, RISC-V instructions are all 32 bits long.

RISC-V has several 32-bit instruction formats:
| Format     | Use Case                                      |
| ---------- | --------------------------------------------- |
| **R-Type** | Register-register arithmetic (add, sub, etc.) |
| **I-Type** | Immediate arithmetic, loads, jalr             |
| **S-Type** | Stores (sd, sw)                               |
| **B-Type** | Branches (beq, bne)                           |
| **U-Type** | LUI/AUIPC                                     |
| **J-Type** | Jump (jal)                                    |

### Importance of Instruction Format
**Instruction format** is not just syntax — it is a hardware contract.

Poor format design can cause:
- Complex and slow instruction decoding
- Large hardware area for decoders
- Higher energy consumption
- Reduced pipeline frequency

Good format design enables:
- Fast instruction fetch and decode
- Efficient pipelining
- Parallel decoding
- Scalable architecture growth

### Fundamental Fields in an Instruction
Most instructions are divided into fields. The exact layout depends on the ISA.

A typical instruction may contain:
- **Opcode** → Specifies operation
- **Register fields** → Identify operands
- **Immediate field** → Constant value
- **Function field** → Further specifies operation

Example R-type format (RISC style):
```
opcode | rd | funct3 | rs1 | rs2 | funct7
```
Instruction format affects:
- Hardware complexity
- Decode speed
- Code size
- Pipeline efficiency

in RISC-V, Each 32-bit instruction is divided into fields:

| Field    | Purpose                                                                   |
| -------- | ------------------------------------------------------------------------- |
| `opcode` | identifies the type of instruction (e.g., arithmetic, load/store, branch) |
| `rd`     | destination register (where the result goes)                              |
| `rs1`    | source register 1                                                         |
| `rs2`    | source register 2                                                         |
| `funct3` | further specifies the operation                                           |
| `funct7` | further specifies the operation (e.g., differentiates ADD vs SUB)         |
| `imm`    | immediate value (constant embedded in instruction)                        |

RISC-V fields are given names to make them easier to discuss:

##### Opcode Field
**opcode** The field that denotes the operation and format of an instruction.

The **opcode** identifies the operation to perform. 

**opcode (7 bits)** Tells the CPU which major operation group the instruction belongs to.

The **opcode** is a group of bits inside an instruction that tells the processor: What general kind of instruction is this? It does not specify the exact operation — it specifies the instruction class.

Example operations:
- ADD
- SUB
- LOAD
- STORE
- BRANCH

**Location of Opcode in RISC-V**

In standard 32-bit RISC-V instructions:
```
|31                       7| 6       0|
----------------------------------------
|     other fields         | opcode   |
----------------------------------------
```
- Opcode = `7 bits`
- Located in bits `[6:0]`
- Always in the same position (simplifies hardware)

**What the Opcode Actually Determines**

the formats are distinguished by the values in the
opcode field: each format is assigned a distinct set of opcode values in the first
field (opcode) so that the hardware knows how to treat the rest of the instruction.

The opcode selects:
- **Instruction format** (`R`, `I`, `S`, `B`, `U`, `J`)
- **Functional unit** (`ALU`, `memory`, `branch`, etc.)
- **Immediate layout** (if any)
- **Control signal template**

Think of it as the top-level instruction category.

**Examples of Real RISC-V Opcodes**
| Instruction Type       | Example           | Opcode (binary) |
| ---------------------- | ----------------- | --------------- |
| R-type (register ALU)  | `add x5,x6,x7`    | `0110011`       |
| I-type (immediate ALU) | `addi x5,x6,10`   | `0010011`       |
| Load                   | `ld x5,0(x6)`     | `0000011`       |
| Store                  | `sd x5,0(x6)`     | `0100011`       |
| Branch                 | `beq x5,x6,label` | `1100011`       |
| JAL                    | `jal x1,label`    | `1101111`       |
| LUI                    | `lui x5,imm`      | `0110111`       |


Notice:
- All ALU register-register operations share the same opcode.
- `ADD`, `SUB`, `AND`, `OR` differ using `funct3`/`funct7`, not opcode.
- `LUI` and `AUIPC` differ using `funct3`, not opcode.

**Why Not Encode Everything in Opcode?**

If opcode encoded every operation directly:
- We would need many more bits
- Instruction size would grow
- Encoding would be inefficient

Instead, RISC-V uses a hierarchical decoding strategy:
- opcode  → instruction class
- funct3  → subcategory
- funct7  → exact operation

This reduces hardware complexity.

The size of the opcode field determines:
- Maximum number of supported instructions
- Encoding flexibility

If opcode is `n bits` → maximum of $2^n$ distinct operations.

In standard 32-bit RISC-V instructions: 7 bits allow $2^7=128$ possible primary instruction categories.
RISC-V uses only some of them, leaving space for:
- Future extensions
- Custom instructions
- Vendor-specific encodings

This supports modular ISA growth.

Trade-off:
- Larger opcode → more instructions
- Smaller opcode → more space for operands

In summary, the **opcode field**:
- Identifies the instruction class
- Determines instruction format
- Controls datapath behavior
- Drives main control signals
- Enables modular ISA expansion

In short: The **opcode** tells the processor **what kind of work to do**, while the other fields specify **how exactly to do it**.

**Example: ADD vs LOAD**

ADD
```
opcode = 0110011
```
Means: This is a register-register arithmetic instruction. Then `funct3/funct7` choose `ADD` vs `SUB` vs `AND`.

LD
```
opcode = 0000011
```
Means: This is a load instruction. Then `funct3` determines:
- LB
- LH
- LW
- LD

Same opcode — different data sizes.

**Hardware Perspective (Decode Stage)**

During the decode stage of a pipeline:

1. **Step 1: Extract opcode bits [6**:0]

2. **Step 2: Send opcode into main control unit, The control unit generates signals like**:
   - RegWrite
   - MemRead
   - MemWrite
   - ALUSrc
   - Branch
   - Jump

For example:
If opcode = 0000011 (load):

Control signals:
- MemRead = 1
- RegWrite = 1
- ALUSrc = 1
- MemWrite = 0

If opcode = 0110011 (R-type ALU):
- MemRead = 0
- RegWrite = 1
- ALUSrc = 0
- MemWrite = 0

So the opcode drives the entire datapath behavior.

Think of opcode as:
- The chapter title
- funct3/funct7 as the section title
- Operands as the details

##### Register Fields
**Register fields** are the bit portions of an instruction that specify:
- **Which registers to read**
- **Which register to write**

**Register fields** are central to how instructions interact with the register file.

###### Register Fields in RISC-V
In RISC-V, the main register fields are:
- `rs1` → source register 1
- `rs2` → source register 2
- `rd` → destination register

1. **rs1 (Source Register 1)**

First input operand.

Example:
```nasm
add x5, x6, x7
```
- rs1 = x6
- Value read from register file

2. **rs2 (Source Register 2)**

Second input operand.
- rs2 = x7
- Also read from register file

3. **rd (Destination Register)**

Specifies the destination register (x0–x31) for the result.

Where the result is written.
- rd = x5
- Written during write-back stage

###### Special Registers in Register Fields
Some registers have special purposes:
| Register | Number | Purpose               |
| -------- | ------ | --------------------- |
| x0       | 0      | Always 0              |
| x1       | 1      | Return address        |
| x2       | 2      | Stack pointer         |
| x8       | 8      | Frame pointer (often) |

Example:
```
add x5, x6, x0
```
Using `x0` means: Add zero (acts like move).

###### Register field size
Registers are usually encoded as fixed-width fields.

If the ISA has:
- `32` registers → `5 bits` needed ($2^5 = 32$)
- `64` registers → `6 bits` needed ($2^6 = 64$)

RISC-V has 32 general-purpose registers, To uniquely identify 32 registers we need $2^5=32$ bits per register field.
So each register field needs exactly `5 bits`.

Register field size directly affects:
- Instruction width
- Number of architectural registers

###### Where Register Fields Appear
1. **R-Type Format**
```
31      25 24   20 19   15 14  12 11    7 6      0
------------------------------------------------------
| funct7 | rs2 | rs1 | funct3 |  rd  |  opcode  |
------------------------------------------------------
```
Used by:
- ADD
- SUB
- AND
- OR
- SLT
- MUL (extension)

Here:
- rs1 and rs2 are read
- rd is written

2. **I-Type Format**
```
31          20 19   15 14  12 11    7 6      0
------------------------------------------------
| immediate | rs1 | funct3 |  rd  |  opcode |
------------------------------------------------
```
Used by:
- ADDI
- Loads (LD, LW, etc.)

Here:
- rs1 is read
- rd is written
- No rs2

3. **S-Type (Stores)**
```
31   25 24   20 19   15 14  12 11    7 6      0
------------------------------------------------------
| imm | rs2 | rs1 | funct3 | imm | opcode |
------------------------------------------------------
```
Here:
- rs1 = base address
- rs2 = data to store
- No rd (because nothing is written back)

###### Hardware Perspective
Inside the CPU:
Register File Has:
- 32 registers
- 2 read ports
- 1 write port

When instruction is decoded:
1. `rs1` → selects first read port
2. `rs2` → selects second read port
3. `rd` → selects write destination

So the register fields directly control the multiplexers of the register file.

Register fields are not just identifiers.
They:
- Control data flow
- Select ALU inputs
- Control write-back
- Affect hazards and forwarding
- Impact pipeline timing

They are physically connected to:
- Register file decoder
- Forwarding unit
- Hazard detection unit

In Summary, Register fields:
- Identify source and destination registers
- Are `5 bits` wide (for `32 registers`)
- Directly control register file hardware
- Appear in fixed bit positions
- Enable clean pipeline design

In short: **Register fields** tell the CPU **where data comes from** and **where it goes**.

##### Immediate Field
An **immediate field** is a portion of the instruction that contains a constant value embedded directly inside the instruction.

Instead of reading a value from a register, the CPU uses this constant.

An **immediate** is a constant embedded inside the instruction.

Example:
```nasm
addi x1, x2, 10
```
Here:
- `10` is the immediate.
- It is encoded directly into the instruction bits(The value `10` is stored in the instruction itself.).

Used in I-Type (arithmetic with immediate), S-Type (store offset), B-Type (branch offset), U-Type (upper 20 bits), J-Type (jump offset).

**Why Immediate Fields Exist**

Without immediates, to add 10 you would need:
```nasm
li x7, 10
add x5, x6, x7
```
That's two instructions.

With an immediate:
```nasm
addi x5, x6, 10
```
- Faster
- Smaller code
- Better performance

###### Immediate Field Size
In base RV32I:
- Most immediates are `12 bits`
- Some are `20 bits`
- Some are split across the instruction

Why `12 bits`?
Because instruction length is fixed at `32 bits`, and space must be shared with:
- opcode
- funct3
- register fields

{/* I-type immediates, memory addressing, and RISC-V instruction constraints. */}
The 12-bit immediate is interpreted as a two’s complement value, so it can
represent integers from $−2^11$ to $2^11−1$. When the I-type format is used for load
instructions, the immediate represents a byte offset, so the load doubleword
instruction can refer to any doubleword within a region of $±2^11$ or 2048 bytes ($±2^8$
or 256 doublewords) of the base address in the base register rd. We see that more
than 32 registers would be difficult in this format, as the rd and rs1 fields would
each need another bit, making it harder to fit everything in one word.

In I-type instructions, like arithmetic with immediate (ADDI) or loads (LD), the instruction contains a 12-bit immediate field (imm[11:0]).
- Two’s complement → allows negative and positive values
- Range of a 12-bit two’s complement number: $−2^11$ to $2^11−1$ or −2048 to 2047

So you can encode offsets or constants within this range directly in the instruction.

For a load instruction like `LD x5, imm(x6)`:
- `x6` → base register (holds starting memory address)
- `imm` → offset from that base

Example:
```
LD x5, 100(x6)  # Load 8-byte doubleword from address (x6 + 100)
```
- Because imm is 12-bit, the addressable region relative to the base is ±2048 bytes.
- Since a doubleword = 8 bytes, the load can reach ±256 doublewords(±2048 bytes÷8 bytes/doubleword=±256)

Immediate size determines:
- Maximum constant size
- Offset range for branches and memory access

Trade-off:
- Larger immediate → more flexible
- Smaller immediate → shorter instruction length

###### Immediate Formats
RISC-V uses different layouts depending on instruction type.

1. **I-Type Immediate (12 bits)**

Used by:
- ADDI
- Loads (LW, LD)
- JALR

Format:
```
31          20
--------------
| immediate |
--------------
```
The immediate is:
- `12 bits`
- Sign-extended to `32 bits` (or `64 bits` in RV64)

Example:
```nasm
addi x5, x6, -3
```
Binary immediate:
```
111111111101
```
Sign bit = 1 → extended to full width

2. **S-Type Immediate (Stores)**

Used by:
- SW
- SD

The immediate is split:
```
--------------------------------
|  31   25  | ..... | 11     7 |
--------------------------------
| imm[11:5] |       | imm[4:0] |
--------------------------------
```
Why split?
Because `rd` field space is reused for immediate bits.
Hardware reassembles it during decode.

3. **B-Type Immediate (Branches)**

Used by:
- BEQ
- BNE
- BLT

Immediate is also split and rearranged:
```
imm[12|10:5|4:1|11]
```
It represents a PC-relative offset.

Important:
- Always multiple of 2
- Least significant bit is always 0
- Actually shifted left by 1 internally

This allows branch range of: ±4 KB

4. **U-Type Immediate (20 bits)**

Used by:
- LUI
- AUIPC
Format:
```
31                12
----------------------
|   20-bit imm     |
----------------------
```
Placed in upper 20 bits of register.

Lower 12 bits = 0.

Example:
```nasm
lui x5, 0x12345
```
Result:
```
x5 = 0x12345000
```

5. **J-Type Immediate (Jumps)**

Used by:
- JAL

Immediate is `20 bits` but scattered:
```
imm[20|10:1|11|19:12]
```
Shifted left by 1.

Range: ±1 MB

**Sign Extension**

Most immediates are signed.

If MSB of immediate = 1:

The CPU fills upper bits with 1s.
Example (12-bit immediate):
```
100000000000
```
Becomes:
```
1111111111111111100000000000  (32-bit)
```
This allows:
- Negative offsets
- Backward branches
- Stack pointer decrements

**Why Split Immediates?**
To keep:
- Register fields in fixed positions
- Decoder simple
- Instruction format uniform

RISC-V design philosophy: Keep hardware simple, even if encoding looks strange.

**Immediate Range Summary (RV32)**
| Type   | Bits         | Range          |
| ------ | ------------ | -------------- |
| I-Type | 12           | -2048 to +2047 |
| S-Type | 12           | -2048 to +2047 |
| B-Type | 13 effective | ±4 KB          |
| U-Type | 20           | Upper 20 bits  |
| J-Type | 21 effective | ±1 MB          |

**Example: Full Walkthrough**

Instruction:
```nasm
beq x5, x6, -8
```
Steps:
1. Immediate field extracted
2. Reassembled
3. Sign-extended
4. Shifted left by 1
5. Added to PC(Program Counter)

New PC = PC - 8

###### Immediate vs Register Operand
Compare:
```nasm
add  x5, x6, x7   → register operand
addi x5, x6, 10   → immediate operand
```
Hardware difference:
- `add` reads two register ports
- `addi` reads one register + immediate generator

Immediate goes through:
```
Instruction → Immediate Generator → Sign Extend → ALU
```

###### Immediate Generator Hardware
During decode:
1. Instruction bits extracted
2. Bits rearranged (for `B/J/S` types)
3. Sign extension applied
4. Output sent to `ALU`

This block is called **Immediate Generator**, It is pure combinational logic.

In summary Immediate fields:
- Reduce instruction count
- Enable constants
- Enable PC-relative addressing
- Support branches and jumps
- Simplify compiler design

Without immediates, modern CPUs would be inefficient.

##### Function Fields
Some ISAs reuse opcodes and differentiate instructions using smaller fields.

**Function fields** are bits inside an instruction that Specify the exact operation to perform.

The opcode tells the CPU the **instruction format category**, but the function fields tell it **the precise operation**.

RISC-V keeps the opcode small (7 bits). Many instructions share the same opcode.

Example: ADD and SUB have the same opcode. So how does the CPU distinguish them? Answer: Function fields.

**Example:**
- Same opcode for all arithmetic instructions
- Use a "function" field to distinguish ADD vs SUB

This reduces opcode size but increases decode complexity.

So, Opcode says: "This is an R-type ALU instruction", Function fields say:
- "Do ADD"
- "Do SUB"
- "Do AND"
- "Do MUL" 

###### The Two Main Function Fields
In RISC-V R-type instructions:
```
funct3  → 3 bits
funct7  → 7 bits
```
funct3 (3 bits): Differentiates instructions within the same opcode.
| funct3 | Meaning (opcode 0110011) |
| ------ | ------------------------ |
| 000    | ADD/SUB                  |
| 111    | AND                      |
| 110    | OR                       |

funct7 (7 bits): Further distinguishes instructions, e.g., ADD vs SUB:
| funct7  | Meaning (for ADD/SUB) |
| ------- | --------------------- |
| 0000000 | ADD                   |
| 0100000 | SUB                   |

Together: `funct3 + funct7 = 10 bits of function control`

Why Split Into funct3 and funct7?
Design reasons:
- Keeps register fields in fixed positions
- Keeps instruction length fixed (32 bits)
- Allows future extensions
- Makes decoder simple

Instead of making opcode huge, RISC-V distributes control bits.

###### Function Fields in R-Type Instructions
**Where Function Fields Appear (R-Type)**

```
31      25 24   20 19   15 14  12 11    7 6      0
------------------------------------------------------
| funct7 | rs2 | rs1 | funct3 |  rd  |  opcode  |
------------------------------------------------------
```
- opcode → broad category
- funct3 → sub-operation
- funct7 → further refinement

**Example: ADD vs SUB**
|             | ADD            | SUB          |
| ----------- | -------------- | -------------- |
| Instruction | add x5, x6, x7 | sub x5, x6, x7 |
|    opcode   | 0110011        | 0110011 (same!)        |
|   funct3    | 000            | 000 (same!)    |
|    funct7   | 0000000        | 0100000 (different!)       |

Only funct7 changes.
That single bit difference tells ALU:
- 0000000 → ADD
- 0100000 → SUB

**Example: Logical Operations**

All share same opcode:
| Instruction | funct3 | funct7  |
| ----------- | ------ | ------- |
| AND         | 111    | 0000000 |
| OR          | 110    | 0000000 |
| XOR         | 100    | 0000000 |

Here funct3 selects operation. funct7 remains same.

###### Function Fields in I-Type Instructions

**Where Function Fields Appear (I-Type)**
```
31      25  24   20 19   15 14  12 11    7 6      0
------------------------------------------------------
| imm[11:0] | rs1 | funct3  |  rd       |  opcode  |
------------------------------------------------------
```
For ADDI:
- opcode = 0010011
- funct3 = 000

For ANDI:
- funct3 = 111

So funct3 selects the ALU operation.

**Example: ADDI vs SUBI**
|             | ADDI         | SUBI          |
| ------ | ------------ | -------------- |
| Instruction | addi x5, x6, 10           | subi x5, x6, 10 |
| opcode | 0010011           | 0010011 (same!) |
| funct3 | 000 | 111          |
| imm[11:0] | 000000000010 | 000000000010 (same!) |

**Multiply Example (Extension)**

In the M-extension:
- MUL
- DIV
- REM

They use:
- Same R-type opcode
- funct7 = 0000001
- funct3 selects specific multiply/divide

Example:
| Instruction | funct7  | funct3 |
| ----------- | ------- | ------ |
| MUL         | 0000001 | 000    |
| DIV         | 0000001 | 100    |
| REM         | 0000001 | 110    |

So funct7 identifies "multiply/divide group".

In Summary, Function fields:
- Refine operation within opcode group
- Control ALU behavior
- Allow many instructions to share opcode
- Keep instruction encoding compact
- Enable extensibility

In simple terms: Opcode chooses the category, Function fields choose the exact operation.

###### How Hardware Uses Function Fields
During decode stage:
1. Opcode determines instruction type
2. funct3 + funct7 go into the control unit
3. Control unit generates ALU control signals

Example logic:
```
if opcode == R-type:
    if funct3 == 000 and funct7 == 0000000 → ADD
    if funct3 == 000 and funct7 == 0100000 → SUB
```
Function fields directly control:
- ALU operation
- Shift type
- Comparison type
- Multiply/divide extension

### Fixed-Length vs Variable-Length
Fixed-Length Instructions
- All instructions have the same size
- Simpler decoding
- Easier pipelining
- Used in RISC architectures

Variable-Length Instructions
- Instructions may vary in size
- Higher code density
- More complex decoding
- Used in CISC architectures

##### Fixed-Length Instructions
All instructions have the same size.

Example:
- 32-bit fixed length

Used in most RISC architectures.

Advantages
- Simple instruction fetch
- Easy pipelining
- Parallel decoding possible
- Predictable alignment

Hardware Benefits
- PC increments by fixed value
- No need for complex length detection logic
- Faster instruction decoding

Disadvantages
- Lower code density
- Wasted bits for simple instructions

##### Variable-Length Instructions
Instructions may have different lengths.

Common in CISC architectures.

Example:
- 1 byte to 15 bytes long
Advantages
- Higher code density
- Compact encoding
- Flexible instruction representation

Disadvantages
- Complex decoding logic
- Harder pipelining
- Slower instruction fetch stage

Variable-length instructions often require:
- Pre-decoders
- Instruction boundary detection
- Micro-op translation


### Types of Instruction Formats
**Instruction formats** determine the arrangement or composition of bits within an instruction. Such formats specify how the operation code (opcode), operand(s), and addressing modes will be spaced or organized. The format determines how the central processing unit (CPU) will interpret and execute instructions. Each instruction must include the basic components required to efficiently perform a task - the type of operation, operands, and knowledge of the addressing of operands.

**Instruction formats** define how CPU instructions are encoded, featuring an **opcode** (operation) and zero to three operand/address fields. The four main types, classified by address count, are: 
1. three-address, 
2. two-address, 
3. one-address (accumulator-based), and 
4. zero-address (stack-based). 

Modern systems also use specialized formats like **R-type**, **I-type**, and **J-type** (e.g., in MIPS/ARM) for efficiency. 

In base RISC-V (RV32/RV64):
- Each instruction = `32 bits`
- Bits are divided into fixed fields
- Format depends on instruction type (R, I, S, B, U, J)

Many RISC architectures use multiple standardized formats.

Key Instruction Format Types
1. **Three-Address Instructions**: 
    * Uses three address fields (e.g.`ADD R1, A, B`). 
    * Efficient for complex calculations, reducing the number of instructions.
2. **Two-Address Instructions**: 
    * Uses two address fields, with one acting as both source and destination (e.g.`ADD R1, A`).
3. **One-Address Instructions**: Uses an implicit accumulator register for all operations (e.g.`ADD A`).
4. **Zero-Address Instructions**: 
    * Operands are accessed via a stack, with no address fields required for the operands themselves (e.g.PUSH A``PUSH B``ADD``POP C).

**Components of an Instruction**
- **Opcode (Operation Code)**: Specifies the action (e.g., `ADD`, `SUB`, `LOAD`).
- **Operands/Address Fields**: References data, such as registers or memory locations.
- **Mode Field**: Specifies the addressing mode (direct, indirect, immediate).

Modern/RISC Instruction Formats (e.g., MIPS)

- **I-Type (Immediate)**: Includes an immediate value within the instruction.
- **J-Type (Jump)**: Used for jump instructions.

**Why So Many Fields?**

RISC-V design goal (by RISC-V International) was:
- Fixed instruction length
- Simple decoding
- Orthogonal design
- Hardware-friendly pipeline

This fixed layout makes:
- Decode stage simple
- Control logic clean
- Pipeline easier

In the decode stage of a pipeline:
1. opcode → selects instruction type
2. rs1, rs2 → read from register file
3. funct3 + funct7 → select ALU operation
4. rd → write-back destination

Very clean data path.

##### Zero-Address Instructions 
A **zero-address instruction** is an instruction that: Does not explicitly specify any operand addresses in the instruction.

It operates without specifying any operands explicitly. Typically used in stack-based architectures, these instructions rely on the stack to store operands. The operations are performed on the top of the stack, and the results are also stored on the stack.

Meaning:
- No rd
- No rs1
- No rs2
- No explicit register names

Operands are implicitly defined.

#### Based on Instruction Encoding Format
This classification  describes: How bits are arranged inside the instruction. This is about binary layout, not architecture style.

Modern ISAs like those defined by RISC-V International use register-based (three-address) design because:
- Fewer instructions
- Faster execution
- Better parallelism
- Easier pipelining

| Format     | Used For                        |
| ---------- | ------------------------------- |
| R-Type     | Register-to-register operations |
| I-Type     | Loads, immediates               |
| **S-Type** | **Store instructions**          |
| B-Type     | Branches                        |
| U-Type     | Upper immediate                 |
| J-Type     | Jumps                           |

RISC-V uses 6 main instruction formats:
| Type       | Usage                                            | Fields                                                         |
| ---------- | ------------------------------------------------ | -------------------------------------------------------------- |
| **R-Type** | Register-register arithmetic (ADD, SUB, AND, OR) | opcode, rd, funct3, rs1, rs2, funct7                           |
| **I-Type** | Immediate arithmetic, loads, jalr                | opcode, rd, funct3, rs1, imm[11:0]                             |
| **S-Type** | Stores (SD, SW)                                  | opcode, funct3, rs1, rs2, imm[11:0] (split across instruction) |
| **B-Type** | Conditional branches (BEQ, BNE)                  | opcode, funct3, rs1, rs2, imm[12:1] (branch offset)            |
| **U-Type** | Upper immediate instructions (LUI, AUIPC)        | opcode, rd, imm[31:12]                                         |
| **J-Type** | Unconditional jump (JAL)                         | opcode, rd, imm[20:1] (jump offset)                            |

##### R-Type (Register Type)
Used for register-register operations.

Typical Layout (32-bit):
```
opcode | rd | funct3 | rs1 | rs2 | funct7
```
Characteristics:
- Two source registers
- One destination register
- No immediate

Used for:
- ADD
- SUB
- AND
- OR
- XOR
- SLT
- MUL (with extension)

Advantages:
- Regular structure
- Easy decode
- High execution efficiency

Layout
```
   7 bits    5 bits   5 bits   3 bits   5 bits   7 bits
----------------------------------------------------------
|31      25| 24   20| 19   15| 14  12 | 11    7| 6      0|
|  funct7  |  rs2   |  rs1   | funct3 |   rd   |  opcode |
----------------------------------------------------------
```
- **opcode**: Basic operation of the instruction, and this abbreviation is its traditional name.
- **rd**: The register destination operand. It gets the result of the operation.
- **funct3**: An additional opcode field.
- **rs1**: The first register source operand.
- **rs2**: The second register source operand.
- **funct7**: An additional opcode field.
So:
| Field  | Bits  | Purpose                      |
| ------ | ----- | ---------------------------- |
| **opcode** | 6–0   | Instruction category         |
| **rd**     | 11–7  | Destination register         |
| **funct3** | 14–12 | Sub-operation selector       |
| **rs1**    | 19–15 | Source register 1            |
| **rs2**    | 24–20 | Source register 2            |
| **funct7** | 31–25 | Further operation refinement |

1. **opcode (7 bits)**

Identifies the main instruction class.
Example:
- `0110011` → R-type arithmetic

Think of it as: "This is an integer register-register operation."

2. **rd (5 bits)**

Destination register.
Example:
```nasm
add x5, x6, x7
```
`rd` = `x5`

Since there are 32 registers: 5 bits are needed ($2^5 = 32$)

3. **rs1 (5 bits)**

First source register.
In:
```nasm
add x5, x6, x7
```
`rs1` = `x6`

4. **rs2 (5 bits)**

Second source register.
In:
```nasm
add x5, x6, x7
```
`rs2` = `x7`

5. **funct3 (3 bits)**

Selects a specific operation inside opcode group.
Example:
| funct3 | Meaning   |
| ------ | --------- |
| 000    | ADD / SUB |
| 111    | AND       |
| 110    | OR        |
| 100    | XOR       |

But ADD and SUB share funct3!
So we need one more field…

6. **funct7 (7 bits)**

Distinguishes between operations that share funct3.
Example:
| Instruction | funct7  |
| ----------- | ------- |
| ADD         | 0000000 |
| SUB         | 0100000 |

So:
```
ADD  → funct7 = 0000000
SUB  → funct7 = 0100000
```
Same opcode, Same funct3, Different funct7

Why RISC-V Splits Operation into opcode + funct3 + funct7? Instead of one large opcode field:
- Allows expansion
- Supports extensions
- Keeps encoding compact
- Enables modular ISA design

In RISC-V:
- `rs1` is always in bits `[19:15]`
- `rs2` always in `[24:20]` (if present)
- `rd` always in `[11:7]`

This consistency makes:
- Decode simple
- Wiring simpler
- Pipeline faster
- Hardware smaller

Unlike complex ISAs where field positions vary.

##### I-Type (Immediate Type)
Used for operations with immediate values.
Layout:
```
opcode | rd | funct3 | rs1 | immediate
````
Used for:
- ADDI
- LOAD
- Logical immediate operations

Characteristics:
- One source register
- One destination register
- Embedded constant

###### Logical immediate operations
shift instructions use the I-type format. 

Since it isn’t useful to shift a 64-bit register by more than 63 bits, only the lower 6 bits of the I-type format’s 12-bit immediate are actually used. The remaining 6 bits are repurposed as an additional `opcode` field, `funct6`.

In RV64, registers are 64 bits wide. If you shift a value: Maximum meaningful shift = 63 bits.
So the shift amount only needs: $2^6 = 64$ bits.
Therefore 6 bits are enough to represent shift values 0–63.
But the I-type immediate field is 12 bits, so:
- lower 6 bits → shift amount
- upper 6 bits → extra opcode field (funct6)

```
Because a 64-bit register cannot be shifted more than 63 bits, RISC-V only uses 6 bits of the immediate for the shift amount, and reuses the remaining 6 bits as funct6 to help identify the specific shift instruction.
funct6 immediate rs1 funct3 rd opcode
0      4         19  1      11 19
```
The encoding of `slli` is `19` in the `opcode` field, `rd` contains `11`, `funct3` contains
`1`, `rs1` contains `19`, immediate contains `4`, and `funct6` contains `0`.
| Field     | Value | Meaning                       |
| --------- | ----- | ----------------------------- |
| opcode    | 19    | I-type arithmetic instruction |
| funct3    | 1     | Shift left                    |
| rs1       | x19   | source register               |
| rd        | x11   | destination register          |
| immediate | 4     | shift amount                  |
| funct6    | 0     | logical shift                 |

For shift instructions the Modified I-Type Format for Shift Instructions (slli, srli, srai):
```
funct6 | shamt(6 bits) | rs1 | funct3 | rd | opcode
```
Where:
- funct6 → identifies the shift type
- shamt → shift amount (0–63 in RV64)
- rs1 → source register
- rd → destination register


**RISC-V Shift Instruction Encodings (RV64)**
| Instruction | Operation              | funct6   | shamt (shift amount) | rs1             | funct3 | rd          | opcode    |
| ----------- | ---------------------- | -------- | -------------------- | --------------- | ------ | ----------- | --------- |
| **slli**    | Shift left logical     | `000000` | 0–63                 | source register | `001`  | destination | `0010011` |
| **srli**    | Shift right logical    | `000000` | 0–63                 | source register | `101`  | destination | `0010011` |
| **srai**    | Shift right arithmetic | `010000` | 0–63                 | source register | `101`  | destination | `0010011` |

##### S-Type (Store Type)
Used for memory store instructions.
Layout splits immediate field across two parts:
```
7 bits      5 bits  5 bits 3 bits    5 bits     7 bits
imm[11:5] |  rs2  |  rs1  | funct3 | imm[4:0] | opcode
```
The 12-bit immediate in the S-type format is split into two fields, which supply
the lower 5 bits and upper 7 bits. The RISC-V architects chose this design because it
keeps the rs1 and rs2 fields in the same place in all instruction formats. Keeping the
instruction formats as similar as possible reduces hardware complexity. Similarly, the opcode and funct3 fields are the same size in all locations, and they are always
in the same place.

Why split immediate?
- Maintain consistent register field positions
- Simplify hardware routing

##### B-Type (Branch Type)
Used for conditional branches.
Immediate fields are rearranged for alignment.
Branch offsets are:
- Sign-extended
- Shifted for instruction alignment
Branch format complexity affects:
- Branch prediction logic
- Pipeline control

###### Full Binary Encoding of beq
We’ll convert a real instruction into its 32-bit machine code.

✅ Example Instruction
```nasm
beq x5, x6, +16
```
Meaning: If `x5 == x6`, jump `16 bytes` forward.

1. **Step 1**: Identify Fields (B-type format)
```
| imm[12] | imm[10:5] | rs2 | rs1 | funct3 | imm[4:1] | imm[11] | opcode |
```
2. **Step 2**: Fill Known Fields
- `rs1` = `x5` → `00101`
- `rs2` = `x6` → `00110`
- `funct3 (beq)` → `000`
- `opcode` (branch) → `1100011`

3. **Step 3**: Encode Immediate (offset = +16)
- Important rules:
    - Offset is in bytes
    - Last bit is always 0 → we drop it
    - So we encode 16 / 2 = 8
- 16 in binary (13 bits for B-type): `0000000010000`
- Now split it:
- Field	Bits
- imm[12]	0
- imm[10:5]	000000
- imm[4:1]	1000
- imm[11]	0

4. **Step 4**: Assemble Instruction
- imm[12]   = 0
- imm[10:5] = 000000
- rs2       = 00110
- rs1       = 00101
- funct3    = 000
- imm[4:1]  = 1000
- imm[11]   = 0
- opcode    = 1100011

Final 32-bit Binary
```
0 000000 00110 00101 000 1000 0 1100011
```
Grouped:
```
0000000 00110 00101 000 1000 01100011
```
Final Answer (Hex): `0x0062A863`

bne x5, x6, +16

##### J-Type (Jump Type)
Used for long-range jumps.
Contains:
- Large immediate field
- Destination register

The J-Type format is used for:
```
JAL  (Jump And Link)
```
Purpose: Perform a PC-relative jump and save the return address.

Example:
```nasm
jal x1, 100
```
Meaning:
- Jump forward by `100` bytes
- Store return address `(PC+4)` in `x1`

This is how function calls work in RISC-V.

Bit layout (32-bit instruction):
```
31        30      21 20 19      12 11     7 6      0
---------------------------------------------------------
| imm[20] | imm[10:1] | imm[11] | imm[19:12] | rd | opcode |
---------------------------------------------------------
```
Key points:
- Immediate bits are not contiguous
- rd is destination register (usually x1)
- opcode identifies JAL

The word "Link" means: Store return address so we can come back. Return is done using:
```
jalr x0, 0(x1)
```
That jumps to address stored in x1.

**Why Not Use I-Type for Jump?**
- I-Type has only 12-bit immediate: ±2048 bytes, Too small for function calls.
- J-Type allows: ±1 MB, Much larger range.


**Why Is Immediate Scattered?**

RISC-V keeps:
- rd always in bits [11:7]
- opcode always in bits [6:0]

To maintain consistency across formats, the immediate had to be split. This simplifies hardware decoding overall.

**How the Immediate Is Reconstructed**

The 20-bit immediate is formed as:
```
imm[20 | 10:1 | 11 | 19:12]
```
Then:
1. Concatenate bits in correct order
2. Sign-extend to 32 (or 64) bits
3. Shift left by 1 bit

Why shift left by 1? Because instruction addresses are aligned to 2 bytes. The least significant bit is always 0, so it’s not stored.

**Effective Immediate Size**

Although 20 bits are stored, after shift-left-by-1: It becomes a 21-bit signed offset.

Jump range: ±1 MB

That is: ±$2^20$

**Step-by-Step Execution of JAL**

Suppose:
```
PC = 1000
jal x1, 16
```
Step 1: Save return address

x1 = PC + 4 = 1004

Step 2: Compute target address

Target = PC + sign_extended_offset

If offset = 16:

New PC = 1000 + 16 = 1016

Jump occurs.

J-Type contains:
- Large PC-relative offset
- Destination register
- Opcode
- Scattered immediate bits

It enables:
- Function calls
- Long-range jumps
- Efficient code generation

J-Type is optimized for:
- Position-independent code
- Efficient function calls
- Simple decoding
- Large jump range

It is one of the key formats that makes RISC-V clean and scalable.

Now remember:
- Immediate is shifted left by 1 internally.
- So actual stored immediate is offset >> 1.

Since 16 = 10000₂

Divide by 2: 8 = 000000000000000001000

This 20-bit value is what we encode.

```
imm[20 | 10:1 | 11 | 19:12]

x1 = register 1

5-bit binary: `00001`

imm[10:1]    → 0000001000
imm[11]      → 0
imm[19:12]   → 00000000
rd           → 00001
opcode       → 1101111
```
Final 32-bit binary:
```

```

2. Sign extension applied
3. Shift left by 1
4. Added to current PC

6. PC+4 written into rd

- Register file (write)

##### Quick Visual Layouts
**R-Type (ADD, SUB)**
```
funct7 | rs2 | rs1 | funct3 | rd  | opcode
7 bits | 5   | 5   | 3      | 5   | 7
```
Example: ADD x5, x6, x7
- rd = x5, rs1 = x6, rs2 = x7
- funct3 = 000, funct7 = 0000000, opcode = 0110011

**I-Type (ADDI, Load)**
```
imm[11:0] | rs1 | funct3 | rd  | opcode
12 bits   | 5   | 3      | 5   | 7
```
Example: ADDI x5, x6, 10
- Add 10 to x6, store result in x5

**S-Type (Store)**
```
imm[11:5] | rs2 | rs1 | funct3 | imm[4:0] | opcode
7 bits    | 5   | 5   | 3      | 5        | 7
```
Example: Store x5, 10(x6)
- Store value in x5 at address (x6 + 10)

**B-Type (Branch)**
```
imm[12|10:5] | rs2 | rs1 | funct3 | imm[4:1|11] | opcode
```
Example: Branch if `x5 != x6`
- The offset for branch is scattered across bits.

**U-Type (LUI, AUIPC)**
```
imm[31:12] | rd  | opcode
20 bits    | 5   | 7
```
Example: LUI `x5`, `10`
- Load upper 20 bits (`10 << 12`) into `x5`

**J-Type (JAL)**
```
imm[20|10:1|11|19:12] | rd  | opcode
```
Example: JAL x5, 10
- Jump offset is split across the instruction bits

### Impact on Pipeline Design
Instruction format influences pipeline stages:
6.1 Fetch Stage
- Fixed length simplifies PC increment
- Variable length requires boundary detection
6.2 Decode Stage
- Regular field positions simplify decoding
- Irregular layouts require complex logic
6.3 Execute Stage
Consistent operand positioning:
- Reduces wiring complexity
- Enables parallel execution units

### Instruction Alignment
In many architectures, words must start at addresses that are multiples
of 4 and doublewords must start at addresses that are multiples of 8. This requirement is
called an **alignment restriction**. RISC-V and Intel x86 do not have alignment restrictions, but MIPS does.

**alignment restriction** A requirement that data be aligned in memory on natural boundaries.

Fixed-length ISAs often enforce alignment.

Example:
- 32-bit instruction must be 4-byte aligned

Benefits:
- Faster fetch
- No cross-boundary fetch complexity

Misalignment increases:
- Hardware complexity
- Power usage

### Extension and Scalability
Good instruction format design allows future expansion.
Strategies include:
- Reserved opcode space
- Extension fields
- Prefix encoding
Poor design leads to:
- Encoding exhaustion
- Complex backward compatibility hacks

### Microarchitectural Consequences
Instruction format affects:
- Decoder area
- Critical path delay
- Instruction throughput
- Energy efficiency
- Front-end bottlenecks
In modern processors:
- Decode can be one of the most power-hungry stages.
- Complex instruction formats increase front-end energy.
### Design Trade-Off Summary
| Design Choice    | Benefit                  | Cost               |
| ---------------- | ------------------------ | ------------------ |
| Fixed Length     | Simple decode            | Lower density      |
| Variable Length  | Compact code             | Complex hardware   |
| Large Immediate  | Flexible constants       | Wider instructions |
| Many Registers   | Fewer memory accesses    | Larger encoding    |
| Multiple Formats | Specialized optimization | Decode complexity  |
