Registers are small, fast storage locations inside the CPU.

The ISA specifies:

* Number of registers
* Register size
* Register roles/purpose

Examples:

* **General-purpose registers(GPRs)**: Used for various data and addresses.
* **Special-Purpose Registers**: Such as
  * Program counter (PC), which holds the address of the next instruction
  * Stack pointer (SP), which points to the top of the stack.
  * Status/flag registers that hold condition codes or control bits.

Registers strongly affect performance and instruction design.

## Relation between size of instruction, size of a register, number of registers
### Instruction Size
Instruction size = number of bits used to encode one instruction.

Example in RISC-V: Most instructions are 32 bits

That 32 bits must encode:
- Operation (opcode)
- Source register numbers
- Destination register number
- Immediate values (if any)

So instruction size is about encoding space.

### Number of Registers
The number of registers determines How many bits are needed to identify one register.

Bits needed=log2​(Number of registers)

Examples:
| Registers | Bits Needed |
| --------- | ----------- |
| 8         | 3 bits      |
| 16        | 4 bits      |
| 32        | 5 bits      |
| 64        | 6 bits      |
| 128       | 7 bits      |

If an instruction uses 3 registers (like add), total register bits: $3×log_2(N)$

So increasing number of registers increases instruction encoding size pressure.

### Register Size
Register size = how many bits each register holds.
Examples:
- 32-bit register
- 64-bit register (RISC-V RV64)
- 128-bit SIMD registers

Important: Register size does NOT affect how many bits are needed to encode its name, Because encoding only specifies which register, not its size.
Example: If you say:
```nasm
add x1, x2, x3
```
The instruction only needs to encode:
- Register index 1
- Register index 2
- Register index 3

It does NOT encode:
- 32-bit
- 64-bit
- 128-bit

That’s determined by the ISA mode.

### Relationship 1:Number of registers ↔ Instruction size
More registers →
- More bits per register field →
- Larger instructions OR fewer bits for other things

So:
```
More registers → More encoding bits needed
```

### Relationship 2: Instruction size ↔ Immediate size
If instruction size is fixed (like 32 bits):
More register bits →
- Fewer bits left for immediate values

Example:
If 15 bits go to registers:
- Only 17 bits remain for opcode + immediate

So instruction size limits everything.

### Relationship 3: Register size ↔ Datapath width (NOT instruction width)
Register size affects:
- ALU width
- Data bus width
- Memory bandwidth
- Performance for large integers

But it does NOT directly affect instruction length.

Example:
- 32-bit registers → ALU is 32-bit
- 64-bit registers → ALU is 64-bit

But instructions can still be 32 bits long in both cases.

**Big Picture Diagram**
```
Number of Registers
        ↓
Bits needed to encode register index
        ↓
Consumes bits inside instruction
        ↓
Affects instruction format design
```
Meanwhile:
```
Register Size
        ↓
ALU width & data processing width
        ↓
Performance & hardware complexity
```

### Why This Matters in Architecture
Designers must balance:
- Instruction size (fixed or variable?)
- Number of registers
- Immediate sizes
- Opcode space
- Hardware speed

That’s why many RISC architectures (RISC-V, MIPS, ARM classic) choose:
- 32 registers
- 32-bit instruction size
- 32- or 64-bit register width

It’s a carefully chosen balance.

**Final Summary**
| Component           | Affects                              |
| ------------------- | ------------------------------------ |
| Instruction Size    | Encoding space                       |
| Number of Registers | Bits needed to encode register index |
| Register Size       | Datapath width & hardware complexity |

Only the number of registers directly impacts instruction encoding size.

## Size Speed Tradeoff
The hardware principle relating size and speed suggests that memory must be
slower than registers, since there are fewer registers. This suggestion is indeed the
case; data accesses are faster if data are in registers instead of memory.
Moreover, data are more useful when in a register. A RISC-V arithmetic
instruction can read two registers, operate on them, and write the result. A RISC-V
data transfer instruction only reads one operand or writes one operand, without
operating on it.

Thus, registers take less time to access and have higher throughput than memory,
making data in registers both considerably faster to access and simpler to use.
Accessing registers also uses much less energy than accessing memory. To achieve
the highest performance and conserve energy, an instruction set architecture must
have enough registers, and compilers must use registers efficiently.

Memory used for this is usually the stack.

General rule in computer hardware:
- Smaller storage → Faster access
- Larger storage  → Slower access

Why?
- Smaller structures are closer to the CPU
- They require shorter wires
- They need simpler circuitry

Example hierarchy:
| Storage Type | Typical Size | Speed     |
| ------------ | ------------ | --------- |
| Registers    | tens         | fastest   |
| Cache        | KB–MB        | fast      |
| Main memory  | GB           | slower    |
| Disk/SSD     | TB           | very slow |

Thus:
```
Registers < Cache < Main Memory < Storage
(fast)                              (slow)
```


**Why Registers Are Faster Than Memory**

Registers are located inside the CPU core.
Memory is located outside the core and accessed through:
- buses
- cache hierarchy
- memory controllers

So accessing memory requires more hardware steps.

Register access
```
CPU → register file → ALU
```
Memory access
```
CPU → cache → memory bus → DRAM → cache → CPU
```
This makes memory significantly slower.

**Registers Are More Useful for Computation**

In RISC architectures such as RISC-V instruction set architecture and MIPS architecture: **Arithmetic instructions only operate on registers.**
Example:
```nasm
add x5, x6, x7
```
Meaning:
```
x5 = x6 + x7
```
The instruction:
- reads two registers
- performs computation
- writes one register

All in one instruction.

**Throughput Difference**

Registers allow higher throughput.

Example pipeline behavior:

**Register operation**
```nasm
add x5, x6, x7
```
CPU can execute many per cycle.

**Memory operation**
```nasm
ld x5, 0(x10)
```
CPU must wait for memory subsystem.
So loads/stores often take multiple cycles.

**Energy Consumption**

Accessing registers also uses less energy.

Reason:
- register file is very small
- wires are short
- no external memory bus

Memory access requires:
- cache lookup
- DRAM activation
- bus transfers

Thus:
```
Register access energy << Memory access energy
```
This is extremely important in mobile processors.

**Why ISAs Provide Many Registers**

To reduce slow memory access, an ISA should provide enough registers.
Examples:
| Architecture                        | Registers |
| ----------------------------------- | --------- |
| RISC-V instruction set architecture | 32        |
| MIPS architecture                   | 32        |
| ARM architecture                    | 31        |
| x86 instruction set architecture    | 16        |

RISC architectures purposely increased the number of registers.

**Role of the Compiler**

Even if registers exist, performance depends on the compiler.

The compiler tries to:
1. Keep frequently used variables in registers
2. Avoid unnecessary memory access
3. Minimize register spilling

Example ideal code:
```nasm
add x5, x10, x11
add x6, x12, x13
add x7, x5, x6
```
No memory access required.

**Key Performance Rule**

Modern CPUs follow this principle: **Keep data in registers as long as possible**

Because:
- faster
- higher throughput
- lower energy consumption

**Summary**

Registers are faster than memory because they are located inside the CPU core and require fewer hardware steps. This makes them ideal for arithmetic operations. 
| Feature    | Registers          | Memory       |
| ---------- | ------------------ | ------------ |
| Size       | very small         | very large   |
| Speed      | fastest            | slower       |
| Energy     | low                | high         |
| Operations | arithmetic + logic | data storage |
| Throughput | high               | lower        |

Therefore: **High performance programs maximize register usage and minimize memory accesses**.

Let’s put the energy and performance of registers versus memory into
perspective. Assuming 64-bit data, registers are roughly 200 times faster (0.25 vs. 50
nanoseconds) and are 10,000 times more energy efficient (0.1 vs. 1000 picoJoules) than
DRAM in 2015. These large differences led to caches, which reduce the performance
and energy penalties of going to memory

## Limitation of Registers
Unlike programs in high-level languages, the operands of arithmetic instructions are restricted; they must be from a limited number of special locations built directly in hardware called registers. Registers are primitives used in hardware design that
are also visible to the programmer when the computer is completed, so you can think of registers as the bricks of computer construction.

In high-level languages (C, Java), you write:
```c
c = a + b;
```
It looks like variables live freely in memory.
But in RISC-V, arithmetic instructions like:
```nasm
add x3, x1, x2
```
can only operate on registers, not memory.
So the CPU requires:
- Load values from memory → into registers
- Perform arithmetic in registers
- Store result back to memory (if needed)

This is called a load-store architecture.

Registers are fast storage locations inside the CPU.

The ISA defines:
- Number of registers
- Register width
- Special-purpose registers

The size of a register in the RISC-V architecture is 64 bits; groups of 64 bits occur so frequently that they are given the name `doubleword` in the RISC-V architecture. (Another popular size is a group of 32 bits, called a `word` in the RISC-V architecture.)

:::info

**doubleword** Another natural unit of access in a computer, usually a group of 64 bits; corresponds to the size of a register in the RISC-V architecture.

:::

:::info

**word** A natural unit of access in a computer, usually a group of 32 bits.

:::

{/* Why Arithmetic Uses Registers (Not Memory) */}
One major difference between the variables of a programming language and registers
is the limited number of registers, typically 32 on current computers, like RISC-V. 

In RISC-V:
- There are 32 general-purpose registers
- Each register is 64 bits wide (in RV64)
- 64 bits = doubleword
- 32 bits = word

the three operands of RISC-V arithmetic instructions must each be chosen from one of the 32 64-bit registers.

The reason for the limit of 32 registers

1. **Physical Hardware Delay**

The reason for the limit of 32 registers may be found in the second of the three underlying design principles of hardware technology: "Design Principle 2: Smaller is faster". A very large number of registers may increase the clock cycle time simply because it takes electronic signals longer when they must travel farther.

If you increase the number of registers:
- The register file becomes larger
- Wiring becomes longer
- Signals must travel farther
- Access time increases

Longer access time → Slower clock → Lower performance

So more registers can slow down the CPU cycle time.

Guidelines such as "smaller is faster" are not absolutes; 31 registers may not be faster than 32. Even so, the truth behind such observations causes computer designers to take them seriously. In this case, the designer must balance the craving of programs for more registers with the designer’s desire to keep the clock cycle fast.

The Design Tradeoff, More registers:
- Fewer memory accesses
- Slower clock
- Larger instruction encoding

Fewer registers:
- Faster clock
- More memory traffic

So architects choose a balanced number. RISC architectures (like RISC-V and MIPS) typically use 32 registers.


2. **Instruction Encoding Size**

Another reason for not using more than 32 is the number of bits it would take in the instruction format.

Why does having more registers affect instruction size? Because the CPU must encode register numbers inside every instruction.

Each instruction must specify:
- Source register 1
- Source register 2
- Destination register

For Example:
```nasm
add x3, x1, x2
```
This instruction must contain:
1. The operation (add)
2. Source register 1 (x1)
3. Source register 2 (x2)
4. Destination register (x3)

All of that must fit into 32 bits.

If we have 32 registers:
- We need 5 bits to identify one register (because 2⁵ = 32)
```
00000 → x0
00001 → x1
...
11111 → x31
```
- An instruction like:
```nasm
add x3, x1, x2
```
needs:
* 5 bits for destination
* 5 bits for source 1
* 5 bits for source 2

So for 3 registers: 5 + 5 + 5 = 15 bits, That’s already almost half the instruction!
The rest of the bits are used for:
- Opcode
- Function codes
- Other control fields

- RISC-V instructions are 32 bits long.

If we had 128 registers:
- We’d need 7 bits per register (2⁷ = 128)
- 7 × 3 = 21 bits just for register fields
- That would:
    - Leave fewer bits for opcode and other fields
    - Force longer instructions
    - Increase instruction size
    - Hurt performance and memory efficiency

If register fields get bigger:
1. Instructions may need to become longer (e.g., 48-bit or 64-bit instructions)
2. **Larger instructions mean**:
    * More memory usage
    * Fewer instructions fit in cache
    * Slower instruction fetch
3. More complex hardware decoding

So increasing registers increases encoding cost.

{/* Why 32 Is a Sweet Spot */}
With 32 registers:
- 5-bit fields are compact
- Instructions stay 32 bits
- Decoding is simple
- Hardware stays fast

It’s a balance between:
- Too few registers → too many memory accesses
- Too many registers → instruction bloat + slower decode

So 32 is a practical balance.

ISA design is a compromise between:
- Hardware physics
- Encoding efficiency
- Software convenience

**Registers are limited because: Making something bigger in hardware doesn’t always make it faster**. That is the deeper architectural lesson.

**Simple Real-Life Analogy**

Imagine writing instructions on a small 32-character sticky note.
You must write:
- Operation name
- Register A
- Register B
- Register C

If register names are short (R1, R2, R3), it fits.
If register names are long (Register127, Register88…), you run out of space.
So the size of the register set affects how long the instruction must be.

## Register Naming Conventions
Although we could simply write instructions using numbers for registers, from 0 to 31, the RISC-V convention is x followed by the number of the register, except for a few register names for clarity and consistency.

Registers Are Just Numbers in Hardware, Inside RISC-V, registers are simply numbered:
```
0, 1, 2, 3, ..., 31
```
Hardware sees them as:
```
00000 → register 0
00001 → register 1
...
11111 → register 31
```
Because: $2^5 = 32$, So 5 bits identify one register.

**Why Use "x" Before the Number?**
Instead of writing:
```
add 3, 1, 2
```
RISC-V uses:
```nasm
add x3, x1, x2
```
The x simply means: "This is a register", It prevents confusion between:
- Register numbers
- Immediate values
- Memory addresses

Example:
```nasm
addi x3, x1, 5
```
Here:
- x3 → register
- x1 → register
- 5 → immediate value

Without the "x", it would be unclear.

#### Special Named Registers (ABI Names)
Although registers are numbered x0–x31, many also have conventional names used by compilers and programmers.

For example:
| Register | ABI Name | Purpose            |
| -------- | -------- | ------------------ |
| x0       | zero     | Always 0           |
| x1       | ra       | Return address     |
| x2       | sp       | Stack pointer      |
| x10–x17  | a0–a7    | Function arguments |
| x5–x7    | t0–t2    | Temporaries        |
Example:
```
add a0, a1, a2
```
This is exactly the same as:
```
add x10, x11, x12
```
The ABI names make code more readable.

x0 is hardwired to zero.
That means:
```c
add x5, x0, x6
```
Copies x6 into x5.
Because x0 is always 0.
This simplifies hardware and instruction design.

There are three levels:
| Level    | Representation         |
| -------- | ---------------------- |
| Hardware | 5-bit binary number    |
| ISA      | Register number (0–31) |
| Assembly | x0–x31 or ABI names    |

So:
- Hardware cares about bits.
- ISA defines register numbering.
- Assembly gives them readable names.

## Zero Register (x0)
In RISC-V, `x0` is hard-wired to zero
- Reading `x0` always returns `0`
- Writing to `x0` has no effect (it ignores writes)

This is different from normal registers which can store any value.

**Why Have a Zero Register?**
1. **Simplifies instruction set**
    - You don’t need special instructions for moving constants like `0`
    - Many operations can use `x0` instead of loading zero from memory
    - Example: to move a value from `x5` to `x6`, you can do:
      ```nasm
      addi x6, x5, 0    x6 = x5 + 0
      ```
      Here, ``0`` can be replaced by `x0` in some pseudo-instructions.

2. **Negate a value**
    - Negation: `-x5`
    - Use sub instruction with `x0` as the first operand:
      ```nasm
      sub x6, x0, x5    x6 = 0 - x5 = -x5
      ```
      This avoids needing a separate NEG instruction.

3. **Make the common case fast**
    - Include frequently used constants in the instruction set
    - `0` is extremely common in programs: initialization, loop counters, comparisons, arithmetic
    - So `x0` reduces instruction count and simplifies hardware.

**Other Useful Patterns with x0**
| Pattern           | Example             | Explanation                            |
| ----------------- | ------------------- | -------------------------------------- |
| Move a register   | `addi x6, x5, 0`    | Copy `x5` to `x6` using zero immediate |
| Negate a register | `sub x6, x0, x5`    | Compute `-x5`                          |
| Clear a register  | `addi x5, x0, 0`    | Set `x5` to 0                          |
| Compare to zero   | `beq x5, x0, label` | Branch if `x5 == 0`                    |

**Hardware Benefits**
- No need to generate 0 in a temporary register
- Fewer instructions → higher throughput
- Simpler instruction encoding
- Makes the common case fast, exactly what RISC-V targets

## Sign Extension
Modern CPUs often have 64-bit registers, but memory may store smaller data types:
| Data type  | Size    |
| ---------- | ------- |
| byte       | 8 bits  |
| halfword   | 16 bits |
| word       | 32 bits |
| doubleword | 64 bits |

Example: loading a byte (8 bits) into a 64-bit register.

Memory byte:
```
10110010
```
The CPU must decide: How do we fill the remaining 56 bits?

If the number is **signed**, the processor copies the sign bit repeatedly into the higher bits. This is called **sign extension**. but its purpose is to place a correct representation of the number within that register

Example

Byte in memory:
```
10110010
```
Sign bit = 1 → negative number.

After sign extension into a 64-bit register:
```
11111111 11111111 11111111 11111111
11111111 11111111 11111111 10110010
```
The upper bits become 1 because the number is negative. This preserves the correct value when used in arithmetic.

If the number is **unsigned**, the CPU fills the upper bits with 0s (**Zero Extension**).

Example:

Memory byte:
```
10110010
```
Loaded into a 64-bit register with zero extension:
```
00000000 00000000 00000000 00000000
00000000 00000000 00000000 10110010
```
Upper bits are 0 because the number is always non-negative.

When a smaller signed number (like 12 bits) must be used inside a larger register (32 or 64 bits), we must preserve its sign. So we extend it to full width by copying the sign bit into the new upper bits. That’s called: **Sign extension**.

The ALU operates on full-width registers:
- 32 bits in RV32
- 64 bits in RV64

But immediates are only 12 bits. So before using the immediate in the ALU, the CPU must convert:
```
12-bit signed value  →  32-bit signed value
```

**Why It Works**

This trick works because positive two’s complement numbers really have an infinite
number of `0s` on the left and negative two’s complement numbers have an infinite
number of `1s`. The binary bit pattern representing a number hides leading bits to fit
the width of the hardware; sign extension simply restores some of them.

In two’s complement: Negative numbers are represented so that: Extending the sign bit keeps the numeric value unchanged

Example:
- `-3` in 4 bits: `1101`
- `-3` in 8 bits: `11111101`

Same pattern — just more leading 1s.

Think of it like this:
- If the number is positive: Add more `0s` on the left.
- If the number is negative: Add more `1s` on the left.

Because in two’s complement: Leading `1s` mean "still negative".

**Example: Positive Immediate**

12-bit value: `0000 0000 0101`

MSB = 0 → positive (+5)

Sign extend to 32 bits: `00000000 00000000 00000000 00000101`

We fill upper bits with 0s.

**Example: Negative Immediate**

Suppose the 12-bit immediate is: `1111 1111 1101`

MSB = 1 → negative

This is `-3` in 12-bit two’s complement.To sign extend to 32 bits:

We copy the sign bit (1) into all upper bits: `11111111 11111111 11111111 11111101`

Now it is `-3` in 32-bit two’s complement. The value is preserved.

If we incorrectly filled upper bits with 0: `00000000 00000000 00001111 11111101`

That would be: 4093 (positive), Instead of: -3, That would completely break arithmetic.

Signed versus unsigned applies to loads as well as to arithmetic. 

signed vs unsigned interpretation affects load instructions, especially when the loaded data is smaller than the register size. The key concept is sign extension vs zero extension.

RISC-V does offer two flavors of byte loads:
| Instruction | Meaning            | Extension      |
| ----------- | ------------------ | -------------- |
| `lb`        | load byte          | sign extension |
| `lbu`       | load byte unsigned | zero extension |

load byte unsigned (`lbu`) treats the byte as an unsigned number and thus zero-extends to fill the leftmost bits of the register, while load byte (`lb`) works with signed integers.

Example

Memory:
```
address A → 10110010
```
Signed load
```nasm
lb x5, 0(x10)

Result in x5:
```
11111111 11111111 ... 10110010
```
Unsigned load
```nasm
lbu x5, 0(x10)
```
Result in x5:
```
00000000 00000000 ... 10110010
```

**Why This Matters**

Suppose the byte represents `-78` in two's complement:
```
10110010
```
With sign extension, arithmetic remains correct:
```
-78 + 10 = -68
```
Without sign extension, the value would be interpreted incorrectly as 178.

Since C programs almost always use bytes to represent characters rather than consider bytes as very short signed integers, `lbu` is used practically
exclusively for byte loads.

Example:
```c
char c = 'A';
```
ASCII values are `0–127`, so they should not become negative.

Therefore compilers typically use:
```
lbu
```
so that characters become:
```
00000000 ... ASCII_value
```

When loading a `64-bit doubleword` into a `64-bit register`, signed and unsigned loads are identical. So no extension is needed:
```
Memory: 64 bits
Register: 64 bits
```
Example:
```nasm
ld x5, 0(x10)
```
The value simply copies directly. 

**Summary**
| Concept            | Signed Load    | Unsigned Load       |
| ------------------ | -------------- | ------------------- |
| Extension type     | sign extension | zero extension      |
| Fill bits with     | sign bit       | zeros               |
| RISC-V instruction | `lb`           | `lbu`               |
| Typical C usage    | rare           | common (characters) |

## Register spilling
Many programs have more variables than computers have registers. Consequently,
the compiler tries to keep the most frequently used variables in registers and places
the rest in memory, using loads and stores to move variables between registers and
memory. The process of putting less frequently used variables (or those needed
later) into memory is called **spilling registers**.

**Register spilling** means: Moving a register value into memory temporarily so the register can be reused. Later the value can be reloaded back into a register.


**Example Without Spilling**

Suppose we compute:
```
x = (a + b) + (c + d);
```
If enough registers exist:
```
add r1, a, b
add r2, c, d
add x, r1, r2
```
Everything stays inside registers. Fast execution.

**Example With Spilling**

Suppose only two registers are available.

Computation:
```
x = (a + b) + (c + d);
```
Compiler must temporarily store intermediate results.

Example assembly:
```
add r1, a, b         r1 = a + b
store r1, temp       spill to memory

add r1, c, d         reuse r1
load r2, temp        reload spilled value

add x, r1, r2
```
Now we see extra memory operations. These are called spill code.

**Example in RISC-V**

Assume registers are limited.
```nasm
add x5, x10, x11     x5 = a + b
sd  x5, 0(sp)        spill to stack

add x5, x12, x13     x5 = c + d
ld  x6, 0(sp)        reload spilled value

add x7, x5, x6
```
Stack memory holds the temporary value.


Spilled Values Usually Stored on the stack. Example stack layout:
``` 
High memory
+------------------+
| saved registers  |
+------------------+
| spilled values   |
+------------------+
| local variables  |
+------------------+
sp →
Low memory
```
Typical spill code:
```nasm
sd x5, -8(sp)     store spilled value
ld x5, -8(sp)     reload later
```

Spilling Is Expensive as Registers are extremely fast. Typical latency:
| Storage  | Cycles |
| -------- | ------ |
| Register | 1      |
| L1 Cache | 3–5    |
| RAM      | 50–100 |

So spilling introduces extra memory access:
```
Store to memory
Later load from memory
```
This slows programs.

### Compiler Strategy
The compiler tries to:
1. Keep frequently used variables in registers
2. Spill rarely used variables

This is done using an algorithm called **register allocation**. A famous approach uses **graph coloring**.

The compiler determines which variables are live at the same time.

Variables that overlap cannot share a register.
 
**Example of Variable Lifetimes**
 
Example code:
```
x = a + b
y = c + d
z = x + y
```
Variable usage timeline:
```
 a b ──┐
       ├─ x ──┐
 c d ──┘      ├─ z
              └─ y
```
Compiler tries to reuse registers when lifetimes do not overlap.

**Example of Real Compiler Output**

C code:
```c
int f(int a,int b,int c,int d,int e)
{
    return (a+b) + (c+d) + e;
}
```
Possible generated code:
```nasm
add x5, x10, x11
add x6, x12, x13
add x5, x5, x6
add x10, x5, x14
```
If registers were insufficient:

```nasm
add x5, x10, x11
sd  x5, 0(sp)      spill

add x5, x12, x13
ld  x6, 0(sp)      reload

add x5, x5, x6
add x10, x5, x14
```
### Real GCC example where spilling happens
show how a real GCC example where spilling happens, including the exact assembly the compiler generates when registers run out. This reveals how compilers actually implement spilling in practice.

We’ll use the architecture defined by RISC-V instruction set architecture.

1. **Example C Program**
```c
long compute(long a, long b, long c, long d, long e, long f)
{
    long x = a + b;
    long y = c + d;
    long z = e + f;
    return x + y + z;
}
```
Here we have many intermediate variables:
```
a b c d e f x y z
```
Even though RISC-V has many registers, calling conventions reserve some registers, so the compiler may still need to spill values.

2. **Function Arguments in RISC-V**

RISC-V passes arguments in registers:
| Argument | Register |
| -------- | -------- |
| a        | x10      |
| b        | x11      |
| c        | x12      |
| d        | x13      |
| e        | x14      |
| f        | x15      |

3. **Assembly WITHOUT Spilling (Ideal Case)**

If enough registers are available:
```nasm
add x5, x10, x11     x = a + b
add x6, x12, x13     y = c + d
add x7, x14, x15     z = e + f
add x5, x5, x6       x + y
add x10, x5, x7      return value in x10
ret
```
Everything happens inside registers. Fast execution.

4. **Assembly WITH Spilling**

If registers are limited, the compiler must store temporary values on the stack.

Example:
```nasm
addi sp, sp, -16      create stack space

add x5, x10, x11      x = a + b
sd  x5, 0(sp)         spill x to stack

add x5, x12, x13      y = c + d
ld  x6, 0(sp)         reload x

add x5, x5, x6        x + y
sd  x5, 8(sp)         spill partial result

add x5, x14, x15      z = e + f
ld  x6, 8(sp)         reload partial result

add x10, x5, x6       final result

addi sp, sp, 16       restore stack
ret
```

5. **What Happened Here**

The compiler needed to reuse registers, so it temporarily stored values.

Stack layout:
```
Memory
+----------------+
| x + y          | 8(sp)
+----------------+
| x              | 0(sp)
+----------------+
sp
```
Operations performed:
```
store x
reload x
store (x+y)
reload (x+y)
```
These extra instructions are called: spill code

6. **Why the Stack Is Used**

Spilled values are usually stored relative to the stack pointer (sp).

Example instructions:
```
sd x5, 0(sp)     store register to stack
ld x6, 0(sp)     load from stack
```
This makes stack memory act as temporary storage for registers.

7. **Visual Execution Flow**
```
Registers full
      ↓
Compiler spills variable
      ↓
Register → Memory (stack)
      ↓
Register reused
      ↓
Memory → Register (reload)
```
8. **Performance Impact**

Registers are much faster than memory.

Typical latency:
| Location | Cycles |
| -------- | ------ |
| Register | 1      |
| L1 cache | 3–5    |
| RAM      | 50–100 |

Spilling introduces extra loads and stores, slowing the program.

9. **What the Compiler Tries to Do**

Compilers try to minimize spilling using register allocation algorithms.

Common technique: Graph coloring register allocation, Idea:
1. Track live variables
2. Assign registers
3. Spill only when necessary

10. Key Idea
- Registers = fast but limited
- Memory    = slow but large

So the compiler:
- keeps hot variables in registers
- spills cold variables to memory

| Concept            | Meaning                                      |
| ------------------ | -------------------------------------------- |
| Register spilling  | Moving register values to memory temporarily |
| Why needed         | Programs have more variables than registers  |

## Role of registers in data transfer instructions
{/* this paragraph is explaining the role of registers in data transfer instructions, especially for addressing arrays, and how that concept evolved. */}
**Base Register in Data Transfer Instructions**

In RISC-V (and most load/store architectures):
```nasm
ld x5, 16(x6)
```
- `x6` is called the base register
- `16` is the offset
- Address computed: `Memory[x6 + 16]`

The register in the data transfer instructions was originally invented to
hold an index of an array with the offset used for the starting address of an array. Thus,
the base register is also called the **index register**.

So, Historical Indexing Arrays Originally:
- Computers had small memories
- Arrays were often small, so offsets could fit in instruction fields (5–12 bits)
- The base register could store the starting address of the array
- The offset could be used to select the specific element

Example:
```
A[i]   // element i of array A
```
RISC-V assembly:
```nasm
ld x5, i*8(x6)    x6 = base address of A
```
- `x6` = start of array
- `i*8` = offset for element `i` (for doubleword arrays)

Base register = `index register` in early terminology.

Today’s memories are much larger,
and the software model of data allocation is more sophisticated, so the base address of
the array is normally passed in a register since it won’t fit in the offset.

So Today:
- Memories are much larger
- Arrays can be very large → offsets may not fit in the instruction field
- Modern compilers:
    - Pass base addresses in registers
    - Compute large offsets using arithmetic instructions
    - Then use load/store with offset = 0 or a small constant

Example:
```nasm
addi x7, x0, 120        compute large offset
add  x8, x6, x7         x8 = base + offset
ld   x5, 0(x8)          load element
```
- `x6` still holds array base
- `x7` is computed offset
- `x8` = full address

**Example: RISC-V Full Load Sequence**

C code:
```c
long A[100];
int i = 12;
x = A[i];
```
RISC-V assembly:
```nasm
addi x7, x0, 12*8    element offset = i*8
add  x8, x22, x7     x22 = base of A, x8 = full address
ld   x5, 0(x8)       load A[12] into x5
```
- `x22` = base register for array
- `x7` = offset
- `x8` = computed full address
