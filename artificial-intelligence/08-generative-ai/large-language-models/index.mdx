{/* ## LLM Fundamentals (Large Language Model Fundamentals) */}

LLM Fundamentals cover the concepts, architectures, mathematical principles, and techniques behind Large Language Models (LLMs) such as GPT, Claude, Gemini, and Llama.

To understand LLMs, you need to understand how computers process language, how neural networks learn patterns from text, how Transformers work, and how models generate responses.

LLMs are a special class of AI models trained on vast amounts of text data to perform NLP tasks. 

LLMs are a major part of Generative AI. They are responsible for many language-related capabilities, including:

- Text generation and completion.
- Question answering.
- Text summarization.
- Translation between languages.
- Code generation.
- Reasoning and problem-solving.
- Information extraction.
- Conversational AI.

Let's build an understanding from the foundations to the internal mechanisms.

## 1. What Is an LLM?

An LLM (Large Language Model) is a neural network trained on enormous amounts of text data to learn statistical and structural patterns in human language.

Its primary training objective is usually to predict the next token based on the tokens that came before it.

For example, consider this sentence:

```
Artificial Intelligence is transforming the ...
```

An LLM might predict:

| Possible next token | Probability |
| ------------------- | ----------- |
| world               | 0.45        |
| industry            | 0.25        |
| future              | 0.15        |
| technology          | 0.10        |
| other tokens        | 0.05        |

The model uses these predictions to generate text one token at a time.

Importantly, an LLM does not simply store and retrieve complete sentences. It learns numerical representations and relationships between tokens through training.

## 2. How Does an LLM Work?

At a high level, an LLM processes text through several stages.

At a high level, LLMs process text input (natural language understanding, or NLU) and generate meaningful responses (natural language generation, or NLG)

[How a Large Language Model (LLM) Works |](https://images.openai.com/static-rsc-4/q4aSN7iia49adWHket7RlcxTNl58jUPjkle2RjqFqnjTYYnnvOgx_n_cVbFApTnOM82sWdSmF7RWhMcYYKUo2C1Pz_0bMqtWJD0yO9wFP61mGEsdx0dRTiE6DG1lcWynDrcz9cTN6I5BtVDWTDxh-XX7rAfcFYqN01IyOVf5nZY?purpose=inline)

[digenaldo.com](https://digenaldo.com/posts/how-a-large-language-model-llm-works/?utm_source=chatgpt.com)

Let's follow a simple example.

Input:

```
Explain how computers work.
```

Step 1: Tokenization

The input text is divided into smaller units called tokens.

```
"Explain how computers work."

       |
       v

["Explain", " how", " computers", " work", "."]
```

Actual tokenization depends on the tokenizer. A word can be represented by one token or several tokens.

Step 2: Token IDs

Each token is converted into a numerical ID.

```
["Explain", " how", " computers", " work", "."]

       |
       v

[15234, 703, 12892, 1495, 13]
```

These numbers are illustrative.

Step 3: Embeddings

Each token ID is converted into a vector of numerical values.

For example:

```
"computer" → [0.21, -0.45, 0.78, 0.12, ...]
```

These vectors are called embeddings.

They provide numerical representations that the neural network can process.

Step 4: Transformer Processing

The embeddings pass through Transformer layers.

These layers use mechanisms such as:

- Self-attention.
- Feed-forward neural networks.
- Residual connections.
- Layer normalization.

The model learns contextual relationships between tokens.

Step 5: Probability Prediction

The model produces scores (logits) for possible next tokens.

These scores are converted into probabilities using a softmax function.

Step 6: Text Generation

The model selects a token according to its generation strategy, appends it to the sequence, and repeats the process.

```
Input:
Explain how computers work

Generated:
Explain how computers work by processing
information through hardware and software...
```

## 3. Core LLM Concepts

These are the fundamental concepts you should understand before studying Transformer architecture in detail.

### Natural language understanding
**NLU** focuses on interpreting and analyzing human input. It is meant for tasks like intent recognition, entity extraction, text classification, and sentiment analysis. This is conceptually similar to the way Java applications parse JSON or XML, extracting key data for business logic. If you are building an AI-powered search or recommendation system, an encoder-based model (e.g., BERT, described later in this chapter) optimized for NLU is typically a good fit.

### Natural language generation
NLG is responsible for constructing meaningful and coherent responses. This is
useful for chatbots, report generation, and text summarization. Conceptually, this
mirrors Java’s templating engines (e.g., Thymeleaf and Apache FreeMarker) that
dynamically generate output based on structured input. Decoder-based models
(e.g., GPT, also described later in this chapter) are more suited for these tasks.
### 3.1 Tokens and Tokenization

A token is a unit of text processed by an LLM.

Tokens can represent:

- Complete words.
- Parts of words.
- Individual characters.
- Punctuation.
- Whitespace combined with text.

For example:

```
"Understanding artificial intelligence"
```

Could be tokenized as:

```
["Understanding", " artificial", " intelligence"]
```

Why is tokenization important?

1. Neural networks process numerical data, not raw text.
2. Tokenization converts language into a manageable numerical representation.
3. Token count influences context-window limits.
4. Token count affects inference cost and processing time.

Important concepts:

- Vocabulary.
- Token IDs.
- Subword tokenization.
- Byte Pair Encoding (BPE).
- WordPiece.
- SentencePiece.
- Tokenizer vocabulary size.

### 3.2 Embeddings

Embeddings represent tokens as numerical vectors in a high-dimensional space.

For example:

```
"King"    → [0.21, 0.45, 0.78, ...]
"Queen"   → [0.19, 0.51, 0.75, ...]
"Computer"→ [0.82, 0.13, 0.24, ...]
```

The numbers above are illustrative.

The important idea is that embeddings allow models to represent relationships between words and other tokens mathematically.

For example, semantically related words can have similar vector representations.

Topics:

- Word embeddings.
- Static vs contextual embeddings.
- Embedding dimensions.
- Vector similarity.
- Cosine similarity.
- Positional embeddings.
- Learned positional embeddings.
- Rotary Position Embeddings (RoPE).

### 3.3 Parameters and Weights

Parameters are the trainable numerical values inside a neural network.

An LLM may contain billions of parameters.

For example:

```
LLM
 |
 +-- Embedding parameters
 |
 +-- Transformer Layer 1
 |      |
 |      +-- Attention weights
 |      +-- Feed-forward weights
 |
 +-- Transformer Layer 2
 |      |
 |      +-- Attention weights
 |      +-- Feed-forward weights
 |
 +-- ...
 |
 +-- Output projection weights
```

During training, these parameters are adjusted to improve the model's predictions.

Important concepts:

- Model parameters.
- Weights and biases.
- Trainable vs non-trainable parameters.
- Parameter count.
- Model size.
- Quantization.
- Precision (FP32, FP16, BF16, INT8, INT4).

### Self-attention mechanisms (transformer architecture)
LLMs built on transformers use a self-attention mechanism to determine which
words (tokens) matter most within a sentence. Instead of treating each word
equally, the model assigns higher importance—or attention—to key words based
on their relevance to the overall meaning. This process is like an IDE’s debugger
highlighting variables or expressions that are most relevant at a given breakpoint:
the values in scope, recent assignments, or key branches in logic get your focus,
while the rest fades into the background. Similarly, in self-attention, the model
dynamically focuses on the most contextually important tokens to understand
and generate language effectively.

### 3.4 Context Window

The context window is the amount of token information a model can process in a particular interaction.

For example:

```
Context Window: 8,192 tokens

+----------------------------------+
| System instructions              |
|                                  |
| User message                     |
|                                  |
| Previous conversation            |
|                                  |
| Retrieved documents              |
|                                  |
| Generated response               |
+----------------------------------+
```

A larger context window allows a model to consider more information at once.

However, a larger context window does not guarantee that the model will accurately use every piece of information.

The context window is analogous to a buffer size or a stack frame in Java. Just
as a method in Java has a limited stack frame size to store local variables, an
LLM has a fixed memory space to store input and output tokens. For example, an
LLM with a 4,000-token context window (such as GPT-3.5) can process roughly
3,000 words at a time before discarding older tokens. Larger models (e.g., GPT-4
Turbo, Claude 3 Opus) support more than 128,000 tokens, which allow for much
longer interactions without losing past context.

Important concepts:

- Context length.
- Input tokens.
- Output tokens.
- Context-window limits.
- Long-context processing.
- Context management.
- Attention complexity.

### 3.5 Attention Mechanism

Attention allows the model to determine which other tokens are relevant when processing a particular token.

Consider:

```
The developer fixed the bug because he understood the problem.
```

When processing "he", the model can use attention to associate it with "developer".

This helps the model understand relationships across a sequence.

Important concepts:

- Query (Q).
- Key (K).
- Value (V).
- Scaled dot-product attention.
- Self-attention.
- Multi-head attention.
- Causal attention.
- Cross-attention.

We will explore these in detail when studying Transformer architecture.

### 3.6 Inference

Inference is the process of using an already-trained model to generate predictions or responses.

There are two major phases:

| Phase     | Description                                                          |
| --------- | -------------------------------------------------------------------- |
| Training  | Adjusting model parameters using training data.                      |
| Inference | Using learned parameters to process new inputs and generate outputs. |

For example:

```
             Training
                |
                v
       Trained LLM Model
                |
                v
       User submits prompt
                |
                v
             Inference
                |
                v
       Generated response
```

Important inference concepts:

- Forward propagation.
- Autoregressive generation.
- Decoding strategies.
- Sampling.
- Greedy decoding.
- Temperature.
- Top-K sampling.
- Top-P (nucleus) sampling.
- KV cache.
- Tokens per second.
- Time to first token (TTFT).

## Lifecycle of LLMs
The LLM Lifecycle describes the complete journey of a Large Language Model, starting from the initial idea and data collection, continuing through model development, training, evaluation, deployment, and finally ongoing monitoring, maintenance, and retirement.

In other words, it explains how an LLM is created, prepared for real-world use, operated in production, and continuously improved.

Understanding the lifecycle is important because building an LLM is not simply a matter of training a neural network. It involves data engineering, machine learning, software engineering, infrastructure, security, and operations.

### simplified view of the LLM development and usage process
a simplified view of the LLM development and usage process, organized into three major phases:

1. Training – Build the initial language model.
2. Tuning – Adapt the model to specific tasks and desired behavior.
3. Inference – Use the model to solve real-world problems.

#### Phase 1: Training

at the heart of the lifecycle lies the training phase. This is where LLMs are fed unbelievable
amounts of data to learn from and adapt to. Once an LLM has been trained, it is
somewhat a general-purpose model. Usually, those models are also referred to as
foundation models. In particular, if we look at very large models like Llama 3, for
example, their execution requires huge amounts of resources, and they are typically
exceptionally good at general-purpose tasks.

The purpose of this phase is to create a pretrained model that learns general language capabilities.

##### 2.1 Data

Example:

```
Raw datasets
     |
     v
Data cleaning
     |
     v
Data filtering
     |
     v
Deduplication
     |
     v
Tokenization
     |
     v
Training dataset
```

The output is a dataset ready for model training.

##### 2.2 Simulation and Test

This stage involves experimenting with datasets, model configurations, and training approaches before committing to large-scale training.

It can include:

- Testing data quality.
- Validating tokenization.
- Experimenting with small training runs.
- Testing model configurations.
- Evaluating training objectives.
- Testing model behavior on validation datasets.

For example, before training a model on billions of tokens, we might perform a small experiment to determine whether our dataset and model configuration work correctly.

Important: Testing is not restricted to this stage. Evaluation also takes place during and after training and tuning.

##### 2.3 Training

This is where the actual model training happens.

The model learns through:

1. Forward propagation.
2. Next-token prediction.
3. Loss calculation.
4. Backpropagation.
5. Weight updates.

The output is a pretrained LLM.

```

Transformer Model

Next-token Prediction
       |
       v
Loss Calculation
       |
       v
Backpropagation
       |

Updated Model Parameters
       |
       v
Pretrained LLM
```

#### Phase 2: Tuning

The next phase a model usually goes through is fine-tuning. Here, we adjust the model’s parameters to optimize its performance on specific tasks or datasets. Through the process of hyperparameter tuning, model architects can fine-tune models for greater accuracy, efficiency, and scalability. This is generally called hyperparameter
optimization and includes techniques like grid search, random search, and Bayesian methods.

The purpose of tuning is to adapt the pretrained model to specific requirements.

There are differnt approaches.

##### 2.4 Prompt Tuning

Prompt tuning is a parameter-efficient adaptation technique.

Instead of updating all the model's parameters, it introduces trainable prompt embeddings (sometimes called soft prompts) that guide the model toward a particular task.

For example:

```
Pretrained LLM
      |
      v
Trainable Prompt Embeddings
      |
      v
LLM Processing
      |
      v
Task-specific Output
```

Prompt tuning is different from writing ordinary text instructions.

It is a training-based technique that optimizes prompt representations.

##### 2.5 Fine-Tuning

Fine-tuning adapts a pretrained model using additional training data.

For example, suppose we have a general-purpose pretrained LLM and want to make it better at Java programming.

We provide it with a dataset containing Java questions, explanations, and code examples.

```
Pretrained LLM
      |
      v
Java Training Dataset
      |
      v
Fine-Tuning
      |
      v
Java-oriented LLM
```

Common approaches include:

- Supervised Fine-Tuning (SFT).
- Full Fine-Tuning.
- LoRA.
- QLoRA.
- Parameter-Efficient Fine-Tuning (PEFT).

##### 2.6 Alignment Tuning

Alignment tuning aims to make model behavior better match human preferences, instructions, and safety requirements.

For example:

```
User:
Explain Java inheritance.

Response A:
A clear, accurate explanation with examples.

Response B:
An incorrect and confusing explanation.

Human preference:
Response A
```

Preference data can be used to improve model behavior.

Common approaches include:

- RLHF.
- DPO.
- Reward Modeling.
- Safety Fine-Tuning.

The output of this phase is an adapted, instruction-following, or aligned model, depending on the techniques applied.

#### Phase 3: Inference

The last and probably most well-known part of the lifecycle is inference, which is
another word for querying a model. In the context of LLMs, inference refers to the
process of drawing conclusions from observations or premises, which is a much more
accurate description of what a model delivers.

Inference is the process of using an already-trained model to generate responses.

Unlike training and tuning, inference normally does not update the model's learned parameters.

There are several ways to query a model, and they can affect the quality and accuracy
of the results, so it’s important to understand the various approaches. One key aspect
is the way you structure your query, and this is where prompt engineering comes into
play. Prompt engineering crafts the input or question in a way that guides the model
toward providing the most useful and relevant response. 

Another important concept is data enrichment, which refers to enhancing the data the model has access to
during its processing. One powerful technique for enrichment is retrieval-augmented
generation (RAG), where the model combines its internal knowledge with external,
up-to-date information retrieved from a database or document source.

##### 2.7 Prompt Engineering

Prompt engineering means designing effective instructions and input context to guide an LLM's responses.

Example:

Without prompt engineering:

```
Explain Kubernetes.
```

With prompt engineering:

```
You are an experienced Kubernetes engineer.

Explain Kubernetes to a beginner.

Include:
1. Definition
2. Architecture
3. Main components
4. Practical YAML example
5. Common use cases
```

The second prompt provides more specific instructions.

The model remains unchanged; only the input prompt changes.

##### 2.8 Retrieval-Augmented Generation (RAG)

RAG combines an LLM with an external information retrieval system.

Instead of relying exclusively on knowledge learned during training, the application retrieves relevant information from external sources and supplies it to the model.

Example:

```
User Question
     |
     v
Embedding Model
     |
     v
Vector Database
     |
     v
Retrieve Relevant Documents
     |
     v
Build Augmented Prompt
     |
     v
LLM
     |
     v
Generated Answer
```

For example, a TechnoWiki assistant could retrieve the relevant Kubernetes documentation before answering a question.

RAG does not normally require retraining the underlying LLM.

However, document ingestion and indexing happen beforehand, outside the actual per-request inference flow.

### Important differences between the tuning and inference techniques

There are some similarly named concepts in your diagram that are worth distinguishing.

| Technique          | Phase     | Updates model weights?                             | Purpose                   |
| ------------------ | --------- | -------------------------------------------------- | ------------------------- |
| Prompt tuning      | Tuning    | Updates trainable prompt parameters                | Adapt model behavior      |
| Fine-tuning        | Tuning    | Usually yes; PEFT updates only selected parameters | Specialize the model      |
| Alignment tuning   | Tuning    | Usually yes, depending on method                   | Improve desired behavior  |
| Prompt engineering | Inference | No                                                 | Guide individual requests |
| RAG                | Inference | No, normally                                       | Supply external knowledge |

The most important distinction is:

Prompt tuning is a model adaptation technique, whereas prompt engineering is an inference-time technique.

#### 2. Problem Definition and Planning

Stage 1

Before developing an LLM, we need to determine what problem we want it to solve.

Not every application needs a model trained from scratch. Depending on the requirements, we might use an existing pretrained model, fine-tune one, or build a new model.

##### Main activities

- Identify the business or technical problem.
- Define the intended users.
- Identify the required capabilities.
- Determine whether an existing model is sufficient.
- Define performance and quality requirements.
- Estimate computational and financial resources.
- Identify privacy, security, and regulatory requirements.

##### Example

Imagine building an AI assistant for TechnoWiki.

Our objective is to create an assistant that can:

- Answer questions about Java.
- Explain Kubernetes concepts.
- Generate programming examples.
- Search technical documentation.
- Provide answers based on the documentation.

We can define the requirements as follows:

| Requirement | Description                    |
| ----------- | ------------------------------ |
| Task        | Technical question answering   |
| Input       | Natural language questions     |
| Output      | Explanations and code examples |
| Knowledge   | Technical documentation        |
| Model type  | Instruction-following LLM      |
| Deployment  | Backend API                    |
| Quality     | Accurate and relevant answers  |

Important decision: Should we train an LLM from scratch?

Probably not. An existing pretrained LLM combined with RAG may be sufficient.

##### Main processing steps

[What Is Pre-Training? From Raw Data to Model Weights](https://images.openai.com/static-rsc-4/426PjCsdj-MlBfCG9TQ-c7lw5BNmDaB9qfwJnETMm4fYaDsM3iXDN6Q3ZiTDkdhJBrEulggx8OjA6aVeakpKX1ZnUnhisznS0yWQFpgZG3kF1wfZwWlnY7z9iUmqhsrwPvBqvWjwbY020wjPye-DzFdJ5GQqmXHt8gCKheSREiE?purpose=inline)

Remove corrupted, incomplete, or unusable data.

Identify and remove duplicate documents or repeated content.

Remove irrelevant, low-quality, or unsuitable content.

4\. Data Normalization

Standardize formatting and representations where appropriate.

Convert text into sequences of tokens using a tokenizer.

Example:

```
Raw text:

After tokenization:

 " interesting", "."]
```

Divide data into different subsets when appropriate.

| Dataset        | Purpose                                           |
| -------------- | ------------------------------------------------- |
| Training set   | Used to train model parameters                    |
| Validation set | Used to evaluate progress and tune configurations |
| Test set       | Used for final independent evaluation             |

One important consideration is preventing data leakage: evaluation examples should not unintentionally appear in training data.

We also determine important model parameters:

| Configuration    | Meaning                           |
| ---------------- | --------------------------------- |
| Number of layers | Number of Transformer blocks      |
| Hidden dimension | Size of internal representations  |
| Attention heads  | Number of attention heads         |
| Vocabulary size  | Number of tokenizer tokens        |
| Context length   | Maximum supported sequence length |
| Parameter count  | Number of trainable parameters    |

For example, a model might use:

```

|

+-- Transformer layers: 32
+-- Hidden dimension: 4,096
+-- Attention heads: 32

```

These are illustrative configuration values, not specifications of a particular commercial model.

#### 6. Pretraining

Stage 5

Pretraining is the initial large-scale training process in which an LLM learns general language patterns, relationships, and representations from a massive dataset.

This is usually the most computationally expensive stage when creating a foundation model from scratch.

##### How pretraining works

Most decoder-only LLMs use next-token prediction as their pretraining objective.

Consider:

```
Input:
The operating system manages computer

Expected next token:
resources
```

The model predicts the next token, compares its prediction with the expected token, calculates the error, and adjusts its parameters.

The process repeats over enormous numbers of training examples.

[How Large Language Models Work: AI Training Explained](https://images.openai.com/static-rsc-4/fiVE3e-oOoqhFdu3X3_PznDGNY2e8BeDHWOSN6vEyqdQNK2iwuFUSMQrWzrmeTVzWoDxl3zXPE68Yl4TwZ2ncsZLBqSJ6JNerrA19FGqudNSDnCYxXfOKGHa0i3YbuVFFz38WjUW7UuyqCn4mNz6pGYqHr_Ly_U6HCgogFjJgTs?purpose=inline)

[intelligenttools.co](https://intelligenttools.co/blog/demystifying-large-language-models?utm_source=chatgpt.com)

##### Main training operations

1. Forward propagation: Pass input tokens through the neural network.
2. Prediction: Calculate probabilities for the next token.
3. Loss calculation: Measure the difference between predictions and expected tokens.
4. Backpropagation: Calculate gradients for model parameters.
5. Optimization: Update parameters using an optimizer.
6. Iteration: Repeat with additional training batches.

A common loss function is cross-entropy loss:

$$
L=-\sum\_{i=1}^{N} y_i\log(p_i)
$$

Where:

- $N$: Number of possible classes (vocabulary tokens).
- $y_i$: Actual target distribution.
- $p_i$: Predicted probability.

The training objective is to minimize the prediction loss.

##### What does the model learn?

During pretraining, the model can learn:

- Grammar and language structure.
- Vocabulary and word relationships.
- General knowledge patterns.
- Programming language syntax.
- Textual relationships.
- Some mathematical and reasoning patterns.

The resulting model is called a Pretrained Model or, when intended as a reusable general-purpose base, a Foundation Model.

#### 7. Fine-Tuning and Alignment

Stage 6

Pretraining produces a model with general language capabilities, but it does not automatically make the model a good conversational assistant.

For example, a pretrained model may be good at completing text but not necessarily at following instructions.

Fine-tuning adapts the pretrained model to specific tasks, domains, or desired behaviors.

##### 7.1 Supervised Fine-Tuning (SFT)

Supervised Fine-Tuning trains the model using curated input-output examples.

Example:

| Input                     | Expected output                                                                  |
| ------------------------- | -------------------------------------------------------------------------------- |
| Explain Java inheritance. | Inheritance allows a class to acquire properties and methods from another class. |
| What is Kubernetes?       | Kubernetes is a container orchestration platform.                                |
| Explain binary search.    | Binary search repeatedly divides a sorted search space into halves.              |

The model learns to respond to instructions rather than simply continue arbitrary text.

##### 7.2 Domain-Specific Fine-Tuning

A model can be adapted to a particular domain.

Examples:

- Medical language models.
- Legal language models.
- Financial language models.
- Programming language models.
- Scientific research models.

For example, a programming assistant might receive additional training on high-quality Java and Spring Boot examples.

##### 7.3 Alignment

Alignment attempts to make model behavior better match human preferences, intended instructions, and safety requirements.

Common techniques include:

| Technique          | Purpose                                               |
| ------------------ | ----------------------------------------------------- |
| RLHF               | Reinforcement Learning from Human Feedback            |
| Reward Modeling    | Learn preferences from comparison data                |
| PPO                | Reinforcement learning optimization algorithm         |
| DPO                | Optimize directly using preference pairs              |
| Safety Fine-Tuning | Improve responses to unsafe or inappropriate requests |

[GPT Models & Text Generation - Complete NLP Series Part 10 - Wasil Zafar](https://images.openai.com/static-rsc-4/uiP5ahc60dAulEuDUvd-QqrPM__g5G9g9rixXlIJABeO-MgvNv_aN7Bu9eH4eOIMbLAvfLq5eo3TGBW4H4C2GKqBzyuYjY16wYyvzuVY0p7RY4pIXFApt8DlgRiRI3FrRfyosbXCU0CIvXzvO39r3FwjdYmQeJnhq0HZz_eQOBY?purpose=inline)

5. Train a reward model to predict those preferences.

Not every LLM uses RLHF or PPO. DPO and other preference optimization techniques provide alternatives.

##### Result of this stage

The model becomes better suited to its intended application.

Test whether the model performs the tasks it was designed for.

- Text summarization.

- Code generation.
- Information extraction.

##### 8.3 Safety Evaluation

Evaluate whether the model:

- Produces harmful content.
- Reveals sensitive information.

- Produces biased responses.

For example:

- Is the answer correct?
- Is it understandable?
- Does it answer the actual question?
- Is it relevant?
- Does it follow the instructions?

Important: Evaluation is not a one-time activity. It should continue after deployment because real-world usage can expose problems that were not present in test datasets.

#### 10. Monitoring and Maintenance

Stage 9

Once deployed, the LLM must be monitored continuously.

A model that performs well during testing might behave differently under real-world conditions.

For example:

- Users may ask unexpected questions.
- Input distributions may change.
- The model may produce hallucinations.
- Response times may increase.
- Infrastructure failures may occur.
- New security vulnerabilities may emerge.

##### 10.1 Model Monitoring

Monitoring generally covers several areas.

| Area            | What to monitor                              |
| --------------- | -------------------------------------------- |
| Quality         | Accuracy, relevance, hallucinations          |
| Performance     | Latency, throughput, tokens per second       |
| Infrastructure  | CPU, GPU, RAM, disk utilization              |
| Availability    | Uptime, error rates, failed requests         |
| Security        | Prompt injection, data leakage, abuse        |
| Cost            | GPU consumption, API usage, cost per request |
| User experience | Feedback, satisfaction, failure reports      |

##### 10.2 Data Drift and Model Drift

These concepts are important in production machine learning systems.

Data Drift

Occurs when the distribution of incoming data changes compared with the data used during training.

Example:

A programming assistant was trained primarily on Java 8 documentation, but users increasingly ask about Java 25.

The incoming questions have changed.

Concept Drift

Occurs when the underlying relationship between inputs and desired outputs changes.

Example:

A model predicts customer preferences based on historical purchasing patterns, but customer behavior changes significantly.

Model Drift is a broader operational term often used to describe deteriorating model performance over time. It can result from data drift, concept drift, or other factors.

##### 10.3 Maintenance Activities

Typical maintenance activities include:

- Fixing inference infrastructure problems.
- Updating dependencies.
- Improving safety filters.
- Updating knowledge sources.
- Optimizing model performance.
- Reviewing user feedback.
- Evaluating newly released models.
- Retraining or fine-tuning when necessary.

An important distinction: updating external knowledge through RAG does not necessarily require retraining the LLM.

## 4. Transformer Architecture

Core LLM architecture

The Transformer is the architecture behind most modern LLMs.

It was introduced in the 2017 research paper Attention Is All You Need.

[Transformer architecture: redefining machine learning across NLP and beyond](https://images.openai.com/static-rsc-4/V-Mhlqs_yUw82BvhshJhBLsmYOufAk4Xs2pBcT6DN8_eReYWaPUHZ9DiGWGEz9I2B85Vg7UtOe85pO_KtmBf_GtAtC2lOoQ5VjXbTkWboBte-4skoiX31SfJUvP8_baJ9qY4SwlV9YHVJbPGWAoy6mocc3mfhrbxrBfjphTJ0go?purpose=inline)

Before Transformers, recurrent neural networks (RNNs) and long short-term memory networks (LSTMs) were widely used for sequential language processing.

Transformers introduced self-attention, allowing tokens to interact directly with other tokens within the supported context.

### Main Transformer components

| Component              | Responsibility                                         |
| ---------------------- | ------------------------------------------------------ |
| Input embeddings       | Convert token IDs into vectors.                        |
| Positional information | Represent token positions and ordering.                |
| Self-attention         | Capture relationships between tokens.                  |
| Multi-head attention   | Learn different types of relationships in parallel.    |
| Feed-forward network   | Transform token representations.                       |
| Residual connections   | Help information and gradients flow through layers.    |
| Layer normalization    | Stabilize neural network computation.                  |
| Output projection      | Convert hidden representations into vocabulary scores. |
| Softmax                | Convert scores into probabilities.                     |

Processes input text to build contextual representations.

## 6. LLM Generation and Decoding Strategies

After training, the model must decide which token to generate next.

Different decoding strategies produce different results.

Consider:

```
The capital of France is ...
```

### Common strategies

| Strategy        | Description                                                                       |
| --------------- | --------------------------------------------------------------------------------- |
| Greedy decoding | Selects the token with the highest probability.                                   |
| Random sampling | Samples from the probability distribution.                                        |
| Temperature     | Controls the sharpness of the probability distribution.                           |
| Top-K           | Samples from the K most probable tokens.                                          |
| Top-P           | Samples from the smallest group of tokens whose cumulative probability reaches P. |
| Beam search     | Explores multiple candidate sequences.                                            |

#### Temperature example

Suppose the model predicts:

```
Paris       0.80
London      0.10
Berlin      0.07
Other       0.03
```

A lower temperature generally makes the distribution more concentrated around the most probable choices.

A higher temperature generally makes it flatter, allowing more variation.

Temperature does not increase the model's actual knowledge or intelligence.

## 7. LLM Limitations

Although LLMs are powerful, they have important limitations.

| Limitation          | Explanation                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------- |
| Hallucinations      | Can generate plausible but incorrect information.                                           |
| Knowledge cutoff    | May not know events after its training data cutoff unless updated through other mechanisms. |
| Context limitations | Cannot necessarily process unlimited information in one interaction.                        |
| Bias                | May reproduce biases present in training data.                                              |
| Reasoning errors    | Can produce incorrect logical or mathematical conclusions.                                  |
| Non-determinism     | Sampling can lead to different responses for the same prompt.                               |
| Computational cost  | Training and inference can require substantial hardware resources.                          |
| Data privacy        | Sensitive information must be handled carefully when using LLM services.                    |

```
               v
       Generated Answer
               |

             User
```

The application could:

1. Accept a question about Java, Kubernetes, or operating systems.
2. Search the documentation for relevant information.
3. Retrieve the most relevant passages.

## Model Selection and Deployment
### size, computational requirements, and deployment environment.

This section explains how to choose an LLM based on its size, computational requirements, and deployment environment.

The main idea is straightforward:

> A larger model generally has more capacity to learn complex patterns, but it also requires more memory, computing power, and money to run.

For a Java developer, this is similar to choosing between a lightweight embedded database, a server-side caching system, and a distributed infrastructure platform. You don't automatically choose the biggest solution; you choose what satisfies your application's requirements.

Let's understand what model size actually means.

#### 1. What are parameters?

An LLM is a neural network containing millions or billions of numerical values called parameters.

When we say that Mistral 7B has
7 billion parameters, we are referring to the total number of trainable weights that
define the model’s behavior. These parameters are stored in tensors. These param‐
eters define the way a model processes input data and generates output, similar
to the way Java developers configure class variables and constants that dictate an
application’s behavior. In mathematical terms, an LLM is essentially a giant function
with billions of parameters, and these parameters exist as multidimensional tensors.
A simple analogy would be Java handling matrices via multidimensional arrays.
Suppose we have a Java program for image processing that uses a three-dimensional
(3D) array to represent an RGB image:
int[][][] image = new int[256][256][3]; // A 256x256 image with 3 color channels
In DL, tensors work similarly but at a much larger scale. A single LLM layer
could have weight tensors shaped like [12288, 4096], meaning it has 12,288 input
features and 4,096 output features. This is much like a huge adjacency matrix, where
each weight value determines how one input influences an output. Working with pretrained LLMs means working with tensor weights stored in formats like Safeten‐
sors or GPT-Generated Unified Format (or GGUF; more on this later). These formats
efficiently load precomputed parameters into memory, similarly to Java loading com‐
piled bytecode into the JVM for execution.

And tensors come in different precisions. While a model’s parameter count defines
its capacity for reasoning, contextual depth, and overall accuracy, the tensor type
determines how efficiently those parameters are stored, loaded, and processed. The
higher the precision of the tensor type, the more memory and computational power
is required per parameter. On the other hand, lower-precision tensors allow for com‐
pression and faster execution, enabling larger models to run on smaller hardware.
They come in full-precision (FP32 or FP16) and in quantized (INT8, INT4) versions.
For large-scale models exceeding 175 billion parameters, full-precision inference is
available only on massively distributed systems. Think of the way a distributed data‐
base partitions and processes large datasets. For smaller or local deployments, INT8
or INT4 quantization reduces memory footprint and still keeps functional accuracy.

Parameters are primarily weights (and sometimes biases) that the model learns during training.

For example, consider a simplified neural network:

```
Input
  |
  v
+-------------------+
| Neural Network    |
|                   |
| Weight 1 = 0.25   |
| Weight 2 = 0.81   |
| Weight 3 = -0.42  |
| Weight 4 = 0.67   |
+-------------------+
  |
  v
Output
```

During training, the model adjusts these values to improve its predictions.

A real LLM has an enormous number of parameters distributed across its embedding layers, attention layers, feed-forward networks, and other components.

For example:

| Model size | Number of parameters |
| ---------- | -------------------- |
| 1B         | 1 billion            |
| 7B         | 7 billion            |
| 13B        | 13 billion           |
| 70B        | 70 billion           |
| 175B       | 175 billion          |

The `B` means billion.

Important: Parameters are not the same as training data, tokens, or vocabulary size.

- Parameters: Learned numerical values inside the model.
- Training data: Examples used to train the model.
- Tokens: Units of text processed by the model.
- Vocabulary: The collection of token IDs the model can produce or recognize.

A model with more parameters has a larger capacity to represent learned patterns, but that does not guarantee better answers. Training quality, architecture, data quality, and model design also matter.

#### 2. Why does model size matter?

The number of parameters directly affects how much memory is needed to store model weights.

Consider a simplified calculation.

Suppose a model has 7 billion parameters, and each parameter is stored using 16 bits (2 bytes).

\\[ 7 \text{ billion} \times 2 \text{ bytes} = 14 \text{ GB} \\]

Therefore, the model weights alone require approximately 14 GB of memory.

The same calculation for other model sizes:

| Model size | FP32 (4 bytes) | FP16/BF16 (2 bytes) | INT8 (1 byte) |
| ---------- | -------------- | ------------------- | ------------- |
| 7B         | 28 GB          | 14 GB               | 7 GB          |
| 13B        | 52 GB          | 26 GB               | 13 GB         |
| 30B        | 120 GB         | 60 GB               | 30 GB         |
| 70B        | 280 GB         | 140 GB              | 70 GB         |
| 175B       | 700 GB         | 350 GB              | 175 GB        |

Approximate decimal GB for weights only. Actual memory requirements vary with quantization format, metadata, runtime overhead, and model implementation.

Notice something important: a 70B model using FP16 needs approximately 140 GB just for its weights.

That is beyond the capacity of many ordinary GPUs.

And there is more to consider.

##### Memory required during inference

Running an LLM requires more than loading its weights.

The main memory consumers are:

1. Model weights: The learned parameters.
2. KV cache: Stores attention keys and values from previous tokens to speed up generation.
3. Activations and temporary buffers: Intermediate computations during inference.
4. Runtime overhead: Memory used by the framework and GPU execution environment.

```
       GPU Memory
+---------------------------+
| Model weights             |
+---------------------------+
| KV cache                  |
+---------------------------+
| Activations and buffers   |
+---------------------------+
| Runtime overhead          |
+---------------------------+
```

This is why a model that theoretically fits into GPU memory based on its weights alone may still fail to run efficiently.

##### A. Small models: approximately 1B–13B parameters

Good candidates for local deployment

- TinyLlama — approximately 1.1B parameters.

##### C. Very large models: 175B+ parameters

High infrastructure requirements

Historically, 175B became a familiar reference point because of models such as GPT-3.

At this scale, deploying a model can require multiple GPUs and distributed inference.

For example, consider a hypothetical dense model with 175 billion parameters stored in FP16:

\\[ 175B \times 2 \text{ bytes} = 350 \text{ GB} \\]

That is approximately 350 GB for model weights alone.

A single GPU generally cannot accommodate that amount of memory, so the model weights may need to be distributed across multiple GPUs.

###### Distributed inference

```
             Java Application
                    |
                    v
              LLM API / Gateway
                    |
                    v
             Model Serving Layer
                    |
          +---------+---------+
          |                   |
          v                   v
     +---------+         +---------+
     | GPU  1  |         | GPU  2  |
     | Part A  |         | Part B  |
     +---------+         +---------+
          |                   |
          +---------+---------+
                    |
                    v
              Generated output
```

This is a simplified example of model parallelism: different parts of the model are distributed across GPUs.

Other techniques include:

- Tensor parallelism: Splits tensor operations across GPUs.
- Pipeline parallelism: Assigns different model layers to different GPUs.
- Data parallelism: Runs model replicas to process separate batches of requests.

###### The Kafka / Elasticsearch analogy

The paragraph compares large-model infrastructure to distributed systems such as Kafka and Elasticsearch.

The connection is mainly about operational complexity:

| Distributed system                | Large-model infrastructure        |
| --------------------------------- | --------------------------------- |
| Multiple nodes                    | Multiple GPUs or servers          |
| Distributed data/processing       | Distributed model computation     |
| Resource allocation               | GPU and memory allocation         |
| Scaling consumers/nodes           | Scaling inference capacity        |
| Monitoring throughput and latency | Monitoring tokens/sec and latency |

They are not technically the same, but both require careful infrastructure management.

##### 4. An important correction about GPT-4o, Claude 3.5, and Gemini 1.5

The paragraph lists GPT-4o, Claude 3.5, and Gemini 1.5 Ultra as examples of models exceeding 175B parameters.

Be careful with this statement.

The publicly available documentation does not establish that these particular models have more than 175 billion parameters. Their exact parameter counts have not been publicly disclosed in the same way as older open-weight models.

Also, the Gemini 1.5 family included models such as Gemini 1.5 Pro and Gemini 1.5 Flash; "Gemini 1.5 Ultra" is not an appropriate example of a publicly documented model in that family.

The lesson: Don't infer a model's parameter count from its product name, capabilities, or API price.

For hosted models, you often cannot determine their exact size. You can still evaluate them based on quality, latency, context window, pricing, and other published characteristics.

#### 5. Why don't we always choose the largest model?

Let's imagine you are developing three Java applications.

| Application                   | Requirement                            | Reasonable starting point          |
| ----------------------------- | -------------------------------------- | ---------------------------------- |
| Support ticket classifier     | Classify tickets into categories       | Small model                        |
| Enterprise document assistant | Understand and summarize documents     | Medium or large model              |
| Complex reasoning assistant   | Handle difficult, multi-step questions | Strong hosted or self-hosted model |

The largest model might give better results in some cases, but it can also introduce unnecessary costs.

Consider these dimensions:

| Dimension            | Smaller model               | Larger model                |
| -------------------- | --------------------------- | --------------------------- |
| Memory               | Usually lower               | Usually higher              |
| Infrastructure cost  | Usually lower               | Usually higher              |
| Local deployment     | Easier                      | More demanding              |
| Inference latency    | Often lower                 | Often higher                |
| Complex reasoning    | May be more limited         | May be stronger             |
| Concurrent workloads | Depends on serving capacity | Depends on serving capacity |

These are general tendencies, not guarantees. Architecture, quantization, hardware, and serving optimizations can change the comparison significantly.

#### 6. Model size is not the only optimization

This connects directly to the previous topic you studied: quantization, distillation, and Mixture of Experts.

For example, a 7B model stored using FP16 requires approximately 14 GB for its weights.

If you quantize it to 4-bit weights, the theoretical weight storage becomes:

\\[ 7B \times 0.5 \text{ bytes} = 3.5 \text{ GB} \\]

The actual memory requirement will be higher because of metadata and runtime requirements.

This allows a smaller-memory machine to run a model that might otherwise not fit.

There is also an important distinction with Mixture of Experts:

- Dense model: Most model parameters participate in processing each token.
- MoE model: Only selected experts participate in processing each token.

An MoE model can have a very large total parameter count but use only a fraction of its parameters for each token. Its total weights may still need to be stored across available hardware.

So, parameter count alone does not tell you the actual inference cost.

#### 8. Practical model-selection summary

Here is the decision process I would take when designing an enterprise Java application:

| Question                          | What to evaluate                                    |
| --------------------------------- | --------------------------------------------------- |
| What task must the model perform? | Classification, search, chat, reasoning, generation |
| How accurate must it be?          | Evaluate model quality on representative examples   |
| How much latency can we tolerate? | Measure response time and tokens/sec                |
| How many users will use it?       | Estimate concurrency and throughput                 |
| Where will it run?                | Local machine, private server, or cloud API         |
| What is the budget?               | GPU infrastructure or API usage costs               |
| Is data privacy important?        | Hosted API versus self-hosted deployment            |

The most important takeaway:

Model size is a resource and capacity consideration, not a quality guarantee. Select the smallest model that reliably meets your application's requirements at an acceptable cost and latency.
