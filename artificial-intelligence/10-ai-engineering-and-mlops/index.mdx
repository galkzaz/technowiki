
## 1. Introduction

MLOps (Machine Learning Operations) is a set of practices, principles, tools, and processes used to develop, deploy, monitor, and maintain Machine Learning (ML) models in production environments.

It combines three major disciplines:

1. Machine Learning (ML): Building and training models that learn from data.
2. DevOps: Automating software development, testing, deployment, and infrastructure operations.
3. Data Engineering: Managing, processing, validating, and delivering data used to train and operate ML models.

The main goal of MLOps is to make Machine Learning systems reliable, scalable, reproducible, and maintainable throughout their lifecycle.

### A simple example

Imagine you're developing a Machine Learning model that predicts house prices.

The development process might look like this:

1. Collect historical house-price data.
2. Clean and preprocess the data.
3. Train a Machine Learning model.
4. Evaluate its prediction accuracy.
5. Deploy the model as a REST API.
6. Allow applications to send house information and receive price predictions.
7. Monitor prediction accuracy and model performance.
8. Retrain the model when new data becomes available or its performance degrades.

MLOps provides the infrastructure and automation needed to manage this entire process.

## 2. Why Do We Need MLOps?

Traditional software applications and Machine Learning applications have different operational challenges.

Consider a traditional Java application versus a Machine Learning application.

| Aspect                  | Traditional software                             | Machine Learning                                 |
| ----------------------- | ------------------------------------------------ | ------------------------------------------------ |
| Source                  | Source code                                      | Source code + data + model                       |
| Development             | Write business logic                             | Train and experiment with models                 |
| Testing                 | Unit, integration, system tests                  | Software tests + data and model validation       |
| Build artifact          | Executable, JAR, container                       | Model artifact + application                     |
| Deployment              | Deploy application                               | Deploy application and model                     |
| Monitoring              | CPU, memory, errors, latency                     | CPU, memory, errors, latency + model quality     |
| Maintenance             | Fix bugs and release versions                    | Fix bugs, update data, retrain models            |
| Performance degradation | Usually caused by code or infrastructure changes | Can also result from changing data distributions |

The important difference: A traditional application generally behaves according to explicitly programmed logic. An ML application depends on a model whose behavior is learned from data.

For example, a house-price prediction model trained on historical data might become less accurate when the real-estate market changes.

This introduces additional challenges:

- Data quality problems.
- Changes in data distributions.
- Model performance degradation.
- Reproducibility of experiments.
- Model version management.
- Model retraining and redeployment.

MLOps addresses these challenges.

MLOps extends the Machine Learning lifecycle by introducing automation, versioning, testing, deployment, and continuous monitoring.

A typical MLOps lifecycle consists of the following stages:

### 3.1 Data Collection and Validation

Collect data from different sources:

- Databases.
- APIs.
- Data warehouses.
- Data lakes.
- Streaming platforms.

Before training, data must be validated.

For example:

- Check missing values.
- Detect duplicated records.
- Validate data types.
- Check expected ranges.
- Detect unexpected changes in data distributions.

Tools: Apache Spark, Pandas, Great Expectations, and TensorFlow Data Validation.

### 3.2 Data Preparation and Feature Engineering

Transform raw data into a format suitable for model training.

Examples:

- Normalize numerical values.
- Encode categorical variables.
- Handle missing values.
- Extract useful features.
- Split data into training, validation, and test datasets.

Feature engineering is particularly important because the quality of input features can significantly affect model performance.

Tools: Pandas, Scikit-learn, Apache Spark, and Feast (Feature Store).

### 3.3 Model Training and Experiment Tracking

Train ML models using prepared datasets.

During experimentation, different algorithms and hyperparameters are evaluated.

For example:

| Experiment | Algorithm           | Learning rate | Accuracy |
| ---------- | ------------------- | ------------- | -------- |
| 1          | Logistic Regression | N/A           | 85%      |
| 2          | Random Forest       | N/A           | 91%      |
| 3          | Neural Network      | 0.01          | 94%      |

Experiment tracking records:

- Training datasets.
- Model parameters.
- Hyperparameters.
- Evaluation metrics.
- Model artifacts.
- Code versions.

Tools: MLflow, Weights & Biases, and Kubeflow.

### 3.4 Model Evaluation and Validation

Before deployment, the model must satisfy predefined quality requirements.

For example:

- Accuracy must be greater than 90%.
- Precision must be greater than 85%.
- Inference latency must be below 100 ms.
- The model must pass fairness and robustness checks where applicable.

If the model fails evaluation, it should not proceed to production.

### 3.5 Model Deployment

Deploy the trained model so that other applications can use it.

There are several deployment approaches:

| Deployment approach | Description                                          |
| ------------------- | ---------------------------------------------------- |
| REST API            | Expose predictions through HTTP endpoints            |
| Batch inference     | Generate predictions for large datasets periodically |
| Streaming inference | Process incoming events continuously                 |
| Edge deployment     | Run models on local devices                          |

For example, you might expose a model through a Spring Boot application or a Python FastAPI service.

Tools: Docker, Kubernetes, KServe, BentoML, and FastAPI.

### 3.6 Model Monitoring

After deployment, monitor both the software infrastructure and the model itself.

There are two important monitoring categories:

Infrastructure monitoring

- CPU utilization.
- Memory consumption.
- Network traffic.
- API response time.
- Error rates.

ML-specific monitoring

- Prediction accuracy.
- Data drift.
- Concept drift.
- Prediction distribution changes.
- Feature distribution changes.

For example, imagine a model trained on house prices from 2020–2024.

In 2026, housing prices change significantly. The model might continue responding successfully to API requests, but its predictions become inaccurate.

This is why monitoring model quality is essential.

### 3.7 Model Retraining

When the model becomes outdated or new training data becomes available, the pipeline can trigger retraining.

A typical process:

1. Collect new data.
2. Validate the data.
3. Prepare the training dataset.
4. Retrain the model.
5. Evaluate the new model against the current production model.
6. Promote the new model if it meets the required criteria.
7. Deploy the new version.

This creates a continuous improvement cycle.

## 4. What Is the Relationship Between MLOps and DevOps?

MLOps is strongly inspired by DevOps.

DevOps combines software development and IT operations to automate the software delivery lifecycle.

MLOps applies similar principles to Machine Learning systems, but extends them to handle data, experiments, models, and model retraining.

MLOps describes
the application of DevOps principles to the ML field. The most obvious difference is
the central artifact they are grouped around. The DevOps team is focused on business
applications, and the MLOps team is more focused on ML models. Both describe the
process of developing an artifact and making it ready for consumption in production.
### 4.1 Similarities

DevOps and MLOps share many similarities, as both are focused on streamlining and
automating workflows to ensure continuous integration (CI), continuous delivery
(CD), and reliable deployment in production environments.


Both DevOps and MLOps emphasize:

| Principle       | DevOps                                    | MLOps                                               |
| --------------- | ----------------------------------------- | --------------------------------------------------- |
| Automation      | Automate software delivery                | Automate ML pipelines                               |
| Version control | Source code versioning                    | Code, data, and model versioning                    |
| CI              | Continuously integrate code               | Integrate and validate ML code and pipelines        |
| CD              | Continuously deliver/deploy software      | Continuously deliver/deploy ML models               |
| Testing         | Automated software tests                  | Software, data, and model tests                     |
| Monitoring      | Application and infrastructure monitoring | Application, infrastructure, and model monitoring   |
| Reproducibility | Reproduce software builds                 | Reproduce experiments and model training            |
| Collaboration   | Developers and operations teams           | Data scientists, ML engineers, and operations teams |

Next Figure describes one possible combination of DevOps and MLOps:
![](/docs/assets/artificial-intelligence/10-ai-engineering-and-mlops/devops-mlops.png)

The shared practices, such as cross-functional collaboration, using Git as a single
source of truth, repeatability, automation, security, and observability, are at the core.

Both DevOps and MLOps rely on collaboration between developers, data scientists,
and operations teams to ensure that code, models, and configurations are well coordinated. Automation and repeatability are emphasized for building, testing, and
deploying both applications and models, ensuring consistent and reliable results.
However, MLOps introduces additional layers, such as model training and data management, which are distinct from typical DevOps pipelines. The need to constantly
monitor models for drift and to ensure their performance over time adds complexity
to MLOps, but both processes share a focus on security and observability to maintain
trust and transparency in production systems.
### 4.2 Differences

The main difference is that MLOps introduces additional components that are not normally required in traditional DevOps.

| Component                | DevOps                   | MLOps                           |
| ------------------------ | ------------------------ | ------------------------------- |
| Main artifact            | Application              | Application + trained model     |
| Data management          | Usually application data | Training and inference datasets |
| Experiment tracking      | Not typically required   | Essential                       |
| Model registry           | Not typically required   | Essential                       |
| Feature store            | Not typically required   | Often used                      |
| Training pipeline        | Not typically required   | Essential                       |
| Continuous training (CT) | Not standard             | Important                       |
| Data drift detection     | Not standard             | Important                       |
| Model drift detection    | Not standard             | Important                       |

### 4.3 CI/CD vs CI/CD/CT

This is one of the most important differences.

In traditional DevOps, we commonly use:

- CI (Continuous Integration): Automatically build and test code changes.
- CD (Continuous Delivery/Deployment): Automatically prepare or deploy software releases.

In MLOps, we extend this approach with:

\- CT (Continuous Training): Automatically retrain models when new data becomes available, or when defined conditions trigger retraining.

Traditional DevOps pipeline

Source Code

CI: Build and Test

CD: Deploy Application

MLOps pipeline

Source Code + Data

CI: Code, Data and Pipeline Validation

CT: Model Training and Evaluation

CD: Deploy Model

Monitor Model and Data

Monitoring feedback can trigger another training cycle.

Note: Continuous training does not necessarily mean training happens continuously. It means training is automated and can be triggered by schedules, new data, or monitoring conditions.

## 6. Relationship Between DevOps, DataOps, MLOps, and LLMOps

As you continue studying AI and Generative AI, you will encounter several related operational disciplines.


| Discipline | Focus                               | Main objective                            |
| ---------- | ----------------------------------- | ----------------------------------------- |
| DevOps     | Software development and operations | Reliable software delivery                |
| DataOps    | Data engineering and operations     | Reliable data pipelines                   |
| MLOps      | Machine Learning operations         | Reliable ML lifecycle                     |
| LLMOps     | Large Language Model operations     | Reliable LLM applications and deployments |
| AIOps      | AI applied to IT operations         | Automate and improve IT operations        |

As **MLOps** has matured, a broader set of terms has emerged, often used interchange‐
ably or with overlapping meaning. These include **ModelOps** (focusing on model
lifecycle management in a more general sense), **LLMOps** (specialized for LLM opera‐
tions), and **DataOps** (emphasizing the reliability and automation of data pipelines).
These terms reflect the increasing specialization in managing AI components at scale.

Adding to the landscape are **AIOps** and **GenAIOps**, which are also relevant in this
context. AIOps, short for artificial intelligence for IT operations, refers to the use of ML
and analytics to automate and enhance IT operational tasks. AIOps platforms ingest
and analyze data from logs, metrics, and traces, helping operations teams detect
anomalies, predict outages, and reduce alert fatigue. While not focused on model
deployment like MLOps, AIOps represents an important application of AI within
production environments and often complements DevOps practices by improving
infrastructure visibility and response times.

**Generative AI operations (GenAIOps)** is an emerging concept that adapts MLOps
principles to the operational needs of generative AI systems, such as LLMs. These
systems pose new challenges, including prompt versioning, input/output validation,
fine-tuning management, context construction, and guardrails. GenAIOps focuses
on ensuring that GenAI components are governed, tested, deployed, and monitored
just like any other critical application service, often using tools and workflows that
DevOps and MLOps teams are already familiar with.
An important distinction:

- MLOps primarily manages the lifecycle of traditional ML models and their training pipelines.
- LLMOps extends operational practices to LLM-based systems, including prompt management, model evaluation, inference optimization, RAG pipelines, and LLM monitoring.

For example, an LLM application using Retrieval-Augmented Generation (RAG) requires managing both the LLM and the retrieval pipeline.

In summary, while DevOps and MLOps share a common foundation, MLOps adds data and model-specific concerns. AIOps and GenAIOps further expand the operational scope of AI in production, targeting infrastructure optimization and generative model management, respectively. There is no single correct setup; each organization will find its balance based on its structure, expertise, and risk profile.

## 7. Practical Example: DevOps vs MLOps in a Real Application

Imagine building a house-price prediction application using:

- Python for ML.
- Scikit-learn for training.
- FastAPI for model serving.
- Docker for packaging.
- Kubernetes for deployment.
- Jenkins for automation.

DevOps responsibilities:

1. Build the FastAPI application.
2. Run unit and integration tests.
3. Build the Docker image.
4. Deploy the application to Kubernetes.
5. Monitor application availability and infrastructure.

MLOps responsibilities:

1. Collect and validate house-price datasets.
2. Train the prediction model.
3. Track experiments using MLflow.
4. Evaluate model quality.
5. Register the approved model.
6. Package and deploy the model.
7. Monitor prediction quality and data drift.
8. Retrain and deploy improved models.

The two disciplines work together.

For instance, Jenkins can execute a pipeline that deploys a newly approved ML model, while an ML orchestration system handles the training process.

## 9. Key Takeaways

1. DevOps automates the software development and deployment lifecycle.
2. MLOps applies DevOps principles to Machine Learning systems.
3. MLOps introduces additional responsibilities: data validation, experiment tracking, model versioning, model evaluation, and retraining.
4. DevOps commonly uses CI/CD, while MLOps extends the process with Continuous Training (CT).
5. MLOps and DevOps are complementary disciplines, not competing alternatives.
6. LLMOps builds on many of these concepts to manage applications based on Large Language Models.

The most important concept to remember:

DevOps ensures that your software can be built, tested, deployed, and operated reliably. MLOps ensures that your Machine Learning models and their supporting data pipelines can also be developed, deployed, monitored, and continuously improved reliably.
