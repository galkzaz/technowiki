# Model Deployment Strategies

Model deployment strategies describe how, where, and when a trained machine learning model is made available to applications or users.

There isn't just one way to deploy a model. The right approach depends on several factors:

- How frequently predictions are needed.
- Whether responses must be immediate.
- Where the model should run.
- How much traffic the model must handle.
- How safely new model versions should be introduced.
- How model updates should be managed.

Let's go through the six groups, with examples and use cases.

## 1. Deployment by Execution Mode

This classification describes when and how the model receives data and produces predictions.

### 1.1 Batch Deployment

The model processes a large collection of records together, usually at scheduled intervals.

Instead of requesting a prediction immediately for every record, the system collects data and processes it later.

Example: Customer churn prediction

A telecom company wants to identify customers who are likely to cancel their subscriptions.

```
Customer Database
       |
       v
Collect customer records
       |
       v
Batch Prediction Job
       |
       v
Trained ML Model
       |
       v
Predictions for all customers
       |
       v
Save results to Database
       |
       v
Marketing team uses predictions
```

For example, the model processes 500,000 customer records every night and stores a churn probability for each customer.

Common technologies:

- Apache Spark
- Apache Airflow
- Python batch jobs
- Kubernetes CronJobs
- Cloud batch services

Use cases:

- Customer churn prediction.
- Fraud analysis over historical transactions.
- Daily sales forecasting.
- Credit risk scoring.
- Recommendation generation.

### 1.2 Online (Real-Time) Deployment

The model receives an individual request and returns a prediction immediately.

The model is usually exposed through an API.

Example: Fraud detection

A customer makes a payment. The payment service requests a prediction before approving the transaction.

```
Customer
   |
   v
Payment Service
   |
   v
ML Prediction API
   |
   v
Trained ML Model
   |
   v
Fraud Probability: 0.95
   |
   v
Payment Service
   |
   v
Reject Transaction
```

A simplified API request might look like:

```
POST /api/predict-fraud
Content-Type: application/json
```

```
{
  "amount": 1500,
  "country": "EG",
  "transaction_count": 12
}
```

The model returns a prediction:

```
{
  "fraud_probability": 0.95,
  "prediction": "FRAUD"
}
```

Common technologies:

- FastAPI
- Spring Boot
- Flask
- TensorFlow Serving
- TorchServe
- vLLM (for LLM inference)

Use cases:

- Fraud detection.
- Credit card authorization.
- Product recommendations.
- Image classification APIs.
- Chatbots and LLM applications.

### 1.3 Streaming Deployment

The model continuously processes incoming events or data streams rather than waiting for a scheduled batch or handling only isolated requests.

Example: Real-time network anomaly detection

A monitoring system continuously receives network traffic metrics and analyzes them to detect unusual behavior.

```
Network Devices
      |
      v
Kafka Topics
      |
      v
Stream Processing
      |
      v
ML Model
      |
      v
Anomaly Detection
      |
      v
Alerting System
```

For example, the model receives network metrics every second and detects unusual traffic patterns.

Common technologies:

- Apache Kafka
- Apache Flink
- Spark Structured Streaming
- Kafka Streams
- Managed cloud streaming services

Use cases:

- Network intrusion detection.
- Real-time fraud monitoring.
- IoT sensor analysis.
- Predictive maintenance.
- Live recommendation systems.

### 1.4 Edge Deployment

The model runs directly on or near the device that generates the data, instead of sending every request to a remote server.

Deploying models at the edge—on Internet of Things (IoT) devices or local gateways—reduces latency and network usage.

Frameworks geared for edge AI often include optimizations for low-power hardware, making it viable for real-time or mission-critical scenarios in remote locations.

Example: Smart security camera

A camera uses an embedded model to detect people and vehicles locally.

```
Camera
   |
   v
Local ML Model
   |
   v
Object Detection
   |
   +----> Person Detected
   |
   +----> Vehicle Detected
   |
   v
Local Alert
```

The camera doesn't need to send every frame to a cloud server.

Common technologies:

- TensorFlow Lite / LiteRT
- ONNX Runtime
- OpenVINO
- ExecuTorch
- NVIDIA Jetson
- Apple Core ML

Use cases:

- Autonomous vehicles.
- Smart cameras.
- Industrial IoT.
- Mobile applications.
- Robotics.

| Strategy  | When predictions happen       | Typical example                  |
| --------- | ----------------------------- | -------------------------------- |
| Batch     | At scheduled intervals        | Daily customer churn predictions |
| Online    | Immediately after a request   | Payment fraud detection          |
| Streaming | Continuously as events arrive | Network anomaly detection        |
| Edge      | Locally on or near a device   | Camera object detection          |

Important distinction: Online and streaming are related but not identical. Online inference typically responds to individual requests, while streaming inference continuously processes events. Edge describes where inference runs, so an edge model can also process requests or streams.

## 2. Deployment by Hosting Environment

This classification describes where the model and its inference infrastructure are hosted.

### 2.1 On-Premises Deployment

The organization runs the model on its own infrastructure, inside its own data center or server environment.

```
Company Data Center
   |
   +-- Application Servers
   |
   +-- GPU Servers
   |      |
   |      +-- ML Model
   |
   +-- Databases
```

Advantages:

- Greater control over infrastructure.
- Data can remain within the organization's environment.
- Custom hardware and security configurations.

Disadvantages:

- Infrastructure purchasing and maintenance costs.
- Hardware capacity must be planned.
- Scaling can be slower.

Use cases: Banks, government organizations, healthcare organizations, and companies with strict data residency requirements.

### 2.2 Cloud Deployment

Another option is to use a model already hosted by an external provider.

Instead of deploying the inference engine yourself, the provider manages the infrastructure, model execution, scaling, and often model updates.

The model runs on infrastructure provided by a cloud provider.

Cloud platforms like AWS, Google Cloud, and Azure offer fully managed model
serving solutions. You can deploy models through their respective marketplaces
or tooling, often with automatic scaling and built-in monitoring. This reduces
operational overhead but may introduce vendor lock-in.

Your Java application communicates with the provider through an API.


**Architecture**

```
       Java Spring Boot
              |
              | HTTPS REST API
              v
      Cloud AI Provider
              |
              v
       Inference Engine
              |
              v
          Hosted LLM
              |
              v
      Generated Response
              |
              v
       Java Application
```

Examples include:

- Amazon Web Services (AWS).
- Microsoft Azure.
- Google Cloud.

```
Cloud Platform
   |
   +-- Compute Instances
   |
   +-- GPU Infrastructure
   |
   +-- Model Serving
   |
   +-- Storage
   |
   +-- Monitoring
```

Advantages:

- Flexible resource provisioning.
- Easier access to GPUs.
- Managed ML services.
- Pay-as-you-go pricing.
- No need to purchase or manage GPUs.
- No need to download and deploy model weights.
- Easier initial integration.
- Provider manages much of the infrastructure.
- Can scale without managing individual model instances.

Disadvantages:

- Ongoing infrastructure costs.
- Dependence on cloud providers.
- Data transfer and compliance considerations.
- Pay-per-use or subscription costs.
- Network latency.
- Dependency on external provider availability.
- Data privacy and regulatory considerations.
- Less control over the underlying inference infrastructure.

Use cases: AI SaaS platforms, recommendation systems, LLM applications, and applications with variable traffic.

Important: Cloud APIs are not necessarily interchangeable. Even when providers support REST, their authentication, request schemas, response formats, and supported capabilities can differ. Some provide OpenAI-compatible APIs, but compatibility should be verified.

### 2.3 Hybrid Deployment

The organization combines on-premises infrastructure with cloud infrastructure.

For example, sensitive customer data may remain on-premises while computationally intensive model inference runs in the cloud, provided the data-sharing and compliance requirements permit it.

```
          On-Premises
               |
       Internal Application
               |
       Secure Connection
               |
               v
          Cloud Platform
               |
          GPU Servers
               |
           ML Model
               |
          Prediction
               |
               v
        Internal Application
```

Use cases:

- Organizations migrating gradually to the cloud.
- Systems with sensitive data.
- Organizations requiring both local control and cloud scalability.

### 2.4 Edge / Device Deployment

The model is deployed directly onto devices such as mobile phones, cameras, vehicles, and embedded systems.

This overlaps with edge deployment by execution mode, but here we are classifying it by hosting location.

Use cases: Offline mobile AI, autonomous vehicles, smart appliances, and industrial devices.

## 3. Deployment by Inference Architecture

This classification describes where the inference computation happens and how applications communicate with the model.

### 3.1 Remote Inference

The model runs on a separate server or service. The application sends input over a network and receives the prediction.

For example, suppose you have a Java Spring Boot e-commerce application that uses an LLM to generate product descriptions.

You don't need to install the LLM or its inference engine inside your Spring Boot application.

Instead, deploy the LLM as a separate service.

![](/docs/assets/artificial-intelligence/10-ai-engineering-and-mlops/model-deployment/Remote-Inference-example.png)
{/* Java Spring Boot Application

Business logic · Authentication · API endpoints

REST / gRPC

Load Balancer / API Gateway

Distributes requests and manages access.

LLM Inference Service

Instance 1

LLM + Engine

Instance 2

LLM + Engine

GPU / CPU Infrastructure */}
```
Java Spring Boot Application
           |
           | HTTP / REST
           v
    Inference Server
           |
           v
       vLLM Engine
           |
           v
        LLM
           |
           v
    Generated Response
           |
           v
Java Spring Boot Application
```

The Java application doesn't need to load the model or manage GPU memory. It only communicates with the inference service.

The Java application doesn't know how the model executes internally.

It simply sends a request:

```
POST /v1/chat/completions
Content-Type: application/json
```

```
{
  "model": "llama-3",
  "messages": [
    {
      "role": "user",
      "content": "Generate a description for this laptop."
    }
  ]
}
```

The inference service returns the generated response.

Why deploy the model as an independent service?

There are several advantages:

1\. Independent scaling

Your Java application and inference service have different resource requirements.

For example:

- Java application: CPU and RAM.
- LLM inference: GPU and substantial VRAM.

You can scale them independently.

2\. Independent deployment

You can upgrade the LLM or replace its inference engine without redeploying the Java application, provided the API contract remains compatible.

3\. Resource isolation

An LLM can consume substantial CPU, GPU, and memory resources. Running it separately prevents those requirements from directly competing with your application's resources.

4\. Multiple consumers

Different applications can use the same inference service:

```
          Java Backend
               |
               |
     +---------+---------+
     |                   |
     v                   v
 Web Application    Mobile Application
     |                   |
     +---------+---------+
               |
               v
        LLM Inference API
               |
               v
           LLM Model
```

Where can the inference service run?
| Environment   | Description                         | Example                  |
| ------------- | ----------------------------------- | ------------------------ |
| On-premises   | Company-owned infrastructure        | Internal GPU servers     |
| Cloud         | Provider-managed infrastructure     | AWS, Azure, Google Cloud |
| Containerized | Packaged and deployed as containers | Docker and Kubernetes    |

These categories can overlap. For example, a containerized inference service can run on-premises or in the cloud.

Common technologies:

- vLLM
- Ollama
- TensorRT-LLM
- Hugging Face Inference Endpoints
- Cloud AI APIs

Advantages:

- Model infrastructure is independent of the application.
- Inference servers can scale independently.
- Multiple applications can share the same model service.
- GPU resources can be managed separately.

Disadvantages:

- Network latency.
- Requires network connectivity.
- Inference service availability becomes an external dependency.

### 3.2 Local Inference


What if you don't want to communicate with an external inference service?
What if you need to run an LLM locally, perhaps because of privacy, offline operation, or latency requirements?

The model runs inside the same application process or on the same machine as the application.

For example, a Java application loads a model through DJL or invokes a native inference library.

```
Application Server
       |
       +-- Java Application
       |
       +-- Inference Runtime
       |
       +-- ML Model
       |
       +-- Prediction
```

Common technologies:

- DJL (Deep Java Library)
- ONNX Runtime
- JNI
- JNA
- llama.cpp

When running models and inference engines locally, containerization simplifies
packaging the runtime, libraries, and optimizations into a single environment. Some
inference engines already provide prebuilt containers. Tools like Podman further
streamline management of these containers, including the ability to pull model
images or create custom containers for your specific hardware. Podman Desktop
provides a user interface for easily spinning up and testing these AI services.

Java provides several ways to integrate with native inference engines.

Advantages:

- No network call to a separate inference service.
- More control over inference execution.
- Can operate without external connectivity.

Disadvantages:

- Application and model compete for machine resources.
- Application deployment becomes more complex.
- Scaling the application also affects model resources.

### Remote vs. Local Inference: Comparison

This is probably the most important comparison in the paragraph.

| Aspect               | Remote inference                          | Local inference                             |
| -------------------- | ----------------------------------------- | ------------------------------------------- |
| Model location       | Separate server or cloud provider         | Same application environment or device      |
| Communication        | REST / gRPC                               | Direct Java API / native bindings           |
| Network dependency   | Usually required                          | Not required for inference                  |
| Hardware management  | Provider or infrastructure team           | Application owner                           |
| Scaling              | Independent service scaling               | Application/device resources                |
| Privacy              | Data may leave the device or organization | Can keep data local                         |
| Latency              | Includes network overhead                 | Avoids network round trip                   |
| Complexity           | Infrastructure/API integration            | Native dependencies and resource management |
| Typical technologies | OpenAI API, vLLM server, Bedrock          | JNI, JNA, DJL                               |

One clarification: local inference is not automatically faster. A remote GPU server can outperform a local CPU significantly. Also, running inference inside the same JVM is different from running it in a separate process on the same device.

### 3.3 Centralized Inference

A central inference service hosts models and serves predictions to multiple applications.

```
Application A ----\
                   \
Application B ------> Central Inference Service
                   /           |
Application C ----/            v
                            ML Models
```

For example, an organization may have a central recommendation model used by its website, mobile application, and customer service platform.

Advantages:

- Centralized model management.
- Shared infrastructure.
- Consistent predictions across applications.
- Easier monitoring and model updates.

Disadvantages:

- The central service can become a bottleneck.
- Multiple applications depend on its availability.
- Network communication is required.

### 3.4 Distributed Inference

Inference computation is distributed across multiple machines or accelerators.

This is particularly useful when a model is too large for one GPU or when the workload is too demanding for one machine.

Two important approaches are:

- Model parallelism: Split a model across multiple GPUs or machines.
- Data parallelism: Run model replicas on multiple devices, with each processing different requests or batches.

Example:

```
                  Inference Requests
                         |
                  Load Balancer
                    /       \
                   v         v
              GPU Server 1  GPU Server 2
                   |         |
                 Model     Model
                   |         |
                   v         v
                Results   Results
                    \       /
                     v     v
                  Responses
```

Common technologies:

- NVIDIA TensorRT-LLM
- vLLM
- SGLang
- Kubernetes
- NVIDIA Triton Inference Server

Use cases:

- Serving large LLMs.
- High-throughput inference.
- Large recommendation systems.
- Computer vision at scale.

| Strategy    | Main idea                                                   | Typical example                      |
| ----------- | ----------------------------------------------------------- | ------------------------------------ |
| Remote      | Model runs in a separate service                            | Spring Boot calling vLLM             |
| Local       | Model runs alongside the application                        | Java application using ONNX Runtime  |
| Centralized | Multiple applications use one shared inference service      | Organization-wide recommendation API |
| Distributed | Inference computation or workload is spread across machines | LLM running across multiple GPUs     |

Important distinction: Remote and centralized inference are related but not identical. Remote describes the separation between the application and model; centralized describes the shared architecture serving multiple consumers. Distributed describes how inference computation or workload is spread across resources.

## 4. Deployment by Release Strategy

This classification describes how a new model version is introduced into a production environment.

Suppose your current production model is `model-v1`, and you have trained a better version called `model-v2`.

You don't necessarily want to replace `model-v1` immediately. A new model might have bugs, worse accuracy, higher latency, or unexpected behavior.

Release strategies help introduce new versions safely.

### 4.1 Recreate Deployment

The existing model instance is stopped, and the new model is started.

```
Before:
Production ---> Model v1

Deployment:
Stop Model v1
Start Model v2

After:
Production ---> Model v2
```

Advantages:

- Simple to implement.
- No need to maintain two versions simultaneously.

Disadvantages:

- Usually causes downtime.
- Requests may fail while the new model starts.

Use cases: Development environments, internal systems, and applications where short downtime is acceptable.

### 4.2 Rolling Deployment

The system gradually replaces old model instances with new ones.

For example, if you have four instances running `model-v1`, you replace them one at a time with `model-v2`.

```
Initial:
[v1] [v1] [v1] [v1]

Step 1:
[v2] [v1] [v1] [v1]

Step 2:
[v2] [v2] [v1] [v1]

Step 3:
[v2] [v2] [v2] [v1]

Final:
[v2] [v2] [v2] [v2]
```

Advantages:

- Reduces downtime.
- Gradual replacement.
- Usually requires fewer additional resources than blue-green deployment.

Disadvantages:

- Old and new model versions coexist temporarily.
- You must ensure both versions can handle incoming requests.
- Rollback can be more complicated than simply switching traffic.

Use cases: Production systems with multiple model-serving instances.

### 4.3 Blue-Green Deployment

Two separate environments are maintained:

- Blue: Current production model (`model-v1`).
- Green: New model (`model-v2`).

The new model is deployed and tested in the green environment. Once it is ready, traffic is switched from blue to green.

```
                 Traffic
                    |
               Load Balancer
                    |
             +------+------+
             |             |
          Blue           Green
          Model v1       Model v2
          (Old)          (New)
             |             |
             +-------------+
```

Before switching:

```
Traffic ---> Blue (v1)
             Green (v2) - Testing
```

After switching:

```
Traffic ---> Green (v2)
             Blue (v1) - Standby
```

Advantages:

- Easy traffic switching.
- Fast rollback: redirect traffic to the previous environment.
- New model can be tested before receiving production traffic.

Disadvantages:

- Requires additional infrastructure.
- Running two complete environments can be expensive.

Use cases: Critical production services where downtime must be minimized.

### 4.4 Canary Deployment

The new model receives a small percentage of production traffic initially.

If the new model behaves correctly, its traffic percentage is gradually increased.

For example:

```
Stage 1:  95% --> Model v1
           5% --> Model v2

Stage 2:  75% --> Model v1
          25% --> Model v2

Stage 3:  50% --> Model v1
          50% --> Model v2

Stage 4:   0% --> Model v1
         100% --> Model v2
```

At each stage, you monitor:

- Prediction quality.
- Error rates.
- Latency.
- Throughput.
- Resource consumption.
- Business metrics.

If the new model performs poorly, you stop the rollout and route traffic back to the old version.

Advantages:

- Limits the impact of a bad model.
- Tests the new model using real production traffic.
- Supports gradual rollout.

Disadvantages:

- Requires traffic routing and monitoring.
- Results can be misleading if the traffic groups are not representative.
- Requires careful handling of differences between model versions.

Use cases: Recommendation systems, fraud detection, search ranking, and LLM applications.

### 4.5 Shadow Deployment

The new model receives copies of real production requests, but its predictions are not used by the application.

The existing model continues to make the actual production decisions.

```
                 User Request
                      |
                      v
                 Application
                      |
                      v
                 Model v1
                      |
                      v
                Actual Response
                      |
                      v
                    User

                 User Request
                      |
                      v
                   Model v2
                      |
                      v
              Shadow Prediction
                      |
                      v
             Compare and Evaluate
```

You compare the predictions of both models without allowing the new model to affect users.

Advantages:

- Tests the new model using real production inputs.
- No direct impact on users.
- Helps discover unexpected behavior before release.

Disadvantages:

- Requires additional inference resources.
- Does not directly measure how users would react to the new model.
- Requires careful handling of duplicated requests and side effects.

Use cases: High-risk models such as fraud detection, credit scoring, and recommendation systems.

### 4.6 A/B Testing Deployment

Two model versions serve different groups of users, and their results are compared.

For example:

- Group A receives predictions from `model-v1`.
- Group B receives predictions from `model-v2`.

```
                 User Requests
                       |
                 Experiment Router
                    /       \
                   v         v
                Group A   Group B
                   |         |
                Model v1  Model v2
                   |         |
                   v         v
                Results   Results
                   \         /
                    v       v
                 Compare Metrics
```

You might compare:

- Click-through rate.
- Conversion rate.
- Recommendation engagement.
- User satisfaction.
- Business revenue.

Advantages:

- Measures real-world business impact.
- Helps determine which model performs better for users.
- Supports evidence-based model selection.

Disadvantages:

- Requires enough traffic for meaningful results.
- User groups must be assigned carefully.
- Results can be affected by external factors.

Use cases: Search ranking, recommendation systems, advertising, and personalization.

### Comparing release strategies

| Strategy    | How the new model is introduced                             | Main purpose                |
| ----------- | ----------------------------------------------------------- | --------------------------- |
| Recreate    | Replace the old model directly                              | Simple deployment           |
| Rolling     | Replace instances gradually                                 | Reduce downtime             |
| Blue-Green  | Switch between two environments                             | Fast switching and rollback |
| Canary      | Gradually increase new-model traffic                        | Reduce release risk         |
| Shadow      | Copy traffic to the new model without using its predictions | Validate safely             |
| A/B Testing | Serve different user groups with different models           | Compare business outcomes   |

### Canary vs. Shadow vs. A/B Testing

These three are particularly important in ML deployment.

| Question                                 | Canary                              | Shadow               | A/B Testing           |
| ---------------------------------------- | ----------------------------------- | -------------------- | --------------------- |
| Does the new model receive real inputs?  | Yes                                 | Yes                  | Yes                   |
| Does it influence actual user responses? | Yes, for a small traffic percentage | No                   | Yes                   |
| Is it used to evaluate business impact?  | Can be                              | No, not directly     | Yes                   |
| Main objective                           | Safe rollout                        | Technical validation | Compare user outcomes |

## 5. Deployment by Serving Infrastructure

This classification describes the infrastructure and platform used to run and expose the model.

### 5.1 Container-Based Deployment

The model-serving application and its dependencies are packaged into a container image.

For example, a Docker image may contain:

- Model-serving application.
- Inference engine.
- Required libraries.
- Runtime dependencies.
- Model configuration.

```
Docker Container
       |
       +-- Model Serving API
       |
       +-- Inference Engine
       |
       +-- Dependencies
       |
       +-- Model Files
```

Example Dockerfile:

```
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000

CMD ["python", "app.py"]
```

Advantages:

- Consistent execution environments.
- Easier packaging and distribution.
- Portable across supported container environments.
- Simplifies deployment automation.

Disadvantages:

- Container images can be large, especially with ML dependencies.
- GPU access requires additional configuration.
- Containers alone don't provide orchestration or automatic scaling.

Common technologies: Docker, Podman, NVIDIA Container Toolkit.

### 5.2 Kubernetes-Based Deployment

The model-serving container is deployed and managed by Kubernetes.

Kubernetes provides orchestration capabilities such as:

- Container scheduling.
- Replication.
- Health checks.
- Automatic recovery.
- Scaling.
- Service discovery.
- Rolling updates.

```
              Kubernetes Cluster
                      |
                Model Service
                      |
               Load Balancer
                      |
             +--------+--------+
             |        |        |
             v        v        v
           Pod 1    Pod 2    Pod 3
             |        |        |
           Model    Model    Model
```

Advantages:

- Automated container management.
- Horizontal scaling.
- High availability.
- Integration with monitoring and deployment pipelines.

Disadvantages:

- More operational complexity.
- GPU scheduling and resource management require configuration.
- Requires Kubernetes expertise.

Common technologies:

- Kubernetes
- KServe
- Seldon Core
- NVIDIA Triton Inference Server
- Helm

### 5.3 Serverless Deployment

The model-serving functionality runs on a serverless platform. The cloud provider manages the underlying infrastructure, and the application invokes the model through an endpoint or function.

```
       Application Request
                |
                v
        Serverless Endpoint
                |
                v
         Managed Runtime
                |
                v
             ML Model
                |
                v
            Prediction
```

The platform may automatically allocate resources when requests arrive and scale them according to demand.

Advantages:

- Less infrastructure management.
- Automatic scaling.
- Potentially lower cost for intermittent workloads.

Disadvantages:

- Cold-start latency.
- Execution time and resource limits may apply.
- GPU availability and model size support vary by provider.

Use cases:

- Low-traffic prediction APIs.
- Event-triggered inference.
- Applications with unpredictable workloads.

### 5.4 Managed ML Platform Deployment

The model is deployed through a cloud provider's managed machine learning service.

The provider manages much of the infrastructure, model hosting, endpoint creation, and scaling.

Examples:

- Amazon SageMaker.
- Azure Machine Learning.
- Vertex AI.

```
        ML Model Artifact
               |
               v
       Managed ML Platform
               |
       +-------+-------+
       |       |       |
       v       v       v
    Hosting  Scaling Monitoring
       |
       v
    Prediction API
       |
       v
    Application
```

Advantages:

- Less infrastructure management.
- Integrated model deployment and monitoring features.
- Cloud-specific ML tooling.
- Easier integration with other cloud services.

Disadvantages:

- Vendor dependency.
- Platform-specific configuration.
- Costs can increase with GPU usage and traffic.

### Comparing serving infrastructure

| Strategy            | Main responsibility                                     | Example                                |
| ------------------- | ------------------------------------------------------- | -------------------------------------- |
| Container-based     | Package and run the model-serving application           | Docker                                 |
| Kubernetes-based    | Orchestrate and scale containers                        | Kubernetes + KServe                    |
| Serverless          | Run inference without managing servers directly         | Cloud Functions / serverless endpoints |
| Managed ML platform | Provide an integrated managed model-hosting environment | SageMaker, Azure ML, Vertex AI         |

## 6. Deployment by Model Update Strategy

This classification describes how new model versions are trained, evaluated, approved, and introduced into production.

A deployed model is not necessarily permanent. Its performance can deteriorate because real-world data changes over time.

For example, a fraud detection model trained last year may become less effective because fraud patterns have changed.

### 6.1 Manual Model Updates

A developer or ML engineer manually deploys a new model version.

```
Train Model v2
      |
      v
Evaluate Model v2
      |
      v
Human Approval
      |
      v
Deploy Model v2
```

Advantages:

- Human control over production releases.
- Useful for high-risk models.
- Straightforward to implement.

Disadvantages:

- Slow release process.
- Requires manual intervention.
- Not suitable for frequent model updates.

Use cases: Credit scoring, healthcare models, and systems requiring formal approval.

### 6.2 Scheduled Model Updates

The model is retrained or updated according to a predefined schedule.

For example:

- Every night.
- Every week.
- Every month.
- Every quarter.

```
             Scheduler
                 |
                 v
          Collect New Data
                 |
                 v
            Train Model
                 |
                 v
          Evaluate Model
                 |
                 v
           Deploy Model
```

The deployment might be automatic after evaluation or require human approval.

Common technologies:

- Apache Airflow
- Kubeflow Pipelines
- MLflow
- Kubernetes CronJobs
- Cloud ML pipelines

Use cases:

- Daily demand forecasting.
- Weekly recommendation model updates.
- Monthly customer behavior models.

### 6.3 Continuous Model Deployment

New model versions are automatically deployed when they pass the required validation and approval criteria.

This is closely related to CI/CD, but the pipeline also handles model-specific validation.

```
       New Training Data
               |
               v
          Model Training
               |
               v
        Model Evaluation
               |
               v
         Quality Gates
               |
               v
        Automated Deployment
               |
               v
          Production
               |
               v
           Monitoring
```

For example, a new recommendation model is deployed automatically only if:

- Its recommendation quality exceeds a threshold.
- Its latency is within the required limit.
- It passes integration tests.
- It satisfies resource constraints.

Advantages:

- Faster model releases.
- Reduced manual work.
- Consistent deployment process.

Disadvantages:

- Requires reliable automated testing.
- Poor quality gates can introduce bad models.
- Requires mature monitoring and rollback mechanisms.

### 6.4 Champion–Challenger Deployment

The current production model is called the Champion.

A newer candidate model is called the Challenger.

The challenger is evaluated against the champion before replacing it.

```
             Production Model
                Champion
                   |
                   v
             Existing Results
                   |
                   |
New Model          |
Challenger         |
    |              |
    v              v
 Evaluation and Comparison
             |
             v
      Select Better Model
             |
       +-----+-----+
       |           |
       v           v
    Promote      Reject
   Challenger   Challenger
```

The comparison can use:

- Historical test datasets.
- Shadow traffic.
- A/B testing.
- Business performance metrics.

Example: Credit risk prediction

A bank currently uses `model-v1` to estimate credit risk. A new `model-v2` is trained using more recent data.

The challenger must demonstrate better predictive performance without violating business or regulatory constraints before becoming the new champion.

Use cases:

- Credit scoring.
- Fraud detection.
- Recommendation systems.
- High-impact business predictions.

### 6.5 Model Rollback

Rollback means returning to a previously deployed model version when the current version causes problems.

For example:

```
Production:
    Model v1
       |
       v
Deploy Model v2
       |
       v
Detect Problems
       |
       v
Rollback
       |
       v
Production:
    Model v1
```

Rollback can be triggered by:

- Increased prediction errors.
- Degraded model quality.
- Unexpected latency.
- High resource consumption.
- Application failures.
- Business performance deterioration.

Important: Rollback is not an alternative to deploying a model; it is a recovery mechanism used when a deployment or update goes wrong.

## 7. How These Strategies Work Together

The six classifications are not competing choices. They describe different dimensions of the same deployment architecture.

Consider a real-world example: deploying an LLM-powered customer support application.

| Dimension              | Selected strategy                                        |
| ---------------------- | -------------------------------------------------------- |
| Execution mode         | Online inference                                         |
| Hosting environment    | Cloud                                                    |
| Inference architecture | Remote, centralized inference                            |
| Release strategy       | Canary deployment                                        |
| Serving infrastructure | Docker + Kubernetes                                      |
| Model update strategy  | Scheduled retraining with champion–challenger evaluation |

The resulting architecture might look like this:

```
                  Customers
                      |
                      v
              Spring Boot Backend
                      |
                      v
                API Gateway
                      |
                      v
               Load Balancer
                      |
             +--------+--------+
             |                 |
             v                 v
        Model v1 (95%)    Model v2 (5%)
             |                 |
             v                 v
          vLLM Server       vLLM Server
             |                 |
             v                 v
           LLM v1            LLM v2
             |                 |
             +--------+--------+
                      |
                      v
                Monitoring
                      |
                      v
             Compare Performance
                      |
                      v
              Promote or Rollback
```

## 8. Quick Summary

| Classification         | Main question                        | Strategies                                                              |
| ---------------------- | ------------------------------------ | ----------------------------------------------------------------------- |
| Execution mode         | When does inference happen?          | Batch, Online, Streaming, Edge                                          |
| Hosting environment    | Where is the model hosted?           | On-premises, Cloud, Hybrid, Edge                                        |
| Inference architecture | Where and how is inference executed? | Remote, Local, Centralized, Distributed                                 |
| Release strategy       | How is a new version introduced?     | Recreate, Rolling, Blue-Green, Canary, Shadow, A/B Testing              |
| Serving infrastructure | What runs and manages the model?     | Containers, Kubernetes, Serverless, Managed ML Platforms                |
| Model update strategy  | How are model versions updated?      | Manual, Scheduled, Continuous Deployment, Champion–Challenger, Rollback |

My recommendation for your learning roadmap: Study these as six separate dimensions under Model Deployment Strategies. This avoids treating concepts such as Kubernetes, Canary Deployment, and Online Inference as alternatives to one another—they solve different problems and can be combined in one production system.
