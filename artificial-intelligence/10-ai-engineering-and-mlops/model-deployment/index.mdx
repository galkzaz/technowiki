# Model Deployment in AI and Machine Learning

Model Deployment is the process of taking a trained machine learning model and making it available for real-world use so that applications, users, or other systems can send it data and receive predictions or generated outputs.

In simple terms:

- Model Training: Teach the model using historical data.
- Model Evaluation: Check whether the model performs well enough.
- Model Deployment: Make the trained model available to users or applications.
- Model Inference: Use the deployed model to make predictions on new, unseen data.

Think of deployment as moving a model from the development environment into a production environment.

The world of creating, training, and serving
these models is heavily centered around Python, with very little involvement from
Java. While there are exceptions, such as TensorFlow for Java, most tooling and
frameworks are designed with Python in mind.

## 2. A practical example: Spam email detection

Imagine you are developing an AI system that detects spam emails.

During training, you provide thousands of emails labeled as:

- Spam
- Not spam

The model learns patterns that help it distinguish between the two categories.

After evaluation, you decide the model is good enough to use.

What happens next?

### Step 1: Package the trained model

The trained model is saved as an artifact containing the information needed to make predictions.

For example:

- Model architecture.
- Learned weights and parameters.
- Tokenizer or preprocessing configuration, if needed.
- Model configuration and dependencies.

For a traditional Python ML model, this might be a serialized file such as `spam_model.pkl`.

For a neural network, it could be a model checkpoint containing millions or billions of learned parameters.

### Step 2: Create a prediction service

You need a way for other applications to communicate with the model.

One common approach is to expose the model through a REST API.

For example:

```
POST /api/predict
```

The application sends an email:

```
{
  "email": "Congratulations! You won a free prize."
}
```

The model processes the email and returns:

```
{
  "prediction": "SPAM",
  "confidence": 0.98
}
```

### Step 3: Deploy the service

You can run the model service on:

- A cloud server (AWS, Azure, Google Cloud).
- A container using Docker.
- A Kubernetes cluster.
- An on-premises server inside your organization.
- An edge device, such as a mobile phone or IoT device.

### Step 4: Allow applications to use the model

Consider a Java Spring Boot application that handles incoming emails.

The architecture could look like this:

```
                  User
                    |
                    v
          Java Spring Boot App
                    |
                    | HTTP REST Request
                    v
           AI Model API Service
                    |
                    v
             Trained ML Model
                    |
                    v
              Prediction
              (SPAM, 98%)
                    |
                    v
           Java Spring Boot App
                    |
                    v
              Application
```

Notice something important: the Java application does not need to implement the machine learning algorithm itself.

It simply sends data to the model service and receives predictions.

This is a common architecture in enterprise applications and microservices.

## 3. Different Model Deployment Strategies

There are several ways to deploy a model, depending on how and when predictions are needed.

### A. Batch Deployment

Scheduled predictions

Instead of predicting each request immediately, the system collects a large amount of data and processes it periodically.

For example, a bank wants to predict the risk of customer churn.

Every night:

1. Collect customer activity data.
2. Send the data to the trained model.
3. Generate churn predictions for all customers.
4. Store the results in a database.
5. Make the results available to business applications.

```
Customer Data
      |
      v
  Database
      |
      v
Scheduled Batch Job
      |
      v
  ML Model
      |
      v
Predictions
      |
      v
Results Database
```

Suitable for:

- Daily sales predictions.
- Customer churn analysis.
- Monthly financial forecasting.
- Periodic recommendation generation.

### B. Real-Time Deployment (Online Inference)

Immediate predictions

The model receives an individual request and returns a prediction immediately.

For example, an online payment system wants to detect fraudulent transactions.

```
Payment Request
       |
       v
  Backend API
       |
       v
  Fraud Detection Model
       |
       v
 Prediction: FRAUD
       |
       v
 Reject Payment
```

The prediction happens as part of the application's request-response workflow.

Suitable for:

- Fraud detection.
- Spam detection.
- Product recommendations.
- Image classification.
- Chatbots and LLM applications.

### C. Streaming Deployment

Continuous data processing

The model continuously receives data from a stream rather than waiting for a scheduled batch or an individual synchronous request.

For example, a manufacturing company monitors machines using IoT sensors.

```
IoT Sensors
     |
     v
Kafka / Event Stream
     |
     v
ML Model
     |
     v
Anomaly Detection
     |
     v
Alert System
```

The model continuously analyzes sensor readings and identifies abnormal behavior.

Suitable for:

- IoT monitoring.
- Network intrusion detection.
- Real-time fraud monitoring.
- Industrial predictive maintenance.

### D. Edge Deployment

The model runs directly on the device instead of sending every request to a remote server.

For example, a smartphone can run an image recognition model locally.

```
Camera
   |
   v
Mobile Device
   |
   v
Local ML Model
   |
   v
Image Classification
```

Suitable for:

- Mobile applications.
- Autonomous vehicles.
- Smart cameras.
- IoT devices.
- Applications requiring low latency or offline operation.

### Comparison

| Strategy  | How it works                          | Example                  |
| --------- | ------------------------------------- | ------------------------ |
| Batch     | Processes collected data periodically | Daily churn prediction   |
| Online    | Predicts for each incoming request    | Fraud detection          |
| Streaming | Continuously processes events         | IoT anomaly detection    |
| Edge      | Runs locally on the device            | Mobile image recognition |

These strategies are not mutually exclusive. An organization can use several of them for the same model.

## 4. What happens during Model Deployment?

Deployment involves more than simply copying a model file to a server.

There are several important activities.

| Activity                    | Description                                                     |
| --------------------------- | --------------------------------------------------------------- |
| Model packaging             | Prepare the model and its dependencies.                         |
| Model serving               | Provide an interface for applications to access the model.      |
| Infrastructure provisioning | Allocate CPU, RAM, GPU, and storage.                            |
| API integration             | Allow applications to send input and receive predictions.       |
| Scaling                     | Handle increasing numbers of prediction requests.               |
| Security                    | Protect the model API and its data.                             |
| Monitoring                  | Track model quality, latency, errors, and resource consumption. |
| Versioning                  | Manage different model versions and releases.                   |

### Model Versioning

Suppose you initially deploy:

```
Spam Detection Model v1
```

After collecting more training data, you train a better model:

```
Spam Detection Model v2
```

You can deploy v2 without immediately removing v1.

This allows you to compare their performance and switch back if the new model causes problems.

Two common deployment techniques are:

- Canary deployment: Send a small percentage of requests to the new model before gradually increasing traffic.
- Blue-green deployment: Maintain two production environments and switch traffic from the old version to the new one.

## 5. Model Monitoring after Deployment

Deployment does not mean the machine learning lifecycle is finished.

A model can perform well during evaluation but become less accurate after deployment.

Why?

Because real-world data can change over time.

For example, a spam detection model trained in 2025 might encounter new spam techniques in 2026.

This introduces two important concepts:

Data drift: The distribution or characteristics of incoming data change compared with the training data.

Concept drift: The relationship between input data and the correct prediction changes.

For example:

- Data drift: The vocabulary and structure of incoming spam emails change.
- Concept drift: A behavior that previously indicated fraud is no longer a reliable indicator of fraud.

Monitoring helps detect these changes.

A typical feedback loop looks like this:

```
       New Data
           |
           v
    Deployed Model
           |
           v
      Predictions
           |
           v
   Monitor Performance
           |
           v
   Detect Model Issues
           |
           v
    Collect New Data
           |
           v
      Retraining
           |
           v
    Evaluate New Model
           |
           v
     Redeployment
```

This continuous process is one of the main reasons MLOps exists.

## 6. Deploying Large Language Models (LLMs)

The same deployment principles apply to LLMs such as GPT, Llama, and Mistral, but LLM deployment introduces additional infrastructure requirements.

For example, imagine deploying a Llama model to provide an AI chatbot.

```
       User
         |
         v
    Chat Application
         |
         v
      Backend API
         |
         v
    LLM Inference Server
         |
         v
      Llama Model
         |
         v
    Generated Response
         |
         v
       User
```

Some additional considerations are:

| Consideration       | Explanation                                                         |
| ------------------- | ------------------------------------------------------------------- |
| GPU requirements    | Large models may require GPUs with substantial VRAM.                |
| Quantization        | Reduce model precision to decrease memory requirements.             |
| Model serving       | Use specialized inference engines such as vLLM or Hugging Face TGI. |
| Token generation    | Generate responses token by token.                                  |
| Concurrent requests | Handle multiple users efficiently.                                  |
| Context management  | Manage conversation history and context windows.                    |
| Batching            | Process multiple requests together to improve GPU utilization.      |

For example, deploying a 7-billion-parameter model using FP16 requires approximately 14 GB just for its model weights. Additional memory is needed for inference, including the KV cache and runtime overhead.

This makes LLM deployment an important area of infrastructure engineering.

## 7. Relationship between Model Deployment and MLOps

You can think of Model Deployment as one stage within the broader MLOps discipline.

MLOps applies software engineering and DevOps principles to the machine learning lifecycle.

| DevOps                  | MLOps                             |
| ----------------------- | --------------------------------- |
| Application development | Model development and training    |
| Application testing     | Model evaluation and validation   |
| Application deployment  | Model deployment                  |
| Application monitoring  | Model and data monitoring         |
| Application updates     | Model retraining and redeployment |
| CI/CD pipelines         | ML CI/CD and continuous training  |

For example, an MLOps pipeline could automatically:

1. Collect new training data.
2. Train a new model.
3. Evaluate its performance.
4. Compare it against the currently deployed model.
5. Deploy it if it meets predefined requirements.
6. Monitor its production performance.

This makes model deployment part of an automated and repeatable process rather than a manual operation.

## 9. Putting everything together

Let's use a real-world e-commerce recommendation system as an example.

## Model Deployment Workflow (End-to-End Lifecycle)

Model deployment is not just uploading a trained model to a server. It is a sequence of engineering steps that takes a model from the development environment into production, makes it accessible to applications, and ensures it remains reliable, scalable, and maintainable.

A typical model deployment workflow looks like this:

### End-to-end model deployment workflow

![](/docs/assets/artificial-intelligence/10-ai-engineering-and-mlops/model-deployment/End-to-end-model-deployment-workflow.png)
{/* 1

Model preparation

Select, validate, and package the trained model.

2

Model optimization

Reduce resource requirements and improve inference performance.

3

Model serving development

Create the interface through which applications access the model.

4

Infrastructure provisioning

Prepare compute, storage, networking, and runtime environments.

5

Deployment and release

Deploy the model and expose it to consumers.

6

Testing and validation

Verify correctness, performance, security, and reliability.

7

Scaling and traffic management

Handle changing workloads and request volumes.

8

Monitoring and maintenance

Track model behavior, infrastructure, and prediction quality.

9

Model updates and rollback

Release improved models or restore previous versions.

Continuous improvement: retraining, redeployment, and monitoring */}

Not every project needs nine separate stages. Some can be combined, and optimization or scaling may be unnecessary for small applications.

Let's examine each step and the available options.

### 1. Model Preparation

Input: Trained model

The first step is to prepare the trained model so it can be moved from the training environment to the production environment.

#### 1.1 Select the model

If you have trained multiple models or experimented with different hyperparameters, select the model that satisfies your requirements.

For example:

| Model   | Accuracy | Inference latency |
| ------- | -------- | ----------------- |
| Model A | 92%      | 20 ms             |
| Model B | 95%      | 80 ms             |
| Model C | 94%      | 35 ms             |

Model B has the highest accuracy, but Model C might be a better production choice if response time is important.

#### 1.2 Save the model artifact

A model artifact contains the information needed to reconstruct or execute the trained model.

Different frameworks use different formats:

| Framework    | Common model formats                                 |
| ------------ | ---------------------------------------------------- |
| Scikit-learn | Pickle, Joblib                                       |
| TensorFlow   | SavedModel, Keras                                    |
| PyTorch      | State Dict, TorchScript, ONNX                        |
| Hugging Face | Safetensors, model configuration and tokenizer files |
| ONNX Runtime | ONNX                                                 |

For example, a PyTorch model might be saved as:

```
torch.save(model.state_dict(), "model.pth")
```

#### 1.3 Store and version the artifact

You need a reliable location to store the model and identify its version.

Options include:

- Local filesystem: development and experimentation.
- Object storage: AWS S3, Azure Blob Storage, Google Cloud Storage.
- Model registries: MLflow Model Registry, cloud provider model registries.
- Artifact repositories: JFrog Artifactory, Nexus Repository.

A model registry is especially useful because it can maintain model versions, metadata, evaluation results, and deployment status.

Output: A versioned, validated model artifact ready for deployment.

### 2. Model Optimization

Goal: Improve inference efficiency

A trained model might be too large or slow for the production environment.

Optimization reduces resource consumption or improves inference performance while maintaining acceptable prediction quality.

Not every model requires optimization.

#### Available optimization techniques

| Technique              | What it does                                                     | Main benefit                                   |
| ---------------------- | ---------------------------------------------------------------- | ---------------------------------------------- |
| Quantization           | Reduces numerical precision, e.g. FP32 to INT8                   | Less memory and potentially faster inference   |
| Pruning                | Removes less important weights or connections                    | Smaller model and potentially faster execution |
| Knowledge distillation | Trains a smaller student model to imitate a larger teacher model | Smaller, cheaper model                         |
| Operator fusion        | Combines multiple operations into fewer operations               | Faster execution                               |
| Compilation            | Optimizes model execution for a target hardware platform         | Better hardware utilization                    |
| Batching               | Processes multiple inference requests together                   | Higher throughput                              |
| Caching                | Reuses previously computed results                               | Avoids repeated computation                    |

For example:

```
Original Model
   7 Billion Parameters
   FP16
      |
      v
Quantization
      |
      v
Optimized Model
   7 Billion Parameters
   INT4
```

The parameter count remains the same, but the memory needed to represent the weights is significantly reduced.

#### Tools and technologies

- ONNX: Model interoperability and execution optimization.
- TensorRT: GPU inference optimization.
- OpenVINO: Model optimization and inference.
- PyTorch: Model compilation and quantization.
- llama.cpp: Efficient local LLM inference.

Output: An optimized model artifact, if optimization is required.

### 3. Model Serving Development

Goal: Make the model accessible

A model file by itself does not provide a convenient way for applications to use it.

You need a serving mechanism that loads the model, receives input, performs inference, and returns results.

There are several approaches.

#### Option A: REST API

Create an HTTP endpoint that accepts requests and returns predictions.

Example:

```
POST /api/predict
```

Request:

```
{
  "temperature": 35,
  "humidity": 70
}
```

Response:

```
{
  "prediction": "HIGH_RISK",
  "confidence": 0.94
}
```

Implementation options:

- Python FastAPI.
- Python Flask.
- Django REST Framework.
- Java Spring Boot.
- Node.js Express.

This is a common choice when integrating ML models with conventional backend applications.

#### Option B: gRPC

Instead of HTTP REST with JSON, expose the model through gRPC.

gRPC uses Protocol Buffers for defining service contracts and serializing messages.

Advantages:

- Efficient binary communication.
- Strongly defined service contracts.
- Streaming support.
- Useful for communication between microservices.

#### Option C: Specialized Model Serving Frameworks

Instead of writing the serving infrastructure yourself, use a framework designed for ML inference.

| Framework                      | Main purpose                               |
| ------------------------------ | ------------------------------------------ |
| TensorFlow Serving             | Serving TensorFlow models                  |
| TorchServe                     | Serving PyTorch models                     |
| NVIDIA Triton Inference Server | Serving multiple frameworks and GPU models |
| BentoML                        | Packaging and serving ML models            |
| KServe                         | Kubernetes-native model serving            |
| vLLM                           | High-throughput LLM serving                |

#### Option D: Direct library integration

Load the model directly inside the application rather than exposing it as a separate service.

For example:

```
Java Application
      |
      v
Python Model Service
```

Alternatively, when the model runtime supports Java:

```
Java Application
      |
      v
ONNX Runtime Java API
      |
      v
Model
```

This can be useful for small applications or edge environments.

Output: A model-serving application or service that can accept inference requests.

### 4. Infrastructure Provisioning

Goal: Prepare the production environment

Now you need to decide where the model-serving application will run and what resources it needs.

This includes compute, memory, storage, networking, and runtime dependencies.

#### 4.1 Choose the deployment environment

| Option       | Description                   | Typical use                            |
| ------------ | ----------------------------- | -------------------------------------- |
| On-premises  | Run on company-owned servers  | Organizations with strict data control |
| Cloud        | Run on cloud infrastructure   | Flexible production workloads          |
| Hybrid cloud | Combine on-premises and cloud | Enterprise environments                |
| Edge         | Run on local devices          | IoT, mobile, autonomous systems        |

#### 4.2 Choose compute resources

Depending on the model, you can use:

| Resource          | When to use                                       |
| ----------------- | ------------------------------------------------- |
| CPU               | Traditional ML models and smaller neural networks |
| GPU               | Deep learning and LLM inference                   |
| TPU               | Specialized tensor computation                    |
| Edge accelerators | Inference on constrained devices                  |

For example, a small spam classification model might run comfortably on a CPU, whereas a large LLM might require one or more GPUs.

#### 4.3 Choose the infrastructure platform

There are several options:

Virtual machines (VMs)

- AWS EC2.
- Azure Virtual Machines.
- Google Compute Engine.

You manage the operating system, runtime, dependencies, and deployment.

Containers

- Docker.
- Podman.

Package the serving application and its dependencies into a portable container.

Container orchestration

- Kubernetes.
- Amazon EKS.
- Azure AKS.
- Google GKE.

Manage multiple containers, scheduling, scaling, networking, and availability.

Managed ML platforms

- AWS SageMaker.
- Azure Machine Learning.
- Google Vertex AI.

These platforms provide managed infrastructure and ML-specific deployment capabilities.

#### 4.4 Prepare the runtime environment

Install or configure:

- Required programming language runtime.
- ML framework and dependencies.
- Model-serving framework.
- GPU drivers and CUDA, when applicable.
- Environment variables and configuration.
- Credentials and access to model artifacts.

Output: A production environment capable of running the model-serving application.

### 5. Model Deployment and Release

Goal: Make the model available in production

At this stage, you deploy the serving application and its model into the selected infrastructure.

There are different deployment approaches.

#### 5.1 Deployment options

| Approach                | Description                                   | Example                        |
| ----------------------- | --------------------------------------------- | ------------------------------ |
| Manual deployment       | Engineers deploy the application manually     | Copy files and start a service |
| Script-based deployment | Deployment automated using scripts            | Bash, Python, Ansible          |
| Container deployment    | Deploy a packaged container                   | Docker                         |
| Orchestrated deployment | Deploy and manage containers automatically    | Kubernetes                     |
| Managed deployment      | Cloud provider manages serving infrastructure | SageMaker endpoint             |

#### 5.2 Deployment release strategies

You also need to decide how to introduce a new model version into production.

A. Recreate deployment

Stop the old version, then start the new version.

```
Model v1: STOP
     |
     v
Model v2: START
```

Simple, but may introduce downtime.

B. Rolling deployment

Gradually replace old instances with new ones.

```
Instance 1: v1 → v2
Instance 2: v1 → v2
Instance 3: v1 → v2
```

Reduces downtime, assuming sufficient healthy capacity.

C. Blue-green deployment

Maintain two environments.

```
         Traffic
            |
       Load Balancer
         /       \
     Blue         Green
     v1            v2
    Active        Ready
```

Switch traffic to green after validation.

D. Canary deployment

Send a small percentage of production traffic to the new version.

```
         Incoming Requests
                |
           Load Balancer
             /       \
         90%           10%
          |             |
         v1            v2
```

Gradually increase traffic if the new model performs well.

Output: A deployed model that is accessible in the production environment.

### 6. Testing and Validation

Goal: Verify production readiness

A model that works in the development environment might fail in production because of differences in configuration, dependencies, hardware, data, or workload.

Testing should happen before releasing the model to all users and continue after deployment.

#### Types of testing

| Test                  | What it verifies                                                |
| --------------------- | --------------------------------------------------------------- |
| Functional testing    | Does the model return valid predictions?                        |
| Integration testing   | Can applications communicate with the model service?            |
| Contract testing      | Does the API follow the expected request/response contract?     |
| Performance testing   | Can it meet latency and throughput requirements?                |
| Load testing          | How does it behave under expected traffic?                      |
| Stress testing        | What happens under extreme traffic?                             |
| Security testing      | Are authentication, authorization, and data protection working? |
| Reliability testing   | Does the service recover from failures?                         |
| Model quality testing | Does prediction quality meet acceptance criteria?               |

#### Example

Suppose you deploy a fraud detection model.

Your production acceptance criteria might be:

| Metric               | Requirement           |
| -------------------- | --------------------- |
| Prediction latency   | Less than 100 ms      |
| Throughput           | 1,000 requests/second |
| Precision            | At least 95%          |
| Service availability | 99.9%                 |

These are illustrative requirements, not universal thresholds.

You should validate both the model's prediction quality and the serving system's operational performance.

Output: Evidence that the deployed model meets production requirements.

### 7. Scaling and Traffic Management

Goal: Handle changing workloads

Imagine your model initially receives 100 requests per minute.

After your application becomes popular, it receives 100,000 requests per minute.

One model-serving instance might no longer be sufficient.

You need to scale the deployment and manage incoming traffic.

#### 7.1 Scaling options

| Strategy           | Description                                                    |
| ------------------ | -------------------------------------------------------------- |
| Vertical scaling   | Increase CPU, RAM, or GPU resources on an existing instance    |
| Horizontal scaling | Add more model-serving instances                               |
| Auto-scaling       | Automatically increase or decrease instances based on workload |
| Model parallelism  | Distribute one model across multiple devices                   |
| Data parallelism   | Process different batches of requests using multiple devices   |

#### 7.2 Traffic management options

- Load balancing: Distribute requests among multiple serving instances.
- Request batching: Combine multiple inference requests into one execution batch.
- Rate limiting: Restrict excessive requests.
- Caching: Reuse previously computed predictions when appropriate.
- Queuing: Buffer requests when processing capacity is temporarily insufficient.

Example architecture:

```
                Clients
                   |
                   v
              API Gateway
                   |
                   v
              Load Balancer
               /    |    \
              /     |     \
             v      v      v
          Model  Model  Model
          v1     v1     v1
          |       |      |
          +-------+------+
                  |
                  v
             Predictions
```

Output: A deployment capable of handling the expected production workload.

### 8. Monitoring and Maintenance

Goal: Maintain production reliability and model quality

Once deployed, you need continuous monitoring.

There are two different aspects to monitor: the serving infrastructure and the ML model itself.

#### 8.1 Infrastructure monitoring

Monitor the health and performance of the serving system.

| Metric          | What it tells you                                |
| --------------- | ------------------------------------------------ |
| CPU utilization | How much CPU is being consumed                   |
| GPU utilization | How much GPU processing capacity is being used   |
| Memory usage    | Whether the service is approaching memory limits |
| Request latency | How long inference requests take                 |
| Throughput      | Number of requests processed per second          |
| Error rate      | Percentage of failed requests                    |
| Availability    | Whether the service is accessible                |

Tools include:

- Prometheus: Metrics collection.
- Grafana: Dashboards and visualization.
- OpenTelemetry: Observability instrumentation.
- Datadog: Infrastructure and application monitoring.

#### 8.2 Model monitoring

Infrastructure monitoring alone is insufficient.

Your service might be healthy, responding quickly, and returning valid predictions while the model itself is producing increasingly inaccurate results.

Monitor:

| Metric                  | What it tells you                                                   |
| ----------------------- | ------------------------------------------------------------------- |
| Prediction distribution | Whether predictions are changing unexpectedly                       |
| Data drift              | Whether incoming input data differs from training data              |
| Concept drift           | Whether relationships between inputs and targets have changed       |
| Accuracy                | Whether predictions are correct when ground truth becomes available |
| Precision and recall    | How well the model identifies relevant cases                        |
| Confidence distribution | Whether prediction confidence changes unexpectedly                  |

ML-specific monitoring options include:

- Evidently AI.
- WhyLabs.
- MLflow.
- Custom monitoring pipelines.

Output: Production visibility into system health and model behavior.

### 9. Model Updates, Retraining, and Rollback

Goal: Keep the model effective over time

Eventually, the deployed model may need improvement.

For example:

- New training data becomes available.
- Model accuracy decreases.
- User behavior changes.
- A better model architecture becomes available.
- Business requirements change.
- Security or performance improvements are needed.

There are several ways to update a model.

#### 9.1 Model update strategies

| Strategy                   | Description                                                                    |
| -------------------------- | ------------------------------------------------------------------------------ |
| Manual retraining          | Engineers explicitly initiate training                                         |
| Scheduled retraining       | Retrain at predefined intervals                                                |
| Event-triggered retraining | Retrain when a condition is met, such as detected drift                        |
| Continuous training        | An automated pipeline regularly processes new data and produces updated models |

#### 9.2 Model promotion

A newly trained model should not automatically replace the existing production model.

A typical workflow:

```
         New Training Data
                 |
                 v
          Train Model v2
                 |
                 v
          Evaluate Model
                 |
                 v
         Compare v1 and v2
                 |
          +------+------+
          |             |
       Pass?           Fail
          |             |
          v             v
     Deploy v2      Keep v1
          |
          v
     Monitor v2
          |
          v
     Rollback if
     problems occur
```

#### 9.3 Rollback

Suppose v2 has a serious performance issue after deployment.

You can restore v1 from the model registry and redirect production traffic to it.

This is why model versioning and deployment strategies are important.

Output: An updated, validated model or a restored previous version.

## 12. Important distinction: Model Deployment vs. MLOps Lifecycle

One final distinction is important for organizing your AI/ML studies.

Model deployment workflow focuses on getting a trained model into production and operating it reliably.

MLOps lifecycle is broader. It covers the entire process, including:

1. Data collection and preparation.
2. Experimentation and model development.
3. Model training and evaluation.
4. Model deployment.
5. Model monitoring.
6. Model retraining and continuous improvement.

In other words, model deployment is a major part of MLOps, not the entire MLOps lifecycle.

My recommendation for your study roadmap: Organize this topic under:

```
MLOps
├── ML Lifecycle
│   ├── Data Preparation
│   ├── Model Development
│   ├── Model Training
│   ├── Model Evaluation
│   └── Model Deployment
│       ├── Model Packaging
│       ├── Model Optimization
│       ├── Model Serving
│       ├── Infrastructure Provisioning
│       ├── Deployment Strategies
│       ├── Testing and Validation
│       ├── Scaling
│       ├── Monitoring
│       └── Model Updates and Rollback
├── ML CI/CD
├── ML Infrastructure
├── Model Registry
└── Continuous Training (CT)
```

This organization separates the general ML lifecycle from the engineering practices and technologies used to implement it.
